```
MySQL(3306) → Redis(6379) → Nacos(8848) → RabbitMQ(5672) → ES(9200) → Seata(8091)
→ SkyWalking(启动 start-skywalking.bat) → Sentinel Dashboard(IDEA 8090)
```

### 2. 确保所有微服务启动（IDEA 按顺序启动）

```
mall-resource → mall-ams → mall-ums → mall-product
→ mall-front → mall-order → mall-search → mall-ai
→ mall-seckill → mall-sso → mall-gateway-server
```

启动 mall-seckill 后 Flyway 会自动执行 `V5__seckill_message_retry.sql` 建表。手动验证：

```sql
SHOW TABLES FROM cs_mall_seckill LIKE 'seckill_message_retry';
```

```sql
SELECT id, spu_id, start_time, end_time FROM cs_mall_seckill.seckill_spu;
-- 应显示 2026-01-01 ~ 2026-12-31
```

### 5. 同步商品数据到 ES

```bash
curl -X POST http://localhost:10010/ai/sync
```

## 二、JMeter 压测联合演示测试

**目的**：100 并发 → Sentinel QPS=10 限流 → SkyWalking QPS 尖峰 → JMeter 聚合报告。

### 步骤

1. **启动 JMeter**
   ```bash
   D:\Jmeter\apache-jmeter-5.6.3\bin\jmeter.bat -t D:\java\csmall\deploy\jmeter\csmall-seckill-demo.jmx
   ```
   或双击 `D:\java\csmall\deploy\jmeter\run-demo.bat`

2. **在 Sentinel Dashboard 添 加流控规则**
   - 打开 http://localhost:8090（sentinel/sentinel）
   - 先在浏览器手动发一次秒杀请求（让 Sentinel 感知到资源）
   - 点击「簇点链路」→ 找到 mall-seckill → 资源名「秒杀订单提交」
   - 点击「流控」→ 新增：
     - 阈值类型：QPS
     - QPS 阈值：**10**
     - 流控效果：快速失败

3. **打开 SkyWalking UI**（http://localhost:8088）— 切到服务仪表盘，选择 mall-seckill

4. **在 JMeter GUI 中点击绿色三角形启动压测**

5. **观察三个窗口**：
   - JMeter「察看结果树」：绿色=200(成功)，红色=限流拦截
   - Sentinel Dashboard：QPS 曲线尖峰 → 限流生效
   - SkyWalking UI：mall-seckill 的 QPS 从 0 飙升

### 预期结果

- [ ] JMeter 聚合报告：100 请求发出，约 10 个 success，约 90 个 blocked
- [ ] 成功请求响应包含 `"state":200`
- [ ] 限流请求响应包含 `"服务器忙"`
- [ ] Sentinel Dashboard 实时 QPS 曲线有尖峰
- [ ] SkyWalking mall-seckill QPS 曲线同步上升
- [ ] 无任何请求报 Connection Refused

### 故障排查

| 问题 | 检查 |
|------|------|
| 全部 success 无限流 | Sentinel 流控规则未添加或资源名不匹配（应为「秒杀订单提交」） |
| 全部 blocked | 检查 Redis 中是否有库存和随机码，秒杀时间窗口是否有效 |
| JMeter 提取不到 token | 确认 mall-sso 已启动，testuser1/123456 账号存在 |
| JMeter 提取不到 randCode | 确认 mall-seckill 已启动，Redis 中有 `mall:seckill:spu:url:rand:code:1` |
| 全部"重复提交" | 确认请求体 contactName 用了 `${__threadNum}`（每个线程不同） |

## 四、秒杀 MQ 降级测试

**目的**：验证 MQ 不可用时 Redis 库存能被正确补偿，MQ 恢复后定时任务能重试成功。

### 4.1 正常流程测试（MQ 可用）

```bash
# 1. 确认 RabbitMQ 正常运行
# 2. 确认 Redis 中有秒杀库存和随机码
# 3. 发起秒杀请求（通过前端或 curl）
# 4. 检查消息表
```

```sql
-- 消息表应有记录且 status=1（已发送）
SELECT * FROM cs_mall_seckill.seckill_message_retry ORDER BY create_time DESC LIMIT 5;
```

### 4.2 MQ 不可用测试（核心降级场景）

```bash
# 1. 停止 RabbitMQ
rabbitmqctl stop
# 或：在 Windows 服务中停止 RabbitMQ

# 2. 记录当前 Redis 库存
redis-cli GET "mall:seckill:sku:stock:1"
# 假设结果为 50

# 3. 发起一次秒杀请求
# 预期：返回「系统繁忙，请稍后重试」

# 4. 再次查看 Redis 库存
redis-cli GET "mall:seckill:sku:stock:1"
# 预期：仍是 50（未被扣减，补偿成功！）
```

```sql
-- 消息表应有记录
-- 如果是在 @GlobalTransactional 内失败，消息记录也被回滚（status=NULL/不存在）
-- 如果是之前 MQ 正常时留下的：status=0 表示待重试
SELECT * FROM cs_mall_seckill.seckill_message_retry;
```

### 4.3 MQ 恢复后重试测试

```bash
# 1. 启动 RabbitMQ
rabbitmqctl start_app
# 或：在 Windows 服务中启动 RabbitMQ

# 2. 等待 5-10 秒（定时任务每 5 秒执行一次）

# 3. 检查消息表
```

```sql
-- 待重试的消息应变为 status=1（已发送）
SELECT * FROM cs_mall_seckill.seckill_message_retry WHERE status = 0;
-- 预期：0 条记录
```

### 4.4 表结构验证

```sql
-- 确认 Flyway 建表成功
SHOW CREATE TABLE cs_mall_seckill.seckill_message_retry;
```

### 预期结果

- [ ] MQ 正常时，秒杀成功，消息表有记录且 status=1
- [ ] MQ 停止时，秒杀返回「系统繁忙，请稍后重试」
- [ ] MQ 停止时，Redis 库存恢复原值（INCR 补偿成功）
- [ ] MQ 停止时，防重标记恢复（用户可重试购买）
- [ ] MQ 恢复后，定时任务将 status=0 的消息重发成功
- [ ] `seckill_message_retry` 表通过 Flyway 自动创建

### 故障排查

| 问题 | 检查 |
|------|------|
| 表不存在 | 检查 Flyway 是否执行：`SELECT * FROM flyway_schema_history WHERE version='5';` |
| Redis 库存未恢复 | 检查 SeckillServiceImpl 日志是否有 "MQ发送失败...补偿Redis库存" |
| 定时任务未执行 | 检查 mall-seckill 启动日志中是否有 `@EnableScheduling` 相关提示 |
| 重试不成功 | 检查 MessageRetryTask 日志，确认 RabbitMQ 已完全启动 |
