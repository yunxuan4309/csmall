# 企业级商品管理升级计划（讨论稿）

> **日期**：2026-08-03
> **状态**：商品基础 CRUD 已打通（列表/新增/编辑/删除/上下架/图片上传，含期间修复的多个历史 bug），企业级升级待启动
> **背景**：当前商品管理已完成基础 CRUD。以下规划将其升级为"企业级"，核心两块：**模板生成 SKU** + **相册管理图片**。

---

## 一、目标与愿景

把"能增删改查商品"升级为"能像真实电商后台一样管理商品"：

1. **模板 → 规格 → SKU**：商品绑定属性模板后，按模板定义的规格维度填写值，系统自动生成 SKU 组合（如 手机模板：存储×颜色 → 6 个 SKU），每个 SKU 单独定价、库存。
2. **相册管理图片**：商品图片通过"相册"统一管理（上传→入库 pms_picture→关联相册），SPU 关联相册，图片可复用、可管理。
3. **完整的商品详情**：富文本详情、规格参数展示、相关推荐等。

**结论**：表结构是为企业级设计的，只缺"业务实现"。

## 二点五、已知技术债（2026-08-03 商品 CRUD 测试中发现）

mall-product 的 mapper 插入 id 有两种方式，**以下 9 个用了 `useGeneratedKeys` 依赖自增，但对应表 id 全部非自增（雪花 ID），一旦调用必报 `Field 'id' doesn't have a default value`**：

|--------|------|
| `SpuDetailMapper` | ✅ **已修**（新增 SPU 在用它，改成了显式插 id） |
| `BrandMapper` | ⚠️ 待修（品牌 CRUD 前端占位，暂未暴露） |
| `CategoryMapper` | ⚠️ 待修（分类 CRUD 前端占位，暂未暴露） |
| `AlbumMapper` | ⚠️ 待修（相册系统休眠） |
| `PictureMapper` | ⚠️ 待修（相册系统休眠） |
| `AttributeMapper` | ⚠️ 待修（属性系统休眠） |
| `AttributeTemplateMapper` | ⚠️ 待修（模板系统休眠） |
| `BrandCategoryMapper` | ⚠️ 待修（关联表） |
| `CategoryAttributeTemplateMapper` | ⚠️ 待修（关联表） |
| `SkuSpecificationMapper` | ⚠️ 待修（SKU 规格系统休眠） |

**修复方式**（与 SpuMapper/SkuMapper 一致）：XML 改为显式插 id 列 + Service 层 `setId(IdWorker.getId())`。
**建议**：作为升级前置，在做对应功能（品牌/分类 CRUD、模板生成 SKU、相册）时一并修复。

### ② SpuUpdateDTO 与 SpuMapper.update XML 已修复（2026-08-03）

- `SpuUpdateDTO` 补了 `listPrice/stock/stockThreshold/unit/pictures/keywords/tags` 字段（原来编辑改价格/传图发不进去）
- `updateById` 补了 `spu.setId(id)`（原来 id=null 导致整个 UPDATE 被跳过，报 "SQL String cannot be empty"）
- `SpuMapper.xml` 的 insert/update 共 7 处 `spuQuery.xxx` 前缀错误已修正（参数是 Spu 实体，不是 SpuQuery）

### ③ 图片删除无后端支撑

`pms_picture` 无删除端点，前端移除图片只删引用、物理文件残留 `csmall-upload/`（孤儿文件无害）。升级相册系统时需补删除接口。

## 三、两大升级块

### 块 A：模板生成 SKU

**目标**：选模板 → 填规格值 → 自动生成 SKU 组合 → 逐个定价/库存。

**后端**：
1. **属性/模板值 CRUD**：管理 `pms_attribute`（模板有哪些属性）和 `pms_attribute_template_value`（每个属性的可选值），填充测试数据
2. **SKU 生成服务**：给定模板 + 已选属性值，笛卡尔积生成 SKU（如 存储{128,256}×颜色{黑,白}=4 个 SKU）
3. **SKU CRUD 接口**：价格/库存/条形码/图片
4. **SPU 冗余字段同步**：listPrice=min(SKU价格)、stock=sum(SKU库存)（已有 synchroniseStock/synchronisePrice 可复用）

**前端**：
- 商品创建向导：基本信息 → 选模板 → 按模板属性填值 → 生成 SKU 矩阵表格（填价/库存）→ 完成
- SKU 列表/编辑界面

### 块 B：相册管理图片

**目标**：图片走"相册"体系，替代/兼容现在的 `spu.pictures` JSON。

**后端**：
1. **相册 CRUD**：新建/删除相册（每个 SPU 一个默认相册）
2. **图片 CRUD**：上传 → 存文件 + 写 `pms_picture` 记录 → 关联相册
3. **SPU 关联相册**：`spu.album_id` 指向相册
4. **老数据迁移**：现有 `spu.pictures` JSON 迁移到相册/图片表，或做"双读兼容"

**前端**：
- 相册管理 UI（图片墙、增删）
- 商品表单的图片选择器改为从相册选 / 上传进相册

## 五、主要风险

1. **数据迁移（最大风险）**：现有 `spu.pictures` JSON → 相册/图片表，需要迁移脚本 + 双读兼容，否则老商品图片会丢
2. **SKU 生成算法**：属性组合的正确性（去重、空值处理、SKU 编号生成）
3. **SKU 与秒杀联动**：秒杀 SKU 用的 `seckill_sku` 关联 `sku_id`，改 SKU 体系要保证秒杀不受影响
4. **部署面大**：涉及 mall-product + mall-front + 前端，需多次重建重启
5. **与现有简化 CRUD 并存**：新向导上线前，现有 SpuList 的简化新增/编辑仍要可用

## 六、建议执行顺序

1. **先稳定现状**：完成当前 CRUD 的测试与修复（进行中）
2. **块 A 先行**（模板→SKU）：后端属性模型 + SKU 生成是最核心、最有"企业级感"的部分
3. **块 B 随后**（相册）：图片系统独立性强，可与块 A 并行或紧随
4. **迁移最后**：数据迁移放功能稳定后
5. **每块结束即部署验证**，避免一次性大重构

## 八、调研摸底结论（2026-08-03 全量调研）

### 8.1 好消息：骨架代码比预想完整

| 能力 | 现状 |
|------|------|

| **SKU 规格写入** | ✅ `SkuServiceImpl.addNew` 会把 `specifications` JSON 解析后写入 `pms_sku_specification` |
| **属性/模板 CRUD** | ✅ `AttributeController`（addnew/update/delete/sale/non-sale）+ `AttributeTemplateController`（addnew/details/list-by-category）已存在 |
| **相册/图片 CRUD** | ✅ `AlbumController` + `PictureController`（addnew/set-cover/按相册查）已存在 |
| **冗余同步** | ✅ `synchroniseStock`（SUM 库存）+ `synchronisePrice`（MIN 价格）已实现，可复用到 SKU 生成后 |

**结论**：企业级升级"后端骨架基本齐全"，主要工作是**打通数据 + 补前端 + 填测试数据**，不是从零写。

### 8.2 关键风险点（升级 SKU 体系的影响面）

**受影响的消费方**（依赖 SkuStandardVO 字段）：mall-front 商品详情/SKU 列表、mall-order 下单/购物车快照、mall-seckill 秒杀详情/SKU、前端 ProductDetail/SeckillDetail。

**核心风险**：
1. **`SkuStandardVO.specifications` 是 `@JsonRawValue`**——JSON 字符串直接透传。模板生成 SKU 后若规格 JSON 结构变化，前端解析会失败
2. **`SkuStandardVO.title` 是冗余字符串**——当前"iPhone 15 Pro 128GB 深空黑色"是手写的。升级后 title 若改为按规格值动态拼接，所有消费 title 的地方（购物车/订单快照/秒杀标题）都要适配生成规则
3. **下单走前端快照**——`OrderItemAddDTO` 的 title/price/mainPicture/data 全由前端从 SKU 详情构造传后端，后端不查库。模板生成 SKU 后，前端必须能拿到一致的 SKU 数据
4. **`SkuStandardVO.stock` 含义冲突**——秒杀 VO 里 `stock` 被秒杀库存覆盖，升级需明确区分
5. **SKU 图片 URL 拼接不一致**——`ForFrontSkuServiceImpl` 没调 `ImageUrlPrefixHelper`，SKU 图片靠前端自行处理相对路径

### 8.3.1 属性模型设计决策（技术债 1/2 的核心矛盾）

`pms_attribute` 存在**两套冲突的属性模型设计**：

| 设计 | 实体/DDL | 列 | 含义 |
|------|---------|----|------|
| **A. 属性定义模型**（实体 `Attribute.java` 采用） | `description, input_type, value_list, unit, is_allow_customize, template_id` | 属性是一个"定义"（如"内存"），有自己的类型/单位/可选值/是否可自定义 |
| **B. 属性值存储模型**（DDL `pms_attribute.sql` + 实际库采用） | `attribute_template_id, type, values, sort` | 属性直接存值列表（如"128GB,256GB,512GB"） |

同理 `pms_attribute_template_value`：
- **实体** `AttributeTemplateValue`：`{templateId, attributeId, sort}`（模板-属性 关联）
- **DDL/库**：`{attribute_template_id, value, sort}`（模板-属性值 存储）

**决策影响**：选择哪种模型决定数据库结构、实体字段、前端表单、SKU 生成算法。建议设计阶段从 B（现状库结构）或 A（实体设计，更贴近企业级）中选一，统一后补列/改列。**当前 `AttributeMapper extends BaseMapper`，若启用会按实体字段名查库 → 报 `Unknown column 'template_id'`**。

### 8.4 数据流现状

```
创建商品: POST /pms/spu/addnew → pms_spu + pms_spu_detail + 异步 syncSpu
创建SKU:  POST /pms/sku/addnew → pms_sku(specifications存JSON) + pms_sku_specification(解析后逐条)
前台查询: Dubbo IForFrontSpuService.getSpuById → ImageUrlPrefixHelper 拼URL
扣库存:   Dubbo IForOrderSkuService.reduceStockNum → skuMapper.updateStockById(stock=stock-#{n} WHERE stock>#{n})
```
