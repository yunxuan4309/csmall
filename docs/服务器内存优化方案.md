## 一、评估结论摘要

### 1.1 内存账单（2026-08-21 实测）

| 占用 | 大小 | 说明 |
|------|------|------|
| 11 个微服务 | ~7.1G | 堆已限 256~448m + Metaspace + SkyWalking agent + 线程栈（稳态） |
| Elasticsearch | 1.19G | 堆 512m + Lucene 文件缓存（正常） |
| SkyWalking OAP | 1.08G | 堆 512m + Netty 堆外 |
| Nacos | 0.98G | **堆 1g，最大可降点** |
| MySQL | 0.51G | buffer pool 默认 128m |
| SkyWalking UI | 0.41G | 静态服务 |
| Seata | 0.39G | 已调优达标 |
| Sentinel | 0.28G | 堆未限（默认上限 ~3.5G） |
| RabbitMQ/Redis/Nginx | ~0.12G | 健康 |
| buff/cache | 2.3G | 可回收，不算实际占用 |
| **available** | **2.1G** | 无 Swap |

### 1.2 核心判断

```
可"省"空间约 600M（最大单点是 Nacos 480M）；
真正值钱的是"安全网"：mem_limit（硬上限）+ Swap（缓冲垫）
= 从"随时可能被 OOM 杀服务"变成"有硬边界、有缓冲"。
```

### 1.3 补充发现：线程栈是 JVM 调优后剩余的"隐形大头"（2026-08-26）

**背景**：8-04 JVM 调优后（堆 -Xmx 448m/256m + 堆外限制），csmall-product RSS 仍 965M。
smaps 实测内存分解：

```
├── JVM 堆（-Xmx448m 上限）        ~250M  ← 已限，正常
├── Metaspace（上限 256m）         ~50M   ← 已限
├── 线程栈：350 线程 × 1M = 350M  ← 🔴 大头！JVM 调优没覆盖
├── DirectMemory（限 64m）         ~64M   ← 已限
├── CodeCache（限 64m）           ~37M   ← 已限
└── SkyWalking Agent 自身          ~几十M
```

**结论**：堆/堆外参数已全部生效，剩余空间在**线程栈**（每线程默认 1M）。
11 个微服务线程数 200~350 不等，合计线程栈 ~2-3G。

**是否再压 `-Xss256k`？——不建议**：
- 收益：每服务省 ~200-300M，11 个合计 ~2G
- 风险：Dubbo 序列化 / MyBatis 复杂 SQL / 递归调用可能超 256K 栈 → 偶发
  `StackOverflowError`，排查困难
- 结论：**JVM 层已到合理下限，继续压收益<风险**；剩余空间靠 mem_limit
  + Swap 做"安全网"兜底，而非继续压榨

## 二、优化项明细（4 项）

### ① 全容器加 mem_limit（安全网，不省内存）🟢 强烈建议

**原因**: 全部容器 `mem_limit=0`，任何进程内存异常可无限吃满宿主 → OOM Killer 杀进程（历史杀过 ES）；JVM 参数是"自限"而非"硬限"。

**建议值**（均按当前 RSS +30% 余量，正常业务碰不到）:

| 容器 | mem_limit | 当前 RSS |
|------|-----------|---------|
| mall-product / order / seckill | 1g | 787~945M |
| mall-front / ai | 1g | 572~686M |
| 其余 7 个微服务 | 768m | 486~649M |
| elasticsearch / skywalking-oap | 1.5g | 1.08~1.19G |
| nacos | 1g | 981M |
| mysql | 1g | 511M |
| sentinel / seata / skywalking-ui | 512m | 282~407M |
| rabbitmq / redis / frontend | 256m | 6~96M |

**执行方式（零重启，即时生效 + 持久化两步）**:
```bash
# 1. 即时生效（无需重启容器）
docker update --memory 1g csmall-product csmall-order csmall-seckill csmall-front csmall-ai
docker update --memory 768m csmall-sso csmall-ums csmall-ams csmall-gateway csmall-search csmall-resource
docker update --memory 1.5g csmall-es csmall-skywalking-oap
docker update --memory 1g csmall-nacos csmall-mysql
docker update --memory 512m csmall-sentinel csmall-seata csmall-skywalking-ui
docker update --memory 256m csmall-rabbitmq csmall-redis csmall-frontend

# 2. 同步 docker-compose.yml（否则 docker compose up 重建后丢失）
#    在 services 下给每个服务加: mem_limit: 1g 等
```

**回滚**: `docker update --memory -1 <容器>`（恢复无限制）。

### ② Nacos 堆 1g → 512m（最大单点收益）🟢 推荐

**原因**: standalone 模式 11 个服务注册量极小，512m 充裕（与 8-04 调优 Seata/OAP 同款逻辑）。

**compose 修改**:
```yaml
  nacos:
    environment:
      MODE: standalone
      JVM_XMS: "512m"     # 新增，覆盖镜像默认 1g
      JVM_XMX: "512m"     # 新增
      JVM_XMN: "256m"     # 新增（新生代，原 512m）
```

**影响**: 重启 nacos 容器（2~5 分钟注册中心抖动，微服务自动重连），**收益 ~480M**。

**回滚**: 删除上述 3 行后 `docker compose up -d nacos`。

### ③ Sentinel 加 `-Xmx256m` 🟡 可选

**原因**: 当前无 JVM 参数，默认堆上限 ≈ 物理内存 25%（~3.5G），当前 RSS 282M 虽无害但无保护。

**compose 修改**:
```yaml
  sentinel:
    environment:
      JAVA_OPTS: "-Dserver.port=8858 -Xms128m -Xmx256m"
```

**影响**: 重启 sentinel（控制台，无业务影响），**收益 ~50-100M**。

### ④ 加 2G Swap 🟡 可选（需 sudo，由 ecs-user 执行）

**原因**: 无 Swap，瞬时内存峰值（JVM 扩容 / ES 段合并 / 秒杀突发）无缓冲直接 OOM。

**执行命令**（ecs-user 执行）:
```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # 持久化
# 验证
free -h    # Swap 行应显示 2.0G
```

> ⚠️ Swap 仅是应急缓冲垫（SSD 上慢），不能依赖它承载业务，只防 OOM 杀进程。

## 五、回滚方案

| 项 | 回滚 |
|----|------|
| mem_limit | `docker update --memory -1 <容器>` + 还原 compose |
| Nacos 堆 | 删除 JVM_XMS/XMX/XMN 行，`docker compose up -d nacos` |
| Sentinel | 还原 JAVA_OPTS，`docker compose up -d sentinel` |
| Swap | `sudo swapoff /swapfile && sudo rm /swapfile` + 删 /etc/fstab 行 |
| 全部 | `cp` 备份的 compose 还原后 `docker compose up -d` |
