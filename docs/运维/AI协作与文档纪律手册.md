## 二、状态源与登记（唯一性规则）

### 2.1 状态源唯一

| 范围 | 唯一状态源 |
|---|---|
| **高优先级**待办（待执行 / 风险 / 安全 / 可实施） | [[TODO文件]]（含顶部「编号总登记表」） |
| **中 / 低优先级**（暂缓 · 仅评估 · 未来计划） | [[TODO中低优先级]] |
| **已完成**明细 | [[TODO已完成]] |
| **方案 / 评估文档**登记 | [[文档索引]] |
| **架构事实** | [[项目上下文文档]] |

- ⚠️ **编号永不重编号**（`docs/` 下 80+ 文件、1600+ 处引用）→ 废弃条目用 ~~删除线~~ + 状态标注，**不要复用编号**。
- 新条目：高优先级写「第一节 + 登记表 A」；中/低写 [[TODO中低优先级]]；完成后迁 [[TODO已完成]]。
- ⭐ **条目关闭 → 正文必须随关闭一起搬走**（2026-09-12 新增，**防复发纪律**）：`TODO文件.md` 的「条目正文」区**只允许存在未关闭的条目**；关闭后该编号只留两处 —— **编号登记表一行**（一句话 + 状态）+ **`TODO已完成.md` 里的正文**。
  > **依据（为什么必须成文）**：2026-09-11 **已经整段迁入过一次**（`TODO已完成` §二十「由 [[TODO文件]] 文末整段迁入」），但**当时没立这条纪律** → 09-12 一天新收口 12 条，`TODO文件.md` 又长回 **339 行档案正文**（占全文 **61%**）⇒ **只搬一次没用，纪律才是解**。
  > **判断口径**：`TODO文件.md` = **仪表盘**（现在做什么 + 编号去哪查）；**档案正文**归 `TODO已完成.md`。**"留档"≠"留在状态源里"**。

### 2.2 新增文档必须双向登记

1. 在 [[文档索引]] **登记一行**（文档名 / 对应条目 / 状态说明）；
2. 在对应 TODO 条目里 `[[链接]]` 该文档。

> **未登记 = 漏跟踪**。反过来"索引表指向不存在的文档"同样是错误 —— 两侧都要对。

### 2.3 定期交叉核对（建议每月或整理文档时）

枚举 `docs/评估报告/*.md`（排除 `*-副本.md`），逐个检查是否出现在索引表中：

- 「文档存在但无条目」→ 补登记
- 「索引表指向不存在的文档」→ 修正或删除该行

**首次全量核对（2026-09-10）实际发现**：2 个文档从未进 TODO（其中 `数据库Schema漂移审计` 含未完成待办 → 补登 #57）+ 4 个只出现在"关联文档"行 → 已补齐正文链接。

## 三、漂移的 5 类形态与纠偏纪律

> **背景**：三个「实现与原理」分册是**边做边追加**长成的，必出漂移。**追加新章节后必须回头同步**：① 文件头 `> **状态**`；② 目录 / 全景表；③ 文中"剩余项 / 待实施 / 待部署"表（**追加章节最常忘的就是这个**）。

| # | 漂移类型 | 典型表现 | 首批实例 |
|---|---|---|---|
| ① | **计划稿未回填执行结果** | 章节标题还挂"待执行" | 第一批 §七「待用户确认执行」（其实 09-07 就做完了） |
| ② | **追加章节没回头改汇总/状态头** | 正文说完成、头部说待做 | **第二批最严重**：§〇 表标 ✅，状态头与 §六 却写"待实施" |
| ③ | **计划与踩坑修正自相矛盾** | 前文计划 + 后文修正并存 | 第一批 §七 `chmod 600` vs §9.4 `chown redis:redis` |
| ④ | **外部事实变化** | 服务器早做了 / 形态变了 | Swap 已上、#29 备份已在跑、端口 `127.0.0.1`→`172.29.193.239` |
| ⑤ | **跨批次归属漂移** | 推给下一批，下批做完没回填 | #14-P2（二批 → 三批） |

### 3.1 纠偏必须带证据（硬要求）

**每条结论都要指向"实测 / 代码 / 其他文档"三者之一**（逐条 SSH 实测 + grep 代码 + 交叉已有文档）。**别凭印象改状态**。

> **教训实例（2026-09-10 自己踩的）**：曾误判两处 —— ① 以为 `mall-search` pom 里有 druid 依赖（实际是**注释**）；② 以为 redis `bind 0.0.0.0` **未变**（实际变的是**宿主端口绑定**，bind 本身没动）。

### 3.2 压缩 / 移动时的**锚点纪律**（2026-09-12 新增）

**外部文档会引用章节编号**（例：`CLAUDE.md §五·8`、`项目上下文文档 §8.12 / 附录 A.6`）。因此：

1. **压缩前先查引用**：`grep -r "文件.md" docs/` → 找出被引用的 `§编号` / `附录编号`；
2. **被引用的编号必须保留**（内容可搬走、可精简，但**标题与编号留在原地** + 加指针）；
3. **搬完复核**：确认每个外部引用仍能落到正确位置。

> 本次瘦身即按此执行：`§五·8`、`§8.12`、`附录 A.6`、`附录 B` 等 8 处被引用的锚点**全部保留**。

### 3.3 全量文档审计方法（2026-09-12 实做过一轮 · 可复用）

> **来源**：[[文档漂移审核报告-2026-09-12]]（111 份文档 / **237 条 finding**，**已全部处置**；该报告已归档）。

**做法（5 步）**

1. **按目录分片** —— `评估报告/`（24）+ `问题解决/`（47）+ `面试准备/`（40），**每 5 份一组**；
2. **子代理并行、只读审核**（本项目 23 组）—— **只记录、不修改被审计文档**；
3. 每组核 **7 类漂移 + 索引一致性** = §三 的 5 类 + **⑥ 编号 / 双链失效** + **⑦ 计数与口径不一致**；
4. **按 高 / 中 / 低 分级**，每条带 **原文证据 + 置信度**（"待人工判断"的单独标注）；
5. 汇总后按 **A/B/C/D 四档处置**（见下表）。

| 档 | 处置 | 适用 |
|---|---|---|
| **A** | **状态源回填** | 只改「状态 / 日期 / 一句话结论」，不动结构 —— **占绝大多数** |
| **B** | **标注历史语境** | 老方案与后文修正并存 → 给前文加「（历史记录，见 §X）」**而不是删除**（保留演进痕迹） |
| **C** | **修交叉引用** | `§编号` / 文档路径 / 双链失效 → 机械替换，但**逐个核对目标真的存在** |
| **D** | **暂不动** | 拿不准 / 需实测 / 历史快照类 → **先记着**，别硬改 |

**顺序**：A（状态源一次改完）→ C（引用，机械）→ B（历史标注）→ D（留档）；**每档一次提交、可分次回滚**。

**⚠️ 三条元教训（这次审计换来的）**

1. **审核结论本身也会错** —— 本次修复时**纠正了 3 处审核结论**（`k3s` 从未部署 / Nacos 实为 **27 服务名 · 6 条配置** / RabbitMQ **无 `x-max-length`**），并**追加 1 条报告未列的问题**（某文档把 JWT 默认密钥 68 字节写成 69，原判"无问题"）⇒ ⭐ **审核记录是"线索"，不是"结论"**；处置前必须**逐条复核**。
2. **"只记录、不修改"是审计纪律** —— 审计与修复分成两次动作，两边都能**独立回滚**；审计报告本身**不含任何改动**。
3. **修复进展必须回填报告状态头** —— 否则报告会误导读者"问题还在"；本项目即分三批回填（`问题解决/` 95 · `评估报告/` 64 · `面试准备/` 78）。

## 四、归档操作纪律（2026-09-10 首次执行的做法，下次照做）

2. **同步修正所有相对路径引用** `docs/评估报告/X.md` → `docs/归档/X.md`

## 五、文档切割纪律（2026-09-10 首次执行：两批"实现与原理" → 8 个问题解决文档）

- **按"一类问题的本质"聚合，不是"一个问题一篇"** —— 目标粒度约 1.5~3 个问题/篇，**共性解法能互相印证**；一篇只讲一个问题是浪费，一篇跨 4+ 个领域是硬凑。
- **每篇统一结构**：`一、这一类问题的共性`（★ 最值钱，先讲本质再讲个案）→ `二~N、逐问题（现象→排查→根因→修复→验证）`→ `跨问题共性认知与踩坑清单`→ `面试综述话术`→ `关联文档`。
- **迁移用"按行范围精确切片"而不是重新手打**（`Get-Content` 取行数组 → 切片 → 拼接 + 新写的共性/话术骨架）→ **内容零丢失、零改写漂移**。
- **切完必做 3 项验证**：
  1. 每个技术点的**标志串**是否落到预期新文档（本项目 19/19）；
  2. 有无**重复**（同一标志串出现在多篇）；
  3. **悬空的 `§` 章节引用**（切割后原 `§` 编号指向已迁走的章节 → 逐个改成 `[[新文档]] §X`）—— 本次修了 6 处。
- **原件去向 = 改成"薄索引"**：保留 `正文切割索引表` + 执行记录 + 通用话术，**不归档**（这样 TODO / 项目上下文里的 `[[TODO第X批实现与原理]]` 链接不失效）。
- ⚠️ **与现有同类文档的关系**：用户 2026-09-10 决定 **"仅加互链、不合并"** → 现有文档一字不改，新文档在 `关联` 行链接早期记录；**代价是同一问题两处描述**，靠互链 + 定期交叉核对防漂移。

## 六、查"服务器现状"的正确姿势（避免拿错事实来源）

1. **看运行中容器的实际值**：`docker inspect <c> --format '{{.HostConfig.RestartPolicy.Name}}'`；
2. **确认容器对应 compose 里哪个服务**：`docker inspect <c> --format '{{index .Config.Labels "com.docker.compose.service"}}'`；
3. **要读生产 jar 里的配置**：容器内**没有 unzip/python3/busybox** → 用 `docker cp` 拷到 `/tmp`，再用**已有镜像**（如 `redis:7-alpine` 的 busybox 解压）；`docker pull` 新镜像会受镜像源限制。

### 6.1 ⚠️ `deploy/docker/docker-compose.yml` 是"两机合并的单一文件"

- 26 服务 = **老机 21 + 新机 5**（新机 5 个用 `network_mode: host`）；
- **两台服务器的 `/data/csmall/docker-compose.yml` 就是这同一份**（实测两机容器 label 的 `com.docker.compose.project.config_files` 都指向它，712 行）。

> **踩坑实例（2026-09-10）**：把文件里 11 个 `on-failure` 当成"老机应有数量"，实际其中 5 个属于新机 —— 老机真实是 6 个，与文件一致。
> **正确做法**：**比较"某机现状"时只看该机在跑的服务**，别拿"文件里的总数"和"某一台的容器数"比。

## 七、本机操作提示（Windows PowerShell 5.1）

- `Get-Content` 默认按 **ANSI** 读 → 处理中文文档**务必加 `-Encoding UTF8`**，否则中文乱码导致匹配全部失效（2026-09-10 踩过）；
- 写 applier 的 JSON 时，字符串里的**半角双引号**会截断 JSON（`.gitignore` 同类坑见 [[CLAUDE.md]] §四）—— 中文里一律用全角引号 `「」`/`“”`；
- 好消息：`apply-multi.ps1` / `apply-json-fix.ps1` 是「**全量预校验、全成功才写**」，报错不会写坏任何文件，照位置修好再跑即可。
