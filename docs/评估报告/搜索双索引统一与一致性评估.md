## 一、现状盘点（2026-09-08 代码 + 服务器双重实测）

### 1.1 三个 ES 索引的实况

| 索引 | 服务归属 | 文档数 | 内容 | 结论 |
|------|---------|-------|------|------|
| `cool_shark_mall_index` | 无（历史遗留） | **0** | 空 | 🗑️ 垃圾索引 |
| `cool_shark_mall_index2` | mall-search | **18** | 缺 id 11、17；残留 id 18 | ⚠️ 过期快照 |
| `cool_shark_mall_ai` | mall-ai | **20** | id 1~20 全（含已下架 18） | ⚠️ 超集但含下架残留 |

**DB 基准（cs_mall_pms.pms_spu）**：当前 `is_published=1 AND is_checked=1 AND is_deleted=0` 共 **19 条**（id 1~17、19、20）；id=18 是 `is_published=0`（已下架）。

**关键推论**：
- AI 索引 20 条 = 19 上架 + **1 条下架残留（18）**
- index2 18 条 = 历史某次手动同步快照（新增的 11/17 从未同步进去；下架的 18 也从未删除）
- **两个索引都残留已下架商品 18** → 下架/删除不会从 ES 移除（同步模型缺陷，见 §2.2）

### 1.2 两条同步链路（代码实证）

```
链路① mall-search（index2）：
  手动 GET /search/sync ─→ SearchServiceImpl.loadSpuByPage()
      ─→ Dubbo IForFrontSpuService.getSpuByPage(page, 2)   ← pageSize=2（低效，注释自嘲"演示分页"）
      ─→ SpuForElasticRepository.saveAll()                  ← 只 upsert，从不 delete
  ❌ 无启动自动同步 ❌ 无商品变更订阅（product 从不通知它）

链路② mall-ai（cool_shark_mall_ai）：
  ① 启动自动 SyncOnStartupRunner ─→ VectorSyncServiceImpl.syncAll()
  ② 商品变更 Dubbo ─→ SpuSyncDubboServiceImpl.syncSpu(spuId)
      ← product 侧 SpuServiceImpl.addNew()/updateById() 调用（唯一通知方）
  ③ 手动 /ai/syncAll、/ai/sync/{spuId}
  ✅ 有自动链路，但同样只 upsert 不 delete
```

**Dubbo 接口 `ISpuSyncService`（mall-ai-service 定义）** 只有一个实现（mall-ai 的 `SpuSyncDubboServiceImpl`），product 的 `SpuServiceImpl` 通过 `@DubboReference(check=false)` 引用它 —— 这是"同步只到 mall-ai"的根因。

### 1.3 谁在消费哪个搜索？（前端代码实证）

| 入口 | 前端调用 | 实际服务/索引 |
|------|---------|--------------|
| 顶部搜索框（FrontLayout.vue） | 跳 `/products?keyword=` | → ProductList.vue |
| 商品列表页搜索（ProductList.vue） | `searchProducts()` = `POST /ai/search` | **mall-ai**（cool_shark_mall_ai）|
| 搜索建议（FrontLayout） | `getSearchSuggestions()` = `GET /ai/search/suggest` | **mall-ai** |
| 相关推荐（ProductDetail） | `getRelatedProducts()` = `GET /ai/product/{id}/related` | **mall-ai** |

### 1.4 复核补充证据（2026-09-08 二轮核查，A1/A2 决策依据）

**mall-search 模块家底盘点**：

| 检查项 | 结果 | 结论 |
|--------|------|------|
| 反向依赖（其他模块 pom 依赖 mall-search） | ❌ 零（仅根 pom 列为 module） | 无模块需要它 |
| 跨模块 import `com.cooxiao.mall.search` | ❌ 零 | 无代码耦合 |
| 对外暴露 Dubbo 提供者 | ❌ 无（`ISearchService` 是普通 Spring 接口，非 @DubboService） | 不是 RPC 服务 |
| 自身代码 | 17 个文件：controller(repository/security 全套/2 个 impl——其一 `@Deprecated` 的 logstash 空壳)/utils/test | 教学式手写 ES 查询（2024 年） |
| 唯一对外 HTTP 入口 | `SearchController`：`GET /search`（搜索）、`/search/sync`（手动全量同步）、`/search/byLogstash`（死代码空壳） | 只有 1 个真接口 |
| ES 数据依赖 | 自建 `index2`，靠**手动** `/search/sync` 同步 | 无自动链路 |

**流量实测（服务器，2026-09-08）**：

| 证据 | 结果 |
|------|------|
| Nacos 注册 | mall-search 1 实例（172.18.0.21:10008），服务本身健康 |
| gateway 日志（全量）含 `/search` 的请求 | **仅 1 条** = `GET /search/query?keyword=0xe60x89...`——**扫描器噪音**（十六进制注入探测，非正常浏览器 URL 编码）|
| nginx 24h 日志 `/api/search` | **0 条**（同窗口内全是扫描器 `/api/phpinfo`、`/api/v`、`/api/config` 之类）|
| 端口暴露 | `0.0.0.0:10008` 宿主机监听（安全组未开 10008，公网不可达）|
| 容器资源占用 | **521.8 MiB / 768 MiB mem_limit**（保留成本不低）|

**结论（复核后）**：
1. mall-search 是**完全孤立的遗留 Web 服务**——无模块依赖、无 RPC、无跨模块 import、Web 前端零调用、真实流量为零
2. 当前它的 index2 数据是**过期且错误**的（缺 11/17、含已下架 18）——**即使作为降级通道，现状也不可用**（降级查出来的结果比不降级更糟）
3. 因此 A1/A2 的共同前提是：mall-search **必须改造**才有价值，维持现状没有意义

- 前端 `search.js` 全部接口都是 `/ai/**`；无 `searchHttp` axios 实例、无任何 `/search/**` 调用
- gateway 虽保留 `mall-search` 路由（`Path=/search/**`），但 **Web 前端从不经过它**
- `mall-search` 服务（端口 10008）当前实际 ≈ **无 Web 消费者的遗留服务**（是否有 App/其它客户端调用需用户确认——评估按"无"处理，若"有"则方案 A 需保留兼容层）

### 1.4 与 TODO #33 原记载的差异（重要修正）

> TODO 原文（2026-09-02）："普通搜索和 AI 搜索各维护一个 ES 索引 + 各一套同步链路……AI 索引 20 > search 索引 18——**2 条新商品只进了 AI 索引，普通搜索查不到新商品 = 用户可见 bug**"

**实测修正**：截至 2026-09-08，"普通搜索"（Web 商品列表搜索）**已经在走 AI 搜索**（`/ai/search`），其索引含全部 20 条 → **Web 用户实际能搜到 11/17，原描述的用户可见 bug 已不成立**。mall-search/index2 只是"无人消费但没退役"的冗余链路。真正的遗留问题转移到：
1. 双索引双链路冗余，两处数据漂移（架构债 + 面试硬伤"两索引怎么保证一致"无法自洽）
2. 索引同步只 upsert 不 delete → **已下架/已删除商品残留在 ES，可能被搜索召回**
3. product 的 `passCheck/deleteById/updatePublishedById` **不触发任何 ES 同步** → 下架不消失、上架不即时（addNew 时 checked=0 也会被写入 AI 索引 → 未审核商品可被搜到）

## 二、问题本质

### 2.1 为什么会出现双索引？（历史成因）

- 早期（2024~2025）搜索由 mall-search 承担（手写 Spring Data ES），`/search/sync` 手动全量同步
- 后期（2026）AI 导购上线，mall-ai 自建 `cool_shark_mall_ai` + Dubbo 变更通知，形成第二条链路
- **product 变更只通知 mall-ai**（`ISpuSyncService` 唯一实现），mall-search 从未接入变更订阅 → 天然漂移
- mall-search 没有自动退役，gateway 路由保留 → 形成"看起来还在用"的假象

### 2.2 同步模型的三个缺陷（代码实证）

| 缺陷 | 代码位置 | 后果 |
|------|---------|------|
| **只 upsert 不 delete** | `SpuForElasticRepository.saveAll` / `VectorSyncServiceImpl.syncSpu`（esClient.index） | 下架/删除商品永远留在 ES |
| **删除/下架/审核不触发同步** | `SpuServiceImpl.deleteById`（仅 `updateDeletedById`）、`updatePublishedById`、`passCheck` 均无 `syncSpu` 调用 | 状态变更对 ES 无感知 |
| **写入不过滤业务状态** | mall-ai `syncSpu` 用 `getSpuById`（不过滤 checked/published）；`esKeywordSearch` 无 published/checked 过滤 | 未审核/未上架商品可能入库并被搜索召回 |

> 参考：订单/秒杀等场景有 Redis+DB 双写一致性经验（见上下文文档 §6.6），ES 侧的一致性目前是"最弱一环"。

## 三、方案选项

### 方案 A1：统一单一索引 + mall-search 彻底退役

**目标架构**：搜索只保留 **一个索引 + 一条同步链路**，mall-search 服务下线。

| 步骤 | 后端动作 | 前端/网关动作 |
|------|---------|--------------|
| A1-1 | 以 `cool_shark_mall_ai` 为唯一业务索引（字段最全：name/title/description/categoryName/brandName/listPrice/pictures/tags/sales/semanticText/suggestField） | 无 |
| A1-2 | mall-search 整体退役：gateway 去掉 `/search/**` 路由（prod/test/dev 三环境对齐）；compose 移除 search 容器 | 若确认无 App 调用 `/search`，前端无需改（本就走 /ai）；**若有 App 调用则 gateway 保留一条转发到 mall-ai 的兼容路由** |
| A1-3 | 同步模型补全：`VectorSyncServiceImpl` 增加 delete/状态过滤；`syncSpu` 前校验 `checked=1 AND published=1 AND deleted=0`（不满足则删文档）；product 的 `deleteById/updatePublishedById/passCheck` 补发同步通知 | 无 |
| A1-4 | 清理：删空索引 `cool_shark_mall_index`；`cool_shark_mall_index2` 删除；`mall-search` 代码仓库归档 | 验证搜索功能回归 |

**优点**：① 消灭双份存储/双链路，数据只有一个事实源 ② 面试可讲"搜索索引从双链路收敛为单索引 + 变更订阅，AI 只做重排层"（淘宝式叙事）③ 顺带修复"下架可搜到/未审核可搜到"的真 bug
**代价**：**无进程级降级通道**——mall-ai 进程挂 = 搜索全挂（仅依赖 mall-ai 内部 `esKeywordSearch` 降级，防不了进程本身故障）；mall-search 退役涉及部署，需确认无外部消费者
**工作量**：后端 ~0.5~1 天（同步模型补全 + 清理），部署窗口 1 次

### 方案 A2：统一数据源 + mall-search 保留为普通搜索降级通道 ⭐（用户意向，2026-09-08）

> **用户质疑点**："为什么要除去 search 模块?难道搜索降级的时候不使用吗?" → 本方案回应此质疑:mall-search **保留为独立进程的降级通道**,但**不再自建第二份索引**,改为只读统一索引——既保留"AI 挂时普通搜索仍可用"的进程级故障隔离,又消灭数据漂移。

**为什么独立进程降级 ≠ mall-ai 内部降级(核心认知)**：

| 降级方式 | 能防什么 | 防不了什么 |
|---------|---------|-----------|
| mall-ai 内部 `esKeywordSearch` 降级（现状） | AI 重排失败 / 预算超限 / LLM 超时 | **mall-ai 进程本身挂掉**（OOM/GC/崩溃）——降级代码在同一个进程里，进程没了什么都没了 |
| mall-search 独立进程普通搜索（A2） | ✅ 上面全部 + **mall-ai 进程级故障**（AI 服务挂了，商品搜索仍可用） | ES 本身挂（ES 挂 = 搜索全挂，属中间件故障，不在服务降级范畴） |

**目标架构**：

```
                    ┌───────────────────────────────┐
                    │   唯一索引 cool_shark_mall_ai   │  ← 一份数据
                    └──────┬───────────────┬─────────┘
                   读(普通) │               │ 读(语义)
        ┌───────────────────▼─────┐   ┌─────▼──────────────────┐
        │ mall-search(独立进程)     │   │ mall-ai(独立进程)        │
        │ GET /search 普通关键词召回 │   │ POST /ai/search 语义重排 │
        │ 纯 ES match,毫秒级,零 AI  │   │ + suggest + related    │
        └───────────────────┬─────┘   └─────┬──────────────────┘
                            │               │
        Web 前端: 先调 /ai/search → 失败/超时 → fallback 调 /search
```

**A2 要点**：

| # | 动作 | 说明 |
|---|------|------|
| A2-1 | **mall-search 不再自建 index2** | 删除/停用 `SpuForElasticRepository` 写入路径（`loadSpuByPage` 全量同步、`/search/sync` 接口）；不再维护任何 ES 写入 |
| A2-2 | **mall-search 改为只读 `cool_shark_mall_ai`** | 用原生 `ElasticsearchClient`（mall-ai 同款 starter，mall-search pom 已有 `spring-boot-starter-data-elasticsearch`）手写 `multi_match` 普通召回：name/title/description/categoryName/brandName/tags（与 mall-ai `esKeywordSearch` 同字段、**不加 semanticText boost、不做 AI 重排**） |
| A2-3 | **统一返回结构** | `/search` 返回 `SearchResultVO`（mall-pojo ai.vo，含 products/totalCount）——与 `/ai/search` 降级输出同构 → **前端 fallback 零适配**（ProductList.vue 已按此结构渲染） |
| A2-4 | **前端 fallback** | `ProductList.vue` 搜索分支：`searchProducts()` 抛错/超时 → 自动改调 `/search`（gatewayHttp，需带登录 token——mall-search `/search` 是 authenticated，与 `/ai/search` 一致） |
| A2-5 | **网关路由保留** | prod/test/dev 三环境 `/search/**` → `lb://mall-search` 不动（mall-search 仍是独立注册服务） |
| A2-6 | **同步链路收敛为一条** | product 变更 → Dubbo `ISpuSyncService` → **仅 mall-ai** 写 `cool_shark_mall_ai`（现状已如此，不再为 mall-search 建任何同步）；mall-search 只读不写 → **天然零漂移** |
| A2-7 | **同步模型补全（A1/A2 共用核心）** | `syncSpu` 校验 `checked=1 && published=1 && deleted=0`，不满足则 delete；product 的 `deleteById/updatePublishedById/passCheck` 补触发；清理下架残留 18 |
| A2-8 | **清理** | 删空索引 `cool_shark_mall_index`；`cool_shark_mall_index2` 全量对齐后删除（或保留为空壳待 mall-search 旧代码彻底移除后删） |

**mall-search 改造工作量**：
- `SearchServiceImpl` 重写为原生 client 普通召回（~80-120 行，可参考 mall-ai `SearchServiceImpl.esKeywordSearch`）
- `SpuForElastic`/`SpuForElasticRepository`/`SpuEntity` 及 `/search/sync` 相关代码停用或删除（保留文件作归档可，但不再启动写入）
- 返回 VO 复用 mall-pojo 已有 `SearchResultVO`/`RelatedProductVO`（✅ 已确认在 `mall-pojo/com/cooxiao/mall/pojo/ai/vo/`，mall-search-service 已依赖 mall-pojo，**无跨模块依赖问题**）
- 前端 ProductList.vue fallback ~20 行

**优点**：① 单一数据源 + 单写链路,一致性根治 ② 保留独立进程普通搜索 = 真降级通道(进程级隔离)③ 面试叙事:"双索引收敛为单索引;mall-search 作为只读普通搜索降级层保留,AI 挂了还能搜"——**完美回应"降级怎么办"追问** ④ Web 前端无感知(正常路径不变)
**代价**：mall-search 需改造(非纯删除);前端加 fallback;返回结构统一需小调
**风险**：mall-search 与 mall-ai **并发读同一索引**——ES 读并发无冲突;唯一注意点是两者查询字段/映射必须一致(同索引同字段名,天然一致)

### 方案 B：双索引自动对齐（保守，保留 mall-search 独立自建索引）

| 步骤 | 动作 |
|------|------|
| B1 | mall-search 增加启动自动全量同步（复用 `loadSpuByPage`，pageSize 改 500）+ 定时/手动对账任务 |
| B2 | 全量重建 index2 对齐 DB（19 条上架） |
| B3 | （可选）product 变更广播到 mall-search（`ISpuSyncService` 增加第二实现或 product 侧双调用） |
| B4 | 清理空索引 `cool_shark_mall_index` |

**优点**：改动小、不碰现有 AI 链路；mall-search 独立服务保留
**缺点**：**双份数据永远要维护一致性**（新增一个服务订阅点/对账任务）；面试被问"两索引怎么保证一致"依旧尴尬（对账是补丁不是根治）；索引残留/状态过滤缺陷仍要单独修
**工作量**：后端 ~0.5 天

### 方案 C：最小止血（现状微调，不解决架构债）

- 手动补 index2 缺的 11/17 + 删残留 18（临时一致性）
- 清理空索引
- 不建自动链路

**优点**：10 分钟
**缺点**：下次加商品又漂移；不解决面试问题 → **不推荐作为最终方案**，仅作方案 A 执行前的临时步骤

## 三·五、A1 vs A2 再评估（2026-09-08 二轮，用户要求全面核查后重新比较）

> 用户顾虑："不太确定是否真要舍弃 search 模块，因为这是很大的架构改动"。本节用复核证据回答：**A1/A2 的改动量差异远小于直觉，且"保留"不等于"少改"**。

### 3.5.1 先破除一个直觉误区：A2 不是"少改"，A1 也不是"大改"

| 维度 | A1（退役） | A2（只读降级层） |
|------|-----------|-----------------|
| mall-search 代码改动 | **删**（gateway 去路由 + compose 移除 + 代码 git rm/归档）| **重写** `SearchServiceImpl`（手写 ES client 查询 ~80-120 行）+ 停用 repository + 删死代码 |
| 改动性质 | 减法，无新逻辑、无新依赖 | 加法/重写，引入新查询实现，**需要长期维护**（字段列表要跟 mall-ai 保持一致）|
| 前端改动 | **零**（前端本就走 /ai）| fallback 逻辑 + 降级 UI 提示 |
| 服务器部署 | 删 1 容器（compose + Nacos 注销）| 改 1 容器（换 jar 重写），**继续占用 768M mem_limit** |
| 后续维护 | 无（模块消失）| **两处查询逻辑（mall-ai 语义召回 + mall-search 普通召回）字段必须同步演进**——新增搜索字段要改两处 |

**结论**：直觉上"A2 保留 = 改动小"是**错的**。A2 的改造面（重写 + 前端 + 长期双维护）实际 **大于** A1（纯删除）。若唯一动机是"不确定能不能删"，删比改更安全。

### 3.5.2 再评估"降级"需求的真实性（用户核心顾虑）

**先确认一个事实**：**当前 mall-search 根本不能当降级通道用**——它的 index2 数据过期且错误（缺 11/17、含已下架 18）。"保留现状 = 有降级"是不成立的；要获得降级能力，**必须先投入 A2 改造**（或 B 方案同步对齐）。所以问题不是"要不要删一个能用的服务"，而是"**要不要为一个当前不可用、且零流量的服务投入改造，换取进程级降级**"。

**进程级降级的真实价值评估**：

| 故障场景 | mall-ai 内部降级能否覆盖 | 独立 mall-search 额外价值 |
|---------|------------------------|--------------------------|
| AI 重排失败 / LLM 超时 / 预算超限（**最高频**） | ✅ 能（esKeywordSearch 已实现）| 无（冗余）|
| ES 本身故障 | ❌ 不能（mall-search 也读 ES）| ❌ 无（同依赖，一起挂）|
| mall-ai 进程 OOM/崩溃（低频，演示环境几乎不触发）| ❌ 不能 | ✅ 唯一受益场景 |
| DB/Redis/MQ 故障 | 部分能 | 无差异 |

- 演示环境 21 容器已稳定运行 **39 天**（`uptime`），mall-ai 容器无崩溃史；compose 已配 `restart: on-failure` → 进程挂会自动拉起
- 唯一"mall-ai 整体挂"的现实触发 = 手动 `docker stop csmall-ai` 做演示/维护 → 此时**搜索本身也应随维护窗口不可用是可接受的**（不是生产 SLA）
- 若面试要演示降级：**A2 落地前必须先 `docker stop csmall-ai` 演练**，成本是真实的（多 521M 内存 + 前端 fallback 分支常驻）

### 3.5.3 决策矩阵

| 决策点 | 选 A1 的论据 | 选 A2 的论据 |
|--------|------------|-------------|
| 改动量/风险 | ✅ 最小（减法；前端零改；无新维护面）| 重写 + 前端 + 双查询长期同步 |
| 资源占用 | ✅ 释放 768M（R7 后 available 3.8G，省下来更宽裕）| 常驻 ~520M |
| 一致性根治 | ✅（A1/A2 共用同步模型补全）| 同左 |
| 面试叙事 | ✅ "双索引收敛单索引，遗留 search 退役"（干净利落）| ✅ "保留独立普通搜索降级层"（更丰满，但需能扛住"为什么不直接让 AI 内部降级"的追问）|
| 进程级降级 | ❌ 无（接受"AI 挂=搜索挂"）| ✅ 有（但覆盖场景窄：仅 mall-ai 进程级故障）|
| 可逆性 | ✅ 高（git 历史可恢复；compose 一行加回）| 中（改造后想退役需再删一次）|
| 诚实边界 | "演示项目无 SLA，进程级降级是过度设计" | "企业搜索服务常独立部署，本方案是低配演练" |

### 3.5.4 复核后的独立建议（记录 AI 票的思考过程 —— 供复盘）

> ⚠️ **本节保留的是讨论中间态（AI 二轮倾向 A1 的分析）**，作为决策过程证明；**最终经三人讨论（§3.5.5）认定 A2**，本节不构成最终结论。

**AI 二轮分析的"A1 论据"（后被翻转，保留作复盘）**：
1. **现状 mall-search 无价值**（零流量、零依赖、数据过期），A1 是"清理僵尸"，不是"砍活服务"
2. **A2 改动反而更大且引入永久双维护点**——与"怕大改动"的初衷相悖
3. **降级诉求已被 mall-ai 内部降级覆盖 90%**（AI 重排/预算/LLM 故障——这些才是高频场景）；进程级故障在演示环境（restart: on-failure + 39 天无崩溃史）价值接近零
4. 若日后真要普通搜索独立层：**git 历史 + 本报告 A2 设计就是现成方案**，随时可恢复（A1 可逆性 > A2）

**翻转原因（为什么 AI 最终投 A2）**：以上分析回答的是"要不要养僵尸"，但三轮追问（AI 能扛搜索吗 / 违背微服务吗 / Spring AI 影响）揭示决策本质是"**搜索职责该不该独立**"——按微服务单一职责/故障隔离原则，搜索（高频稳定毫秒级）与 AI（慢贵绑 LLM 预算受限）必须服务边界隔离；A2 是"职责正确的形态 + 可控代价"。详见 [[TODO第二批实现与原理]] §5.2。

### 3.5.5 最终认定（2026-09-08 三人讨论拍板）

**参与**：用户（owner）+ 用户同学（终票）+ AI（同级票，独立判断）。**结果：A2 全票**。

```
统一数据源（cool_shark_mall_ai 单一索引 + 单写链路）
    ├── mall-ai（独立进程）：语义搜索 /ai/search + suggest + related + AI 重排
    └── mall-search（独立进程，改造为只读降级层）：GET /search 纯 ES 召回（零 AI）
Web：正常走 /ai/search → 失败/超时 → fallback /search
```

**A1 去向**：完整方案/步骤/优缺点**原文保留**（§三 方案 A1），作为讨论过程证明——面试被问"考虑过退役吗"可展示完整决策树。

**A2 落地范围（要改 search 模块 —— 重写查询层而非删服务）**：
1. mall-search `SearchServiceImpl` 重写为原生 ES client 普通召回（multi_match，不加 semanticText boost、不重排），返回 `SearchResultVO`（mall-pojo ai.vo，已确认无跨模块问题）

6. **面试文档（09-AI 模块等）不改**——代码向文档叙事靠拢（Q7"普通搜索=地基、AI=重排层"）

> ⚠️ **同步模型补全（§五 共同必做）与 mall-search 去留无关，是当前真实存在的搜索正确性问题（下架商品 18 残留），必做。**

## 七、面试价值（A1/A2 两版叙事）

**选 A1 时**：
- "我发现两个搜索各维护索引、数据漂移（18 vs 20），Web 前端其实早已全走 AI 搜索（nginx/gateway 实测零流量、零模块依赖）→ 双链路收敛为**单一索引 + 单写链路**，遗留的 mall-search 是僵尸服务，**软退役**（compose 注释保留 + git 历史可恢复）"
- "顺带修了真 bug：只 upsert 不 delete + 删除/下架不触发同步 → 下架商品残留在 ES 能被搜到"
- 被追问"搜索降级怎么办"："AI 搜索内部有 ES 原始排序兜底（覆盖 LLM/预算/超时这些高频故障）；进程级故障在演示环境由 restart 策略兜底。**我评估过保留独立进程做降级层（A2），结论是：为一个零流量的僵尸服务投入重写 + 双查询永久维护，性价比为负**——这个取舍本身就是面试点"

**选 A2 时**：
- "降级分两层——mall-ai 内部 AI 重排失败降 ES 原始排序（防 LLM 故障）；mall-search 独立进程普通搜索（防 **mall-ai 进程整体挂掉**）。进程级隔离才是真降级"
- 诚实边界："mall-search 保留为降级层而非独立搜索服务，因为 Web 无直连消费者；代价是两处查询逻辑要同步维护——演示项目可接受，商业上会把它并入统一搜索网关"
