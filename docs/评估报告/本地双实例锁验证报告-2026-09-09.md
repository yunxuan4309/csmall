## 一、验证目标

单实例跑不出分布式锁的价值，必须**两个真实 JVM 抢同一把锁**。本实验回答三个问题：

| # | 问题 | 判据 |
|---|---|---|
| 1 | 两实例同时触发定时任务时，是否只有一个执行？ | 同一时刻只有一台打印任务执行日志；另一台打印"未抢到锁，跳过" |
| 2 | 会不会重复执行（同一次待处理数据被处理两次）？ | 人为制造 N 次漂移 → 恰好出现 N 条修正日志 |
| 3 | 锁是否被正确释放（不漏锁、不误删）？ | 实验后 `KEYS mall:seckill:lock:*` 为空；Redis 数据回到 DB 基准值 |

## 三、实验设计（为什么用"对账任务"而不是"重试任务"）

| 候选任务 | 是否采用 | 原因 |
|---|---|---|
| `SeckillReconcileTask.reconcileOnline`（库存对账） | ✅ **采用** | 只读 DB + 写 Redis，**无 MQ、无外键副作用**；制造一次"Redis 库存 ≠ DB 库存"即可触发 |
| `MessageRetryTask.retryFailedMessages` | ⚠️ 仅观察抢锁 | 要触发需往 `seckill_message_retry` 插一条 pending 记录 → 会真的发 MQ → 本地无 Dubbo provider，消费会失败重投，污染环境。**改为观察它在并发时的"未抢到锁"日志** |

**漂移制造方式**：把 `mall:seckill:sku:stock:1` 从 DB 基准值 **45** 改成 **999**（差异 954 ≥ 对账阈值 2 → 立即修正）。
对账任务每 **5 秒**跑一次（`--seckill.reconcile.online-fixed-delay=5000`，生产默认 5 分钟），并把任务包日志级别调到 **DEBUG** 以便看到"未抢到锁"。

## 五、结果证据

### 5.1 双实例确实互斥（交叉证据，同一时刻各丢一把锁）

```
实例1  14:57:05.588 [scheduling-1] DEBUG SeckillReconcileTask - 未抢到运行期对账锁，跳过本次执行（另一实例正在执行）
实例2  14:57:05.382 [scheduling-1] DEBUG MessageRetryTask      - 未抢到消息重试任务锁，跳过本次执行（另一实例正在执行）
```
→ 同一秒内：**实例1 丢了对账锁、实例2 丢了重试锁**，说明两个任务上都发生了"一方持有、另一方跳过"。

### 5.2 3 轮漂移实验：4 次漂移 → 恰好 4 次修正

| 轮次 | 造漂移时刻 | Redis 设定 | 修正者 | 修正时刻 | 修正后 | 另一实例的"丢锁"证据 |
|---|---|---|---|---|---|---|
| 基线 | 14:57:35.126 | 999 | **实例1** | 14:57:35.913 | 45 | 实例2 未在此时刻抢到（实例1 持有） |
| 1 | 14:58:39.705 | 999 | **实例1** | 14:58:41.489 | 45 | 实例2 14:58:46.542 丢对账锁 |
| 2 | 14:58:53.831 | 999 | **实例2** | 14:58:56.587 | 45 | 实例1 14:59:16.731 丢对账锁 |
| 3 | 14:59:07.277 | 999 | **实例2** | 14:59:11.661 | 45 | 实例1 14:59:31.788 丢对账锁 |

**关键点**：
- 修正日志原文：`【秒杀库存对账】skuId=1, Redis=999, DB=45, 差异=954, 已按DB修正为 45`
- **4 次漂移 = 4 条修正日志**（实例1 两条、实例2 两条）→ **没有任何一次被重复执行**
- 两个实例**交替**拿到锁（不是固定一台）→ 锁释放正常、竞争公平

### 5.3 收尾校验

| 校验项 | 结果 |
|---|---|
| 锁 key 残留 | `KEYS mall:seckill:lock:*` → `[]` ✅ 全部释放，无漏锁 |
| 数据一致性 | `mall:seckill:sku:stock:1` = **45** = DB `seckill_stock` = **45** ✅ |
| Nacos 实例 | `mall-seckill` → 10007 + 10017 均 `healthy=true` ✅ |
| 锁行为汇总 | 实例1：修正 2 / 丢对账锁 4 / 丢重试锁 0；实例2：修正 2 / 丢对账锁 2 / 丢重试锁 1 |

## 八、踩坑记录（本次实验新增 4 条）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **`dubbo.registry.address=N/A` 不可用** | 启动失败：`No such any registry to reference ...IOmsOrderService`（Dubbo 消费者必须能从注册中心解析地址） | 起本地 Nacos，走真实注册中心（也顺带验证了双实例注册） |
| 2 | **Dubbo QoS 默认端口 22222** | 第二个实例 `QosBindException: qos-server can not bind localhost:22222`（仅 WARN，不致命） | 实例2 加 `--dubbo.application.qos-port=22223` |
| 3 | **`Start-Process` 启动的 Nacos 被回收** | Nacos 一度 8848 可达，随后端口全 CLOSED（进程随工具调用结束被进程树回收） | 改用**后台常驻任务**运行 `startup.cmd`，Nacos 保持存活 |
| 4 | **Sentinel 日志噪音极大** | 日志文件 850KB，绝大部分是 `DateFileLogHandler` 的 NPE 刷屏；按中文关键字过滤易漏 | 用**类名**精确匹配（`SeckillReconcileTask` / `MessageRetryTask`），并统计行数而非肉眼扫 |

> 附带认知：日志文件里"两实例启动耗时完全相同（45.377s）"曾让人怀疑是同一进程——实际是两个独立 JVM（PID 不同、端口不同、Nacos 双实例），时间巧合源于同一台机器同时启动。

## 十、企业级做法对照与"锁的正确性边界"（复盘）

> 本节回答"真实企业也这样测 Redis 吗？我们的方式是不是粗鲁"——**不算粗鲁，但确实偏手工/一次性**。

### 10.1 我们做对的部分（企业同款）

| 做法 | 为什么不算粗鲁 |
|---|---|
| 真实两 JVM + 真实 Redis（不用 mock） | 锁的原子性是 Redis 服务端行为，mock 掉等于自证 |
| 选**对账任务**制造场景（避开 MQ 副作用） | 主动控制实验污染面，是有意识的工程判断 |
| **量化判据**（4 次漂移 → 恰好 4 次修正） | 可证伪的计数断言，而非"看起来正常" |
| 收尾校验（锁 key 无残留 + 数据回基准） | 企业测试同样要求"测试后状态可断言" |

### 10.2 "粗鲁"具体在哪（诚实对照）

| 维度 | 本次做法 | 企业规范做法 | 代价 |
|---|---|---|---|
| 环境隔离 | 本机 + 共享 dev Redis/MySQL | 独立测试环境；Java 用 **Testcontainers** 每测试起一次性容器 | 靠人工恢复（本次零污染） |
| 可重复性 | 手工起 2 个 JVM、手工改 key、grep 日志 | **自动化测试** + CI 每次跑（回归） | 不可回归，改一次要重做一遍 |
| 故障注入 | 手工改 1 个 key | Chaos Mesh / ToxiProxy 注入**网络分区、延迟、进程 kill** | 未覆盖"锁过期/实例崩溃/网络分区" |
| 观测 | grep 日志 | 指标 + 链路追踪 + 断言（Prometheus/Grafana） | 证据靠人看，不可自动判定 |
| 样本量 | 4 轮 | 数百轮随机化 + 竞态压力 | 偶发竞态抓不到 |
| 数据操作 | 直接改业务语义 key（已恢复） | 测试专用数据/影子库/构造 API | 理论有污染风险（低） |

**定性**：本次 = **exploratory test（一次性手工实验）**，把问题**证实**了；企业要的是**可自动重跑的回归测试**。二者不矛盾，但长期不退化必须脚本化。

### 10.3 ⭐ 锁**不是**正确性的唯一保证（面试高段位答案）

Redis 主从是**异步复制**：A 在 master 加锁 → master 挂 → slave 提升 → B 在**新 master** 加锁也成功 → **两实例同时持锁**（Redlock 争议：Kleppmann vs antirez 的核心）。

企业应对不是"把锁做得更完美"，而是**让锁失效也不出错**：

```
锁       → 降低并发概率（减少无效工作，性能手段）
幂等     → 重复执行不出错
DB 约束  → 最后一道防线
```

**本项目三层齐备**：`updateStatusSent` 状态标记（幂等）+ `seckill_stock >= qty` 条件扣减 + `uk_sku_user` 唯一索引 → **即使锁在极端切换下短暂双持，也不会造成数据错误**。这句话比"我用了分布式锁"值钱得多。

### 10.4 定时任务防双跑：企业更少自研 SETNX

| 方案 | 定位 |
|---|---|
| **ShedLock** | 专为 `@Scheduled` 设计（`@SchedulerLock` + `lockAtMostFor`/`lockAtLeastFor`），语义最贴合 |
| **Redisson `RLock`** | 业务互斥标准件：看门狗自动续期、可重入、支持 Redlock |
| **XXL-JOB / ElasticJob** | 调度平台自带分片防重（不靠锁） |
| **K8s CronJob + leader election** | 云原生做法 |
| 自研 SETNX + Lua（本次） | **白盒教学版**：可控、可讲清、零依赖 |

> 📌 **顺带发现**：`mall-seckill-webapi/pom.xml` **已引 Redisson 3.24.3 但代码零使用**（无 `RedissonClient` 配置、无 API 调用）= **死依赖**。若要走企业路线，可**零新增依赖**换成 `RedissonClient.getLock()`（自带看门狗续期/可重入），功能与现实现等价。
