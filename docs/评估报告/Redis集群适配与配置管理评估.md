## 一、Redis 集群扩容：业务代码适配性评估

### 1.1 结论：✅ 基本可适配，且适配成本极低

**核心依据（2026-08-21 代码实测）——全项目零跨 key 操作**：

| 检查项 | 结果 |
|--------|------|
| `mget` / `multiGet` / 管道 pipeline | ❌ 零使用 |
| 事务 MULTI/EXEC / SessionCallback | ❌ 零使用 |
| Lua 多 key 脚本 | ❌ 零调用（RedisBloomUtils 为死代码） |
| 集合运算（zUnionStore / sInterStore 等） | ❌ 零使用 |

集群最大的坑是 **CROSSSLOT 错误**（一条命令涉及多个 slot 的 key 直接报错），而项目所有 Redis 操作都是**单 key**——单 key 天然分布在任意 slot，集群下行为完全不变。

秒杀的"多 key 联动"（orderLock / ordered / stock / reseckill）是**顺序的单 key 命令 + 分布式锁 + 失败补偿**，不是原子多 key 操作，集群下同样不受影响。

### 1.2 重定向（MOVED/ASK）适配性：✅ 天然适配，业务代码无感

Redis Cluster 的 key 迁移/节点变化通过两个错误码驱动客户端重定向：

| 错误码 | 含义 | Lettuce 行为 |
|--------|------|-------------|
| `MOVED` | key 所在 slot 已永久迁移到另一节点 | 自动重发到新节点 + **更新本地拓扑缓存**（后续直达，无重复重定向） |
| `ASK` | key 正在迁移中（临时） | 发送 `ASKING` 后重发到目标节点，迁移完成即收敛 |

- 项目使用 Spring Data Redis + **Lettuce**（默认客户端），集群模式下**自动处理 MOVED/ASK，业务代码零改动**
- `ClusterTopologyRefreshOptions` 支持拓扑自动刷新（节点增删/主从切换后客户端自动感知，周期可配，默认 ~60s）
- 项目无 `KEYS *`、无跨 slot `MGET`、无跨 slot 事务/pipeline → **集群模式下的受限命令全部未使用**，无适配障碍

### 1.3 三个适配点（未来做集群时必须处理）

1. **key 设计约定（hash tag）**：目前 key 无 hash tag（`{userId}` 这种）。将来若引入 Lua 多 key 原子脚本（如秒杀扣库存+标记），必须约定用 hash tag 强制同 slot——建议**未来新 key 都带 `{业务维度}` 约定**，避免 CROSSSLOT
2. **客户端切换零成本**：Lettuce 原生支持集群，只需 compose 注入 `SPRING_DATA_REDIS_CLUSTER_NODES`（节点列表），**业务 yml 和代码都不用改**
3. **密码/节点一致性**：集群每个节点都要 `requirepass` + 客户端配 `SPRING_DATA_REDIS_PASSWORD`（正好并入 R1 加固方案）；节点扩容/缩容需在拓扑刷新周期内平滑过渡

## 二、配置是否写进 Nacos 统一管理？（评估结论：当前没必要）

### 2.1 当前配置管理方式（先认清现状）

```
11 个模块 application-prod.yml  = 默认值/模板（${REDIS_PASSWORD:} 等回退值）
compose + .env 环境变量注入      = 实际生效值（SPRING_DATA_REDIS_HOST/PASSWORD...）
```

**关键事实：Redis 地址/密码的实际变更点已经集中在 compose/.env 一处**——11 个 yml 只是默认值，生产实际值由环境变量统一注入。改一处即全服务生效。

### 2.2 Nacos Config 的收益 vs 成本

| 维度 | 收益（为什么有人用） | 本项目现状 |
|------|-------------------|-----------|
| 动态刷新 | 改配置不用重启（@RefreshScope） | 变更频率极低，重启容器 30 秒内完成 → **价值为零** |
| 多环境管理 | dev/test/prod 集中管理 | 已有 profile + .env 分离 → **已覆盖** |
| 配置审计/回滚 | 变更留痕 | 已有 git + 服务器备份 → **已覆盖** |
| 灰度发布 | 按实例灰度配置 | 单实例部署 → **用不上** |

**引入成本**：每个模块加 `nacos-config` 依赖 + bootstrap 配置 + Nacos 上为 11 个模块建 dataId + 启动顺序变成"Nacos 必须先起" + 本地 dev/test 也要处理配置拉取 → **运维复杂度显著上升**。

### 2.3 结论

- **当前没有必要**引入 Nacos 配置中心：变更点已集中、变更频率极低、动态刷新无场景、成本大于收益
- 而且**哨兵方案落地后客户端连哨兵（节点对客户端透明）**，Redis 节点变更根本不需要改任何配置——配置中心的场景进一步缩小
- **未来触发条件**（商业化后）：配置变更频繁（多环境/多租户/灰度）、需要动态调参（限流阈值/开关）、合规审计要求

## 三、业务代码 jar 容器多副本必要性评估（结论：当前没必要）

### 3.1 硬约束：硬件不允许 🔴

服务器 4C16G，内存 available 仅 2.2G（无 Swap），已跑 21 个容器。多副本 = 资源翻倍，**当前机器连 1 个副本都放不下**。

### 3.2 无流量压力

演示流量下所有微服务 CPU < 5%，单实例无瓶颈。多副本解决"扛流量 + 故障转移"，当前两者都不存在。

### 3.3 有状态服务的坑（多副本的真正难点）

| 服务类型 | 多副本问题 | 项目现状 |
|---------|-----------|---------|
| 无状态（可随便扩）✅ | — | Dubbo + Nacos 天然负载均衡，**这是最大优势** |
| 定时任务 ⚠️ | `SeckillInitialJob`（库存预热）、`MessageRetryTask`（重试）**多实例会重复执行** | 需分布式锁/任务调度改造 |
| MQ 消费者 ⚠️ | 多实例消费需幂等 | success 表已幂等 ✅ |
| Seata ⚠️ | TM/RM 多实例需集群配置 | 当前单实例 |

### 3.4 正确演进路径

```
单实例（当前）→ 先解决基础（哨兵/内存加固/监控）→ 多机部署 → 再谈单服务多副本
```

> 想演示"集群"，Redis 哨兵（已定稿）和 Nacos 本身就是集群形态，比业务多副本更有展示价值、成本更低。

### 3.5 未来触发条件（商业化时）

- 流量真实增长出现性能瓶颈（先压测验证）
- 高可用 SLA 要求（单实例故障不能接受）
- 服务器扩容/多机部署后
