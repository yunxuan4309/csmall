## 二、⭐ 遇到的问题与解决方案（11 条，全部有实测证据）

> 三类：**A. 会让压测结论作假的**（1~6）· **B. 度量口径错的**（7~8）· **C. 现场/流程事故**（9~11）

| # | 问题（现象） | 根因 | 解决方案 |
|---|---|---|---|
| **1** | `/ai/chat/stream` **并发下 ~50% HTTP 500**（串行却 20/20 全 200） | `StreamingResponseBody` 在异步线程写完流后触发 **ASYNC 二次派发**，那一刻容器线程上无认证对象 → `anyRequest().authenticated()` 拒绝 → `AccessDeniedException`（串行时"响应已提交"把它掩盖了） | 授权规则最前面加 `.dispatcherTypeMatchers(DispatcherType.ASYNC, DispatcherType.ERROR).permitAll()`。🔴 **只放 ERROR 不够**（原分析只猜到 ERROR）；原有的 `MODE_INHERITABLETHREADLOCAL` 也无效（ASYNC 用的是池里**另一个线程**）→ 收敛为 **#62** |
| **2** | mock 侧出现一条**空请求体**（`rawlen=0 json_ok=False`）→ 误判任务类型 → 回纯文本 → 应用 `JSON.parseObject` 抛 `fastjson.JSONException` ⇒ **每次对话产生一个假 500** | 应用的 `chatJson`（`PreferenceExtractor`）用 **`Transfer-Encoding: chunked`** 发送，而 mock 只按 `Content-Length` 读 | mock 实现 **chunked 请求体解析**；并加 `--verbose` 打请求摘要（`clen/te/rawlen/json_ok`）作为固定排查手段 |
| **3** | mock 自压时 100 并发出现 **17 次失败** | `ThreadingHTTPServer.request_queue_size` **默认只有 5**，100 并发把 accept 队列撞爆 | 自定义 `MockServer.request_queue_size = 512`。**这条只有"先单独压 mock"才会发现** |
| **4** | 若 mock 只发 `data: [DONE]` 后保持 keep-alive，客户端会**挂到读超时** | Java 客户端 `openSseStream` 里 `[DONE]` 是 `continue`、**不是 break** ⇒ 流结束靠**连接 EOF** | mock 用 **chunked 编码**写 `0\r\n\r\n` 终结 body（**不能**只发 keep-alive 傻等） |
| **5** | 预算会被 mock 的 `usage` 记满 → 之后**每个请求都返回"服务繁忙"**（阈值 2 元/天；单价 1+2 元/百万；每次调用 ≈ 0.00011 元 ⇒ **约 5000 请求打满**，而 100 并发 × 45s 一档就 ~4500 次） | `recordUsage` 会把 mock 的 usage 也记账 | mock 用 **0 token 模式**（`--prompt-tokens 0 --completion-tokens 0`）⇒ 零记账、零污染，**比放开预算更干净**（项目自身也告诫 relaxed binding 易错） |
| **6** | 客户端**分不清"闸门满"与"其它异常"**（我的 `busy` 列报了 0，实际约 65% 被闸门拒） | 闸门满时服务端 `catch` 写的是**通用文案** `AI 服务暂时不可用，请稍后重试。`，与真异常**同一句** | 判闸门**回看服务端日志** `docker logs csmall-ai \| grep '【AI并发闸门】'`；脚本加醒目提示，且**不把不确定的东西归到 busy** |
| **7** | "总 RPS"在限流下**虚高**（agent@100 总 53.6，实际成功仅 ~18/s） | 被拒请求毫秒级返回，把总 RPS 抬起来 | 脚本新增 **`成功 RPS`**（成功数/耗时）并排打印；**判承载只看成功 RPS** |
| **8** | 原计划"构造 120 个用户 token"实测**不够** | 每用户频控 10 次/60s ⇒ **可持续 RPS = N × 10/60**；120 用户只够 **20 req/s** | 建 **800** 用户池（上限 ≈133 req/s）；脚本把该公式直接打印出来并给建议值 |
| **9** | **预热档就把整个阶梯中止了**（一步正式阶梯都没跑） | 我的集成缺陷：预热与正式阶梯**共用同一个 `stop_flag`** | 预热改用**独立** `stop_flag`（预热触发阈值不应杀掉正式阶梯） |
| **10** | 🔴 **服务宕机**：`csmall-ai` `Exited (1)`，日志 `NacosException: user not found!` | 部署时 **jar 传错**——传上去的是 **2026-08-15 的老产物**（`application.yml` 1583B，**缺 #13 Nacos 认证配置**） | 用**从本仓库构建的 jar** 恢复（核对 md5 + 挖出镜像内 class 验证）。教训：**scp 后必须先核对 md5 再替换** |
| **11** | Nacos 热改后**紧接的 GET 仍显示旧值** → 一度误判为"写入未生效"，还据此改了脚本绕弯路 | **配置读缓存 / 传播延迟**，不是写入失败 | 修正判据：**等 1~2 秒再复核**，并与落盘 md5 比对（已写进 B册 §五 Runbook；同时**推翻了我自己先前的错误结论**） |
