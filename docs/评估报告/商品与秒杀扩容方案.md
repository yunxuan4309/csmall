## 一、前置修复 #63：ES 索引 mapping 与代码期望不符 🔴 **先做这一件**

### 1.1 现状对照（2026-09-11 老机 `curl localhost:9200` 实测）

| 期望（`EsIndexInitializer.createIndex()`） | **线上实际** | 影响 |
|---|---|---|
| `dynamic: false` | **未设置 → ES 默认 `true`**（动态映射） | 字段类型由首个写入值决定，随时可能变 |
| `name/title/description/semanticText` 用 `ik_max_word` | 全部 `text`+`keyword` 子字段，**无 analyzer** | `_analyze "小米手机"` → **4 个 `<IDEOGRAPHIC>` 单字** = **standard 分词，IK 未生效** |
| `categoryName/brandName/pictures/tags` 为 `keyword` | 全是 `text` | 见下 1.2-① |
| `listPrice: double` | `listPrice: float` | 精度/类型不一致（影响小） |
| `semanticVector: dense_vector(dims=1024, cosine)` | **完全没有该字段**（`grep -c semanticVector` = **0**） | 见下 1.2-③ |
| `suggestField: completion` | **`text`** | 见下 1.2-② |

### 1.2 三个已实测的后果

1. **品牌过滤恒不生效** 🔴 —— `RagServiceImpl.intentSearch` 用 `term brandName` 打 `text` 字段：实测 `term brandName="小米"` = **0 命中**，`match brandName="小米"` = **4 命中** → 品牌维度只能靠 `fullTextSearchNoPrice` 兜底（`SearchProductsTool` 的降级路径）。
2. **`/ai/search/suggest` 补全恒返回空** 🔴 —— completion suggester 打 `text` 字段会抛异常被吞掉。
3. **向量检索一旦开启必失败** 🔴 —— 当前 `embedding-enabled: false` 所以还没暴露；**开启后** `semanticVector` 会被动态映射成 `float` 数组，而检索用 `scriptScore + cosineSimilarity(params.queryVector, 'semanticVector')` → 类型不匹配 → 必然失败 → **#31 白做**。

### 1.3 为什么不会自愈

`EsIndexInitializer` **只在索引不存在时才创建**（`if (exists) return`）→ 这份漂移**永不修复**。索引 `creation_date` ≈ 2026-07-31，**早于**该初始化类上线；**这份 dynamic mapping 是谁创建的未能查明**（非该初始化类，也不是已废弃的 `SpuForElastic`/`index2`）。

#### 🔴 新发现的一个回归风险（重建前必须先知道）

重建后 `brandName / categoryName / pictures / tags` 会从 `text` 变成 **`keyword`**，而 `RagServiceImpl` 的 `multiMatch` **正包含 `brandName`/`categoryName`/`tags`** → 这三个字段从"部分匹配"变成"**整值精确匹配**"：

- **好处**：`term brandName` 过滤（原本恒 0）**开始生效**；
- **风险**：查询串若是"小米手机"，keyword 字段 `"小米"` **不再命中** → **召回可能变少**；
- ⇒ **重建后必须跟一次召回回归**（对 5~10 个典型问题看结果集变化）。若召回明显变差，把 `tags` 从 `SEARCH_FIELDS` 摘掉或改打 `.keyword` —— 那是**另一件事（改代码）**，按纪律**不夹带**。

#### 🔴 #31 的前置：同批实测 —— **现在开不了**

`POST https://api.siliconflow.cn/v1/embeddings`（生产 key，模型 `BAAI/bge-m3`）→ **HTTP 402** `{"code":30001,"message":"Sorry, your account balance is insufficient"}` → **#59 仍未解决**。
**若此刻开 `embedding-enabled=true`：`syncAll` 每批会 try-catch 吞掉 402 → 同步 0 条但接口返回成功 → 索引里一个向量都没有**，反而更难排查。

**但有一个更好的事实**：`EsIndexInitializer` 的 mapping **常量里始终包含 `semanticVector`**（不依赖 `embedding-enabled`）→ **修 #63 时就把向量的"地基"打好了**。

> ⇒ **结论：两件事应分开做，且必须 #63 先做。**
> **#63 现在做**（一次停机换来：正确 IK 分词 + 可用的补全 + 品牌过滤生效 + **`semanticVector` 字段就位**）；
> **#31 等 #59 充值后再开** —— 那时只需改配置 + 重新同步，**零停机、无需再删索引**。

> **与 #57 的关系**：同属"代码与线上不一致"这一类。本条只处理 ES mapping；MySQL 侧的漂移（`seckill_message_retry` 无 DDL、`ams_permission` 多 `value` 列）已在 #57 登记。

## 二、商品 20 → 60（方案 A：直接写库）

### 2.1 写入面（只碰 `cs_mall_pms`，**全库 0 真实外键**）

| 表 | 必需 | 主键策略 | NOT NULL |
|---|---|---|---|
| `pms_spu` | 1 行 | **无 AUTO_INCREMENT**，应用侧雪花 | `id`、`name`、`type_number`（**UNIQUE**）、`title` |
| `pms_spu_detail` | 1 行（详情页用） | 同 | `id`、`spu_id`（`uk_spu_id`） |
| `pms_sku` | ≥1 行 | 同 | `id`、`spu_id`、`title` |
| `pms_sku_specification` | 可选（规格展示） | 同 | `id`、`sku_id`、`attribute_id`、`attribute_name`、`attribute_value` |

### 2.2 三条必须写对的规则

1. **可见性三字段（充要条件）**：`is_deleted=0 AND is_checked=1 AND is_published=1`
   - 前端列表过滤：`ForFrontSpuServiceImpl`（按分类 / 全部 / `getSpuByPage` 三处）
   - AI 可检索判定：`VectorSyncServiceImpl.isSearchable()`
   - ⚠️ `is_published` 列**可空**；实测 20 行里 19 行满足（`id=18` 是 `is_published=0`）
   - ℹ️ `check_user` / `gmt_check` 是**纯装饰字段**（全仓库只有一处 set 成 null，无任何查询读它们）→ 可 NULL
2. **冗余字段必须自己算**（直接写库不会自动同步）：
   - `pms_spu.stock = SUM(pms_sku.stock)`
   - `pms_spu.list_price = MIN(pms_sku.price)` ← **ES 的价格区间过滤与价格排序用的正是它**，写错则"5000 元以内"类搜索失效
3. **主键自备唯一 bigint**：建议 **`1001+`**，避开既有 `1~20` 与雪花 `2.08e18` 区间

## 三、秒杀 6 → 12

### 3.1 写入面与必填

| 表 | 必填字段 |
|---|---|
| `seckill_spu` | `id`（**无自增**，实体 `ASSIGN_ID` 雪花）、`spu_id`、`list_price`、`start_time`、`end_time` |
| `seckill_sku` | `id`、`sku_id`、`spu_id`、`seckill_stock`、`seckill_price`（`seckill_limit` 可空默认 1） |

- **没有"场次表"**：`cs_mall_seckill` 只有 `seckill_spu / seckill_sku / success / seckill_message_retry / undo_log / flyway_schema_history`。"场次"就是每行自己的 `start_time`/`end_time`，Quartz 每分钟取 `start_time <= now+5min <= end_time` 的行。
- ℹ️ `seckill_limit` **购买链路从不校验**（"永久限购 1 件"是 Redis `reseckill` 实现的）。

### 3.2 🔴 硬约束：三值相等（否则预热永不生效）

> 依据 **#64**：`seckill_sku.spu_id` 存的是 **`seckill_spu.id`**（前端详情/限购按它查），而**预热 Job 用的是 pms `spu_id`**。二者只在**碰巧相等**时一致 —— 现有 6 行里 **4 行错位**，实测 **12 个秒杀 SKU 只有 8 个被预热**，另外 4 个靠凌晨 03:30 对账写的 `TTL=-1` 永久 key 兜住。

**⇒ 新增秒杀必须满足：`seckill_spu.id == seckill_sku.spu_id == pms_spu.id` 三者相等。**
（对新增商品来说，就是直接复用 §2.3 里那个自备 bigint；⚠️ **不要用后台接口新增** —— MyBatis-Plus 会给雪花 id → `id ≠ spu_id` → 预热永不命中。）

### 3.3 Redis 预热：哪些能手工写，哪些绝对不能

| key | 能不能手工写 | 原因 |
|---|---|---|
| `mall:seckill:sku:stock:<pmsSkuId>` | ✅ **能**（建议写） | 用 `StringRedisTemplate`，值是**纯数字字符串** → `redis-cli SET` 兼容 |
| `mall:seckill:spu:url:rand:code:<pmsSpuId>` | ❌ **不能** | 值是 **JDK 序列化的 Integer** → 手工写格式对不上，反序列化异常 |
| `spu:bloom:filter:<today>` | ❌ **不能** | 是 Redis **SET**（不是真布隆），成员是 **JDK 序列化的 String** |

- `rand:code` 与 `bloom` 由 Quartz **每分钟**自动维护（窗口覆盖 `now+5min` 时 ≤1 分钟生成），**新增后不需要手动重建**，等一分钟即可。
- 不预热就下单的后果：直接 500 `没有该商品缓存信息(可能在真空期,等下一分钟再试)`。

### 3.4 验证清单

```bash
# 1) 三值相等（新增行必须全部满足）
SELECT sp.id, sp.spu_id, sk.spu_id FROM cs_mall_seckill.seckill_spu sp
  JOIN cs_mall_seckill.seckill_sku sk ON sk.spu_id = sp.id
 WHERE sp.id >= 1001;
# 2) 没有重复行（spu_id 无唯一约束，重复会让 findSeckillSpuById 抛 TooManyResultsException）
SELECT spu_id, COUNT(*) FROM cs_mall_seckill.seckill_spu GROUP BY spu_id HAVING COUNT(*) > 1;
# 3) 每个秒杀 spu_id 都能在 pms_spu 查到（否则 /seckill/spu/list 整页 NPE 500）
SELECT sp.spu_id FROM cs_mall_seckill.seckill_spu sp
  LEFT JOIN cs_mall_pms.pms_spu p ON p.id = sp.spu_id WHERE p.id IS NULL;
# 4) 库存键存在且是普通字符串
redis-cli get   mall:seckill:sku:stock:<pmsSkuId>
redis-cli ttl   mall:seckill:sku:stock:<pmsSkuId>     # 期望 ≈ 83~112s（由 Job 轮转），不是 -1
# 5) bloom 成员与 rand code 自动就位（等 1 分钟）
redis-cli sismember spu:bloom:filter:$(date +%F) <pmsSpuId>
redis-cli exists mall:seckill:spu:url:rand:code:<pmsSpuId>
# 6) 前端秒杀页
curl -s "http://127.0.0.1/api/seckill/spu/list?page=1&pageSize=20"
```

## 四、与 #48 造数的衔接（这才是扩容的隐藏收益）

| 项 | 现在 | 扩到 60 商品后 |
|---|---|---|
| 在售 SKU 数 | **36**（`stock>0` 且已上架） | 约 **110+** |
| **可用库存合计** | **1456 件** | **数千件** |
| 对 #48 的意义 | `need_units = days × per_day × 5% × 2`，**库存是硬约束**（§〇.1 D7） | **造数规模不再受库存卡**；同时 SKU 多样性提升，`search_products` 的召回质量更好 |

**建议顺序**：**#63（ES mapping）→ 商品扩容 → 秒杀扩容 → #48 造数 → #48 AI 并发压测**。
理由：mapping 不对时扩容后的搜索体验会被打折；库存池放大后造数才有余量；#48 压测放最后（它要求生产可短暂放开限流）。

## 五、风险清单（扩容专用，逐条给"为什么 + 怎么验"）

| # | 风险 | 为什么 | 怎么验 / 规避 |
|---|---|---|---|
| 1 | **图片裂图** | `pictures` 存的是**路径引用**，复用同一张图时若删/换图会连带所有引用方裂图 | 写完逐张 `curl -o /dev/null -w '%{http_code}'`；统一存**相对文件名** |
| 2 | **ES 与 DB 不一致** | 直接写库不触发 Dubbo push；清理残留靠 `cleanupInvalidDocs`，而它只扫 `size(1000)` 条 | `ES _count` 对比 DB 有效数；调 `/ai/sync` 或重启；**N 接近 1000 前先改代码** |
| 3 | **ES mapping 漂移**（#63） | 见 §一 | 先修 #63，再扩容 |
| 4 | **品牌 term 过滤恒失效** | `term` 打 `text` 字段 | 修 #63 后改用 `brandName.keyword` 或 `match` |
| 5 | **`/ai/search/suggest` 恒空** | completion suggester 打 `text` | 修 #63（`suggestField` 恢复 `completion`） |
| 6 | **秒杀预热不一致**（#64） | 两套 `spu_id` 语义冲突 | §3.2 三值相等 + §3.4 验证 |
| 7 | **秒杀库存键缺失** | 未预热 → 下单 500 | §3.3 手工 `SET`，或等次日 03:30 对账 |
| 8 | **销量/库存冗余失真** | `stock`/`list_price` 只在 SKU 增删改时同步 | §2.5 第 2 条 SQL 逐行比对 |
| 9 | **分类/品牌"外键式引用"** | 无真实 FK，只在 `addNew` 校验 | 只用 `brand_id ∈ 1..7`（enable=1）、`category_id ∈ 4..9`（`is_parent=0 AND enable=1`） |
| 10 | **秒杀重复行 / 孤立引用** | `seckill_spu.spu_id` 无唯一约束 | §3.4 第 2、3 条 |
| 11 | **秒杀列表整页 500** | `BeanUtils.copyProperties(null, vo)` 对查不到的 SPU 会 NPE | §3.4 第 3 条 |
| 12 | **分布式事务缺口** | `@GlobalTransactional` 全仓库只在秒杀下单一处；商品新增**无事务** | 直接把 SPU+详情+SKU 放进**同一事务** |
| 13 | **逻辑删除形同虚设** | 全仓库**无** `@TableLogic`，靠每个查询手写过滤 | 新增任何查询自己带 `is_deleted=0` |
| 14 | **`dense_vector` dims 不可改** | 建成后改维度只能删索引重建 | 修 #63 时一次定好（`AiProperties.embeddingDimensions` = 1024） |
| 15 | **向量化被额度卡死** | 硅基流动余额不足返 402 → 每批 try-catch 吞掉 → **同步 0 条但接口返回成功** | #59 充值前保持 `embedding-enabled: false`；比对日志里"同步完成，共 N 条" |
| 16 | **手工写 Redis 格式不兼容** | rand code / bloom 是 JDK 序列化 | §3.3：**只手工写库存键** |
| 17 | **前端"列表有、搜不到"** | 列表走 DB、搜索走 ES，两个数据源 | 每次扩容后**两条路都验** |
| 18 | **字段长度/正则约束** | 走接口时有 `pictures ≤ 500 字符`、`name 2~16`、`sort ≤ 99` 等 | 直接写库无此约束，但**仍应遵守**（否则前端展示异常） |
