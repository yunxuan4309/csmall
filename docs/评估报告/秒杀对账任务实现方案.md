## 〇、为什么需要对账（背景与目标）

秒杀走"**Redis=闸门、DB=账本**"模型：

```
下单：Redis 预扣（DECR mall:seckill:sku:stock:{skuId}）→ 放行/拒绝   ← 资格闸门
异步：MQ 消费 → DB 条件扣减（seckill_sku.seckill_stock>=qty）+ 写 success 表  ← 账本
```

两者**异步**，任何一环失败都可能让 Redis 与 DB 库存值漂移：
- **Redis 丢预扣**（进程崩溃/主从切换丢写）→ Redis 偏大
- **Redis 多放行但 DB 未成交**（MQ 扣失败 rows==0）→ Redis 偏小（多放）
- 人工/测试误操作、Redis 手动改动等

对账目标：**定期比对 Redis 与 DB 值，把漂移在用户感知前自动修掉**，避免"Redis 显示有货但 DB 实际无货"（付钱没货）或"Redis 无货但 DB 有货"（有货不能买）。

**核心哲学**（沿用 #14）：不追求 Redis 永不漂移，追求"漂移能被自动修正、用户无感知"。

## 一、关键数据模型（已核实）

### 1.1 库存值存哪

| 侧 | key/字段 | 写入时机 | 含义 |
|----|---------|---------|------|
| Redis | `mall:seckill:sku:stock:{skuId}`（String） | `SeckillInitialJob` 预热 `sku.getSeckillStock()`；下单 `DECR` | 剩余可放行数（闸门） |
| DB | `seckill_sku.seckill_stock`（int） | 插库初值；MQ `updateReduceStockBySkuId` 条件扣减 | 剩余可成交数（账本） |

> 预热初值 `= DB seckill_sku.seckill_stock`（`SeckillInitialJob` 第 86-90 行）。
> **稳态下 Redis 值应等于 DB 值**（Redis 下单放行数 = MQ 成交数，DB 扣到相同位置）。

### 1.2 成交记录

| 字段 | 说明 |
|------|------|
| `success` 表 | 每条 = 一次成功落库的秒杀成交（`sku_id`, `quantity`, `order_sn`） |
| `seckill_sku.seckill_stock` | 扣减后的**当前**剩余库存（权威账本） |

## 二、对账公式与方向（已确认：以 DB 为准、双向都修）

### 2.1 核心定义

对每个有预热库存 key 的 sku：

```
redisValue = Redis mall:seckill:sku:stock:{skuId} 当前值
dbValue    = DB seckill_sku.seckill_stock 当前值
diff = redisValue - dbValue
```

### 2.2 稳态语义

- **`redisValue == dbValue`**：完全一致，无需处理。
- **`redisValue > dbValue`（Redis 偏大 = 扣少了）**
  - 含义：Redis 预扣放行数 **少于** DB 成交数（丢了一次 DECR，或 Redis 被调大）。
  - 风险：继续下单会按 Redis 值放行，放行数 > DB 实际可成交 → **可能超卖**。
  - 修正：把 Redis 拉回 DB 值（`set(dbValue)`），消除超卖窗口。
- **`redisValue < dbValue`（Redis 偏小 = 扣多了）**
  - 含义：Redis 预扣放行数 **多于** DB 成交数（放行了但 MQ 没成交，如 rows==0 或重试中）。
  - 风险：Redis 已显示无货，但 DB 实际还有货 → **有货不能买**（用户可见）。
  - 修正：把 Redis 回补到 DB 值（`set(dbValue)`），修复缺额。

> **结论**：两个方向都修（以 DB 为权威值覆盖 Redis），实现简单且能自愈。

## 三、两层对账架构（业界分层，已确认）

> **关键修正（2026-09-07，用户指出）**：对账**不能**只在高峰期做，也**不能**只放凌晨——社区主流是**分层**：
> ① 运行期**高频轻量纠偏**（每 5 分钟，只比对已预热热点 sku，容错瞬时差）；
> ② 凌晨**低峰全量校准**（每日 cron，以 DB 为唯一基准，全量比对所有 sku，彻底清累积脏数据）。
>
> **只放凌晨的风险**：秒杀窗口白天有效，一旦高峰漂移，用户当天就"看到有货买不到/超卖"，要等次日凌晨才对账——伤害持续一整天。故运行期必须有轻量纠偏，凌晨全量是兜底。

### 3.1 两层职责与调度

| 层 | 调度 | 作用 | 高峰期风险 | 依据 |
|----|------|------|-----------|------|
| **A 运行期轻量纠偏** | `@Scheduled(fixedDelay=5min)` | 只比对**已预热热点 sku**，\|diff\|≥2 或连续同向差才修（容忍瞬时差） | 低：只读 Redis/W 少量改写，不动主链路 | 社区"每 5 分钟对账"常规做法 |
| **B 凌晨全量校准** | `@Scheduled(cron="0 30 3 * * ?")` | 全量比对**所有 sku**，以 DB 为唯一基准彻底修复（含慢漂移/死信/未成交遗留） | 无：低峰执行，无并发干扰 | 社区"每日凌晨低峰全量校准，以 DB 为唯一基准" |

### 3.2 合法时间差问题（两层都需处理）

秒杀高峰下单链路：`Redis DECR`（同步、毫秒级）→ `MQ 异步扣 DB`（排队+消费，秒级）。

**对账那一刻，可能存在合法的瞬时差**：
- Redis 刚放行 1 单（DECR 到 X），该单 MQ 还没被消费扣 DB（DB 仍 Y，Y 比 X 大 1）。
- 此时 `redisValue < dbValue` 是**正常的追赶过程**，不是漂移。

若对账立刻把 Redis 回补到 DB，会**误覆盖掉刚预扣的合法订单**，造成超卖。故两层都需**容错**。

### 3.3 容错策略（避免误修）

**只在"差异足够大"或"连续多次一致方向差异"时才修正**，规避单个合法预扣的瞬时差：

- **阈值容错**：仅当 `|redisValue - dbValue| >= 2` 才触发修正（±1 可视为合法的单笔追赶，交给下一次对账自然收敛）。
- **连续校验**：对差异 1 的情况，记录到 Redis 计数，**连续 N 次（如 3 次，即 15 分钟）都保持同方向差异**才修正——若只是瞬时追赶会在对账间隔内被 MQ 追平。

> 说明：±1 的合法瞬时差是短暂的，连续多轮仍存在才说明是真实漂移。**凌晨全量校准（B 层）可放宽阈值**（低峰无并发，\>=1 即修），彻底对齐。

## 四、方案设计（实现思路）

### 4.1 新增对账 Job

在 `mall-seckill-webapi` 新增：

```
com.cooxiao.mall.seckill.task.SeckillReconcileTask
```

**一个类，两个 @Scheduled 方法**（复用同一 `reconcileAll()` 核心，仅范围/阈值不同）：

| 方法 | 调度 | 范围 | 阈值 |
|------|------|------|------|
| `reconcileOnline()` | `@Scheduled(fixedDelay=5min)`（运行期） | 只处理**已预热**的 sku（Redis 有 key） | \|diff\|≥2 或连续同向差≥3 次才修 |
| `reconcileDaily()` | `@Scheduled(cron="0 30 3 * * ?")`（凌晨） | 全量所有 sku（含 Redis 无 key 的也检查 DB 基准） | \|diff\|≥1 即修（低峰无并发，彻底对齐） |

> **B 层（凌晨）也处理 Redis 无 key 的情况**：若某 sku 的 Redis 库存 key 缺失但 DB 有库存（如预热未跑/已过期），在低峰补建 Redis key 预热到 DB 值，保证第二天开抢前 Redis 就绪。

### 4.2 核心逻辑（伪代码）

```java
// ---------- 运行期轻量纠偏（A 层） ----------
@Scheduled(fixedDelay = 300000)
public void reconcileOnline() {
    reconcileAll(true);   // online=true：容错 + 只处理已预热 sku
}

// ---------- 凌晨全量校准（B 层） ----------
@Scheduled(cron = "0 30 3 * * ?")
public void reconcileDaily() {
    reconcileAll(false);  // online=false：|diff|>=1 即修，低峰彻底对齐
}

private void reconcileAll(boolean online) {
    List<SeckillSku> skus = seckillSkuMapper.selectList(null);
    for (SeckillSku sku : skus) {
        Long skuId = sku.getSkuId();
        String stockKey = SeckillCacheUtils.getStockKey(skuId);
        Integer dbValue = sku.getSeckillStock();   // DB 账本（权威）

        String redisStr = stringRedisTemplate.boundValueOps(stockKey).get();
        if (redisStr == null) {
            // Redis 无 key：运行期跳过（交给预热重建）；凌晨全量：低峰补建到 DB 值
            if (!online && dbValue != null && dbValue > 0) {
                stringRedisTemplate.boundValueOps(stockKey).set(dbValue + "");
                log.info("【对账-凌晨校准】补建 Redis 库存 key, skuId={}, DB={}", skuId, dbValue);
            }
            continue;
        }
        long redisValue = Long.parseLong(redisStr);

        long diff = redisValue - dbValue;
        if (diff == 0) {
            resetDiffCounter(skuId);   // 一致，清累计
            continue;
        }

        boolean shouldFix;
        if (online) {
            shouldFix = Math.abs(diff) >= THRESHOLD_ONLINE
                    || (Math.abs(diff) == 1 && shouldFixAfterConsecutive(skuId, diff));
        } else {
            shouldFix = true;   // 凌晨：|diff|>=1 即修
        }
        if (shouldFix) {
            fixStock(skuId, stockKey, redisValue, dbValue, diff);
        }
    }
}

private void fixStock(Long skuId, String stockKey, long redisValue, Integer dbValue, long diff) {
    stringRedisTemplate.boundValueOps(stockKey).set(dbValue + "");
    resetDiffCounter(skuId);
    log.warn("【秒杀库存对账】skuId={}, Redis={}, DB={}, 差异={}, 已按DB修正",
            skuId, redisValue, dbValue, diff);
}
```

> 注：`THRESHOLD_ONLINE`（默认 2）、`shouldFixAfterConsecutive`（连续 N=3）、`resetDiffCounter` 均在类内实现。

### 4.3 需要的新增方法

| 方法 | 位置 | 说明 |
|------|------|------|
| `selectList(null)` | `SeckillSkuMapper`（BaseMapper 现成） | 查全部 sku 及其 `seckillStock`（dbValue） |
| `shouldFixAfterConsecutive(skuId, diff)` | job 内部 | 用 Redis 记同方向累计次数（`mall:seckill:reconcile:cnt:{skuId}`，TTL 30min），≥N 才修 |
| `resetDiffCounter(skuId)` | job 内部 | 一致/已修正后清累计计数 |
| `fixStock(...)` | job 内部 | 覆盖 Redis 值 + 日志 |

### 4.4 配置项（`application-test.yml` 注入 @Value）

| 配置 | 默认 | 说明 |
|------|------|------|
| `seckill.reconcile.online-fixed-delay` | 300000 | A 层运行期间隔（5 分钟） |
| `seckill.reconcile.online-threshold` | 2 | A 层 \|diff\| 阈值（≥2 直接修） |
| `seckill.reconcile.online-consecutive` | 3 | A 层连续同向差次数（±1 时） |
| `seckill.reconcile.daily-cron` | `0 30 3 * * ?` | B 层凌晨全量校准 cron |

### 4.5 复用点

- 用 `SeckillSku.seckillStock`（已有）作为 dbValue，**无需新表/新列**。
- 连续计数存 Redis hash（`mall:seckill:reconcile:cnt:{skuId}`, TTL 30min），兼容未来集群化（非单实例内存）。
- 复用 `SeckillCacheUtils.getStockKey` + `SeckillSkuMapper`（BaseMapper）。

## 五、风险与边界（诚实评估）

| 场景 | 处理 | 风险 |
|------|------|------|
| 秒杀进行中合法差分（Redis 刚 DECR、MQ 未扣） | A 层 ±1 容错 + 连续校验，不误修 | 低 |
| Redis key 不存在（未预热/已过期） | A 层跳过、B 层补建到 DB 值 | 无 |
| 对账覆盖用户已预扣的合法单 | 只有"差异大/连续差"才修，且以 DB 为准 | 低 |
| MQ 消费积压导致 DB 滞后 | DB 滞后时 Redis 偏小，A 层会把 Redis 回补到 DB → 可能短暂放行超卖 | 中，需接受（A 层 5min 内 MQ 会追平） |
| 凌晨全量校准影响 | B 层低峰执行，无并发干扰；放宽阈值（≥1）彻底对齐 | 无 |
| 多实例并发对账 | 秒杀集群化后需分布式锁（复用 #4 定时任务锁思路）；单机无此问题 | 低 |

> **关键权衡诚实说明**：对账"以 DB 为准回补 Redis"在 MQ 积压时，若 DB 滞后，回补 Redis 会让 Redis 短暂大于真实可成交数 → 可能放行超出 DB 当前值的单数。但这些单仍会被 `seckill_stock>=qty` 条件扣减拦下（rows==0 不成交），**不会真正超卖**，只是从"拦截在 Redis"退化到"拦截在 DB"。这是可接受的兜底（DB 条件扣减仍是最终防线）。
