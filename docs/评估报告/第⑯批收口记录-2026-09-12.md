## 三、方法论收获（**提炼候选** —— 每条都配了实测证据）

1. ⭐ **"测试自己也会说谎"，而且它会拦住你自己的修复**：#65 的第一版修复（参数改 `List<OrderItemMessage>`）是**被我自己写的回归测试否掉**的 —— 实测 `SmartMessageConverter` **不按方法参数推断泛型**，集合元素退化成 `LinkedHashMap`。⇒ 教训：**"看起来对"的类型契约，要用框架的真实转换器跑一遍**（不需要 broker 也能测）。
2. ⭐ **判据必须"对你真正要测的东西敏感"**：SSH 那轮我连错两次 ——
   - "sshd **PID 是否变化**" **不是** reload 的判据（sshd 是 `execve` 重执行，**PID 不变**）；
   - "客户端看到的 `Authentications that can continue` 列表" **不反映 `PermitRootLogin`**（它由 `PasswordAuthentication` 决定；root 账号**锁定**也照样列 `password`）⇒ 我据此得出的"root 仍允许密码"是**误报**。
   - ✅ 正确判据：`sshd -T -C user=…,host=…,addr=…`，或者**真去试一次**。
3. ⭐ **"照抄旧结论"= 把别人的判断当事实**：TODO §55 原写"公网可直接暴力破解"，实测 **root 本就是锁定账号** ⇒ 严重度不成立。⇒ 教训：**连"严重度"也要取证**（不只是"有无风险"）。
4. ⭐ **命令的交付方式也是工程的一部分**：`<KEY>` 这类**尖括号占位符**在 PowerShell 里直接报错（`<` 是保留运算符）；`[本地]` / `[服务器]` 的标注**必须做到不可误读** —— 本批两次把本地命令粘进服务器 shell（一次还静默写了个 0 行文件）。⇒ 改进：**把结果写到双方都能读的 `/tmp` 文件**（本批后半程改用这招后，终端关了也不影响取证）。
5. ⭐ **环境事实要先查，再动手**：Ubuntu 24.04 的单元名是 **`ssh`**（不是 `sshd`），且**默认 socket 激活** —— 改端口 / `Match` 需要 `systemctl daemon-reload` + `systemctl restart ssh.socket`（[Ubuntu bug 2069041](https://lists.ubuntu.com/archives/foundations-bugs/2024-June/517043.html)）；generator 处理不当会让 sshd 以**默认配置**运行（[bug 2076023](https://lists.ubuntu.com/archives/foundations-bugs/2024-August/520089.html)）。
6. **观测手段本身可能是错的（与既有文档同族）**：`e2e_probe.py` **刻意不查 `/actuator/health`** —— 2026-09-10 那次"21 容器全 Up、health 200、业务挂 24.5 小时"里，坏的是**组件之间那条路**。另实测两条本项目判据：**鉴权失败是 HTTP 200 + body `state=401`**（不是 401 状态码）、**所有业务 API 都需登录** ⇒ 只看状态码的监控会把"没登录"当"一切正常"。

> ✅ **已落地的提炼（2026-09-12）**：#70 的两个真缺陷已提炼为 [[问题解决--消息可靠性与毒消息治理]] **§四 问题 3**（现象两副面孔 / 根因表 / off-by-one 伴随缺陷 / 4 条可复用修复 / 面试话术），并在该节**显式更正**了原 §3.2 的设计前提。

7. **"单实例重启必然有一段 503 窗口"**（2026-09-12 实测）：`mall-order` 应用启动 **60.9 s**（容器创建 → 就绪≈76 s），网关侧 `removed ips(1) mall-order` → **`No servers available for service: mall-order`** → `new ips(1)` 共 **≈66 s** —— 期间所有 `/oms/**` 请求 **503**。⇒ **别在演示/录像时重启服务**；要消灭该窗口只能起**双实例**（像秒杀那样）。**判据**：`docker logs csmall-gateway | grep "No servers available"`。

**提炼建议**：第 2、3 条**建议并入** [[问题解决--代码与线上不一致的静默失效]]（它已有 §四"变更做了≠生效了"，本批的两条正好是"**判据不敏感 / 严重度未验证**"的新增面）；若想单独成篇，题目可用《**判据要对你真正要测的东西敏感 —— 三次误判复盘**》。第 1 条适合并入 [[问题解决--压测结论的可信性（先证伪干扰项与工具自身）]]（"工具自身会说谎"）。

## 八、收尾之二：**#72 秒杀队列终止态可观测性**（已实施并实测闭环）

### 8.1 设计与关键约束

| 决策 | 原因 |
|---|---|
| 代码声明 `seckill_ex_dlx` / `seckill_queue_dlx` / 绑定 + `SeckillDlxConsumer`（方法级监听 + 原始 `Message` + `【MQ死信告警】` + 不手动 ack） | 与 order 侧同款口径；方法级监听避免 #65 那类「按载荷类型挑方法」失效；不手动 ack 避免 #70 E 的 406 |
| **主队列 `seckill_queue` 保持零参数，死信改由 broker policy 施加** | 🔴 该队列**早已存在**于 broker，RabbitMQ **不允许修改已存在队列的参数**（加了 `x-dead-letter-*` 就 `PRECONDITION_FAILED` ⇒ 容器起不来、消费断流）。policy 路线**不动参数、不删队列、不丢消息** |
| 回归测试断言「主队列**必须没有**死信参数」 | 防止后人「顺手」加回声明里，把生产消费弄断 |

### 8.2 实测闭环（构造毒消息 `quantity=999999` ⇒ `rows==0`，数据安全：事务回滚、零业务写入）

```
① AmqpRejectAndDontRequeueException: 秒杀落库失败(rows==0)，拒绝且不重投
② 【秒杀落库留痕】DB库存扣减失败 … requeue 0/3            ← 共 3 次（= max-attempts）
③ 【MQ死信告警】… 原因: reason=rejected count=1 exchange=seckill_ex queue=seckill_queue，
   消息体: {"skuId":…,"orderSn":"POISON-SECKILL-20260912","quantity":999999}   ← 原文保留 ✅
```

终态：`seckill_queue` **0 / 2 消费者**、`seckill_queue_dlx` **0 / 2 消费者**；两台容器内 jar 均 `00a2fcb4cf6acde413d64aa4468de584`、HTTP 200；老机 `.env` 已收紧为 **`640 ecs-user:docker`**（与「新机口径」一致，AI 账号在 docker 组仍可读）。

### 8.3 本轮的三个「纪律」新增

1. **部署顺序**：**先部署声明 DLX 组件的版本，再打 policy** —— 否则 `dead-letter-exchange` 不存在，被 reject 的消息会**再次被静默丢弃**。
2. **policy 属 broker 侧配置（不在仓库）** ⇒ Mnesia 卷丢失/重建 broker 后必须**重新施加**；已在代码注释 + TODO #72 + 问题解决文档三处登记。
3. **「修好重投」≠「修好可观测性」**：把「无限重试」改成「拒绝」时，必须追问「拒绝之后这条消息去哪了」。
