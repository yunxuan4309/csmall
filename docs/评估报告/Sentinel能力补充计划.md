## 二、🟠 P1：热点参数限流（秒杀爆款精准保护）—— **与 #5-P1 同一件事**

- **秒杀商品详情 / 下单按 `spuId` 限流**：
  - 爆款 `spuId`（销量高）限 **QPS=100**
  - 普通 `spuId` 限 **QPS=1000**
  - 未配置的商品**不限**
- **价值**：精准保护热点，不误伤其他商品（当前整接口共享 QPS=10，**互相误伤**）
- **成本**：中（`ParamFlowRule` + Nacos 规则 + 秒杀接口改造）
- **面试价值**：高（"热点参数限流 + 秒杀爆款"是电商标准玩法）

**实施步骤**

1. 秒杀相关接口（商品详情 / 下单）加 `ParamFlowRule`：
   - 参数索引 = `spuId`
   - 爆款阈值 = 100，普通 = 1000
2. Nacos 建 `mall-seckill-hot-param-rules` dataId（**规则 JSON 仍以 `deploy/docker/sentinel/` 为事实来源**，先改仓库再发 Nacos）
3. **验证**：压测爆款 `spuId` 限流生效、普通 `spuId` 不受影响

> ⚠️ **实测提醒（2026-09-11 压测标定带出的坑）**：秒杀 / 订单侧接口**限流靶子不好选**——`load_test.py` 限流档实测 `支付订单` 只有 **0.66%** 被限流（583 次全被 `@Idempotent` 的 `409` 挡在前面），**`adminLogin` 才是干净靶子（93.26%）**。做 P1 验证前要先确认**靶子接口的拦截顺序**（幂等锁 / SSO / Sentinel 谁先命中），否则压出来的数字说明不了限流生效。

## 三、🟡 P2：集群流控（与秒杀集群化配套）

- **秒杀集群化后启用**（老机 10007 + 新机 10017 双实例）：
  - token server 统一计数，多实例**共享 QPS 配额**
  - 否则每实例各自 QPS=10 → **集群总量 20，限流值失真**
- **价值**：集群化后限流准确（解"副本后 QPS 翻倍"的坑）
- **前置**：~~[[集群化与配置中心迁移方案]] 阶段 B 实施后~~ → ✅ **前置已满足**（跨机双实例 2026-09-09 上线，并完成负载分布 30:30 / 停实例剔除演练）
- **成本**：中高（需 token server 部署 + 规则改造）

**实施步骤**

1. 部署 token server（`sentinel-token-server` 独立服务）
2. 双实例配置 token-server 地址
3. 规则改集群模式（`clusterMode=true`）
4. **验证**：两实例共享配额，**总量 10 不翻倍**

> ⚠️ **跨机版的新增约束（原方案未考虑）**：两个实例现在**跨两台机器**（老机 + 新机），token server 自身成了**跨机单点** —— 要么与 Sentinel dashboard 同机放老机，要么接受"token server 挂 → 退化为单机限流"。面试话术要把这层**新的单点**讲清楚。

## 五、风险与回滚（仅 P1 / P2）

| 风险 | 等级 | 缓解 |
|---|---|---|
| P1 热点参数配置错误 | 低 | 先在测试环境验证 `spuId` 参数索引；阈值从宽起步 |
| P1 规则太严误伤正常商品 | 低 | "未配置的商品不限" + 控制台实时看 QPS |
| P2 token server 单点（**跨机后更明显**） | 中 | 与 dashboard 同机；保留"退回单机模式"的开关 |
| P2 改 `clusterMode` 后两实例行为不一致 | 中 | 一个维护窗口内两实例同时改；先备份 Nacos 规则（可秒回） |

**回滚**：P1 删 `mall-seckill-hot-param-rules` dataId + 摘掉 `ParamFlowRule`；P2 把 `clusterMode` 改回 `false`（各实例独立限流）→ 均**零数据风险**。
