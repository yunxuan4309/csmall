## 二、新发现的 3 个硬障碍（**已定夺，2026-09-09**）

> ✅ **决策记录（2026-09-09 用户拍板，含一次修订）**
> 1. **跨机 Dubbo → 走 Path 1（`DUBBO_IP_TO_REGISTRY` + 端口映射）**：符合 Dubbo 官方为"容器 + 端口映射"场景提供的机制，不依赖网络技巧；代价 = 重启老机 product/order 各约 1 分钟（并入窗口 A，分两步安全落地）
>    > 📌 **修订说明**：初版推荐 Path 2（静态路由 + host 网络），复核后认定它是"手工版 overlay"——依赖对端网段稳定、无自愈、单向可达，**不属于行业规范做法**，故改回规范路径。Path 2 保留为回退方案。
> 2. **Redis 客户端 → 全量迁移 11 个服务到哨兵模式**（canary 灰度 1→3→全量）
> 3. **阶段 0 暂不动代码**：方案先行，等窗口时间敲定后再实施

### 🔴 障碍 1：跨机 Dubbo provider 不可达（原纪要只提了"注册 IP"，实际更严重）

事实 #4：**所有 Dubbo provider 注册的都是容器 IP `172.18.0.x:20880`**。新机秒杀副本要消费 product/order 的 Dubbo 服务，而 `172.18.0.0/16` 是老机的 docker bridge 网段，**新机根本路由不到**（且新机若自建同名网段还会 IP 冲突）。

**根因（原理，必须讲清）**：Dubbo 的地址解析链是
```
消费方订阅接口 → Nacos 返回 provider 地址列表 → 消费方【直连】该地址
```
**Nacos 只做注册发现，不做流量代理**——它不是网关，不会替你转发请求。因此**注册进注册中心的地址，必须是"消费者能直连的地址"**。容器默认注册 bridge 网段 IP（`InetAddress.getLocalHost()` 拿到容器 IP），单机内同网段容器互通所以一直没暴露问题，**跨机立刻断**：

```
新机秒杀副本 → 问 Nacos 要 IForSeckillSpuService 的地址
             → 拿到 172.18.0.18:20880（老机 bridge 网段）
             → 新机路由表里没有 172.18.0.0/16
             → 连不上 → No provider available from registry / client-side timeout
```

**运行时行为（排错必须知道）**：Dubbo 默认 `random` 负载均衡 + `Failover` 集群容错（`retries=2`）+ 本项目 `consumer.check: false`（启动不校验 provider）→ **provider 不可达不会导致启动失败，只在调用期报错**。所以跨机排错不能只看"服务起没起来"，要看消费方调用日志关键词：`No provider available from registry` / `Waiting server-side response timeout` / `Failed to invoke the method`。

**两条解法**：

| 路径 | 做法 | 改谁 | 重启 | 影响面 | 风险 |
|---|---|---|---|---|---|
| **✅ Path 1（已选定）** | 老机 product/order 加 `DUBBO_IP_TO_REGISTRY=172.29.193.239` + `DUBBO_PORT_TO_REGISTRY` + 发布 `20880:20880`/`20881:20880` | 老机 2 个服务 | **要重启 product/order** | 全站 Dubbo 消费方改走宿主 IP | 🟡 中（可分两步降风险） |
| Path 2（回退方案） | 新机加静态路由 `172.18.0.0/16 via 172.29.193.239` + 新机容器 host 网络 | 只改新机 | 无 | 仅新机 | 🟡 依赖老机网段、无自愈 |

**为什么选 Path 1（规范优先）**：
- `DUBBO_IP_TO_REGISTRY` / `DUBBO_PORT_TO_REGISTRY` 是 **Dubbo 官方为容器/NAT 端口映射场景提供**的机制（[主机配置](https://cn.dubbo.apache.org/zh-cn/overview/mannual/java-sdk/tasks/framework/more/set-host/) / [部署到 Docker](https://cn.dubbo.apache.org/zh-cn/overview/mannual/java-sdk/advanced-features-and-usage/others/docker/)）→ 声明式、不依赖网络技巧、无"网段变更即失效"隐患
- **改动面比预想小**：实测 `mall-seckill` **无任何 HTTP/Feign 调用**（`@FeignClient`/`RestTemplate` 零命中），跨机依赖**只有 Dubbo**，且只需老机 **product + order** 两个 provider 改注册
- **对老机本地消费方无副作用（已实测）**：容器 → 宿主私网 IP 的映射端口**可达**（`csmall-mysql` 内 `/dev/tcp/172.29.193.239:8848|5672|9200` 全部 OK）→ 本地消费方走宿主 IP 只多一跳 docker-proxy（毫秒级）
- **两步落地降风险**：先发端口并验证 → 再改注册 IP 重启；端口不通就不动注册

**Path 2 的短板（为什么放弃）**：① 不声明式、无自愈，路由丢了就断；② 依赖老机 `csmall_csmall-net` 网段稳定；③ 只打通单向；④ 违反"容器网络由编排层负责"的分层原则——面试被问"为什么不用 overlay/K8s"时只能答"演示级取舍"

### 🔴 障碍 2：Redis 客户端是 standalone，**哨兵切换后"业务无感"不成立**

事实 #11：11 个服务全部配 `spring.data.redis.host=redis`（standalone）。
- kill 老机 Redis → 哨兵把新机从库提升为主 → **老机 Redis 容器重启后变成从库（只读）**
- 此时 11 个服务仍连老机 Redis → **全部写操作报 `READONLY You can't write against a read only replica`** → 登录/秒杀/幂等全挂

→ 要兑现"业务无感切换"，**已定夺：把 11 个服务改成 sentinel 模式**（`spring.data.redis.sentinel.master/nodes`），纯配置改动（compose 注入 env），需**重启 11 个服务**（窗口 B，canary 灰度见 §六：1 → 3 → 全量）。

### 🟡 障碍 3：跨机地址稳定性 → 必须发布 MySQL/Redis 到宿主内网 IP

- 新机秒杀副本要连老机 MySQL/Redis。若走"容器 IP"（配合障碍 1 的路由）→ **容器一旦重建 IP 可能变**，配置即失效；哨兵监控的 master 地址更不能是容器 IP（哨兵会把它写进配置并长期使用）

- 代价：需重建 mysql/redis 容器（**数据在卷里不丢**，约 15~30s 抖动）→ 窗口 A

## 三、阶段 0：定时任务分布式锁（代码，无服务器依赖）

### 3.1 目标
秒杀双实例后，`@Scheduled` 任务**每 tick 只允许一个实例执行**；不引入新依赖（不引 ShedLock），复用项目已有 SETNX 写法。

### 3.2 改造范围（**只改 mall-seckill，不动 mall-common**）
> 为什么不放 mall-common：`mall-common` 被 11 个 jar 依赖，改它=11 个 jar 全量重建重部署；放 mall-seckill 则只重建 seckill 一个 jar，blast radius 最小。

| 文件 | 改动 |
|---|---|
| `mall-seckill-webapi/.../utils/RedisLockUtils.java` | **新增**：`tryLock(key, ttl)` / `unlock(key, token)`（SETNX + Lua CAS 释放） |
| `.../task/MessageRetryTask.java` | 方法体包一层锁，key=`mall:seckill:lock:message-retry`，TTL 30s |
| `.../task/SeckillReconcileTask.java` | `reconcileOnline` key=`...:lock:reconcile-online` TTL 5min；`reconcileDaily` key=`...:lock:reconcile-daily` TTL 30min |

### 3.3 锁语义设计（面试要讲清的点）

```
tryLock：SET key <token> NX EX <ttl>   —— 单命令原子，NX 保证互斥，EX 兜崩溃
unlock ：Lua 比较 token 再 DEL        —— 只删自己加的锁，防"释放别人的锁"
TTL    ：远大于任务耗时（兜进程被杀/网络断），任务正常结束显式释放
```

**为什么不用"只靠 TTL 不释放"**：那样锁窗口内另一个实例的 tick 会被自己人挡掉，任务实际频率腰斩；**显式释放 + TTL 兜底**既保证不并发双跑（互斥），又保持原有节奏。
**为什么并发才是问题**：`MessageRetryTask` 是"扫表 → 发 MQ → 标记已发"，两个实例**同时**扫会拿到同一批 pending 记录 → **重复发消息**；串行执行则后一次扫描时前一次已标记 `status=1`，安全。

### 3.4 代码骨架

```java
// mall-seckill-webapi/.../utils/RedisLockUtils.java
@Component
public class RedisLockUtils {
    /** 释放锁：仅当 value 与 token 一致才删（防误删他人锁） */
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
            Long.class);

    private final StringRedisTemplate redisTemplate;

    public RedisLockUtils(StringRedisTemplate redisTemplate) { this.redisTemplate = redisTemplate; }

    /** 尝试加锁，成功返回 token（释放凭证），失败返回 null */
    public String tryLock(String key, Duration ttl) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redisTemplate.opsForValue().setIfAbsent(key, token, ttl);
        return Boolean.TRUE.equals(ok) ? token : null;
    }

    /** 释放锁（Lua 原子比较并删除） */
    public void unlock(String key, String token) {
        if (token == null) return;
        redisTemplate.execute(UNLOCK_SCRIPT, Collections.singletonList(key), token);
    }
}
```

### 5.3 compose 新增（同一份文件，**仅新机启动**）

```yaml
  # ===== 跨机集群：仅新机（csmall-node2）启动 =====
  redis-replica:
    image: redis:7-alpine
    container_name: csmall-redis-replica
    network_mode: host                       # 关键：注册宿主内网 IP，无需 announce 覆盖
    command: ["redis-server", "/usr/local/etc/redis/redis-replica.conf"]
    volumes:
      - ./redis/redis-replica.conf:/usr/local/etc/redis/redis-replica.conf
      - redis_replica_data:/data
    mem_limit: 256m
    restart: on-failure

  redis-sentinel-1:
    image: redis:7-alpine
    container_name: csmall-sentinel-1
    network_mode: host
    command: ["redis-server", "/usr/local/etc/redis/sentinel-1.conf", "--sentinel"]
    volumes:
      - ./redis/sentinel-1.conf:/usr/local/etc/redis/sentinel-1.conf
      - sentinel_1_data:/data
    mem_limit: 128m
    restart: on-failure
  # redis-sentinel-2 / -3 同构（port 26380 / 26381）
```
+ 顶部 `volumes:` 追加 `redis_replica_data:`、`sentinel_1_data:` 等。
> **为什么 Redis/哨兵用 host 网络、而秒杀副本用 bridge**：Redis 没有注册中心，唯一要求是"主/哨兵看到的是可达地址"——host 网络天然满足（`replica-announce-ip` 只是防御性冗余）；秒杀副本必须在 Nacos/Dubbo 注册**宿主 IP + 映射端口**，故用 bridge + 显式覆盖，与老机同构。
> **新机启动命令永远带服务名**：`docker compose up -d redis-replica redis-sentinel-1 redis-sentinel-2 redis-sentinel-3`（不带服务名会把老机的 21 个服务一起拉起来）。

> 🔴 **阶段 3 踩的坑（三层，逐层剥开，详见 [[TODO第三批实现与原理]] §5.4）**：
> 1. `not writable: Permission denied` → conf 属 `ecs-user(1000)`，容器内 redis 是 **uid 999** → `chown 999:1000` 文件；
> 2. `Could not create tmp config file` → 容器内 `/usr/local/etc/redis/` 属 **root** → 改挂到 `/data`；
> 3. `Could not rename tmp config file (Resource busy)` → **单文件 bind-mount 不能被 rename 覆盖**（Docker 固有限制）→ **改为挂目录 `./redis:/conf`** + 宿主目录 `chown 999:1000`。
>
> 结论：**Redis Sentinel 的配置必须放在「目录挂载」里且属 uid 999**，否则它无法持久化故障转移状态（重启后退回监视旧主）。

### 5.6 可选加固：`min-replicas-to-write 1`（TODO #14-P2）```conf
min-replicas-to-write 1
min-replicas-max-lag 10
```
- ✅ 好处：主库在"从库失联"时**拒绝写入**，防切换丢数据（面试点）
- ⚠️ 代价：**新机宕机 → 老机主库拒绝所有写入 → 全站不可用**。必须**从库同步成功后再开**，且要接受这个取舍（回滚 = 改回 0 并 `CONFIG REWRITE`）
- 建议：演练时开启（讲清取舍），日常演示期可留 0

## 六、阶段 3.5：客户端迁移哨兵模式（新增，窗口 B 下半场）

> **不做的后果**：障碍 2——切换后 11 个服务全部 `READONLY`，"业务无感"是假的。

### 6.1 改动（compose env，11 个服务各加 2 行）

```yaml
      SPRING_DATA_REDIS_SENTINEL_MASTER: mymaster
      SPRING_DATA_REDIS_SENTINEL_NODES: 172.29.193.240:26379,172.29.193.240:26380,172.29.193.240:26381
      # SPRING_DATA_REDIS_PASSWORD 保持不变（数据节点密码）；SPRING_DATA_REDIS_HOST 会被忽略，可留可删
```
> Spring Boot 3.2 原生支持 `spring.data.redis.sentinel.*`；配置了 sentinel 后 `host/port` 自动失效。哨兵无密码，故**不设** `SPRING_DATA_REDIS_SENTINEL_PASSWORD`。

### 6.2 灰度顺序（防 11 个服务一起起不来）

```
① 金丝雀 1 个低影响服务（mall-resource 或 mall-search）→ 重启 → 验证 Redis 读写 + 业务接口
② 扩大到 3 个（sso / product / front）
③ 全量（order / seckill / ums / ams / ai / gateway）
④ 每个服务验证：日志无 Redis 连接异常；接口回归（登录/商品详情/下单）
```
| 验证 | 命令 |
|---|---|
| 客户端真的走了哨兵 | `docker logs csmall-xxx --tail 50 \| grep -i sentinel`；或 kill 老机 Redis 后看服务是否自动连新主 |
| 故障转移端到端 | 停老机 Redis → 秒杀下单/登录**成功** → 起老机 Redis |
| 回滚 | 去掉两个 env → `docker compose up -d <服务>`（standalone 立刻恢复；若此时主库已在新机，需先切回或临时把 host 指向新机） |

### 6.3 实施结果（2026-09-09 实测，✅ 已完成）

| 项 | 结果 |
|---|---|
| 配置注入 | 11 个服务均注入 `SPRING_DATA_REDIS_SENTINEL_MASTER=mymaster` + `SPRING_DATA_REDIS_SENTINEL_NODES=172.29.193.240:26379,26380,26381`（抽样 gateway/seckill/front/sso 已确认） |
| 灰度批次 | ① `mall-resource` ② `mall-front`+`mall-product`+`mall-search` ③ `mall-sso`+`mall-ums`+`mall-ams` ④ `mall-order`+`mall-seckill`+`mall-ai`+`mall-gateway` |
| 启动结果 | 全部 `Started` + `/actuator/health=200`；启动耗时（第4批 4 服务并发）：gateway 106s / ai 154s / order 178s / seckill 181s |
| 错误检查 | 11 个服务近 10 分钟 **Redis 相关错误 0 条**（`RedisConnectionFailure`/`NOAUTH`/`WRONGPASS`/`Cannot connect`） |
| **行为验证（关键）** | `mall-seckill` 的 Redis 对端地址由 **`172.18.0.5:6379`（容器 IP，standalone）→ `172.29.193.239:6379`（宿主 IP，哨兵模式）**；预热任务 2 分钟 44 条日志、零异常 → **客户端确实通过哨兵解析主库** |

| 冒烟 | nginx 200 / gateway health 200 / nacos 200 |

> 💡 **验证经验（值得记）**：
> 1. **Lettuce 是懒连接**——服务启动后若没业务访问 Redis，`/proc/net/tcp` 里看不到连接。所以"没连接"≠"配置错了"。
> 2. **哨兵连接是瞬态的**：客户端只在**解析主地址时**连哨兵（26379-26381），之后只保留到主库的长连接 → 用"有没有连哨兵端口"来判断哨兵模式是**错误判据**；正确判据是**主库连接的对端地址是宿主 IP 还是容器 IP**。
> 3. **`mall-resource` 是弱金丝雀**：它几乎不访问 Redis，只能验证"配置没把服务搞挂"，验证不了"真的走了哨兵"。真正的行为验证要用**有定时任务读写 Redis 的服务**（如 `mall-seckill` 的 Quartz 预热）。

## 十一、面试话术（本批可讲点）

1. **跨机容器互通的两种解法**：注册宿主 IP + 端口映射（Dubbo 官方 `DUBBO_IP_TO_REGISTRY`，规范做法）vs 静态路由打通 bridge 网段（手工版 overlay，非规范）——我选了前者，因为它声明式、无"网段变更即失效"隐患
2. **哨兵为什么必须 3 个**：多数派机制，容忍度 =(N-1)/2；2 哨兵挂 1 个即失去仲裁（不是"奇数迷信"）
3. **主从切换的业务无感前提**：客户端必须配 sentinel 模式——standalone 客户端在切换后打到只读从库会 `READONLY`（我实测扫过 11 个服务的 Redis 写点）
4. **双实例定时任务**：SETNX+TTL 互斥 + Lua CAS 释放；并发才是问题（同批 pending 会被重复发 MQ）
5. **注册 IP 陷阱**：容器默认注册 bridge IP，跨机不可达；两条标准解法——`DUBBO_IP_TO_REGISTRY`/`SPRING_CLOUD_NACOS_DISCOVERY_IP`（注册层改写）或 host 网络（网络层）
6. **诚实边界**：2 台小机 = 演示级 HA，不防地域灾难；其余 19 容器仍是老机单实例

## 十二、知识补充：文件完整性校验（哈希指纹）

> 起因：本批每次下发 compose/配置/jar，AI 都要求"本地算 md5 → 你落位后 `md5sum` 比对"。这不是仪式，是**内容寻址（content addressing）**这一通用工程实践的手工版。

### 12.1 我们为什么需要它

跨机下发要经过 **4 跳**：`本地仓库 → scp → 服务器 /tmp → sudo cp → /data/csmall`。每一跳都可能静默出错：

| 风险 | 具体表现 | 本批是否遇到过 |
|---|---|---|
| 换行符转换 | CRLF ↔ LF 差异 | 是（git 换行警告） |
| 编码/BOM | UTF-8 BOM 使首行解析异常 | 是（写 Java 校验工具时） |
| 传输截断 | 大文件中断、磁盘满 | 未遇到（但有风险） |
| 复制不完整 | `cp` 失败/权限不足被忽略 | 未遇到（但有风险） |

> ⚠️ **本仓库自身就有此风险**：每次 `git add` 都提示 `LF will be replaced by CRLF`——说明本机 `core.autocrlf` 会在检出时改写换行符。所以"本地文件与服务器文件是否同字节"**不能靠肉眼，只能靠哈希**。

**哈希 = 文件内容的"身份证"**：内容差 1 个字节（哪怕一个空格、一个换行），32 位十六进制全变。所以 `md5sum` 一致 ⟺ **服务器上的文件与仓库里的文件字节级相同**。

它把"仓库为事实来源"这条纪律从**口号**变成了**可验证的断言**——这是本批最实用的一条运维纪律（已并入 §开头「命令块纪律」第 6 条）。

### 12.2 它是版本号吗？—— 不是

| | 版本号 | 哈希指纹 |
|---|---|---|
| 语义 | 人为命名，单调递增（`v1.2.0`） | 内容的数学函数，无顺序含义 |
| 用途 | 沟通、发布、回滚标记 | **校验"是不是同一份内容"** |
| 改内容会怎样 | 需要人工改 | **自动全变**（这正是我们要的） |

所以本批记录的 `compose md5 b6591fac…` 只回答一个问题："两台机器/仓库里的 compose 是同一份吗？"——不表达"这是第几版"。

### 12.3 行业规范吗？—— 是，而且企业里更自动化

| 场景 | 行业做法 |
|---|---|
| 软件分发 | 发行版 ISO 公布 **SHA-256**；Maven Central 每个制品旁挂 `.sha1`/`.md5` |
| 容器 | 镜像 **digest = `sha256:…`**（内容寻址；`image@sha256:…` 拉取即校验） |
| K8s | ConfigMap/Secret 变更触发滚动更新靠**内容哈希**（Helm `checksum/config` 注解） |
| CI/CD | 制品完整性、SBOM、**SLSA** 供应链 |
| 备份 | `mysqldump \| sha256sum`，恢复后比对 |
| 配置管理 | Ansible/GitOps 下发后做**漂移检测（drift detection）** |

> 我们做的是**手工版**（AI 算 + 人比对）；企业里是**自动版**：CI 产出制品并记录 digest，Ansible/Argo CD 下发后自动比对并报告漂移。**原理完全相同，只是被自动化了。**

### 12.4 局限与更优选择（诚实边界）

1. **MD5 已被证明可构造碰撞**（2004 年起）→ **防"意外损坏"够用，防"恶意篡改"不够**
2. 现代默认应选 **SHA-256**；本批场景是防意外（传输/编码/截断），MD5 可接受，但换 `sha256sum` 更规范
3. 更好的演进路径（择机做，对应 TODO #39）：
   - ① 改用 `sha256sum`（零成本）
   - ② 配置纳入 git，服务器 `git pull` —— git 的对象哈希天然完成校验
   - ③ CI 构建 + 制品 digest 下发（彻底告别手工比对）
