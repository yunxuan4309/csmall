### P0-1: ES 集群状态 Red — `cool_shark_mall_index2` 主分片未分配

**问题描述**:

ES 集群 (单节点) 当前状态为 `red`，共 13 个未分配分片。其中**绝大多数是副本分片**（单节点无法分配副本，属正常现象），但 **`cool_shark_mall_index2` 索引的主分片状态为 `ALLOCATION_FAILED`**，这是商品搜索的业务索引，可能导致搜索功能异常。

```
# 当前状态
"status": "red"
"active_primary_shards": 72
"active_shards": 72
"unassigned_shards": 13
"active_shards_percent": 84.7%

# 关键故障分片
cool_shark_mall_index2  0  p  UNASSIGNED  ALLOCATION_FAILED  ← 主分片！
```

**根因分析**:

单节点 ES 上，13 个未分配分片的构成：
- **12 个副本分片** (SkyWalking 索引): 单节点无法分配副本，`INDEX_CREATED` / `CLUSTER_RECOVERED` — 这是正常的，改 `number_of_replicas: 0` 即可消除
- **1 个主分片** (`cool_shark_mall_index2`): `ALLOCATION_FAILED` — 这可能是曾经重启 ES 或磁盘空间不足时导致的分配失败，需要排查

**解决方案**:

```bash
# === Step 1: 诊断那个失败的主分片 ===
curl -s 'http://localhost:9200/_cluster/allocation/explain?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "index": "cool_shark_mall_index2",
    "shard": 0,
    "primary": true
  }'

# 看返回的 "explanation" 和 "can_allocate" 字段，
# 常见原因：磁盘空间不足、分片损坏、节点离开又加入

# === Step 2a: 如果分片数据已损坏或无法恢复 → 重建索引 ===
# 删除旧索引
curl -X DELETE "http://localhost:9200/cool_shark_mall_index2"

# 重新同步（通过 mall-ai 服务的同步接口）
docker exec csmall-frontend curl -X POST http://mall-ai:10010/api/ai/sync

# === Step 2b: 如果 explanation 显示可以重新分配 → 强制重试 ===
curl -X POST "http://localhost:9200/_cluster/reroute?retry_failed=true"

# === Step 3: 将所有索引的副本数改为 0（单节点不需要副本） ===
curl -X PUT "http://localhost:9200/_all/_settings" \
  -H 'Content-Type: application/json' \
  -d '{"index": {"number_of_replicas": 0}}'

# === Step 4: 验证恢复 ===
curl -s http://localhost:9200/_cluster/health?pretty
# 预期输出: "status": "yellow"  ← 单节点没有副本，yellow 是正常的！
# "unassigned_shards": 0
# "active_shards_percent": 100%
```

**重要说明**: 单节点 ES 集群在设置 `number_of_replicas: 0` 之后，状态为 **yellow 是完全正常的**（主分片全部可用，只是没有副本）。只有单节点才能变成 green，但那是浪费资源。**目标不是 green，而是 unassigned_shards = 0 的 yellow。**

**验证搜索功能正常**:

```bash
# 访问前端搜索一个商品，确认搜索能返回结果
```

## 🟡 P1 — 尽快修复（影响稳定性和性能）

### P1-1: 服务器内存使用率 93% — JVM 堆外内存未限制

**问题描述**:

11 个 Java 微服务容器的**实际物理内存消耗远超过 `-Xmx` 堆上限**，原因是 JVM 堆外内存（Metaspace、线程栈、NIO Direct Buffer、JIT 编译缓存）未设置上限，导致内存持续膨胀。

```
总内存 14Gi | 已用 ~13Gi | 可用仅 ~1Gi

Java 容器实际 vs 配置对比:
容器            -Xmx配置    实际RSS     差值(堆外)
mall-product    448MB      906MB       +458MB
mall-order      448MB      843MB       +395MB
mall-seckill    448MB      764MB       +316MB
mall-ai         384MB      714MB       +330MB
mall-ums        256MB      644MB       +388MB
mall-front      384MB      630MB       +246MB
mall-search     256MB      622MB       +366MB
mall-ams        256MB      616MB       +360MB
mall-sso        256MB      550MB       +294MB
mall-gateway    256MB      518MB       +262MB
mall-resource   256MB      428MB       +172MB
-------------------------------------------
11个微服务合计  ~3.6GB     ~7.2GB      +3.6GB 堆外！

中间件:
Seata           -          1.46GB      (JVM, 未设 -Xmx)
SkyWalking OAP  1024MB     1.17GB      (接近上限)
Nacos           -          963MB       
ES              512MB      1.12GB      (OS 文件缓存)
```

**解决方案 — 给每个 Java 容器加 JVM 堆外限制**:

在 `docker-compose.yml` 中，给每个 Java 微服务添加 `JAVA_TOOL_OPTIONS` 环境变量。以下为各服务的具体配置：

```yaml
# ====== 各服务 JVM 参数模板 ======
# 
# -XX:MaxMetaspaceSize=128m    限制类元数据（默认无上限！这是最大的泄漏源）
# -XX:ReservedCodeCacheSize=64m  限制 JIT 编译缓存
# -XX:MaxDirectMemorySize=64m    限制 NIO 堆外直接内存
# -XX:+UseStringDeduplication    启用字符串去重，节省堆内存
# -XX:+UseG1GC                   使用 G1 垃圾回收器（低延迟）
# -XX:MaxGCPauseMillis=200       限制单次 GC 暂停时间

# ====== mall-gateway (当前 RSS 518MB, -Xmx256m) ======
mall-gateway:
  environment:
    JAVA_TOOL_OPTIONS: >
      -Xms128m -Xmx256m
      -XX:MaxMetaspaceSize=128m
      -XX:ReservedCodeCacheSize=64m
      -XX:MaxDirectMemorySize=64m
      -XX:+UseG1GC
      -XX:MaxGCPauseMillis=200
```

### P1-2: RabbitMQ CPU 偶尔飙到 84%

**问题描述**:

`docker stats` 显示 `csmall-rabbitmq` CPU 偶尔到 84.76%，这通常是瞬时大量消息消费导致的。

**可能原因**:

1. 有积压的消息队列在被消费
2. 秒杀相关的异步消息集中到达
3. `seckill_message_retry` 表中有 4 条重试记录，可能有消息在反复重试

**排查步骤**:

```bash
# 1. 查看当前队列积压情况
docker exec csmall-rabbitmq rabbitmqctl list_queues name messages messages_ready messages_unacknowledged

# 2. 查看重试表
docker exec csmall-mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" \
  -e "SELECT * FROM cs_mall_seckill.seckill_message_retry;"

# 3. 如果有大量积压，检查消费者是否正常运行
docker logs csmall-seckill --tail 50 | grep -i error
docker logs csmall-order --tail 50 | grep -i error
```

## 🟢 P2 — 有暇时处理（不影响核心功能）

### P2-1: RedisBloom 模块缺失 — 秒杀布隆过滤器用 Set 兜底

**现状**:

服务器 Redis 7 Alpine 镜像未包含 RedisBloom 模块，`BF.ADD` 等命令不可用。当前秒杀代码使用 `Redis Set`（`SADD`/`SISMEMBER`）替代布隆过滤器。

**影响评估**:

| 维度 | RedisBloom | Redis Set (当前) | 影响 |
|------|-----------|-----------------|------|
| 内存效率 | 10 万条 ≈ 120KB | 10 万条 ≈ 5MB | 当前仅 6 场秒杀，差异可忽略 |
| 查询速度 | O(1) | O(1) | 无差异 |
| 误判率 | ~1% | 0% | Set 反而更精确 |
| 删除支持 | 不支持 | 支持 | Set 更灵活 |

**结论**: 当前数据量下（6 场秒杀、12 个 SKU），影响**可忽略**。未来商品量大了再装。

**以后安装时**:

## ⏸️ P3 — 暂缓（受制于外部条件）

### P3-1: HTTPS/SSL 配置

**阻塞原因**: 没有域名 → 没有 SSL 证书 → 无法配置 HTTPS

```
HTTPS → SSL 证书 → 域名 → ICP 备案 → 服务器续费 ≥ 3 个月
  ↑                                ↑
阻塞在此                      卡在预算（8月29日到期）
```

**临时代替方案**（都不理想）:

1. 阿里云免费 SSL 证书（部分产品支持单域名绑定 IP）
2. Cloudflare Tunnel（需要域名但不需要备案）
3. 接受 HTTP（学习/开发项目可接受）

**以后配置步骤**（等条件具备时）:

```bash
# 1. 安装 certbot
sudo apt install -y certbot

# 2. 获取证书
sudo certbot certonly --standalone -d your-domain.com

# 3. 修改 /data/csmall/frontend/nginx.conf：
#    listen 443 ssl;
#    ssl_certificate /etc/letsencrypt/live/your-domain.com/fullchain.pem;
#    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;
#    
#    # HTTP 自动跳转
```
