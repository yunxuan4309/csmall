## 四、k3s 价值边界（为什么"现在不值"，不是"没用"）

| k3s/K8s 擅长 | 本项目需求 | 匹配度 |
|---|---|---|
| 大量无状态服务统一调度/扩缩容/自愈 | 只有 1 个秒杀副本（无状态） | ❌ 1 个实例不需要调度器 |
| 有状态应用编排 | Redis 主从是 **K8s 里最麻烦的有状态应用**（StatefulSet+PV+哨兵），比裸 compose 更复杂 | ❌ 方向反了 |
| 跨机容器网络 overlay | 唯一有点用，但 2 个成员手动配 IP 即可 | ⚠️ 边际价值小 |
| 滚动更新/灰度 | 演示项目手动 compose up 足够 | ❌ |

**结论**：k3s 的价值在"几十个无状态服务 + 自动扩缩容/自愈"的规模化场景；本项目"2 个 Redis（有状态）+ 1 个秒杀副本（无状态）"**恰好在 k3s 最不擅长的象限**。与 TODO #42、K8s 评估文档结论一致：**k3s 不是跨机演示的前置，是后续学习/规模化的选项**。且注意：k3s 只管它自己调度的容器，老机 21 个 compose 容器不会自动进 k3s，强行引入形成"双轨"，管理复杂度反而更高。面试时"知道 k8s 何时该用、何时不该用"本身就是加分项。

## 五、管理方式（用户已选方案 A）

**方案 A：一套 compose 文件，两机共用，各拉起属于自己的服务**

```
老机：docker compose up -d mysql redis nacos ... mall-seckill      # 拉起主 Redis + 秒杀1 + 全部业务
新机：docker compose up -d redis-replica redis-sentinel-1 redis-sentinel-2 redis-sentinel-3 mall-seckill-2
      # 只拉起从/哨兵/副本
```

**优点**：一份文件、配置同源（Redis 密码/Nacos 地址只维护一份）、每机 `docker compose ps` 看自己的
**备选 B（不用）**：两套独立 compose（老机不动、新机单独文件）——配置要维护两份，易漂移

### 你日常真正要做的管理（极少）

```bash
# 看集群状态（三视角）
docker ps | grep -E "redis|sentinel|seckill"            # 老机+新机各跑（或脚本）
redis-cli -h 老机IP info replication                     # 主视角：role=master / connected_slaves
redis-cli -h 新机IP -p 6380 info replication             # 从视角：role=slave / master_link_status:up
redis-cli -h 新机IP -p 26379 sentinel master mymaster    # 哨兵视角：谁才是当前主

# 更新秒杀副本（发新版）
老机：docker compose up -d mall-seckill
新机：docker compose up -d mall-seckill-2

# Redis 故障演练（面试演示）
docker stop csmall-redis          # 老机主挂 → 哨兵自动提升新机从 → 服务无感
```

**核心认知**：不需要"管理集群"，需要三个**自动机制**各自就位：
1. **Nacos** = 服务发现/故障剔除（秒杀两实例谁活着、gateway 轮询到谁）——已有，自动
2. **哨兵** = Redis 故障转移（主挂→从提升，客户端重连）——需配置，故障时自动
3. **compose** = 进程拉起（每机各自）——已有

**诚实边界**：跨机 = 管理分散在两台机器（日志/ps 分两处看），这是两台机器的固有成本，k3s 只是把命令统一成 kubectl，不减少"要理解两台机器"的事实。

## 七、前置硬障碍（跨机必改，第一批加固的副作用）

### 7.1 MySQL(3306) / Redis(6379) 绑定 127.0.0.1（实测确认）

第一批 #24/R1 把这两个端口收窄到 `127.0.0.1`。**新机副本/从库从内网访问老机 3306/6379 会被拒绝**。

**解法**：compose 端口映射改为绑定**内网 IP**（如 `172.29.193.239:3306:3306`）或 `0.0.0.0`，并在**阿里云安全组层面仅放行两台机器互访**（不是公网 0.0.0.0/0）——纵深防御不降级：
```yaml
# docker-compose.yml
mysql:
  ports: ["172.29.193.239:3306:3306"]   # 或 0.0.0.0 + 安全组限定
redis:
  ports: ["172.29.193.239:6379:6379"]
```
> 注意：老机服务间走容器网络（container 名直连）不受端口映射影响，此改动只影响"外部（新机）访问"路径。

### 7.2 注册 IP（新机容器以容器 IP 注册 Nacos，老机 consumer 不可达）

新机副本默认以容器 IP（172.18.x）注册 → 需显式覆盖为**新机内网 IP**：
```yaml
# 新机副本 env 注入
SPRING_CLOUD_NACOS_DISCOVERY_IP: <新机内网IP>
# Dubbo 注册 IP 同理（dubbo.protocol 或 registry 参数）
```
老机 gateway `lb://mall-seckill` 轮询到新机实例后，需能路由到新机内网 IP:10017（依赖 7.1 的网络 + 新机端口映射）。

### 7.3 秒杀副本连接串全部指向老机

副本无独立数据，所有中间件地址用老机内网 IP（不能再用容器名 `mysql`/`redis`）：
```
SPRING_DATASOURCE_URL: jdbc:mysql://老机内网IP:3306/cs_mall_seckill
SPRING_DATA_REDIS_HOST: 老机内网IP
SPRING_RABBITMQ_HOST: 老机内网IP
Nacos/Sentinel 同理
```

### 7.4 秒杀多实例代码改造（唯一硬改造）

`MessageRetryTask`（每 5s 定时重发）双实例会**双跑** → 需 Redis 分布式锁（SETNX TTL）或 ShedLock（与 #4 单机集群同一改造点，跨机只是把"同机双实例"换成"两机双实例"）。

### 7.5 对账任务并发

P1 对账任务（SeckillReconcileTask）同为 @Scheduled → 也需同一把分布式锁（TODO 第二批已预告"集群化后需加锁"）。

## 八、风险与边界（诚实声明）

| 项 | 说明 |
|---|---|
| 跨机真 HA 的边界 | 2 台小机器防"单机宕机"（老机挂→秒杀流量切新机、Redis 主切新机从）；**不防地域灾难**；其他 19 容器仍是老机 compose 单实例 |

## 十、追问答疑（2026-09-09 第二轮讨论：哨兵角色 / 端口放行 / 面试价值）

### 10.1 哨兵是干嘛的？能承担业务还是只负责投票？

**哨兵不承担任何业务读写——它完全在业务链路之外，是一个"看门人集群"**。业务读写仍直连 Redis（主写从读），哨兵只做三件事：

| 哨兵职责 | 机制 | 类比 |
|---|---|---|
| **监控**（monitor） | 每 1s PING 主/从，`down-after-milliseconds`（5000ms）无响应 → 主观下线（SDOWN） | 看门人定期点名 |
| **通知** | 主挂了 → 告诉客户端"新主是谁" | 广播 |
| **故障转移**（failover） | 多数派确认客观下线（ODOWN）→ 选从提升为主 → 通知其他从改认新主 | 指定接班人 |

**"投票"只发生在故障转移的确认阶段**：哨兵必须**多数派同意（quorum）**才切换——防网络分区脑裂（两边都以为自己是主）。

**为什么 3 哨兵而不是 2（关键认知，面试说这个比"奇数迷信"高一个段位）**：
- 哨兵判定是**多数派**机制：3 哨兵 + quorum=2 → 挂 1 个还剩 2 = 多数，仍能切换
- 容忍度公式：可挂哨兵数 = (哨兵数 - 1) / 2 → 3 哨兵容忍 1 个、2 哨兵容忍 **0 个**（挂 1 就失去仲裁）
- 原定稿方案（Redis配置加固与哨兵模式方案 §1.2）的"2 哨兵"是演示取舍（文档明说"挂 1 个哨兵失去仲裁能力，可接受"）；**跨机改 3 哨兵是更标准做法，代价仅多 1 个 ~50M 容器**
- 注：数据节点（主/从）**不需要奇数**——主从复制不是投票，1 主 N 从任意

**结论：哨兵 = 纯投票/看门角色，零业务；客户端不直连主，而是先问哨兵"当前主是谁"再连（`spring.data.redis.sentinel.*`）——这是业务无感切换的来源。**

### 10.2 MySQL/Redis 改绑定（127.0.0.1 → 内网）复杂吗？

**改动本身很小（🟢 低），但要协调窗口与安全性（🟡 中）**：

```yaml
# compose 仅两处端口映射改动
mysql:  ports: ["172.29.193.239:3306:3306"]   # 127.0.0.1 → 内网 IP
redis:  ports: ["172.29.193.239:6379:6379"]
```

真正要小心的两点：
1. **重启窗口**：改端口映射 = 重建 mysql/redis 容器（数据在卷里不丢，但依赖它们的全站服务要重启一次）→ 必须与副本部署同一维护窗口
2. **安全组**：放开后攻击面从"仅本机"变"内网可达" → 阿里云安全组**只允许新机内网 IP 访问 3306/6379**，不能裸 0.0.0.0

**关键安心点**：老机服务间走**容器网络**（container 名直连），不走端口映射 → 此改动只影响"从新机来的流量"，老机自身服务零影响。风险不在"改错"，在"协调时机 + 安全组收口"。

### 10.3 这套方案值得面试讲吗？

**值得，而且是第三批里面试价值最高的组合**（TODO 推荐路线 P1 = #4 + #9），价值不在"集群本身"而在"讲出的认知"：

✅ **值得讲的（高价值）**：
| 点 | 为什么值钱 |
|---|---|
| 哨兵多数派机制（10.1） | 能讲"3 哨兵不是奇数迷信而是多数派容错" = 远超背概念的人 |
| Redis 跨机真 HA + 故障演练 | 面试必问"Redis 挂了怎么办"→ "我 kill 过主，哨兵 ~15s 自动切换，服务无感" = **实证 > 背书** |
| 秒杀双实例（负载均衡 + 故障剔除 + 定时任务分布式锁） | 秒杀是简历核心，"双实例下 MessageRetryTask 防双跑"是加分细节 |
| 网关 lb:// 跨机 + Nacos 剔除 | 展示理解服务发现与负载均衡的真实工作方式 |
| k3s 选型判断 | 能讲"为什么这个规模不用 k8s" = 展示架构取舍（比"我会 k8s"显成熟） |
| 127.0.0.1 加固与集群扩展的矛盾 | 展示能看到"安全加固 vs 集群扩展"的矛盾并给安全解法（安全组限定） |

⚠️ **要诚实标注的边界（讲过头会翻车）**：
- 2 台小机器 = **演示级 HA**：防单机宕机，不防地域灾难；其他 19 容器仍是老机单实例 → 话术"选依赖最广的中间件+并发最高的业务验证机制，不是全量迁移"
- Sentinel 按实例统计 → 副本后集群 QPS 翻倍（QPS=10×2）→ 主动讲清或后续 #5-P2 集群流控统一配额
- 说"验证了故障转移机制"，别说"我做了高可用架构"

## 十一、故障演练剧本（录视频用，2026-09-09 初稿）

> **定位**：视频演示 = 在真实环境 kill 组件 → 观察自动恢复 → 讲解机制。每条演练**独立可回滚、不碰数据、低峰执行**。
> **前置**：拓扑落地（老机主+新机从+3 哨兵 + 秒杀双实例）+ 全部验证通过后录制。

### 11.1 Redis 故障转移演练（⭐ 核心，约 3 分钟）

```bash
# 0. 演练前状态确认（录屏起点）
redis-cli -h 新机IP -p 26379 SENTINEL get-master-addr-by-name mymaster
#   → 老机 6379（当前主）
docker exec csmall-mysql mysql ...  # 可选：业务侧正常下单一次，展示"业务在跑"

# 1. kill 主节点（模拟 Redis 宕机）
docker stop csmall-redis
#   → 此时秒杀/登录等 Redis 依赖短暂报错或等待（5s 内哨兵开始动作）

# 2. 观察哨兵自动故障转移（tail 哨兵日志 = 录屏最有说服力的画面）
docker logs csmall-redis-sentinel-1 --tail 20
#   → +sdown master mymaster 127.0.0.1 6379        （主观下线）
#   → +odown master mymaster ... #quorum 2/2        （多数派确认客观下线）
#   → +failover-state-select-slave                    （选从）
#   → +switch-master mymaster 老机IP 6379 新机IP 6380 （切换完成！）

# 3. 验证新主生效 + 业务无感
redis-cli -h 新机IP -p 26379 SENTINEL get-master-addr-by-name mymaster
#   → 新机 6380（已提升为主）
# 业务侧再下单/登录一次 → 成功（客户端已自动连新主，无感知）

# 4. 恢复原主（可选演示"原主回归降级为从"）
docker start csmall-redis
sleep 15
redis-cli -h 新机IP -p 26379 SENTINEL replicas mymaster
#   → 老机 6379 以 slave 角色重新加入（哨兵自动降级）
```

**讲解要点（对着镜头说）**：① 为什么 5s 判定 + 10s 切换（down-after 5000 + failover 15000）② 为什么 quorum=2/3 哨兵（多数派防脑裂）③ 客户端为什么无感（Lettuce 问哨兵拿主地址）④ 主从异步的诚实边界（最后几笔写可能丢，靠 DB 条件扣减兜底）。

### 11.2 秒杀双实例故障剔除演练（约 2 分钟）

```bash
# 0. 确认两实例都在 Nacos
curl "http://老机:8848/nacos/v1/ns/instance/list?serviceName=mall-seckill" -H token...
#   → 2 个实例：老机 10007 + 新机 10017

# 1. 压测脚本打秒杀接口 → 观察请求分散到两实例（gateway/SW 日志或 Nacos 连接数）

# 2. kill 一个实例（模拟宕机）
docker stop csmall-seckill-2        # 或 csmall-seckill（老机那个）
#   → Nacos 心跳超时（默认 ~15s）剔除该实例

# 3. 观察自动剔除 + 流量切换
#   → Nacos 实例列表剩 1 个；gateway lb:// 不再轮询到已挂实例
#   → 压测继续 → 全部请求落在存活实例（无 500）

# 4. 恢复
docker start csmall-seckill-2
#   → 重新注册 → Nacos 恢复 2 实例 → 轮询恢复
```

**讲解要点**：① lb:// 轮询机制 ② Nacos 心跳剔除（临时实例 ephemeral）③ 与 Redis 故障转移的对比（服务发现剔除 vs 哨兵选主——两种"自愈"模式）。
