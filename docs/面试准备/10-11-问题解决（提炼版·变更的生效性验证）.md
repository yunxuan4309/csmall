### Q29. 变更没生效的两种形态：**只改了一半** 与 **改的不是那一份**

> 来源：[[问题解决--代码与线上不一致的静默失效]] §4.1 / §4.2

【追问1】你修完 bug、重建镜像、重启服务，重跑验证**错误又出现了** —— 代码没改对？
【追问2】你在 Nacos 上改了阈值，PUT 返回 `true`、`GET` 也读到了新值，但压测里成功 RPS **恒定在旧值** —— 是限流器有 bug 吗？
【追问3】这两次有什么共性？

【简答】有共性的，而且是同一条：**我看到的是"提交侧"的成功，不是"生效侧"的事实**。**① 多实例只改了一台** —— 那个微服务是**跨机双实例**（主 + 副本），两者注册**同一个 RPC 服务**、消费**同一个 MQ 队列**（竞争消费）；我只重建了主实例，这条消息**恰好被另一台旧 jar 的副本消费**了，所以旧逻辑照旧执行（副本日志时间戳能和这次消费对上）。**② 改的不是被订阅的那份配置** —— 应用订阅的 dataId 是 `xxx-flow-rules`（**没有扩展名**），我 PUT 的是 `xxx-flow-rules.json`（**仓库文件就叫这个名**）⇒ 我在配置中心**新建了一个同名影子配置**，应用侧**从未收到通知**，`notify-ok` 的 md5 从头到尾都是旧规则的。两次都不是"改错了代码/配置"，而是**改的东西没有任何一条路径去读它**。

【深挖】
- **多实例取证要落到"每个实例"**：把"部署完成"定义成一条可执行命令，而不是一个感觉 —— 逐实例比对**容器内 jar 指纹**、宿主 jar 文件指纹、容器状态、健康检查返回码，四者全绿才算完成；**两台指纹必须相同**，不同就直接红字报警。这件事一旦脚本化（`-CheckOnly` 只读模式，随时可跑），"我明明改了"这种自我说服就没有生存空间了。
- **副本形态的坑：别把镜像 tag 写死日期** —— `docker compose build` 会**覆盖同名 tag**，于是"我明明构建了新版本"却拿到旧层；正确做法是主/副本**共用同一个镜像**，差异**收敛成环境变量**（端口 + 链路追踪的服务名），从根上消灭"两个版本并存"的土壤。
- **配置类变更的取证位在"消费侧"**：配置中心的返回码只证明**它存下了**；要证明**应用用了**，就得看应用侧的**变更通知日志（md5）**或**行为指标**。而且**改之前先确认应用订阅的 dataId/group 是哪个** —— 照应用的配置项抄，**别照仓库的文件名抄**（仓库文件名往往只是本地约定的产物）。
- **小档探针是"生效性"的最短路径**：配置改完**先跑最小的一档**（比如最小档并发 / 单次调用）—— 阈值如果真的生效了，**最小的那一档就该变**；不变就别往下压，先回来查生效性，能省掉整轮无效压测。
- **误建的影子配置当场删掉** —— 否则它迟早会被下一个人（包括未来的自己）改到。

**面试话术**
"同一天我在这上面栽了两次，而且两次都**不报错**。第一次是我修了一个微服务的缺陷、重建镜像、重启，重跑验证**错误又出现了** —— 后来查出来这个服务是**双实例**，主实例和副本**消费同一个消息队列**，我只重建了主实例，那条消息**恰好被副本的旧 jar 消费**了，所以跑的还是老逻辑。从那以后我把'部署完成'改成一条命令：**逐实例**比对容器内 jar 的 md5、宿主的 jar 文件、容器状态和健康检查，**四个都绿、而且两台指纹一致**才算完成；副本也不再单独维护镜像，而是**和主实例共用同一个镜像**、差异只留端口和追踪名两个环境变量。第二次是调并发阈值：配置中心 **PUT 返回 `true`、`GET` 也读到新值**，可压测的成功 RPS **一直卡在旧阈值** —— 根因是应用订阅的 dataId **没有扩展名**，我改的是仓库里那个带 `.json` 的同名配置，等于**在配置中心建了个影子配置**，应用侧压根没收到通知。所以我现在有一条纪律：**配置类变更不看服务端返回码，只看消费侧**（应用的变更通知日志和行为指标），而且改之前先照应用的配置项确认 dataId；改完**先跑最小的一档**当探针。"

### Q30. 观测与自动化**自己也会说谎**："假通过"与"编排空跑"，以及变更生效性的四个检查位

> 来源：[[问题解决--代码与线上不一致的静默失效]] §4.3 / §4.4 / §4.5

【追问1】你的清理脚本每次都打印「✅ 全部回位 / 校验通过」，你凭什么还去查数据？
【追问2】一段 5 步的远程编排"执行完成"了，怎么会出现"一步没执行"？
【追问3】那判断一次变更到底有没有生效，你现在怎么做？

【简答】**① "假通过"**：脚本的校验**只覆盖了库存表**，而实际被写坏的是**销量（累加字段）** —— **校验集不是变更集的超集**，那个 ✅ 是**假的**，而且比没有校验更危险（它让我**停止了怀疑**）；最后是靠**造数前存基线、清理后比对基线**（11 张表的行数 + 两个累加量合计）才抓出来，顺带还修掉了"全局口径跨批次必然误报"的问题。**② "编排空跑"**：那段编排在 PowerShell 里用了单字母函数名 `R`，而 **`r`/`R` 是 `Invoke-History` 的内置别名**，我的函数**被别名优先解析**，`R ...` 变成了"调用历史命令" ⇒ **整段静默空跑**，连"还原"那一步也没执行，生产就这么停在了临时状态上（事后手工还原并逐项复核）。**③ 现在我用四个检查位**：**落到几个实例 / 改的是不是被订阅的那份 / 校验是否覆盖了所有会被写的字段 / 编排有没有真的跑完**。

【深挖】
- **"校验通过"必须能回答"校验覆盖了哪些字段"** —— 答不上来的 ✅ 一律当**假通过**处理。做法上有个兜底：对**会被写到的聚合量**做**前后基线比对**（行数 + `SUM`），而不是只做"写得对不对"的点检；因为"漏检"是无法靠"更仔细地看同一份校验"发现的。
- **校验口径也有时点与范围问题**：全局口径在校验"某一次批次的清理"时**必然误报**（别的批次的数据也算进来）⇒ 校验要**按批次/按作用域**收敛，这与"分母要按批次"是同一个教训。
- **脚本要能自证执行过**：每一步打印 + 关键返回值 + 幂等；**别用单字母或易撞别名的函数名**（先查别名表），否则你连"它跑没跑"都不知道（PowerShell 的别名是**内置优先级高于自定义函数**的）。
- **有副作用的编排必须配看门狗（事前，不是事后）**：**先武装"定时自动还原"**，再开始有副作用的步骤 —— 这样即使编排中断、被杀、或像上面那样空跑，**最终状态也会自己回到基线**。这一次是事后补的手工还原，**下一次必须是事前就位**。
- **长脚本的"完成"以独立复核为准**：对**生产最终状态**做一次独立取证（AI 指向 / 开关 / 阈值 / 进程 / 容器数），而不是相信脚本自己的打印 —— 这和"压测机要放在被测系统之外"是同一个思路：**别让被验证的对象自己出具证明**。
- ⭐ **一句话**：**别问"我改了吗"，要问"生效侧现在是什么"** —— 版本看**逐实例指纹**、配置看**消费侧日志**、数据看**前后基线**、流程看**独立复核**。

**面试话术**
"我给自己抓到过两个更'元'的问题：**验证手段自己会说谎**。第一个是我写的数据清理脚本，跑完打印「✅ 校验通过」，但我每次核对都发现**销量总和比基线多 1** —— 因为它的校验**只覆盖库存表、没覆盖销量**这个会被累加的字段，也就是说**校验集不是变更集的超集**，那个 ✅ 是假的。这类"假通过"比"没有校验"更危险，因为它会让你**停止怀疑**；我最后的解药不是"更仔细地看同一份校验"，而是**造数前存一份基线**（11 张表的行数加两个累加量合计），清理后**比对基线**，任何一项不符就报错 —— 顺便还修掉了"全局口径跨批次必然误报"的毛病。第二个更离谱：我写了一段 5 步的远程编排（备份 → 切流量 → 压测 → 还原 → 复核），执行完看着正常，复核时发现**生产还停在临时状态** —— **还原那一步没跑**，整段编排**一步都没执行**。根因是 PowerShell 里 `r` 和 `R` 是 `Invoke-History` 的内置别名，把我自定义的函数名覆盖了，命令变成了"调用历史命令"，**静默空跑**。所以我现在对'变更是否生效'有四个固定检查位：**① 落到几个实例（逐实例核 jar 指纹）② 改的是不是被订阅的那份（看消费侧日志，不看服务端返回码）③ 校验有没有覆盖所有会被写的字段（含累加量，用基线比对兜底）④ 编排有没有真的跑完（独立复核，而且有副作用的编排要事前武装看门狗还原）**。"
