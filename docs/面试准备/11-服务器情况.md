### Q3. 网络是怎么设计的？哪些端口对外？🔴

【追问1】安全组？
【追问2】中间件端口为什么不暴露？

【简答】
安全组只开放 22（SSH）、80（HTTP）。数据库/Redis/Nacos 等中间件端口只在 VPC 内网，不对公网。

【深挖】
- **对外**：22（SSH）、80（前端 HTTP + API 反代）
- **内网**：3306（MySQL）、6379（Redis）、8848（Nacos）、9200（ES）等都不暴露公网
- **为什么**：中间件暴露公网 = 被攻击面。SSH 隧道访问管理界面（Nacos/Sentinel/SkyWalking）
- **访问方式**：`ssh -L 8090:localhost:8090 ecs-user@IP` 本地隧道访问内网管理界面
- **面试话术**："**最小暴露面**——公网只开 22/80，中间件全走内网，管理界面用 SSH 隧道访问。这是基础但重要的安全实践"

### Q7. 安全组只开 80/22，那 AI 模块的 API 调用怎么办？

【追问1】出站流量？
【追问2】DeepSeek 调用？
【追问3】入站出站具体怎么验证的？（实测背书）
【追问4】服务器上跑 AI 代码助手，安全上怎么隔离的？（误报插曲）

【简答】
安全组限制的是**入站**（别人访问我），出站（我访问 DeepSeek API）不受限。所以服务器可以正常调 DeepSeek/硅基流动 API。

【深挖】
- **入站 vs 出站**：安全组是"有方向的防火墙"——入方向和出方向是**两套独立规则**；新建安全组默认**出方向全放行**（系统自动加"出方向允许所有流量"规则），只对入方向收紧 → 你配的"只开 22/80"只挡"别人访问你"，不挡"你访问别人"
- **官方依据**：阿里云安全组规则文档明确分入/出方向、默认出方向放行
- **AI 调用**：服务器出站调 DeepSeek API、Embedding API，不受 22/80 限制影响

**🧪 实测背书（2026-09-04，宿主机 + 容器内双向验证）**：

| 实测 | 结果 | 解读 |
|------|------|------|
| 宿主机 → api.deepseek.com | HTTP 401（TLS 0.015s） | ✅ 网络通；401=没带 key，只差认证 |
| 宿主机 → api.siliconflow.cn | HTTP 404 | ✅ 网络通；404=根路径无资源 |
| **csmall-ai 容器内** → DeepSeek | HTTP 401 | ✅ 容器内也通（真实调用路径是容器，不是宿主机） |
| 外部连公网 IP:3306 | 超时/拒绝 | ✅ 入站确实被安全组挡住 |

- **🛡️ 小插曲：AI 运维触发的安全告警（误报 + 处置 = 面试好素材）**：
  - 事件：AI 代码助手（ai-deepseek 账号）远程执行网络测试时，用了 `echo <base64> | base64 -d | sh` 的编码脚本形态 → **阿里云云安全中心告警"可疑编码命令"**（检测模型把"base64 编码 + 管道给 sh"识别为木马/后门常见混淆手法）
  - 处置流程（正确姿势）：收到告警**不慌 → 先验证再处置**——解码告警中的 base64 → 内容 = 自己刚跑的 curl 连通性测试（只读、无破坏）→ 确认为**误报** → 控制台标记误报/加白 + 今后改用直连命令避免编码形态
  - 为什么有价值：① 证明**服务器上有行为检测且真的在抓可疑特征**（监控不是摆设）② AI 账号是**独立隔离账号**（ai-deepseek = docker 组、无 sudo、专属密钥，见 [[服务器权限收紧方案]]：sudoers 白名单 + 每模型独立账号可单独吊销）→ 就算账号真被攻破，破坏面也受限 ③ 展示"告警处置方法论"：先验证 IOC 准确性，再决定忽略还是处置（阿里云官方处置建议也是这个流程）
- **面试话术**："安全组是**入站防火墙**——限制别人访问我，不影响我主动访问外部 API（DeepSeek/Embedding），我用 curl 实测过：宿主机和 AI 容器里访问 DeepSeek 都通（401=只差认证），外部连我 3306 是超时的，入站出站两个方向用实验验证过。还有个有意思的小插曲：我的 AI 助手在服务器上跑脚本触发过一次'可疑编码命令'告警——解码一看是我自己的测试脚本，误报。但这件事让我理解了三点：**云厂商的行为检测是真的在抓东西、AI 运维账号要按模型隔离（docker 组无 sudo、可单独吊销）、收到告警先验证再处置**。我把 AI 助手的权限收敛和密钥管理都写成了文档（[[服务器权限收紧方案]]）"

### Q9. 域名/HTTPS 配置了？

【追问1】为什么没配？
【追问2】怎么配？
【追问3】HTTP 和 HTTPS 的区别？TLS 握手？
【追问4】TCP 三次握手为什么是三次？和 TLS 握手的区别？

【简答】
没配 HTTPS，因为无域名 + ICP 备案要求服务器续费 3 个月以上（预算不足）。配置 HTTPS 需要：域名 → 备案 → SSL 证书（Let's Encrypt）→ Nginx 配 443。

【深挖】
- **HTTP vs HTTPS 核心**：HTTPS 不是新协议 = **HTTP 跑在 TLS 之上**（HTTP over TLS），端口 80→443。TLS 解决三个问题：

| 问题 | HTTP 的暴露 | HTTPS 解决 |
|------|------------|-----------|
| 机密性 | 明文传输，抓包看到密码/Token | 对称加密，内容不可读 |
| 完整性 | 中间人篡改内容 | MAC 校验，改了即发现 |
| 身份认证 | 任何人可冒充服务器 | CA 证书证明"我是真的" |

> 类比：HTTP = 寄明信片（谁都能看能改）；HTTPS = 上锁保险箱快递（带防拆封条）。

- **基础概念（被追问时的弹药，逐个讲清）**：

**RTT（往返时间）**：一个包"你 → 服务器 → 应答回你"的总时间。HTTPS 比 HTTP 慢的原因不是计算慢，而是握手多等了几次往返（RTT）。

**对称加密**：加密和解密用**同一把钥匙**（快，适合加密大量数据）。类比：一把钥匙开一把锁，锁上再开锁都靠它。

**非对称加密**：**两把钥匙**——公钥（公开，谁都能拿）+ 私钥（私藏，只有自己有）。两个用途，各配一个例子：

| 场景 | 做法 | 效果 |
|------|------|------|
| ① 发密信（保机密） | 别人用你的【公钥锁】把信锁进箱子寄给你 | 只有你的【私钥】能打开，路上谁拿到都看不了 |
| ② 验身份（防冒充） | 你用【私钥】给公告盖章 | 大家拿你的【公钥】验证，能验过 = 一定出自你 |

> 关键认知：非对称很慢（大数运算），所以 HTTPS 里它只干一件事——**安全传递"会话密钥"**，数据本身不靠它。

**HTTPS = 混合加密**（非对称传钥匙 + 对称传数据，各用所长）：

```
① 浏览器生成一个随机"会话密钥"
② 用服务器的【公钥】加密后发给服务器     ← 非对称（只此一次，慢但安全）
③ 服务器用【私钥】解开，拿到会话密钥
④ 之后所有 HTTP 数据用会话密钥加密传输    ← 对称（快，量大也不怕）
```

> 类比：非对称 = 保险柜运钥匙（慢但绝对安全）；对称 = 拿到钥匙后用普通锁进出（快）。HTTPS 先把钥匙安全运到，再用钥匙快速开锁。

**证书**：服务器的"电子身份证"——{域名 + 服务器公钥 + 颁发者 + 有效期 + CA 签名}。作用：**把"公钥"和"域名"绑死**，防止中间人塞给你一把假公钥。

**CA**：发证书的可信第三方（DigiCert / Let's Encrypt）。浏览器预装"可信 CA 名单"，验证证书四连问：① 发证 CA 在不在名单？② 域名匹配吗？③ 过期没？④ 用 CA 公钥验签真不真？——全过才信任。

- **TLS 握手（简化）**：① ClientHello（我来了+支持的加密套件）→ ② ServerHello + 证书 → ③ 客户端验证书（可信 CA？域名匹配？）→ ④ 用证书公钥加密"预主密钥"发出 → ⑤ 双方算出相同会话密钥 → 之后 HTTP 内容对称加密传输

- **TCP 三次握手 vs TLS 握手（两层、先后发生）**：

| | TCP 三次握手 | TLS 握手 |
|--|------------|---------|
| 层 | 传输层（建可靠连接） | TLS 层（协商加密，在 TCP 之上） |
| 目的 | 双方确认"能收能发" | 协商加密密钥 + 验证身份 |
| 开销 | 1.5 RTT | 1-2 RTT（可优化 1-RTT/0-RTT） |
| 顺序 | **先 TCP**，再 TLS，之后才是 HTTP |

- **为什么 TCP 握手要三次不是两次（幽灵请求，展开理解）**：
  - 完整时间线：客户端发 SYN#1 → **网络拥塞卡住** → 客户端超时重发 SYN#2 → SYN#2 正常建连、传完数据、关闭 ✅ → **此时迟到的 SYN#1 才到服务器**
  - 若只两次握手：服务器不知道 SYN#1 是过期幽灵 → 回 SYN+ACK → **认为连接建立、分配资源傻等客户端发数据** → 但客户端连接早用完了，不会理它 → **服务器资源白占**（攻击者狂发只 SYN 不应答 = SYN Flood 攻击，靠这个原理打垮服务器）
  - 三次握手：客户端收到幽灵的 SYN+ACK → "我没发过对应的新 SYN"（我的 SYN#2 早完成握手了）→ **不回应 ACK** → 服务器等不到 ACK → 知道没人要这个连接 → 主动释放 ✅
  - 本质：**两次握手只能确认"服务器能收能发"，确认不了"客户端能收"**——服务器区分不了"新请求 vs 迟到幽灵"；第三次 ACK 由客户端发出 = 告诉服务器"连接是活的，我确实在"，服务器才放心分配资源。类比：电话里对方说"喂?"（SYN），你回"喂?听到吗"（SYN+ACK），对方再说"听到了"（ACK）——三句才确认双方通话正常，只来回两句总有一方不确定
- **怎么配（若上 HTTPS）**：certbot 获取 Let's Encrypt 证书 → Nginx 443 + 80 跳转 → cron 自动续期
- **阻塞链**：HTTPS → SSL证书 → 域名 → ICP备案 → 服务器续费≥3月 → 预算不足
- **加分点（TLS 终止）**：证书只放 **Nginx（边缘）**，Nginx 终止 TLS → 内网反代 HTTP 到 Gateway → 微服务间容器网络走 HTTP 明文无妨——**只有边缘要加密**，不是每个服务都配证书
- **面试话术**："HTTPS 卡在**域名 + 备案**的流程上——国内服务器要备案，备案要求续费 3 个月。技术上我很清楚：HTTPS = HTTP over TLS，解决机密性/完整性/身份认证三件事；TLS 握手在 TCP 三次握手之后，用非对称安全交换会话密钥、之后对称加密传输。TCP 三次握手为什么是三次——为了防'迟到幽灵 SYN'让服务器白等，第三次 ACK 是客户端给服务器的'连接是活的'确认。真上 HTTPS 我会用 Let's Encrypt + Nginx 边缘终止 TLS，微服务内网保持 HTTP。"
