## 一、秒杀为什么用 Redis 预扣库存？

**问题**：为什么不直接操作数据库库存？

**回答思路**：
- 秒杀是**读多写少**且**瞬时高并发**场景，100 万用户抢 100 件商品
- 如果把库存放在 MySQL，100 并发同时 `UPDATE` 同一行，会触发**行锁排队**，数据库成为瓶颈
- Redis 是**单线程 + 内存操作**，`DECR` 原子自减，吞吐量远超数据库
- 所以：**库存预扣在 Redis 完成**，数据库只负责最终落库

**追问点**：Redis 扣库存为什么不会超卖？
- 用 `DECR` 命令，**原子性**——单线程保证同一时刻只有一个请求能执行
- 判断 `leftStock < 0` 才拒绝，不会出现负数卖出

## 二、为什么用 RabbitMQ 异步落库？

**问题**：为什么不在请求线程里直接创建订单？

**回答思路**：
- 秒杀的核心矛盾：**请求量大，但真正成功的少**（100 并发只有 10 个能买到）
- 如果同步落库，10 个成功请求 + 90 个被限流请求都会阻塞在数据库操作
- **异步削峰**：Redis 扣库存成功后，把"创建订单"的任务丢进 MQ，请求立刻返回，消费者异步处理
- 好处：① 请求响应快；② 数据库压力被消息队列削平

**追问点**：消息积压怎么办？
- RabbitMQ 设置了队列长度、`basicNack` 失败重试
- 秒杀场景下积压是正常的（排队消费），只要消费者处理速度足够

## 三、Sentinel 限流的作用？

**问题**：为什么配置 QPS=10？

**回答思路**：
- 秒杀是**天然的限流场景**——后端只能处理有限的订单
- QPS=10 表示每秒最多放行 10 个请求进业务逻辑，超出的直接拒绝（快速失败）
- **防止缓存击穿**：如果不限流，100 并发同时查 Redis 库存，Redis 扛不住
- **防止数据库打爆**：控制进入业务逻辑的请求量，保护下游

**追问点**：限流和熔断的区别？
- **限流**：控制单位时间内进入系统的请求量（防流量过大）
- **熔断**：下游服务故障时，快速失败避免雪崩（保护下游）
- 本项目秒杀用限流，其他服务可配熔断

**追问点**：为什么用代码配置 + Nacos，不手动在 Dashboard 配？
- 生产环境规则应**持久化**（Dashboard 规则重启丢失）
- 本项目通过 Nacos 配置中心管理 `mall-seckill-flow-rules`，规则可动态更新

## 四、Seata 分布式事务解决什么问题？

**问题**：秒杀为什么需要分布式事务？

**回答思路**：
- 秒杀下单涉及**两个服务**：mall-seckill（扣库存）+ mall-order（创建订单）
- 两个服务各自操作**不同数据库**，无法用本地事务保证一致
- **场景**：Redis 库存扣了，但订单创建失败 → 库存"蒸发"（扣了但没订单）
- Seata AT 模式通过 `@GlobalTransactional` 保证：**要么都成功，要么都回滚**

**追问点**：Seata AT 模式原理？
- 本地事务 + 全局事务协调：业务代码正常提交本地事务，Seata 记录 undo_log
- 全局提交失败时，通过 undo_log 反向补偿回滚

## 五、防重复购买怎么实现？

**问题**：同一个用户怎么防止买两次？

**回答思路**：
- 两个 Redis key 双重拦截：
  1. **`orderLock`（下单锁）**：`SETNX` 原子操作，1 分钟 TTL，防并发重复提交
  2. **`ordered`（未支付标记）**：订单存在则拦截，防锁过期后二次下单
  3. **`reseckill`（购买标记）**：支付后标记，防止再次购买
- 三个 key 分离设计：下单、未支付、已购买分别管理，互不干扰

**追问点**：为什么要三个 key 分离？
- 历史踩坑：下单锁和购买标记混用，导致"支付后还能再下单"
- 分离后：`orderLock` 管并发防重，`ordered` 管未支付拦截，`reseckill` 管购买完成

## 六、压测到底测什么？（核心理解）

**问题**：已经有防重复/防超卖逻辑，为什么还要压测？

**回答思路**（关键）：
- **防重复/防超卖是"功能正确性"**——验证单用户、正常流量下逻辑对不对
- **压测是"系统健壮性"**——验证 100 并发下保护机制是否真的生效
- 具体验证 4 点：
  1. Sentinel 限流是否触发（防缓存击穿）
  2. Redis 预扣库存是否扛住（无超卖）
  3. RabbitMQ 削峰是否生效（数据库不被打爆）
  4. Seata 事务是否一致（无数据不一致）
- **本质**：验证"保护机制在高并发下确实在工作"，而不是纸面上写了

**追问点**：压测结果怎么看？
- 成功 ~10 = Sentinel 放行的
- 被限流 ~80-90 = Sentinel 拦截的（"服务器忙"）
- 无超卖 = Redis DECR 原子性生效
- 无重复 = 防重复 key 生效

## 七、随机码（randCode）机制？

**问题**：秒杀 URL 为什么带随机码？

**回答思路**：
- **防提前下单**：秒杀开始前，用户不知道随机码，无法提前构造请求。否则知道 URL 的人可以在秒杀开始前就下单
- **防刷接口**：即使知道 URL，没有正确的随机码也下单失败（后端校验 Redis 中的值）
- 随机码存在 Redis（`mall:seckill:spu:url:rand:code:{spuId}`），前端从详情接口获取

**类比**：随机码像演唱会门票的防伪码——只有入场时（秒杀开始后）才告诉你这个码，有码才能进，没码想混进去会被拦。

**追问点**：随机码怎么生成的？
- 6 位随机数（100000~999999），`SeckillInitialJob` 定时任务生成
- 存在 Redis，TTL 约 2 小时 5 分钟，过期后定时任务重新生成
- 每次压测前要重新查 randCode（因为会过期）

**代码逻辑**（可简述）：
```java
// 1. 定时任务生成随机码存 Redis
int randCode = ThreadLocalRandom.current().nextInt(900000) + 100000;
redisTemplate.boundValueOps(randCodeKey).set(randCode);

// 2. 前端详情接口返回 url="/seckill/{randCode}"
seckillSpuVO.setUrl("/seckill/" + randCode);

// 3. 下单时校验随机码
String redisRandCode = redisTemplate.boundValueOps(randCodeKey).get();
if (!redisRandCode.equals(randCode)) {
    throw new Exception("随机码不正确");
}
```

## 八、幂等防重复提交？

**问题**：怎么防止用户快速双击导致重复下单？

**回答思路**：
- `@Idempotent(key = "seckill", expire = 3)` 注解
- 基于 `MD5(userId + args)` 生成幂等 Key，Redis 判断是否已处理
- 3 秒内相同请求只处理一次，防双击

---

## 九、Redis 挂了怎么办？（降级方案）

**问题**：Redis 不可用时秒杀还能用吗？

**回答思路**：
- 本项目有 `seckill_message_retry` 表（本地表缓冲 + 定时重试）
- Redis 扣库存成功后，先写本地重试表，再发 MQ
- MQ 失败时，MessageRetryTask 每 5 秒扫描重试，MQ 恢复后自动补发
- 保证"库存扣了但消息丢失"的情况能恢复

## 十、压测讲解完整话术（面试口述版）

> **"我的秒杀模块针对高并发做了四层防护**：
> 第一，**Redis 预扣库存**——用 DECR 原子操作在缓存层扣减，扛住瞬时压力，单线程保证不超卖；
> 第二，**Sentinel 限流**——配置 QPS=10，超过的直接拒绝，防止缓存击穿和数据库打爆；
> 第三，**RabbitMQ 异步落库**——创建订单走消息队列削峰，请求不阻塞；
> 第四，**Seata 分布式事务**——保证扣库存和建订单两个服务的数据一致性。
>
> 我用压测脚本模拟了 100 个并发用户同时抢购，结果约 10 个成功、80 多个被限流保护，全程无超卖、无重复下单。从 SkyWalking 能看到完整的跨服务调用链，Sentinel 控制台能看到 QPS 从 0 飙升到 100 再被削平到 10。这套体系覆盖了高并发下的限流、削峰、事务一致性、可观测性，是完整的生产级方案。"

## 面试被追问的应对原则

1. **不知道具体数字就不说**（如"支撑 10 万 QPS"这种编造数据，一问就露馅）
2. **不确定的实现说"这个可以查代码确认"**，显得诚实
3. **讲清楚"为什么"比"是什么"更重要**——每个设计都要能说出它解决了什么问题
4. **可讲坑**：三个 key 分离（历史踩坑）、Nacos 规则覆盖本地规则（压测时发现的）、Redis 无 RedisBloom 用 Set 替代

## 常见坑点提醒（面试时避免）

| 坑 | 正确说法 |
|----|---------|
| "支撑 100 QPS" | "配置了 QPS=10 限流，压测 100 并发验证机制"（真实数据） |
| "高可用" | 不夸大，说清是单机部署 |
| "10 万用户" | 没有这个量级，不说 |
| "用了布隆过滤器" | 实际是 Redis Set 替代（本地无 RedisBloom） |
