## 一、先立住核心模型：容器 = 镜像层 + 可写层

```
┌─ 容器(运行中的实例)───────────────────────────┐
│  可写层(可读可写,容器私有)   ← 运行时写的都在这   │
├─────────────────────────────────────────────┤
│  镜像层 1(只读):temurin-jre 基础(OS+JVM)      │
│  镜像层 2(只读):mall-seckill.jar             │  ← 镜像 = 只读模板
└─────────────────────────────────────────────┘
```

| | 镜像层 | 可写层 |
|--|--------|--------|
| 读写 | **只读**(内容不可改) | 可读可写 |
| 归属 | 多容器**共享**(同镜像) | 每容器**私有** |
| 生命周期 | 镜像在就在(永久) | **容器销毁即消失** |
| 类比 | 印刷好的教材 | 白板上的临时笔记 |

## 二、镜像层是干嘛的？（秒杀例子）

**镜像层 = 把"运行环境 + 程序 + 启动命令"打包成的只读内容层**，每层对应 Dockerfile 一行。

```dockerfile
FROM eclipse-temurin:21-jre   → 层 1:操作系统 + JRE 21
COPY mall-seckill.jar /app/app.jar → 层 2:秒杀程序本体
```

**三个作用**：
① **自包含模板**：任何机器用这镜像拉起容器 = JRE + jar 都齐，环境一致（不会"我这能跑你那不能跑"）
② **分层缓存复用**：改 jar 重新 build 只重建 jar 层，基础层（几百 MB JRE）走缓存秒出
③ **只读安全**：内容不可篡改，容器坏了重建一个还是原样

> 类比：镜像 = 一包"预制菜"（食材+调料+做法都封好）；JRE 层 = 统一供应链的锅具标准，jar 层 = 你这道菜

---

## 三、可写层是干嘛用的？（秒杀例子）

**可写层 = 容器运行时专属的"草稿区"**——进程跑起来要写的东西都落这里。

**秒杀容器运行时会写什么？**
```bash
java 进程(PID 1)                    # 进程本身
/tmp 下的文件(HeapDump 路径配了 /tmp)  # OOM 时才写
日志 → 实际走 stdout(被 Docker 捕获,不落可写层)
/etc/hosts、临时文件等                # 容器运行需要
```

**三个作用**：
① **进程能正常跑**：任何程序都要写文件，可写层给容器内的"小世界"
② **隔离**：每容器一份，A 容器的写入不影响 B 容器
③ **易失性**：docker exec 装的、运行生成的，容器一重建全没

**秒杀例子（为什么它几乎不用可写层）**：
```
秒杀是【无状态服务】——业务数据全在 Redis/MySQL/RabbitMQ
容器自身不存业务数据 → 可写层基本空着
→ 重建容器 = 换个空壳重新连中间件,数据毫发无损
→ 这就是为什么秒杀/订单容器随便重建
对比:MySQL/Redis/ES 有本地数据 → 必须挂卷,重建不能丢(有状态)
```

> ⚠️ Q1 教训回放：ES 的 IK 用 `docker exec` 装在可写层 → compose up -d 重建 → 可写层销毁 → IK 没了 → red。
> 所以必须"挂载"（写宿主机目录，重建保留）或"写进镜像"（COPY 进镜像层）。

## 四、为什么把 JAR COPY 进镜像，而不是直接跑 jar 本体？

**核心：镜像 = "环境+程序"打包的发布单元；直接跑 jar = 只给程序，环境靠猜。**

| 对比 | COPY 进镜像（项目做法） | 直接跑 jar（反例） |
|------|------------------------|-------------------|
| 目标机要求 | 只要有 Docker | 要装 JRE、要对版本 |
| 启动命令 | 固化在镜像（ENTRYPOINT） | 手动拼 java -jar + 参数 |
| JVM 参数 | 固化（-Xmx448m/GC/SW agent 全在 Dockerfile） | 每次手动传，容易漏 |
| SW agent | 镜像里声明路径，一致 | 路径/版本各机器难管 |
| 版本化/回滚 | 镜像 tag 版本，可回滚旧镜像 | 只有一个 jar，覆盖就没了 |
| 分发 | 镜像仓库 push/pull，多机一致 | 每台机器单独传 jar 手搓 |
| 一句话 | 预制菜包：拆开即食 | 只给食材：别人还得有锅有火 |

**秒杀具体看**：Dockerfile 把 `-Xmx448m -XX:MaxMetaspaceSize=256m -javaagent:/skywalking-agent/... -jar app.jar` 全部固化 → **部署 = 拉起镜像，运行行为 100% 确定**；发布新版本 = 重新 build 成新镜像 tag，随时回滚旧 tag。

> 类比：COPY jar 进镜像 = 把"菜谱+食材+锅"做成**预制菜包**；只传 jar = 只给食材，对方还得自己有锅有火、自己会炒。镜像让你**在哪都能吃到同一道菜**。

## 五、完整生命周期（秒杀模块，贯穿镜像/可写层/挂载）

```
编码 ──mvn package──> 胖JAR ──scp──> /data/csmall/jars/
  → docker compose build(镜像层:JRE 层 + 新 jar 层;基础层走缓存)
  → compose up -d:
      创建容器 = 镜像只读层 + 新可写层
      + 挂载 /data/csmall/skywalking-agent(宿主机目录映进容器)
      + 注入 env(prod/密码/连接地址)
      + 加入 csmall-net → java 变 PID 1 → 连 Nacos/Redis/MySQL 上线
日常:docker ps / docker logs / docker exec(进容器,可写层视角)
更新:改代码 → 重新 build → up -d
      旧容器销毁:可写层丢 ✅ 挂载保留 ✅(SW agent 在宿主机)数据卷保留 ✅
```

## 六、容器里的操作系统是谁的？（宿主机 Ubuntu ≠ 容器内 Debian）

> 高频追问："你的服务器明明是 Ubuntu，为什么容器里是 Debian？"

### 核心：容器内 = 镜像自带的迷你系统，与宿主机无关

```
┌─ 宿主机服务器(Ubuntu 24.04)─────────────────────┐
│  内核(Linux Kernel) ← 容器共享这一层            │
│  Docker 引擎                                    │
│  ┌─ 容器 A ──────────┐  ┌─ 容器 B ──────────┐   │
│  │ 用户态:Debian 系   │  │ 用户态:Alpine      │   │
│  │ (glibc,镜像自带)   │  │ (musl,镜像自带)    │   │
│  └───────────────────┘  └───────────────────┘   │
└──────────────────────────────────────────────────┘
```

| 层 | 谁决定 | 说明 |
|----|--------|------|
| **内核** | 宿主机(共享) | 容器不打包内核，用宿主机的 |
| **用户态**(libc/工具/运行库) | **镜像自带**(`FROM` 第一行决定) | 容器内"看起来"是哪个系统，全看镜像 |
| 所以 | 一台 Ubuntu 服务器 | 可同时跑 Debian / Alpine / CentOS 容器 |

### 用你的服务器实测（2026-09-03）

| 对象 | 实测结果 | 说明 |
|------|---------|------|
| 宿主机 | Ubuntu 24.04.4 LTS | 跑 Docker 的机器 |
| csmall-sso 容器内 | Ubuntu/Debian 系 | 基础镜像 `eclipse-temurin:21-jre`（无 `-alpine`） |
| csmall-redis | **仍是 Alpine** | 非 Java 程序不挑 libc，可继续用 Alpine 省体积 |
| csmall-rabbitmq | **仍是 Alpine** | 同上 |

> 一个服务器上同时存在 glibc 系（Java 服务）和 musl 系（Redis/RabbitMQ）容器——**这本身就是"容器内系统独立于宿主机"的铁证**。

### 为什么 Java 服务必须换、中间件不用换？

| 程序类型 | 对 libc 的挑剔程度 | 原因 |
|---------|------------------|------|
| **Java(JVM)** | 挑剔 | JVM 本体是 C++ 写的，Oracle 官方只认证 glibc(musl 上安全算法层会翻车) |
| Redis(C)/RabbitMQ(Erlang) | 不挑 | 原生程序对 musl/glibc 兼容良好 |

> 详见 [[10-问题解决]] Q12（SkyWalking Alpine→Debian 案例：musl 上 MD5 实例化失败，11 个服务全崩）。

### 类比

> 宿主机 = 一栋楼（Ubuntu），容器 = 楼里的房间，**共享水电煤（内核），但每间房内部装修（发行版/软件）各自独立**。你住 301（Debian 装修），隔壁 302（Alpine 装修）互不影响——楼是开发商盖的（宿主机系统），房间怎么装是租户决定的（镜像）。

### 追问：内核都共享了，为什么用户态不能直接用宿主机的？

> 高频追问："Java 直接跑在宿主机 Ubuntu 上不行吗？为什么要给每个容器带一套 Debian 用户态？"

**一句话**：内核只提供"系统调用接口"（敲门的动作），不提供"库文件"（门后的工具）——程序运行需要的 glibc/运行库是**文件**，必须存在于进程能看到的文件系统里；容器自带 rootfs = 自带这些文件。

**先分清"内核"和"用户态"（用 printf 的例子）**：

```
你的程序调用 printf("hi")
  → printf 是 glibc 提供的函数，glibc 本体是文件 /lib/x86_64-linux-gnu/libc.so.6
  → glibc 内部再调内核的 write 系统调用（真正把字节写到屏幕/文件）
       ┌─────────────────────────────────────────────┐
       │ 用户态(你的程序 + glibc + 所有运行库)         │ ← 镜像自带
       │   调用关系: 程序 → glibc.printf → write()     │
       ├─────────────────────────────────────────────┤
       │ 内核态(Linux Kernel)                          │ ← 宿主机共享
       │   执行 write() → 驱动硬件输出                 │
       └─────────────────────────────────────────────┘
```

**为什么不能直接用宿主机 Ubuntu 的库？4 个理由**：

| 理由 | 说明 | 类比 |
|------|------|------|
| ① 程序需要"文件" | printf/malloc/socket 全在 glibc.so 里，进程从文件系统加载它；内核不提供这些文件 | 内核=政府窗口(办事动作)，库=工具书(内容)，窗口不给书 |
| ② 隔离 | 容器 A 改了/升级了共享库 → 宿主机和 B/C/D 全被影响；自带一份 = 各改各的 | 房间共用一个工具箱 vs 各房自带 |
| ③ 可移植 | 依赖宿主机 Ubuntu 的库 → 换 CentOS 服务器就缺库跑不起来；自带 = 哪台机器都一致 | 自带工具包出差，不借当地人的 |
| ④ 版本冲突 | 服务 A 要 glibc 新特性、服务 B 锁旧版——全塞宿主机打架 | 合租共用水龙头，一人改装全楼停水 |

**这不是 Docker 的限制，是"隔离要花钱买"**：如果 Java 直接用宿主机用户态，那它就不是容器了，是宿主机上一个普通进程——**你们项目早期 systemd 部署就是这种**（旧 IP `/data/jars/` 直接裸跑），后来迁 Docker 本质就是从"共享宿主机用户态"走向"镜像自带用户态"。

**精妙点：该共享的共享、该隔离的隔离**（磁盘并不存 11 份 Ubuntu）：
```
内核            → 宿主机共享(1 份)
公共基础层      → 11 个 Java 容器共享同一份只读 eclipse-temurin 层(OverlayFS,1 份)
可写差异层      → 每容器私有(薄薄一层)
```

### 终极心智模型：办事大厅 / 代办事务所（背下这套就能答所有追问）

把上面整条链压缩成一张角色表，面试被追问时直接按它答：

| 角色 | 对应物 | 说明 |
|------|--------|------|
| **办事大厅 + 窗口** | 内核 + 系统调用(syscall) | 一栋楼共享，只此一家 |
| **顾客(办事的人)** | 容器里的程序(Java/Redis) | 想办"打印/联网/读文件"这些事 |
| **代办事务所** | 发行版(Debian/Ubuntu/Alpine) | 容器自带的一整家公司(打包 glibc + ls/bash/curl 等一堆员工) |
| **代办员(具体干活的员工)** | glibc / musl | 把 printf/socket 翻译成窗口听得懂的话；不同事务所雇不同风格的代办员 |

**三个关键认知**：

1. **程序挑的是"代办员风格"，不是"事务所招牌"**——Java 挑的不是 Debian 这个名字，是 glibc 这种代办员；Debian/Ubuntu 恰好雇 glibc，所以 Java 选它。Redis 不挑风格，谁干都行 → 就选最省钱的精简事务所(Alpine)。

2. **宿主机"有"代办员但不借你用**——Ubuntu 宿主机自己跑进程也靠 glibc，但那是自用的：借给你 = 你升级它全楼遭殃(无隔离)、你和别人版本打架、换台 CentOS 服务器你就不认识那边的代办员了(不可移植)。所以必须自带。

3. **选事务所的逻辑 = 先看顾客挑不挑**：
```
Java(挑剔,只认 glibc)   → 大事务所 Debian/Ubuntu(雇 glibc)      ← 你 11 个 Java 容器
Redis(不挑)             → 精简事务所 Alpine(雇 musl,省体积)     ← 你的 redis/rabbitmq
```

**一句话总结**："内核 = 共享办事大厅；容器 = 顾客；发行版 = 顾客自带的代办事务所；glibc/musl = 事务所里风格不同的主力代办员。顾客挑代办员风格（Java 只认 glibc），不挑的顾客就挑最便宜的事务所（Redis 选 Alpine）。"

### 面试话术

> "容器确实共享宿主机内核（所以比 VM 轻）；不能共享的是用户态文件——程序运行要从文件系统加载 glibc/运行库，而内核只提供系统调用不提供库文件。隔离、可移植、防版本冲突都要求每容器自带 rootfs，这是'隔离要花钱买'；但 Docker 分层让公共基础层只存一份、多容器共享，所以没浪费。我们项目早期 systemd 直接跑 jar 就是'共享宿主机用户态'的形态，迁 Docker 本质是走向自带用户态。"

## 七、端口映射（网络基础，Sentinel 8090→8858 案例）

### 格式与含义
```yaml
ports: ["8090:8858"]
#     宿主机端口 : 容器内端口
#     外部访问的    进程实际监听的
```

**一次完整访问链路**：
```
浏览器 http://8.156.77.197:8090
  → 宿主机监听 8090(Docker 开的转发口)
  → Docker 转发 → 容器内 8858
  → java 进程(-Dserver.port=8858)响应 ✅
```

### 为什么必须映射
容器有独立网络（像独立房间）——容器内进程监听 8858 只在"房间里"有效，外面默认进不去，必须开"门"（映射）。类比：酒店前台（宿主机 8090）+ 房间（容器 8858）——客人只知道前台号，前台带你到房间，两边号码不必相同。

### 两边端口为什么可以不一样
Docker 中间转发，两边独立：外部 8090 = 部署时选的"对外招牌"；容器内 8858 = 镜像/进程定的"实际房间"。映射写对，外部任何端口都能转到容器内 8858。

### 故障案例（见 10-问题解决 Q3：HTTP 000）
```
写错:ports ["8090:8080"] → 宿主机 8090 转发到容器【8080】
     但 java 实际监听【8858】→ 转到没人听的端口 → HTTP 000
修对:ports ["8090:8858"] → 转发到 java 真在听的端口 → 能打开
本质:映射的"右边"写错(写 8080,进程在 8858),不是 8090 的问题
```

### 面试话术
> "端口映射 = 宿主机端口:容器内端口——Docker 在宿主机开个口,转发到容器内进程监听的端口。容器有独立网络,进程监听只对容器内可见,必须映射才能对外。两边端口独立不必相同,8090 是对外招牌、8858 是实际房间。Sentinel 那次打不开就是映射右边写 8080,但 java 真在 8858,转发到空端口 = HTTP 000。"

## 八、面试话术（全文总结：镜像层/可写层/COPY jar）

> "镜像层是只读模板——JRE 层 + jar 层，多容器共享、内容不可改、可分层缓存；可写层是容器私有草稿区——进程运行时的写入、exec 装的都在这，容器重建即销毁。秒杀是无状态服务，业务数据全在 Redis/MySQL，可写层基本空着，所以容器随便重建不丢——有状态的 MySQL/Redis 才必须挂卷。为什么 COPY jar 进镜像而不是直接跑：镜像把环境+程序+启动命令(JVM 参数、SW agent)打包成确定性的发布单元，可版本化可回滚可分发——就像预制菜包，拆开即食、味道一致；直接传 jar 只给食材，环境靠猜。Q1 的 IK 丢失就是装在可写层，重建就没了，所以要么挂载要么写进镜像。"

## 九、维护提示

Docker 其他概念（网络/volume/compose）随聊随补本节。
