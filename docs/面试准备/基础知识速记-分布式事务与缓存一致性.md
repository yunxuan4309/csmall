## 05-分布式事务（Seata）

### 一句话定义
分布式事务 = 一次业务操作**跨多个服务、多个数据库**时，
保证所有参与方数据一致的手段。Seata 是阿里的开源实现。

### 为什么本地事务不行
本地事务只能控制**自己一个库**。`commitSeckill` 
里 Dubbo 调 order 建订单，两个服务各自操作自己的库，
seckill 的本地事务管不了 order 的数据库。

### 核心三组件
| 组件 | 全称 | 类比 | 在项目里 |
|------|------|------|---------|
| TC | 事务协调者 | 总指挥 | Seata Server（独立中间件） |
| TM | 事务管理器 | 发起人 | mall-seckill 的 `commitSeckill` |
| RM | 资源管理器 | 干活的分支 | mall-product / mall-order |

### 4 种模式对比 & 为什么选 AT
| 模式 | 特点 | 侵入性 | 适合 |
|------|------|--------|------|
| **AT** | 自动：拦截 SQL + undo_log 快照回滚 | 无侵入，加注解 | 短事务、跨库强一致 |
| TCC | 手写 Try/Confirm/Cancel | 侵入强 | 高性能、业务自控并发 |
| SAGA | 状态机 + 逆向补偿 | 中 | 长事务（审批流） |
| XA | 数据库级两阶段 | 无侵入但**同步阻塞** | 标准但并发低 |

**选 AT 理由**：① 无侵入（只加注解）② 秒杀是短事务、
强一致 ③ 性能优于 XA（XA 全程持锁，AT 只短暂加全局锁）④ 
与 Dubbo 集成成熟。

### XA vs AT 核心区别（必考）
> **一句话**：XA = 数据库原生 2PC，全程持锁、同步阻塞（
> 强一致，并发低）；AT = 先提交后补偿，用 undo_log 快照（
> 最终一致，并发高）。核心区别 = **持锁时间 + 回滚方式**。

| 维度 | XA | AT |
|------|----|----|
| 实现 | 数据库原生 XA 接口（prepare/commit） | 框架拦截 SQL + undo_log 快照 |
| 一阶段 | prepare：执行但不提交，**锁住资源** | 业务 SQL **直接提交** + 写 undo_log |
| 二阶段 | 数据库原生 commit/rollback | 删 undo_log / beforeImage **逆向补偿** |
| 事务期间锁 | **全程持有** → 其他事务阻塞 | 短暂全局锁，本地事务立即释放 |
| 回滚方式 | 数据库原生回滚 | 应用层补偿 SQL |
| 一致性 | **强一致**（同步阻塞） | **最终一致**（异步补偿） |
| 并发/吞吐 | 低 | 高 |
| 风险 | 协调者单点，RM 挂了全局卡死 | undo_log 丢失/脏写需兜底 |

**AT 为什么是对 XA 的优化**：用"空间（undo_log）
"换"时间（锁的持有时长）"——XA 全程锁资源所以慢，AT 
先提交快速释放、失败靠快照补偿。

**防追问：XA 是不是没用了？** 不是。强一致要求极高、
并发不高的场景（如金融对账）仍用 XA；AT 
的全局锁高并发下也可能成瓶颈；业务要精确控制补偿则上 TCC。
看场景选型。

### 项目实际使用（真实情况，面试加分）
- **TM**：mall-seckill 
  `commitSeckill`（
  @GlobalTransactional）
- **RM**：mall-product 
  `reduceStockNum`（扣库存）；mall-order 
  建订单（XID 经 Dubbo 传播参与）
- **XID 传播**：mall-common 自研 
  `SeataTransactionConsumerFilter/ProviderFilter`
  （修官方 2.1.0 bug）
- **undo_log 表**：cs_mall_pms / 
  cs_mall_oms / cs_mall_seckill 三个库
- **演进故事**：order 早期自己加全局事务，库存扣减改 
  **MQ 异步**后移除注解（代码注释里写着）
  ——秒杀主链路用 AT 
  保强一致，普通下单走 MQ 保最终一致，按场景取舍

### undo_log 真的保证一致性吗？（批判性）
- **不能**。一致性靠**三件套**：TC 全局提交/回滚协议 + 
  全局锁写隔离 + undo_log 补偿
- undo_log 存 beforeImage/afterImage（
  改前改后快照），**和业务 SQL 
  同一本地事务写入**（同生共死）
- 回滚：TC 决定 → RM 用 beforeImage 生成逆向 
  SQL 恢复 → 删 undo_log
- **边界**：依赖业务表有主键；回滚是逆操作，
  极端并发恢复可能非预期值（全局锁降风险非零）；undo_log 
  异步清理占空间；无多副本

### 常被追问
- **自研 Seata Dubbo Filter 是什么？** 
  Seata 2.1.0 的 
  `dubbo-filter-seata` 
  在无 XID 场景取 branchType → NPE。自研 
  Filter 先判 XID 再安全取，SPI 注册。
  **Apache 
  Seata v2.2.0 已修复**（#6816），升级后可移除
- **AT 会锁全局记录吗？** AT 默认全局读已提交 + 写隔离（
  全局锁），比 XA 同步阻塞高效
- **回滚遇到并发修改怎么办？** 全局锁降风险 + 版本号乐观锁兜底 
  + 补偿幂等 + 对账任务，工程上可接受（详见 01-架构设计决策.
  md Q5）

### 面试怎么讲
> "undo_log 不是一致性本身，是 AT 模式回滚的依据。
> 真正的一致性是 TC 协调的全局提交/回滚协议 + 全局锁 + 
> undo_log 三件套共同保证的，它只是必要的一环，而且依赖主键、
> 依赖与业务 SQL 原子写入——所以长事务/复杂补偿我会换 TCC 
> 或 SAGA。"

## 07-Redis 与分布式事务

### 一句话定义
Seata AT 只回滚**数据库**（undo_log），
**Redis 操作不在它管辖内**。Redis 与 DB 
交织在同一全局事务里时，回滚会产生不一致，需**应用层手动补偿**。

### 为什么会有不一致
秒杀 `commitSeckill`（
@GlobalTransactional）里：Redis DECR 
扣库存、set orderedKey；DB 建订单、插 
success 记录。全局回滚时 DB 被 undo_log 补偿，
**Redis 已扣的库存不会自动恢复** → Redis 库存少、
DB 库存多。

### 项目实际做法（手动补偿三层，不是靠 Seata）
1. **try-catch 手动反向补偿**：订单失败 
   `increment()` 库存 + 删锁；后处理失败再删 
   orderedKey（代码注释"补偿Redis库存"）
2. **TTL 兜底**：orderLockKey 1 分钟、
   orderedKey 2 小时自动过期
3. **以 DB 为最终真相**：Redis 库存是可重建的预扣缓存，
   重启预热任务从 DB 重灌

### Redis 与 DB 一致性的三种策略
| 数据 | 策略 |
|------|------|
| 秒杀库存 | Redis 预扣 + DB 最终真相 + SQL `seckill_stock>=数量` 防超卖 |
| 分类树 | Cache Aside + 短 TTL（1 分钟），短暂不一致可接受 |
| 普通商品 | 没走缓存（SpuServiceImpl 直查库），无一致性负担 |

### 常被追问
- **能不能让 Redis 也回滚？** 可以但复杂：把 Redis 
  预扣纳入补偿（Lua 脚本 + 事务钩子），或上 
  TCC 业务自控 
  Try/Cancel
- **最终一致 vs 强一致？** 项目接受最终一致；强一致场景换 
  TCC/SAGA

### 面试怎么讲
> "Seata 只管数据库，Redis 补偿靠业务 try-catch 
> 手动做 + TTL 兜底 + 以数据库为准。Redis 
> 库存是可重建的预扣缓存，最终一致就够，强一致换 TCC。"

## 08-缓存三大问题（穿透/击穿/雪崩）

### 一句话定义
三个都是"缓存没挡住、请求打到 DB"，但原因完全不同。

| | 穿透 | 击穿 | 雪崩 |
|---|------|------|------|
| 查什么 | 查**不存在的 key** | 一个**热点 key** | **一大批 key** |
| 为什么打库 | 数据不存在，缓存永远没有 | 单个热点 key 过期瞬间 | 大量 key 同时过期（或 Redis 宕机） |
| 比喻 | 天天敲**不存在的门**，仓库也没有 | 爆款缓存恰好过期，**所有人同时**查这一个 | **所有货架同时到期**，都涌去仓库 |
| 本质 | 无效请求（恶意刷） | 单点瞬时冲击 | 群体性失效 |
| 防御 | 布隆过滤器 / 缓存空值 / Set | 互斥锁重建 / 热点永不过期 | 随机 TTL / 集群高可用 |

### 记忆口诀
- **穿透** = 数据**不存在**（和过期无关）
- **击穿** = **一个**热点 key **过期**
- **雪崩** = **一堆** key **同时过期**

### 项目实际应对
- 穿透 → Redis **Set** 记录秒杀 SPU ID（
  没用布隆：本地 Redis 不支持 RedisBloom）
- 击穿 → 秒杀库存**预扣 + 限流**保护热点 key
- 雪崩 → 分类树用**短 TTL**（1 分钟）减少同时失效堆积；
  生产可加随机 TTL

### 面试怎么讲
> "穿透是查不存在的数据，缓存永远为空，靠布隆/Set 挡；
> 击穿是一个热点 key 过期的瞬时冲击，靠互斥锁或预扣+限流；
> 雪崩是一批 key 同时过期，靠随机 TTL 错开。三个我都处理过：
> Set 防穿透、预扣+限流防击穿、短 TTL 防雪崩。"

## 09-幂等（防重复提交）

### 一句话定义
幂等 = **同一个操作重复做多少次，结果都和只做一次一样**。用 
**Redis SETNX + TTL** 实现"同用户 + 同参数 
+ 时间窗内只执行一次"。

### 生活例子（取票机）
1. 第一次按"取票" → 取票机记下"已取票"（SETNX 成功）→ 出票
2. 手抖再按 → 取票机查"已取票"（SETNX 失败）→ 
   拒绝"请勿重复操作"
3. 记录 TTL 自动清掉（如 5 秒），之后不影响正常操作
4. 取票失败（卡纸）→ 代码主动删记录 → 允许重新取

### 项目实现（IdempotentAspect，AOP）
```java
@Around("@annotation(idempotent)")          // 拦截 @Idempotent 方法
String lockKey = "idempotent:" + key + ":" + userId + ":" + md5(参数);
Boolean acquired = setIfAbsent(lockKey, "1", expire, SECONDS);
if (false == acquired) throw 409 "请勿重复提交";
try { return point.proceed(); }             // 第一次放行
catch (e) { delete(lockKey); throw e; }     // 失败释放，允许重试
```

### 三个关键点
1. **key 组成** = 业务 key + userId + 参数 
   MD5 → 不同用户/参数不误判
2. **setIfAbsent 原子性** → 并发下只有一个请求能拿到锁
3. **TTL 防死锁 + 失败释放允许重试** → 锁不会永久占住

### 使用位置与时间尺度
| 场景 | TTL | 防什么 |
|------|-----|--------|
| 幂等锁（下单 5s/支付 10s/秒杀 3s） | **秒级** | 防**瞬时重复提交**（连点、网络重试） |
| 防重复购买三 key | 分钟~小时级 | 防**业务上真的重复买** |

### 和秒杀手写锁的关系
`commitSeckill` 里 `orderLockKey.
setIfAbsent("1",1,MINUTE)` 
是**同原理手写版**；`@Idempotent` 是通用 AOP 
封装。两者都靠 SETNX + TTL。

### 面试怎么讲
> "幂等不是锁业务，而是用 Redis SETNX 
> 保证同一把锁只能被一个请求拿到，TTL 防死锁、失败释放允许重试。
> 它是短时间窗的去重，防的是手抖连点和网络重试；
> 防业务上重复购买是另一套三 key 机制，时间尺度完全不同。"

## 10-秒杀防重三 key

### 一句话定义
三把 Redis 钥匙，时间尺度递进（1 分钟 → 2 小时 → 
永久），覆盖"下单瞬间 → 未支付 → 已购买"三关防重。

| # | Redis key | TTL | 职责 | 写入时机 |
|---|-----------|-----|------|---------|
| ① | `mall:seckill:order:lock:{skuId}:{userId}` | **1 分钟** | 下单锁：防连点 | 点秒杀按钮时 |
| ② | `mall:seckill:ordered:{skuId}:{userId}` | **2 小时** | 未支付标记：有单没付别重复下 | 下单成功后 |
| ③ | `mall:seckill:reseckill:{skuId}:{userId}` | **永久** | 购买标记：付过就不能再买 | **支付成功后** |

### 生命周期（下单 → 支付 → 结束）
1. 提交下单：先查 ③ 已买过？→ 拒；拿 ① 锁（抢不到=连点）→ 拒；
   查 ② 有未付单？→ 拒
2. DECR 库存 → Dubbo 建订单 → set ② = 
   订单号（2 小时）
3. 支付成功：delete ② + set ③ = "1"（
   永久标记已购买）
4. 取消订单：delete ② + delete ①（允许重新下单）

### 为什么必须分开（历史踩坑，面试亮点）
早期"下单锁"和"购买标记"混用成一个 key → **下单锁 1 
分钟过期后，用户支付完还能再抢**。分离后职责单一：**① 防手抖、
② 防"没付还占坑"、③ 防"付过还来抢"**，时间尺度递进互不干扰。

### 面试怎么讲
> "秒杀防重用三把 Redis 钥匙，时间从 1 分钟到 2 
> 小时到永久递进。分开是因为早期混用出过'支付后还能再抢'的 
> bug——下单锁过期后没有独立的购买标记拦住他。分离后三关各管一段：
> 防连点、防未支付重复下、防已购再来。"

## 11-限流熔断与雪崩

### 一句话定义
限流管"来多少请求"，熔断管"下游还活着吗"；
服务雪崩是服务间级联故障，缓存雪崩是缓存失效砸垮 DB。

### 限流 vs 熔断
| 维度 | 限流 | 熔断 |
|------|------|------|
| 管什么 | 进来的请求量 | 下游健康状态 |
| 触发依据 | 请求量超阈值（QPS=10） | 错误率/耗时超阈值 |
| 时机 | 主动预防 | 被动反应 |
| 保护对象 | 自己不被流量打爆 | 不被下游拖垮 |
| 类比 | 门口保安只放 X 人 | 电路保险丝跳闸 |
| 失败行为 | 快速失败/排队 | 短路快速失败 |
| 状态机 | 无 | 关闭→打开→半开 |
| 工具 | Sentinel 限流、令牌桶 | Sentinel 熔断、Hystrix |

### 熔断为什么能防服务雪崩
- **服务雪崩机制**：A 调 B，B 慢/挂 → A 线程
  傻等 B（同步等待）→ A 线程池占满 → A 也假死
  → 传染给 C → 级联放大，整个链路瘫痪
- **熔断断在源头**：下游错误率超标 → 断开不再调用
  → 线程不空等 → 快速失败 → 故障隔离在 B 一点
- 核心 = **快速失败 + 故障隔离**

### 服务雪崩 vs 缓存雪崩（不是一回事）
| | 服务雪崩 | 缓存雪崩 |
|---|---------|---------|
| 故障层级 | **服务之间**的调用链 | **缓存→数据库**之间 |
| 发生机制 | 同步等待 + 线程耗尽 | 缓存失效 + 压力传导 |
| 防御 | 熔断/降级/隔离/超时 | 随机 TTL/多级缓存/集群 |
| 精神相通 | 都是"局部失效被级联放大" |

### 面试怎么讲
> "限流管流量维度——每秒只放 10 个进；熔断管依赖
> 维度——下游错误率超标就跳闸快速失败，线程不空等，
> 故障隔离在源头防级联雪崩。服务雪崩和缓存雪崩不是一回事
> ——一个服务间级联、一个缓存失效砸垮 DB，但都是
> 局部失效被级联放大，所以各防各的。"
