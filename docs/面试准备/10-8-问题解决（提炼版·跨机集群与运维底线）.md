### Q20. #46+#47 有状态组件的两条铁律：**没挂卷 = 重建即丢；备份没验证过 = 没有备份**

> 来源：[[问题解决--有状态组件的持久化与可恢复性]] §二 / §四 / §五

【追问1】nacos 容器 healthy、403 也正常，你凭什么说它的数据"根本没接上"？
【追问2】你手动建的卷，compose 为什么不认？这种事故为什么会**零报错**？
【追问3】备份文件每天都在生成、有大小、有成功日志 —— 这还不算"有备份"吗？

【简答】有状态组件只有两条铁律：**① 持久化** —— 一律挂**命名卷**，而且**卷名/属主要对得上**；**② 可恢复性** —— 必须用**独立临时容器演练**证明，"脚本在跑"不算证明。附带一条把纪律变成断言的手段：**哈希指纹**（多跳下发后 `md5sum` 比对，一致 ⟺ 字节级相同）。

【深挖】
- **#46：nacos 是 21 个容器里唯一没挂卷的中间件**
  - derby 的配置/用户/规则全裸存在容器**可写层** `/home/nacos/data`，重建（`compose up` / 版本升级 / 故障 recreate）即清空 —— **`#13` 部署时已实测丢过 6 条 Sentinel 规则**。
  - ⚠️ **唯一症状是登录报 `User nacos not found`**：容器 healthy、无 token 403 正常 ⇒ **"零报错 + healthy"不是配置生效的证据**。
- ⭐ **最值钱的坑是"卷名前缀"**：compose 卷名 = `项目名_卷名` = **`csmall_nacos_data`**，而我手动 `docker volume create nacos_data` 建的是**裸名卷**，compose 根本不认识它。
  - 后果链：compose 发现 `csmall_nacos_data` 不存在 → **静默自动建了一个空卷**挂上去（这是它的设计行为，不是报错）→ nacos 在空库上全新初始化（derby 文件时间戳 = 本次启动时刻）→ **没用户、没规则，但容器 healthy**。
  - **三证据锁定根因**：① 卷列表出现**两个**卷（手动的 `nacos_data` + compose 的 `csmall_nacos_data`）；② `docker inspect` 看挂载名是 `csmall_nacos_data`；③ `docker compose config` 输出 `name: csmall_nacos_data`（**真相在此，它是排坑神器**）。
  - 修复与验收：删空卷 → 用**全名**重建 → 从备份灌入 → `up -d`；验证 **403 / 登录 accessToken / 6 条规则 / 挂载名 / 27 个服务重注册**全通过（数据全程零丢失，宿主机备份 + 卷双保险）。
- **587.6M → 8.5M 不是丢数据**：运行中 `du` 的 587.6M 里 **protocol 584.9M 是 JRaft/RocksDB WAL 的膨胀态**，`docker stop` 优雅停机后 compact 到 **5.8M**；`docker cp` 复制的是**停机后的持久状态** = **8.5M**。
  - 真正"重建即丢且不可再生"的只有 **derby-data（运行中 2.7M ≈ 备份 2.8M，量级一致）** ⇒ **备份实质完整**。
  - 判据：**容器数据备份以"停机后"为准**（或在运行中容器里用 `docker exec tar`，别直接 cp 目录，否则可能拷到不一致的中间态）。
- **#47：备份没验证过 = 没有备份** —— cron 每天 **02:30** 跑 `backup-db.sh`（`docker exec mysqldump --databases 6 库 | gzip`，靠 **`--single-transaction`** 做 InnoDB 一致性快照、不加锁备份），文件在、有大小（本次验证对象就是 cron 产物 **`cs_mall_20260909_0230.sql.gz`，49KB**）、有成功日志 —— 但**从没还原过**。
  - 我**自己否掉了第一版方案**（在生产容器内 `sed` 改库名导临时库）：备份含 `CREATE DATABASE` + `DROP TABLE IF EXISTS`，**只要一处漏网**（`USE cs_mall_ams` 以原名执行）就**触发 DROP 清空生产表** ⇒ "依赖替换完备性"的风险不为零，对"演练"不够纯粹。
- ⭐ **最终方案 B：独立临时容器（把风险面从"小心替换"变成"物理隔离"）**
  - 配置：同版本 `mysql:8.0`、`--memory 512m`、**不映射端口**、匿名卷、`--innodb-buffer-pool-size=64M`（空实例默认 128M+，49KB 演示数据用不到）；**原名直接导入、无 sed**（临时库里没有生产数据，DROP 谁都无所谓）。
  - 实测：退出码 **0**，恢复库 **39 表**（ams7/oms6/pms15/resource2/seckill6/ums3）+ 抽样**逐行一致**（`ums_user` **110** / `pms_spu` **20** / `ams_admin` **3** / `oms_order` **86** / `seckill_spu` **6**）；`docker rm -f` **用完即删、零残留**，**生产全程零接触**（生产 `csmall-mysql` 事后仍 Up healthy）。
  - ⚠️ **诚实边界**：只验证了"单日全量可还原"，**没做单表定点恢复**（`--databases` 全库模式不支持）**和跨机恢复**（灾难场景需新机 + 备份异地 → 建议 rsync 到异机/对象存储）。
- **哈希指纹（§5.8）：把纪律变成断言** —— 一次下发跨 **4 跳**（本地仓库 → `scp` → 服务器 `/tmp` → `sudo cp` → `/data/csmall`），每跳都可能**静默改字节**（CRLF↔LF、UTF-8 BOM、传输截断、`cp` 未报错的失败）⇒ 落位后 `md5sum` 比对，**一致 ⟺ 与仓库字节级相同**。
  - 哈希是**内容的身份证，不是版本号**：版本号人为命名、单调递增、有顺序含义；哈希是内容的数学函数、**无顺序含义**，改 1 个字节 32 位十六进制全变（雪崩效应）—— 这正是我们要的。
  - **行业里是同一个原理的自动版**：ISO 公布 SHA-256、Maven 制品旁挂 `.sha1`、镜像 **digest = `sha256:…`**、K8s 靠内容哈希触发滚动更新、Ansible/GitOps 下发后做漂移检测 ⇒ **我们做的是手工版（AI 算 + 人比对），原理完全相同**。
  - ⚠️ **MD5 已被证明可构造碰撞（2004 年起）→ 只防意外损坏、不防恶意篡改**，安全场景用 **SHA-256**；**`.env` 例外：只统计行数/权限，连哈希也不对外报**（避免任何形式的凭据侧信道）。

**面试话术**
"有状态组件我就两条铁律：**没挂卷 = 重建即丢，备份没验证过 = 没有备份**。#46 我给唯一没挂卷的 nacos 补卷 —— 它是 21 个容器里唯一一个，derby 的配置、用户、规则全裸存在容器可写层，重建就丢，`#13` 时就实测丢过 6 条 Sentinel 规则。过程踩了两个坑：一是 **`docker cp` 出来只有 8.5M 而运行中 `du` 是 587.6M**，我一度怀疑备份不完整，追下去发现差的是 JRaft/RocksDB WAL 的膨胀态，停机 compact 后 protocol 只剩 5.8M，真正不可再生的 derby-data 2.7M 完整无损 —— 所以**容器备份要以停机后为准**；二是**卷名前缀**，compose 的卷名是 `项目名_卷名`=`csmall_nacos_data`，我手动建的是裸名卷 `nacos_data`，compose 不认识就**静默自动建了个空卷**挂上去，容器 healthy、403 正常，唯一症状是登录报 `User nacos not found`；我靠三个证据定位：卷列表里出现两个卷、`docker inspect` 看挂载名、**`docker compose config` 直接显示真实卷名**。#47 同理 —— 脚本在跑 ≠ 能恢复，而且我**自己否掉了第一版方案**：本来打算在生产容器里 `sed` 改库名导临时库，但备份里有 `DROP TABLE IF EXISTS`，`sed` 只要漏一处、`USE cs_mall_ams` 以原名执行就会清空生产表，'依赖替换完备性'的风险不为零；最后改成**独立临时容器**：同版本 mysql、限 512M、不映射端口、匿名卷，备份原名直接导入，验证 6 库 **39 表** + 抽样逐行一致（用户 110、订单 86 等），然后 `rm -f` 删容器，**生产零接触**。这两条线共用一条纪律：**哈希指纹** —— 一次下发跨 4 跳，每跳都可能静默改字节，`md5sum` 一致才算'仓库是事实来源'；但 MD5 只防意外不防篡改，安全场景要 SHA-256，凭据文件连哈希都不报。"

### Q21. #4 跨机第一道坎不是业务，是**"地址"的三重语义**（监听 / 注册 / 连接）

> 来源：[[问题解决--跨机通信的地址三重语义]] §三 / §四 / §六 / §七

【追问1】秒杀副本报 `No provider available from registry`，你第一反应查什么？为什么不是先查业务代码？
【追问2】`DUBBO_PORT_TO_REGISTRY` 你填的是容器内端口，还是映射后的宿主端口？
【追问3】把端口绑到私网 IP，是不是就等于"公网连不上"了？

【简答】同一个"地址"在跨机后有**三重语义**：**监听地址**（进程绑哪个网卡收包）、**注册地址**（注册中心里别人看到谁）、**连接地址**（副本连数据源 / 向新主上报用谁）。**改错任意一个，症状都一样：服务在跑、端口在听、注册也有，链路就是不通**。单机上这三种写法常常"碰巧都能通"（同网段、同宿主机、容器名可解析），跨机后每一个都必须显式回答"**这个地址是给谁看的**"。

【深挖】
- **根因（注册地址写错）**：Dubbo 的地址解析链是 `消费方订阅接口 → Nacos 返回 provider 地址列表 → 消费方【直连】该地址` —— **Nacos 只做注册发现、不做流量代理**（它不是网关，不会替你转发）⇒ **注册进去的地址必须是"消费者能直连的地址"**。
  - 容器默认用 `InetAddress.getLocalHost()` 注册 **bridge 容器 IP**，单机内同网段互通所以一直没暴露，**跨机立刻断**：新机副本拿到 **`172.18.0.18:20880`**（老机 bridge 网段）→ 新机路由表里没有 `172.18.0.0/16` → `No provider available from registry` / client-side timeout。
  - Nacos API 实测（三个实例**全是容器 IP**）：`mall-product` = **172.18.0.18:20880**、`mall-order` = **172.18.0.20:20880**、`mall-seckill` = **172.18.0.19:10007** —— **HTTP 发现与 Dubbo 注册都是容器 IP**。
- **解法：选"注册层改写"，不选"网络层打通"** —— 老机 product/order 加 **`DUBBO_IP_TO_REGISTRY=172.29.193.239`** + `DUBBO_PORT_TO_REGISTRY` + compose 发布 `20880:20880` / `20881:20880`，这是 Dubbo 官方为容器/NAT 场景提供的**声明式**机制，**无"网段变更即失效"隐患**。
  - 被否掉的那条路：新机 host 网络 + 静态路由 `172.18.0.0/16 via 老机` —— 老机零改动，但属**手工版 overlay**（依赖对端网段、无自愈、单向可达），**不是规范做法**。
  - **按需改造、改动面最小**：跨机依赖只有秒杀副本对 product/order 的 Dubbo 调用（扫过代码，`mall-seckill` 没有任何 HTTP/Feign 调用）⇒ **老机只改 2 个服务，其余 19 个容器零改动**。
- **两个必踩的细节**：① **`dubbo.protocol.port: -1`（各模块默认）是隐形地雷** —— 自动选端口 ⇒ 没法做端口映射，**跨机必须显式固定协议端口**（`DUBBO_PROTOCOL_PORT`）；② **`DUBBO_PORT_TO_REGISTRY` 必须填"映射后的宿主端口"**（product **20880** / order **20881**，宿主端口要错开），**不是**容器内的 20880。实测支撑：容器 → 宿主私网 IP 的映射端口可达（`/dev/tcp/172.29.193.239:8848|5672|9200` 全 OK），本地消费方改走宿主 IP **只多一跳 docker-proxy、无副作用**。
- **连接地址（同一族的第二种形态）**：老机 Redis 必须配 **`replica-announce-ip 172.29.193.239` + `replica-announce-port 6379`** —— 它**被降级为从库时**要向新主上报自己的地址，若上报容器 IP `172.18.0.22` → 新机不可达 → **复制断链**，这就是"**切换成功但回不来**"的隐形杀手（光看哨兵日志发现不了）。
  - **哨兵必须 3 个**：多数派机制，容忍度 =`(哨兵数−1)/2` ⇒ 3 哨兵容忍挂 1、**2 哨兵容忍 0**（挂 1 即失去仲裁）；⚠️ **数据节点（主/从）不需要奇数** —— 复制不是投票。
  - **有没有注册中心，决定用不用 host 网络**：Redis/哨兵无注册中心 → `network_mode: host` 天然满足"主/哨兵看到可达地址"；秒杀副本必须在 Nacos/Dubbo 注册**宿主 IP + 映射端口** → 用 bridge + 显式覆盖。
- **监听地址（①）+ 一个 Docker 挂载的硬限制**：老机 **3306/6379 由 `127.0.0.1` 改绑宿主私网 IP `172.29.193.239`** —— 绑 `127.0.0.1` 只收本机流量，**跨机永远连不上，而端口"看似在听"**。
  - 同批还有个坑：**单文件 bind-mount 不能被 rename 覆盖**。哨兵每次状态变化（发现从库 / 发现其他哨兵 / 选出新主）都要"写 `.tmp` → rename"重写自己的配置（`sentinel myid` / `known-replica` / `known-sentinel` / 新主地址），写不进去时它**内存里照常工作（监控、投票、切换全正常），一重启就退回监视旧主地址**。
  - 处置 = **挂目录**（`./redis:/conf`）+ 宿主目录 `chown 999:1000`（容器内 redis 进程是 uid 999）；修好后日志出现 `Sentinel new configuration saved on disk`。⭐ **这类问题不重启、不演练根本发现不了**。
- ⭐ **认知修正：「绑了私网 IP 就安全了」在阿里云 NAT 架构下根本不成立**：公网 IP **不在网卡上**，是阿里云侧的 **NAT 映射**；发往公网 IP 的包**先被 DNAT 成私网 IP 再进网卡** ⇒ **监听 `0.0.0.0` 与监听 `172.29.193.239` 的公网可达性完全等价**，**真正决定公网能不能连的只有安全组**。
  - 巡检实证（本地非 VPC 探测）：老机 **6379/3306/10087** 与新机 **26379/6380 全部 blocked**，只有老机 **`:80` REACHABLE**（SG 放行了）—— 与绑的是私网 IP 还是 `0.0.0.0` **毫无关系**。
  - 所以边界是**四层**：**L1 安全组（唯一真正的公网边界）→ L2 `bind`/`ports`（监听面收敛，属纵深防御）→ L3 `requirepass`/ACL（身份）→ L4 TLS（传输）**；**把 L2 当成 L1 是这类误解的根源**（绑私网 IP 只对"内网/本地暴露面"有意义）。
  - 跨机流量一律走**内网 IP**：内网不限速不计费；老机公网仅 **5Mbps** 固定带宽（瓶颈），新机按量计费 ⇒ **走公网 = 又慢又花钱**。

**面试话术**
"跨机部署最大的坑是 **Dubbo 注册的是容器 IP**。我实测 Nacos 里 provider 全是 `172.18.0.x:20880`（product 172.18.0.18、order 172.18.0.20、seckill 172.18.0.19）—— 单机内没问题，跨机直接 `No provider available from registry`。根因是 **Nacos 只做注册发现、不做流量代理**，消费方拿到地址后是**直连**的，所以注册进去的地址必须是消费者能直连的；容器默认用 `InetAddress.getLocalHost()` 拿到容器 IP，单机同网段碰巧通，跨机必断。我用 Dubbo 官方为容器/NAT 场景提供的 `DUBBO_IP_TO_REGISTRY` + `DUBBO_PORT_TO_REGISTRY`，让 provider 注册**宿主内网 IP + 映射端口**；这里有两个细节：`dubbo.protocol.port: -1` 是自动选端口，跨机**必须显式固定**才能做映射；`DUBBO_PORT_TO_REGISTRY` 要填**映射后的宿主端口**（product 20880 / order 20881 得错开），不是容器内的 20880。另一条路是新机加静态路由打通老机 bridge 网段，属**手工版 overlay**、依赖对端网段、无自愈，**我选了规范的那条，并把老机改动收敛到 2 个服务**。Redis 那边是同一族问题的另一种形态：除了哨兵选主，还必须给老机 Redis 配 **`replica-announce-ip`** —— 它被降级成从库时要向新主上报**宿主内网 IP**，否则上报容器 IP，新机连不回来、复制就断了；这种'**切换能成功、但回不来**'的坑，光看哨兵日志发现不了。最后我把边界认知也纠正了：我原以为把端口绑到私网 IP 就等于不对外暴露，实测发现阿里云**公网 IP 是 NAT 映射、根本不在网卡上**，所以 `bind 0.0.0.0` 和 `bind 172.29.193.239` 的**公网可达性完全等价** —— 6379/3306/26379 这些端口**全被安全组挡在外面**，而绑法五花八门。所以我的边界模型是四层：**SG 是边界、bind 是监听面、认证是身份、TLS 是传输**。"

### Q22. #4 "集群"不是"多起一个实例"：**四个必须被分别证明的机制 + 一层诚实的边界**

> 来源：[[问题解决--集群机制的验证（负载均衡·故障转移·剔除）]] §二 / §四 / §五 / §七 / §八

【追问1】你配了 `lb://mall-seckill` 就说负载均衡生效了 —— 凭什么说它是**均分**的？
【追问2】停掉一个实例，服务还能用吗？"高可用"和"零中断"是一回事吗？
【追问3】既然 `min-replicas-to-write 1` 更安全，为什么从库一停，主库就写不进去了？

【简答】四个机制必须**分别被证明**：① **负载均衡真的均分**（"配了轮询"只是声明）；② **故障转移真的自动**（切换不靠人）；③ **注册剔除真的有窗口**（"注册中心摘除" ≠ "客户端停发"）；④ **优雅下线真的零中断**。最后必须自己划出边界：**副本要分布在"会独立故障的机器"上** —— 只有两台机器时 `min-replicas-to-write` 存在**固有局限**，**2 台机器下无解**。

【深挖】
- **① 负载均衡：60 请求 → 精确 30:30**。"谁来告诉你这个请求被哪个实例处理了"在本项目里**没有现成答案**：服务访问日志没配、`actuator/metrics` 被业务 `SSOFilter` 拦住（返回业务 401 体）、网关日志只在出错时才有 ⇒ **可观测性不够时，就用"副作用 + 来源 IP"来归因**。
  - 办法：`/seckill/spu/list` 的实现里对列表中每个 SPU 都做一次 `hasKey`，**每请求固定产生 12 条 `EXISTS mall:seckill:reseckill:<spuId>:<skuId>`**；而 Redis `MONITOR` 记录**命令来源 IP**（`172.18.0.1` = 老机实例经 docker bridge SNAT、`172.29.193.240` = 新机实例宿主 IP）。
  - 实测：**60 请求全部 HTTP 200**、`EXISTS` 总数 **720 = 60×12**、老机 **360** / 新机 **360** ⇒ **分布 50%:50%（精确 30:30）**，**Spring Cloud LoadBalancer 默认 `RoundRobin` 跨机精确均分**。
  - 踩点：登录字段名是 **`tokenValue`** 不是 `token`，且必须带 `Bearer` 前缀；`/seckill/spu/list` 不带 `page` 会报 `Cannot invoke "Integer.intValue()" because "page" is null`。
- **② 故障转移：6.1s 选主 + 9.1s 客户端自愈**。一次选主四阶段：`+sdown` 主观下线（+0~5s）→ `+odown` 达到 `quorum`（**+5.0s = `down-after-milliseconds 5000`**）→ `+elected-leader` 基于 Raft 选出主持切换的哨兵（**+5.1s**）→ `+promoted-slave`/`+switch-master` 提升从库并广播新拓扑（**+6.1s**）。
  - **时间绝大部分花在"必须等够 5s 才能确认主库真死"**（否则网络抖动就会误切），真正的选举 + 提升只用了 **1.1s** ⇒ 这个值就是"**误判风险 vs 切换速度**"的旋钮：调小切得快但易误切，调大更稳但停机久。
  - 客户端侧 Lettuce `ConnectionWatchdog` 先按退避重连旧地址 → 失败就**重新向哨兵询问主地址**：`11:34:01.810` 重连失败 → **`11:34:10.912 Reconnected to 172.29.193.240:6380`（9.1s 自愈）** → `11:35:59` 切回老主（`SENTINEL FAILOVER` **1.1s**）；11 个服务零硬错误、**数据零丢失**。
  - ⚠️ **对照**：若客户端还是 standalone 模式，它会**永远重连那个已死的旧地址** —— 主从切换对它是"从可用变成不可用"，这正是必须把 11 个服务全迁到哨兵模式的原因。
- **③ 脑裂窗口 10.9s ⇒ `min-replicas-to-write 1` 不是可选项**。老主库重启后，因为 conf 里**没有 `replicaof`**，它会**按静态配置自认为主**（实测 `role:master` 持续 **10.9s**），直到哨兵下发 `+convert-to-slave` 才降级。
  - 业务没事（客户端只连**哨兵返回的地址**），但**万一有客户端/脚本直连老地址**，这 10.9s 内会把数据写进一个**即将被全量覆盖的主库**。所以开 **`min-replicas-to-write 1` + `min-replicas-max-lag 10`**（**仅老机主库**，已落盘 `/data/csmall/redis/redis-master.conf` **第 15~16 行**；`CONFIG REWRITE` 在单文件 bind mount 上必然 `Resource busy`，故走手工追加、**无需重启**）。
  - 🔴 **红线：哨兵 conf 是"运行时状态"，不能反向覆盖** —— 演练后 3 个 `sentinel-*.conf` 被整体重写，多了 `config-epoch`/`myid`/`known-replica`/`known-sentinel`；仓库里的 conf 只是**初始模板**，反向覆盖会丢 epoch 与拓扑认知。
- **④ 注册剔除：Nacos <1 秒摘除，但客户端有 ~16s 窗口**。停实例实测时间线：`21:29:06` 网关 500 而 **Nacos 实例数已变 1（不到 1 秒摘除）** → **21:29:06~21:29:22 500/200 交替**（网关仍把一半请求打到死实例）→ `21:29:24+` 全部 200；`21:32:07` 副本恢复、实例数回 2。根因日志 `finishConnect(..) failed: Connection refused: /172.29.193.240:10017`。
  - **服务发现有三层，任何一层有延迟都会出现"打到死实例"的窗口**：① 实例 → 注册中心：**<1 秒**（Spring Cloud Alibaba 优雅停机**主动注销**，`ContextClosedEvent → deregister`；⚠️ 若是 `docker kill`/进程崩溃，就只能等 **15s 心跳超时**）；② 注册中心 → 客户端：秒级（Nacos 推送 + 客户端兜底轮询）；③ 客户端本地 LB 缓存：**`spring.cloud.loadbalancer.cache.ttl` 默认 35s，实测窗口 ~16s**。
  - ⇒ **"高可用"治的是"服务还能用"，"零中断"要的是"请求一次都不失败"** —— 这个窗口光看配置文件永远发现不了。
- **⑤ 优雅下线：16s 窗口 → 0**。⚠️ **`DELETE /nacos/v1/ns/instance` 注销是无效的**（返回 `ok`，但客户端心跳立刻把它重新注册，30s 内始终存在）；必须用 **`PUT ...&enabled=false`**（**实例仍在服务，只是不再被负载均衡选中**）。
  - 流程：`enabled=false` → **等 20s**（> LB 缓存 TTL，滚动发布一般等 30–60s）→ `docker stop` ⇒ **30 次请求 0 失败**（粗暴停是 **9 次 5 失败**）；`docker start` 后启动时自动以 `enabled=true` 重新注册（网关 10/10 成功）。
  - 脚本 `deploy/scripts/graceful-stop.sh` —— **这是"操作流程层"的修复：零配置变更、零重启**，本质就是 K8s 的 `readiness probe + preStop sleep`；兜底手段还有网关重试 / 断路器 / 缩短 LB TTL（应对"别人直接 `docker kill`"这类绕过流程的情况）。
- ⚠️ **诚实边界：两台机器租不出高可用**。1 主 1 从下开 `min-replicas-to-write 1`，新机一停老机立刻报 **`NOREPLICAS Not enough good replicas to write.`**（**读还能用，写全挂** → 下单失败、库存扣减失败、锁拿不到）。
  - 根因：**Redis 复制是异步的**（主库写完就回客户端，不等也不确认从库），而**主库分不清"从库真死了"还是"只是网络断了"** —— 两种场景下 `connected_slaves` 都是 **0**。一个参数、两种情况、只能选一种行为 ⇒ **宁可误拒，也不静默丢数据**。
  - 为什么宁可报错：分区里继续写不是"写进安全的地方"，而是**写进一个即将被格式化的磁盘** —— 愈合时哨兵按 **`config-epoch`** 收敛到新主，老机被降级 + **全量同步覆盖**，它刚才写的全部作废；报错 → 用户看到失败、运维立刻知道、可重试；静默丢数据 → 几小时后才发现、无法挽回。
  - **为什么不能把从库放老机本地**：分区时老机能看见本机从库 → 参数满足 → 继续写 → **保护失效**；而且同机主从对"主机宕机"**零防护** ⇒ **同一台机器上的副本，在"这台机器挂掉"的场景里等于没有副本**。
  - **2 台机器下无解**（要么"某个节点挂了就不能写"，要么"允许静默丢数据"），正确演进是**把第三个副本放到第三台机器**，或**只对关键写用 `WAIT 1 100`**（等至少 1 个从库确认，超时 100ms）。⚠️ 该参数还有两个前提：**≥2 个从库**、**不要开在"可能被提升为主库"的从库上**（切换后新主库手里没有从库 → 会长时间拒写）。
  - 本项目取舍：**不加第三台**（再 ¥71/月，收益不划算）、**参数只开老机主库**、**停新机演练/维护前先 `CONFIG SET min-replicas-to-write 0`**（恢复后设回 1）⇒ 🟡 **接受这个局限：「已知、已量化、有开关」比「不知道」强得多**。

**面试话术**
"跨机集群这条线我做完最大的体会是：**'集群'不是'多起一个实例'，而是四个必须被分别证明的机制**。**第一，负载均衡真的均分** —— 我没有只相信配置里的 `lb://`，而是用 Redis `MONITOR` 把每个请求的副作用（每请求固定 12 条 `EXISTS`）按**来源 IP** 归因到实例：60 个请求拿到 **720 条 EXISTS**，老机 360 / 新机 360，**精确 30:30**，证明 `RoundRobin` 真的在跨机轮询；这也是我一条方法论 —— **没有监控指标时，'命令流 + 来源 IP'就是最可靠的归因手段**。**第二，故障转移真的自动** —— 我停掉老机主库做了真实演练：**6.1s 哨兵完成选主**（其中 5s 是 `down-after` 必须等够，真正的 Raft 选举 + 提升只有 1.1s），**9.1s Lettuce 客户端自动重连到新主**，11 个服务零硬错误、数据零丢失，之后 `SENTINEL FAILOVER` 1.1s 切回；而且我发现老主库重启后有 **10.9s 的脑裂窗口**（它按静态配置自认为主），所以 `min-replicas-to-write 1` 不是可选项 —— 官方 Sentinel 文档里就是拿这个场景举例的。**第三，注册剔除真的有窗口** —— 停实例后 Nacos **不到 1 秒**就摘除了，但网关侧仍有一半请求打到死实例报 500，持续 **~16 秒**，根因是服务发现三层里**客户端本地 LB 缓存（默认 TTL 35s）**这一层不即时，所以'**高可用不等于零中断**'。**第四，优雅下线真的零中断** —— 注意 `DELETE` 注销是无效的、心跳会立刻重新注册，必须 `PUT ...&enabled=false` 先摘流量、等 20s 超过缓存 TTL、再 `docker stop`，**30 次请求 0 失败**；这本质就是 K8s 的 readiness probe + preStop。最后我保留了一条**诚实的边界**：副本必须分布在'会独立故障的机器'上 —— 我只有 1 主 1 从两台机器，`min-replicas-to-write 1` 于是变成'新机一停老机就拒写'，这是**副本数量不足时该参数的固有局限**；我也想过把从库放回老机本地，但那会**破坏分区保护**、对主机宕机也零防护，所以最后量化后选择接受 + 保留'演练开关'，**而不是假装没这回事**。"

> **来源**：[[第⑯批-认知增量提炼一页版-2026-09-12]] §四 / §五（**该文档已于 2026-09-12 归档**）· 实测明细见 [[TODO已完成-明细-2026-09-12]] §二十一。

### A. 凭据与取证卫生（4 条）

1. **明文一旦进入聊天 / 文档 / 提交 ⇒ 视为已泄露**：处置只有两条路 —— **轮换**，或**书面记录「接受」并写明范围**（本项目各发生一次，且都留了档）。
2. **取证命令自己别造泄漏**：`--format '{{.Config.Image}} | {{range .Config.Env}}{{println .}}{{end}}'` 会把**镜像名与第一个环境变量粘成一行**，`grep` 一打就把同行密钥带出来 ⇒ 正确写法是 `{{.Name}}{{println}}…` + `grep -E '^…='` **行首锚定**。
3. **切换凭据前先证明新凭据可用**：`rabbitmqctl authenticate_user <user> <pw>`（**只读、不改状态**）⇒ 再去 recreate 服务 —— 否则会把服务改成"连不上中间件"。
4. **改服务器配置的标准姿势**：备份 → `read -rp`（或 `read -rsp` 静默输入）→ `sed` 写入 → `unset` → **只回显前 4 位**（操作手册 → [[运维手册--密钥密码轮换]] §六）。

**面试话术**
"我给自己定了一条规矩：**明文只要进了聊天、文档或提交，就当它已经泄露** —— 要么立刻轮换，要么写一份书面'接受'并写清影响范围，不允许'假装没发生'。还有两条更细的：① **取证命令本身不能制造泄漏** —— 我原来用 `docker inspect --format '{{.Config.Image}} | {{range .Config.Env}}…'` 取环境变量，它会把**镜像名和第一个变量粘在同一行**，`grep` 一打就把同行的密钥带出来了；正确写法是让每个变量单独成行、再用**行首锚定的 `grep -E '^KEY='`**。② **切凭据之前先证明新凭据能用**：用 `rabbitmqctl authenticate_user`（只读、不改任何状态）先验一次，再去重建服务 —— 否则很容易把服务改成连不上中间件。"

### B. 工具链与验收自身（4 条）

1. **`deploy/` 写在 `.gitignore:49` 里**（里面的关键文件是**遗留 tracked**）⇒ 往 `deploy/` **新增文件必须 `git add -f`**，否则"写了但没入库"。
2. **编辑工具可能抹掉 UTF-8 BOM**：含中文的 `.ps1` 在 PowerShell 5.1 下没有 BOM 会按 ANSI 解析（报"字符串缺少终止符"之类怪错）⇒ 改完 `.ps1` **复查头三字节**（`EF BB BF`）。
3. **管道会吞掉退出码**：`cmd | tail -3` 能让失败"看起来成功"（本项目部署脚本因此**静默跳过构建**）⇒ 关键命令别挂在管道末尾。
4. **验收命令自身要经得起推敲**：`grep -c 406` 会命中 Nacos 连接 id（`…b220ed2d4061_config-0`）这类**假匹配** ⇒ 要按整串 `channel error 406 PRECONDITION_FAILED` 判。

**面试话术**
"最后我还发现**工具链和验收动作自己也会说谎**。比如 `deploy/` 目录写进了 `.gitignore`，我新建的脚本没加 `-f` 就没进仓库 —— '我写了'和'它入库了'是两件事；又比如含中文的 `.ps1` 一旦丢了 BOM，在 PowerShell 5.1 下会按 ANSI 解析、报一堆莫名其妙的语法错，所以我改完脚本会顺手看一眼头三字节；还有 `cmd | tail -3` 这种写法会**把退出码吞掉**，让失败看起来成功（我们的部署脚本就这样静默跳过过一次构建）；最后连**验收命令本身**都得推敲 —— 我用 `grep -c 406` 查 MQ 的 `406 PRECONDITION_FAILED`，结果命中的是 Nacos 连接 id 里的 `…4061…`，所以现在改成按整串 `channel error 406 PRECONDITION_FAILED` 判。"
