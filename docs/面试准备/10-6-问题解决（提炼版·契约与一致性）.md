### Q15. #58+#32 契约漂移：生产依赖一个"已公告停用"的模型名（顺带挖出死参数/死配置/死代码）

> 来源：[[问题解决--LLM链路的契约漂移与分层降级]] §二 / §三 / §四 / §五 / §六

【追问1】你怎么确定生产**真的**在跑哪个模型名？（不是读文档，是钉"生效值"）
【追问2】停用日已经过了，为什么线上还一切正常？那你怎么判断它还能用多久？
【追问3】为什么最后**不改模型名**，而是改用官方的 `thinking` 开关？

【简答】生产 `csmall-ai` 的 chat 模型是 `deepseek-chat` —— 一个官方**已公告停用**的别名（公告 2026-07-24），但**兼容层还没撤，所以一切"正常"**。我是**解包生产容器的 `app.jar`** 才把生效值钉死的；实测又发现两个别名底层**已经是同一个 `deepseek-flash`**，真正的差异只在"思考模式开没开" → 于是改用官方的 `thinking` 开关（而不是继续换模型名）。改的过程中还挖出三类"设了但没用"的东西：**死参数 / 死配置 / 死代码**。

【深挖】
- **怎么钉"生效值"**：解包生产容器 `/app/app.jar` → `BOOT-INF/classes/application.yml` 第 26 行 `chat-model: deepseek-chat`；再确认 `application-prod.yml` **未定义 `cooxiao.ai` 段**（直接继承 jar 默认值）→ 才敢下结论；`git log` 定位 commit `c0d7209`（2026-09-08）从 `deepseek-v4-flash` 改过来。⭐ 判某配置的生效值**必须 yml + 代码默认值一起看**（日预算就栽过：`AiProperties` 写 10 元、yml `daily-budget: 2.0` 覆盖了它）。
- **为什么"停用"了还能跑**：兼容期没结束。用 `max_tokens=1` 的最小请求（只读、成本可忽略）实测 **5 个模型名全部 200**；响应里的 `model` 字段暴露真相 —— `deepseek-chat` / `deepseek-v4-flash` / `deepseek-reasoner` 返回的都是 `deepseek-flash`。⚠️ **`GET /models` 不是权威清单**（只列 `deepseek-flash` 与 `deepseek-v4-pro`，但别名都能调），据它判断会得出**反向结论**。
- **根因是"过度思考"**：`deepseek-v4-flash` 是 reasoning 模型，思考量**随 `max_tokens` 水涨船高**（实测 `=1000` 想满 1000、`=4000` 想满 4000）→ 思考吃满预算 → `content` 为空或被截断 → JSON 解析失败 → 降级。当年"按任务类型换模型名"**方向对、手段过时**（用换名字间接控制思考开关）。
- **实测出来的硬契约**：`tools` 与 `response_format` **互斥**；思考模式**不带回传 `reasoning_content` 直接 400**；`tools` 轮一律 `thinking: disabled`；每次改完对照"AI 模型路由"日志确认**路由恰好 1 次**（防双 bean/双调用）。
- **降级分层的核心分界**（六层：工具级 → 未写出内容就失败 → 已写出后失败 → 轮数用尽 → 预算超限 → 空答复）：**"是否已经写给用户"** —— 没写出去就**降级到旧流水线**，写出去了就**如实报错收尾、绝不降级**（"已经给用户的东西不能装没发生"）。所以流式路径**缓冲正文**、`products` 事件**早于第一个 `chunk`**（实测第 7 行 < 第 16 行）—— 这是降级能力的**前提**，不是优化。
- **死参数 / 死配置 / 死代码**：`temperature` 在思考模式下不生效（死参数）· `compare-model` 全仓 grep **零引用**（死配置，已删）· `DeepSeekAiClient.embed/embedBatch` **无任何注入点**，且它打的是 DeepSeek baseUrl + 硅基流动的 model + DeepSeek 的 apiKey（**三样对不上**）。#32 Agent 上线的 4 条坑**全是"不崩但不对"**：`sleep 45` 早于 44.7s 启动/注册 → 503；偶发 500（**客户端 18/18 全成功**却仍有 `AccessDenied` → 真病灶是 SSE 失败转 `/error` 时过滤器链又跑一遍）；回答正确但 `products: []`（首轮 `tool_choice=required` **只对商品意图**用）；库存张冠李戴（`get_stock` 的 observation 补 `spuName`）。

**面试话术**
"AI 这块我最想讲的不是功能，是**失败面**。第一层是**契约**：模型侧不掌握在我们手里，所以我把'模型名、`thinking` 开关、`tools` 与 `response_format` 互斥'这些都**实测**了一遍定成契约 —— 其中一条是生产当时依赖的 `deepseek-chat` **已被官方公告停用**（2026-07-24），只是兼容层还没撤，所以一切'正常'。我是**解包生产容器的 jar 配置**才把这个'生效值'钉死的，顺便发现 `deepseek-chat` 和 `deepseek-v4-flash` 底层其实是**同一个 `deepseek-flash`**，真正的差异只在'思考模式开没开'，所以正确做法是用官方的 `thinking` 开关，而不是继续换模型名。改的过程中还挖出三个'死的'东西：思考模式下的 `temperature` 是**死参数**、`compare-model` **零引用**、`DeepSeekAiClient.embed` **没有注入点**且三样配置对不上。第二层是**降级**：我做了六层，关键分界是'**是否已经写给用户**'—— 没写出去就降级到旧流水线，写出去了就**如实报错收尾、绝不降级**，因为已经给用户的东西不能装没发生；为此流式路径专门缓冲正文、把 `products` 事件排在第一个 `chunk` 之前。第三层是**把模型当不可信输入**：只给 3 个只读工具、参数在工具内收敛。上线后 4 个坑全都是'不崩但不对' —— 尤其是那个偶发 500，日志里一直有 `AccessDeniedException`，但我用**客户端成功率 18/18** 和 **ERROR 派发**把它定性成噪声，而不是跑去改鉴权。"

### Q16. #63+#64 代码与线上不一致的"静默失效"（ES mapping 不符 + 秒杀预热同字段两套语义）

> 来源：[[问题解决--代码与线上不一致的静默失效]] §二 / §三 / §五

【追问1】线上 mapping 和代码写的不一样，为什么**没人报障**？
【追问2】你怎么排除"IK 插件本身坏了"这个最坏情况（否则不敢删索引）？
【追问3】数据没问题、是查询打错字段形态 —— 这条结论你是怎么**证明**的？

【简答】线上 ES 索引的 mapping 与代码期望**完全不同**（IK 未生效、`keyword` 变 `text`、没有 `dense_vector`、`suggestField` 是 `text`）→ 品牌过滤**恒 0 命中**、补全接口**恒空**、向量检索**一开必废**。根因是初始化类 **`if (exists) return` 只创建、不校验 → 永不自愈**。我用三个**决定性实验**定的性，之后删索引重建，并跟一次召回回归。同类还有 `#64` 秒杀预热：**同一个 `spu_id` 字段有两种含义**，12 个 SKU 有 4 个从来没被预热过。

【深挖】
- **"静默"的三种形态**：① 查询打错字段形态 → **0 命中**（看着像"没有数据"）；② 补全接口**异常被 try-catch 吞掉** → 恒空；③ 类型不匹配 **只在开关打开后才炸**（当时 `embedding-enabled: false`，所以向量检索还没暴露）。
- **三个决定性实验**（缺一不可）：`_analyze` 对 `name` 出来 **4 个 `<IDEOGRAPHIC>` 单字** = standard 分词 ⇒ IK 未生效（**确定性**证据，重建不成功它骗不了人）；`term brandName`=**0** ／ `term brandName.keyword`=**4** ／ `match`=**4** ⇒ **数据没问题，是查询打错了字段形态**（最强证据形态）；`_cat/plugins` 显示 **`analysis-ik 8.6.0` 已加载** ⇒ 排除"IK 不可用"这个失败预案，**否则不敢动**。
- **根因 = 谁创建的 + 为什么不自愈**：`EsIndexInitializer` **只在索引不存在时才创建**，启动日志 `ES索引 [cool_shark_mall_ai] 已存在` 是铁证；线上 `settings`（`shards=1/replicas=0`）与代码一致但 **mapping 全空** ⇒ 是**历史上某次"带 settings 没带 mappings"的创建**（不是 ES 自动创建 —— 自动创建 `replicas` 会是 1），**具体版本未能查明**。
- **修复与验收**：停 `mall-ai` → `DELETE` 索引（`dense_vector` 的 `dims` 建成后**不可改**，只能删了重建）→ `up -d` 重建 + 全量同步 → 等日志 `Started MallAiWebApiApplication`；验收逐项对照：`dynamic=false`、分词回 `CN_WORD`、4 字段 `keyword`、`semanticVector` = `dense_vector dims=1024 cosine`、`suggestField=completion`、`term brandName="小米"`=**4**、`prefix=小米` → 返回「小米 14」。🔴 **我自己的错误**：验收命令 `grep -c ik_max_word` 期望 4 是错的 —— `grep -c` 数**行数**而 mapping 是**单行 JSON**，且实际出现 **5** 次（4 个 text 字段 + `suggestField`）⇒ 正确写法 `grep -o … | wc -l`。**验收命令本身也要被验收。**
- **修 A 会牵动 B**：`keyword` 化让 `multiMatch` 从"部分匹配"变"**整值精确匹配**" → 查询串"小米手机"可能不再命中 `keyword` 字段"小米" ⇒ **修复清单必须自带回归项**。实测未劣化：`小米手机` 8 · `小米` 4 · `手机` 7 · `华为` 3 · `笔记本` 5 · `旗舰` 3 —— 原因是 `semanticText` 里本身就写着「品牌：小米 | 分类：手机 | 标签：…」（权重 3）兜住了。
- **同类 #64：同一字段两种含义**：`seckill_sku.spu_id` **存的是 `seckill_spu.id`**（前端详情/限购按它查），而**预热 Job 用的是 pms 的 `spu_id`** → 现有 6 行里 **4 行错位**，4 个 SKU 靠凌晨 03:30 对账写的 `TTL=-1` **永久 key 偶然兜住**（所以"能下单"、没人报障）。硬约束：新增秒杀必须 **`seckill_spu.id == seckill_sku.spu_id == pms_spu.id` 三值相等**，⚠️ **不要用后台接口新增**（MyBatis-Plus 会给**雪花 id**）；**未修**，登记 `#64` 单独窗口处理。

**面试话术**
"我最怕的不是 500，是 **200 但是错的**。这两个案例本质都是'**代码期望**'和'**线上实际**'两个事实来源谁都不自动对齐：ES 那边，代码里写好了 `ik_max_word`、`keyword`、`dense_vector`，但线上这份索引是**更早的某个版本**建的、`mapping` 全空，而初始化类是 `if (exists) return`，所以**永不自愈**；表现就是品牌过滤恒 0 命中、补全恒空、向量检索一开就废 —— 但因为都有兜底路径，**功能看着是正常的**。我是靠三个**决定性实验**定的性：`_analyze` 出来 4 个单字说明 IK 没生效；`term brandName` 打 0 而 `term brandName.keyword` 打 4，说明**是查询打错了字段形态、数据没问题**；`_cat/plugins` 说明 IK 插件其实好好的，排除了最坏情况，我才敢删索引重建。修完还专门做了**召回回归**，因为 `keyword` 化会让部分匹配变成整值匹配。第二个案例更阴 —— 秒杀预热里同一个 `spu_id` 字段有**两套语义**，只在碰巧相等时才一致，12 个 SKU 有 4 个从来没预热过，全靠对账任务写的永久 key 偶然兜住，**这类问题的可怕之处就是'能下单'**。所以我的结论是：**这类'不报错、不自愈、只在特定路径暴露'的问题，必须靠定期核对机制去发现，不能等报错 —— 报错时通常已经是生产事故了**。"

### Q17. #57 实体 / 线上库 / 建表 DDL 三方漂移审计（"建表脚本不是事实来源"）

> 来源：[[问题解决--实体库表DDL三方漂移审计]] §一 / §二 / §三 / §四 / §五 / §六

【追问1】三方漂移你**没有动手改**，为什么？按报告 ALTER 不是更快吗？
【追问2】"实体里有字段、库里没有列"，为什么线上**不报错**？
【追问3】这种漂移**什么时候会炸**？炸出来是什么样子？

【简答】把 **Java 实体类 / 线上库 / 仓库建表 DDL 文件**三方放在一起对：**39 张表 × 32 个实体 × 34 个 SQL 文件**。核心发现不是某张表错了，而是**三方之间没有任何自动校验机制，所以漂移是必然的、发现是偶然的 —— 而且它不会报错**。差异归三类，我逐类建了台账：**实体有库没有**（靠自定义 Mapper XML 掩盖）、**表整体缺失**（4 张休眠表）、**DDL 文件/文档过期**（永久静默）。

【深挖】
- **三个事实来源各自是什么**：`mall-pojo` 实体类 = **代码期望**（读注解，`@TableField` 优先级高于字段名）；线上库 = **实际事实**（唯一真正跑的数据源，只读查 `information_schema`）；`database/*.sql` = **只是历史快照**，⚠️ **不是事实来源**（`seckill_message_retry` 就是反例：线上有、仓库没有）。⭐ 但**线上库也没有版本历史**（它是"当前状态的堆叠"）⇒ 结论必须落在"**DDL 文件补齐 + 固定核对周期**"，不能指望库自证。
- **为什么不报错**（本类最值钱的一句）：实体有库没有 → 本该 `Unknown column`，但**项目大量走自定义 Mapper XML**（手写 SQL 只 SELECT 真实存在的列）→ 多出来的字段根本不参与 SQL → 静默；表整体缺失 → 本该 `Table doesn't exist`，但对应功能**从未被调用** → 静默；DDL 文件过期 → 文件不参与运行时 → **永久静默**。⇒ **暴露条件不是"代码有 bug"，而是"路径被换掉了"**：一旦换成 MyBatis-Plus `BaseMapper`（`selectById`/`insert` 按实体全字段生成 SQL），漂移**当场变成 `Unknown column`**。
- **台账（类别级，含列级实例）**：`pms_sku_specification` 的 `attribute_name/attribute_value/unit/sort`、`pms_attribute` 的外键列 `template_id`（库是 `attribute_template_id`）、`pms_attribute_template_value`、`pms_picture`、`pms_album`、`ams_login_log` 的 `ip` vs 库 `ip_address`、`gmt_login` vs `login_time`。⚠️ **`@TableField` 会"掩盖"漂移** —— 实体字段名 ≠ 列名时，代码侧看起来是对的而库侧仍是错的 ⇒ **对比时必须用"注解后的真实列名"，否则差集算错**。
- **休眠表**：`ums_user_detail` / `ums_delivery_address` / `ums_reward_point_log` / `ums_change_password_log` 四张 —— **用到即 `Table doesn't exist`**；处置二选一（**补建表**启用功能 / **删实体**明确弃用），**不做决定本身就是风险**，会在某次"顺手用一下"时变成线上事故。
- **状态必须分两层记（别混为一谈）**：**本地库已全部修复**（2026-08-03 企业级升级时补的列：`pms_attribute_template` 补 3 列、4 张关联表补 `gmt_modified`、`pms_brand.sql` 更新为完整结构）；**服务器是否已执行同款 ALTER —— 未假设，登记 `#57`（P3）待只读核实**。⭐ **只读优先**：先查 `information_schema` 出差异表，**有差异才生成 ALTER** —— 因为审计报告是 **2026-08-04 的快照、不是线上现状**，直接按报告 ALTER 会撞 `Duplicate column name`。
- **2026-09-11 新增的两处（方向正好相反，两种极端都占了）**：① `cs_mall_seckill.seckill_message_retry` **生产存在（79 行）但 `database/` 里没有 DDL** —— 它是本地消息表（`MessageRetryTask` 每 5 秒轮询重发），说明是在线上"长"出来的 ⇒ **一旦环境重建这张表会凭空消失、重试机制静默失效**；② 生产 `ams_permission` **多出一列 `value`（全 NULL）而 DDL 没有** ⇒ 说明没有代码在写它，疑似历史残留，**删不删要先追根因，不能顺手 DROP**。两处都**只登记、不变更**（遵守"不夹带"纪律）。验收标准也不是"有没有报错"，而是**逐列差集为空**。

**面试话术**
"我做过一次**三方漂移审计**：把 **Java 实体类**、**线上库**、**仓库建表 DDL 文件**放在一起对 —— **39 张表 × 32 个实体 × 34 个 SQL 文件**。核心发现不是某张表错了，而是**这三方谁都不自动对齐，而且它不会报错**。实体侧我看注解后的真实列名（`@TableField` 会覆盖字段名），库侧查 `information_schema.COLUMNS`/`TABLES`，DDL 侧读文本，然后做**差集**，把差异归成三类：① **实体有、库没有**（`pms_sku_specification` 的 `attribute_name`/`unit`、`ams_login_log` 的 `ip` vs 库的 `ip_address`）→ 平时不报错是因为**全走自定义 Mapper XML**，手写 SQL 根本不带那些字段，**一换成 MyBatis-Plus `BaseMapper` 就 `Unknown column`**，这是**路径侥幸**；② **表整体缺失**（4 张 ums 休眠表）→ 用到即 `Table doesn't exist`，必须做"补建 or 删实体"的决策；③ **DDL 文件/文档过期**（`pms_brand.sql` 只有 8 列而真实库 17 列、`README` 目录树过期、`init-test-data.sql` 文案说 3 个测试用户实际插 10 个）→ **永久静默，只能靠人读**。我的三条结论是：**第一，建表脚本不是事实来源，线上库才是**；**第二，但线上库也没有版本历史**，它只是当前状态的堆叠，所以结论必须落在'**DDL 文件补齐 + 固定核对周期**'；**第三，这类问题跟 ES 那边的 `#63` 是同一类** —— 共同特征就是'**不报错、不自愈、只在特定路径暴露**'，所以**必须有定期核对机制，而不是靠报错发现**。落地节奏上我也很克制：本地已经修了，但**服务器是否执行过同款 ALTER 我没敢假设**，登记成 `#57`，做法是**先在 `information_schema` 上做只读核对、有差异才生成 ALTER**，低峰由用户执行、一次一处可独立回滚 —— 因为报告是 2026-08-04 的快照，**线上可能比报告更新，直接照报告 ALTER 会撞 `Duplicate column name`**。"
