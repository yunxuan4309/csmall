## 06-集群与高可用

### 一句话定义
集群 = 用**多个节点**协同工作，解决**单点故障**（HA）+ 
支撑**横向扩展**。核心三要素：多节点协同 + 数据同步 
+ 故障转移。

### Nacos 集群（注册中心 HA）
- **为什么**：单机 Nacos 是单点故障——挂则新服务注册不了、
  新消费者发现不了
- **怎么做**：≥3 节点 + Raft 选举（主挂自动切换）+ 
  注册数据节点间同步 + 客户端配多地址 
  failover + 独立 
  MySQL 持久化
- **项目现状**：单机 csmall-nacos，无 HA → 
  面试诚实边界："单机注册中心是学习项目短板，生产要 3 
  节点集群 + 
  MySQL 存储"

### ES 集群（搜索数据）
- **纠正误区**：ES 集群 **≠ 服务 IK 分词器**。IK（
  analysis-ik）只是 ES 的一个**插件**，
  负责中文分词，
  不是集群功能
- **ES 集群真正作用**：
  把索引**分片**分布到多节点——主/副本分片（高可用）、
  加节点扩容（
  水平扩展）、并行检索（性能）
- **项目实况**：单节点 ES（`number_of_nodes: 
  1`），**status yellow**——8 个副本分片 
  unassigned，因为副本必须放和主分片不同的节点，
  单节点放不了。
  加一个节点就 green。IK 8.6.0 已装 ✅
- **历史坑**："ES red"是容器重建时 **IK 插件丢了**（
  插件目录未持久化）导致索引映射问题——是"集群里插件丢了出问题"，
  不是"集群=服务插件"

### ES 健康状态三色（必背，别把 yellow 当故障）
| 颜色 | 含义 | 可读写？ | 危险度 |
|------|------|---------|--------|
| **green** | 主分片 + 副本**全部分配** | ✅ | 完全健康 |
| **yellow** | **主分片齐**、部分**副本**没分配 | ✅ | 无数据风险，**冗余度降低** |
| **red** | 部分**主分片**没分配 | ❌ 数据缺失 | **真危险**，必须处理 |

- **yellow 不是故障**：主分片都在 → 数据完整可读写；
  缺副本只是"没兜底"，主分片节点挂了该分片数据会临时丢。
  **单节点集群必然 yellow**（副本必须放不同节点，
  一个节点放不下）——正常现象
- **red 才危险**：主分片起不来 → 数据读不了。历史"ES 
  red"= 容器重建时 IK 插件丢导致索引映射失败，
  主分片无法加载
- **面试话术**："三色里 green 主副本齐、yellow 
  主齐副本缺（可读写但冗余降）、red 主分片缺失才危险。
  单节点必然 
  yellow，这是合理降级；red 才需要处理，我们那次 IK 
  插件丢失就是 red"

### 两个"集群"区别（面试重点）
| 维度 | Nacos 集群 | ES 集群 |
|------|-----------|---------|
| 管什么 | 服务元数据/配置（小但关键） | 搜索数据（大、分片） |
| 目的 | 服务发现高可用 | 数据高可用 + 扩展 + 检索性能 |
| 核心机制 | Raft 选举 + 数据同步 | 分片复制（主/副本）+ 路由 |
| 类比 | 总机交换机群 | 图书馆分书架 |

### 面试怎么讲
> "Nacos 和 ES 都是多节点做高可用，但管的东西不一样：
> Nacos 管服务地址和配置，数据小但丢了微服务就瘫，集群用 
> Raft 选举保注册中心可用；ES 管搜索数据，量大，
> 集群核心是分片复制和分布式检索。IK 分词器只是 ES 
> 的中文分词插件，不是集群功能——那次 ES red 就是容器重建时 
> IK 插件丢了。"

## 12-Kubernetes

### 一句话定义
K8s 是**容器编排平台**：管理多台服务器上的容器，
负责调度、自动扩缩容、自愈。

### 解决什么问题
单机 Docker Compose 只能管一台机器；多机部署时
需要"容器放哪台、挂了怎么办、流量大自动加实例"。

### 项目里的例子
❌ **没用**。项目是单机 Docker Compose（21 容器，
1 台 4C16G 服务器）。K8s 自身要吃 1~2G 内存 +
运维复杂度，演示场景是负担（2026-08-22 实测确认无
kubelet/etcd/6443 等任何 k8s 痕迹）。

### 面试怎么讲
> "单机规模用 Compose 足够，我为用而用引入 K8s 是
> 负收益；商业化多机部署时它才是演进方向——先有规模
> 再上编排，这是成本收益判断。"

### k3s vs 完全体 K8s（2026-09-07 补充）
> **k8s = Kubernetes 缩写（中间 8 字母）；k3s = Rancher(SUSE) 出的轻量发行版**——不是另一套系统,是同一个 Kubernetes 的"瘦身版",API 完全兼容,kubectl 命令一样。

| 维度 | 完全体 k8s | k3s |
|------|-----------|-----|
| 状态存储 | etcd（独立分布式存储） | **SQLite**（单节点默认）/可选 etcd |
| 安装 | kubeadm 复杂（证书/多组件） | 一个二进制 `curl|sh` |
| 资源 | 控制平面 ~1.5-2G+ | ~500MB-1G |
| 网络/LB/Ingress | 需配 CNI/MetalLB/nginx-ingress | 内置 Flannel/ServiceLB/Traefik |
| 适用 | 生产大型集群 | 边缘/IoT/单机/学习/资源受限 |

**关键认知**：
- k3s 把 etcd → SQLite、网络/LB/Ingress 内置 = **一台机器跑起完整 k8s API**（还是真 Kubernetes）
- **为什么 k8s 重 = etcd**：集群状态全存 etcd，**3/5 节点多数派才高可用** → 2 台机器做不了高可用控制平面（这就是为什么单机实验用 k3s、企业上云托管）
- 面试定位："我在两台机器上用 k3s 验证了跨节点调度/自愈机制，清楚边界：单节点 SQLite 控制平面是单点，真高可用要 3 节点 etcd 或直接上云托管"

### 托管 k8s = k8s 的"RDS 形态"（企业真实用法）
> **和 RDS 之于 MySQL 完全同类的产品逻辑**：云厂商把最难运维的"大脑"变成开箱即用商品。

```
自己装 MySQL → 管安装/备份/主从/HA      自己装 k8s → 管 etcd/证书/升级/HA
RDS = 阿里云管 MySQL，你只连库          ACK = 阿里云管 k8s 控制平面，你只管部署应用
```

- **企业主流形态 = 云托管 k8s**：阿里云 ACK / AWS EKS / 腾讯 TKE——控制平面(etcd/API Server)云厂商管,公司只管工作节点 + 写 YAML 部署
- 大厂日常 = 写 Deployment/Service manifest + `kubectl`,**几乎不碰 k8s 安装**
- 类比："自己装 k8s = 养大象(喂 etcd/驯 API Server);托管 k8s = 动物园养,你骑上去指挥"

### compose 文件 vs k8s manifest（"给业务上编排"= 声明式 YAML）
> 你的直觉对：k8s 部署应用写的就是**类似 docker-compose.yml 的声明式文件**（叫 manifest），只是拆成 Deployment/Service 等概念 + 加了"调度/自愈/扩缩容"大脑。

| docker-compose.yml（你熟） | k8s manifest | 关系 |
|--------------------------|-------------|------|
| `services:` 定义服务 | `Deployment`（应用+副本数） | 最像 |
| `image: xxx` | `image: xxx` | 一样 |
| `ports:` | `Service`（暴露）+ `Ingress`（对外） | compose 简化了,k8s 拆开 |
| `restart: on-failure` | Deployment 自带（挂了自动拉起） | k8s 内置自愈 |
| 一行扩两个实例？ | `replicas: 2` | **compose 做不到,k8s 一行多实例** |

**秒杀 Deployment 示例**（理解"编排长什么样"）：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mall-seckill
spec:
  replicas: 2            # ← 多实例!compose 没有这个能力
  selector:
    matchLabels:
      app: mall-seckill
  template:
    metadata:
      labels:
        app: mall-seckill
    spec:
      containers:
      - name: mall-seckill
        image: mall-seckill:1.2.3
        ports:
        - containerPort: 10007
---
apiVersion: v1
kind: Service            # ← 给上面 2 个副本做负载均衡入口
metadata:
  name: mall-seckill-svc
spec:
  selector:
    app: mall-seckill
  ports:
  - port: 10007
```

**一句话**：compose = "**这台机器**上跑这些容器"；k8s manifest = "**整个集群**要这些 Pod，调度器决定放哪台、挂了自动补、多了自动扩"。同样的声明思想，k8s 多了"调度/自愈/扩缩容"这层大脑。

### 演进路径（你该站哪）
```
docker run → docker-compose(单机,你现在) ✅ → k3s(轻量验证集群机制) → 托管 k8s ACK/EKS(企业形态)
```

## 13-ZooKeeper

### 一句话定义
ZK 是**分布式协调服务**（注册中心/分布式锁/配置），
旧版 Dubbo（2.x）的经典注册中心。

### 解决什么问题
服务发现：提供者注册地址，消费者查地址再调用。

### 项目里的例子
❌ **没用**。注册中心用 **Nacos**（Dubbo 3.x 原生支持）——
注册（AP）+ 配置（CP）+ 控制台三合一（2026-08-22 实测：
无 ZK 容器、无 2181 端口；仅 fat jar 里有 Dubbo 内置的
zk 依赖类，未启用）。

### 为什么用 Nacos 不用 ZK（必考）
| 维度 | Nacos | ZooKeeper |
|------|-------|-----------|
| 生态 | Spring Cloud Alibaba 全家桶 | 需自己集成 |
| 功能 | 注册 + 配置 + 控制台 | 仅协调，配置另搭 |
| 一致性 | 注册 AP（可用性优先） | CP（强一致，注册场景易抖动） |

### 面试怎么讲
> "用 Nacos 是体系选择——Spring Cloud Alibaba 生态 +
> 注册配置二合一 + 自带控制台；ZK 是旧 Dubbo 时代的方案，
> 功能单一，CP 模型在服务发现场景不如 AP 抗抖动。"

## 19-Docker 容器原理（镜像层 / 可写层 / 生命周期）

### 一句话定义
容器 = **镜像层（只读模板）+ 可写层（容器私有，重建即销毁）**

### 镜像层（干嘛的）
- 只读内容层：temurin-jre 层 + mall-seckill.jar 层（每层 = Dockerfile 一行）
- 三作用：① 自包含（任何机器拉起 = 环境+程序都齐）② 分层缓存（改 jar 只重建 jar 层，基础层秒出）③ 只读安全
- 类比：预制菜包（食材+调料+做法封好）

### 可写层（干嘛的）
- 容器运行时专属草稿区：进程写入、exec 装的东西都在这；**容器重建即销毁**
- 秒杀例子：无状态服务（数据全在 Redis/MySQL）→ 可写层基本空着 → **容器随便重建不丢**；有状态组件（MySQL/Redis/ES）才必须挂卷
- ⚠️ Q1 教训：ES 的 IK 用 docker exec 装在可写层 → 重建丢 → 必须"挂载"或"写进镜像"

### 为什么 COPY JAR 进镜像，不直接跑 jar？
- 镜像 = 环境+程序+启动命令（JVM 参数/SW agent 全固化）打包的**确定性发布单元**：可版本化、可回滚、可分发、哪都一致
- 直接跑 jar = 目标机要装 JRE、手动拼 java 命令、参数易漏、无版本化（"我这能跑你那不能跑"）
- 类比：COPY jar = 预制菜包拆开即食；只传 jar = 只给食材，别人还得有锅有火

### 面试怎么讲
> "容器 = 镜像只读层（JRE+jar，共享/缓存/安全）+ 可写层（私有，重建即毁）。秒杀是无状态服务，业务数据全在 Redis/MySQL，可写层基本空着，所以容器随便重建不丢；ES 那次 IK 丢失就是 docker exec 装在可写层，重建就没了，所以要么挂载要么 COPY 进镜像。COPY jar 进镜像是因为它把环境+程序+启动命令打包成确定性发布单元——可版本化回滚，直接传 jar 环境靠猜。"

## 20-Spring Boot 配置优先级（命令行/JVM 属性 > 环境变量 > yml）

### 一句话定义
同一个 key 有多个来源时，**优先级高的覆盖低的**——改配置不生效先想"有没有更高优先级来源盖住了"

### 优先级顺序（高 → 低，记住前三档就够）
```
① 命令行参数:java -jar app.jar --server.port=8080
② JVM 系统属性:-Dserver.port=8080        ← 镜像 ENTRYPOINT 常在这写死
③ OS 环境变量:SERVER_PORT=8080           ← compose environment 注入的就是这个
④ application-{profile}.yml(prod 等)
⑤ application.yml
⑥ 更低:默认值/随机端口
```

### Q3 案例（Sentinel 8858 为什么改不掉）
```
bladex/sentinel-dashboard 镜像 ENTRYPOINT 硬编码:
  ["java", "-Dserver.port=8858", ...]     ← ② JVM 系统属性,高优先级!
compose 之前映射 8080、想用环境变量改 → 盖不过 -D
→ 只能改端口映射(8090:8858)或改镜像,不能靠 environment 覆盖
8858 来源:Sentinel Dashboard 在 SCA 生态的惯例端口(镜像 build 时固化,
进程实测 java -Dserver.port=8858 实证)
```

### 面试怎么讲
> "Spring Boot 配置有优先级：命令行/JVM 系统属性最高，其次是 OS 环境变量(compose 注入的就是)，再是 yml。Sentinel Dashboard 那次就是镜像 ENTRYPOINT 用 -Dserver.port=8858(JVM 属性)写死，比 compose 的 environment 优先级高——所以映射 8080 是空的打不开，只能改映射或改镜像。教训：改配置不生效，先查有没有更高优先级的来源把它盖住了。"

### 约定大于配置（延伸理解）
- 精神 = **系统内默认一致、少配置**，不是"必须追平框架出厂默认值"
- 案例判断：Sentinel 端口不改回 8080——8080 是 Spring Boot 通用默认，8858 是 SCA 生态里 Dashboard 的部署约定（镜像固化、全系统消费方对齐）= 这套系统自己的约定；compose 端口映射已把对外端口解耦，改容器内端口零收益
- **什么时候才改**：① 出现真实问题（端口冲突/安全/公司规范）② 换官方镜像/组件（默认变了，顺带统一）③ 团队统一规范
- 面试一句话："约定大于配置 = 少配置 + 系统内一致，不是追框架默认值——只要一套系统里大家都按同一个约定走且没真实问题，就别为'看起来像默认'做无收益的全链路改动"
