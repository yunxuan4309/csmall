### Q1. 为什么用 Nacos 做注册中心，不用 Eureka/Zookeeper？🔴
**追问1**：AP 和 CP 模式是什么意思？
**追问2**：注册和配置两个功能各有什么用，举个例子？
**追问3**：项目里 Nacos 实际承载了什么？（服务器实测）
**追问4**：配置都在 .env 里，配置中心是不是被放弃了？
**追问5**：Dubbo 接口暴露会不会有安全问题？Nacos 泄露了怎么办？
【简答】Nacos 是阿里开源，集**注册中心 + 配置中心**于一体，Spring Cloud Alibaba 生态标配。相比 Eureka（只做注册，已停更）、Zookeeper（CP 模型，不适合注册），Nacos 功能全、支持 AP/CP 切换、国内文档多。
【深挖】
- **vs Eureka**：已停更且只做注册；Nacos 还做配置中心，一个顶俩
- **vs Zookeeper**：ZK 是 CP，分区时宁可不可用；Nacos 默认 AP 更适合服务发现
- **CAP**：服务发现要 AP（可用性优先），Nacos 支持 AP/CP 切换
- 话术："选 Nacos 因为它**一个顶俩**（注册+配置），且是 Spring Cloud Alibaba 标配"
【追问1】AP 和 CP 模式是什么意思？① CAP 定理：网络分区 P 时，一致性 C 和可用性 A 只能二选一
- **CP**（ZK）：宁可系统不可用也要数据一致 → 像电话会议投票，有人掉线会就开不成
- **AP**（Nacos 默认）：宁可数据暂时不一致也要可用 → 像旧号码本，断了也能先打打看② 网络分区 P 是什么意思？（面试高频澄清点）
- **不是 Nacos 不可用**！是**节点之间网络断了，节点本身还活着**
- 例：机房 A（Nacos-1, mall-product）与机房 B（Nacos-2, mall-order）  之间的光缆被挖断 → 两边都活着但互相联系不上 → 被切成两个"孤岛"= 分区
- P 不是"选不选"的问题，是**必然发生**的前提（网络总会断），  所以实际选择只有 CP 或 AP
- 澄清：整个 Nacos 全挂 = "全挂"不是分区（没得选，直接不可用）；  3 节点挂 1 个 = 单点故障不是分区（多数派还能工作）③ 为什么服务发现必须 AP（核心考点）
- 拿到**过期地址** = 调用失败重试一次，可接受
- 注册中心**整体不可用** = 所有服务互相找不到 = 全站瘫痪
- → "弱一致性可接受、不可用不可接受" → AP；ZK 分区时选举阻塞拒绝服务 → 不适合④ AP/CP 切换：临时实例（ephemeral=true，默认）= AP 心跳剔除；  持久实例（ephemeral=false）= CP（Raft，类似 ZK）→ 项目用默认 AP
【追问2】注册中心和配置中心各有什么用，举个例子？① 注册中心 = 服务的"通讯录"
- 启动 → 登记"我叫 mall-product，在 172.18.0.5:9010"；调用方 → 按服务名查地址
- 扩容 3 实例 → 自动登记 3 个地址 → 自动负载均衡；挂了 → 心跳超时自动剔除
- 项目例子：Gateway 路由 `lb://mall-front` 靠 Nacos 解析地址② Dubbo 接口注册 = "按接口名找提供者"（服务间 RPC 用）
- 例：mall-front 要商品数据 → 不关心 mall-product 在哪台机器，  只订阅接口 `providers:com.cooxiao.mall.product.service.front.IForFrontSpuService::`  → Nacos 返回该接口下【所有实例地址】→ Dubbo 客户端长连接 + 负载均衡调用
- 四大作用：接口解耦应用（消费者只认接口不认应用名）/  多实例负载均衡（接口下多个地址自动分流）/  故障剔除（实例挂 → 该实例接口地址被移除）/  版本隔离（接口名带版本号，新旧共存灰度）
- 对比：应用级注册（Spring Cloud）= 按应用名找服务（Gateway 路由用）；  接口级注册（Dubbo）= 按接口名找提供者（服务间 RPC 用）——同一通讯录两种词条
- 补充：**Nacos 2.x 客户端通信走 gRPC**（HTTP/2 + Protobuf 长连接，  服务端主动推送；容器线程 grpc-nio-worker 实证；1.x 是 HTTP 长轮询）  ——Dubbo 管服务间 RPC、gRPC 管 Nacos 通信，各管各的（详见基础知识速记 17）
- **接口暴露全景表（代码实证 @DubboService/@DubboReference）**：  暴露方 4 模块 10 接口，按"数据归谁管"设计——  product(7)：IForFront
* 给 front、IForSeckill
* 给 seckill、IForOrderSku 给 order  order(1)：IOmsOrderService 给 seckill（秒杀创建订单）  ums(1)：IUserService 给 sso（登录验证）  ai(1)：ISpuSyncService 给 product（商品变更同步 ES）  消费者：front/seckill/order/search/ai/product 等按需引用
- 通信三方式：Dubbo RPC（必须暴露 @DubboService）/  HTTP 经 Gateway（不用暴露，路由即可）/ MQ（不用暴露，发队列解耦）  → 按需开洞，保持服务边界清晰③ 配置中心 = 配置的"中央管理台"
- 集中管理改一处全局生效 + 热更新（@RefreshScope 不用重启）+ 多环境隔离（dev/test/prod）
- 项目实际情况：业务配置还在本地 yml + 环境变量，见追问3/4④ 一个顶俩 → 少运维一个中间件（选 Nacos 的理由之一）
【追问3】项目里 Nacos 实际承载了什么？（服务器实测 2026-08）① 注册中心：23 个服务名（13 应用服务 + 10 个 Dubbo Provider `providers:com.cooxiao.mall.*`）② 配置中心：只有 1 条配置 = `mall-seckill-flow-rules`（group=SENTINEL_GROUP）
- 其余业务配置全在本地 yml + compose 环境变量；gateway 配了 config 但 Nacos 没有  gateway-server.yml → 实际没拉到配置③ 限流规则（Sentinel）
- flow 规则（生效）：秒杀订单提交，QPS=10，快速失败直接拒绝  → 双重保险：代码硬编码（SentinelFlowRuleConfig）+ Nacos 规则，两份 QPS=10 一致
- **为什么重启后规则会失效？**（面试高频）  → Sentinel 规则默认存在**内存**（FlowRuleManager.loadRules 加载的），    控制台配的规则是推到服务内存 → **重启 = 内存清空 = 规则丢失**  → 三种持久化来源对比：内存（默认，重启丢）/ Nacos（启动拉取，重启不丢）/    代码硬编码（@PostConstruct 每次启动重新加载，重启不丢）  → 本项目 flow 规则走 Nacos + 硬编码双持久化 → 重启不丢；    degrade 规则 Nacos 无配置 → 重启后拉取空 = 等于失效
- **degrade 规则（熔断，没生效）**：dataId 配了 `mall-seckill-degrade-rules`，  但 Nacos 里不存在 → 订阅返回空 → 0 条规则空转（日志证实已 subscribe 但无配置）  → 教训：**Sentinel 数据源配置 ≠ 规则本身**，配了 dataSource 没建规则 = 空转  → 建议补：异常比例 50% + minRequestAmount 5 + 熔断 10s（grade=1），    别用 RT 慢调用（秒杀排队 RT 天然高会误熔断）
- 注：SeckillFallback（异常兜底）一直生效，不依赖 degrade 规则；  缺的是"熔断"——下游异常比例高时快速失败保护线程④ 话术（诚实版）：配置中心用得轻，主要持久化 Sentinel 规则保证重启不丢；  降级规则当时只配了数据源没建配置，实际没生效——这个坑让我明白  "数据源配置≠规则"，后来补了异常比例 50% 熔断 10s 的规则 → 主动暴露+已解决加分
【追问4】配置都在 .env 里，Nacos 配置中心是不是被放弃了？① 三层配置体系（实测）：yml 默认值 → compose environment 覆盖（★主力）→ .env 敏感值（不进 git）
- 宽松绑定：SPRING_DATASOURCE_URL 自动映射 spring.datasource.url
- 注入示例：ALIYUN_SERVER_IP=nacos（注册中心地址）、SPRING_DATA_REDIS_HOST=redis、  SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/xxx、SPRING_RABBITMQ_HOST=rabbitmq、  SPRING_ELASTICSEARCH_URIS=http://elasticsearch:9200、SEATA_SERVICE_GROUPLIST_DEFAULT=seata:8091、  JWT_SECRET、AI_API_KEY② 为什么单机够用（不是放弃，是场景匹配）
- 配置中心核心痛点 = **多实例同步 + 动态热更新 + 多环境隔离**
- 单机部署、每服务 1 实例、只有 prod → 改 .env + 重启几分钟搞定 → 不需要配置中心
- 所以配置中心只存"重启后会丢的"（Sentinel 规则），其余走环境变量 = 合理取舍③ 什么时候必须用配置中心（企业级生产环境）
- 多实例：同一服务 ≥2 实例，改配置不能逐个改逐个重启
- 动态变更：限流阈值、开关、灰度比例要不停机热更新（@RefreshScope 秒级生效）
- 多环境：dev/test/prod 用 namespace/group 隔离，切换只改一个 profile④ 敏感值为什么不进 Nacos（2026-08-28 补充）
- 两条理由：① Nacos 当前**无认证**（实测无 token 读配置 200）——  存了 = 网络可达就能读；.env 在服务器文件系统，泄露面小得多  ② Nacos 本身是攻击面（历史出过认证绕过 RCE）——注册中心  沦陷 = 全部配置泄露
- **企业三级分离**：非敏感配置 → 配置中心；敏感配置（密码/  密钥/API Key）→ **密钥管理服务（KMS/Vault/Secrets Manager，  有审计 + 自动轮换）**；密码明文 → 永远不出现
- 核心：**配置中心管配置、密钥管理管机密，两码事**——即使  Nacos 开认证（TODO #13），密码也不放配置中心
- 你的取舍：.env 存敏感值（比无认证 Nacos 安全 ✅）；集群化  升级（TODO #4）时非敏感进 Nacos、敏感留 .env 或引 KMS
- 审计安全：谁改了什么可追溯，敏感配置可加密存储
- 标准做法：能进配置中心的都进，环境变量只留引导配置（如 Nacos 地址本身）④ 话术：单机用 .env + 重启成本可接受，是场景匹配的取舍不是配置中心没用；  扩到 3 实例改数据库密码不可能逐个登录改，Nacos 改一次全部实例自动生效；  规模上来第一件事就是把配置迁到 Nacos，环境变量只留引导配置
【追问5】Dubbo 接口暴露会不会有安全问题？Nacos 泄露了怎么办？① Nacos 泄露 ≠ 直接打穿业务，按危害分三层：
- 侦察层：拿到内网 ip:port 拓扑（"藏宝图"），但连不上端口就打不进来
- **服务伪装（最危险）**：攻击者在 Nacos 注册假 provider →  消费者从注册中心拿到假地址 → 请求打到攻击者 → 数据被截获  （不一定要打进内网，只要让消费者连上你）
- 配置投毒：改 Sentinel 规则（限流失效）/ 改业务配置（数据源指向攻击者）② 我们项目实际暴露面（2026-08-26 实测）：
- Nacos 8848 映射 0.0.0.0，但阿里云安全组只开 22/80 → 公网打不进来 ✅
- **Nacos 认证未开启**（无 token 直接读配置返回 200）→ 内网任意主机可操作 ⚠️
- Dubbo 端口 port=-1 随机 + 容器内网，不映射公网 → 公网无法直达 ✅
- 配置中心只存 Sentinel 规则（无密码）→ 投毒影响有限
- 结论：公网进不来；薄弱点是"内网信任模型"（内网容器被攻破后可无认证操作 Nacos）③ 企业级加固方案（按优先级）：
- Nacos 开认证：NACOS_AUTH_ENABLE=true + 强 token + 用户权限 + 命名空间隔离
- Nacos 端口不暴露公网：映射 127.0.0.1:8848 或仅内网
- Dubbo token：provider 校验 token，防止未授权调用
- 网络最小化：安全组白名单 + compose 网络隔离④ 话术："注册中心要当数据库一样保护——认证 + 网络隔离 + 最小权限。  最危险的是服务伪装：攻击者注册假服务，消费者就把请求打到攻击者机器。  生产环境 Nacos 必须开认证，我的项目因为安全组只开 22/80、  Dubbo 端口不暴露公网，所以公网进不来；但内网无认证是待加固项，  生产化第一件事就是开 NACOS_AUTH_ENABLE。"

### Q2. 为什么用 RabbitMQ，不用 Kafka/RocketMQ？🔴
**追问1**：秒杀场景需要什么消息特性？
**追问2**：Kafka 适合什么场景？
**追问3**：三种 MQ 的底层区别是什么？市面上还有哪些 MQ？
**追问4**：你的项目具体怎么用 MQ 的？（防"抄的"质疑）
**追问5**：Dubbo 通信用什么序列化？不用 JSON 吗？
**追问6**：Kafka 只能做日志吗？能不能用于业务场景？
**追问7**：MQ 超时重投会不会重复消费？死信能解决吗？
**追问8**：AMQP 标准和 Kafka 私有协议的区别？
**追问9**：为什么 seckill_queue 非持久、order_queue 持久？
【简答】秒杀是**削峰**场景，RabbitMQ 功能完整、易用、支持消息确认。Kafka 追求吞吐量（日志/大数据），对消息语义和生态更适合流处理；RocketMQ 也是阿里系但配置更重。
【深挖】
- **RabbitMQ 优势**：功能完善（交换机/队列/确认/死信）、  AMQP 标准、易运维、吞吐量对秒杀足够（几千/秒）
- **Kafka 优势**：百万级吞吐、分区、持久化，  但**适合日志/流处理**，不适合强业务消息
- **秒杀场景**：10 并发只产生 ~10 个成功订单，  RabbitMQ 吞吐完全够；重要的是**可靠性**（确认机制）
- **"易运维"具体体现（4 层，防"只会说空话"）**：  ① 部署简单：单组件 docker 一条命令；Kafka 曾要 ZK、     RocketMQ 要 NameServer+Broker 多角色  ② 自带 Web 管理台 15672：队列积压(ready/unacked)、消费者状态、     消息内容全部可视化，出问题一眼定位；Kafka 无官方 UI 要装     Kafdrop/CMAK 等第三方  ③ 排查链路短：无 Kafka 分区再平衡(rebalance)那种经典疑难     （消费者增减/broker 抖动触发、期间消费暂停、可致 rebalance 风暴）  ④ 内存/磁盘水位自管理：快满自动阻塞生产者防 OOM，不用盯 JMX  
- 项目实证：RabbitMQ 健康检查超时（timeout 5s→10s）就是    控制台+日志定位修复的 → "运维过才敢说易运维"
- **面试话术**：  "选型看场景——秒杀要的是**可靠的消息投递**不是**超大的吞吐**  ，RabbitMQ 足够且好用；Kafka 是留给日志流处理的"
【追问1】秒杀场景需要什么消息特性？
- **可靠性 
> 吞吐量**：秒杀成功订单少（QPS=10 限流后 ~10/秒），  吞吐几千/秒的 RabbitMQ 绰绰有余；真正要命的是"消息不能丢"  （丢一条 = 用户秒杀成功但订单没落库）
- 需要：消息确认（ack/nack）、持久化、消费失败重试
- 不需要：百万吞吐、海量分区、流式处理
【追问2】Kafka 适合什么场景？
- **日志/埋点采集**：海量写入、允许延迟、按偏移量回溯
- **流处理**：Kafka Streams / Flink 实时计算（订单金额聚合、风控）
- **事件溯源**：消息不删、可重放，重建状态
- 不适合：强业务消息（无事务/无死信/消费即删语义弱）、  需要灵活路由（只有主题，没有交换机路由键那套）
【追问3】三种 MQ 的底层区别 + 市面上还有哪些？
- **模型差异（底层根因）**：  RabbitMQ = 队列 + 推模式（消费即删，功能全，AMQP 标准）  Kafka = 分区日志 + 拉模式（append-only 顺序写盘，消息不删按偏移量保留，          消费者组各自偏移量可重放 → 百万吞吐的根源）  RocketMQ = 借 Kafka 分区存储 + 加事务消息/延迟消息（吞吐+功能都要）
- **记忆**：RabbitMQ=万能胶 / Kafka=日志流 / RocketMQ=既要又要
- **其他 MQ**：Pulsar（存算分离云原生）、ZeroMQ（嵌入式无 broker）、  ActiveMQ（JMS 老牌）、Redis Pub/Sub（不算 MQ，无持久化丢了就没）
- 加分点："我知道 Redis Pub/Sub 的局限，所以用 RabbitMQ 而不是 Redis 做队列"
【追问4】项目具体怎么用 MQ？（代码实证，防"抄的"质疑）① 全景：2 个队列都是 Direct 交换机 + 手动确认
- 秒杀队列（seckill_queue）：秒杀下单异步落库——  Redis 预扣库存成功后发 MQ → 消费者写 success 表 + 扣 DB 库存
- 订单队列（order_queue，durable=true）：普通订单异步扣库存——  Dubbo IForOrderSkuService.reduceStockNum 逐项扣② 三个不是"抄来的"设计细节：
- 手动 ack/nack（application-prod.yml: acknowledge-mode: manual）：  成功才 ack，失败 nack requeue 重回队列 → 消息不丢
- 本地重试表兜底（seckill_message_retry + MessageRetryTask 每5s轮询 ×3）：  先写表再发 MQ，MQ 挂了消息不丢 → 自研"低配可靠投递"
- JSON 序列化（非 Java 序列化）：跨服务版本升级字段变更不炸，  SeckillQueueConsumer 兼容旧消息（id null 时雪花生成）③ 项目为什么用 RabbitMQ 而不换 Kafka（量级分析）：
- 消息量：QPS=10 限流 → ~10 成功订单/秒，  RabbitMQ 几千/秒完全够，换 Kafka 是引入复杂度没有收益
- 需求：可靠投递（不能丢订单）
> 吞吐 → ack/nack + 重试表更契合
- 结论：量级没到，不引入 Kafka 的幂等/死信自建复杂度④ 话术：见上方"防抄"完整版
【追问5】Dubbo 通信用什么序列化？不用 JSON 吗？
- 项目实测：`dubbo.protocol.name: dubbo`，未配 serialization →  用 Dubbo 默认 **Hessian2 二进制序列化**（yml 里 log-serialization:  jackson/kryo 是 Seata undo_log 的，跟 Dubbo 无关，别搞混）
- 三种序列化对比：  Hessian2 = 二进制，体积小 ~50%，快，跨语言部分支持 → RPC 用  JSON = 文本带字段名，体积大，全语言可读 → MQ/HTTP 用  Kryo = 二进制最小最快，仅 Java → 可选
- 为什么 Dubbo 不用 JSON：RPC 调用频率极高（每次秒杀下单调  order、front 每次查询调 product），性能敏感；  同是 Java 服务不需要可读性，出错有 SkyWalking 定位
- 一句话：**能读给机器看的（RPC）用二进制求快，  能读给人看的（MQ 排查/HTTP 给前端）用 JSON 求可读**
【追问6】Kafka 只能做日志吗？能不能用于业务场景？
- **能**，Kafka 是"日志场景最强"，不是"只能做日志"；  大厂业务消息大量用 Kafka（美团自研基于 Kafka、字节 BMQ  兼容 Kafka 协议、阿里日志管道 Kafka + 核心交易 RocketMQ 分场景）
- Kafka 做业务的"能/不能"：  能：分区内有序、at-least-once、可重放、事件流  难：恰好一次要业务幂等配合；无内置延迟/死信；复杂路由做不到
- 适合 Kafka 的业务：订单事件流、库存变更事件、风控规则触发、  用户行为分析——"事件"可重复消费、可重放、允许延迟
- 不适合：必须精确一次的核心交易指令、要死信/延迟的强业务
- 面试话术："Kafka 做业务完全可行，但要清楚代价：至少一次语义  要业务幂等配合，没有内置死信和延迟消息。我的秒杀每秒只有 10 个  成功订单，要的是可靠投递，RabbitMQ 确认机制更契合；量级到百万  我会把订单事件迁 Kafka 同时把消费端做成幂等。"
【追问7】MQ 超时重投会不会重复消费？死信能解决吗？
- **会**，这是 MQ 的"至少一次投递"语义（at-least-once）——  消费者处理完正准备 ack，进程被杀/网络断/ack 丢失 →  RabbitMQ 没收到 ack → 重投 → 重复消费。所有 MQ 都这样，是设计不是 bug
- 死信解决不了：死信管"失败消息去哪"，重复消费只能靠【消费端幂等】
- 项目防线（代码实证）：  ① 扣库存"条件更新"天然幂等：SQL `stock >= #{quantity}`，     重复消费第二次 rows=0 → 直接 ack 跳过 → 不会超卖  ② success 表 `UNIQUE KEY uk_sku_user`（但消息级幂等最好加 orderSn 唯一）  ③ 未来非幂等业务（发短信/转账）必须加业务幂等键
- 话术："MQ 至少一次投递，重复消费必然存在，我靠条件更新防超卖；  死信解决不了重复消费，只能消费端幂等"
【追问8】AMQP 标准和 Kafka 私有协议的区别？
- AMQP = 消息队列行业标准（Advanced Message Queuing Protocol）  RabbitMQ 实现 AMQP → 任何语言按 AMQP 写的客户端都能连，  换厂商实现不改代码
- Kafka = 自有私有协议 → 客户端必须用官方库，协议不对外开放  （这也是 Kafka 生态虽大但"绑定"更深的原因）
【追问9】为什么 seckill_queue 非持久、order_queue 持久？
- 代码差异：`new Queue(name)` = 非持久 vs `new Queue(name, true)` = 持久  （durable 含义：RabbitMQ 重启后队列定义+消息是否还在）
- 设计逻辑：秒杀队列有【本地重试表兜底】（丢了能从表补发）→ 非持久可接受；  订单队列【无兜底】（convertAndSend 直接发，丢了真丢）→ 必须 durable  （订单已落库、库存必须扣，丢消息 = 用户下单但库存没减 ❗）
- 诚实点：严格讲两队列都该持久化（重试表只兜 MQ 不可用，不兜重启丢消息），  秒杀非持久是复盘发现的不一致，生产化统一改 durable=true

【深挖】

- **你的项目**：商品搜索用 ES（  `cool_shark_mall_index2`），IK 分词，  商品变更经 Dubbo 自动同步 ES
- **面试话术**："LIKE 是'从头翻一遍找包含关键字的'，ES   是'先建好词到文档的索引，直接定位'——这是倒排索引的本质"
【追问1】ES 是什么？和 MySQL LIKE 性能本质区别？
- ES = 基于 Lucene 的分布式全文检索引擎：  全文检索(倒排索引)/相关度排序(BM25)/中文分词(IK)/聚合分析/分布式分片副本
- 本质区别（不是"ES 快 MySQL 慢"，是查询方式不同）：  MySQL `LIKE '%华为%'` = 全表扫描，且前导通配符 % 让 B+Tree 索引失效，  无相关度、不支持中文分词  ES 搜"华为" = 建索引时分词成词项，查倒排表直接定位，O(logN)，  BM25 相关度排序，IK 中文分词
- 一句话："LIKE 是全表翻，ES 是查字典"
【追问2】IK 分词器是什么？怎么配合 ES？
- 为什么需要：中文没有空格，ES 自带英文分词器（按空格切）切不了中文，  必须用中文分词器 → IK 是 ES 插件（非内置）
- 两种模式：`ik_max_word` = 细粒度穷尽切分（召回率高，商品搜索用这个）  `ik_smart` = 粗粒度只切最合理（召回率低更精确）  例："华为手机" → ik_max_word 切出 [华为,手机]
- 粒度本质：**召回率 vs 精确率的权衡**  细粒度 = 宁滥勿缺（用户搜什么都能沾边）→ 召回优先，排序兜底  粗粒度 = 宁缺勿滥（搜到的都是对的）→ 精确优先  按业务定：电商/文章 C 端搜索→细粒度（输入随意，召回第一）；           法律合同语义敏感→粗粒度；标签/分类名→keyword 不分词
- 粒度设计分三层（别只盯 ik_max_word/ik_smart）：  ① 分词模式：按业务选细/粗粒度  ② 同义词词典（synonym.dic）：解决"不同词同义"——衣服=男装女装     （你的项目已建 synonym.dic：衣服/男装/女装/鞋子，AI 导购在用）  ③ 自定义词典（main.dic 扩展）：解决"切不开的新词"——"Mate70"  → 你的落地现状：细粒度 + 同义词词典已做；自定义词典是待办（诚实）
- 怎么配合：① 插件装到 plugins/analysis-ik/ ② mapping 声明字段  `analyzer: "ik_max_word"`（你的 SpuForElastic.java @Field 注解）  ③ 写入和查询都自动走 IK 分词
- 真实坑（面试加分）：Docker 重建后 IK 插件丢失 → ES red  （analyzer [ik_max_word] has not been configured）→  解决：插件目录挂载 /data/csmall/es-plugins 持久化
【追问3】倒排索引是什么，简单说？
- 正排（MySQL 思维）：文档→词，查"手机"要扫所有文档
- 倒排（ES 思维）：**词→文档列表**，建索引时反过来记  "华为"→[文档1,文档3] "手机"→[文档1,文档2]  搜"华为"直接查词项字典定位，不用扫全量
- 一句话："正排是查文档看有没有这个词，倒排是查词直接告诉你哪些文档有  ——把搜索变成查字典"
【追问4】深分页（1000+ 页）怎么办？
- 问题根源：项目用的 `from+size`（Spring Data PageRequest 底层）  翻第 1000 页 = from 9990，每个分片都要取 9990+10 条汇总再截取  → 内存/耗时线性增长，ES 默认 max_result_window=10000 直接报错  → 比喻：翻书翻到 1000 页，每次都要把前面 999 页重新翻一遍
- 三种解法：  ① **search_after（游标）**：记住上一页最后一条的排序值(id)，     下一页只查"比它大"的 → 每次只取 10 条性能恒定；     限制：只能顺序下一页，不能跳页/回翻 → 适合"加载更多"  ② **scroll（滚动）**：生成快照 scroll_id 持续取 → 适合后台全量导出，     不适合实时翻页（快照不实时）  ③ **业务规避（最实用）**：限制只翻前 100 页，深分页无业务意义     （百度/Google 也是翻几页就让你换关键词）
- 话术："from+size 深分页每个分片都要取 from+size 条，线性膨胀，  默认 1 万条封顶。search_after 记游标只取需要的 10 条，  适合'下一页'场景不能跳页；scroll 适合导出；业务上限制翻页深度  最实用。我项目数据量小 from+size 够，量上来第一件事换 search_after"
【追问5】ES 在生产环境一般承担什么任务？

【追问6】怎么自己构建 ES 查询和评分？（query 构建 + 评分举例）
- 场景：用户问"推荐 5000 元左右的手机"
- 第 1 步 query 构建（自然语言 → 结构化条件）：  正则解析价格区间（RagServiceImpl 代码实证）：  "5000元左右" → `new PriceRange(center*0.75, center*1.3)` = [3750, 6500]  → 把"左右"这种模糊表达变成机器可过滤的区间（上限放宽 30% 兜住稍高价）
- 第 2 步 评分（决定返回哪些、按什么顺序）：  向量检索用 ES scriptScore + 余弦相似度（代码实证）：  `.scriptScore(q -
> q.matchAll()).script(inline    .source("cosineSimilarity(params.queryVector, 'semanticVector') + 1.0"))`  → 商品文本 embedding 成 1024 维向量存 ES dense_vector 字段，    用户问题也转向量 → cosineSimilarity 算两个向量夹角余弦    （越接近 1 越相似）→ **+1 归一化到 [0,2]** 避免负分排序  → 按分数降序返回 topK
- 第 3 步 结果拼上下文：命中的商品拼成"参考资料"文本喂给 LLM  （buildContext：名称/标题/描述/品牌/价格/销量 → 塞进提示词）
- 一句话："query 构建 = 把人的话翻译成过滤条件；  评分 = 算相似度排顺序（IK 用 BM25 文本分，向量用余弦相似度）"
- **为什么向量化后 ES 能快速搜索？（HNSW 图索引）**：  ① 向量 = 语义坐标：bge-m3 把文本转 1024 维坐标，语义相近坐标近  ② 搜索 = 找最近邻：用户问题转向量 → 找 ES 里最近的商品向量  ③ 快的根源 = **HNSW 分层导航图**（mapping "index": true 开启）：     暴力全算 O(N)=100 万次余弦；HNSW 像 GPS 逐级放大 =     O(logN) 几十次跳跃 → 这就是"向量化后能快速搜索"的根源  ④ 倒排索引管字面（IK），HNSW 管语义（向量），共存一个 ES 索引
- 面试话术："ES 查询我手写过——用户说'5000左右'，  我用正则把它变成价格区间[3750,6500]过滤，再让 ES 算  cosineSimilarity 语义相似度排序，+1 归一化保证正分。  评分是 ES 的灵魂：全文用 BM25，向量用余弦，都能自定义。  向量检索快的根源是 HNSW 分层图——O(N) 暴力算变 O(logN) 图导航"
- **通俗版（"语义地图"比喻，对照着看）**：  核心事实：**向量 = 语义世界里的坐标**（1024 维空间 = 一张超大"语义地图"）  "华为Mate60" 坐标A=[0.12,-0.05,0.87...] / "小米14" 坐标B（离A近，都是手机）  "牛奶" 坐标C（离A远）→ 语义像的坐标近，不像的坐标远（bge-m3 的本事）  📥 存的时候（商品→向量→ES，用户来之前就做完了）：    MySQL 商品行 → 标题+描述+品牌拼成一段文本    → ① 调 bge-m3（embeddingClient.embed）→ ② 变成 1024 个数字=坐标    → ③ 存进 ES 的 semanticVector 字段（VectorSyncServiceImpl 同步时做的）  📤 查的时候（问题→向量→比距离）：    用户问"推荐性价比高的手机" → ① 用【同一个 bge-m3】把问题也变成坐标    → ② scriptScore = "比距离"的指令：cosineSimilarity(问题坐标, 商品坐标)    → ③ 相似度高的（坐标近的）排前面 → 返回 topK  为什么是"语义"搜索：关键词搜索要求标题真的出现"性价比"三个字；    向量搜索只要"性价比高的手机"和"便宜好用的手机"坐标近就能命中  为什么 +1.0：cosineSimilarity 范围 [-1,1]（1=一模一样 0=没关系 -1=相反），    +1 变 [0,2] 全正数，排序不会因负分出问题  完整数据流：    【写入】MySQL商品 → Dubbo同步 → 拼文本 → bge-m3 API → 坐标 → ES semanticVector    【查询】用户问题 → bge-m3 API（同一模型）→ 坐标 → ES scriptScore比距离 → topK    ⚠️ 存和查必须同一个模型，否则坐标系不一样没法比  一句话：商品提前存好坐标，用户问题现算坐标，ES 找最近的——    scriptScore 是算距离的工具，余弦相似度是"距离怎么算"的公式
【追问7】全文检索的完整流程？（写入 + 查询双链路）
- 链路一：写入（商品 → ES 倒排索引 = "建字典"）  ① 触发同步：手动全量 loadSpuByPage()（Dubbo 分页查 MySQL →     转 SpuForElastic → saveAll 批量写）/ 增量（商品增改 → Dubbo 同步）  ② ES 处理文档：title="华为Mate60 Pro 5G手机 鸿蒙系统"  ③ IK 分词：→ [华为, Mate, 60, Pro, 5G, 手机, 鸿蒙, 系统]  ④ 建倒排索引："华为"→文档1、"手机"→文档1,文档2...  ⑤ 预计算 BM25 统计量（词频/逆文档频/文档长度）为打分做准备
- 链路二：查询（用户输入 → 结果 = "查字典 + 打分"）  ① 查询词同样 IK 分词："华为手机" → [华为, 手机]  ② 查倒排表（multi_match 在 title/name/description 查）  ③ 合并去重 → 候选文档集合（召回）  ④ BM25 打分：词频高/稀有词命中/文档短 → 分高  ⑤ 按分降序 + 分页截取（PageRequest page-1）  ⑥ 返回 JsonPage 给前端
- 一句话：把"搜索时全表扫"变成"写入时预先建字典，搜索时直接查字典"
【追问8】ES 里的"文档"（Document）是什么？
- **ES 是 JSON 文档数据库**：一条记录 = 一个文档（Document）
- 你的项目：**一个商品（SPU）= 一个文档**，对应 SpuForElastic 实体  （id=spuId，字段=名称/标题/描述/品牌/价格/销量/标签）
- 例子（实际索引里的一个文档）：  
```json  {    "spuId": 1,    "name": "华为Mate60 Pro",    "title": "华为Mate60 Pro 5G手机 鸿蒙系统 昆仑玻璃",    "description": "超可靠玄武架构，卫星通话，AI 摄影大师...",    "brandName": "华为",    "categoryName": "手机",    "listPrice": 6999.0,    "sales": 1280,    "tags": "5G,旗舰,鸿蒙"  }  
```
- 对比 MySQL：MySQL 一行记录 = ES 一个文档；  但 ES 文档是**非结构化的 JSON**（字段可以不同），MySQL 行必须同结构
- 相关概念：索引(Index) = 文档的"集合"（≈MySQL 一张表）；  映射(Mapping) = 字段类型定义（≈建表语句）；  分片(Shard) = 索引拆成多份分布到多节点

【追问6】OAP / APM / Jaeger / RSS 都是什么意思？Agent 有啥用？

- **APM** = Application Performance Monitoring（应用性能监控）  = 一类软件统称，不是某个工具：监控(Metrics) + 链路追踪(Trace) +    依赖拓扑(Topology) + 日志(Logs)  市面上：SkyWalking/Datadog/New Relic/听云/博睿  一句话：给分布式系统装的行车记录仪+仪表盘
- **Jaeger** = Uber 开源的分布式链路追踪（CNCF 项目）= SkyWalking 竞品：  专精【链路追踪 Trace】（只回答"请求怎么走的"），埋点靠 OpenTelemetry  vs SkyWalking = APM 一体化（Trace+Metrics+拓扑）+ Agent 零侵入  选型结论：Jaeger 专精追踪，SkyWalking 全家桶+零侵入 → 选了后者
- **RSS** = Resident Set Size（常驻内存集）= Linux 进程实际占用的物理内存  对比：VSZ=虚拟内存(虚的) / RSS=真实占用(看这个才准) / PSS=按共享分摊  为什么 RSS ≠ JVM 堆：OAP 配 -Xmx512m 但 RSS 1.08G → 多出的 ~570M 是  元空间/代码缓存/线程栈/gRPC 缓冲等【堆外开销】→ APM 吃内存的实证
- **Agent 的作用（三层）**：  ① 字节码增强：Byte Buddy 动态改写 Dubbo/Spring MVC/MyBatis 字节码插桩，     业务代码零改动（非侵入）  ② 采集数据：记录 traceId/span/耗时/父子关系 → 拼成调用树  ③ 上报：gRPC 发给 OAP(11800)  你的部署：-javaagent:skywalking-agent.jar + SW_AGENT_NAME=mall-seckill  → 11 服务一行参数全接入  对比比喻：Zipkin=每个房间手动装摄像头(侵入)；    SkyWalking=装修预埋线路，住进去就有(改字节码不改代码)
- 话术："Agent 是采集端、OAP 是分析端、ES 是存储端、UI 是展示端，  四件套分工明确——Agent 靠字节码增强自动埋点，一行 javaagent 参数  11 个服务全接入，这是 SkyWalking 零侵入的核心卖点"

### Q5. 为什么用 Seata 不用其他分布式事务方案？🔴
**追问1**：Seata AT / TCC / SAGA 区别？其他模式怎么用？
**追问2**：为什么不用消息最终一致性？
**追问3**：你的 Seata 回滚实际用在哪些模块之间？
**追问4**：undo_log 是自动生成的吗？（表 vs 数据）
**追问5**：Seata + Dubbo 的官方 bug 你修过？（Issue #6815）
【简答】Seata AT 模式**无侵入**（自动生成 undo_log，业务代码不用改），适合微服务场景。相比 TCC（要写三个方法）、SAGA（要编排），AT 最简单。
【深挖】
- **Seata AT vs TCC**：AT 无侵入（自动快照回滚），  TCC 要手写 Try/Confirm/Cancel 三个方法（  侵入强但控制精细）
- **AT vs SAGA**：SAGA 是长事务编排，  适合跨多个服务长时间流程；AT 适合短事务（秒杀）
- **面试话术**："秒杀需要**即时一致性**（库存扣了订单必须成），  消息最终一致有延迟窗口，所以用 Seata AT——无侵入，  业务代码保持纯净"
【追问2】为什么不用消息最终一致性？
- 消息最终一致适合"可以容忍延迟一致"的场景；  秒杀需要即时保证库存和订单一致，AT 的全局事务更合适
- 补充：普通订单（非秒杀）**确实用了消息最终一致**——库存扣减改 MQ 异步  （order 的 @GlobalTransactional 因此注释掉）→ 按场景取舍：秒杀要即时一致用 AT，  普通下单容忍延迟用 MQ 最终一致（诚实点：强一致不是所有场景都需要）
【追问1】四种模式区别 + 其他三种模式使用方案简述？**四种模式对比：**

| 模式 | 侵入性 | 原理 | 适合场景 | 成本 |
|---|---|---|---|---|
| **AT** ✅ | 零侵入 | 代理数据源 + 解析 SQL + undo_log 自动回滚 | 简单 CRUD 跨库（秒杀下单） | 最低（加注解） |
| **TCC** | 高 | 手写 Try/Confirm/Cancel 三方法 | 强隔离 / 资金类 | 高（3 倍代码） |
| **SAGA** | 中 | 状态机编排 + 补偿 | 长事务 / 跨多系统 | 中 |
| **XA** | 低 | 数据库原生两阶段提交 | 依赖 DB 支持 | 低但性能差 |

**其他三种模式怎么用：**
- **TCC**：业务接口拆 3 方法——Try（预留资源，如冻结库存）→ Confirm（确认执行，扣减冻结库存）→ Cancel（取消回滚，释放冻结库存）；框架自动调 Confirm/Cancel，业务自己保证幂等。例：支付 = Try 冻结金额 → Confirm 扣款 / Cancel 解冻
- **SAGA**：定义状态机（订单创建→扣库存→发货，每步配补偿）；正向失败 → 反向执行补偿（扣库存失败 → 补偿撤销订单）。例：下单→支付→发货全流程
- **XA**：直接用数据库 XA 事务（两阶段提交），业务代码几乎不改，但要求所有库支持 XA、锁时间长性能差，现代微服务很少用
- **为什么选 AT**："我的秒杀就是'扣库存+建订单'短事务，AT 加注解就能用，TCC 要写 3 倍代码，SAGA 是长事务用不上，XA 性能差——AT 最匹配"
【追问3】你的 Seata 回滚实际用在哪些模块之间？（代码实证）
- @GlobalTransactional 只有 2 处：  ① 秒杀提交入口（seckill 模块）SeckillServiceImpl.commitSeckill     → 本地 cs_mall_seckill 库 + Dubbo 调 order 生成订单（cs_mall_oms 库）  ② 商品库存扣减（product 模块）ForOrderSkuServiceImpl.reduceStockNum     → 本地 cs_mall_pms 库（sku 库存）
- 跨库链路：seckill(cs_mall_seckill) → order(cs_mall_oms) → product(cs_mall_pms)  三个库各有一张 undo_log 表 = 参与事务的铁证
- ⚠️ 诚实点：order 的 OmsOrderServiceImpl @GlobalTransactional 被注释掉了  （"库存扣减改为 MQ 异步处理，不再需要"）——后来把订单扣库存改 MQ 异步，  那条链路的强一致拆掉了；现在真正跨库强一致只在秒杀提交链路
- **为什么只加这两处（设计理由）**：判断标准 = 是否跨库写  ① commitSeckill 真正跨库：本地写重试表(cs_mall_seckill) + Dubbo 调 order     写订单(cs_mall_oms) → 任一失败要整体回滚 → 必须全局事务  ② reduceStockNum 防御性：单库写但可能被上游跨库事务调用 → 加注解     通过 XID 传播加入上游事务（给调用方兜底）
- **回滚会发生什么（例子）**：用户秒杀"华为Mate60"，  第 3 步写重试表失败：  无 Seata：oms_order 已写但重试表没写 → 订单存在但秒杀记录丢失 = 数据撕裂  有 Seata：@GlobalTransactional 开全局事务 → order 写订单时记录 undo_log    → 异常 → 所有分支回滚 → oms_order/oms_order_item 用 before 镜像恢复  ⚠️ Seata 只管 DB：Redis 库存预扣(DECR) 在全局事务之前，回滚靠代码手动    补偿（catch 里 increment 加回 + delete 删锁）= 双保险  → 面试讲"我知道 Seata 边界，Redis 自己补偿"
【追问4】undo_log 是自动生成的吗？（易混淆，表 vs 数据）
- **表：手动建的**（你记得对的点）——Seata 不自动建表！  你项目里 database/cs_mall_seckill/undo_log.sql + Flyway V4/V5/V14  手动建：xid / branch_id / rollback_info(longblob) / log_status...
- **数据：自动生成的**（AT 模式核心）——Seata 代理数据源后自动：  ① UPDATE 前自动查 before 镜像（改之前的样子）  ② 业务执行正常 SQL  ③ 自动查 after 镜像（改之后的样子）  ④ 自动序列化写入 rollback_info 字段  ⑤ 提交→删记录；回滚→用 before 镜像恢复 + log_status=1
- 证据：启动日志 `SeataAutoDataSourceProxyCreator 
- Auto proxy data  source 'dataSource' by 'AT' mode`
- 一句话："**表是你手动建的（记得对），表里的回滚数据是 Seata  自动生成的（自动的）**——你记的'不是自动生成'指表，我说的是数据，  都对，只是指的东西不同"
【追问5】Seata + Dubbo 的官方 bug 你修过？（Issue #6815）🔴⭐ 防抄核弹**① 现象**
- 触发：秒杀浏览商品（Dubbo 查商品，不在事务里）报错  `Cannot invoke "BranchType.name()" because "branchType" is null`

- **NPE**：空指针异常，对 null 调方法就抛
- **dubbo-filter-seata:1.0.2**：Maven 坐标（Dubbo 扩展组:组件:版本）  = Dubbo↔Seata 桥梁（Dubbo 调用时自动携带/恢复 XID）**③ 根因（三方责任 + 触发机制）**

> 传递依赖版本，  你完全可以在 pom 里自己声明 3.3.1 覆盖它。当时选自写三个理由：  ① 3.3.1 是 Dubbo 扩展仓库的版本，适配 org.apache.seata 2.1.0，     和你 seata-all 2.1.0 + Dubbo 3.3.2 的组合是否完美匹配需额外验证（踩坑风险）  ② 自写判空+bind/unbind 逻辑简单，每一行都清楚，出问题能自己排查；     用别人的版本是黑盒  ③ 修复一个 NPE，自写 filter 改动面最小，不用连带升级验证  → "自写更可控"的工程判断，不是"不能用 3.3.1"
- 教训：**官方修复 ≠ 你的实际依赖版本**，要看 Maven 传递依赖最终解析版本；  跨仓库组件版本不同步是常见坑**⑦ 话术**"Seata 和 Dubbo 集成有官方 bug（Issue #6815）：dubbo-filter-seata:1.0.2桥接代码 branchType 为 null 时 NPE，XID 传不过去全局事务名存实亡。它是 seata-all 2.1.0 传递依赖带进来的（我没直接引入），官方修在dubbo-spi-extensions 3.3.1 但聚合包没跟进，我实际跑的还是坏版本。我排除依赖、手写 XID filter（先判 xid 再取 branchType + bind/unbind）解决。有人问为什么不直接升级 3.3.1——可以覆盖，但我自写更可控：逻辑简单每一行都清楚、不用连带验证版本组合、改动面最小。这个传递依赖和跨仓库版本不同步的坑，比 bug 本身更值得讲。Issue 编号写在代码注释里，面试官一看就知道这代码是亲手写的"
