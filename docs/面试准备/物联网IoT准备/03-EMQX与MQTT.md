# 03 EMQX 与 MQTT

> **核心问题**：MQTT 协议、EMQX 选型、消息机制、数据链路
> 难度：中-高

---

### Q1. MQTT 是什么协议？为什么 IoT 用它？🔴

【追问1】发布/订阅模型？
【追问2】和 HTTP 区别？

【简答】
MQTT 是**发布/订阅**模式的轻量消息协议，专为 IoT 
设计——低带宽、低功耗、离线消息（QoS）。设备发布遥测，订阅指令。

【深挖】
- **发布/订阅**：设备发布到 Topic，订阅者接收，
  解耦生产者和消费者
- **vs HTTP**：
  | 维度 | HTTP | MQTT |
  |------|------|------|
  | 模式 | 请求/响应 | 发布/订阅 |
  | 连接 | 短连接 | 长连接 |
  | 带宽 | 重（HTTP 头） | 轻（2字节头） |
  | 离线 | 无 | 遗嘱消息/QoS |
  | 场景 | Web | 物联网 |
- **QoS**：0（最多一次）、1（至少一次）、2（恰好一次），
  设备数据用 QoS 0/1
- 面试话术："MQTT 是**为 IoT 而生**的——报文头只要 2 
  字节（HTTP 几十字节），长连接省握手，还有 QoS 
  保证离线消息。
  路灯这种低功耗设备非常适合"

### Q2. EMQX 和 RabbitMQ 都是消息中间件，为什么两个都用？🔴

【追问1】各自职责？
【追问2】能不能只用一个？

【简答】
两个消息中间件职责不同：EMQX 管**设备 MQTT**（IoT 
通信），RabbitMQ 管**业务异步**（电商秒杀）。各司其职。

【深挖】
- **EMQX**：设备 ↔ 平台通信（遥测上行、指令下行），
  MQTT 协议
- **RabbitMQ**：业务服务间异步（电商秒杀落库、订单）
- **能不能只用一个**：理论上 RabbitMQ 有 MQTT 插件，
  但 EMQX 更专（海量连接、认证/ACL/规则引擎）；反之 
  EMQX 不擅长业务消息。**按场景选专业工具**
- 面试话术："这是两个项目的对比——电商用 RabbitMQ 
  做业务异步，IoT 用 EMQX 做设备通信。
  **每个中间件用在它最擅长的场景**，这是我选型的原则"

### Q3. 数据怎么从设备流到数据库的？🔴

【追问1】EMQX 规则引擎？
【追问2】绕过后端？

【简答】
改造后：设备 → MQTT → EMQX → **规则引擎直写 
TDengine**（绕过后端），后端只做业务逻辑。

【深挖】
- **改造前**：Device → MQTT → EMQX → 
  MqttSubscriber → telemetryMapper.
  insert(MySQL)
- **改造后**：Device → MQTT → EMQX → 
  **规则引擎** → TDengine（
  遥测/视觉/语音三张流水表）
- **为什么**：真实硬件数据频率提升（每 5 分钟 → 每 
  10-30 秒），MySQL 写入和存储成瓶颈，
  TDengine 时序更优
- **后端角色**：不做数据写入，专注业务逻辑（决策引擎、告警、控制）
- **规则引擎**：EMQX 内置，可以 SQL 风格配置数据转发规则
- 面试话术："**EMQX 规则引擎直写 TDengine** 
  是数据链路的优化——高频遥测不再经过后端转发，直接在 EMQX 
  层落库，后端专注业务。这体现了对'数据管道'的架构思考"

### Q4. TDengine 和 MySQL 的流水表迁移怎么做？

【追问1】哪些表迁移？
【追问2】前端要改吗？

【简答】
telemetry、vision_event、voice_event 
三张流水表从 MySQL 迁到 TDengine。前端零改动（
Controller 返回结构不变），后端 DAO 层切换。

【深挖】
- **迁移表**：telemetry（遥测）、vision_event（
  视觉）、voice_event（语音）——三张高频流水表
- **不改**：device（主数据）、control_command、
  alarm_record 等业务表留 MySQL
- **后端改动**：新增 
  tdengine/TdengineTemplate + 
  三个 DAO，
  Controller 查询源从 MySQL → TDengine
- **前端零改动**：Controller 返回 
  `Result<IPage<Entity>>` 结构不变
- **面试话术**："迁移的关键是**接口不变**——前端不用动，后端 
  DAO 层切换数据源。这体现了抽象的价值：
  Controller 面向 
  Service，不感知数据存储变化"

### Q5. TDengine 的建表模型？子表/超级表？

【追问1】为什么按设备建子表？
【追问2】时序库特性？

【简答】
TDengine 用**超级表（STable）+ 
子表**模型——超级表定义 schema，每设备一个子表（
`t_SL_001`）。时序数据按时间聚合，写入查询都高效。

【深挖】
- **超级表**：定义列结构（时间 + 设备 + 各传感器），
  `TAGS` 标记设备属性
- **子表**：每设备一张（`t_SL_001`），继承超级表 
  schema + 设备 tag
- **为什么**：时序数据按设备分表，查询单设备数据快；
  TDengine 按时间列存储压缩
- **特性**：写入快（时序优化）、查询按时间窗口、聚合函数内置
- 面试话术："TDengine 的**超级表 + 
  子表**模型是为时序设计的——设备越多子表越多，
  但查询和存储都高效。
  路灯遥测这种'持续产生、按时间查'的数据非常适合"

### Q6. 健康评分怎么算的？为什么用 TDengine 数据？🔴

【追问1】四维权重？
【追问2】什么时候算？

【简答】
HealthScoreTask 每天凌晨 2 点，从离线频次（30%）
、通信质量（25%）、指令响应率（25%）、传感器异常率（20%）
四维打分（0-100），更新 device.health_score。

【深挖】
- **四维权重**：`0.30离线 + 0.25通信 + 0.25响应 
  + 0.20传感器`
- **数据源**：离线频次（device 表）、通信质量（
  TDengine 遥测）、响应率（
  control_command）、
  传感器异常（TDengine）
- **触发**：每日 2:00 定时任务（`@Scheduled`）
- **应用**：健康分 < 60 自动产生 HEALTH_LOW 告警
- 面试话术："健康评分是**数据驱动的设备体检**——四维加权（
  离线/通信/响应/传感器），每天算一次，低于 60 自动告警。
  它把'设备状态'量化成 0-100，是运维的抓手"

### Q7. 边缘决策（EdgeNodeSimulator）是什么？

【追问1】云端和边缘怎么配合？
【追问2】断网怎么办？

【简答】
边缘决策模拟真实路灯内置边缘节点的本地决策——ConditionEvaluator
纯函数评估，断网时也能自主判断开关/调光。

【深挖】
- **双层决策**：
  - 云端 DecisionEngine：收到遥测后评估策略，下发指令
  - 边缘 ConditionEvaluator：**纯函数**（
    可迁移到硬件），本地评估
- **EdgeNodeSimulator**：定时任务模拟边缘节点，
  读策略缓存 + 最新遥测，本地评估，写 decision_log（
  EDGE_MATCH_EXECUTED）
- **断网自主**：边缘节点断网也能按本地策略决策（
  路灯不依赖云端也能亮/调光）
- **面试话术**："**边缘计算**是 IoT 
  的差异化能力——断网时路灯不能瞎，边缘节点有纯函数决策引擎，
  按本地策略自主工作。这体现了'云端 + 边缘'的双活设计"

### Q8. 心跳检测怎么做？离线怎么发现？🔴

【追问1】检测机制？
【追问2】多久算离线？

【简答】
HeartbeatMonitorTask 每 60 秒扫描，检测超时（
默认 360 秒）未上报的设备，标记离线并生成告警；重新上报自动恢复。

【深挖】
- **机制**：设备上报遥测即心跳 → `@Scheduled` 每 
  60s 扫描 → 超 360s 未上报 → 离线告警
- **恢复**：设备重新上报 → 自动恢复告警
- **告警类型**：OFFLINE（离线）、FAULT（故障）、
  HEALTH_LOW（健康分低）
- **面试话术**："心跳检测是**定时扫描 + 超时判定**——每 
  60 秒查一次，360 秒没动静就判离线。
  离线/故障/健康低三类告警自动产生自动恢复，运维不用盯屏幕"

### Q9. 能耗统计怎么算的？

【追问1】节能率公式？
【追问2】数据来源？

【简答】
EnergyCalcTask 每日 23:55 执行，读取当日 
control_command，按时间加权平均亮度，计算节能率、
用电量、碳减排，写入 energy_record。

【深挖】
- **节能率**：`(基准能耗 - 实际能耗) / 基准能耗 × 
  100%`，代码 `savingRate = 100 - 
  avgBrightness`（亮度代表能耗）
- **数据来源**：control_command 的 DIMMING 
  指令亮度值，按时间加权平均
- **无调光**：默认 avg_brightness=100%，节能率 
  0%（不虚报）
- **面试话术**：
  "能耗统计用**控制指令推算**——根据调光指令的亮度按时间加权算平均亮度
  ，亮度越高能耗越高，节能率 = 100 - 平均亮度。无调光就报 
  0%，不虚报"

### Q10. 多端协同怎么做的？

【追问1】Web/移动/硬件？
【追问2】接口怎么统一？

【简答】
Web 管理端（Vue3 + ECharts + 高德地图）、移动端（
33+ 接口文档）、真实硬件（小熊派）三端。后端一套 API，
移动端用 `{{BASE_URL}}` 占位符。

【深挖】
- **三端**：
  - Web：Vue3 + Element Plus + ECharts 
    + 高德地图（设备分布）
  - 移动端：33+ 接口（登录/设备/控制/告警/报表/助手）
  - 硬件：小熊派 BearPi 通过 MQTT 接入
- **接口统一**：一套后端 API，移动端文档用 
  `{{BASE_URL}}` 占位符支持不同环境
- **面试话术**："多端协同的核心是**一套后端 API 
  服务所有端**——Web 直接调，移动端按文档调（
  BASE_URL 
  可配），硬件走 MQTT。前端和移动端共享同一套业务逻辑"
