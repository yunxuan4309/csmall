> 难度：高

### Q1. MaxKB OOM 死循环怎么解决的？🔴

【追问1】根因？
【追问2】假 celery 替身？

【简答】
MaxKB 在 3.48G 内存 ECS 上，celery 进程 
~600MB 被 OOM Killer 杀 → 连锁重启 → 又被杀 
→ 死循环。用内存限制 + 假 celery 替身解决。

【深挖】
- **现象**：MaxKB 容器频繁重启，后端请求失败
- **根因**：3 容器共存 3.48G，celery 占 
  ~600MB，OOM 被杀后 `start-all.
  sh` 连锁重启 
  celery → 死循环；Gunicorn 
  timeout 30s 
  复杂 RAG 超时
- **解决三步**：
  1. `docker update --memory 1.8g 
     --memory-swap 2g maxkb`（内存硬限制）
  2. 删除 3 个大 PDF（减少 celery 向量化压力）
  3. **假 celery 替身**：空 shell 脚本替换 
     `/opt/py3/bin/celery`，占几 KB 不干活，骗过 
     `start-all.sh` 的 `wait -n` 监控；
     后端超时调大（connect 15s, read 120s）
- **面试话术**："这是低配服务器跑 AI 的经典坑——OOM 
  死循环。**假 celery 替身**是个 hack：
  用空脚本占位骗过进程监控，让 start-all.sh 认为 
  celery 活着。虽然 hack，但在资源受限时是有效方案，
  体现我能深入容器内部解决"

### Q2. 设备 MQTT 鉴权踩了哪些坑？🔴

【追问1】最致命？
【追问2】怎么排查？

【简答】
10 个连环坑：SSL 端口未开放、Docker 映射缺失、
容器重建配置丢失、EMQX MySQL 认证 Prepared 
Statement bug、Java SSL 
hostname 验证等。

【深挖】
- **10 坑清单**（按严重度）：
  | 问题 | 类型 |
  |------|------|
  | SSL 8883 安全组未开放 | 服务器 |
  | Docker 未映射 8883/8084 | 服务器 |
  | 重建 EMQX 挂空目录 → 配置丢失 | 操作 |
  | EMQX 认证器/ACL/规则全丢 | 操作 |
  | Java SSL hostname 验证失败 | 代码 |
  | device_credential 表不一致 | 数据库 |
  | **EMQX MySQL 认证 Prepared Statement + caching_sha2_password 不兼容** | EMQX Bug |
  | **disable_prepared_statements 不生效** | EMQX Bug |
  | 前端 KeepAlive 白屏 | 前端 |
  | system/alarms 发布超时 | 代码 |
- **面试话术**："设备鉴权踩了 10 个坑，**两个是 EMQX 
  的 bug**（Prepared Statement 和 
  caching_sha2_password 不兼容）。这让我学会：
  中间件文档说支持，实际部署可能遇到厂商 bug，要会绕过"

### Q3. 设备 ID 下划线兼容性问题？

【追问1】为什么担心？
【追问2】怎么验证？

【简答】
设备 ID 用下划线格式（SL_001），担心 
MQTT/EMQX/MySQL/TDengine 兼容性。
逐项评估验证：MQTT 允许任意 UTF-8、MySQL `=` 
不把 `_` 当通配符、ACL 下划线合法、TDengine 
子表名统一。

【深挖】
- **评估项**：
  | 组件 | 影响 |
  |------|------|
  | MQTT Username | 允许任意 UTF-8，下划线合法 |
  | EMQX MySQL Auth SQL | `=` 精确匹配，`_` 非通配符 |
  | EMQX ACL | 下划线是 Topic 合法字符 |
  | 后端 split | 字符串分割，与 ID 格式无关 |
  | TDengine 子表 | 已统一下划线格式 |
- **历史坑**：EMQX 规则引擎 `payload.
  deviceId` 为 null（JSON 解析 bug，
  不是下划线问题），用 `nth(2, split(topic, 
  '/'))` 从 Topic 提取
- 面试话术："设备 ID 格式看似小事，但**影响 MQTT、
  MySQL、ACL、TDengine 
  多个组件**——我逐项评估下划线兼容性，这体现了'改一个 ID 
  格式要评估全链路'的系统思维"

### Q4. EMQX 容器重建后配置丢失？

【追问1】为什么会丢？
【追问2】怎么避免？

【简答】
EMQX 重建后认证器、ACL、规则引擎全丢——因为没持久化配置。
重建时挂空目录覆盖了默认配置。

【深挖】
- **原因**：EMQX 配置在容器内，重建后回到默认；`-v 
  /opt/.../emqx/etc:/opt/emqx/etc` 
  挂空目录覆盖默认配置
- **影响**：认证器、ACL、规则引擎全丢，设备连不上
- **解决**：配置持久化（挂载正确目录）+ 重建后重建规则引擎
- **教训**：Docker 重建 = 全新环境，配置要挂载或写进镜像
- 面试话术："**Docker 重建 = 全新环境**——EMQX 
  配置不持久化，重建就丢。和电商项目 ES IK 
  分词器丢失是同一类问题，我深刻理解了容器配置必须持久化"

### Q5. MQTT 模拟数据链路排查？

【追问1】什么问题？
【追问2】怎么定位？

【简答】
MQTT 模拟数据链路问题排查——模拟器发布数据、后端订阅处理、
写入存储，全链路验证。

【深挖】
- **链路**：模拟器 → MQTT → EMQX → 后端 
  MqttSubscriber → 处理/存储
- **排查点**：模拟器是否发布（MQTT 客户端状态）、EMQX 
  是否收到（Dashboard）、后端是否订阅（topic 匹配）、
  数据是否入库（TDengine/MySQL）
- **常见坑**：topic 不匹配、JSON 序列化、设备 ID 提取
- 面试话术："数据链路排查是**逐跳验证**——模拟器 → EMQX 
  → 后端 → 存储，每层看数据有没有到。MQTT 问题常出在 
  topic 不匹配或格式问题，逐层看最有效"

### Q6. 你排查问题的方法论？🔴

【追问1】步骤？
【追问2】工具？

【简答】
方法论：① 复现现象；② 逐层定位（前端→网关→服务→中间件→数据库）
；③ 看日志/监控；④ 找到根因；⑤ 修复 + 防复发。

【深挖】
- **步骤**：
  1. 复现（明确现象和影响范围）
  2. 分层排查（从最外层到最里层）
  3. 用工具（日志、监控、命令）
  4. 定位根因（不是表面现象）
  5. 修复 + 持久化（防复发）+ 写文档
- **电商例子**：ES red → 前端卡死 → 
  _cluster/health → _cat/shards → 
  allocation/explain → IK 丢失
- **IoT 例子**：设备连不上 → SSL 端口 → Docker 
  映射 → EMQX 配置 → 证书验证
- 面试话术："我的排查方法是**复现 → 分层 → 工具 → 根因 → 
  防复发**。比如 ES red 是前端卡死 → 集群健康 → 
  分片状态 → explain 堆栈 → IK 丢失，一层层剥。
  最重要的是**找到根因后还要防复发**（挂载持久化）+ 
  写文档沉淀"

### Q7. 前后端联调踩过什么坑？

【追问1】KeepAlive？
【追问2】接口字段？

【简答】
坑：前端 KeepAlive 缓存导致返回列表白屏（
MainLayout Transition 多根节点冲突）；
接口字段对齐（空字符串 vs null）；分页字段（
list/records）。

【深挖】
- **KeepAlive 白屏**：MainLayout 移除 
  Transition 外套（DeviceDetail 
  多根节点冲突）
- **空字符串问题**：可选字段空字符串触发后端校验，应传 null
- **分页字段**：不同服务可能用 list 或 records
- **面试话术**："前后端联调踩过前端缓存白屏、
  字段格式对齐这些细节——**空字符串和 null 的语义差异**、
  分页字段不统一，都是实际会遇到的问题"

### Q8. 权限系统遇到过什么坑？

【追问1】动态权限？
【追问2】菜单权限？

【简答】
权限系统做过：权限分配修复、动态更新、菜单权限树、前端路由守卫 + 
v-if 按钮显隐。坑：权限变更后前端不及时刷新、菜单权限码绑定。

【深挖】
- **后端**：JwtInterceptor 动态查用户 → role 
  → permissions
- **前端**：router.beforeEach 守卫 + meta.
  permission + `v-if="hasPerm()"`
- **坑**：权限变更要刷新；菜单树按 permission_code 
  绑定，无权限的不显示
- 面试话术："权限系统做了**动态权限**（JWT 里带权限码，
  前端守卫校验）+ 菜单权限树。
  坑是权限变更的及时性和菜单绑定，都处理过"

### Q9. 移动端开发遇到什么坑？

【追问1】接口文档？
【追问2】兼容？

【简答】
移动端主要靠接口文档（33+ 接口，BASE_URL 占位符），坑：
WSS 自签名证书浏览器不信任 → 改回 WS；natapp 
内网穿透配置。

【深挖】
- **WSS 证书**：前端 MQTT WebSocket 用 WSS，
  自签名证书浏览器不信任 → 改回 WS
- **接口文档**：BASE_URL 占位符支持多环境
- **natapp**：内网穿透（开发时手机访问本地服务）
- 面试话术："移动端开发遇到 **WSS 
  自签名证书不被信任**——浏览器不认自签名证书，只好改回 WS。
  这是移动端连 MQTT 的常见坑"

### Q10. 如果让你重构/改进 IoT 项目，你会做什么？🔴

【追问1】技术？
【追问2】架构？

【简答】
① 单体拆微服务（按设备/告警/策略/AI 拆）；② 
引入消息队列做告警异步；③ 边缘计算真正部署到硬件；④ 
加时序数据降采样/冷热分层。

【深挖】
- **拆微服务**：当前单体，可拆设备服务/告警服务/AI 服务
- **告警异步**：大量设备告警用 MQ 削峰
- **边缘真实化**：ConditionEvaluator 
  从模拟器迁到真实边缘节点
- **时序优化**：TDengine 冷热分层、降采样（老数据降精度）
- 面试话术："改进方向是**从单体到微服务 + 
  边缘真实化**——当前单体够用，但设备规模大了要拆；
  边缘决策现在在模拟器，应该真正部署到硬件。
  我理解当前项目的边界和演进方向"
