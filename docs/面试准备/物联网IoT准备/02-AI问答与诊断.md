# 02 AI 问答与诊断

### Q1. AI 问答是做什么的？和电商 AI 有什么不同？🔴

【追问1】MaxKB 是什么？
【追问2】面向什么场景？

【简答】
IoT 项目集成 MaxKB 
做**维修知识库问答**——运维人员问"灯不亮怎么办"，AI 
基于故障手册回答。和电商导购（卖商品）不同，这是**运维诊断**场景。

【深挖】
- **MaxKB**：开源的 RAG 知识库平台，提供 OpenAI 
  兼容的对话接口
- **知识库内容**：路灯常见故障手册（3 份：故障手册 + 操作指南 
  + 诊断维修）
- **场景**：运维人员在设备详情页发起诊断 → AI 返回维修建议
- **vs 电商 AI**：
  | 维度 | 电商 AI | IoT AI |
  |------|---------|--------|
  | 平台 | DeepSeek 直连 | MaxKB 平台 |
  | 数据 | 商品库 | 故障手册 |
  | 场景 | 导购（卖） | 运维诊断（修） |
  | 交互 | 多轮对话 | 诊断 + 调参 |
- 面试话术："两个 AI 我都做过——电商是 DeepSeek 导购，
  IoT 是 MaxKB 维修诊断。**同一套 RAG 思想，
  不同落地场景**，这体现了我对 AI 应用的理解不限于某个平台"

### Q2. 三段式 AI 流程是什么？🔴

【追问1】本地正则 → AI 意图 → RAG？
【追问2】为什么分段？

【简答】
`/api/assistant/chat` 接口三段式处理：
本地正则快匹 → AI 意图识别 → RAG 问答。
快速问题不走大模型，省成本省延迟。

【深挖】
- **三段式**：
  1. **本地正则快匹**：简单规则直接命中（如"调高亮度"→ 直接返回）
  2. **AI 意图识别**：判断是"知识问答"还是"阈值控制"
  3. **RAG 问答**：命中知识库，调 MaxKB 返回维修建议
- **为什么分段**：
  - 快：简单指令走正则，毫秒级，不调大模型
  - 省：省 token 成本
  - 准：意图识别区分"问问题"和"要操作"
- **阈值控制**：命中"把阈值调到30" → 直接改后端真实策略，
  不调 MaxKB
- 面试话术：
  "三段式是**成本与智能的平衡**——能用正则解决的绝不动用大模型，
  AI 只处理真正需要理解的。这也是一种工程化思维"

### Q3. 自然语言调参怎么实现的？🔴

【追问1】"把阈值调到30"怎么处理？
【追问2】安全怎么控制？

【简答】
用户说"把阈值调到30"，AI 识别阈值控制意图，解析参数，
直接修改后端真实策略。有 7 参数白名单限制可调项。

【深挖】
- **流程**：`POST /api/assistant/chat` 
  → 识别"阈值控制"意图 → 解析"光照阈值=30" → 
  调策略接口修改
- **白名单**：7 个参数白名单（光照阈值等），
  只能改允许的参数，防止乱改
- **真实生效**：不是模拟，直接改后端 
  lighting_policy，前端能看到策略变化
- 面试话术："自然语言调参是**意图识别 + 参数解析 + 
  实际生效**——AI 不只是聊天，它能真的改系统。7 
  参数白名单是安全边界，防止 AI 误操作"

### Q4. 一键诊断怎么做的？🔴

【追问1】传入什么？
【追问2】怎么生成诊断建议？

【简答】
设备详情页点"诊断"，后端收集设备完整上下文（
最新遥测/告警/控制历史），调 MaxKB 做 RAG 问答，
返回诊断建议。

【深挖】
- **上下文收集**：设备最新遥测（光照/温湿度）、告警记录、
  控制历史——完整"病历"
- **RAG 问答**：把上下文 + 问题传给 MaxKB，
  基于故障手册生成诊断建议
- **返回**：类型 KNOWLEDGE_QA，内容是维修建议
- 面试话术："一键诊断的核心是**给 AI 
  足够的上下文**——不是空问'怎么了'，而是把设备遥测、告警、
  历史全喂给它，AI 才能准确判断"

### Q5. MaxKB 接入方式？

【追问1】OpenAI 兼容接口？
【追问2】配置？

【简答】
MaxKB 提供 OpenAI 兼容的 
`/chat/completions` 接口，后端

【深挖】

  `MAXKB_CHAT_COMPLETIONS_URL` +

  URL 和 
  Key，这也说明了大模型接口标准化的价值"

### Q6. MaxKB 遇到过什么问题？（OOM）🔴

【追问1】什么现象？
【追问2】怎么解决的？

【简答】
MaxKB 在低配 ECS（3.48G 内存）上 OOM 死循环：
celery 进程占 ~600MB 被 OOM Killer 杀 → 
连锁重启 → 又被杀。用内存限制 + 假 celery 替身解决。

【深挖】
- **现象**：MaxKB 容器频繁重启，后端报请求失败
- **根因**：3 容器共存 3.48G ECS，MaxKB 的 
  celery 进程 ~600MB，被 OOM 
  Killer 杀后触发 
  `start-all.sh` 连锁重启 celery → 
  又被杀 → 
  死循环；Gunicorn timeout=30s 导致复杂 
  RAG 超时
- **解决**（三步）：
  1. `docker update --memory 1.8g 
     --memory-swap 2g maxkb`（内存硬限制）
  2. 删除 MaxKB 后台 3 个大 PDF（减少 celery 
     向量化压力）
  3. **假 celery 替身**：用空 shell 脚本替换 
     `/opt/py3/bin/celery`，占几 KB 内存但不干活，
     骗过 `start-all.sh` 的 `wait -n` 进程监控；
     后端超时调大（connect 15s, read 120s）
- 面试话术："这是 **低配服务器跑 AI 组件的经典坑**——OOM 
  死循环。我用内存硬限制 + 假 celery 替身（
  用空脚本骗过进程监控）解决。'假 celery 替身'是有点 
  hack 但很有效，体现我**能深入容器内部解决问题**"

### Q7. 为什么 AI 和电商的 TokenBudgetService 类似的东西？

【追问1】成本控制？
【追问2】MaxKB 免费吗？

【简答】
MaxKB 是私有化部署，没有按次计费，所以成本主要是服务器资源（
内存），不像 DeepSeek 按 token 计费需要预算控制。

【深挖】
- **电商 AI**：DeepSeek API 按 token 收费 
  → TokenBudgetService 2元/天预算控制
- **IoT AI**：MaxKB 私有化部署（Docker），不按 
  token 收费 → 成本是内存/资源，需要的是**内存优化**（
  OOM 问题）
- **面试话术**："两种 AI 的成本模型不同——API 计费要控 
  token，私有化部署要控资源。
  **我根据成本模型选择了对应的控制手段**，
  这也是工程化思维的体现"

### Q8. 知识库怎么更新的？

【追问1】文档导入？
【追问2】向量化？

【简答】
在 MaxKB 后台创建知识库，上传故障手册文档，MaxKB 
自动向量化存储。应用关联知识库后即可问答。

【深挖】
- **导入**：MaxKB 后台上传 
  `docs/路灯常见故障手册.md` 等
- **向量化**：MaxKB 自动对文档切分 + 
  embedding 向量化
- **关联**：创建应用关联知识库，生成 API Key
- **注意**：大 PDF 向量化耗内存（OOM 的一个诱因）
- 面试话术："知识库更新是**平台侧操作**——上传文档 MaxKB 
  自动向量化。我理解了 RAG 的知识注入流程，
  也知道大文档向量化对资源的压力"

### Q9. AI 诊断和人工维护怎么配合？

【追问1】AI 建议可靠吗？
【追问2】有没有兜底？

【简答】
AI 诊断基于故障手册提供建议，作为**辅助**——运维人员参考 
AI 建议，同时有告警系统兜底。AI 减少排查时间，但不替代人工。

【深挖】
- **定位**：AI 是**辅助诊断**，不是自动修复
- **流程**：设备告警 → 运维查详情 → 一键诊断（AI 给建议）
  → 人工处理
- **兜底**：健康评分预警、告警记录、人工确认
- 面试话术："AI 
  诊断是**辅助决策**——它把'翻手册找答案'变成'直接问 AI'，
  缩短排查时间。但最终人工确认，AI 不当自动执行者，这是负责任的 
  AI 应用"

### Q10. 如果让你扩展 AI 功能，会加什么？

【追问1】可行性？
【追问2】成本？

【简答】
① 设备故障预测（基于时序数据 + 健康评分，ML 预测）；② 
语音助手（移动端语音问"灯怎么了"）；③ 批量诊断（区域级故障分析）。

【深挖】
- **故障预测**：复用 TDengine 时序数据 + 健康评分，
  训练预测模型，高价值
- **语音助手**：移动端接 ASR + 现有 MaxKB 问答
- **批量诊断**：一个区域多设备故障，AI 汇总分析
- **成本**：故障预测要 ML 训练（重）；语音接 ASR（轻）；
  批量诊断复用现有（轻）
- 面试话术："最想加**故障预测**——它有真实数据（TDengine 
  时序）+ 明确的业务价值（提前发现灯故障）。相比语音这种锦上添花，
  预测是真正解决问题"
