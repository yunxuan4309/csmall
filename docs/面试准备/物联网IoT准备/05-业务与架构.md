# 05 业务与架构

> **核心问题**：决策引擎、RBAC、多端、真实硬件接入
> 难度：中

---

### Q1. 整个系统架构？🔴

【追问1】分层？
【追问2】和电商架构区别？

【简答】
后端 Spring Boot 单体 + EMQX（设备接入）+ 
TDengine（时序）+ MySQL（业务）+ MaxKB（AI）。
设备 → EMQX → 规则引擎/TDengine → 后端业务 → 
前端/移动端。

【深挖】
- **架构**：
  ```
  硬件/模拟器 → MQTT → EMQX → 规则引擎 → TDengine
                         ↓
                      后端 Spring Boot（决策/告警/控制/鉴权）
                         ↓
              Web前端(Vue3+ECharts+地图) / 移动端
                         ↓
                    MaxKB（AI诊断）
  ```
- **后端结构**：common（统一响应/异常/权限）+ 
  config + controller（18）+ 
  engine（决策）
  + mqtt + service + task（定时）+ 
  tdengine + util
- **vs 电商**：电商是微服务（11 服务），IoT 是单体（
  但功能完整）。面试要诚实："IoT 项目是单体 Spring 
  Boot，因为设备接入 + 业务逻辑一个服务能覆盖；但分层清晰（
  controller/service/engine/task）
  ，后续可拆"
- 面试话术："IoT 架构的核心是**设备数据管道 + 
  业务决策**——设备进 EMQX，数据落 TDengine，
  后端做决策和告警，多端消费。相比电商的微服务，IoT 
  更偏单体 + 
  外部中间件"

### Q2. 决策引擎（DecisionEngine）怎么工作的？🔴

【追问1】策略是什么？
【追问2】怎么评估？

【简答】
收到遥测后触发 DecisionEngine，读取启用的照明策略，
按优先级匹配条件（阈值/时间/场景），命中后下发控制指令并记录 
decision_log。

【深挖】
- **策略**：lighting_policy 表，条件 JSON + 
  动作 + 优先级 + 生效时段
- **流程**：遥测 → DecisionEngine → 读策略 → 
  按优先级匹配条件 → 命中 → 下发 MQTT 指令 + 写 
  decision_log
- **decision_log**：记录每次评估的输入快照、匹配策略、
  执行动作（结果：MATCH_EXECUTED / 
  NO_MATCH 
  / EDGE_MATCH_EXECUTED）
- **手动锁定**：手动操作后 30 分钟（
  MANUAL_LOCK_MINUTES），AI 策略跳过该设备，
  防止自动策略覆盖人工
- 面试话术："决策引擎是**规则驱动的自动控制**——策略是条件 
  JSON，收到遥测就评估，命中就下发。
  还有'手动优先'——人工操作后 
  30 分钟 AI 不干预，这是可靠性的设计"

### Q3. 策略管理支持什么？条件怎么配置？

【追问1】条件 JSON？
【追问2】模拟测试？

【简答】
策略支持阈值/时间/场景条件，JSON 配置，优先级排序。
有"模拟测试"功能——前端构造条件 JSON + 模拟传感器值，
后端评估返回是否命中。

【深挖】
- **条件类型**：光照阈值（如 lux < 50 开灯）、时间（
  晚上）、场景
- **模拟测试**：`POST /api/policies/test` 
  → DecisionEngine.
  matchesCondition() 评估 → 
  返回命中 + 动作 
  + 所有策略对比
- **面试话术**："策略管理有**模拟测试**——不用真等设备触发，
  前端构造模拟条件直接测评估结果。这体现了'可验证'的工程意识"

### Q4. 告警系统怎么设计的？🔴

【追问1】告警类型？
【追问2】怎么产生/恢复？

【简答】
三类告警：OFFLINE（离线）、FAULT（故障）、
HEALTH_LOW（健康分低）。定时任务/健康评分自动产生，
条件恢复自动解除。

【深挖】
- **类型**：
  | 类型 | 触发 |
  |------|------|
  | OFFLINE | 心跳超时（360s 未上报） |
  | FAULT | 设备故障 |
  | HEALTH_LOW | 健康分 < 60 |
- **产生/恢复**：HeartbeatMonitorTask 
  判离线生成告警，重新上报自动恢复；HealthScoreTask 
  健康分低告警，回升恢复
- **手动处理**：告警可人工处理
- 面试话术："告警是**自动产生 + 自动恢复**——离线、故障、
  健康低三类，条件满足就告警，条件消失就解除。运维不用盯着，
  系统自己发现问题"

### Q5. 设备管理做了哪些？

【追问1】CRUD？
【追问2】批量/地图？

【简答】
设备 CRUD、批量导入导出（Excel）、地图分布（高德地图）、
区域管理、健康分。设备表有 source 字段区分真实/模拟。

【深挖】
- **功能**：设备台账 CRUD、批量导入（Excel 模板）、
  设备地图（高德选点）、区域分组、健康分展示
- **source 字段**：SIMULATED（模拟器）/ REAL（
  真实硬件），模拟器跳过真实设备
- **面试话术**："设备管理是**运维的入口**——CRUD 是基础，
  批量导入、地图分布、健康分是实用功能。source 
  字段区分真实硬件和模拟器，接入真实设备时逻辑清晰"

### Q6. RBAC 权限怎么设计的？和电商有什么区别？🔴

【追问1】角色矩阵？
【追问2】@RequirePermission？

【简答】
4 角色 × 17 权限码矩阵（
SUPER_ADMIN/MAINTENANCE/MUNICIPAL/EMERGENCY
），自定义 `@RequirePermission` 注解 + 
JwtInterceptor 校验，102 处接口鉴权。

【深挖】
- **角色**：SUPER_ADMIN（超管）、MAINTENANCE（
  路灯管理员）、MUNICIPAL（市政人员）、
  EMERGENCY（应急人员）
- **权限码**：dashboard:read、device:
  create、alarm:handle 等 17+（实际 
  34 个权限码）
- **实现**：`@RequirePermission("device:
  create")` 注解 → JwtInterceptor 
  比对用户权限 → 无权限 403
- **前端**：路由 meta.permission + 
  `v-if="hasPerm('xxx')"` 控制菜单/按钮显隐
- **vs 电商**：电商用 Spring Security 
  @PreAuthorize + 角色；IoT 用自定义注解 + 
  权限码（更细粒度）
- 面试话术："IoT 的权限是**4 角色 × 
  权限码矩阵**——不同角色（路灯管理员/市政/应急）
  看到和操作的范围不同，用自定义 
  @RequirePermission 
  注解做细粒度控制，前端菜单按钮也按权限显隐"

### Q7. 真实硬件（小熊派）怎么接入的？🔴

【追问1】硬件是什么？
【追问2】接入流程？

【简答】
小熊派 BearPi-HM_Nano + E53_SC1 扩展板（
BH1750 光照 + LED），通过 MQTT 连 EMQX，
用独立凭证，发布遥测 + 订阅指令。

【深挖】
- **硬件**：小熊派 BearPi-HM_Nano，E53_SC1（
  BH1750 光照传感器 + LED）
- **固件**：E1_smartlighting_device，
  Flash 配置存储 + AT 串口配网 + WiFi/MQTT 
  连接 + 边缘决策 + 远程控制
- **接入**：device 表 source=REAL，EMQX 
  built_in 用户 Real_CS_001，独立凭证
- **数据链路**：硬件遥测 → MQTT → EMQX → 
  TDengine → 后端决策 → 指令下发
- 面试话术："真实硬件接入让项目**从模拟到真实**——小熊派通过 
  MQTT 用独立凭证连 EMQX，光照数据实时上报，LED 
  接收控制指令。source 字段区分真实/模拟，
  模拟器不干扰真实设备"

### Q10. 这个项目你最自豪/最有价值的点？

【追问1】差异化？
【追问2】难点？

【简答】
三个点：① 设备 MQTT 鉴权（真实硬件安全接入）；② 边缘计算（
断网自主决策）；③ 时序数据管道（EMQX 直写 TDengine）。
都是真实落地，不是 Demo。

【深挖】
- **设备鉴权**：每设备独立凭证 + TLS + ACL，真实路灯在用
- **边缘决策**：断网自主控制，云端边缘双活
- **数据管道**：EMQX 规则引擎直写 TDengine，绕过后端
- **真实性**：接入了小熊派真实硬件
- 面试话术："IoT 项目最有价值的是**真实性**——真实硬件接入、
  真实数据链路、真实安全鉴权。它不是 CRUD Demo，
  是一个能实际跑起来的物联网系统，
  这比电商项目更能体现'从硬件到云端'的完整能力"
