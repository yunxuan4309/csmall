### Q26. 压测第一步不是加压，是**先把三个干扰项证伪**（它们的失败长得像成功）

> 来源：[[问题解决--压测结论的可信性（先证伪干扰项与工具自身）]] §一 / §六 / §八

【追问1】你压的是 mock、又不花真钱，为什么还要临时改生产 Nacos 限流、还要把预算绕开？
【追问2】你说 AI 的并发上限是 **20** —— 凭什么说那个 20 不是"**限流器的** 20"？
【追问3】方案里写"准备 **120** 个用户 token，≥ 阶梯峰值"，为什么实测必须建到 **800**？

【简答】**入口限流 / 每用户频控 / 预算墙都会先于系统承载生效**，而且它们拒绝时**HTTP 仍是 200**（流式接口是 SSE 里一帧 `event:error`，**不是 429**）—— **失败长得像成功**。不先关掉或绕开，你量到的是**限流器的能力**。三种干扰三条路：**入口限流**（Sentinel `ai-chat` 阈值 5）Nacos 热改临时放开（**改前把规则原文落盘 + 记 md5，改后恢复**）；**预算墙**让 mock 回 **0 token**（比"临时调大预算"干净：不碰安全限额、无需善后）；**每用户频控**（10 次/60s）**绕不开，只能算** —— 它决定的是**可持续 RPS**：`可持续 RPS ≈ N × 10 / 60`，**120 用户只有 20 req/s**，所以必须建 **800** 用户池（≈133 req/s）。

【深挖】
- **判据要能区分"它拦的"和"它扛不住的"**：服务端日志会说话 —— 闸门满是 `【AI并发闸门】…当前并发 20/20，已拒绝本次调用`；而**预算超限与闸门满在客户端是同一句文案**（见 Q28），所以"分不开类"时**回看服务端日志**，别猜。
- **干扰项要"算"，不能"估"**：把每个限额换算成**对你真正要测的那个量的约束**（这里是 RPS）再倒推资源。"用户数 ≥ 并发数"是错的直觉 —— 本项目实测把 120 改成 800，并把公式**直接打进脚本启动提示**（低于阈值就提示）。
- **两个"坑上坑"**：① 生产 `AI_AGENT_ENABLED=true` ⇒ 压测必须**两条链路各压一遍**（流水线单轮 vs Agent 双轮），否则量到的是"**没开 Agent 的假上限**"；② 生产预算 **2 元/天**、单价 1 元/百万（入）+ 2 元/百万（出）⇒ **约 5000 次调用就打满**，而 100 并发 × 45s 一档就 ~4500 次 —— 不切断记账，压测就变成**测额度**。
- **一句话**：**压测的产出不是 RPS，而是"我凭什么相信这个 RPS"。**

**面试话术**
"我做 AI 并发压测，**第一步不是加压，而是先证伪三个'会替我回答'的干扰项**：入口限流（Sentinel 阈值 5）、每用户频控（10 次/60s）、日预算墙（2 元/天）。它们的共同点是**失败长得像成功** —— 流式接口被限流返回的是 **HTTP 200 + SSE 里一帧 error**，不是 429。所以我先动手把它们逐个摘掉：限流用 Nacos 热改临时放开，**改之前把规则原文和 md5 都落盘、改完恢复**；预算是让 mock 回 **0 token**，从记账层面彻底不花钱 —— 比临时把预算调大干净，不碰安全限额也不用善后。第三个**绕不开只能算**：每用户 10 次/60s 决定的是**可持续 RPS**，`N × 10 / 60`，方案里写的 120 个用户只够 **20 req/s**，我按这个公式倒推出需要 **800** 个用户，并把公式直接打进脚本的启动提示里。**先证伪干扰项，再谈承载** —— 否则你量到的是限流器的能力，不是系统的能力。"

### Q27. 替身和客户端都要**自证**：三个"工具自己说谎"的实例

> 来源：[[问题解决--压测结论的可信性（先证伪干扰项与工具自身）]] §二 / §三 / §四 / §五

【追问1】mock 是你自己写的，为什么还要"**先单独压一遍 mock**"？
【追问2】读一个请求体能有多难？它怎么能制造出"**每次对话都 500**"？
【追问3】压测脚本所在的机器也要取证？取什么证？

【简答】因为**替身与客户端同样会"替你回答"**。三个实例都来自"先单独压工具"这一步：**① mock 只按 `Content-Length` 读请求体**，而应用用 **chunked** 发送 ⇒ 读到空体 → 误判任务 → `fastjson` 抛异常 ⇒ **每次对话都产生一个假 500**；**② 内置 `ThreadingHTTPServer` 的 accept 队列默认只有 5** ⇒ 100 并发丢 17 条连接（CPU 才 0.4%）；**③ 流结束的语义照抄了"文档直觉"** ⇒ 客户端读到超时。**顺序是硬性的：压 mock（拿 P50/P99 + 吞吐，证明它不是瓶颈）→ 再压被测系统**；客户端也取 CPU/负载证据。

【深挖】
- **实例①：`Content-Length` 与 `Transfer-Encoding` 只认一个是错的** —— 应用的 `chatJson`（JSON 结构化任务）走 **chunked、没有 `Content-Length`**，mock 读到 0 字节 ⇒ 判成"普通任务"、回纯文本 ⇒ 业务侧 JSON 解析失败。**修法**：mock 实现 chunked 请求体解析（读块长 → 读块 → 直到 0 块）。**证据是给 mock 加"请求摘要"日志**：`clen=None te=chunked rawlen=0 json_ok=False` → 修复后 `rawlen=854 json_ok=True`（**替身的日志是证据，不是噪声**）。
- **实例②：`request_queue_size` 默认 5** —— 线程化了**不等于**扛得住并发（线程模型之外还有 **accept 队列 / fd / 端口**）。设 512 后复测 20 / 50 / 100 / 150 并发 **0 失败**、**峰值并发 = 150**（证明确实并发）、吞吐 **306 req/s**。
- **实例③：协议里的"结束标记"≠"流结束"** —— mock 发完 `data: [DONE]` 就保持 keep-alive → Java 客户端**阻塞到读超时**（表现像"系统很慢"）。读码发现客户端把 `[DONE]` 当 **`continue`**、**真正靠连接 EOF 结束** ⇒ mock 必须显式写 chunked 结束块 `0\r\n\r\n` **终结响应体**。**做替身/桩要照抄客户端代码，不能照抄文档。**
- **客户端自证**：压测脚本跑在**另一台机器**（被测系统之外、走私网），并取该机 load（0.27）作证据 —— 避免"**自压自伤**"把被测系统与压测机混成一个。

**面试话术**
"我压测时有一条固定纪律：**先单独压工具，再压被测系统**。原因是替身和客户端同样会'抢答'。我自己的 mock 上就抓到两个——一个是我只按 `Content-Length` 读请求体，而我的应用发**结构化任务时用的是 chunked**，于是 mock 读到空体、把任务判错、返回纯文本，**每次对话都制造一个假 500**，如果不先单独压 mock，这 500 会被我当成'系统的降级'记下来；另一个是 Python 内置的 `ThreadingHTTPServer` **accept 队列默认只有 5**，100 并发实测丢了 17 条连接，而 CPU 才 0.4%，根本不是算力问题 —— 这就说明'线程化了'不等于'扛得住并发'。第三个更隐蔽：mock 发完 `data: [DONE]` 之后什么都不做，客户端一直阻塞到读超时；我去读客户端代码才发现，它把 `[DONE]` 当 **continue**，真正结束靠的是**连接 EOF**，所以替身必须显式写 chunked 的结束块。再加上压测机本身也要取 CPU/负载证据、并且**必须跑在被测系统之外的另一台机器上**，这样才谈得上'我量到的是被测系统'。"

### Q28. 三条读数规矩：**成功 RPS · 失败必须可分类 · "数字变好看"要警惕**

> 来源：[[问题解决--压测结论的可信性（先证伪干扰项与工具自身）]] §六 / §七 / §八 / 跨问题共性

【追问1】100 并发总 RPS **53.6**、20 并发才 **20.7** —— 那 100 并发更强？
【追问2】闸门满和真异常，客户端收到的文案一样 —— 那你的失败率还有意义吗？
【追问3】你修完一个缺陷，RPS 反而从 **12.9 掉到 7.5**，这不是改坏了吗？

【简答】三条规矩：**① 判承载只看"成功 RPS"** —— 被限流/被闸门拒的请求**毫秒级返回**，会把"总请求数/耗时"抬得很高，**总 RPS 变成"失败得有多快"**（实测 agent 链路 100 并发总 53.6，而成功只有 ~18/s）；**② 分不开类的失败率是伪指标** —— 闸门满与真异常**客户端同一句文案**，这时去**看服务端日志**，脚本也**宁可报成"其它降级 + 提示去查"，不猜一个好看的数**；**③ "数字变好看"是危险信号** —— 修 #62 之前，一半请求在安全过滤器被**秒拒（~130ms）**，反而把 RPS 抬高、把 p50 压低；**变化方向 ≠ 改善方向，要看分子**。

【深挖】
- ⭐ **这轮压测最值钱的产出不是曲线，是挖出一个生产缺陷（#62）**：`/ai/chat/stream` 走 `StreamingResponseBody`（异步），业务在异步线程写完后触发一次 **ASYNC 二次派发**；Spring Security 6 的 `anyRequest().authenticated()` **对所有 dispatcher type 都生效**，那一刻容器线程上**已无认证对象** → 拒绝 ⇒ **20 并发硬失败 50%，而串行 20/20 全 200**。修法是在授权链**最前面**加 `.dispatcherTypeMatchers(DispatcherType.ASYNC, DispatcherType.ERROR).permitAll()`；🔴 **只放行 ERROR 不够**（旧记录只猜到那一半）—— 两种派发都要放行，安全性上它们都是**已鉴权请求的内部再派发**，外部客户端无法伪装。
- **同条件对照才是验收**：修复后硬失败 **50% → 0**、成功率 **60.49% → 100%**、100 并发 0 失败 —— 但 **RPS 12.9 → 7.5、p50 1787ms → 2210ms**，因为修复前**一半请求被秒拒**在抬数。**"修好了反而变慢"是正确结果的常见形态。**
- **串行正常、并发炸 ⇒ 先怀疑时序/竞态，不是容量**；**失败请求"没进业务逻辑"是最强的分流线索** ⇒ 立刻查**框架层**（安全 / 限流 / 序列化 / 线程池），别先查数据库与下游。
- **服务端日志与客户端分类要交叉印证**，两者不一致时**以能解释现象的那个为准，并当场改判据**（本项目就是把脚本判据从"按文案分类"改成"不确定就报 degraded + 提示查日志"）。

**面试话术**
"最后我给自己立了三条读数规矩。**第一，判承载只看'成功 RPS'**：我实测 agent 链路 100 并发的**总 RPS 是 53.6，但成功只有 ~18/s** —— 因为被闸门拒的请求是**毫秒级返回**的，它们把'总请求数除以耗时'抬得很高，**总 RPS 其实是在说'失败得有多快'**。**第二，分不开类的失败率我不认**：闸门满和真异常在客户端是**同一句文案**，我这边就去看服务端日志里 `【AI并发闸门】` 的计数，脚本也宁可输出'其它降级 + 提示去查服务端'，**绝不为让报表好看而猜一个分类**。**第三，'数字变好看'恰恰要警惕**：我修完一个并发缺陷后，RPS 反而从 12.9 掉到 7.5、p50 还涨了 —— 因为修复前一半请求是在安全过滤器被**秒拒**的，那 130ms 的快速失败把 RPS 抬高了。**变化方向不等于改善方向，要看分子是什么。** 这轮压测最值钱的产出也不是曲线，而是它**挖出了一个真实的生产缺陷**：流式接口在并发下 50% 500、串行却 100% 正常，根因是 `StreamingResponseBody` 的 ASYNC 二次派发被授权规则当成新请求又鉴权了一次；修完同条件对照硬失败 50%→0。"
