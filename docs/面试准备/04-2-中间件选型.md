### Q6. 为什么用 Sentinel，不用 Hystrix？🔴
**追问1**：Sentinel 和 Hystrix 的核心区别？
**追问2**：Sentinel 的流控规则有哪些？
**追问3**：国内熔断限流主要用啥？（市场现状）
**追问4**：你项目 Sentinel 用到了什么程度？（代码实证）
**追问5**：灰度发布是什么？Sentinel 在里面什么角色？
【简答】Sentinel 是阿里开源，支持**实时流控**（QPS 维度）+ 熔断降级 + 规则持久化，比 Hystrix（已停更）功能强，和 Spring Cloud Alibaba 无缝集成。
【深挖】
- **出身与命运**：Hystrix(Netflix 2015) **2018 停更**；  Sentinel(阿里 2018) 活跃维护，Spring Cloud Alibaba 标配
- **功能差异**：Sentinel 支持 QPS/线程数/并发数三种限流 +  慢调用/异常比例/异常数三种熔断 + 快速失败/WarmUp/排队三种流控效果；  Hystrix 只有错误率熔断 + 线程池隔离，无 QPS 限流概念
- **规则管理**：Sentinel 控制台/Nacos **热更新不重启**；  Hystrix 改配置要发版重启
- **底层隔离**：Hystrix 线程池隔离（每依赖一个线程池，开销大但隔离彻底）；  Sentinel 信号量隔离（轻量，零额外线程，性能好）
- **你的流控规则**：QPS=10 限流（快速失败），  规则存 Nacos（重启不丢）
- **面试话术**："Sentinel 是 Spring Cloud   Alibaba 生态的，和 Nacos 无缝配合（规则存   Nacos   持久化），这是它比 Hystrix 强的地方"
【追问1】Sentinel 和 Hystrix 的核心区别？
- 命运：Hystrix 停更（Netflix 2018 放弃），Sentinel 活跃（阿里在养）  → "选活的不选死的"是最硬理由
- 功能：

| 维度 | Sentinel | Hystrix |
|------|----------|---------|
| 限流维度 | QPS/线程数/并发数 | 无 QPS 限流，只有线程池/信号量隔离 |
| 熔断策略 | 慢调用比例/异常比例/异常数 | 只有错误率超阈值 |
| 流控效果 | 快速失败/WarmUp/排队等待 | 只有快速失败 |
| 规则管理 | 控制台+Nacos 热更新不重启 | 静态配置，改代码重启 |
| 控制台 | 自带 Web 控制台（秒级监控） | 无官方控制台 |
- 底层隔离：Hystrix 线程池隔离（每依赖一池，开销大隔离彻底）；  Sentinel 信号量隔离（轻量零线程，性能好）  类比：Hystrix=每供应商配独立柜台+员工；Sentinel=总台按号码计数
- 话术："Hystrix 停更 + 功能少（无 QPS 限流、无热更新、无控制台），  Sentinel 阿里在养 + 功能全 + 规则热更新，选型没有悬念"
【追问2】Sentinel 的流控规则有哪些？
- 三种流控维度（grade）：  ① QPS 限流（grade=1）：每秒最多 N 次 → 你项目用这个（QPS=10）  ② 线程数限流（grade=0）：并发线程最多 N 个  ③ 并发数限流
- 三种流控效果（controlBehavior）：  ① 快速失败（0）：超了直接拒绝 → 你项目用这个  ② Warm Up（1）：冷启动预热，渐进放行（防系统刚启动被压垮）  ③ 排队等待（2）：匀速排队，削峰填谷
- 三种熔断策略（degrade）：  ① 慢调用比例：RT 超过阈值且比例超限 → 熔断  ② 异常比例：异常占比超阈值 → 熔断  ③ 异常数：异常个数超阈值 → 熔断
- 你的项目：QPS=10 快速失败（flow 生效）+ degrade 规则没建  （之前 Q1 追过：dataSource 配了但 Nacos 无配置 = 熔断空转）
【追问3】国内熔断限流主要用啥？
- **Sentinel 是国内 Java 微服务事实标准**：  国内主流是 Spring Cloud Alibaba 栈 → Sentinel 标配；  阿里云 MSE 服务治理也内置 Sentinel 能力
- Hystrix 基本退出：停更 + Netflix 系国内用得少
- Resilience4j：Hystrix 作者推荐的继任，功能类似但  **无控制台、动态规则弱** → 国内用的人少
- 新趋势：云原生 K8s + Istio 服务网格把限流熔断下沉到  Sidecar（业务零侵入），中小项目未普及
- 话术："国内 Java 微服务熔断限流事实标准是 Sentinel——  国内主流是 Spring Cloud Alibaba 栈，它是标配；  Hystrix 停更在迁移，Resilience4j 无控制台用的人少；  云原生新趋势是下沉 Istio，中小项目未普及。  我选 Sentinel 因为它和 Nacos 无缝配合（规则热更新）"
【追问4】你项目 Sentinel 用到了什么程度？（代码实证 2026-08）
- **已用（基础三件套）**：流控（秒杀 QPS=10，Nacos+代码双保险）+  规则持久化 Nacos + 控制台（csmall-sentinel 8090）
- ✅ **@SentinelResource 的规则已全部补齐（#5-P0，2026-09-08）**：  秒杀订单提交 QPS=10 / 新增订单 20 / 支付订单 20 / adminLogin 10 / AI 三档 `ai-chat`=5、`ai-reason`=10、`ai-light`=30 —— **原先只有秒杀有规则、其余"有注解无规则"空转，现已闭环**
- **高级能力**：**degrade 熔断已用**（#5-P0：`grade=0` 慢调用 RT>2s、比例 0.5 → 熔断 10s，覆盖秒杀 + 订单；此前 dataSource 配了但 Nacos 无规则 = 空转）；系统自适应保护 / 热点参数限流 / 授权规则 / 集群流控 = **仍未用**
- 诚实话术："我用了 Sentinel 基础三件套：QPS 流控、规则存 Nacos、控制台监控；**后来把注解对应的规则全补齐了**（秒杀/订单/支付/登录 + AI 三档，Nacos 里 6 条配置），还补了慢调用熔断。**这个过程本身就是教训**：早期 4 个接口打了 @SentinelResource 但只有秒杀配了规则，其余是空转——**注解 ≠ 规则**，配了 dataSource 也 ≠ 规则存在。企业级高级能力（热点参数限流/集群流控/系统保护）我了解但没用到，最该补的是热点参数限流"
【追问5】灰度发布是什么？Sentinel 在里面什么角色？
- 灰度发布 = 新版本先接小部分流量，验证 OK 再逐步放量到全量  （像煤矿金丝雀先试毒气）  旧版90%→新版10% → 观察 → 旧70%新30% → ... → 新版100%
- 三种策略：按比例随机 / 按用户白名单 / 按地域渠道
- 实现手段：Nginx 按 header 分流 / Gateway 按权重路由 /  Nacos 标签路由（Dubbo 场景）/ Istio 服务网格（云原生）
- **Sentinel 的角色（配合不替代）**：  分流决策是 Gateway/Nacos/Istio 的事；  Sentinel 管灰度期间的【流量保护与监控】——  ① 新版本实例设更保守限流（V2 限 QPS=5 防被打垮）  ② 新版本出问题熔断降级快速失败  ③ 控制台监控新实例 QPS/错误率辅助判断灰度是否成功

**追问10**：代码层面如何防主从切换？（五层方案）
【简答】Redis 做了：缓存、秒杀预扣库存、防重复购买（SETNX）、幂等 key、随机码存储、登录 token 校验。选它因为**单线程原子操作 + 内存快 + 丰富数据结构**。
【深挖】
- **数据结构应用**：  
- String：库存（DECR）、随机码、token  
- 幂等/防重：SETNX 原子  
- 布隆（Set 替代）：秒杀商品 ID 记录
- **为什么单线程原子**：Redis 单线程执行命令，DECR   天然原子，**扣库存不需要分布式锁**（但秒杀集群化后**定时任务防双跑用了**分布式锁，见 `02-秒杀高并发.md` Q11）
- **单线程瓶颈**：Redis 6+ 多线程 IO 处理，  但命令执行仍单线程；瓶颈通常是网络/内存不是 CPU
- **面试话术**："Redis   单线程是**特性不是缺陷**——它保证了命令原子性，  我用 DECR   扣库存天然防超卖，**扣库存不需要加分布式锁**；  我加的分布式锁只用在**定时任务防双跑**上（双实例会重复发 MQ/重复对账）"
【追问1】Redis 数据结构的应用？
- **DECR 是什么**：DECRement（递减）缩写，对称 INCR（Increment）  单线程原子执行 → 防超卖根基
- **你的用法**：String（库存 DECR/随机码/token/幂等锁 SETNX）+  Set（布隆替代）；Hash/List/ZSet 基本没用
- **数据结构业务全景（面试扩展）**：  String：计数器(INCR)/分布式锁(SETNX)/限流(INCR+EXPIRE)/对象缓存/位图签到  Hash：对象存储(用户信息)/购物车(cart:userId→skuId:数量)/商品属性(HINCRBY)  List：轻量消息队列(LPUSH/BRPOP)/最新列表(时间线)/任务队列  Set：标签/共同好友(SINTER)/抽奖(SRANDMEMBER)/去重/关注关系  ZSet：排行榜(score=销量ZREVRANGE)/延迟队列(score=时间戳,订单超时关单)        /滑动窗口限流/热门商品 —— 你项目零使用但 TODO#11 评估过  HyperLogLog：UV 去重计数(100万用户~12KB)/GEO：附近的人/Stream：专业队列
- **选型逻辑**：数据形态决定结构——单值 String、对象 Hash、  有序要排名 ZSet、去重 Set
- 单线程 + 原子性：DECR 天然防超卖，不用分布式锁
【追问2】Redis 单线程是瓶颈吗？
- 单线程 = 特性不是缺陷：命令原子执行（DECR 防超卖）、无锁无竞争
- Redis 6+ 多线程只处理网络 IO，命令执行仍单线程
- 瓶颈通常是网络/内存，不是 CPU；慢命令（KEYS *）才是大忌
- 你的秒杀用 DECR 原子扣库存，正好吃到单线程红利
【追问3】缓存穿透/击穿/雪崩？你的防御？（代码实证）
- **穿透**：查不存在的 key 打到 DB → 你的防御 = Redis Set 当布隆，  SeckillBloomInitialJob 预热 spuId 到 Set，查前先 hasBloomFilter 拦截
- **击穿**：热点 key 过期瞬间大量打 DB → 你的防御 = 热点数据预热常驻  （SeckillInitialJob 预热库存/随机码，秒杀窗口全年不过期）
- **雪崩**：大量 key 同时过期 → 你的防御 = 关键数据无 TTL/长 TTL  （库存/随机码常驻、reseckill 永久），不用短 TTL 缓存模式
- **企业级分层防御（面试加分）**：不只后端——CDN 层（热点页面边缘缓存）→  网关层（IP 限流/黑白名单）→ 应用层（布隆/互斥锁/多级缓存）→  数据层（连接池/读写分离）；你只做了应用层（演示项目无真实流量）
- 企业级进阶：空值缓存（穿透 key 缓存空值 5 分钟）、逻辑过期  （返回旧数据+后台异步更新）
【追问4】Redis 锁用了吗？基础用法？（代码实证）
- **用了 2 种 SETNX 锁**：  ① 幂等锁 @Idempotent（AOP 实现）：秒杀提交/新增订单/支付订单 3 处     setIfAbsent(key,"1",ttl) → 没抢到=重复提交拒绝 → 异常时 delete 释放     key=前缀+userId+参数MD5（不同参数不误判）  ② 下单锁 orderLock（SeckillServiceImpl）：防同一用户重复购买同商品，     1 分钟 TTL；与 reseckill 购买标记分离（刻意设计）
- **基础用法三要素**：加锁 SETNX 原子（setIfAbsent 带 TTL）→ 业务 →  释放（异常时 delete）；**必须带 TTL 防死锁**（持锁线程挂锁永不释放）
- **锁演进四代**：①SETNX 简单锁（死锁风险）→ ②SETNX+TTL（你现在的）→  ③唯一标识防误删+Redisson 看门狗续期 → ④RedLock 多节点多数派（有争议）
- **功能分类**：可重入锁/公平锁/读写锁/信号量/闭锁（Redisson 实现）
- ⚠️ 诚实点：pom 引了 Redisson 3.24.3 但代码没用（grep 无 RLock），  唯一 RLock 是 Leaf 项目内部读写锁；生产化升级 Redisson 看门狗
【追问5】布隆过滤器 vs Redis Set？项目用哪些锁？
- 布隆：N 哈希映射 bit 数组，"不存在"100% 确定、"存在"有假阳性；  省内存（百万 id ~1MB）、不能删元素
- Redis Set（你的）：100% 精确、可删（SREM）、但存真实元素占内存
- 你的取舍：数据量极小（6 场秒杀 12 SKU）→ Set 精确+可删+内存可忽略，  真布隆省内存优势在小数据量无意义，还得装 RedisBloom 模块  （代码注释写了取舍 + TODO，百万级再换）
- 项目锁确认：2 种 SETNX（幂等锁+orderLock）✅；  Redisson/可重入/看门狗/Lua 原子锁 ❌ 未用（场景不需要，生产化再上）
【追问6】秒杀预扣/防重复/随机码/幂等/缓存 详解（代码实证）
- **秒杀预扣库存**：先扣 Redis 虚拟库存，成功后再异步落库  DECR 微秒级（内存操作）→ 扛高并发；DB 扣库存延后（MQ 异步）  为什么 DECR 防超卖：StringRedisTemplate 直接在 Redis 内改数值 +  Redis 单线程命令原子 → 100 并发也是 99→98→97 依次扣，不会重复读  （代码注释原话：StringRedisTemplate 无序列化过程可直接操作数值，   Redis 天生单线程保证防超卖；集群需 Redisson 分布式锁）
- **防重复购买（三 key 组合）**：  ① orderLock 下单锁（SETNX 1min）：防同一秒重复提交  ② ordered 未支付标记（2h）：防锁过期后二次下单  ③ reseckill 购买标记（永久无 TTL）：防支付后永久重复购买  三 key 刻意分离（代码注释：与 reseckill 分离，下单不影响 isPurchased）
- **随机码**：6 位随机数（100000-999999），秒杀开始前 5 分钟  SeckillInitialJob 生成预热到 Redis  key=mall:seckill:spu:url:rand:code:{spuId}  TTL=秒杀2h+提前5min+防雪崩随机30s  提交时从 Redis 取码和 URL 路径里的码比对 → 防绕过秒杀页直接调接口
- **幂等（@Idempotent + AOP + SETNX）**：方法执行前 setIfAbsent 加锁，  抢到执行业务（完成后等 TTL 自然过期），没抢到抛"请勿重复提交"，  业务异常 delete 释放允许重试；key=前缀+userId+参数MD5（不同参数不误判）
- **你的"缓存"具体是啥**：秒杀数据（库存/随机码/三锁/购买标记）+  登录 token + AI 会话；【没有商品列表缓存】——数据量小（18 商品）  DB 无压力；秒杀数据是"定时预热写缓存"不是"读时缓存"
【追问7】Redis 预扣库存符合企业生产吗？数据一致性怎么保证？（🔴 深度）
- **符合吗**：符合，是电商秒杀标准做法（Redis 预扣 + DB 兜底），  但生产会做得更完整（见下"企业级加强"）
- **预扣过程的数据不一致风险**：  ① Redis 扣了但订单没生成（下单失败）→ 库存虚扣  ② Redis 扣了但 MQ 消息丢（异步落库失败）→ DB 库存没同步扣  ③ Redis 与 DB 库存数值漂移（对不上）
- **你的三层保证（代码实证）**：  ① 下单失败补偿：catch 里 increment 加回 Redis 库存 + delete 锁     （SeckillServiceImpl 注释"补偿Redis库存"）  ② MQ 兜底：本地重试表 seckill_message_retry + MessageRetryTask     每 5s 重发 ×3 → 异步落库不丢  ③ DB 条件扣减防超卖：消费者 SQL `seckill_stock >= #{quantity}`     → 即使 Redis 与 DB 不一致，DB 层也扣不出超卖的
- **企业级加强（面试讲）**：  ① 对账任务：定期比对 Redis 库存 vs DB 库存，差异自动修正  ② 库存预热校验：秒杀开始前 Redis 库存 = DB 库存（初始化对齐）  ③ Redis 高可用：主从+哨兵 = **✅ 已完成（2026-09-09 跨机部署，#9）** 老机主库 + 新机从库 + 3 哨兵；R1~R4 加固亦已完成（requirepass + AOF everysec + maxmemory 256mb volatile-lru）；实测选主 6.1s / 客户端 9.1s 自愈 / 数据零丢失  ④ 最终一致性认知：秒杀用"Redis 预扣 + DB 异步扣"是最终一致，     不是强一致；靠条件扣减兜底保证不超卖（宁可少卖不超卖）

【追问8】主从切换丢数据/MQ 挂了怎么办？（🔴 高可用深挖）
- **主从切换确实可能丢数据**（诚实）：主从复制是异步的，  主节点挂了瞬间最后几笔写没同步 → 从提升为主 → 这几笔丢了
- **库存 DECR 丢的例子**：5 台手机 6 人抢，Redis 预扣到 0 时主挂，  E 的 DECR 没同步（从节点库存还是 1）→ F 也抢到 → Redis 层面超卖 1 台  → 但 6 人订单异步落库时 DB 条件扣减 `stock >= 1`：前 5 个成功、  第 6 个（F）扣不动返回 0 行 → 订单失败 → **DB 只成交 5 台不超卖**  → "Redis 可能虚报、DB 永远准确"，宁可少卖不超卖

- 一句话：WebFlux = 响应式 Web 框架（编程模型），  Netty/Tomcat = 底层服务器（引擎），Gateway = 用 WebFlux 写的应用
- Netty：Java NIO 网络框架，事件驱动（boss/worker 事件循环），  非阻塞 I/O，只解决"高效收发字节"
- WebFlux：Spring 响应式 Web 框架（Reactor Mono/Flux），  **不是只能跑 Netty**——Tomcat/Jetty 也有响应式模式
- 传统 vs 响应式：Servlet = 一请求一线程阻塞（200 线程打满排队）；  WebFlux = 少量线程（核数×2）事件回调不排队；  **非阻塞 ≠ 更快 = 同样线程扛更多并发**，且全链路都得非阻塞
- ⭐ 你的生产网关实测：响应式 ✅（Reactive 上下文日志实证），  但**引擎是 Tomcat 不是 Netty**（日志 "Tomcat started on 10087"  + 线程 http-nio-10087，无 Netty 服务器线程）——因为 starter-web  和 gateway 同时在 classpath，装配顺序 Tomcat 在前

- 话术："网关是响应式模型没错，但我实测过生产网关——两个服务器  都在 classpath 时 Spring Boot 选 Tomcat，所以我的网关底层是  Tomcat 响应式。这恰恰说明 WebFlux 是框架、Netty/Tomcat 是引擎"

- 网关能转 Dubbo 吗：不能——Gateway 是 HTTP 网关，Dubbo 是  TCP 二进制 RPC，协议不通；要 Dubbo 化只能换 ShenYu 或嵌  Dubbo consumer
- 话术："路由规则手写、目标地址 lb:// 走 Nacos + 负载均衡，  既安全又灵活；pms 直连是踩坑修复——product 的 Dubbo 应用名  撞了，根治是改名对齐 order（**已完成，#6** 实测 `mall-product-dubbo`）"
【追问5】TraceIdGlobalFilter 是什么？
- 是什么：全局过滤器（GlobalFilter = 所有请求都执行，大门保安；  GatewayFilter = 只对绑定路由的请求执行，楼层闸机）。逻辑 =  生成 8 位 traceId → 塞 X-Trace-Id 请求头 → 放行；order=-1000  最先执行。返回 Mono<Void
> = 异步处理完成，filter 不阻塞  （响应式形态，对比 Servlet 的 void 同步阻塞）
- 作用：全链路日志串联。下游服务（mall-common TraceIdFilter）  读请求头 → 写 MDC → 日志统一带 [traceId]（11 服务同格式），  报障拿一个 ID 全链路日志一次拉齐
- 边界（诚实点）：只覆盖 HTTP 链路——定时任务/MQ 消费者/  Dubbo provider 线程日志 [] 空（MDC 线程绑定）
- 和 SkyWalking：两套独立机制，ID 不同互不索引——X-Trace-Id  管日志检索，sw8 traceId 管拓扑/耗时；改进方向 = SW logback  集成把 sw8 写进日志（一行配置即可对号，优先级低）
- 话术："网关生成 traceId 塞请求头，服务读进 MDC，日志统一  [traceId]——排查拿一个 ID 串全链路；SkyWalking 是另一套，  一个管日志检索、一个管拓扑耗时"
【追问6】Netty / Tomcat / Jetty 有什么区别？企业用啥？
- 定位：Tomcat/Jetty = **Servlet 容器**（能跑 Spring MVC）；  Netty = **网络框架**（无 Servlet 概念，Dubbo/RocketMQ/ES  底层都是它）。线程模型：Servlet = 一请求一线程阻塞（默认  200）；Netty = 事件循环少量线程回调
- 资源：Jetty 最轻量（嵌入式）；Tomcat 最流行生态全（企业  默认）；Netty 性能上限最高但开发复杂
- Spring Boot 默认：MVC→Tomcat、WebFlux→Netty；生产主流 =  Tomcat 跑业务 + Netty 跑网关（混合是常态）
- 你的项目：11 业务服务 Tomcat + 网关 Tomcat 响应式 = **全家  Tomcat 家族**；Netty 只当转发客户端。够用吗：够——Tomcat  响应式同为非阻塞，瓶颈在下游不在引擎（Netty 优势要百万  连接/极高 QPS 才体现）
- 诚实点：SCG 官方不推荐带 starter-web（配置不干净，只为  knife4j）；要锁 Netty = 显式 NettyReactiveWebServerFactory  Bean（6 行）或删 starter-web——演示项目都不做，压测证实  瓶颈再说
- 话术："Tomcat/Jetty 是 Servlet 容器、Netty 是网络框架；  MVC 默认 Tomcat、WebFlux 默认 Netty；我项目全家 Tomcat，  Tomcat 响应式同为非阻塞，这个量级完全够"
【追问7】Netty 在项目里到底用在哪？未来怎么考虑？
- 真实使用（线程名服务器实证）：Web 服务器层 = 没有 Netty  （全家 Tomcat）；但 **Dubbo RPC、Nacos gRPC、网关转发**全是  Netty——一个进程里 Tomcat 和 Netty 并存各管一摊（网关：  入站 Tomcat http-nio-10087 接待 / 出站 Netty reactor-http-ep  转发）。结论：**Netty 是传输层事实标准，Web 服务器层是  Tomcat 的地盘**
- 未来考虑：网关引擎换 Netty / 业务 WebFlux 化——都要压测  证实瓶颈才做，演示项目不需要；**选型看场景，不是看热度**
- 话术："Netty 在我项目里其实无处不在——Dubbo 传输、Nacos  gRPC、网关转发都是 Netty，只是 Web 服务器层恰好是 Tomcat"
【追问8】SCG 转发机制是什么？（一条请求的完整旅程）
- 用"状态变化"追踪一个请求（GET /front/spu/list）：  ① 入站：Tomcat 接待（http-nio-10087 线程）     → 请求还在网关手里，没变  ② 路由匹配：/front/*
* 命中"mall-front"路由     → 确定目标 = lb://mall-front（地址还是服务名）  ③ 过滤器链：TraceIdGlobalFilter 加 X-Trace-Id 头...     → 请求头被改造（多了 traceId）  ④ 负载均衡：lb:// 解析——发请求时才去 Nacos 查 mall-front     实例，轮询选一个     → 目标从 lb://mall-front 变成真实 http://172.18.0.19:10004  ⑤ 转发：NettyRoutingFilter 用 WebClient（reactor-netty）     异步发出，不等响应（到了回调）     → 请求真正离开网关，发往下游  ⑥ 回传：下游响应经过滤器链，Tomcat 写回客户端     → HTTP 200 + JSON 回到用户
- 核心变化只有一处：**lb://服务名 →（Nacos 查实例+轮询）→  真实 IP:端口**——路由静态、地址动态
- 细节：**路径原样透传**——最终 URL = 真实前缀 +  /front/spu/list（网关默认不重写路径，除非配 StripPrefix，  你的项目没配）；且是"发请求时才"查 Nacos（延迟解析，  DeferringLoadBalancer 语义），不是路由匹配时就查
- 为什么用 WebClient 不用 RestTemplate：响应式应用线程不能  阻塞（RestTemplate 会堵死事件循环）；WebClient 非阻塞 +  支持流式（AI 的 SSE 流式输出靠它转发）
- 话术："一条请求进网关：Tomcat 接待 → 路由匹配定服务 →  过滤器改造（加 traceId）→ lb:// 解析成真实地址 → WebClient  异步转发 → 响应回 Tomcat 写回。核心是 lb://服务名变真实  IP，路由静态地址动态，全程异步非阻塞"
【追问9】响应式/非阻塞为什么性能好？如何体现？
- 响应式 = 数据像水流，订阅 + 回调 + 背压（Reactor：Mono 0-1  个 / Flux 0-N 个）；非阻塞 = 发起 I/O 不等线程，完成时事件  循环回调（Java NIO + Selector 多路复用）
- 为什么性能好（本质 = 少线程 + 少切换）：  ① 线程少：Servlet 200 线程（1MB 栈/个）vs 事件循环核数×2  ② 等 I/O 不占线程：阻塞模型线程 BLOCKED 空转；非阻塞发起     后释放，回调时再处理  ③ 无上下文切换：阻塞频繁 BLOCKED↔RUNNABLE，非阻塞几乎没有  ④ 无排队雪崩：线程打满新请求排队（吞吐天花板）；非阻塞     在途请求不受线程数限制  ⑤ 背压：下游慢自动减速
- 核心公式（面试加分）：阻塞吞吐上限 = 线程数 ÷ 单请求耗时。  200 线程 × 每请求等下游 200ms → 上限 1000 req/s，超过就  排队雪崩；非阻塞 8 线程能同时挂几千在途请求，吞吐由下游  决定（理论示例，非本人压测数据）
- 如何体现（你项目）：网关 ~16 个网络线程（12 Tomcat 入站 +  4 Netty 转发）扛全部请求；SCG 转发用 WebClient（非阻塞）  不用 RestTemplate（阻塞会堵死事件循环）
- 诚实边界：非阻塞 ≠ 更快（单请求延迟不降）；低并发无感  （QPS=10 时 Tomcat/WebFlux 没区别）；业务代码调阻塞 SDK =  全白搭（一个慢请求堵死事件循环，比 Servlet 更惨）；纯 CPU  计算无优势
- 话术："响应式 = 订阅回调 + 背压，非阻塞 = I/O 不等线程。  性能好的本质是少线程少切换：阻塞吞吐上限 = 线程数÷单请求  耗时。但我不吹——非阻塞不加速单请求，低并发没区别，  业务里调一个阻塞 SDK 反而全堵死"
### Q10. 全局一套中间件选型的逻辑是什么？（总结）🔴
【追问1】所有选型遵循什么原则？
【追问2】如果重新选，会换什么？
【追问3】生态一致是什么意思？好处和缺点？
【简答】核心原则：**生态一致（Spring Cloud Alibaba）+ 场景匹配 +可靠性优先 + 文档成熟**。
【深挖】
- **生态一致**：Nacos（注册+配置）+ Sentinel（流控）  + Seata（事务）+ Dubbo（RPC）都是 Alibaba 系，和 Spring  Cloud Alibaba 无缝集成（详见追问3）
- **场景匹配**：秒杀用 RabbitMQ（可靠优先），日志用  Kafka（吞吐优先），搜索用 ES（检索优先）
- **可靠性优先**：业务数据（订单/库存）用可靠消息 + 事务，  不用最终一致
- **会换什么**（诚实，2026-09-12 回填）：Redis 加集群（**✅ 已完成 2026-09-09**：主从 + 3 哨兵跨机，选主 6.1s / 自愈 9.1s / 零丢失）；ES 加 IK 持久化；  秒杀布隆替代 Set；Nacos 集群
- 面试话术："我的选型逻辑是**先看场景要什么，  再选生态里最合适的**——比如秒杀要可靠不要吞吐所以用  RabbitMQ，搜索要倒排索引所以用 ES，  每个选择都能说出为什么"
【追问1】所有选型遵循什么原则？
- ① **生态一致**：同一家族组件互相认识、开箱即用（见追问3）
- ② **场景匹配**：先看场景要什么再选——可靠用 MQ、  吞吐用 Kafka、检索用 ES、缓存用 Redis
- ③ **可靠性优先**：业务数据（订单/库存）要可靠消息 +  事务，不用"最终一致"凑合
- ④ **文档成熟**：踩坑少、资料全（Nacos/Sentinel/ES  都是，冷门组件再强也不碰）
- 话术："先看场景要什么，再选生态里最合适的，  每个选择都能说出为什么"
【追问2】如果重新选，会换什么？
- 诚实三换：Redis 加集群（主从+哨兵，防单点）**✅ 已完成（2026-09-09 跨机部署，实测选主 6.1s / 客户端 9.1s 自愈 / 数据零丢失）**；  ES 加 IK 持久化（历史踩坑：Docker 重建丢分词器）；  秒杀布隆替代 Set（百万级再换，现在数据量小）
- 不换的：Nacos/Sentinel/Seata 继续用（生态一致 +  无替代必要）；RabbitMQ 不换（场景匹配，量级没到）
- 话术："演示项目不做大改；真要升级先做  Redis 集群（**已完成 2026-09-09**）+ IK 持久化，其他等规模到了再说"
【追问3】生态一致是什么意思？好处和缺点？
- 意思：选中间件优先选同一家族（Alibaba 系），组件被设计  成"互相认识"——配置风格统一（spring.cloud.alibaba.*）、  一键 starter、版本同一 BOM 管、组件互操作零胶水  （Sentinel 规则存 Nacos、Seata 注册到 Nacos、  Dubbo 用 Nacos 当注册中心）
- 好处：  ① 集成成本低（最大）：组件互操作开箱即用  ② 版本兼容有保障：BOM 统一管，避开版本打架  ③ 心智模型统一：一套配置/文档/运维  ④ 踩坑经验可迁移：全家桶的坑社区都踩过  ⑤ 升级节奏一致
- 缺点（诚实）：  ① **供应商锁定**：换 Consul/Istio 要动一整套  ② **生态短板硬用**：生态弱的领域也得用（或偷偷换掉）  ③ 升级受制兼容矩阵（Spring Boot 3.2.5 等 SCA 2023.0.1.2）  ④ 自动配置黑盒化（踩过：Sentinel 数据源≠规则、     Seata filter 传递依赖锁坏版本）  ⑤ 技术视野单一
- 两种策略：生态一致（集成成本低但锁定）vs best-of-breed  （每块选最强但胶水多）——中小团队前者，大厂后者
- ⭐ 你的项目定位（诚实）：不是纯生态一致，是**生态为主 +  场景优先的混合**——Nacos/Sentinel/Seata/Dubbo 是 Alibaba  系；但 MQ 用 RabbitMQ（非 RocketMQ）、链路用 SkyWalking、  搜索用 ES、网关用 Spring 官方 Gateway——都是场景匹配  压过生态一致。**原则是死的，场景是活的**
- 话术："生态一致 = 同一家族组件互相认识、开箱即用，  集成成本最低；缺点也清楚：锁定、短板硬用、升级受制  兼容矩阵。我的项目不是纯生态一致——RabbitMQ/  SkyWalking/ES 都是场景匹配压过生态一致"
