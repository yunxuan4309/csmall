### Q1. 整个电商的完整业务流程？🔴
**追问1**：从用户浏览到收到商品，经历了哪些环节？
**追问2**：每个环节对应哪个服务？
**追问3**：浏览商品的数据模型？SPU/SKU 是什么意思？
**追问4**：密码怎么存的？BCrypt 是什么？
【简答】注册登录（SSO）→ 浏览商品（front/product）→ 搜索（search）→ 加入购物车（order）→ 下单（order）→ 支付（order+支付宝）→ 秒杀（seckill）→ AI 导购（ai）。
【深挖】
完整链路：
1. **注册/登录**：mall-sso 服务，BCrypt 加密密码，JWT 签发 token
2. **浏览商品**：mall-front 通过 Dubbo 调 mall-product 查 SPU/SKU
3. **搜索**：mall-search 查 ES 倒排索引
4. **购物车**：mall-order 的 oms_cart 表（纯 MySQL）
5. **下单**：mall-order 创建订单（省市区级联 + 收货地址）
6. **支付**：支付策略模式（支付宝沙箱 + 模拟支付）
7. **秒杀**：mall-seckill 完整链路
8. **AI 导购**：mall-ai 的 RAG 流水线
**追问3 答案（SPU/SKU）**：浏览商品查的是商品数据模型——  **SPU**（标准化产品，如"华为 Mate60 Pro"，标题/品牌/分类/组图  在 pms_spu）+ **SKU**（具体规格，如"256G 曜金黑"，价格/库存/  规格参数在 pms_sku），一对多。**为什么拆**：价格/库存/销量是  SKU 级、标题/组图/品牌是 SPU 级——不拆要么每条规格重复存  商品信息（冗余），要么没法按规格定价管库存。浏览链路 =  mall-front 通过 Dubbo 查 SPU + 关联 SKU 列表（详见 Q5）
**追问4 答案（BCrypt）**：密码不存明文也不"加密"——存的是  **BCrypt 哈希"指纹"**（单向不可逆）。哈希 vs 加密：加密可逆  （要密钥）、哈希不可逆（数据库泄露也拿不到密码）。BCrypt 三  特点：内置随机盐（相同密码哈希不同，防彩虹表）+ 故意慢  （~100ms 防暴力破解）+ cost 可调。校验：注册 encode(明文)  存库、登录 matches(明文, 库里哈希) 取盐重算对比，全程无  解密（UserSSOServiceImpl L46 实证）。企业级：BCrypt 是行业  标准（Spring Security 默认），更严格可换 Argon2id；哈希只是  第一层（详见 Q2 / 06-Q1 / 认证安全方案）
- 面试话术："每个环节是独立服务，通过 Dubbo/RPC 协作，  这个链路完整覆盖了电商的核心场景"

### Q2. 登录认证是怎么实现的？JWT 流程？🔴
**追问1**：JWT 结构？
**追问2**：token 失效/登出怎么处理？
**追问3**：HS512 签名/密钥长度/过期时间怎么定的？
**追问4**：JWT 和单点登录（SSO）什么关系？为什么不用 Session？
【简答】用户登录 → SSO 服务验证 BCrypt 密码 → 签发 JWT → 前端存 localStorage → 请求带 Authorization 头 → 各服务 SSOFilter 校验。
【深挖】
- **JWT 结构**：Header（算法） + Payload（  用户信息、过期时间） + Signature（签名）
- **签发**：SSO 服务用 `JwtTokenUtils` 生成：  `Jwts.builder().claims(...).expiration(now+7天)  .signWith(hmacShaKeyFor(密钥), Jwts.SIG.HS512)`
- **HS512 签名**（追问3）：HMAC-SHA512——同一个对称密钥  签/验，512 = SHA-512 输出 64 字节；微服务内部统一信任域  用 HS512 简单快（对比 RS256 非对称适合跨信任域）
- **密钥 ≥64 字节**：HS512 要求 512 位密钥，JJWT 0.12 严格  校验，短了抛 WeakKeyException（0.9→0.12 升级坑：9 模块  密钥全换 69 字节）；项目默认 CooxiaoMall2026...Long  （≈69 字节），生产用 JWT_SECRET 环境变量覆盖（诚实点：  演示用固定值，生产应换随机强密钥）
- **过期时间**：`jwt.expiration: 604800` = **7 天**，生成  `new Date(now + expiration*1000)` 写进 exp；校验时 JJWT  自动检查，过期抛 ExpiredJwtException → 401。服务器实证：  front 日志真实 JWT exp-created ≈ 604800 秒（前端  VITE_TOKEN_EXPIRATION 对应）
- **JWT vs Session**（追问4 简述）：Session 有状态（服务端  存、多实例要粘性会话或 Redis 集中存、跨服务共享难）；  JWT 无状态自包含，任何实例验签即用 → 适合微服务水平  扩展。代价：无法主动失效 → 登出靠 Redis 黑名单。  完整对比见 06-Q2
- **JWT vs SSO**（追问4）：JWT = 令牌技术（凭证+验签机制）；  SSO = 认证架构（一次登录全系统通行，目标）。你的  mall-sso = 统一认证中心（SSO 形态）+ JWT 令牌：登录一次  签发 JWT，所有服务验签即用。诚实边界：这是 SSO 的  "同域轻量形态"，企业级跨系统 SSO 用 CAS/OIDC
- **校验**：各服务 `SSOFilter` 从   Authorization 头取 token，解析用户信息放入   SecurityContext
- **登出**：token 加入 Redis 黑名单（  `token_list_.lock`），校验时查黑名单
- **双 token**：前台 `mall_token`，后台   `admin_token`，区分用户/管理员
- **坑**：Bearer 前缀截取后要 `.trim()`（JJWT   0.12 严格校验前导空格）；HS512 密钥要 ≥64 字节
- **BCrypt 是什么**（密码存储）：哈希不是加密——  加密可逆（要密钥），哈希不可逆（永远还原不了）。  库里存的是"密码指纹"不是密码。BCrypt 特点：  ① 单向不可逆 ② 内置随机盐（相同密码哈希不同，  防彩虹表）③ 故意慢（~100ms，暴力破解成本高）  ④ 自适应（cost 可调）
- **校验流程**（代码实证）：注册 `encode(明文)` 存库；  登录 `matches(明文, 库里哈希)` —— BCrypt 从库里哈希  串取出盐，用"输入密码+盐"重算后对比，全程无解密  （UserSSOServiceImpl L46 / AdminSSOServiceImpl L52，  10 服务统一 BCryptPasswordEncoder）
- 面试话术："JWT 是无状态认证——服务端不存 session，  通过签名校验，适合微服务水平扩展。登出用 Redis 黑名单解决   JWT 无法主动失效的问题。密码存 BCrypt 哈希——单向不可逆，  数据库泄露也拿不到密码"

### Q3. 支付是怎么实现的？策略模式？🔴
**追问1**：策略模式怎么用的？
**追问2**：模拟支付和真实支付怎么切换？
【简答】支付用**策略模式**：`PaymentStrategy` 接口 + `PaymentStrategyFactory` 工厂自动收集实现类 + `AlipaySandboxStrategy`（支付宝，含 simulated 模拟模式）。`alipay.simulated` 开关切换。
【深挖】
- **策略模式**：定义 `PaymentStrategy` 接口（4 个方法：  `getPaymentType` 标识类型 / `initiatePayment` 发起支付 /  `handleCallback` 处理异步回调验签 / `queryPayment` 主动查单），  主流程只认识接口，不认识具体支付渠道
- **工厂自动收集**（代码实证）：`@Autowired List<PaymentStrategy>`  Spring 自动收集所有实现类 → `@PostConstruct` 按  `getPaymentType()` 注册进 ConcurrentHashMap → `getStrategy(type)`  取策略，没有就抛"支付渠道 [xx] 暂未实现"
- **设计原则（面试必考，就是这个题目的名字）**：**依赖倒置（DIP）**  ——高层（OmsOrderServiceImpl）只依赖 `PaymentStrategy` 抽象，  不依赖具体实现（"上流不依赖下流业务"）；同时是**开闭原则  （OCP）**——对扩展开放（新增渠道 = 新实现类）、对修改关闭  （主流程零改动）。统称 **SOLID 五原则**（S 单一职责 / O 开闭 /  L 里氏替换 / I 接口隔离 / D 依赖倒置）
- **SOLID 速查**（面试可能让逐个展开）：  S 单一职责 = 一个类只干一件事（JwtTokenUtils 只管 JWT）；  O 开闭 = 加功能靠加代码不改代码（PaymentStrategy 加微信    零改动主流程）；  L 里氏替换 = 实现类必须能替换接口用且行为一致（所有    PaymentStrategy 实现都返回 PaymentResult）；  I 接口隔离 = 接口要小别塞用不到的方法（PaymentStrategy    只 4 个方法，没塞退款/对账）；  D 依赖倒置 = 高层依赖抽象不依赖实现（主流程只认接口）  记忆：单开里接依
- **不用策略模式会怎样**：`if (type==1) 支付宝... else if  (type==2) 微信...` 散落在业务代码，加支付方式 = 改业务代码 +  引入 bug 风险
- **接入微信的完整流程**（演示开闭）：写 WechatPayStrategy  implements PaymentStrategy（实现 4 个方法）→ 加 @Component →  Spring 自动收集进工厂 Map → 前端传微信 code → 主流程不用改  （诚实点：微信策略是 TODO #4 未实现，已实现只有  AlipaySandboxStrategy 一个，simulated 是它内部模式）
- **切换**：`application.yml` 配 `alipay.  simulated: true/false`，  改配置重启即可切换，代码不用动
- **支付宝沙箱**：签名验签 + 查单全链路，`page.  pay` 方式
- **支付流水**：`oms_payment_record`   表记录每笔支付（可追溯）
- **模拟支付**：跳过支付宝 API，直接更新订单状态为"已支付"，  `tradeNo=SIMxxxxxx`
- **真实情况**：支付宝沙箱前端支付页有 bug（JS 兼容性 +   内网资源泄露），走不通，所以用模拟模式兜底
- **为什么没有真实支付（诚实三层）**：  ① **资质门槛（最根本）**：真实支付要企业商户签约     （营业执照 + 支付宝开放平台入驻），个人项目拿不到  ② **沙箱也走不通**：支付页 bug + 踩过空密钥坑（.env     密钥为空 → SDK 初始化崩溃 → 修复为自动检测空密钥     切模拟模式）  ③ **演示定位**：模拟支付展示的是支付流程的代码结构     （策略模式/流水表/状态流转），不是真扣钱
- **simulated 怎么工作**（代码实证）：OmsOrderServiceImpl  判断 `paymentForm==null && paymentUrl==null` → 模拟策略  不返回支付表单 → 直接置"已支付"+ 流水 tradeNo=SIMxxxxxx；  真实策略返回表单 → 状态 PENDING → 等回调
- **以后怎么切真实**：签约后改 `alipay.simulated: false`  即可，代码不用动——这就是策略模式的价值（TODO #5）
- 面试话术："支付用策略模式是为了**可扩展**——以后加微信支付，  只要实现 PaymentStrategy 接口，不用改主流程"

### Q4. 购物车怎么实现的？
【追问1】购物车存哪？Redis 还是 DB？
【追问2】秒杀有购物车吗？和普通购物车什么关系？
【简答】购物车在 mall-order 服务，**纯 MySQL** `oms_cart` 表（无 Redis）。秒杀**没有购物车环节**——秒杀商品不进普通购物车，走独立流程。
【深挖】
- **普通购物车**：oms_cart 表存商品 + 数量 + 用户，纯 MySQL
- **接口**（OmsCartController，5 个全需登录）：add 加购 /  delete 删除 / delete-all 清空 / update-quantity 改数量 /  list 分页查询
- **表结构亮点**：title/picture_url/price/data(JSON) 全是  **商品快照冗余**（购物车列表直接展示，免 JOIN 商品表——  03 冗余字段的实例）；`UNIQUE KEY uk_user_sku(user_id,sku_id)`  ——同用户同 SKU 只一条，重复加购 = 数量累加
- **下单衔接**（代码实证）：创建订单时遍历订单项 → 按  userId+skuId 调 removeUserCarts() 删除已下单商品——前端  勾选 → 传 OrderItemAddDTO → 下单成功后自动清购物车
- **为什么不做 Redis 缓存**（评估）：购物车是"写多 + 不可丢 +  用户天然分片"的数据——缓存适合读多写少可丢失（商品详情），  购物车丢了 = 用户体验事故；MySQL 按 user_id 索引查询毫秒级，  你的量级（单用户操作）完全扛得住。企业用 Redis 主要是  **游客购物车**（TTL 天然适合）和海量用户场景，量级到了再上  （演进方案见 TODO #18）
- **快照要不要"更新"**（面试必考）：按字段性质分——**低频稳定  字段（标题/图/品牌名）= 快照 + 不更新**；**高频变动字段  （价格/库存/下架）= 不更新快照，展示层实时取**（拼多多购物车  价格实时变 = 列表查询时取最新价，不是"更新快照"——更新快照  要改 1 万行引用记录，成本高还有延迟窗口）
- **快照不是彻底冗余，三大价值**：  ① **免跨库 JOIN**：购物车(order库)和商品(product库)分库，     跨库 JOIN 不可能 → 快照让列表一条 SQL 自包含，不用每次     Dubbo 调商品服务  ② **降级兜底**：商品服务挂了购物车还能显示（价格旧但能看）——     展示价格策略 = 优先实时查 → 失败回退快照（标"参考价"）  ③ **历史凭证**：data JSON 存加购时点规格；订单快照必须定格     （凭证，改了 = 篡改）
- **"列表实时价覆盖"可行性**（评估）：高——listCartByPage 查完  快照 → 收集 skuId → 一次 Dubbo 批量查当前价 → 覆盖展示 →  失败回退快照（~20 行 + 一个批量查价接口，拼多多式体验标准  做法）。但演示项目优先级低：**先做 TODO #19（结算价服务端  重算，管"钱"）再做这个（管"展示"）**
- **购物车快照 vs 订单快照**（关键区分）：购物车快照 = 展示  辅助，可实时；**订单快照（oms_order_item 的 title/price）=  法律凭证，必须定格**——改了 = 篡改订单金额。快照的"历史  一致性"价值主要在订单
- **你的现状**（诚实）：购物车快照仅展示用，演示量级接受短暂  过期；但**结算价来自前端传入（无服务端重算）**——防篡改 +  改价同步要补（TODO #19）；订单快照绝不更新
- **秒杀为什么没购物车**：秒杀页选 SKU 直接提交（随机码 + 限购），  不经过购物车——限购一个用户一件，"攒着一起买"的场景不存在  （代码实证：seckill 模块无任何 cart 相关代码）
- **面试话术**："购物车是电商的基础功能，  重点是**秒杀和普通购物流程要分离**——秒杀有限购和随机码，  没有购物车环节，直接下单。购物车我刻意不用 Redis——写多  不可丢的数据，MySQL 按用户分片毫秒级够用，缓存反而引入  双写一致性问题"

### Q5. 商品模块的数据模型？SPU/SKU 是什么？🔴
**追问1**：SPU 和 SKU 区别？
**追问2**：规格怎么存储？
【简答】SPU（Standard Product Unit）是标准化产品（如"华为Mate60"），SKU（Stock Keeping Unit）是具体规格（如"256G 黑色"）。一对多关系。
【深挖】
- **SPU**：商品主体（名称、标题、品牌、分类、组图），  pms_spu 表
- **SKU**：具体规格（价格、库存、规格参数），pms_sku 表
- **为什么拆两层**（面试重点）：价格/库存/销量是 **SKU 级**  （256G 和 512G 价格库存不同）；标题/描述/组图/品牌是  **SPU 级**（共用不重复）。不拆 = 要么每条规格重复存  商品信息（冗余），要么没法按规格定价管库存
- **例子**：SPU = "华为 Mate60 Pro"；SKU = "256G 曜金黑"、  "512G 白沙银"
- **规格**：pms_sku_specification 存规格，  属性模板（attribute_template）定义规格维度
- **品牌/分类**：pms_brand、pms_category，  SPU 冗余了 brand_name/category_name
- **相册**：pms_album/pms_picture 表 + AlbumController/  PictureController 后端**已就绪**（TODO 只缺前端管理页面，  不是"预留"）；SPU 组图用 SPU.pictures JSON 存相对路径
- 面试话术："SPU 是'这个产品是什么'，SKU   是'哪个具体规格能买'，电商标准模型。我的项目 SPU   冗余了品牌名、  分类名，是空间换时间的经典设计"

### Q6. 后台管理做了什么？RBAC 权限？
**追问1**：管理员/角色/权限三级？
**追问2**：权限怎么校验？
【简答】后台（mall-ams）提供商品/订单/用户/权限管理，RBAC 三级模型：管理员→角色→权限，接口用权限码校验。
【深挖】
- **RBAC**：ams_admin（管理员）→ ams_role（  角色）→ ams_permission（权限码），多对多关联
- **校验**：Controller 方法注解**权限码**——后台管理用  `@PreAuthorize("hasAuthority('/ams/admin/read')")`  （URL 风格权限码，/ams/admin/read、/pms/product/update  等）；C 端用角色 `@PreAuthorize("hasRole('user')")`。  SSOFilter 解析 JWT 里的 authorities 放进 SecurityContext
- **知识点**：`hasRole('user')` ≡ `hasAuthority('ROLE_user')`  ——hasRole 自动加 ROLE_ 前缀（代码注释实证）；项目是  **"后台权限码 + C 端角色"双模型混用**
- **C 端/B 端是什么**：C 端 = Consumer 消费者端（用户逛商城的前台：/front 页面 + /seckill/**、/oms/** 用户接口）；B 端 = 商家管理端（/admin 后台 + /ams/**、/pms/** 管理接口）
- **双模型详解**（面试必考）：同一套 Spring Security 两种粒度  按场景混用——C 端权限简单（登录了就能买东西）→ 单角色  `hasRole('user')`（本质=已登录判断）；后台权限复杂（运营/  客服/超管权限不同）→ 三级 RBAC + 权限码 `hasAuthority  ('/ams/admin/read')` 细粒度到"能读/能写/能删"。**没有一种  模型通吃：简单场景简单模型，复杂场景复杂模型**
- **服务器实证**（JWT authorities）：用户 token = ["ROLE_user"]；  管理员 token = ["pms:manage","oms:order:list","/ams/admin/  read","/pms/product/update",...]——单角色 vs 权限码列表
- **诚实点**：管理员权限码两种风格并存（旧冒号式 pms:manage +  新 URL 式 /ams/admin/read）——历史遗留。**核实结论：冒号式  代码 0 引用**（104 处 @PreAuthorize 全 URL 式、前端无权限  判断）= 死数据 → 建议**直接清理**（Flyway 删死码 + 清  role_permission 关联），不是迁移（改了也没人用），见 TODO #20
- **后端接口**：商品 CRUD、订单管理、用户管理、  角色分配、权限配置
- **面试话术**："RBAC 是标准的权限模型——**用户挂角色，  角色挂权限**，这样权限配置灵活，新用户只要分配角色就继承了权限"

### Q7. 前台和后台是怎么区分的？
【追问1】前端两套系统？
【追问2】API 怎么分开？
【追问3】mall-front 模块有什么用？为什么这么设计？
【简答】前台（C端用户）+ 后台（管理员）两套前端，走不同 API。后台用 admin_token 认证，权限更严格。
【深挖】
- **前端**：csmall-vue 一个项目，前台页面（/front）  + 后台页面（/admin）分开路由
- **Token**：前台 mall_token，后台   admin_token，请求拦截器区分
- **Gateway**：生产环境后台管理服务不对外（  `application-prod.yml` 只暴露前台必需路由）
**追问3 答案（mall-front = BFF）**：mall-front 是前台浏览  专用门面，本质是 **BFF（Backend for Frontend）模式**——  只读（4 个 Controller 全查询）、无数据库、纯 Dubbo 聚合  product 的 SPU/SKU/分类/属性，裁剪成前台 VO。设计理由：  ① **接口隔离**（前台摸不到 /pms/** 管理接口，读写分离）  ② **聚合裁剪**（前端不用关心微服务拆分）  ③ **独立演进**（前台改版/扩容不影响商品服务）  原则 = BFF + 门面模式 + 接口隔离（ISP）
- **轻量 BFF 三个差距**（面试深挖点，TODO #21）：  ① **无缓存层**：商品详情是"读多写少"热点，企业 BFF 配     Redis Cache Aside（首查 DB 回填，后续命中缓存）；     你的项目无商品缓存（18 条商品毫秒级，量级没到）     ——类比：前台放畅销书样书，不用每次去仓库翻  ② **串行 Dubbo 调用**：组装详情 VO 依次查 SPU→SKU→分类     →属性，延迟 = 4 次之和；企业用 CompletableFuture 并行     （延迟 ≈ 最慢一次）或聚合 RPC     ——类比：串行 = 一个人跑 4 个办公室盖章  ③ **单实例无独立扩容**：企业 BFF 无状态可水平扩展、按     前台流量弹性扩；你单机单实例（内存剩 2G、CPU<5%，     场景不匹配不是不会扩）  共同结论：**"量级到了再上"，选型看场景**
- 面试话术："前后台共用后端微服务，但**认证体系分开**（用户   token vs 管理员 token），  后台接口在网关层就不对外开放，  安全边界清晰。mall-front 是 BFF——前台只读门面，  接口隔离 + 聚合裁剪。三个企业级差距我也清楚：缓存  Cache Aside、并行聚合、独立扩容——量级到了再上"

### Q8. 订单状态流转？
【追问1】订单有哪些状态？
【追问2】超时未支付怎么处理？
【追问3】超时瞬间用户支付了怎么办？（竞态）
【追问4】超时关单用悲观锁还是乐观锁？
【追问5】真出现"已支付但已关单"怎么补救？
【简答】订单状态：0未支付 → 1已关闭（超时） / 3已支付 → 4已签收。秒杀有"未支付拦截"（ordered key）。
【深挖】
- **状态枚举**：0未支付、1已关闭、2已取消、3已支付、4已签收、  5已拒收、6退款处理中、7已退款
- **超时未支付**：秒杀场景用 Redis ordered key   拦截——有未支付订单不能再下单同 SKU
- **支付后**：更新订单状态 + 写支付流水 + 标记秒杀已购买（  reseckill）
**追问3 答案（竞态分析）**：现状诚实——**超时自动关单未实现**  （状态机预留 1=已关闭，无触发代码；TODO #11 评估过 ZSET  延迟队列），且支付更新是**无条件 updateOrderById setState(3)  （无 WHERE state=0）**→ 竞态当前不存在（因为没关单动作），  但订单会永久挂"未支付"
- **企业四道防线**（做超时关单必须配套）：  ① **条件更新（CAS，核心）**：关单和支付都     `UPDATE ... WHERE state=0`——原子互斥谁先谁赢，     后执行 rows=0：先关后付 → 退款；先付后关 → 关单失败  ② **回调先查状态**：已关闭 → 直接退款不入账（配合 ①）  ③ **关单幂等**：ZSET ZREM 天然防重复 + 关单前再查支付状态  ④ **对账兜底**：扫"已支付但已关闭"订单 → 修正/退款
**追问4 答案（锁怎么选）**：**关单不需要显式锁**——  条件更新（WHERE state=0）本身就是**乐观锁思想**（state 当  版本号），单条 UPDATE 数据库原子。对比：悲观锁  （SELECT FOR UPDATE）= 先锁行再做（适合多步骤读-改-写、  冲突频繁；缺点串行化+死锁管理）；乐观锁（version 字段）=  改时校验版本（适合写冲突少、并发高；条件更新是它的简化）。  关单=单条 UPDATE → 条件更新够用，用悲观锁是杀鸡用牛刀；  关单逻辑复杂才需要 Redis 分布式锁（ZSET ZREM 已防重复）
**追问5 答案（已支付关单补救六步）**：  ① **检测**：对账/告警扫"支付流水存在 + 订单已关闭"冲突  ② **核实**：查 oms_payment_record——钱真到了吗（tradeNo     真实、金额匹配、渠道验签）  ③ **处置**：确认真实支付 → **自动退款**（调支付渠道退款     接口 + 记录退款流水 + 订单标"关闭待退款"；或按业务     恢复已支付）  ④ **通知**：告知用户"订单已关闭，款项原路退回"  ⑤ **复盘**：修根因（条件更新漏配/竞态窗口）  ⑥ **对账**：每日三面对齐（渠道账单 vs 支付流水 vs 订单状态）  核心原则：**钱错了必须原路退回，不能收了钱不给货**
- **面试话术**："订单状态是业务核心，  秒杀场景对'未支付'有专门拦截——防止用户占着库存不买还反复下单。  超时关单的竞态我知道：核心是条件更新 WHERE state=0 原子互斥，  先关后付自动退款，先付后关关单失败，再加对账兜底"

### Q10. 秒杀和普通下单的区别？为什么要单独一个服务？🔴
【追问1】秒杀服务和订单服务什么关系？
【追问2】秒杀订单和普通订单都存哪？
【简答】秒杀单独 mall-seckill 服务，因为它有独立的高并发逻辑（限流/预扣/异步），和普通下单流程不同。但最终订单都存 oms 库。
【深挖】
- **为什么单独服务**：秒杀是**极端高并发 + 限购 +   抢购**场景，需要独立扩容、独立限流，不能影响普通下单
- **关系**：秒杀服务通过 Dubbo 调 order 服务创建订单（  复用订单逻辑），订单存 oms_order 表
- **秒杀特有**：随机码、预扣库存、限购（一个用户一件）、异步落库
- 面试话术："秒杀单独服务是因为它**峰值流量是平时的几十倍**，  如果和普通下单混在一起，秒杀一波动就拖垮整个订单服务。  所以秒杀独立服务 + 独立限流，通过 Dubbo 调 order   复用订单逻辑"
