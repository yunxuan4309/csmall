### Q1. 为什么选择微服务架构，而不是单体？🔴
**追问1**：你分成了哪些服务？拆分依据是什么？
**追问2**：微服务的缺点你知道吗？你这个项目有没有遇到？
【简答】电商业务复杂（商品/订单/秒杀/搜索/AI），单体应用在多人协作、独立部署、技术异构上有瓶颈。微服务按领域拆分，独立开发部署，故障隔离，可独立扩缩容。
【深挖】
- **11 个服务**：mall-product（商品）、mall-order（订单）、mall-seckill（秒杀）、mall-search（搜索）、mall-ums（用户）、mall-ams（管理员）、mall-resource（资源/文件）、mall-ai（AI导购）、mall-sso（登录）、mall-gateway（网关）、mall-front（前台聚合）
- **拆分依据**：按**业务领域**（DDD 思想）  ——商品/订单/秒杀各自独立，因为它们是不同的业务域，变化频率不同
- **数据库独立**：每个服务有自己的库（  cs_mall_pms/oms/ums/ams/seckill/resource  ），不共享表，这是微服务的核心特征
- **mall-front 的作用**（前台聚合模块 / BFF）：  端口 10004，**本身不连数据库**，是纯   Dubbo 消费者   + 薄代理。它通过 `@DubboReference` 消费   mall-product 的 4 个接口（  `IForFrontSpuService` /   `IForFrontSkuService` /   `IForFrontCategoryService` /   `IForFrontAttributeService`），把 C   端页面需要的商品数据（SPU 列表/详情、SKU、规格属性、  三级分类树）打包成 HTTP API（  `/front/spu/**`、  `/front/category/**`）暴露给前端。  为什么需要它：  
1. **接口定制化**：mall-product 是内部服务，     接口为后台管理/订单/秒杀多端设计，字段多而杂；mall-front      做裁剪和组合，只暴露前台要的精简视图  
2. **解耦，稳定前台契约**：前端只依赖 mall-front 的      HTTP 契约，mall-product 内部改接口只要      mall-front 不变，前端零感知  
3. **职责单一**：无 Mapper、无业务逻辑，一个方法就是一行      `dubboSpuService.xxx()` 转发，真正的实现（     分页、图片 URL 拼接、缓存）都在提供者一侧；     以后加缓存/组合逻辑放这层很干净  
4. **与 Gateway 的区别**：Gateway 在网络层（     路由/统一认证/CORS/限流），是客户端第一道入口；     mall-front 在业务层（视图聚合/字段裁剪），两者不冲突  
- 注意：它目前只聚合了商品域（product 一个提供者），定位是"C     端的统一业务门面"，未来可扩展聚合搜索/AI 等
- **缺点与应对**：  
- 服务间通信开销 → 用 Dubbo RPC（比 HTTP 快）  
- 分布式事务复杂 → 引入 Seata  
- 运维复杂 → 用 Docker Compose 统一管理  
- 链路追踪难 → 引入 SkyWalking  
- 面试加分话术："我知道微服务不是银弹，对这个体量单体也能跑，    但**微服务的价值在于团队协作、独立部署和未来的水平扩展**，    同时我也用了 Seata/SkyWalking/Docker     解决了微服务带来的问题"**

**各模块定位速查（速记）**：

| 模块 | 端口 | 一句话定位 | 备注 |
|------|------|-----------|------|
| mall-gateway | 10087 | 入口网关 | 路由/认证/CORS/限流，WebFlux |
| mall-sso | 10009 | 统一认证 | 管理员+用户两套 JWT 签发 |
| mall-product | 9010 | 商品域 | **唯一 Dubbo 提供者(7 接口)**，最重 |
| mall-front | 10004 | 前台聚合/BFF | 无库，纯消费者，为 C 端裁剪视图 |
| mall-order | 10005 | 订单域 | 支付宝策略模式 + MQ 扣库存 |
| mall-seckill | 10007 | 秒杀域 | Redis 预扣+Sentinel+MQ+Seata |
| mall-search | 10008 | 搜索域 | ES，技术异构 |

**记忆口诀**：入口两个（gateway/sso），中央一个（product），交易一条链（seckill→order），异构两块（search/ai），支撑三个（ums/ams/resource），前台一个门面（front）。

### Q2. 为什么用 Dubbo 而不是 Feign/OpenFeign？🔴
**追问1**：Dubbo 和 Feign 的核心区别是什么？
**追问2**：Dubbo 的通信协议是什么？性能好在哪里？
【简答】Dubbo 是高性能 RPC 框架，默认 Netty + 自定义协议（Dubbo 协议），长连接 + 连接复用，性能优于 Feign（HTTP + 短连接 + Tomcat 线程）。且 Dubbo 自带负载均衡、集群容错、服务治理。
【深挖】
- **核心区别**：  
- Feign：HTTP 协议，走 Tomcat/Netty HTTP，    **短连接**，JSON 序列化，面向 HTTP REST 风格  
- Dubbo：自定义协议，**长连接 + 连接复用**，二进制序列化（    Hessian2），面向 RPC 内部调用
- **性能差距**：长连接省去每次 HTTP 握手开销；二进制序列化比   JSON 小且快
- **你的项目实际情况**：mall-product 是核心   Dubbo **提供者**（7 个接口），  mall-front/order/search/seckill/ai   是**消费者**。跨服务调用走 Dubbo，前端访问走   Gateway HTTP
- **面试话术**："内部服务间调用用 Dubbo（追求性能、长连接），  对外暴露用 Gateway（HTTP），这是微服务常见架构"

### Q3. 网关（Gateway）的作用是什么？为什么需要它？🔴
**追问1**：你的网关做了哪些事？
**追问2**：认证是在网关做还是每个服务做？
【简答】API 网关是微服务的统一入口，负责**路由转发**、**统一认证**、**统一鉴权**、**跨域处理**、**限流**。客户端只跟网关通信，不直接访问各服务。
【深挖】
- **你项目的网关职责**：  
- **路由转发**：按路径前缀路由到对应服务（    `/product/**` → mall-product，    `/seckill/**` → mall-seckill）  
- **统一认证**：网关校验 JWT Token，    把用户信息放入请求头传给下游  
- **统一 CORS**：跨域在网关统一处理，避免各服务重复配置  
- **路由白名单**：生产环境只暴露前台必需服务，后台管理服务不对外
- **认证是网关做还是服务做**：你的项目是**网关 +   各服务双重校验**——网关做入口认证，各服务（Spring   Security + SSOFilter）再做一次校验，双保险。  面试话术："网关负责入口认证拦截，各服务用   SecurityContext   获取当前用户做业务级权限校验，防御纵深"
- **细节**：`application-prod.yml` 配置了   9 条手动路由（`locator.enabled:   false`），  生产只暴露前台服务

### Q4. 服务间如何通信？Dubbo 调用链是怎样的？
**追问1**：画出你的 Dubbo 调用拓扑
**追问2**：Dubbo 注册中心用的什么？服务发现机制？
【简答】服务间通过 Dubbo RPC 通信，Nacos 做注册中心。mall-product 提供 7 个 Dubbo 接口，其他服务作为消费者调用。
【深挖】
- **调用拓扑**：  

```
mall-product(提供者) ← mall-front / mall-order / mall-search / mall-seckill / mall-ai
```
- **核心接口**：IForFrontSpuService（前台SPU）  、IForOrderSkuService（订单扣库存）、  IForSeckillSpuService（秒杀SPU）、  ISpuSyncService（商品同步ES）
- **注册中心**：Nacos，提供者启动时注册服务 + IP +   端口，消费者订阅服务列表，实现服务发现
- **负载均衡**：Dubbo 默认加权随机，支持轮询、一致性哈希等
- **失败容错**：Dubbo 默认 failover（  失败重试其他节点），可配 failfast
- **面试话术**："提供者注册到 Nacos，消费者订阅，通过   Dubbo 的长连接池复用连接，比每次 HTTP   请求都握手快得多"
**追问3：Nacos 和 Dubbo 是怎么协作的？  有没有先后顺序？**
- **整体定位**：Nacos = 中介/电话号码簿，  只帮你"找到对方在哪"；Dubbo = 直接打电话，  实际通信是双方直连，**不经过 Nacos**
- **完整时序**（有先后顺序）：  
1. **提供者先启动** → 向 Nacos 注册（接口名 +      IP + 端口）  
2. **消费者后启动** → 向 Nacos 订阅（声明要哪些接口），     Nacos 推送当前服务列表  
3. **消费者缓存**服务列表 → 之后调用**不每次问 Nacos**  
4. **调用时**：消费者从本地缓存选一台（负载均衡）→ Dubbo      长连接**直连**提供者（Nacos 不在场）  
5. **变更通知**：实例增减 → Nacos 主动推送给订阅者 →      更新本地缓存
- **所以有先后顺序**：提供者先注册、消费者后订阅 → 这就是为什么   product 必须**最先启动**
- **追问：Nacos 挂了会怎样？**   已建立连接的消费者继续用**缓存的服务列表**，  已建立的调用不受影响；  但新服务无法注册、新消费者无法发现 →   扩缩容/重启场景出问题。单机   Nacos 无集群高可用，是学习项目边界
- **追问：为什么提供者必须先启动？** ① 消费者启动时 Dubbo   有 `reference check`，检查依赖服务是否可用，  提供者没注册会导致启动失败或告警；②   消费者立即发起调用会找不到目标。  部署时 product 先起，再起 5 个消费者

### Q5. 服务拆分后，数据一致性怎么保证？（引出 Seata）
**追问1**：Seata 的 AT 模式原理？
**追问2**：什么是分布式事务？本地事务为什么不行？
【简答】跨服务调用涉及多个数据库，本地事务无法保证。用 Seata AT 模式（`@GlobalTransactional`）实现分布式事务，通过全局事务协调 + 分支事务 + undo_log 回滚保证最终一致。
【深挖】
- **为什么本地事务不行**：`commitSeckill` 里   Dubbo 调用 mall-order 创建订单，
- 两个服务各自操作自己的库，mall-seckill   的本地事务控制不了 mall-order 的数据库
- **AT 模式原理**（两阶段提交）：  
1. **一阶段**：各分支事务正常提交，同时记录      undo_log（数据快照）  
2. **二阶段**：全局事务协调者（TC）判断是否全部成功     
- 全部成功 → 删除 undo_log     
- 有失败 → 根据 undo_log 反向补偿回滚
- **关键组件**：TC（事务协调者，Seata Server）、TM（  事务管理器，发起方）、RM（资源管理器，参与方）
- **你的项目**：`@GlobalTransactional`   标注在秒杀提交方法上，扣库存（seckill）+ 建订单（  order）  组成一个全局事务
- **追问可能**："AT 模式会锁全局记录吗？" → AT   默认**全局读已提交 + 写隔离**（用全局锁），比 XA   的同步阻塞更高效
**追问3：Seata 有哪几种模式？为什么选 AT？**
- **4 种模式**：AT（自动，undo_log 快照回滚）/   TCC（手写 Try/Confirm/Cancel）/ SAGA（  状态机+逆向补偿，长事务）/
- XA（数据库级两阶段，同步阻塞）
- **为什么选 AT**：  
1. **无侵入**：业务只加      `@GlobalTransactional` 注解，框架自动拦截      SQL 生成快照；TCC 要手写 3 个方法  
2. **场景匹配**：秒杀下单是短事务、强一致要求，AT 正好  
3. **性能优于 XA**：XA 全程持锁同步阻塞，AT      只在提交瞬间短暂加全局锁  
4. **与 Dubbo 集成成熟**：本项目还自研了 Seata      Dubbo Filter 修官方 bug（见下）
- **什么时候该换**：长流程/复杂补偿用 SAGA；  需要业务精确控制并发一致性用 TCC——AT 不是万能的
**追问4：项目里 Seata 用在哪些模块？**
- **mall-seckill**：**TM 发起方**，`SeckillServiceImpl.commitSeckill` 加 `@GlobalTransactional`
- **mall-product**：**RM 分支**，`ForOrderSkuServiceImpl.reduceStockNum`（Dubbo 扣库存）
- **mall-order**：RM 分支，建订单参与全局事务（XID   经 Dubbo 传播），但其自身注解已**移除**
- **mall-common**：自研   `SeataTransactionConsumerFilter/ProviderFilter`  ，跨 Dubbo 传播 XID
- **数据库**：3 个库有 undo_log（cs_mall_pms   / cs_mall_oms / cs_mall_seckill）
- **演进故事（加分）**：order 模块早期自己加全局事务，  后来把库存扣减改成 **MQ 异步削峰**，
- 本地事务够用就移除了注解（`OmsOrderServiceImpl`   第 82 行注释）。
- 说明不是无脑全链路加 Seata——秒杀主链路用 AT 保强一致，  普通下单走 MQ 保最终一致
**追问5：undo_log 真的能保证数据一致性吗？（批判性）**
- **不能**。undo_log 只是"回滚的素材"，一致性靠**三件套**：① TC 协调的全局提交/回滚协议 ② 全局锁写隔离 ③ undo_log 补偿
- **undo_log 存什么**：beforeImage（改前快照：主键+被改字段）+ afterImage（改后），和业务 SQL **同一本地事务写入**，保证日志与数据同生共死
- **回滚怎么工作**：TC 决定回滚 → RM 用 beforeImage 生成逆向 SQL 恢复 → 删 undo_log
- **为什么不足以保证**：依赖业务表有**主键**（没主键补偿定位不了行）；回滚是逆操作，极端并发下恢复可能非预期值（全局锁降风险但不为零）；undo_log 异步清理占空间；undo_log 无多副本，跟随数据库可靠性
- **面试话术**："undo_log 不是一致性本身，是 AT 模式回滚的依据。真正的一致性是协议+全局锁+undo_log 三件套共同保证的，它只是必要的一环，而且依赖主键、依赖与业务 SQL 原子写入，这些边界我清楚——所以长事务/复杂补偿我会换 TCC 或 SAGA"
- **追问：回滚遇到并发修改怎么解决？**（防→检→兜底三层）：  
1. **防**：全局锁写隔离把并发全局事务挡在外面；可再加      `SELECT ... FOR UPDATE` 把非 Seata      的普通写也挡住  
2. **检**：AT 有**镜像校验**——回滚前对比当前值和      afterImage，一致才执行逆向 SQL；不一致判定"脏写"，  抛异常报警而不是静默覆盖**（关键细节，面试加分）  
3. **兜底**：业务表加 `version` 字段乐观锁，补偿 SQL      带 `WHERE version=?`，  冲突则影响 0 行可重试；补偿操作设计成幂等可安全重试；  再上对账任务扫描不一致数据自动/人工修复（最终一致思维）  
4. **还不够 → 换 TCC**：Cancel 由业务手写，     可自由加并发校验、状态判断、重试策略，一致性控制权拿回业务层（     代价是侵入大）
- **面试话术**："AT 全局锁把并发冲突概率压到很低，即使发生，  镜像校验会对比 afterImage   发现脏写就报警而不是静默覆盖；  再加版本号乐观锁、补偿幂等和对账兜底，工程上完全可接受。  对一致性极其敏感的场景我换 TCC 把补偿攥在自己手里"
**追问6：自研 Seata Dubbo Filter 修官方   bug？新版修了吗？**
- **Bug**：Seata 2.1.0 的 `dubbo-filter-seata` 在**非全局事务**场景（无 XID）调用 Dubbo 接口时，直接取 `RootContext.getBranchType()` 返回 null → NPE（报错 `Cannot invoke BranchType.name() because branchType is null`，GitHub Issue #6815/#6816）
- **自研方案**：自定义 Filter 先 `RootContext.getXID()` 判空，XID 存在才安全取 branchType，  再塞进 Dubbo 附件，通过 SPI（`META-INF/dubbo/org.apache.dubbo.rpc.Filter`）注册
- **新版状态**：**Apache Seata v2.2.0   已修复**（Release Notes #6816，  修复方式正是"先检查 XID 再取 branchType"）。  所以升级到 2.2.0+ 后官方 filter 已可用，  可考虑移除自研实现

### Q6. Nacos 的作用？注册中心和配置中心都做了什么？🔴
**追问1**：服务是怎么注册到 Nacos 的？
**追问2**：Nacos 挂了会怎样？
【简答】Nacos 既是注册中心（服务发现）也是配置中心（配置管理）。所有服务启动时注册到 Nacos，消费者从 Nacos 获取服务列表；配置中心管理动态配置。
【深挖】
- **注册中心**：服务启动时 `Spring Cloud   Alibaba` 自动注册到 Nacos（服务名 +   IP + 端口）  ，消费者订阅服务列表，
- 实现动态服务发现
- **配置中心**：管理应用配置（如 Sentinel 流控规则存   Nacos），配置变更可动态推送
- **Nacos 挂了会怎样**：  
- 已建立连接的消费者**继续用缓存的服务列表**，不立即挂  
- 新服务无法注册、新消费者无法发现 → 部分功能异常  
- 面试话术："Nacos 高可用在单机环境依赖它的内存缓存，    真正的生产要集群部署"
- **你踩过的坑**：Sentinel 规则存 Nacos，但   Nacos 里配置为空时会把本地规则**覆盖清空**（限流失效），  这是真实的坑，讲出来很加分

### Q7. 为什么用 Redis？缓存了什么数据？缓存策略？
**追问1**：缓存穿透/击穿/雪崩怎么防？
**追问2**：Redis 和数据库一致性怎么保证？
【简答】Redis 做缓存 + 秒杀预扣库存。缓存分类树、秒杀 SPU/库存/随机码、登录 Token、幂等 key、防重复购买标记。**注意：普通商品详情（SPU/SKU）实际走数据库直查，未走 Redis 缓存**（面试按真实情况讲）。
【深挖】
- **缓存内容**（2026-08-09 核实代码后的真实情况）：  
- 分类树（`category_tree`，TTL 1 分钟短兜底）→     减少 DB 压力  
- 秒杀 SPU/库存（预扣）+ 随机码（randCode）→     高并发扣减 / 防刷  
- 秒杀防穿透 Set（`spu:bloom:filter:{日期}`，    TTL 2 天）  
- JWT 黑名单/登录态 → 认证  
- 幂等 key → 防重复提交  
- 防重复购买标记（三 key）→ 业务正确性  
- AI 会话上下文 + Token 成本计数（mall-ai）  
- **普通商品详情（SPU/SKU）没走 Redis**：    `SpuServiceImpl`/`ForFrontSpuServiceImpl`    直接查库，无缓存一致性负担
- **缓存穿透**（查不存在的 key）：  你的项目**没用布隆过滤器**（本地 Redis 不支持   RedisBloom），用 **Redis Set 记录秒杀商品   ID** 兜底。面试要诚实："本地 Windows Redis   不支持 RedisBloom，我用 Set 替代，生产可换布隆"
- **缓存击穿**（热点 key 过期）：秒杀库存 key   通过**预扣 + 限流**保护
- **缓存雪崩**（大量 key 同时过期）：项目用**短 TTL**（  分类树 1 分钟）减少同时失效堆积；秒杀库存靠预扣 +   限流保护热点   key。生产可加**随机 TTL** 错开过期时间（代码暂未实现）
- **一致性**（真实情况分三种策略）：  
1. **分类树**（读多写少）→ Cache Aside + **短      TTL**（1 分钟），短暂不一致可接受  
2. **秒杀库存**（高并发写）→ **Redis 预扣 +      数据库是最终真相**，防超卖靠 SQL `seckill_stock      >= 数量` 兜底  
3. **普通商品详情** → 没走缓存，无一致性问题  
- 图片是存相对路径由服务层拼接，不是缓存问题
**追问3：Seata 回滚时，Redis 与 MySQL   会不会不一致？**
- **会**，这是 AT 模式已知边界：Seata AT   只回滚**数据库**（undo_log 记录 SQL 前后镜像），  **Redis 操作不在它管辖内**。秒杀链路   Redis 与 DB   交织在同一 `@GlobalTransactional`   里——Redis DECR 扣库存、set orderedKey，  DB 建订单、插 success 记录。全局回滚时 DB 被   undo_log 补偿，**Redis 已扣的库存不会自动恢复**
- **项目实际做法**（不是靠 Seata，是**手动补偿**）：  
1. try-catch 里手动反向补偿：订单创建失败      `increment()` 库存 + 删 orderLockKey；     后处理失败再删 orderedKey（     代码注释写着"补偿Redis库存"）  
2. **TTL 兜底**：orderLockKey 1 分钟、     orderedKey 2 小时自动过期，即使补偿漏了 key 也会失效  
3. **以 DB 为最终真相**：Redis 库存是"可重建的预扣缓存"，     重启预热任务从 DB 重灌
- **残留不一致窗口**：异常从没被 try-catch   覆盖的路径逃逸时，Redis 库存无人补偿；方向安全（  最多少卖、不会超卖）
- **面试话术**："Seata 只管数据库，Redis   的补偿我靠业务 try-catch 手动做 + TTL 兜底 +   以数据库为准。Redis 库存是可重建的预扣缓存，接受最终一致；  强一致场景换 TCC 把补偿攥在业务手里"
**追问4：幂等 key 防重复提交是怎么实现的？**
- **原理**：Redis **SETNX 原子性 + TTL   自动过期**，实现"同一用户 + 同一参数 + 时间窗内只执行一次"
- **实现**：`mall-common` 的   `IdempotentAspect`（AOP 环绕通知）拦截   `@Idempotent` 注解方法：  
- key = `idempotent:{业务key}:{userId}:    {参数MD5}`（MD5 保证不同参数不误判）  
- `setIfAbsent(lockKey, "1", expire,     SECONDS)`：第一次设置成功返回 true → 放行；    重复请求返回 false → 抛 409"请勿重复提交"  
- 成功 → TTL 到期锁自动删除；**业务异常 → 主动     delete 释放锁，允许用户重试**
- **使用位置**：下单 5s / 支付 10s / 秒杀 3s（秒级，  防瞬时连点、网络重试）
- **和秒杀手写锁的关系**：`commitSeckill` 里   `orderLockKey.setIfAbsent("1",1,  MINUTE)` 是同原理手写版；`@Idempotent`   是通用化封装，两者都靠 SETNX + TTL
- **时间尺度区分（加分）**：幂等锁秒级防"手抖重复提交"；  防重复购买三 key 分钟~小时级防"业务上真的重复买"——两回事

### Q9. 如果你重新设计这个项目，会做什么改进？
**追问1**：现在有什么你觉得可以更好的？
**追问2**：哪些是学习项目可以接受、生产必须改的？
【简答】几个方向：① Nacos/Redis/ES 做集群高可用；② 引入分布式缓存双写/消息最终一致性；③ 秒杀用布隆过滤器替代 Set；④ 加 CI/CD 流水线；⑤ JWT Secret 换随机强密钥。
【深挖】
- **诚实复盘**（面试加分）：  
- 单机部署，中间件无集群 → 生产要 HA  
- Sentinel 规则最初靠代码硬编码，后来才用 Nacos 管理     → 配置应该一开始就用配置中心  
- 秒杀 Set 替代布隆 → 数据量大要换  
- JWT 密钥默认值在代码里 → 生产必须随机化  
- Druid 连接池踩坑后换 HikariCP → 选型要调研
- 面试话术："**我能说出项目的不足，说明我真正理解它**。  比如单机中间件是高可用短板，这是我学习项目的边界，  也是我接下来想改进的方向"
**追问3：分布式缓存双写/消息最终一致性是什么？和   TCC 像吗？**
- **双写**：应用同时写 DB 和缓存。问题：两次写不是原子的，  DB 成功缓存失败就旧了 → 裸双写不推荐，要配消息补偿
- **消息最终一致**（推荐）：DB 是唯一权威，写库后发 MQ 消息  "刷新/删除缓存key"，消费者异步执行；失败 MQ 重试直到成功
- **和 TCC 的异同**（相似但级别不同）：

| | TCC | 消息一致性 |
|---|-----|-----------|
| 解决什么 | 跨服务/跨库分布式事务 | 缓存与 DB 一致性 |
| 一致性 | **强一致**（事务内） | **最终一致**（异步追上） |
| 共同点 | 都靠**应用层手动写**补偿逻辑（像 AT 那种框架自动） | |
- **为什么是改进**：当前手动 try-catch 补偿 + 短 TTL 依赖  程序员在每个 catch 写对；MQ 方案把补偿统一到消费者，  失败自动重试，系统自己兜底
- **面试话术**："TCC 和消息一致性都靠业务手写补偿，但 TCC   管跨库强一致、消息一致性管缓存最终一致——一个像同步手术，  一个像快递派送，晚到但一定到"
**追问4：消息一致性到底怎么"一致"？（原理）**
- **秘密 = MQ 的"至少一次投递 + 不 ack 就重试"**，  消息不会丢、直到被消费成功
- 步骤：① 写库成功 ② 发 MQ 消息"删缓存key" ③ 业务返回  （此刻缓存可能旧）④ 消费者删缓存 ⑤ 失败？不   ack → MQ   重投 → 消费者恢复后重试 → 直到成功
- **对比无 MQ**：改库后顺手删缓存，这步失败缓存就永远旧，  只能等 TTL 兜底 → "靠运气"；有 MQ → "保证发生"
- **生活例子**：支付成功后通知仓库发货。不用 MQ 仓库宕机  单就丢；用 MQ 订单号进队列，仓库起来后取 → 晚发但一定发
- **面试话术**："最终一致不是同一瞬间一致，而是 MQ 的投递  和重试保证'一定会追上'——缓存刷新任务躺在队列里，直到成功  为止"
**追问5：CI/CD 在国内服务器访问 GitHub   不稳怎么办？**
- **国内方案**（不依赖 GitHub）：  ① 代码托管换/加 **Gitee**（国内快），  GitHub 只做备份  ② CI 平台用 **阿里云效 / CODING / Gitee   Go**（替代      GitHub Actions）  ③ 自建 **Jenkins**（在 ECS 上，从 Gitee   拉代码构建部署）  ④ Docker 镜像走 **阿里云 ACR**（容器镜像服务），     ECS 从 ACR 拉（国内/内网快），别直连 Docker Hub
- **推荐组合**：代码推 Gitee + 云效/Gitee   Go 构建 +  镜像推 ACR + ECS 拉 ACR，全程国内链路
- **面试话术**："国内服务器访问 GitHub 不稳，所以   CI/CD   不依赖它——代码推 Gitee、CI 用云效或自建   Jenkins、  镜像走阿里云 ACR，全程国内；GitHub 只当代码备份"
**追问6：JWT Secret 换随机强密钥？**
- **现状**：`jwt.secret` 是配置里写死的   69 字节固定值  （满足 HS512 ≥64 字节），但固定 + 落代码 =   泄露就能伪造 token
- **改法**：① SecureRandom 随机生成 ②   放环境变量/KMS  不入代码 ③ 定期轮换，配 Redis 黑名单平滑过渡不踢用户
- **面试话术**："长度满足 ≠ 安全。固定密钥泄露就能伪造  token，重做会随机生成 + 放 KMS + 定期轮换"
