## 14-Java并发（volatile / synchronized）

### 一句话定义
Java 多线程安全三件事：**原子性**（操作不可分割）、**可见性**（线程间看得见）、**有序性**（不被指令重排搞乱）——volatile 管后两个，synchronized 三个都管。

### volatile（你记的"防 JVM 调乱执行顺序"）
- **两个作用**：
  ① **可见性**：volatile 变量修改后立即对其他线程可见（普通变量各线程可能缓存一份，volatile 强制刷主内存）
  ② **禁止指令重排**：编译器和 CPU 会为优化重排指令（单线程无影响，多线程出错）——volatile 加**内存屏障**禁止它前后的重排
- **经典例子：DCL 单例必须 volatile**——`new Singleton()` 底层三步：分配内存→构造→赋引用，**没有 volatile 可能"先赋引用再构造"** → 其他线程拿到**半初始化对象** → 用的时候崩
```java
private static volatile Singleton instance;   // ← volatile 关键
```
- **注意**：volatile **不保证原子性**（i++ 不是原子操作，volatile 管不了）

### synchronized（你记的"sy 开头的独占锁"）
- **独占锁/互斥锁**：同一时刻只有一个线程能进同步块（其他线程阻塞等待）
- **三个作用全包**：原子性（代码块串行执行）+ 可见性（退出锁强制刷主内存）+ 有序性（锁内代码不重排出锁）
- **实现**：JVM 层面 monitor（监视器锁）；**可重入**（同一线程可重复进入）
- **用法**：修饰方法 / 代码块（`synchronized (obj) {}`）
- **与 ReentrantLock 区别**（加分）：ReentrantLock 可中断等待、可超时、公平锁可选、需手动 unlock；synchronized 自动释放、简单

### 三者对比速查
| | volatile | synchronized | ReentrantLock |
|---|---|---|---|
| 原子性 | ❌ | ✅ | ✅ |
| 可见性 | ✅ | ✅ | ✅ |
| 有序性（禁重排）| ✅ | ✅ | ✅ |
| 锁释放 | 无锁 | 自动 | 手动 unlock |
| 适用 | 单写多读标志位 | 代码块互斥 | 需要超时/中断 |

### happens-before（面试加分）
JMM 规定：volatile 写 happens-before volatile 读；synchronized 解锁 happens-before 加锁——**前一个操作的修改对后一个操作可见**，这是可见性/有序性的理论依据。

### 面试怎么讲
> "并发安全三件事：原子性、可见性、有序性。volatile 管可见性 + 禁重排（DCL 单例必须用它，防半初始化对象），但不保证原子性；synchronized 是独占锁，三个都管，自动释放；要超时/中断用 ReentrantLock。JMM 的 happens-before 是这些的理论基础。"

## 15-JDK 发行版（OpenJDK / Oracle / 信创）

### 一句话定义
JDK 11+ 后 **OpenJDK 和 Oracle JDK 代码基本一致**——选"哪个 JDK"实际是选"哪个发行版提供 LTS 更新"。

### OpenJDK vs Oracle JDK
| | OpenJDK | Oracle JDK |
|---|---|---|
| 许可 | GPLv2 + Classpath Exception（开源免费可商用）| NFTC（17+ 生产免费）|
| 本质 | 开源代码库 | 从 OpenJDK 构建 + branding |
| 差异 | — | 11+ 基本没差（历史：JDK 8 时代有商业组件）|
| 谁用 | **绝大多数公司** | 少数 |

### 国内大厂/信创 JDK（都是 OpenJDK 发行版，不是从零写）
| 发行版 | 厂商 | 特点 |
|--------|------|------|
| **Dragonwell（龙井）** | 阿里 | 业务优化（高吞吐/低延迟），JDK 8/11/17/21 LTS，国内最常用 |
| **毕昇 Bisheng** | 华为 | 针对**鲲鹏 ARM** 优化——信创/国产化核心 |
| **Kona** | 腾讯 | 腾讯业务优化 |
| **Corretto** | 亚马逊 | AWS 环境 |

**信创** = 国产化替代：政府/国企/关键行业要**自主可控** → 国产芯片（鲲鹏/飞腾）+ 国产 JDK（毕昇/Dragonwell）。

### 选 JDK 四要素（生产考虑）
① **LTS 版本**（8/11/17/21，非 LTS 只支持 6 个月）② 发行版**更新支持 + 许可合规** ③ **硬件平台**（信创国产芯片用毕昇）④ 容器镜像兼容（temurin alpine 省内存）

### 你的项目
JDK 21 + Docker 镜像 `eclipse-temurin:21-jre-alpine`——**Temurin = Adoptium 的 OpenJDK 发行版**（社区最流行），这就是现代主流做法。

### 收费问题
**国内这些 JDK 全部免费开源**（GPLv2 + Classpath Exception 可自由商用）；收费的是"**商业支持服务**"（SLA/紧急补丁），不是 JDK 本身。唯一注意：Oracle JDK 旧版本（8/11）商用订阅、Oracle 品牌产品许可条款。

### 面试怎么讲
> "JDK 11+ 后 OpenJDK 和 Oracle JDK 代码一致，差别在发行版和 LTS 支持。我项目用 JDK 21 + eclipse-temurin（Adoptium OpenJDK 发行版，社区最流行）。国内 Dragonwell/毕昇/Kona 都是 OpenJDK 发行版 + 自家补丁，全免费开源；生产选 JDK 看 LTS、支持、硬件平台（信创用毕昇+鲲鹏）、镜像兼容。"

## 16-MyBatis 注入（#{} vs ${}）

### 一句话定义
`#{}` = 预编译参数（**结构数据分离**，参数永远变不成代码）；`${}` = 字符串拼接（**参数即代码**，SQL 注入就发生在这）。

### 为什么 #{} 安全（预编译）
```sql
SELECT * FROM user WHERE id = #{id}
→ PreparedStatement：SELECT * FROM user WHERE id = ?   -- 先编译
→ 参数作为"数据"绑定进占位符
→ 传 "1 OR 1=1" → WHERE id = '1 OR 1=1'（一个字符串值）-- 变不成代码
```
**核心**：数据库**先编译**（生成执行计划，`?` 占位），参数**后绑定**——参数在引擎眼里永远是字面量。

### 为什么 ${} 危险（拼接 + 经典注入例子）
```sql
SELECT * FROM user WHERE id = ${id}
传 "1 OR 1=1" → WHERE id = 1 OR 1=1          -- 全表查出
传 "1; DROP TABLE user;--" → 删表（多语句）

-- 经典登录绕过（面试必讲）：
SELECT * FROM user WHERE username='${username}' AND password='${password}'
攻击者输入：admin' --
拼出：WHERE username='admin' --' AND password='...'
     '--' 注释掉密码校验 → 绕过登录！

-- UNION 拖库（复杂例子，搜索接口）：
SELECT * FROM pms_spu WHERE title LIKE '%${keyword}%'
输入：%' UNION SELECT username, password FROM ams_admin -- 
拼出：... LIKE '%%' UNION SELECT username, password FROM ams_admin -- %'
→ 商品列表 + 管理员账号密码哈希一起返回 = 拖库！
```

### ⚠️ 日志假象（常见误解）
MyBatis 调试日志会打印"完整 SQL + 参数值"，看起来像拼接了——**实际发送给数据库的是预编译 SQL + 参数分开传**，日志只是方便排查把参数值打出来。**别被日志误导以为真的拼接了**；`#{}` 不拼接，参数在编译后绑定，**没机会成为语法**（不是"识别为字符串"，是"根本没参与语法解析"）。

### 对比速查
| | #{} | ${} |
|---|---|---|
| 机制 | 预编译，参数当**值** | 拼接，参数当**代码** |
| 注入风险 | 无 | 有 |
| 性能 | 同 SQL 只编译一次 | 每次重新拼接编译 |
| 适用 | 值（id/name/条件）99% 场景 | 表名/列名（标识符无法参数化）→ **必须白名单** |

### 你的项目
全项目 Mapper **0 处 `${}`**（2026-08-28 审计）——全部 `#{}`，无 SQL 注入面 ✅

### 面试怎么讲
> "`#{}` 是结构数据分离——SQL 先编译、参数后绑定，参数永远变不成代码；`${}` 是把参数拼进 SQL，注入就在这。99% 场景用 `#{}`，只有动态表名/列名才用 `${}`（标识符无法参数化）且必须白名单。我项目 0 处 `${}`。"

## 18-ES 底层（Lucene / 倒排索引 / 分片状态 / 运行逻辑）

### 一句话定义
ES = **分布式 Lucene**——每个分片 = 一个独立 Lucene 索引实例；搜索快的根源是**倒排索引**（词 → 文档），不是扫全文。

### Lucene 索引长什么样
- **倒排索引（核心数据结构）**：建立时把"文档 → 词"翻成"词 → 文档列表"：
  ```
  正排:doc1"小米手机拍照好" → [小米,手机,拍照,好]  (存文档)
  倒排:"手机" → [doc1, doc2]  "小米" → [doc1]     (存词表)
  查询"手机":直接查词表命中 → 拿 doc1/doc2,不扫全文
  ```
  类比：书末尾索引页（字 → 页码）——查词直接翻索引，不用从头翻全书
- **磁盘形态**：多个**不可变 segment（段）**——写入先进内存 buffer → 每秒刷成一个 segment（此后可搜索）→ 段不可变、后台自动合并

### 为什么搜得快（底层逻辑）
```
扫全文 = 每篇文档查一遍词 = O(N×M),全表扫
倒排   = 建索引时预先把词→文档映射好,查询查词表(词典二分)= O(logN)
         → 命中直接取文档,毫秒级
```

### 完整例子（商品文档，+倒排的局限）
```
入库:doc1"Redmi K70 拍照旗舰" doc2"iPhone 影像" doc3"小米14 拍照"
倒排:"拍照"→[doc1,doc3]  "Redmi"→[doc1]  "小米"→[doc3]
搜"拍照手机"→ 查词表命中 doc1/doc3 → 毫秒返回
局限:doc2 用"影像",搜"拍照"命不中 = 字面匹配盲区
→ 这正是后来上向量检索(语义搜索)的原因——一个例子串起倒排和向量
```

### segment（段）详解
- **segment = Lucene 磁盘存储基本单位**,一个"小索引块"(含自己的倒排表)
- **为什么分段不写一个大文件**：不能每次写一个词就改整个大文件(太慢)
  → 写入先进【内存 buffer】攒着 → 每 1 秒(或满)刷成一段 → 可搜索
  → 磁盘上积累多个段 → 后台合并(merge)成大段
- **段不可变**(写好不改)→ 好处:① 并发读不用锁 ② 顺序写快 ③ 删除=打"墓碑标记"(空间合并时才释放),更新=标记删+写新段
- **"近实时"的含义**：默认 1s 才刷新成段 → 刚写入数据最多 1s 后可搜(refresh_interval 可调)；buffer 在内存,崩溃靠 translog(磁盘日志)重放恢复不丢
- 类比：写日记不是每句重抄整本——每天写在新纸上,攒几天订一册(段),册子不可改,要改就写新册;旧册太多就整理合并成新册,顺便扔掉划掉的页
- **时间线例子（分批落盘）**：写 doc1/doc2 → 内存 buffer → ★1 秒刷新 → segment1；再写 doc3 → ★刷新 → segment2；写 doc4 → ★刷新 → segment3 → ★后台 merge 合成大段——每次刷新后新数据才可搜索（近实时）；查询 = 搜所有段再合并
- **merge 代价**：合并占 CPU/IO（后台限速执行）——为了减少段数（查询更快）+ 物理清掉墓碑文档（释放空间）。思想与 MySQL buffer/redo 刷盘同源：内存攒批 → 顺序写 → 后台整理
- **segment 专项话术**："索引由很多 segment 组成——写入先进内存攒一批（约 1 秒）刷成新段，段生成即不可变。分段避免'往大文件中间插数据要重写全索引'；不可变带来并发无锁/顺序写/缓存友好，代价是删除只能打墓碑标记，真正释放靠后台 merge 合并时清理。查询搜所有段再合并，所以段多了要 merge——这就是近实时和 merge 存在的原因"

### SkyWalking 索引为什么也在 ES
**无联动**——ES 只是 SkyWalking 的**存储选型**：SW agent 上报 trace → OAP 分析 → 存进 ES 的 sw_xxx 索引（按时间分，一堆）；ES 不知道 SW 是谁，SW 把 ES 当数据库用

### 分片状态值（区分正常 vs 故障，配合 06 三色）
| 状态 + reason | 含义 | 正常? |
|--------------|------|-------|
| UNASSIGNED + CLUSTER_RECOVERED | 节点重启后等待重新分配 | 🟢 正常中间态 |
| UNASSIGNED + NO_ATTEMPT | 还没尝试 | 🟢 通常正常 |
| UNASSIGNED + **ALLOCATION_FAILED** | 分配失败（加载报错如 analyzer 缺失）→ ES 重试 5 次封死 | 🔴 真故障（需手动 `reroute?retry_failed=true`） |
| 记忆 | 副本缺 = 丢冗余（yellow 常态）；**主分片缺 = 丢访问（red 真故障）**——看 reason 是"等分配"还是"分配失败" |

### ES 运行逻辑（读写流程）
```
写:hash(docId) % 分片数 路由 → 主分片(内存 buffer + translog 防丢)
   → 每 1s 刷 segment(可搜索) → 同步副本 → 返回
读:请求广播到所有分片 → 各 Lucene 倒排索引并行搜 → 打分
   → 协调节点合并排序 → 返回 Top-N
```

### 面试怎么讲
> "ES 底层是 Lucene，每个分片是独立 Lucene 索引，核心是倒排索引——建索引时把词到文档的映射存好，查询查词表直接命中，不扫全文，这是毫秒级搜索的根源。单节点也叫集群（size=1），副本必须放不同节点所以单节点副本 UNASSIGNED 是正常；区分故障看 reason：等分配（CLUSTER_RECOVERED）正常，ALLOCATION_FAILED 才是真故障（那次 IK 丢失导致主分片加载失败、重试 5 次封死）。SW 的 sw_xxx 索引也在 ES，因为 ES 是它的存储选型，无联动。"

## 21-JSON 库选型（Jackson vs fastjson）

### 一句话定义
Web 层默认 **Jackson**（Spring Boot 深度集成）；业务手写解析混用 **fastjson 2.x**——决定统一 Jackson（TODO #35）

### 分工（项目现状，代码实证）
| | Jackson | fastjson 2.x |
|--|---------|-------------|
| 用在哪 | Web 序列化（Controller VO 自动转）、@JsonFormat/@JsonSerialize、Long→String 精度（JacksonConfiguration）、401/403 ObjectMapper、jjwt | 手写解析 JSON.parseObject/JSONObject/JSONArray（AI 请求拼装/MQ 消息/支付宝参/JWT） |
| 依赖 | Spring Boot 自带 | 显式 2.0.43（根 pom）8 模块 |

### 为什么统一 Jackson
- **fastjson 1.x 有反序列化 RCE 连环漏洞史**（2020-2022：1.2.24/1.2.68 多版本爆洞）——团队规范常禁 1.x
- 2.x 重写已修（项目用的 2.0.43 安全版）但双库维护无必要
- Jackson = Spring 深度集成（消息转换器/注解/配置中心化）+ 安全生态活跃

### 面试怎么讲
> "项目 Web 层序列化是 Spring Boot 默认 Jackson（@JsonFormat + Long→String 精度全局配置），业务手写解析早期混用了 fastjson——版本是 2.0.43 安全版。我倾向统一 Jackson：fastjson 1.x 出过反序列化 RCE 连环漏洞，虽然 2.x 重写修复了，但统一到 Jackson = 单库维护 + Spring 集成 + 生态安全；替换工作量主要是把几十处 JSON.parseObject 换成 ObjectMapper（已记 TODO #35）。"

## 22-池化思想（线程池/连接池/各种池）

### 一句话定义
同一思想的多个实现：**昂贵资源（线程/连接/对象）用完不销毁、复用 + 上限 + 生命周期管理**——避免"每次用都重新创建"的高成本

### 常见池清单（各装什么）
| 池 | 装什么 | 为什么贵（要池化） | 项目里的实现 |
|----|--------|------------------|-------------|
| 数据库连接池 | DB TCP 连接 + 会话 | 三次握手+认证+服务端会话（最贵） | Druid（6 服务）+ HikariCP（resource） |
| 线程池 | 线程（执行单元） | 创建 = ~1MB 栈 + OS 调度实体 | Tomcat http-nio / Dubbo 线程池 / SSE_EXECUTOR |
| HTTP 连接池 | keep-alive 连接 | 握手（+TLS） | RestClient 底层 JDK HttpClient |
| Redis 连接池 | Redis 连接 | 握手+认证 | Lettuce（自带） |
| MQ 连接池 | RabbitMQ connection/channel | 握手 | RabbitMQ 客户端 |
| 对象池 | 昂贵大对象 | 初始化成本 | commons-pool |
| 内存池 | 直接内存缓冲 | 分配/GC | Netty ByteBuf（网关/Dubbo 底层） |

### 共同点（为什么都叫池）
① **复用**：用完还给池，不销毁 ② **上限**：池大小 = 并发资源上限（满了排队/拒绝）③ **管理**：空闲回收/超时/健康检查 ④ **目的**：一次创建、反复用。类比：共享仓库——工具用完放回，不每次现买，仓库有库存上限

### 线程池 vs 连接池（最容易混，关键认知）
```
线程池 = "谁去干活"（CPU 执行单元）
连接池 = "用什么通道干活"（通信连接）
一次数据库查询 = 线程池出【线程】+ 连接池借【连接】——两个池协作管不同资源
```
区别维度：资源类型（执行单元 vs 通道 vs 对象 vs 内存）；创建成本来源（栈 vs 握手认证）；池的管理策略（线程池=核心/最大/队列/拒绝策略；DB 连接池=最小/最大/空闲回收/有效性探测 testWhileIdle）

### 面试怎么讲
> "池是同一思想的多个实现——昂贵资源复用 + 上限 + 生命周期管理。数据库连接池最典型：建连 = 握手+认证+服务端会话，每次请求新连接 = 每个请求多几十 ms，所以项目 6 服务 Druid + resource Hikari；线程池管执行单元（Tomcat/Dubbo），HTTP/Redis/MQ 连接池管通道。**线程池和连接池协作不冲突**：一次查询 = 线程池出线程、连接池借连接。区别在资源类型和管理策略。"
