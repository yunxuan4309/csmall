### Q1. 密码怎么存储的？为什么 BCrypt？🔴
【追问1】BCrypt 和 MD5/SHA 的区别？
【追问2】为什么 BCrypt 能防彩虹表？
【简答】密码用 BCrypt 哈希存储（不是明文，也不是 MD5/SHA）。BCrypt 内置盐 + 可调计算成本，抗彩虹表攻击。
【深挖】
- **BCrypt 特点**：自动生成随机盐，输出格式   `$2a$10$盐哈希`；计算成本可调（`$10$`   表示 2^10   次迭代），让暴力破解变慢
- **vs MD5/SHA**：MD5/SHA 是快速哈希，  无盐或固定盐 → 彩虹表可破解；BCrypt 慢 + 随机盐 →   每个密码的哈希都不同
- **彩虹表是什么**（追问2 原理）：一张"预计算的哈希→明文"  查找表——攻击者提前把常见密码的哈希算好存表，拖库拿到  哈希后查表秒出明文。**无盐的致命弱点**：所有用户的相同  密码哈希都一样 → 一张表通吃所有库
- **盐怎么废掉彩虹表**：随机盐让每个用户哈希都不同 → 要为  每种盐建表（盐 2^22 种）→ 表爆炸建不起；再加上 BCrypt  故意慢 → 只能暴力试，成本极高。**盐废彩虹表、慢废暴力**
- **你的项目**：`PasswordEncoder` Bean =   `new BCryptPasswordEncoder()`，  Spring Security 标准
- **真实坑**：管理员登录 BCrypt 兼容性问题（历史记录），  说明加密方案切换要兼容存量数据
- **企业生产也是 BCrypt 吗**（诚实）：**是**——Spring Security  默认、行业标准（GitHub/Django/Laravel 同类）。但"无法破解"  要打三个补丁：① 弱密码照样被字典命中（要密码策略）  ② BCrypt 非内存困难型，cost 默认 10 可提到 12+  ③ 防拖库不防撞库（要登录限流/锁定）
- **拖库 vs 撞库**（补丁③展开）：拖库 = 攻击者拿数据库哈希，  BCrypt 防（不可逆+盐+慢）；**撞库 = 拿别处泄露的"用户名+  密码对"直接试你的登录接口**（不碰哈希，BCrypt 完全防不住）  → 靠登录限流/锁定（5 次锁 15 分钟）、IP 限流、验证码。  类比：拖库=撬保险柜拿指纹；撞库=拿别家偷来的钥匙挨家试门
- **盐为什么防不住字典**（补丁①展开）：盐防**彩虹表**（预计算  复用——一表破所有）、慢防**暴力**（全空间穷举变慢），但  **字典攻击是"现场拿常见密码跑 BCrypt"**——针对你单个哈希  现场算，盐只是带上，成本不变（几万字典 × 100ms ≈ 1 小时内）。  **结论：弱密码是原罪**——盐防"复用"不防"单个破解"，  所以要密码策略（拒绝 123456 这类弱密码）
- **算法演进**：BCrypt → scrypt → **Argon2id**（OWASP 首选，  内存困难型抗专用硬件；Spring Security 6.3+ 内置）
- **企业不止哈希**：TLS / 登录限流锁定 / MFA / 密钥轮换 /  审计风控——哈希只是第一层（详见 [[认证安全企业级升级方案]]，  TODO #17）
- **算法迁移标准做法**：`DelegatingPasswordEncoder` 多算法并存  （{bcrypt} 前缀），老密码旧算法验证 + 登录成功时平滑升级  新算法——换算法不用全量重设密码
- 面试话术："BCrypt 的'慢'正是它的优点——哈希计算慢，  暴力破解的代价就高，再加上随机盐，两个相同密码的哈希也不同。  我知道企业还有 Argon2id、登录限流、MFA 这些外围——我的项目  做了哈希这一层，外围是诚实边界"

### Q2. 认证体系是 JWT，为什么不用 Session？🔴
【追问1】JWT 无状态的好处？
【追问2】JWT 的缺点？
【追问3】什么场景用 Session？现代生产还用吗？
【简答】JWT 无状态，服务端不存 session，适合微服务水平扩展。每个服务都能独立校验 token，不需要共享 session 存储。
【深挖】
- **好处**：① 无状态，任意服务都能校验（不用集中式   session）；② 跨域/移动端友好；③ 服务间传递用户信息
- **缺点**：① 无法主动失效（所以用 Redis 黑名单）；②   token 泄露风险（所以要 HTTPS + 过期时间）；  ③ 无法踢人
- **你的项目**：JWT 存 localStorage，请求带   Authorization 头，登出用 Redis 黑名单
**追问3 答案（Session 场景）**：Session+Cookie **现代生产  大量在用，不是被 JWT 淘汰**——两者是"可控 vs 无状态"的  取舍。Session 适用：① B 端管理后台/企业内部系统（能踢人/  失效/会话审计）② 单体 Web（服务端渲染）③ **认证服务器/  SSO 中心**（Keycloak/OIDC 必须知道谁登录着）④ 支付金融  ⑤ 浏览器应用（HttpOnly Cookie 防 XSS）
- **为什么这些场景不用 JWT**：① 无法主动失效（踢人/封号/  改密码后旧 token 还能用，除非黑名单=回到有状态）  ② 无会话管理（在线数限制/设备管理做不了）  ③ localStorage 的 JWT 能被 XSS 偷（Cookie+HttpOnly 防）  ④ 认证服务器必须"有状态"（会话列表/审计）
- **现代主流 = 混合**：认证服务器用 Session 管登录态 +  发**短命 JWT**（access token + refresh token）给客户端；  B 端管理用 Session，C 端 API/移动端用 JWT
- **你的项目定位**（诚实）：C 端用 JWT 合理（移动端友好、  微服务无状态）；后台管理严格说更适合 Session（管理员可  踢人）——你用 JWT + Redis 黑名单是统一方案，黑名单就是  给 JWT 补"可控性"
- 面试话术："JWT 无状态是微服务的最优解——11   个服务都能独立校验，不用依赖集中式 session；  代价是无法主动失效，所以用 Redis 黑名单兜底。  Session 没被淘汰——B 端后台、认证服务器还在用，  现代主流是 Session 管登录态 + 短命 JWT 给客户端"

### Q3. 秒杀有哪些防刷机制？🔴
【追问1】随机码、限流、幂等分别防什么？
【追问2】还有哪些能做的？
【简答】四层防刷：随机码（防提前下单）、Sentinel 限流（防流量冲击）、幂等注解（防重复提交）、防重复购买（防囤货）。
【深挖】
- **随机码怎么生成**（代码实证）：SeckillInitialJob 预热时  `ThreadLocalRandom.nextInt(900000)+100000`（6 位），存 Redis  key `mall:seckill:spu:url:rand:code:{spuId}`（每 SPU 一个），  TTL = 2h+5min+**随机 0~30s**（随机化防同时过期雪崩）。  提交订单必须带码，不拿码直接 POST → 被拒 → 防"提前下单/  接口直刷"
- **幂等怎么实现**（代码实证）：`@Idempotent(key="seckill",  expire=3)` 注解 + AOP——key = `idempotent:{业务}:{userId}:  {参数MD5}`（不同参数不误判），`setIfAbsent`（SETNX）原子，  重复返回 false 拒绝；业务异常 delete 释放锁允许重试。  用在秒杀提交/新增订单/支付 3 处
- **限流**：Sentinel QPS=10 快速失败（防流量冲击，规则存 Nacos）
- **防重复购买**：三 key（orderLock 下单锁/ordered 未支付拦截/  reseckill 永久购买标记），防囤货
- **企业四层（你没做，诚实边界）**：  IP 限流（按 IP 计数频率，防单 IP 刷）/ 验证码（人机识别，  防脚本）/ 设备指纹（采集浏览器特征哈希成设备 ID，防同一  设备换账号）/ 用户风控（行为打分，防职业黄牛）
- **分层对应**：随机码→提前下单；Sentinel→流量；幂等→重复  提交；三 key→囤货；验证码→脚本；IP→单 IP 刷；指纹→换  账号；风控→黄牛
- 面试话术："秒杀防刷是**分层防御**——知道随机码才能下单、  限流控制流量、幂等防重复、防重复购买限购，每层挡一种攻击。  企业还有 IP 限流/验证码/设备指纹/用户风控四层我没做，是  诚实边界里的演进方向"

### Q4. JWT 密钥安全吗？怎么管理的？🔴
【追问1】密钥在哪配置？
【追问2】HS512 对密钥长度的要求？
【简答】JWT 密钥在配置文件，HS512 要求密钥 ≥64 字节（512位）。生产通过环境变量注入，不硬编码。
【深挖】
- **密钥配置**：`jwt.secret`，开发在 yml 有默认值，  生产通过环境变量 `JWT_SECRET` 注入（  compose 里配）
- **HS512 长度**：必须 ≥64 字节（512 位），  你的密钥 69 字节
- **安全实践**：生产密钥要随机生成，不能代码里硬编码（  你的项目开发有默认值，生产用环境变量——面试可提"生产要随机化，  这是待改进项"）
- **坑**：JJWT 0.12 严格校验密钥长度，不够会报错
- 面试话术："密钥是 HS512 签名的基础，**长度必须 ≥64   字节**。生产用环境变量注入，不写死代码里"

### Q5. 跨域（CORS）怎么处理的？
【追问1】为什么网关统一处理？
【追问2】`*` 和 credentials 冲突？
【简答】CORS 在网关统一配置。前端访问不同服务有跨域，网关统一加响应头，各服务不重复配置。
【深挖】
- **原理**：Spring Security 6 中 `allowedOrigins("*")` 不能和  `allowCredentials(true)` 同用（有凭证时不允许通配）→ 官方  推荐 `allowedOriginPatterns("*")`，或**显式域名白名单**
- **你的网关**（代码实证）：`CorsConfig`（CorsWebFilter）用  **显式白名单** `addAllowedOrigin`（localhost:5173 /  127.0.0.1:5173 / 8.156.77.197）+ `allowCredentials(true)`  ——比通配更严，正确做法
- **诚实点：并不是"各服务不重复配置"**——全景（代码实证）：  ① mall-ai 自带 CORS（**SSE dev 直连需要**——vite.config     `/ai` 直连 10010 绕过网关避免缓冲，注释原文实证；     生产走网关不需要）  ② 5 个服务（ums/search/product/resource/seckill）的     WebMvcConfiguration 有 `allowedOriginPatterns("*")`     宽松通配（**dev 直连需要，但没限定 profile → 生产也     生效 = 多余**）  ③ **order 是范例**：WebMvcConfiguration 已注释，注释原文     "CORS 已由网关统一处理，微服务不再处理"  ④ ai 路由配 `DedupeResponseHeader` 去重（服务加头 +     网关加头会重复，04-Q9 提过）
- **为什么收敛到网关**：CORS 是**浏览器机制**——只有"浏览器  直接跨域访问服务"才需要；生产所有浏览器请求走网关（同域）  → 网关加一次就够；服务间 Dubbo/内网无浏览器 → 不需要
- **统一方案**（照 order 范例推广，TODO #22）：  ① 5 服务 WebMvcConfiguration 的 CORS 改 **@Profile("dev")**     限定（不是删——dev 直连还要用）  ② mall-ai CORS 同样收窄 dev-only  ③ 网关显式白名单不动  ④ ai 路由 DedupeResponseHeader 可删（重复源消失）  ⑤ 验证：生产 curl -i 只有一个 Access-Control-Allow-Origin
- **坑**：Spring Boot 3 / Security 6 的   CORS 配置变化（`*` 不允许 + credentials）
- **例子（帮理解）**：dev 页面在 **5173**（Vite 前端端口），  请求 **10087**（网关端口）→ 端口不同 = 跨域 → 浏览器扣住  响应，除非服务端回 `Access-Control-Allow-Origin:  localhost:5173`（通行证）；带 JWT 还要先发 OPTIONS 预检 +  `Allow-Credentials: true`（这就是不能用 `*` 的原因）。  类比：浏览器=门卫，跨域=去隔壁楼，CORS 头=隔壁楼贴的  "允许进入"告示；代理（Vite/Nginx）=门卫跑腿，你只和门卫  打交道（同源），不需要告示——**服务端之间没有跨域**
- 面试话术："CORS 在网关统一处理，用显式域名白名单 +  credentials——Security 6 里 allowedOrigins 不能和   credentials 同时用通配符。诚实说：项目里 mall-ai 和  5 个服务还有历史遗留的宽松 CORS，生产应收敛到网关统一"

### Q6. 接口参数校验怎么做？
【追问1】@Validated + 注解？
【追问2】自定义校验？
【简答】用 Jakarta Validation（@NotNull/@Pattern/@Validated），Controller 参数自动校验，失败抛异常由全局异常处理器统一返回。
【深挖】
- **注解**：`@NotNull`、`@Pattern`（正则）、  `@Size`、`@Validated` 触发
- **自定义**：  `SeckillOrderRegExpression`   定义正则常量（  手机号、座机、姓名长度等），如手机号   `^1[3-9]\d{9}$`
- **全局异常**：`GlobalExceptionHandler`   统一捕获校验异常，返回 `{state:400,   message}`，  前端友好提示
- **坑**：空字符串和 null 的校验差异（空字符串可能触发   @Pattern，null 跳过）；  RequestBody 缺失问题（  历史 bug）
- **注解表**：@NotNull 非空（null 拒、**空串过**）/  @NotBlank 非空白（null+空串+纯空格都拒，比 NotNull 严）/  @Pattern 正则（手机号 ^1[3-9]\d{9}$）/ @Size 长度范围 /  @Email 邮箱格式 / @Min/@Max 数值范围 /  @Validated **总开关**（没它其他注解不生效）/ @Valid 嵌套对象校验
- **注解会失效的情况**（面试深挖，实测实证）：  ① **漏 @Validated 触发**（最常见，实测打脸）：规则在 DTO、     触发在接口——39 个 @RequestBody 有 **5 个漏触发**（含     **注册接口** UserRegistryDTO 校验全静默失效）→ 比 if     更隐蔽（if 没写一眼可见，注解漏触发是隐性）  ② **嵌套漏 @Valid**：@Validated 只校验第一层，DTO 里的     子对象/List 不加 @Valid → 子约束不校验  ③ **组合依赖漏一个**：@Pattern 对 **null 跳过**（null 归     @NotNull 管）→ 只加 @Pattern 不加 @NotNull，null 能过  ④ **@NotNull 挡不住空串**："" 能过 → 字符串要用 @NotBlank  ⑤ **只认 HTTP 入口**：Service 内部调用/Dubbo 调用不经过     Controller → 校验不执行（约束只在入口生效）  ⑥ **缺依赖**：Spring Boot 2.3+ 校验不在 starter-web 里，     要显式加 spring-boot-starter-validation，缺了注解全失效  ⑦ **异常处理器没接**：GlobalExceptionHandler 没处理     MethodArgumentNotValidException → 返回 500 而非 400  → 防漏三招：Review 约定（写接口必 @Validated）+ 单元测试    （传非法值断言 400）+ AOP 统一触发（从根上消灭漏触发）
- **为什么不用 if**（面试必考）：注解是**声明式**——规则  "跟着数据走"集中在 DTO 字段上（自文档化、一处定义到处  生效、不会漏）；if 是命令式——散落每个方法、重复、易漏、  每个都要自己处理异常。框架统一抛异常 → GlobalException  Handler 统一返回 400，接口层干净
- 面试话术："参数校验用标准 Bean Validation +   自定义正则，全局异常统一处理——**校验规则集中在   DTO 上**，  接口层干净。声明式校验跟着数据走，不用在每个接口写  一堆 if"

### Q7. 全局异常怎么处理？
【追问1】@RestControllerAdvice？
【追问2】不同异常返回什么？
【追问3】Exception 和 Error 有什么区别？遇到 ERROR 还能跑吗？
【简答】`GlobalExceptionHandler`（@RestControllerAdvice）统一捕获：业务异常、校验异常、系统异常，返回统一的 `{state, message}` 格式。
【深挖】
- **统一响应**：`JsonResult{state,   message, data}`，成功 200，业务错误   400/403，未登录 401
- **处理**：CoolSharkServiceException（  业务）、  MethodArgumentNotValidException（校验）  、Exception（兜底）
- **好处**：前端统一解析，不用每个接口单独 try-catch
**追问3 答案（Exception vs Error）**：  Throwable 下两个分支——**Exception**（可处理：业务/IO/校验，  全局异常处理器接的就是它）+ **Error**（JVM 级严重错误：  OOM/StackOverflowError/NoClassDefFoundError，JVM 自己抛）
- **遇到 ERROR 还能跑吗**（诚实分情况）：OOM **基本不能**  （内存已耗尽，catch 后继续还是 OOM）；StackOverflowError  catch 理论可行但说明有死递归 bug；NoClassDefFoundError  **起不来**（类加载失败）
- **为什么别 catch Error**：catch(Exception) 根本接不住  Error（不是子类）；catch(Throwable) 千万别（把 Error  也吞了）。正确姿势 = **不 catch、记日志、让进程崩、  靠 Docker restart 拉起、修根因**
- **你的项目实证**：JVM 配了 `-XX:+HeapDumpOnOutOfMemoryError`  （OOM 自动 dump 堆快照排查，不是 catch）——这就是对待  Error 的正确方式；历史 ES 被 Linux OOM Killer 杀过 = 进程  级被杀，靠内存优化 + 容器限制解决，不是 Java 层能处理的
- 面试话术："统一异常处理是**约定优于配置**——前端只要看   state 就知道结果，业务异常、校验异常、系统异常分类返回，  前端按类型提示。Error 是另一层——全局异常处理器接不到它，  遇到 OOM 让它崩、靠外部重启、修根因，我配了 HeapDump  留现场"

### Q8. 权限注解怎么用的？@PreAuthorize？
【追问1】方法级权限？
【追问2】秒杀为什么 hasRole('user')？
【简答】Spring Security 的 `@PreAuthorize` 方法级鉴权，如秒杀接口 `hasRole('user')`（角色），管理员接口 `hasAuthority('/ams/admin/read')`（权限码）。
【深挖】
- **@EnableMethodSecurity**：开启方法级安全
- **@PreAuthorize 原理**：AOP 代理 + SpEL——Spring 对标注注解  的 Controller 创建代理，方法调用前 MethodSecurityInterceptor  拦截 → 解析 SpEL（hasRole/hasAuthority）→ 从 SecurityContext  取权限校验 → 通过执行 / 失败抛 AccessDeniedException。  **注解不存权限，是"消费者"**
- **三端配合链路**（签发→提取→消费）：  ① SSO 登录：把角色/权限塞进 JWT claims（authorities）  ② 各服务 SSOFilter（代码实证）：取 Authorization 头 →     substring(6).trim() 去 Bearer 前缀 → JwtTokenUtils 验签     解析 → 取 authorities → 转 SimpleGrantedAuthority →     new UsernamePasswordAuthenticationToken → 塞进     SecurityContextHolder  ③ @PreAuthorize：AOP 拦截 → SpEL 从 SecurityContext 消费
- **JWT 分割拿角色**：三段用 `.` 分割，Payload = Base64URL 的  JSON（{"authorities":["ROLE_user"],...}）——角色在  authorities 数组；项目用 JJWT 解析不手写 split（服务器  实证：front 日志真实 payload）
- **秒杀**：  `@PreAuthorize("hasRole('user')")`，  只有登录用户能抢
- **后台**：权限码校验 `hasAuthority('/ams/admin/read')`  （不是"角色校验"——全代码无 hasRole('admin')，  见 05-Q6 双模型）
- **自定义权限**：可结合 `@RequirePermission`（  自定义注解）做细粒度权限码（IoT 项目用了）
- 面试话术（诚实修正）："@PreAuthorize 是 AOP + SpEL——  注解是消费者，权限来自 SSOFilter 从 JWT 解析塞进  SecurityContext。链路：SSO 签发塞 authorities → SSOFilter  提取 → 注解消费。**诚实说：我的网关不做认证**，认证下沉  到每个服务（SSOFilter），方法级是最后一道防线（见 Q9）"

### Q9. 如果前端绕过网关直接调服务怎么办？
【追问1】服务有独立安全吗？
【追问2】生产怎么防？
【简答】每个服务有独立 Spring Security + SSOFilter，即使绕过网关，服务自己也会校验 JWT。生产环境中间件端口不对公网开放。
【深挖】
- **服务独立安全**：每个服务   ResourceWebSecurityConfiguration +   SSOFilter，不是只依赖网关
- **⭐ 网关不做认证**（代码实证）：网关只有 TraceIdGlobalFilter  + CorsConfig，无 JWT/认证过滤器——JWT 校验下沉到**每个服务  自己的 SSOFilter**。两种架构对比：  网关统一认证（集中式）= 服务信任网关，但**绕过网关直连就  裸奔**；服务认证（你的项目）= 服务独立验签，直连也被拦  ——这是"防绕过"的关键设计
- **网关在安全层面的作用**（不认证，但有三层贡献）：  ① **暴露面控制**：手写路由白名单（locator.enabled: false），     后台管理接口（/pms/** 等）不在网关层对外开放——这是     网关最重要的安全作用（04-Q9）  ② **入口级防护可加**：IP 限流 / 黑白名单 / 粗略校验——企业     纵深防御 = 网关入口挡一波 + 服务细粒度（权限码）再挡一波     （你的网关入口级防护是待改进项）  ③ **统一 CORS + traceId**：响应头统一、链路标识统一
- **网络隔离**：数据库/Redis/Nacos 等中间件端口只在   VPC 内网，不对公网（安全组只开放 22/80）
- **服务端口**：10003~10010 只内网可达，只有 80（  Nginx）对外
- 面试话术（诚实修正）："安全是**纵深防御**——网关控制暴露面  （只暴露前台路由）+ 服务二次校验（JWT 独立验签）+ 网络隔离，  三层都挡。**诚实说：我的网关不做认证**，认证在服务层——  这样绕过网关直连服务端口，JWT 校验照样拦住"

### Q11. 如何防 SQL 注入？🔴
【追问1】SQL 注入的常规手段？
【追问2】#{} 为什么安全？
【简答】SQL 注入 = 用户输入拼进 SQL 变成代码。防御核心 = **预编译（#{} / PreparedStatement）**——先编译结构、后绑定参数，参数永远变不成代码。你的项目 Mapper 0 处 `${}`（审计实证）。
【深挖】
- **常规手段 + 完整例子**（面试要能背出 payload）：
  ① **绕过登录**（目的=免密进入）：
  ```sql
  SELECT * FROM user WHERE username='${u}' AND password='${p}'
  输入：admin' --
  拼出：WHERE username='admin' --' AND password='...'   → 绕过登录
  ```
  ② **UNION 拖库**（目的=窃取其他表数据）：
  ```sql
  SELECT * FROM pms_spu WHERE title LIKE '%${keyword}%'
  输入：%' UNION SELECT username,password FROM ams_admin --
  拼出：... LIKE '%%' UNION SELECT username,password FROM ams_admin -- %'   → 商品列表 + 管理员账号密码哈希一起返回 = 拖库
  ```
  ③ **盲注**（目的=无声逐字符窃取，页面无回显时）：
  ```sql
  -- 布尔盲注：结果真假当"是/否"
  x' AND (SELECT SUBSTRING(password,1,1) FROM ams_admin LIMIT 1)='a' --
  -- 时间盲注：响应快慢当"是/否"
  x' AND IF(1=1, SLEEP(5), 0) --   → 慢 5 秒 = 条件为真 → 逐字符/二分法爆破出密码
  ```
  ④ **堆叠查询删表**（目的=破坏）：
  ```sql
  WHERE id = ${id}
  输入：1; DROP TABLE oms_order;--   → 多语句删表 = 业务瘫痪
  ```
  ⑤ **提权/横向**（目的=服务器沦陷）：
  ```sql
  -- 读服务器文件（高权限 DB 账号）
  UNION SELECT LOAD_FILE('/etc/passwd'),2 --
  -- 写 WebShell（MySQL 高权限 + 写权限）
  UNION SELECT '<?php system($_GET["c"]);?>',2 INTO OUTFILE '/var/www/shell.php' --   → 数据库权限 → 服务器权限 = 沦陷
  ```
  共同本质：**输入被拼进 SQL 变成了代码**（${} 拼接 / 未预编译）。
- **为什么 #{} 安全**（机制）：#{} 不拼接——预编译 SQL  （带 ?）和参数**分开传输**，数据库先解析语法（参数不在  里面）后绑定参数（只当值、不解析）——注入内容**没机会  成为语法**。日志里看到的"完整 SQL"是调试假象（参数值  打印），实际执行是预编译
- **多层防御**（企业）：预编译（主）/ 动态标识符白名单  （${} 只能用于表名列名且枚举校验）/ 参数类型长度校验 /  DB 最小权限账号（注入也拿不到全库）/ WAF 兜底
- 面试话术："SQL 注入的常规手段：绕过登录、UNION 拖库、  盲注、堆叠删表。我的防御核心是**预编译**——#{} 不拼接，  参数在编译后绑定没机会成为语法；${} 只用于动态标识符且  必须白名单。我审计过项目 0 处 ${}。企业再加 DB 最小权限  和 WAF 兜底"
