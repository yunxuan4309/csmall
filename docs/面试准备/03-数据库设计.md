### Q1. 为什么分成 6 个数据库？🔴
**追问1**：每个库管什么？
**追问2**：为什么不共用一个大库？
【简答】按业务领域分库：pms（商品）、oms（订单）、ums（用户）、ams（管理员）、seckill（秒杀）、resource（资源）。微服务架构要求服务独立数据库，避免共享表耦合。
【深挖】
- **6 库**：cs_mall_pms、cs_mall_oms、cs_mall_ums、  cs_mall_ams、cs_mall_seckill、cs_mall_resource
- **表数（2026-08-17 实测，含系统表）**：pms（15 表，  业务 13）、oms（6 表，业务 4）、ums（3 表，业务 2）、  ams（7 表，业务 6）、seckill（6 表，业务 4）、  resource（2 表，业务 1）→ 合计 39 张（业务表 30）
- **系统表说明（深挖点）**：  
- `flyway_schema_history`（6 库都有）：Flyway    数据库版本迁移记录表 → 表结构变更纳入版本管理，    `docker exec` 启动时自动执行迁移脚本  
- `undo_log`（仅 pms/oms/seckill 有）：Seata AT 模式    的回滚日志表 → **只有参与分布式事务的库才有**，    面试可反推"哪些服务挂了 Seata 事务"
- **为什么分库**：微服务核心特征——每个服务独立数据库，  服务间不共享表，通过接口/RPC 通信。如果共库，服务间就强耦合了
- **面试话术**："分库是微服务的必然结果——各服务独立演化、  独立部署、独立扩展，数据库是服务边界的一部分"
- **代价**：跨库无法本地事务 → 需要 Seata；  这是分库的必然成本

### Q2. 主键用什么？为什么雪花 ID？🔴
**追问1**：为什么不用数据库自增 ID？
**追问2**：雪花 ID 会不会重复？时钟回拨怎么办？
**追问3**：扩展成多实例会出问题吗？
【简答】主键用 MyBatis-Plus 的 `IdWorker.getId()`（雪花算法）生成19 位 Long ID。因为分布式环境自增 ID 冲突 + 需要全局唯一。
【深挖】**① 为什么不用自增 + 雪花结构**
- **为什么不用自增**：分库后每个库自增会重复；且自增 ID   可被猜测（爬取）
- **雪花 ID 结构**：64 位 = 1 位符号 + 41 位时间戳 +   10 位机器 ID + 12 位序列号（每毫秒 4096 个）**② 时钟回拨（概念 → 自带处理 → 话术）**
- **概念**：雪花 ID 的 41 位时间戳取自服务器系统时钟。  **回拨 = 系统时钟突然往前跳**（变回过去），如 NTP 校时、  手动改时间、虚拟机时钟漂移修正。后果：新 ID 的时间戳  可能小于之前已生成的 → **同一毫秒 + 同机器 + 同序列 =  重复 ID**（主键冲突）
- **MyBatis-Plus 自带处理**（内部 `Sequence` 类，2026-08-17   反编译 3.5.9 源码确认）：  
- 回拨 ≤5ms：`wait(回拨毫秒 × 2)` 等待后重试；仍回拨则抛异常  
- 回拨 >5ms：直接抛 `RuntimeException("Clock moved     backwards...")`  
- 3.5.x 用 `SystemClock` 缓存时钟（后台线程定时刷     AtomicLong），减少取系统时间开销
- **话术**："单机部署靠 MyBatis-Plus 自带回拨保护兜底，  生产集群建议自定义 Sequence 加**时钟回拨时记录   lastTimestamp 并拒绝生成**（美团 Leaf 方案）或改用   Redis 发号器"**③ workerId（概念 → 推导 → 集群风险 → 解决）**
- **概念**：雪花 ID 中 10 位"机器 ID"段（5 位   datacenterId + 5 位 workerId），作用是在**多台机器/多个  实例间区分身份**，保证不同实例生成的 ID 不撞。10 位最多   32×32=1024 个组合 → **集群里每个实例必须拿到不同的   workerId**
- **推导来源（深挖点）**：MyBatis-Plus 自动从   datacenterId（MAC 地址后 2 字节运算 % 32）和 workerId  （datacenterId + 进程号 pid 拼串 hash % 32）推导，  **不用手动配置**
- **集群扩展风险（追问3，2026-08-17 模拟面试补充）**：  把秒杀服务从 1 实例扩到 3 实例，**可能撞 workerId**——  pid 是操作系统分配的（用完回收，容器里可能相同），且  hash 后只有 32 个桶，**碰撞概率存在** → 两实例算出相同  (datacenterId, workerId) → **同一毫秒生成重复 ID →   主键冲突**（与时钟回拨无关，是另一个独立风险）  
- 注意：Docker 默认 bridge 网络下每容器 MAC 不同，但     pid 撞车 + 32 桶 hash 仍可能冲突
- **解决**：① 环境变量给每实例显式指定唯一 workerId；  ② 注册中心（ZK/Nacos）分配 workerId（美团 Leaf 做法）
- **话术**："扩展实例的核心风险是 workerId 冲突而不是  时钟——MyBatis-Plus 的 workerId 从 MAC 和 pid hash   推导，没有全局协调，多实例可能撞 ID。我项目当前单机  单实例没问题，扩展时我会用环境变量显式指定 workerId，  或像 Leaf 那样用 ZK 分配"**④ 为什么 19 位 Long 要转 String**JS 的 Number 精度只有 53 位，19 位 Long 会丢失精度 →全局 Jackson 配置 Long→String 序列化。（详见 Q8）**⑤ 自定义 XML 插入的坑（真实踩坑）**MyBatis-Plus 的 `ASSIGN_ID` 只在 BaseMapper 生效，自定义 XML INSERT 需手动调 `IdWorker.getId()`。**⑥ Leaf 与雪花对比（曾集成 Leaf 后弃用，面试可深聊）**
- **弃用原因**：Leaf 基于 JDK8 + SB 2.5（2020 停更），  与项目 JDK21 + SB3 代差无法统一构建 → 改用   MyBatis-Plus 雪花（`mall-leaf/DEPRECATED.md`）
- **Leaf 两种模式**：  
- **号段模式（segment）**：DB 表 `leaf_alloc` 记     `max_id+step`，服务一次性从 DB 取一段     `[max_id-step, max_id]` 放内存，`AtomicLong` 递增发号；    **双 buffer**：当前段用到 90% 时后台线程预取下一段，    用完无缝切换；step 自适应（15 分钟用完 step×2，上限 100w）  
- **雪花模式（snowflake）**：标准雪花 ID，但 workerId     由 **ZooKeeper 持久节点自增分配**    （`/snowflake/{name}/forever/{ip:port}-{自增id}`），    启动时校验本机时间 ≥ ZK 记录时间（防回拨），定时上报    本机时间到 ZK 供他节点检测
- **对比**：

| 维度 | 雪花（MyBatis-Plus） | Leaf 号段 | Leaf 雪花 |
|---|---|---|---|
| ID 结构 | 时间戳+机器+序列 | 纯递增 Long | 同雪花 |
| 依赖 | 无（时钟） | MySQL | MySQL+ZK |
| 吞吐 | 高（内存计算） | 极高（内存递增） | 高 |
| 时钟回拨 | 自带 5ms 兜底 | 无此问题 | ZK 校验+上报 |
| workerId | 自动推导（有冲突风险） | 不需要 | ZK 分配（唯一） |
| 趋势递增 | ✅ 时间序 | ✅ 严格递增 | ✅ 时间序 |
| 运维成本 | 零 | 需部署 Leaf 服务+表 | 需 ZK |
- **举例（面试讲故事）**：订单模块用 Leaf 号段 →   `leaf_alloc` 表 `biz_tag='order'`，step=1000，第一次   DB 取 `[1,1000]`，内存发 1..1000，用到 900 时后台  预取 `[1001,2000]`；DB 只被访问 2 次/千单 → 吞吐高但  **依赖 DB 可用性**（DB 挂了发不了新号段）
- **选型话术**："订单/流水这类**单调递增**业务用号段  模式（高吞吐+顺序 IO 友好）；需要**带时间信息**的 ID   用雪花。学习项目用 MyBatis-Plus 雪花够用，生产高并发  订单中心我倾向 Leaf 号段或自研号段"**⑦ 完整面试话术（时钟回拨 + workerId 连招）**
> "雪花 ID 的 41 位是时间戳，所以依赖系统时钟。时钟
> 回拨（NTP 校时/手动改时间）会让新 ID 时间戳倒退，可能
> 和之前的 ID 重复。我的项目直接用 MyBatis-Plus 的
> IdWorker，它自带保护：回拨 ≤5ms 会 sleep 等时钟追回来，
> 回拨 >5ms 直接抛异常拒绝生成，所以单机部署不会出问题。
> 它的 workerId 是自动从 MAC 地址和进程号 hash 推导的，
> 零配置，但集群部署时多实例可能推导出相同 workerId 导致
> 撞 ID——所以我之前集成过美团 Leaf 来对比：Leaf 雪花模式
> 用 ZooKeeper 给每个实例分配唯一 workerId，还定时上报
> 时间检测回拨；Leaf 号段模式则是数据库批量发号、内存
> 递增，吞吐更高但不带时间信息。我项目后来因 Leaf 停在
> JDK8 弃用了，但生产上我会按业务选：订单流水要严格递增
> 用号段，需要时间维度用雪花+ZK 分配 workerId。"
- 一句话话术："雪花 ID 保证了**全局唯一 + 趋势递增**，  缺点是依赖机器时钟，这是它和 UUID（完全随机）的取舍"

### Q3. 订单表设计？为什么大量冗余字段？🔴
**追问1**：冗余了哪些？为什么冗余？
**追问2**：分页查询用什么？
【简答】订单表（oms_order）冗余了商品名称、品牌名、分类名等。冗余是为了**查询性能**（避免每次 JOIN 多表）。
【深挖】
- **冗余设计**（SPU 表）：`brand_name`、  `category_name`、`sales`、  `comment_count` —— 存冗余值，查询不用 JOIN
- **为什么冗余**：商品列表页要显示品牌/分类名，如果 JOIN   品牌表，每页 20 条就查 20 次；冗余后单表查询即可
- **代价**：更新冗余字段要同步（改品牌名要更新所有 SPU）  ——这是典型的空间换时间
- **分页**：MyBatis-Plus 分页插件（  jsqlparser），`Page<>` 封装**冗余字段全景（6 张冗余表 + 2 反例，跨 pms/oms/seckill 3 库，2026-08-17 从建表 SQL 逐一确认）**：
- **3 种冗余类型（面试总结框架）**：  
- **名称冗余**：免 JOIN，列表页单表查询 →     `spu.brand_name`、`spu.category_name`、    `cart.title`、`order_item.title`  
- **计数冗余**：免 COUNT 聚合 →     `spu.sales`（下单累加）、`spu.comment_count`、    `spu.positive_comment_count`、`spu.stock`（SKU 汇总）  
- **快照冗余**：历史数据不被后续修改影响（电商刚需）→     `oms_order` 的收货人/省市区地址、`order_item` 的    标题/价格/图片/SKU属性JSON、`success` 的    标题/秒杀价/手机号
- **6 张表明细**：  
- `pms_spu`：brand_name/category_name/sales/    comment_count/positive_comment_count/stock/    check_user/gmt_check（名称+计数混合）  
- `oms_order`：收货人+电话+省市区 code+name+    详细地址+标签（注释标"冗余，历史"=地址快照）  
- `oms_order_item`：title/bar_code/picture_url/    price/spu_name/sku_properties（下单时快照）  
- `oms_cart`：title/picture_url/price/bar_code/data  
- `success`（秒杀成功记录）：title/main_picture/    seckill_price/quantity/user_phone（防秒杀表清理后丢信息）  
- 反例：`seckill_spu`/`seckill_sku` **不冗余**    （秒杀商品信息变化少，实时取数）
- **面试话术**："我的项目里冗余字段分三类：一是名称冗余，  商品表存品牌名、分类名，列表页不用 JOIN；二是计数冗余，  销量、评论数是累计值直接存；三是快照冗余，订单和秒杀  记录会把下单时的商品标题、价格、地址完整复制一份，因为  用户改地址、商品改价都不能影响历史订单。快照型冗余在  电商是刚需，这也是我理解'空间换时间'的真正含义——不只  换查询性能，还换**数据历史一致性**"

### Q4. 秒杀表怎么设计的？success 表是干嘛的？🔴
**追问1**：seckill_spu 和 seckill_sku 的关系？
**追问2**：秒杀成功记录表的作用？
【简答】seckill_spu（秒杀场次）→ seckill_sku（秒杀SKU/库存）→ success（秒杀成功记录）。success 表记录谁在什么时候抢到了什么。
【深挖】
- **关系**：一个秒杀 SPU 对应多个秒杀 SKU（不同规格），  seckill_sku 存秒杀价 + 秒杀库存
- **success 表**：秒杀成功记录（userId +   skuId + 时间），用于：  
- 数据统计分析  
- 防重复（配合 Redis 标记）
- **seckill_message_retry**：消息重试表（  MQ 降级方案）
- **时间窗口**：秒杀 SPU 有   start_time/end_time，  SeckillInitialJob 预热时判断窗口
- **面试话术**："秒杀数据是**分层存储**——SPU 层（场次）、  SKU 层（规格库存）、success 层（成功记录），  这样能灵活配置不同规格的秒杀价和库存"

### Q5. Flyway 是做什么的？为什么用？🔴
**追问1**：Flyway 怎么管理版本？
**追问2**：遇到过什么问题？
**追问3**：Flyway 管数据吗？
【简答】Flyway 是数据库版本管理工具，SQL 变更通过迁移脚本（`V1__xxx.sql`）管理，应用启动时自动检查并执行未应用的脚本，保证数据库结构和代码一致。
【深挖】
- **作用**：每次启动自动检查并执行未应用的迁移脚本，版本表   `flyway_schema_history` 记录已执行的版本  （installed_rank/version/success，success=1 成功）
- **好处**：数据库结构变更可追溯、可重复部署（团队/环境一致）
- **配置**（6 个有库的服务一致）：`enabled: true` +  `baseline-on-migrate: true` + `baseline-version: 0`  —— 已有旧库时打基线跳过已存在的表，不报错
- **迁移脚本分布**（`src/main/resources/db/migration/`）：  
- product：V1~V14（14 张表 + **V14 undo_log**）  
- order：V1~V5（4 张表 + **V5 undo_log**）  
- seckill：V1~V5（3 张表 + **V4 undo_log** + **V5 重试表**）  
- ams：V1~V6；ums：V1~V2；resource：V1  
- **Seata 的 undo_log 表也是 Flyway 建的** → schema 全走 Flyway
- **服务器实测（2026-08-17，6 库 history 全 success=1）**：  
- pms/oms/seckill 有 `<< Flyway Baseline >>` 版本 0    记录 → 这 3 个库**先手动 source 建表、后接入 Flyway**    （baseline 跳过已有表）  
- ums/ams/resource **无基线记录** → 表完全由 Flyway 从零建  
- V5 秒杀重试表是唯一"增量"脚本（其余全是建表）
- **本地 vs 服务器**：同一份 JAR（脚本打进包里），本地 IDEA  启动执行、服务器 Docker 容器启动执行，机制一致
- **Flyway 管数据吗（追问3）**：Flyway 本身能执行 DML，  但项目里**所有迁移脚本都是 CREATE TABLE（纯结构）**，  数据（20 个 SPU/用户/权限等）放 `database/*.sql` 手动  source —— **结构版本化走 Flyway，环境相关数据走手动脚本**
- **注意**：Flyway 有 checksum 校验，已执行脚本不能改，  只能新增 V+n —— 所以数据脚本不适合进 Flyway（数据常改）
- **Flyway 的边界（追问4，2026-08-17 模拟面试补充）**：  
- **手动 ALTER 检测不到**：checksum 只校验**脚本文件**是否被改，**从不校验数据库实际结构和脚本是否一致** → 运维手动 `ALTER TABLE` 加列，部署时 Flyway **不报错**（反直觉！）  
- **真正的问题 = 环境漂移（Schema Drift）**：手动改的    库在 Flyway 版本历史里**没有记录** → 新环境用 Flyway    建库没有这个列 → 代码在新环境报 "Column not found"  
- **正确做法**：任何结构变更**必须走 Flyway 脚本**；    若已手动改，补**幂等**的 V+n 脚本登记（如     `ADD COLUMN IF NOT EXISTS`），或用 baseline 把当前    状态设为基线  
- 面试话术："Flyway 管不到你绕过它的操作——它只校验    脚本文件，不校验数据库实际结构。手动 ALTER 不会报错，    但会导致环境漂移，所以规范是结构变更一律走 Flyway"
- **真实情况**：部分表结构靠 `database/*.sql`   手动 source 初始化，Flyway 和手动 SQL   并存——面试可提"Flyway 管增量，初始数据用脚本"
- **面试话术**："项目用 Flyway 做数据库版本管理，每个服务  有 db/migration 目录，脚本 V1__xxx.sql 递增编号，启动时  Flyway 自动对比 flyway_schema_history 执行未应用的脚本。  早期表是手动初始化的，所以配了 baseline-on-migrate 打基线  跳过已有表，后续增量（如秒杀重试表 V5）交给 Flyway。  好处是结构变更可追溯、多环境一致、部署不用手动执行 SQL。"

### Q6. 图片存储策略？为什么不存完整 URL？🔴
**追问1**：图片存哪？
**追问2**：怎么拼接完整 URL？
【简答】数据库只存相对路径（`spu_1_1.jpg`），服务层用 `ImageUrlPrefixHelper` 根据环境配置拼接完整 URL。生产图片由 Nginx 直接静态服务。
【深挖】
- **为什么存相对路径**：开发/生产环境域名不同，存相对路径可切换；  未来迁移 OSS 只改拼接逻辑，不动数据库
- **拼接**：`ImageUrlPrefixHelper` 读 `resource-host` 配置（开发 `localhost:9060`，生产 `http://8.156.77.197/`）拼接
- **静态服务**：生产 Nginx 直接 `root   /data/csmall-upload` 服务图片，不经过   Java 服务栈，快
- **坑**：富文本（spu_detail.content）里的   `<img>` 相对路径未统一处理（遗留 TODO）
- **OSS vs MongoDB（追问3，2026-08-17 补充）**：  
- **OSS（对象存储）**：存**文件**（图片/视频/文档），    通过 HTTP URL 直接访问，配 CDN 加速、容量无限、    便宜；不能 SQL 查询，只能按 key 存取  
- **MongoDB（文档型数据库）**：存**可查询的数据**，    支持 CRUD/索引/聚合；GridFS 虽能存文件但是附加功能，    访问要过程序层，不适合对外直接服务图片  
- **一句话**："文件用 OSS，数据用数据库（MySQL/    MongoDB）"；图片等"存起来让人访问"的用 OSS，    "还需要查"的用 MongoDB  
- **连接点**：项目里 `sku_properties`、`cart.data`    等 JSON 字段就是"半结构化"——如果面试官问为什么    不用 MongoDB，答"数据量级没到需要 NoSQL 的程度，    MySQL 的 JSON 类型够用，保持技术栈统一"
- 面试话术："图片 URL 是**配置驱动**——数据库存相对路径，  服务层按环境拼接，这样切换环境、迁移 OSS 都不影响数据库"

### Q7. 数据库连接池用什么？为什么？
**追问1**：Druid 和 HikariCP 区别？
**追问2**：Druid 踩过什么坑？
**追问3**：为什么不用 Druid starter 版？要统一吗？
【简答】mall-resource 用 HikariCP（曾因 Druid 线程挂死切换）；其余 6 个服务仍为 Druid 1.2.24 稳定运行。长期规划统一HikariCP（Spring Boot 默认、最稳、少依赖）。
【深挖】
- **现状（2026-08-17 服务器 JAR 核实）**：7 服务都打包  HikariCP（Spring Boot 默认），但仅 resource 真用（无  druid 依赖）；其余 6 服务 prod yml 显式 `type:  DruidDataSource` 稳定运行。文档曾误记"全面替换"，已更正
- **Druid 的坑（4 层因果链，见 `问题解决--安卓图片上传.md`）**：  ① 上传慢请求并发占满池（默认 maxActive=8）→ 等连接  ② `max-wait=0` **无限等待** → 线程永久阻塞、try-catch  抓不到 → Nginx 504 / 安卓 499 → 重试雪崩  ③ 配 `max-wait: 10000` 不生效：普通版 druid 不认  `druid.*` 命名空间（需 starter 版）  ④ 换 HikariCP `connection-timeout: 10000` 原生生效 →  **快速失败而非无限等**，解决  
- 诚实边界：①②③ 是确认根因，"连接被占满"是现象反推
- **普通版 vs Starter**：普通版=连接池实现类，配置不识别；  Starter=自动配置生效 + 自带监控面板（StatViewServlet）。  Druid 免费（Apache 2.0）
- **为什么不用 Druid starter**：监控职责被 SkyWalking 覆盖  （链路级），少一个依赖少一类坑
- **HikariCP 优势**：Spring Boot 默认、快、轻；参数  connection-timeout 10s / max-lifetime 5min（防 MySQL  8h 杀连接）
- **统一建议**：短期不动（Druid 稳定 + 重启风险）；长期  统一 HikariCP（详细方案见 `docs/评估报告/连接池统一HikariCP方案.md`）
- **面试话术**："真实选型教训——Druid 功能全但重，上传场景  线程挂死（max-wait=0 无限等 + 普通版配置不生效），换  HikariCP 解决；审计发现文档与线上不符（仅 resource 切换），  已更正——选型要结合场景，文档必须和线上对齐"

### Q8. Long 精度问题？为什么全局转 String？🔴
【追问1】哪些字段受影响？
【追问2】怎么配置的？
【简答】雪花 ID 是 19 位 Long，JS 的 Number 精度只有 53 位（约 16 位十进制），超出会丢失精度。全局 Jackson 配置 Long→String 序列化。
【深挖】
- **问题场景**：后端返回 `id:   2085323773447188482`（19位），JS 解析   `JSON.parse` 后变成   `2085323773447188500`（精度丢失），  导致查不到数据
- **解决**：Jackson 全局配置，所有 Long 类型序列化为   String
- **影响字段**：所有雪花 ID（订单 id、用户 id、商品   id）都受影响
- **面试话术**："这是**前后端协作的经典坑**——后端雪花 ID   是 19 位 Long，JS Number 装不下，必须全局转   String，否则 id 一传一改前端就找不到数据"

### Q9. 分页查询的实现？IPage 转 VO 的坑？
**追问1**：为什么 IPage<Model> 不能直接转 IPage<VO>？
**追问2**：为什么不一开始就用 VO？
【简答】MyBatis-Plus 分页用 `IPage<Model>`，转 `IPage<VO>` 需手动 stream + convertToVO + new Page<>，不能直接强转。
【深挖】
- **原因（泛型擦除）**：Java 泛型是编译期概念，运行时擦除  → `IPage<Brand>` 和 `IPage<BrandVO>` 运行时是同一个裸类。  强转编译能过（编译器信了你的谎），但 records 里实际是  Brand → 取出赋值给 BrandVO 时 JVM 才发现 →   **ClassCastException 延迟到运行期才爆**  
- **类型不安全 = 编译器发现不了错误，错误延迟到运行时**  
- 正确写法安全：`new Page<VO>()` 空壳 + `setRecords(转换后的    List<VO>)` 元素类型真实一致 → 编译期、运行期都安全
- **正确做法**：  
```java
IPage<VO> voPage = new Page<>(page.getCurrent(), page.getSize());
List<VO> voList = spus.getRecords().stream().map(this::convertToVO).collect(toList());
voPage.setRecords(voList);
```
- **为什么不一开始就用 VO（追问2，分层设计）**：  
- **实体 Model 是"数据库的镜子"**：1:1 对应表全字段（含    gmtCreate/gmtModified），MyBatis-Plus CRUD 载体；    **VO 是"前端的菜单"**：只放展示字段，隐藏内部细节  
- 若直接用实体返回：新增敏感字段（密码/内部码）会**直接    泄露给前端**；且**写操作必须用实体**（insert/update 要    全字段）→ 实体不可替代  
- **一个实体 → 多个 VO**：`Spu` → `SpuStandardVO`（详情）    + `SpuListItemVO`（列表），前端不同页面字段不同  
- 分层必然：DAO 用实体 ↔ Service 转换 ↔ Controller 用 VO
- **两种分页路径（深挖点）**：  
- **BaseMapper**（BrandServiceImpl）：返回实体 → 手动转 VO  
- **自定义 XML**（SpuServiceImpl）：resultMap 的 type 直接    写 VO，SQL 只查 VO 字段 → MyBatis 直接造 VO，天然安全。    但**只适用读操作**，写操作绕不开实体
- **两种风格为什么共存（追问3，2026-08-17 补充）**：  
- **不是非黑即白，是互补的两种风格**，由"Mapper 的泛型    参数"决定：    
- `extends BaseMapper<Spu>` → 框架内置方法（selectPage/      insert/updateById）**泛型写死为实体**，只能返回实体    
- **自己声明的方法**（如 `IPage<SpuListItemVO> list(...)`）      → 泛型由你定，XML 里 `resultMap type=VO` 指定 →       MyBatis 直接造 VO  
- **为什么框架内置方法只能返回实体**：MyBatis-Plus 只认识    "表↔实体"映射（@TableName/@TableId），**不认识业务 VO**，    不知道前端要哪种 VO（列表/详情）——那是业务的事  
- **为什么两种都要写**：简单查询（Brand 列表）用 BaseMapper    省事，转一下 VO 不费劲；复杂查询（SPU 多条件+排序白名单+    关联字段）写自定义 XML 更灵活，顺便直接映射 VO  
- **项目真实规律**：简单 CRUD 用 BaseMapper+转 VO    （Brand/Category/Album...）；复杂列表/详情用自定义 XML+    resultMap=VO（Spu 的 list/getById）——**同一项目两种    风格并存，按查询复杂度选择**  
- 面试话术："两种风格不是二选一，是按需混用：框架内置    方法只能返回实体（它不认识 VO），所以简单查询用    BaseMapper 再转 VO；自己声明的方法可以用 resultMap    直接映射 VO，适合复杂查询。我的项目两种都有"
- **面试话术**："泛型擦除导致 IPage 转 VO 要手动转换；  实体和 VO 职责不同（镜子 vs 菜单），一个实体对应多个 VO，  所以转换是分层必然。自定义 XML 直接查 VO 只适合读操作"
