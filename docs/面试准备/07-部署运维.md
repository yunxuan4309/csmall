### Q1. 整个项目怎么部署上云的？🔴
【追问1】用了什么云服务？
【追问2】部署流程？
【简答】项目用 Docker Compose 部署到阿里云 ECS（4核16G，Ubuntu）。本地打 JAR → 上传服务器 → compose 编排 21 容器启动。
【深挖】
- **云服务器**：阿里云 ECS，4核16G，公网 IP 8.156.77.197，成都地域
- **部署方式**：Docker Compose（  `/data/csmall/docker-compose.yml`）  ，21 容器
- **流程**：本地 `mvn package` 打 JAR →   scp 上传 → compose 编排（JAR 挂载进容器）
- **目录**：`/data/csmall/jars/`（11 个   JAR）、`/data/csmall/frontend/`（前端   dist）、`/data/csmall-upload/`（图片）
- **前端**：Nginx 容器服务静态文件 + 反向代理 API
**追问3：开发用 Vite 代理，生产用 Nginx 代理，为什么？**  本质相同：都是"浏览器请求看起来同源"——浏览器只看到  代理地址（5173/80），代理**服务端**转发到后端（服务端之间  没有跨域）。工具匹配环境：  dev 要"快" → Vite dev server 实时编译热更新 + 内置 proxy    一行配置解决跨域（nginx 做不了热更新）  生产要"稳" → Nginx 静态托管（gzip/缓存/高并发）+ 反向代理    分发（Vite 是开发工具，性能稳定性不适合生产）  类比：脚手架（Vite）方便改造，正式大楼（Nginx）才能住人
**追问4：为什么选 Ubuntu 不选阿里云 Linux？**  先澄清概念：Ubuntu / CentOS / Alibaba Cloud Linux 都是  **发行版**（内核 + 包管理 + 工具链），跑的是同一个 Linux  内核（你的服务器 6.8.0 实测）。  选 Ubuntu = **场景匹配**：学习项目要熟悉度 + 资料多  （Docker/Spring 教程全是 Ubuntu 示例，apt 一条命令装  Docker），不需要企业级内核优化。  **Alibaba Cloud Linux**（阿里云官方发行版）= 内核针对 ECS  优化（virtio/云盘 IO/网络栈）+ 云生态集成 + 商业支持——  **企业生产在阿里云上更倾向它**（尤其 CentOS 7 停更迁移）；  但它的优化收益（IOPS/网络）你 CPU<5% 用不上，yum 系资料  也少。**选型看场景，不是看谁更高级**
- **面试话术**："从本地开发到云上部署，我完整走了一遍：打 JAR、  写 compose、传服务器、编排启动、  验证——这是全栈工程师的基本功。前端 dev 用 Vite 代理（要快），  生产用 Nginx 代理（要稳），本质都是解决跨域。  系统选 Ubuntu 是场景匹配——学习项目要熟悉度和资料，企业  生产在阿里云我会考虑 Alibaba Cloud Linux（内核优化+支持）"

### Q2. 21 个容器分别是什么？🔴
【追问1】中间件有哪些？
【追问2】为什么 SkyWalking 有两个容器？
【简答】9 中间件（含 SkyWalking OAP/UI）+ 11 微服务 + 1 前端 Nginx= 21 容器。OAP 是数据收集处理，UI 是可视化看板。
【深挖】
- **中间件（9）**：MySQL、Redis、Nacos、  RabbitMQ、ES、Seata、Sentinel、SkyWalking-OAP、SkyWalking-UI
- **微服务（11）**：gateway、sso、product、  front、order、search、seckill、  ums、ams、  resource、ai
- **前端（1）**：Nginx
- **SkyWalking 拆两个容器**：OAP（接收 agent 数据   + 存 ES）+ UI（可视化）——所以中间件是 9 不是 8  （别把 SkyWalking 重复计数）
**追问3：为什么 MySQL 放容器里？不放外面？**  放容器 = 统一编排（一条 compose 管全部）+ 环境一致（镜像  固定版本 8.0）。但数据库是**有状态服务**（数据是生命），  容器化必须解决三件事：  ① **持久化**：数据卷 csmall_mysql_data（✅ 做了，重建不丢）  ② **备份**（⚠️ 待改进，Q9）  ③ **高可用**（❌ 未做）  核心认知：**容器适合无状态应用；有状态服务容器化，持久化  + 备份 + HA 必须跟上**。企业生产其实更倾向**云 RDS**（云  厂商管备份/主从/高可用/监控）——应用容器化 + 数据库托管  是主流。你的定位：学习项目一站式合理，生产用 RDS
- **面试话术**："21 个容器里 9 个是中间件、11   个是业务服务、1 个是前端，每个容器一个职责，  compose 统一编排。MySQL 放容器是统一编排 + 环境一致，  但数据库是有状态服务——持久化我做了（数据卷），备份和  HA 是待改进；企业生产我会用云 RDS 托管"

### Q3. 容器间怎么通信？网络怎么配置？🔴
【追问1】compose 网络？
【追问2】服务发现怎么做的？
【简答】compose 定义了一个自定义网络 `csmall-net`，所有容器加入。服务名（如 `mysql`、`redis`）即 DNS 域名，容器间用服务名通信。
【深挖】
- **网络**：`networks: csmall-net`（  bridge 驱动），所有容器在同一网络
- **服务名通信**：`SPRING_DATASOURCE_URL:   jdbc:mysql://mysql:3306/...`，  `mysql` 是 compose 服务名，Docker 内部   DNS 解析到容器 IP
- **服务发现**：业务服务通过 Nacos 注册（不是靠   compose 网络），Nacos 是注册中心
- **端口映射**：**并非只有对外端口映射宿主机**（2026-08-28  实测修正）——中间件端口也全映射宿主机 0.0.0.0（Redis 6379/  MySQL 3306/Nacos 8848/ES 9200/Seata 8091...），安全组只开  22/80 挡住了公网，但宿主机网卡全监听。企业做法：中间件  端口改 `127.0.0.1:6379:6379` 绑定（TODO #24）；内部通信  走自定义网络（服务名 DNS）不受影响
**追问3：自定义网络和 Dubbo 是两个层面**：  自定义网络（Docker 层）= **传输通道**（容器能不能通、  服务名 DNS 怎么找——类比"道路"）；Dubbo（应用层）=  **服务发现 + RPC 调用**（类比"快递系统"）。  **Dubbo 的流量就跑在自定义网络上**（provider 注册到  Nacos 的是容器 IP 172.18.0.x，consumer 走网络访问）；  MySQL/Redis/Nacos 的流量也走同一条"道路"——网络管  "通不通"，Dubbo 管"怎么找 + 怎么调"
- **csmall-net 设计**（简单）：compose 单网段一锅烩（21 容器  一个 bridge 网络 + 服务名 DNS）。诚实差距：企业会分  **应用网/数据网**（数据库只接受应用访问 = 网络隔离纵深  防御，TODO #26）；类比打电话：网络=电话线路（连通性），  Dubbo=通讯录+拨号规则（发现+RPC，跑在线路上）
- 面试话术："compose 自定义网络让容器用**服务名互访**（  mysql/redis/nacos），这是 Docker 内部   DNS；业务服务间的高层发现交给 Nacos。  自定义网络和 Dubbo 是两个层面——网络是道路（连通性），  Dubbo 是快递（RPC 调用跑在道路上）"

### Q4. 健康检查怎么配置的？为什么重要？🔴
【追问1】healthcheck 有什么用？
【追问2】依赖关系怎么控制？
【简答】compose 给中间件配置了 healthcheck（如 mysqladmin ping、redis-cli ping），`depends_on` 用 `condition: service_healthy` 控制启动顺序，保证服务就绪后再启动依赖它的。
【深挖】
- **healthcheck 示例**：  
```yaml  mysql:    healthcheck:      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]      interval: 10s      timeout: 5s      retries: 10  
```
- **为什么重要**：如果不做健康检查，  服务可能"容器起来了但内部没就绪"，依赖它的服务启动就失败
- **启动顺序**：`depends_on: { mysql: {   condition: service_healthy }   }`，保证   MySQL 就绪才启动 SSO
- **真实踩坑**：resource 容器没配 restart，  Nacos 竞态导致 Exited(1) 后不自动拉起——加了   `restart: unless-stopped` 解决
- **你的 6 个 healthcheck**（compose 实证）：  MySQL=mysqladmin ping（带密码，能认证才算活）/  Redis=redis-cli ping（响应 PONG）/  Nacos=curl 8848/nacos/ / RabbitMQ=rabbitmqctl status /  ES=curl _cluster/health / Seata=wget 7091  ——**应用级检查不是 TCP 探针**（端口在听 ≠ 内部就绪）
- **Docker 三态**：starting（检查中）→ healthy / unhealthy  （连续失败超 retries）；参数 interval/timeout/retries/  start_period（启动宽限期，防启动慢被误判）
- **诚实点**：Sentinel/SkyWalking 没配（低风险——无服务  依赖它们启动）；11 微服务 compose 没配 HEALTHCHECK——  有 actuator /actuator/health 但没接进 Docker 探针（企业  /k8s 用 liveness/readiness，待改进）
- **Sentinel/SkyWalking 能配吗**（可以，P3 低优先）：  健康检查两用途——① 控制启动顺序（不需要：无服务依赖它们）  ② 健康可见性（有价值："监控的监控"）。现成配置：  Sentinel：`curl -f http://localhost:8858/`；  OAP：`wget http://localhost:12800`；  UI：`curl -f http://localhost:8080`。  影响面：Sentinel 挂=限流照跑（规则在 Nacos/本地）、OAP 挂  =agent 重连——都是"监控组件挂了不影响业务但要让你知道"，  healthcheck 是最便宜的监控；接 Prometheus 告警时一起补
- 面试话术：  "健康检查是容器编排的**关键**——它把'进程起来了'和'服务可用了'区分开  ，控制依赖服务的启动时机。我的 6 个中间件配了应用级检查  （mysqladmin ping/redis-cli ping/curl），不是 TCP 探针。  我还踩过没配 restart   导致容器挂了不重启的坑"

### Q5. 环境变量怎么管理？敏感信息怎么处理？🔴
【追问1】.env 文件？
【追问2】数据库密码等怎么不泄露？
【简答】敏感配置（数据库密码、JWT 密钥、API Key）通过 `.env` 文件管理，compose 用 `${VAR}` 引用，不硬编码。Spring 生产配置用环境变量注入。
【深挖】
- **.env 文件**：`/data/csmall/.env` 存   `MYSQL_ROOT_PASSWORD`、  `JWT_SECRET`、  `AI_API_KEY` 等
- **compose 引用**：  `${MYSQL_ROOT_PASSWORD}`，环境变量注入容器
- **Spring 配置**：`application-prod.  yml` 用 `${MYSQL_PASSWORD}` 占位符，  从环境变量读取
- **安全**：.env 加入 .gitignore，不上传仓库  （诚实修正：位置对了一半——**JWT_SECRET 生产值 = 代码默认  值没换**（2026-08-28 实测），clone 仓库就能伪造 token，  值要随机化，TODO #25）
**追问3：为什么敏感值不存 Nacos 配置中心？**  两条硬理由：① **Nacos 当前无认证**（实测无 token 读配置  200）——存了 = 网络可达就能读；.env 在服务器文件系统，  泄露面小得多（攻破服务器才拿得到）② **Nacos 本身是攻击  面**（历史出过认证绕过 RCE）——注册中心沦陷 = 全部配置  泄露，鸡蛋别放一个篮子
- **企业三级分离**（面试加分）：  非敏感配置（数据源地址/开关/规则）→ 配置中心 Nacos ✅  敏感配置（密码/密钥/API Key）→ **密钥管理服务**    （KMS/Vault/Secrets Manager，有审计+自动轮换）  密码明文 → 永远不出现（或加密存储）  核心：**配置中心管配置、密钥管理管机密，两码事**——  即使 Nacos 开认证，密码也不放配置中心
- **你的取舍**：.env 存敏感值（比无认证 Nacos 安全 ✅）；  升级到配置中心（TODO #4）时：非敏感进 Nacos、敏感留 .env  或引 KMS
- **KMS 简单了解**（认知即可）：用法 = 开通 → 存机密 →  RAM 授权 → 应用集成（最常用"加密后存配置"：密文放配置  中心，运行时 Decrypt 解密）→ 审计 + 自动轮换。成本 =  云 KMS 按量计费（小规模每月几十元级）、Vault 开源免费  自建。**你的项目不上**——单机单团队 .env 够用，优先级  排在 JWT 密钥随机化/MySQL 强密码/Nacos 认证之后
- **面试话术**："敏感信息全部走环境变量，  代码里只有占位符——这是部署安全的基本要求，密码、密钥、API   Key 都不写进代码。敏感值不进 Nacos：当前无认证（实测）+  Nacos 本身是攻击面；企业是三级分离——非敏感进配置中心、  敏感进 KMS/Vault 密钥管理"

### Q6. 服务器资源紧张怎么办？（内存调优）🔴
【追问1】内存怎么不够的？
【追问2】做了什么调优？
【简答】服务器 16G 内存，11 个 JVM + 9 中间件吃紧（93%）。通过 JVM 调优释放：Seata 2G→512M、OAP 1G→512M、微服务加堆外限制，降到 71%。
【深挖】
- **为什么吃紧**：11 个 Spring Boot JVM +   ES + Seata + SkyWalking，每个   JVM 有堆   + 堆外（Metaspace/线程栈/直接内存）
- **调优**：  
- Seata `-Xmx2048m → 512m`（实测堆只用     27MB，2G 浪费）  
- SkyWalking OAP `-Xmx1024m → 512m`  
- 11 微服务加 `MaxDirectMemorySize` /     `MaxMetaspaceSize` /     `ReservedCodeCacheSize` 限制
- **结果**：内存 93% → 71%，释放约 3G，可用从 1.1G → 4.4G（2026-08-04 调优后快照；当前 ~86% 见 11-服务器情况 Q5）
- **容器级缺口**（2026-08-21 实测）：**全部 21 容器  mem_limit=0**（无内存上限）——任何进程失控可直接吃满宿主  （历史杀过 ES）；R7 方案：全容器加 mem_limit + Nacos 降堆  + Swap 2G
- **依据**：用 `jstat -gc` 实测 Seata 堆使用，  Old Gen 只用 3.5%，证明 2G 堆浪费
- 面试话术："调优不是拍脑袋，我**先用 jstat   实测堆使用**——Seata 2G 堆实际只用   27MB，才敢降到   512M。数据驱动的调优，不是瞎改"

### Q7. 日志怎么管理？排障怎么看？
【追问1】日志在哪？
【追问2】SkyWalking 和日志的关系？
【简答】容器日志输出到 stdout，`docker logs` 查看。SkyWalking 做链路追踪，日志用 logback 配置级别。
【深挖】
- **日志**：所有服务日志输出 stdout，`docker   logs csmall-xxx` 查看
- **stdout 是什么**（追问3）：**标准输出流，不是日志文件  位置**——logback 控制台输出打到 stdout → Docker 捕获  stdout/stderr → `docker logs` 读的是**流不是文件**（容器  里通常没有日志文件）。12-factor 原则：日志=事件流，交给  运行环境采集（docker logs/ELK），应用不自己管日志文件
- **logback 五级**（追问3）：TRACE（最细，方法级/SQL 参数，  ⚠️ 秒杀曾 trace 刷屏改 info）/ DEBUG（调试）/ INFO（正常  业务）/ WARN（警告，如"二级分类没有三级分类"）/ ERROR  （业务/系统错误）。**过滤规则：设某级 = 显示该级及更高级**  （INFO 显示 INFO+WARN+ERROR）。生产配置 = 业务 INFO +  框架 WARN；级别太细是性能隐患（trace 刷屏的教训）
- **级别控制**：logback 配置（框架 WARN、业务   INFO），秒杀日志曾因 trace 刷屏改 info
- **SkyWalking 和日志**：SkyWalking   是链路追踪（调用链），日志是应用输出，两者配合（先看链路定位服务，  再看该服务日志查细节）
- **面试话术**："排障流程：SkyWalking   看调用链定位到哪个服务慢/错，然后 docker logs   看具体日志，再结合 ES/DB 数据验证。  stdout 是标准输出流不是文件——docker logs 读的是流；  logback 五级设某级显示该级及更高级，生产业务 INFO + 框架  WARN，trace 会刷屏拖性能"

### Q8. 遇到过容器不自动恢复的问题吗？
【追问1】resource 容器故障？
【追问2】为什么之前没重启？
【简答】遇到过！mall-resource 容器 Exited(1) 后没自动重启，原因是 compose 没配 restart 策略。加 `restart: unless-stopped` 解决。
【深挖】
- **故障**：resource 容器 2 天前 Exited(1)，  一直没起来（后台静默挂 2 天）
- **根因**：07-31 整栈部署时负载高，resource 启动时   Nacos gRPC 50s 未连上 → 注册失败 →   Spring   启动中止；且它是唯一没配 restart 的
- **修复**：加 `restart: unless-stopped`，  `docker compose up -d   mall-resource` 拉起
- **教训**：① 应用服务必须配 restart；② restart   只解决崩溃拉起，仍需监控告警防"静默挂 2 天"
- **排查六步**（面试讲述）：docker ps 看 Exited → docker  inspect 看 ExitCode/RestartCount → docker logs 找到  NacosException: Client not connected → 理因果（整栈部署  负载高 → gRPC 超时 → 启动中止）→ 对比发现唯一漏配  restart → 修复拉起
- **防复发三层**：① restart 全覆盖（崩溃自动拉起）✅  ② healthcheck + depends_on（依赖就绪才启动）✅  ③ 部署分批降负载（教训记录）✅  **诚实缺口**：主动告警未做（Q10）——restart 只能拉起  崩溃，静默挂/循环崩还是靠人工发现
- **再出现应急预案**：先看 RestartCount（**在涨=循环崩溃  起不来反复死；不变=restart 没生效/被停**）→ docker logs  找根因 → 分场景（Nacos 依赖未就绪 / OOM 被杀加 mem_limit /  配置问题）处理
- 面试话术："这是真实的运维事故——**容器挂了 2 天才发现**。  暴露了两个问题：restart 策略缺失 +   没有监控告警。我加了   restart，但更深刻的教训是要有主动监控。排查六步 +  防复发三层（restart/healthcheck/分批），诚实说告警是  根治，再出现先看 RestartCount 判断循环崩还是没生效"

### Q9. 数据库运维怎么做的？备份？
【追问1】数据备份？
【追问2】Schema 变更？

### Q11. 生产集群都在一台服务器上吗？K8s 能跨服务器管理容器吗？🔴
【追问1】演示级集群和生产级集群的区别？
【追问2】完全体 K8s 和 k3s 什么关系？
【简答】生产集群一定在多台服务器上。我们项目是**单机多实例 = 演示级**（只验证机制，机器宕机全挂）；**完全体 K8s 天生跨多台服务器管理容器**——调度、自愈、伸缩，节点宕机自动在其他机器重建。
【深挖】
- **高可用四级**：单机单实例（无 HA）/ 单机多实例（演示级，机器宕机全挂）/ 多机多实例（生产级 HA，机器宕机切流量）/ 多机房（同城双活、异地多活）
- **一句话**：单机集群 = 防"进程死"；多机集群 = 防"机器死"——**机器死才是生产最常见故障**（断电/磁盘坏/系统崩溃）
- **生产集群形态**：SLB 负载均衡（入口）+ 服务跨机器多实例 + Nacos 3 节点跨机器（Raft 多数派）+ MySQL 主从 + Redis 哨兵——**任何单点宕机流量自动切换**
- **我们项目**：单机 2 实例（TODO #4）= 演示级——价值是验证机制（负载均衡轮询/故障剔除/限流热更新），面试**只讲"验证了机制"不讲"高可用"**；单机资源有限，真实 HA 需多台机器
- **K8s 天生跨服务器**：  
- 架构：控制平面（API Server/etcd/Scheduler/Controller Manager）+ 多个 Node（每台服务器一个，跑 kubelet + Pod）  
- 核心能力：① **Scheduler** 把新 Pod 调度到资源空闲的节点 ② **自愈**——节点宕机，Controller 在其他节点自动重建 Pod ③ CNI（Calico/Flannel）跨节点网络互通 ④ 滚动更新、水平伸缩  
- 对比：**Compose = 管一台机器的容器；K8s = 管多台机器的容器，且机器挂了自动搬家**
- **完全体 K8s vs k3s**：同一个 API，k3s 轻量（单二进制 ~500MB）——单机可跑可学习，**同样能加 Node 变多机集群**（TODO #15）；单机 4C16G 跑 K8s 是大材小用，等真实多机需求再上
- **类比**：Compose = 一个管家管一栋楼的房间；K8s = 物业公司管多栋楼，哪栋塌了自动把住户搬去别的楼
- 面试话术："生产集群一定在多台机器：SLB + 服务多实例 + Nacos/MySQL/Redis 全跨机器冗余，任何单点宕机流量切换。我们项目是**单机多实例 = 演示级**——验证了负载均衡/故障剔除/热更新机制，但机器宕机全挂，所以只讲机制不讲 HA。K8s 天生跨服务器：调度、自愈、伸缩，节点宕机自动重建，和 Compose 管单机是两代东西；k3s 与完全体同 API，单机学习、加节点变多机"
