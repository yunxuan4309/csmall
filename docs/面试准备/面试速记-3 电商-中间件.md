# 面试速记-3 电商-中间件（面试前 5 分钟快速过）

> **所属**：面试速记版分册 3/7。完整深挖见 04-1/04-2-中间件选型.md。
> **场景**：被问"Nacos/Sentinel/Seata/SkyWalking/RabbitMQ/为什么选这个"时。

---

## 中间件一句话选型

- **Dubbo**：长连接 + 二进制，比 Feign 快
- **Nacos**：注册 + 配置一体的
- **Seata AT**：无侵入，undo_log 回滚
- **Sentinel**：实时流控 + 规则持久化 Nacos
- **RabbitMQ**：可靠消息（JSON 序列化 + 重试表兜底），秒杀削峰够用
- **Redis**：主从+哨兵 ✅ 已完成（2026-09-09，老机主 + **新机从库** + 3 哨兵；故障转移实测：选主 6.1s、客户端 9.1s 自愈、数据零丢失），边界 = 1 主 1 从两台机器，`min-replicas-to-write 1` 下**新机停则老机拒写**
- **ES**：倒排索引 + IK 分词
- **SkyWalking**：Agent 无侵入链路追踪

## Nacos 速记（Q1）

```
CAP：服务发现选 AP——过期地址=重试一次可接受，注册中心不可用=全站瘫痪；ZK 是 CP 不适合注册
AP/CP 切换：临时实例(ephemeral=true,默认)=AP 心跳剔除；持久实例(false)=CP(Raft)
注册中心=通讯录：登记 ip:port → 按名查 → 扩容多地址负载均衡 → 心跳剔除
配置中心=中央管理台：集中+热更新+多环境；但本项目配置走三层体系
三层配置：yml 默认值 → compose 环境变量(主力) → .env 敏感值(不进git)；宽松绑定 SPRING_*→spring.*
Nacos 实测(2026-09-12)：注册服务名 27 个(含 *-dubbo 与 providers:* 接口级)；配置 6 条全在 SENTINEL_GROUP：
  mall-seckill-flow-rules / mall-seckill-degrade-rules / mall-order-flow-rules
  / mall-order-degrade-rules / mall-sso-flow-rules / mall-ai-flow-rules → degrade 已建，不再空转
配置中心取舍：单机 1 实例用 .env+重启够用；多实例/热更新/多环境才必须上配置中心
Sentinel 坑：数据源配置≠规则本身(配了 dataSource 没建规则=空转)；flow 双重保险(代码+Nacos)
            degrade 曾 0 规则空转 → 已补规则(#5-P0,2026-09-08)并部署
Sentinel 重启：规则默认存内存，控制台配的重启即丢→持久化 Nacos/代码硬编码才不丢
```

## 选型逻辑速记（Q10）

```
四原则：生态一致(SCA:Nacos/Sentinel/Seata/Dubbo互操作零胶水)
       + 场景匹配(可靠MQ/吞吐Kafka/检索ES) + 可靠性优先 + 文档成熟
生态一致好处：集成成本低/BOM管版本/心智统一/坑可迁移
缺点(诚实)：供应商锁定/短板硬用/升级受制兼容矩阵/自动配置黑盒
你的定位：生态为主+场景优先的混合——MQ用Rabbit(非Rocket)、
         链路SkyWalking、搜索ES、网关Spring官方=场景压过生态
         原则是死的场景是活的
```

## Sentinel 速记（Q6）

```
vs Hystrix：Hystrix 停更(Netflix 2018)+无QPS限流+无热更新+无控制台
            Sentinel 阿里在养+三种限流(QPS/线程/并发)+三种熔断+三种流控效果
底层隔离：Hystrix=线程池(每依赖一池,开销大隔离彻底)；Sentinel=信号量(轻量零线程)
国内现状：Sentinel=Java 微服务事实标准(SCA 标配+阿里云MSE内置)
          Hystrix 退出/Resilience4j 无控制台用的人少/云原生下沉 Istio
你的用法：QPS=10 快速失败(grade=1,count=10,controlBehavior=0)，规则存 Nacos
          流控效果三选：快速失败/WarmUp预热/排队等待(匀速)
程度评估：4个@SentinelResource(秒杀/订单/支付/登录) + AI 3档 均已有规则(#5-P0 已补齐)
          flow: 秒杀QPS=10/新增订单20/支付订单20/adminLogin 10/ai-chat 5/ai-reason 10/ai-light 30
          degrade: 慢调用 RT>2s 比例0.5→熔断10s(秒杀+订单)；高级能力(热点限流/系统保护/授权/集群流控)未用；最该补热点参数限流
灰度发布：新版本先接小流量逐步放量(金丝雀)；分流靠 Gateway/Nacos/Istio
          Sentinel 管灰度期间流量保护(新版本保守限流+熔断+控制台监控)
```

## Seata 速记（Q5）

```
四种模式：AT(零侵入,自动undo_log,简单CRUD跨库) / TCC(手写Try/Confirm/Cancel,强隔离)
          SAGA(状态机编排+补偿,长事务) / XA(DB原生两阶段,性能差)
实际链路：@GlobalTransactional 仅2处——seckill提交(seckill→order→product 3库各1张undo_log)
          order 的已注释(库存改MQ异步,强一致拆掉=诚实点)
undo_log 区分：表=手动建(Flyway V4/V5/V14,Seata不建表)；数据=自动生成
          (代理数据源→UPDATE前before镜像→执行→after镜像→写rollback_info→提交删/回滚恢复)
选型：秒杀要即时一致(库存扣了订单必须成)，消息最终一致有延迟窗口 → AT
官方 bug 修复(防抄核弹⭐)：dubbo-filter-seata:1.0.2 branchType null NPE(Issue #6815)
          XID=全局事务身份证(IP:端口:事务号)，在 ThreadLocal，无事务 getXID()=null
          → 所有非事务 Dubbo 调用都会炸(浏览商品只是最先暴露)，不是它特有
          → 排除官方依赖+手写 XID filter(Consumer 塞 TX_XID 附件/Provider bind+unbind)
          Apache Seata v2.2.0 已修复(#6816)，升级后可移除
Redis 回滚是代码手动补偿(catch increment)，Seata 只管 DB=双保险
```

## SkyWalking 速记（Q4）

```
定位：APM 一体化(监控+追踪)；国产 Apache 顶级项目；vs Zipkin 需埋点 / Prometheus 只指标
名词：OAP=可观测性分析平台(后端大脑,收11800/存ES/UI8088) / APM=应用性能监控统称
Agent：官方配套 skywalking-agent.jar，-javaagent 字节码增强零侵入，寄生业务进程
        作用三层=插桩(Byte Buddy改字节码)+采集(traceId/span)+上报OAP
内存大正常：OAP 1.08G(堆512M+非堆缓冲) + ES 1.2G
        实测发现 ES 大头是 SkyWalking 不是商品搜索：sw_segment 9万段/天 +
        sw_metrics 50万条/天 ≈240MB/天(7天留存1.4G+)；商品索引(cool_shark_mall_ai)才 19~20 条文档
降采样：SW_TRACE_SAMPLING_RATE 千分比(1000=100%,100=10%)，省 ES 存储/CPU 不省 OAP 内存
        演示项目没降(要完整链路)，生产高流量才降；优化三板斧=调堆/降采样/BanyanDB
国产全家：SkyWalking / CAT(大众点评) / Arthas(诊断非追踪) / 鹰眼(未开源)
```

## RabbitMQ 速记（Q2）

```
三 MQ 底层：Rabbit=队列推模式(消费即删) / Kafka=分区日志拉模式(偏移量重放,百万吞吐的根)
            Rocket=借 Kafka 存储 + 事务/延迟消息(既要又要)
选型：秒杀要可靠不要吞吐——QPS10 只有 ~10 成功订单，Rabbit 几千/秒够；Kafka 留日志流
易运维 4 层：单组件部署 / 自带 15672 控制台(积压·消费者·消息可视化) /
             无 Kafka rebalance 疑难 / 内存磁盘水位自管理防 OOM
项目用法：2 队列 Direct 交换机 + AUTO ack(容器确认) + 重试 3 次 + 耗尽 reject 进死信 + 死信告警
          旧写手动 ack/nack、失败 nack 重入队 —— 实测会热循环+无限重投，故改 AUTO(#70)
          本地重试表(seckill_message_retry 每5s补发×3,先写表再发MQ防丢)
          JSON 序列化(跨版本兼容,旧消息 id=null 雪花补)
Dubbo 序列化：默认 Hessian2 二进制(RPC 求快)；JSON 留给 MQ/HTTP(求可读)
Kafka 业务：能用于事件流(美团/字节在用)，但至少一次要幂等、无死信延迟；
            秒杀量级没到不换，量到百万再迁+消费端幂等
重复消费：MQ 至少一次投递是设计→靠消费端幂等；死信解决不了重复
          项目防线=条件扣减 SQL(stock>=qty,第二次 rows=0 跳过)防超卖
持久化：order_queue durable(无兜底,丢了真丢)；seckill 非持久(重试表兜底)
         严格讲都该持久化，秒杀非持久是复盘发现的不一致
防抄话术：能讲出 ack 模式(AUTO+限次重试+reject 进死信)/重试表/JSON 三细节 = 自己写的
```
