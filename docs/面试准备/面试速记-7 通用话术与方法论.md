## 二、8 条通用话术（每条：适用 / 核心一句 / 可直接背）

### ① 「我最怕的不是 500，是 200 但是错的」——**静默失效**总纲

**适用**：任何"代码与线上不一致""配置设了不生效""功能看着正常但结果不对"的场景。
**核心一句**：**不报错 ≠ 生效；这类问题不自愈，只在你走到某条特定路径时才暴露 ⇒ 必须靠定期核对机制发现，不能等报错。**

> "项目里我遇到过三次**同一类**问题：① ES 索引的 mapping 和代码写的不一样（品牌过滤**恒 0 命中**、补全**恒空**）；② 模型侧依赖了一个**官方已公告停用**的别名，只是兼容层没撤，所以一切'正常'；③ MySQL 侧的**实体 / 库 / 建表脚本三方漂移**。
> 它们的共同指纹是：**不报错、不自愈、只在特定路径上暴露**。比如那个索引是更早版本建的、`mapping` 全空，而初始化类是 `if (exists) return` —— **永远不会被自动修好**；库表漂移平时不报错，是因为**全走自定义 Mapper XML**，手写 SQL 根本不带那些字段。
> 所以我的结论是：**这类问题必须靠定期核对机制去发现，不能等报错 —— 报错的时候通常已经是生产事故了。**"

**出处**：[[问题解决--代码与线上不一致的静默失效]] · [[问题解决--实体库表DDL三方漂移审计]] · 同类更早记录 [[问题解决--请求校验与静默失效]]

### ② 「断言失败时，第一个要验证的对象是断言本身」——**验证方法也会说谎**

**适用**：被问"你怎么保证你的结论是对的""测试/校验可信吗"。

> "我有一条很具体的教训：**断言失败时，第一个要验证的对象是断言本身**。当时有一条 TTL 断言一直失败，看上去像'锁没有 TTL'，追下去发现是 `getExpire(key, SECONDS)` 对 **1 秒**的 TTL **向下取整成 0** —— **代码是对的、断言是错的**；如果直接相信断言，我就会把**正确的代码改坏**。
> 同一批里还犯过一次：验收索引 mapping 时我用 `grep -c` 数关键字，**期望 4 实际返回 1**，因为 `grep -c` 数的是**行数**、而 mapping 是**单行 JSON** ⇒ **验收命令本身也要被验收**。"

**出处**：[[问题解决--本地双实例分布式锁验证方法]] §三坑 2 · [[问题解决--代码与线上不一致的静默失效]] §三

### ③ 「单实例跑不出价值；判据必须落在失败方」——**"怎么证明它生效了"**

**适用**：分布式锁 / 幂等 / 互斥 / 定时任务不重复执行 / 限流生效。

> "单实例跑不出锁的价值，也**证明不了任何事**。锁的价值恰恰体现在**没抢到的那一次**，而失败方的日志默认是 DEBUG 级、根本看不见 —— **只看成功方的'我修正了'日志，你无法区分'互斥生效'和'另一个实例压根没在跑'**。
> 所以我起**两个真实 JVM** 抢同一把 Redis 锁，用**可证伪的计数断言**：制造 **N 次**待处理状态，成功方日志**恰好 N 条**（多了就说明没互斥）；同时把失败方日志打开，拿到累计 **7 条**『未抢到锁，跳过本次执行』，而且这 7 条**跨两个任务** —— 把'互斥'从**单点巧合**变成**交叉证据**。收尾再断言：锁 key 为空（无漏锁）、状态值回到 DB 基准值、两个实例在注册中心都是 `healthy`。"

**出处**：[[问题解决--本地双实例分布式锁验证方法]] · [[问题解决--Redis加固与主从数据一致性]]

### ④ 「契约靠实测钉死；判生效值必须 yml + 代码默认值一起看」——**依赖外部系统的纪律**

**适用**：接入 LLM / 第三方 API / 中间件；被问"你怎么保证对方变了你不受影响"。

> "依赖外部系统时我的习惯是**契约靠实测钉死，不靠文档**。我发过一次最小请求（`max_tokens=1`，只读、成本可忽略）把**五个模型名**全测了一遍，发现生产依赖的那个别名**已被官方公告停用**、只是兼容层没撤；而且它和另一个别名**底层其实是同一个模型**，真正的差异只在'思考模式开没开' ⇒ 所以正确做法是用**官方的思考开关**，而不是继续换模型名。
> 这里还有一条我踩过的坑：**判某个配置的生效值，必须同时看配置文件和代码默认值** —— 我第一版只看代码默认值（10），而实际配置文件把它覆盖成了 **2**，结论直接判错。"

**出处**：[[问题解决--LLM链路的契约漂移与分层降级]] · [[AI模型名停用风险与thinking参数改造方案]]

### ⑤ 「只有两条铁律：可逆、可证」——**生产写操作的纪律**

**适用**：造数 / 数据修复 / 一次性脚本 / 批量变更。

> "往生产库做写操作，我只有两条铁律：**可逆**和**可证**。
> **可逆** = 必须有一份**唯一的清理依据**（我用影子登记表），**不能靠'猜哪些是假的'** —— 我实测过三个反例：清理顺序错会导致订单删不掉、`sales` 和库存这类**累加字段根本算不回去**、Redis 按 pattern 删会**误伤真实数据**；外面再加一层**整库快照**兜底。
> **可证** = 校验必须覆盖**没登记的表** —— 我就在这儿栽过：订单子表漏标了 3 行，而校验脚本打印了'✅ 通过'，因为它只校验'**登记表里出现过的表**'（根因还是个经典陷阱：**参数里的 SELECT 先开启了脚本事务，把快照定格在了'App 还没建订单'那一刻**）。
> 所以我的结论是：**造数的产出不是数据，而是'数据 + 一份能清干净的台账 + 一套能证明它对了的校验'。**"

**出处**：[[问题解决--生产造数的数据隔离与复核方法]]

### ⑥ 「不是代码有 bug，是路径被换掉了」——**什么时候会炸**

**适用**：被问"这个隐患的触发条件是什么""为什么不报错"。

> "这类问题**什么时候会炸**，我总结成一句话：**暴露条件不是'代码有 bug'，而是'路径被换掉了'**。
> 实体里有字段、库里没有列，平时不报错是因为**手写 SQL 只 SELECT 真实存在的列**；**一旦换成 MyBatis-Plus 的 BaseMapper**（按实体全字段生成 SQL），立刻就是 `Unknown column`。表整体缺失也一样 —— 不报错只是因为**那个功能从来没被调用过**，用到即 `Table doesn't exist`。
> 所以我把它当**定时炸弹**处理：登记 + 固定核对周期 + '要么补建、要么删实体'的明确决策，而不是等它自己炸。"

**出处**：[[问题解决--实体库表DDL三方漂移审计]] §一 · [[问题解决--请求校验与静默失效]]

### ⑦ 「错误结论比没结论更危险」——**你怎么证明自己的结论可信**

**适用**："你犯过什么错""怎么保证结论不是猜的""被追问后发现自己错了怎么办"。

> "**错误结论比没有结论更危险** —— 它会被写进文档、被后来的人继承。我踩过一次典型：把登录失败归因成'`$2a` 跨平台不兼容'，后来复核发现**逻辑上就站不住**（纯 Java 自实现、同 jar 跨平台必然一致），于是用 python **独立算了一遍哈希**做对照实验，证明那个哈希**压根就不是那个密码算出来的**，跟平台、跟版本都无关。
> 我做了三件事：**用实验推翻自己**、把错误归因**标注在文档里**、写清'当时为什么会误判'。
> 同类还有两处：**手抄正则抄错了位数**（后来改成从源码抽字面量做**机器比对**）、以及**误把 'HTTP 200' 当成成功**（这个项目鉴权失败也返回 200，错误在 body 的 `state` 里）。"

**出处**：[[问题解决--BCrypt错误归因复盘]] · [[10-问题解决]] Q11 · [[问题解决--生产造数的数据隔离与复核方法]] §四（G3/G5）

### ⑧ 「本地只能证明机制，不能证明容量和故障」——**边界诚实 + 不夹带纪律**

**适用**：收尾；被问"这套实验能说明生产没问题吗""顺手发现的问题你怎么处理"。

> "每次收尾我都会**主动划边界**：**本地只能证明'机制'，不能证明'容量和故障'** —— 跨机注册可达性、哨兵切换、网关跨机轮询、带宽压测，我留到服务器阶段做——**且已于 2026-09-09 全部做完并留下实测数字**：负载分布 60 请求精确 **30:30**（两实例）、Redis 选主 **6.1s** / 客户端 **9.1s** 自愈 / **数据零丢失**、停实例剔除通过；不过那仍是一次 exploratory test，**不是可回归的自动化测试**（企业做法是 Testcontainers 统一环境 + 故障注入 + 指标断言 + CI 每次跑）。
> 另一条纪律是**不夹带**：造数时顺带发现'**付了钱不扣库存**'（消费端类型不匹配 → 消息进死信又二次失败），我**只登记、不在这次变更里顺手改** —— 因为**每次变更都要能独立回滚**。
> 还有一层要主动说：**锁不是正确性的唯一保证** —— 异步复制下主挂瞬间锁可能双持，所以我的三层是'锁降低并发 + 幂等 + DB 约束兜底'，**验证的目标是'降低并发'而不是'绝不重复'**。"

**出处**：[[问题解决--本地双实例分布式锁验证方法]] §五 · [[问题解决--生产造数的数据隔离与复核方法]] §四（G8）

## 三、万能收尾三句（任何案例都能接）

1. **落到认知**："这件事让我对 X 有了实感 —— ①…②…③…"（把踩坑升维成一类问题）
2. **落到判据**："我的判据是 **Y**，而不是'看起来正常'。"（说出可证伪的东西）
3. **落到边界**："这套东西能说明 **A**，不能说明 **B**。"（主动划界，比被追问出来强）

## 四、反面清单（这些话别说）

| ❌ 别说 | ✅ 换成 |
|---|---|
| "日志看起来正常" / "跑通了" | "判据是 **…**；并且我用**未改动的服务/客户端成功率**做了对照" |
| "我改了就修好了" | "验收项 N 条 + **回归项** M 条（改 A 会牵动 B）" |
| "接口返回 200，说明成功了" | "这个项目**鉴权/业务失败也返回 200**，要看 body 的 `state`" |
| "应该没问题" | "我**没验证到**的地方是 X，边界是 Y" |
| "顺手把这个也修了" | "按**不夹带**纪律只登记，单独一次上（保证独立回滚）" |
| "文档里写着是 Z" | "我**实测**过生效值是 Z（yml + 代码默认值都看了）" |

## 五、一句话总纲

> **面试官验证的不是"你修过多少 bug"，而是"你能不能说清：什么是可证伪的判据、什么是你的边界、以及你什么时候推翻过自己"。**
