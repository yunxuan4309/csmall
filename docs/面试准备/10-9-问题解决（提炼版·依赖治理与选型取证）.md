### Q23. 要不要引入一个新框架：**不是查文档，是实测影响面**（"只影响一个模块"是错觉）

> 来源：[[问题解决--引入新依赖前的影响面取证]] §一 / §二（1.2~1.7）/ §三 / §四

【追问1】你想用 Spring AI —— 不引入框架，Agent 你自己造船吗？
【追问2】升 Boot 只是把 `mall-ai` 的版本提一提吧？为什么说这是全站的事？
【追问3】让 `mall-ai` 不继承根 pom、单独挂一套新 Boot，编译也能过 —— 这个方案为什么被你否掉？

【简答】**选型不靠查文档和感觉，靠"影响面实测"**：先量化"我到底缺什么能力"，再逐条对比候选方案"在本项目能不能落地"，最后用**一条决定性实测**定案 —— **版本下限会沿继承链放大**。因为 Boot 版本声明在**根 pom 的 `<parent>`**、**13 个顶层模块全体继承**，所以"升 Boot"从来不是"改一个模块"，而是**一整套 starter 矩阵重排 + 全站回归**。而本例的实测结论是：**Agent 不是框架，是一个循环 + 一份工具清单**，我们缺的只是一层薄编排。

【深挖】
- **认知前提：Agent 的本体只有三十来行** —— `for (round = 1..maxRounds)` 循环 + 带 `tools` 调一次 + `toolCalls` 为空即收敛 + `assistant(tool_calls)` 原样回灌 + 逐条执行 `role:"tool"` + 最后一轮流式吐答案。**框架省掉的正是这几十行，真正值钱的是周边生态**（多供应商抽象 / MCP / 向量库 / Advisor / 评测）—— 而这些我们**要么已有、要么用不到**。
- **候选方案逐条落地判定（4 条，全部给出可/不可）**：**手写薄编排 + OpenAI 兼容 HTTP ✅**（零新依赖、复用已有设施）；**Spring AI ❌**（🔴 **卡版本代际**：官方支持 **Boot 3.4.x→1.0.x / 3.5.x→1.1.x / 4.x→2.x**，**Boot 3.3 及更早不在支持范围**，而本项目是 **Boot 3.2.5、低于下限**）；**Spring AI Alibaba ❌**（同样卡代际，且多绑阿里生态）；**LangChain4j 🟡**（可脱离 Boot starter、**理论上能绕开升级**，但需另行核实版本，且仍是**新增重依赖**，收益不抵）⇒ **没有"既用 Agent 框架、又不升 Boot"的免费午餐**。
- ⭐ **决定性证据 = 影响面实测**：`pom.xml`（根，`artifactId = csmall`）的 `<parent>` 写着 **`spring-boot-starter-parent 3.2.5`**，`properties` 里 **`spring-cloud.version = 2023.0.3`**、**`spring-cloud-alibaba.version = 2023.0.1.2`**（**必须与 Boot 同代际**）；实测 **13 个顶层模块全部 `parent = csmall`**（mall-ai / ams / common / front / gateway-server / order / pojo / product / resource / search / seckill / sso / ums）⇒ **改根 pom 的 Boot 版本 = 整个反应堆一起改**。
- **代价要量化到数字**：Boot **3.2.5 → ≥3.4**、Spring Cloud **2023.0.3 → 2024.0.x**、SCA 换配对版本（⚠️ **SCA 发布节奏常滞后 = 首要风险，且不受自己控制**），springdoc 2.5.0 / Knife4j 4.5.0（与 Boot **强耦合**）、MyBatis-Plus 3.5.9 / mybatis-spring-boot 3.0.3 / PageHelper 1.4.7、Dubbo 3.3.2 / Seata 2.1.0 / Sentinel starter、Druid / Redisson / Quartz 全要跟着对齐；规模 = **13 个顶层模块 / 30+ 个 pom.xml / 需重建部署 11 服务 + 1 网关、跑在两台机器（老机 21 容器 / 新机 5 容器）**，必做回归 9 项（SSO+网关路由 / 秒杀跨机双实例 / Redis 主从哨兵 / Seata / Dubbo 全链路 / ES 搜索 / AI 全链路 / Sentinel 规则 / Nacos 注册与配置）。
- ⚠️ **"绕开限制"技术上可行 ≠ 应该做**：让 `mall-ai` **不继承根 pom**、单独挂 Boot 3.4 是可行的，但它依赖按 3.2.5 编译的 `mall-common` / `mall-pojo` / `mall-product-service` ⇒ fat jar 里 3.4 的 Spring Framework 会**在运行期覆盖传递依赖**，而 `mall-common` 的 Security Filter / Redis 配置是按 6.1 编译的 → **编译期无感、运行期 `NoSuchMethodError`**；Nacos/Sentinel/Seata/Dubbo starter 也得为它单选一套 ⇒ **一个反应堆两套 Spring 代际、两套 SCA，构建与排障复杂度翻倍**，收益只是"让一个演示模块用上框架"，性价比不成立。
- **决策：不是造船，是装船舵 🚢** —— 把方案拆成 **11 个部件**并标注 🆕 新建 / ♻️ 已有：`AiTool` 契约 + `ToolRegistry`（~60 行）、带 `tools` 的请求 + 解析 `tool_calls`（扩展 `DeepSeekAiClient` ~80 行）、`agentBranch` 循环（~100 行）、工具实现（~40 行/个）；会话（`SessionManager` Redis TTL 24h）/ 预算（`TokenBudgetService` 2 元/天）/ 并发闸门（`AiConcurrencyGuard` 上限 20）/ 限流（Sentinel 三组 + `AiUserRateLimiter`）/ SSE 流式 / 检索（`RagServiceImpl`）/ 降级兜底 **全部 ♻️ 已有** ⇒ **新增 ≈ 300 行（一半还是 Schema 与工具）**。
- **必须附"诚实的代价"与退出通道**：失去的四条（现成工具编排 / 多供应商切换 / 结构化输出 / 可观测）逐条给缓解（就是那 ~150 行且**已被实验 E/C/H 验证** / `base-url` + 模型占位符已可配且 DeepSeek 与硅基流动**都是 OpenAI 兼容协议，配置层可换** / **本来就必须做服务端二次校验** / 已有 `usage` 记账 + SkyWalking）；再给 **Spring AI 映射表**（`AiTool`→`@Tool`、`tasks.json`→`ChatOptions`、`agentBranch`→`ChatClient`+Advisor 或直接删、工具实现 **一行都不用改**）⇒ **不锁死将来的选择，本笔投入不浪费**。

**面试话术**
"Agent 我用的是 **OpenAI 兼容的 Function Calling 手写编排**，没上 Spring AI —— **不是不会用，是这个项目不该用**。Spring AI 官方支持代际是 Boot 3.4/3.5 对 1.0/1.1、Boot 4 对 2.x，**3.3 及更早不在支持范围**；我这边是 Boot 3.2.5，而 Boot 版本声明在**根 pom 的 `<parent>`** 里、**13 个模块全体继承** —— 我实测过，13 个顶层模块 `parent` 全是 `csmall`。所以接它就要连带升 Spring Cloud 2023.0.3→2024.0.x 和 SCA，还得把 springdoc、MyBatis-Plus、Dubbo、Seata 全套跟着换：**30+ 个 pom、11 服务 + 1 网关要重建、跑在两台机器上，还要做 9 项回归 —— 那是全站框架升级，不是加个功能**。我也想过'让 mall-ai 不继承根 pom、单独挂一套 Boot 3.4'，技术上可行，但 fat jar 里的 Spring Framework 会在**运行期覆盖**传递依赖，而 mall-common 是按旧代际编译的，这是典型的**编译期无感、运行期 `NoSuchMethodError`**，还要维护两套 SCA，性价比不成立。而 Agent 的本体其实**就是一个循环加一份工具清单**，三十来行；我把方案拆成 11 个部件逐个标注'新建还是已有'，发现会话、预算、并发闸门、限流、SSE、检索、降级**全是现成的**，真正要写的只有 ≈300 行、一半还是 Schema 和工具。所以我做的是**框架无关的薄编排**，并写下诚实的代价和到 Spring AI 的映射表 —— 将来真要迁，工具实现一行都不用改。一句话：**先在继承链上量影响面，再决定要不要那个 jar。**"

### Q24. 换掉一个外部依赖要跨三道门：**配置层能改 ≠ 抽象层能换 ≠ 失败有退路**

> 来源：[[问题解决--外部依赖的降级与可替换性]] §一 / §二 / §四（11.1~11.5）/ §五 / §六 / §七

【追问1】你说"换个 Embedding 平台只改配置" —— 配置能改，就等于代码解耦了吗？
【追问2】代码里明明有 try-catch，日志还写着"降级到全文检索"，怎么能说没有降级？
【追问3】向量维度这个配置，为什么你专门为它加了一个"启动自检"？

【简答】"换掉一个外部依赖"要跨**三道门**：**① 配置层能改**（地址 / Key / 模型名 / 维度是否外部化）、**② ⭐ 抽象层能换**（上游依赖的是**接口**还是**具体实现类**）、**③ ⭐ 失败有退路**（外部挂了，业务是**抛错**还是**回落基线**）。这道题最值钱的地方在于：② 和 ③ **最容易被假象骗过** —— ② 被"配置都能改，应该解耦了吧"骗过，③ 被"代码里有 try-catch，应该有降级吧"骗过。**能换 ≠ 配好；有 catch ≠ 有退路。**

【深挖】
- **① 配置层：这一层早就做到了（加分项）** —— 供应商的"三个坐标"全走环境变量（`AiProperties:85-91`；yml `embedding-api-key: ${EMBEDDING_API_KEY}`、`embedding-base-url: ${AI_EMBEDDING_BASE_URL:…}`、**`embedding-model: ${AI_MODEL_EMBEDDING:BAAI/bge-m3}`，代码里没有默认模型名**）；内部契约**供应商无关**（`float[]` / `List<float[]>`）；协议是**通用 OpenAI 兼容格式**（`POST {base}/v1/embeddings` + `{model,input,encoding_format}`，解析 `data[i].embedding` 与 `usage.total_tokens`）⇒ **任何 OpenAI 兼容平台（通义 / 智谱 / OpenAI / 本地 vLLM / Ollama 兼容层）换 `base-url` + `model` 即通**；另有超时可配、并发闸门覆盖、成本记账、维度单一配置驱动（`embedding-dimensions` → ES mapping 的 `dims`）。
- ⭐ **② 抽象层的真正缺口：上游直接依赖具体类** —— `RagServiceImpl:9,48` 与 `VectorSyncServiceImpl:5,36` 都是 `import …SiliconFlowEmbeddingClient;` + 按**具体类型**注入 ⇒ 换**协议**（非 OpenAI 兼容）、加**多供应商并存**、加**本地模型**、加**缓存 / 降级装饰器**，**每一件都得改上游源码**。一句话结论：**"换同一协议的另一家"✅ 做到了，"换另一种协议 / 另一种部署形态"❌ 没做到** —— **配置层解耦 ≠ 抽象层解耦**，缺的就是**依赖倒置**。
  - **处置（P1）**：新增接口 **`EmbeddingClient`**（`float[] embed(String)` / `List<float[]> embedBatch(List<String>)`，**出参不暴露任何 SDK / HTTP 类型**）；原类 `git mv` 改名 **`OpenAiCompatEmbeddingClient implements EmbeddingClient`**（**git 历史保留，状态 `R`**）；两处注入由**具体类改为接口** ⇒ 换协议 / 加本地模型 / 加缓存装饰器**只加实现、上游零改动**。⭐ **意外收益是可测性**：抽接口后 fake 只需实现 2 个方法，新增 `EmbeddingSelfCheckTest` **6 条**（**手写 fake、不用 Mockito**）。
  - ⚠️ **厂商名泄漏也会害人**：类名叫 `SiliconFlowEmbeddingClient`、日志 `"Calling SiliconFlow Embedding API"`、javadoc 写 **"免费调用"**（**这条早已过期，正是 #59 余额误判的来源**）⇒ 改名并清理，注释只保留"原名是什么、为什么改"。
- ⭐ **③ "以为有降级，其实没有" —— 一次读码复核（最值钱的坑）**：`RagServiceImpl.ask()` L82-89 在 `embeddingEnabled=true` 时**直接** `embed()` → `vectorSearch()`，**向量分支外没有 try-catch** ⇒ **硅基流动一挂，`ask()` 直接抛错，搜索报错**（不是降级）；而 `vectorSearch()` L352-355 的 catch 里日志写着 **"ES 向量检索失败，降级到全文检索"，实际却是 `return List.of()`** ⇒ **日志与行为不符**：检索变空、回答退化成"未检索到相关商品信息"，**排查时会被这条日志带偏**。
  - **处置**：`ask()` 改调新增的 **`vectorSearchWithFallback(question, topK)`** —— **三种失败都回落 `fullTextSearch()`**（embedding 调用失败 / ES 向量检索失败 / 向量结果为空）⇒ **语义能力降级，但搜索仍可用**；并把那条日志改成"**（是否回落全文检索由调用方决定）**"，与实际行为一致；同步侧也补：`syncAll()` 里 `embedBatch` 抛错原本**整批 catch 跳过**（该批商品**完全进不了索引**）→ 降级为"**仅全文索引**" + 新增 **`vectorDegraded` 计数** + 汇总 **WARN 显式暴露"其中 N 条向量化失败"**；`syncSpu()` 把 `embed()` 包进 try（原本在 try **之外**，单条更新完全不同步）。
  - **设计原则（为什么这么改）**：**外部依赖故障不应放大成"功能不可用"** —— **语义检索是增强、全文检索（BM25）是基线**，embedding 挂了就掉到基线；而且 **降级必须可见**（显式日志 / 计数），否则就是**静默降级** —— 那是**比报错更难查**的故障形态。
- **④ 第五道门（我在复核里补出来的）：建索引后不可变的量必须"启动即校验"** —— 全仓 `embeddingDimensions` 只出现在 `AiProperties` 与 `EsIndexInitializer`，**没有任何地方校验"返回向量长度 == 配置维度"**；而 **ES `dims` 建成后不可改** ⇒ 换成 768 / 1536 维的模型时，**忘改配置**或**改了没删索引重建**，**两种错都只在运行时暴露**。加固 = **P0 `EmbeddingSelfCheck` 启动探针**：**维度不一致 → 抛异常、启动失败**并给出"模型返回 N 维、配置为 M 维，请同步改 `embedding-dimensions` 并**删索引重建**"的可操作报错；**网络 / 余额 / 401 / 超时 → 只 WARN、不阻断启动**（把"外部 API 挂了"放大成"**服务起不来**"比降级更严重）；`embedding-enabled=false` 时**完全不调用外部接口**（零副作用、零 token）。⭐ 必须用 **`@DependsOn("embeddingSelfCheck")`** 而不是两个各自 `@PostConstruct` —— 后者**无顺序保证**，若 `EsIndexInitializer` 先跑就会**按错误维度把索引建出来**。另配 P2（把"改维度 = 改配置 + 删索引重建"写进代码注释与 yml）、P3（`encoding_format` 可配化，新增 `embedding-send-encoding-format` 默认 true）。
- 🔍 **复核又抓出 3 个真实问题（这部分最能体现"改完要再看一遍"）**：**① `syncAll` 的 `vectors.get(i)` 越界** —— `embedBatch` 的返回**不保证"条数 == 入参条数"**（少返 / 部分失败都可能）⇒ 抛 `IndexOutOfBoundsException` 被外层 catch 成"整批同步失败"，**等于把刚修好的降级又绕了回去**；改为 `i < vectors.size()` 才取 + 计入 `vectorDegraded`。**② `vectorSearchWithFallback` 的 null / 空向量** —— `null` 会以 **NPE** 形式被 catch（行为对、日志难读），**空数组**则白跑一次 ES 检索 ⇒ 显式判断 `null || length == 0` 直接回落。**③ `getAllSpus()` 两处 NPE** —— `getList()` 可空；🔴 **`getTotalPage()` 声明是 `Integer`（可空）**，直接比较会**自动拆箱 NPE**；改为 **"空页即到底"作主终止条件 + `MAX_PAGES = 200` 防御上限 + 触顶 WARN**（既不会无限循环，也不会静默截断）。
- **验收：靠读码复核 + 用例，不是靠"看起来没问题"** —— 补齐降级 / 容错用例后 `mall-ai-webapi` 从 **56 → 82 项**测试全绿（新增 `EmbeddingSelfCheckTest` **6** + `RagServiceImplVectorFallbackTest` **6** + `VectorSyncServiceImplDegradeTest` **14**），8 个反应堆模块 BUILD SUCCESS。其中⭐ **测试接缝（test seam）**手法可直接讲：`vectorSearchWithFallback` 原是 `private` 且依赖具体类 `ElasticsearchClient`（难伪造），处置是**只把可见性放开为包级（不改任何行为）**，同包测试**只重写两个检索入口**（`vectorSearch` 伪造"ES 挂了/返回空"、`fullTextSearch` 返回标记结果），而 `embeddingClient.embed()` 调用、**三条降级判断**、日志**仍走真实代码** ⇒ 测到的是**真实降级逻辑**，不是"把整个类 mock 掉"的空壳。
- ⚠️ **纪律与边界**：这类加固是**改代码**，按纪律**单独窗口、不夹带**；而且**开"生产启用向量检索"这个开关之前必须先补退路**，否则等于把一个**第三方服务的可用性绑到核心搜索**上（该开关的前置已解除、尚未开启）。另附一条环境坑：`mvn install` 在本项目 AI 沙箱里**必然失败**（要写工作区之外的 `C:\Users\<用户>\.m2\repository`，报错形态像 Maven 故障、其实是沙箱），正确姿势是**反应堆内构建** `-pl mall-ai/mall-ai-webapi -am test`。

**面试话术**
"我对外部依赖（这里是 Embedding / 向量检索）做过一次完整的『可替换性』体检，用**三道门**讲最清楚：**① 配置层能改** —— 平台地址、Key、模型名、维度全在配置里，协议走通用 OpenAI 兼容格式，所以换一家**同协议**的平台只改环境变量、不动一行代码。**② 抽象层能换** —— 这才是当时真正的缺口：上游 `RagServiceImpl` / `VectorSyncServiceImpl` 直接注入的是**具体类**，没有接口，于是『换协议、加多供应商、加本地模型、加缓存 / 降级装饰器』每一件都得改上游源码；我抽了 `EmbeddingClient` 接口（出参只有 `float[]`，不暴露任何 SDK / HTTP 类型），实现改名 `OpenAiCompatEmbeddingClient`，上游改成按接口注入 —— 这才叫**依赖倒置**；顺便清掉了把**厂商名写进类名、注释里还写着'免费调用'**这类会误导后人的东西（那条过期注释真的害我们误判过一次），抽完接口还白捡了可测性：fake 只要实现两个方法，6 条启动自检用例手写就够。**③ 失败有退路** —— 这条我踩过一个很典型的坑：catch 块里写着『ES 向量检索失败，降级到全文检索』，实际却是 `return List.of()`，**根本没有降级**；更糟的是**这条假日志会在排查时把人带偏**。我补了 `vectorSearchWithFallback`：embedding 调用失败 / 向量检索失败 / 向量结果为空，**三种情况都回落全文检索**，同步侧也改成『向量化失败就只写全文索引 + 计数 + WARN』，坚决不做**静默降级**。加固时我坚持两条判据：**语义检索是增强、全文检索 BM25 是基线**，外部挂了就该掉到基线，而不是让搜索整体不可用；**要区分确定性配置错误与瞬态外部故障** —— 向量维度写进 ES mapping 后**不可改**，所以维度不一致我让**启动直接失败**并给出『改配置 + 删索引重建』的步骤，而网络 / 余额 / 401 / 超时只 WARN、不阻断启动。最后**改完我又自己复核了一遍**，抓出三个真问题：批量接口返回长度不是契约导致 `get(i)` 越界、null / 空向量没显式回落、分页依赖可空 `Integer getTotalPage()` 会**自动拆箱 NPE** —— 修完补用例，`mall-ai-webapi` 从 **56 条涨到 82 条全绿**。一句话：**『配置能改』不等于『实现能换』，『写了 catch』不等于『有降级』。**"

### Q25. 配置可配化的两个坑：**必须用显式占位符** + **契约实验要留总表（13 格）**

> 来源：[[问题解决--LLM链路的契约漂移与分层降级]] §六 / §七

【追问1】你说模型名"全可配、改名不重编译" —— 凭什么保证环境变量真的被吃到了？
【追问2】把模型名抽到配置就够了？如果官方出了新模型，你还得改代码吗？
【追问3】为什么要花时间做 13 次契约实验、还专门留一张总表？

【简答】两件事，都是"可配化"的另一半：**① 显式占位符** —— 环境变量绑定的映射规则**比直觉窄**（`chat-model` 对应的是 `COOXIAO_AI_CHATMODEL`，**去横线**；写带下划线的**不映射**），所以**不能指望 Spring relaxed binding 兜底，必须写显式占位符**；**② 契约实验总表** —— 写代码前先把 A~M **13 格契约**测出来并留表，**下次换模型 / 改参数时，边界是查表而不是重新踩坑**。

【深挖】
- **改造前的现状是"半可配"（实测）**：API Key `${AI_API_KEY:…}` ✅、API 地址 `${AI_API_BASE_URL:…}` ✅；但 **chat 模型 `chat-model: deepseek-chat` 是字面量 🔴**、**embedding 模型 / 地址也是字面量 🔴**；向量维度 ✅ 且 `EsIndexInitializer` 真读了它（⚠️ 可改但**需重建 ES 索引**）。**两个结构性缺口**：① **2 处模型名硬编码在代码里**（`ChatServiceImpl:316` 的 `"deepseek-chat"`、`:367` 的 SSE `"deepseek-v4-flash"`）；② **prod 未覆盖 `cooxiao.ai` 段** ⇒ 生产模型名来自 **jar 内的 `application.yml`** ⇒ **想换模型必须重编译**。
- **两层设计**：**第 1 层** 消灭硬编码 + 模型名外置（`chat-model: ${AI_MODEL_CHAT:deepseek-v4-flash}`、`embedding-model: ${AI_MODEL_EMBEDDING:BAAI/bge-m3}`、`embedding-base-url: ${AI_EMBEDDING_BASE_URL:https://api.siliconflow.cn}`）；**第 2 层能力档位**把**"任务语义"与"模型 id"解耦** —— `models:` 逻辑档位 → 实际 id、`tasks:` 任务 → 档位 + 思考模式 ⇒ **代码里只出现 `TaskType.CHAT` / `TaskType.JSON`，永不出现模型名**；**官方改名 = 改一个环境变量 + 重建 `mall-ai` 一个容器**，出新档位 = 加一行 yml、**代码零改动**。
  - ⚠️ **落地形态与草图有差异**（别照草图讲）：档位层**只保留 `flash` / `pro` 两档**（**embedding 不放进档位表**，仍是独立标量 `embedding-model` —— 它属于**另一个供应商**、也不是"思考 / 非思考"的档位概念）；任务层由 **`AiTask` 枚举**（`CHAT` / `JSON` / `EXPAND` / `AGENT` / `COMPARE`）承载；**缺失档位启动不报错、调用时报明确错误**（`modelFor()` 抛异常并提示检查 `cooxiao.ai.models`），并在启动打印一次"**任务→档位→模型 id / 思考模式**"路由表。
- ⭐ **坑 1（隐性，最容易静默失效）：必须用显式占位符** —— `cooxiao.ai.chat-model` 对应的环境变量是 **`COOXIAO_AI_CHATMODEL`（去横线）**；写 `COOXIAO_AI_CHAT_MODEL`（带下划线）**并不直接映射** ⇒ **"可配"会静默失效**（配了不生效、还不知道）。所以与项目既有 `api-key` / `base-url` **同风格写显式占位符**，不靠 relaxed binding 兜底。
- **顺带清掉的 9 项硬编码（含 1 处结构性问题）**：① `"deepseek-chat"`（`ChatServiceImpl:316`）② `"deepseek-v4-flash"`（`:367`）③ `temperature 0.7`（`:369`）④ `max_tokens 2000`（`:370`，**偏紧**，见实验 D/I）⑤ `temperature 0.3`（`DeepSeekAiClient:82`）⑥ 🔴 **SSE 自建 body + 自建 `Authorization`**（`ChatServiceImpl:354-373`）—— **与客户端重复一份请求逻辑**，**改模型要改两个地方**，收敛为 `AiClient.streamChat(...)` 后"模型 / 思考 / 温度 / max_tokens 只有一处"；⑦ yml 里的模型名 / embedding 地址字面量 → 显式占位符；⑧ **`compare-model` 死配置**（`AiProperties:22` + yml，**全仓库零引用，实测确认**）→ 删除；⑨ **`DeepSeekAiClient.embed/embedBatch` 死代码**（`:180-235`，无人调用，**真调用必失败** —— 打的是 DeepSeek 地址 + 硅基流动模型名）→ 已删除。
- ⭐ **坑 2（方法论）：契约实验要留总表** —— 前 10 格是 **#58 / P0** 阶段（模型契约、tools 可行性、互斥规则），**K/L 两格是 P1 补的**（流式 + tools），**M 是 P1 加固补的**（`tool_choice=required`）。**写代码前先把契约测出来**是本项最省时间的习惯；**留表的意义 = 下次改模型时，边界是"查表"而不是"重新踩坑"**。13 格的关键结论（A~M）：
  - **A** `thinking: disabled` + json mode → 200、**无 `reasoning_content`**、content 干净 JSON ⇒ ✅ 开关从根上生效；
  - **B** `thinking: enabled` + `tools` + 不带 `reasoning_content` → 🔴 **400**（`The reasoning_content in the thinking mode must be passed back to the API.`）⇒ 400 规则**实测复现**；
  - **C** `thinking: disabled` + `tools` + 不带 → **200** ⇒ ✅ **"工具轮用 disabled"的设计成立**；
  - **D** `thinking: enabled` + `tools` + **带** `reasoning_content` → 200（reasoning **103**、**content 0**）⇒ 规则只因缺字段；⚠️ 顺带暴露"**思考吃满**"；
  - **E** `thinking: disabled` + `tools` + "推荐5000以内的手机" → 200、`finish=tool_calls`、参数 `{"keywords":"手机","budgetMax":5000}` ⇒ ✅ **P0 可行性证实**；
  - **F** `tools` + **`response_format: json_object`** → 200 但 **`tool_calls` 为空** ⇒ 🔴 **新坑：两者互斥**；
  - **G** `thinking: enabled` + `tools` + 全新提问 → 200、`tool_calls` 1 个 ⇒ 推理模式也能调工具，但需维护 reasoning 回传；
  - **H** **完整两轮循环**（工具轮 disabled）→ round1 `finish=tool_calls`；**round2 `finish=stop`、`content_len=272`、输出真实推荐表格** ⇒ ✅ **循环端到端会收敛、会出最终答案**；
  - **I** `reasoning_effort=low/high` → 均 **200**；但 `max_tokens=120` 时 **reasoning 183/174、content 均为 0** ⇒ ⚠️ 参数可用但**思考极耗 token、`max_tokens` 必须留足**；
  - **J** **SSE 流式 + thinking** + `include_usage` → **129 行**（**content 分片 38 / reasoning 分片 88**、usage chunk 有、`[DONE]` 有）⇒ ✅ 现有解析器只读 `delta.content` 与 `usage`，**reasoning 被安全忽略、SSE 改造无破坏**；
  - **K** **流式 + `tools` + disabled** → `finish_reason=tool_calls`，`tool_calls` **20 行分片**、`arguments` 被切成 **19 段**（`""`→`{`→`"`→`keywords`→…→`}`）；首片带 `id`+`name`、后续只有 `arguments`；**同一响应里先有 13 个 `content` 分片（英文 preamble）再出现 tool_calls** ⇒ ✅ 唯一正确姿势是"**按 `index` 拼接连缀 arguments**"；⭐ preamble 证明"**products 之前先缓冲正文**"是必需的，否则前端会**先收正文、后收商品**；
  - **L** **K 之后回灌 `role:"tool"` 结果继续流式** → `content` **112 个分片**（真正逐字）、`tool_calls`=**0**、`finish_reason=stop`、usage 1 行 ⇒ ✅ 收敛轮天然流式、不再调工具，且 usage 可记账；
  - **M** **`tool_choice: "required"`** → **200**、`finish_reason=tool_calls`，**即使输入是"你好"也被强制去搜**（`{"keywords":"你好"}`）⇒ ✅ 官方兼容该参数、可用于"商品类问题首轮强制检索"；⚠️ **但不能对所有消息都强制**（"你好"也会白搜一次）。
  - **实验带来的 5 条方案修正**：① 工具轮**不能与 `response_format` 共存**；② SSE 的 `max_tokens: 2000` **应改读配置**（实测 J 中 reasoning 分片是 content 的 **2.3 倍**）；③ `DeepSeekAiClient.embed` 是**死代码**；④ 流式下 `tool_calls.arguments` **按 index 分段到达、必须拼接**（不能假设一条分片就是完整 JSON）；⑤ 工具轮会**先吐 preamble 正文**再吐 tool_calls ⇒ 流式 Agent 必须**缓冲正文**直到商品列表发出。
- **落地与验证（2026-09-10，模型配置可配化已实施并部署生产）**：路由日志**恰好 1 次**（修双 bean 前是 2 次）、`/ai/search` 5s 返回 AI 重排说明、`/ai/ask` 4s 返回完整推荐、`ai:daily_cost` **0 → 0.002492 元**、`content 为空` / `reasoning` / 4xx 告警均 **0**；**9 项硬编码全部清零** + 新增 2 个测试类（yml→Java 绑定 / 请求体规则）。
- ⚠️ **诚实边界**：本节只讲**已完成**的"配置可配化（#58 已部署）"与"13 格契约实验总表（A~M）"这两件事；Agent 链路还有一段**并发压测**属于未完成的任务，**不在此展开**。

**面试话术**
"模型这块我做了**可配化**，但真正的收获是两个坑。**第一，必须用显式占位符**：我一开始的现状是**半可配** —— Key 和地址是占位符，`chat-model` 却是**字面量**、代码里还有两处硬编码模型名，而且 prod 没覆盖 `cooxiao.ai` 段，所以生产模型名其实来自 **jar 里的 application.yml，想换模型必须重编译**。我把模型名全外置成 `${AI_MODEL_CHAT:…}` 这种**显式占位符**，再加一层**能力档位** —— 代码只说'我要 JSON 任务'或'我要对话任务'，档位到实际模型 id 的映射放在配置里，服务启动还会打一张'任务→档位→模型'的路由表；这样官方**改名、换代，我只改一个环境变量重启一个容器**。这里有个容易静默失效的细节：**不能指望 Spring 的 relaxed binding** —— `cooxiao.ai.chat-model` 对应的环境变量是 **`COOXIAO_AI_CHATMODEL`（去横线）**，写带下划线的反而不映射，所以我坚持显式占位符。**第二，契约实验必须留总表**：我在写代码前把 A 到 M 一共 **13 格契约**全测了一遍并留了表 —— 比如 **`tools` 和 `response_format: json_object` 互斥**（200 但 `tool_calls` 为空）、**thinking 模式下不带 `reasoning_content` 会 400**、**流式下 `tool_calls.arguments` 是按 index 切成 19 段到达的、必须拼接连缀**、**工具轮会先吐一段 preamble 正文再吐 tool_calls，所以流式 Agent 必须缓冲正文**，还有 **reasoning 分片是 content 的 2.3 倍、`max_tokens` 必须留足**。这张表的价值是**下次换模型、改参数时，边界是查表而不是重新踩坑** —— 这 13 格当场就带出 5 条方案修正。最后说一下结果：**9 项硬编码全部清零**（还顺手删了零引用的死配置和一处真调用必失败的死代码，并把 SSE 里重复造的第二份请求逻辑收敛到客户端一处），上线后路由日志恰好 1 次、两个接口分别 5s / 4s 正常返回、成本记账从 0 走到 0.002492 元、告警全 0。"
