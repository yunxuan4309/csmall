### Q0. 你的 AI 功能算 Agent 吗？Spring AI 是什么？🔴

【追问1】Agent 的核心特征？
【追问2】为什么不用 Spring AI？未来要换怎么办？

【简答】
两个项目都是 **RAG 应用，不是 Agent**——流程写死，无自主规划/多步循环；
IoT 有**工具调用雏形**（调参 = 一次 Function Calling）。Spring AI 没用到
（代码实证：两项目 pom 无 spring-ai/langchain 依赖），手写 HTTP 客户端。

【深挖】
- **Agent 四特征**：① 自主规划（LLM 决定下一步做什么）② 工具调用（Function Calling：调外部 API/函数）③ 多步循环（ReAct：想→做→看结果→再想）④ 记忆。类比：Agent=有自主权的员工；RAG 应用=只会照流程走的问答机
- **LLM 是什么**：Large Language Model 大语言模型——海量文本训练的语言模型，理解/生成自然语言。关键认知：① 学的是语言规律，不是数据库 ② **不知道你的私有数据**（→ RAG 的意义）③ 知识有截止日期 + 会幻觉 ④ 按 token 计费（→ 预算控制）。类比：读过海量书的优等生，需要"开卷考试"。⚠️ 区分：deepseek-v4-flash = LLM（对话/生成）；**BGE-M3 = embedding 模型，不是 LLM**（把文本转成向量的"翻译官"）
- **Function Calling 机制（LLM 的"手"）**：
  - 流程：① 请求带 tools 声明（name + description + parameters JSON Schema = 给 LLM 的"菜单和规则"，参数类型/必填/枚举都约束）② LLM 决策返回 **tool_calls**（不回普通文本，回"要调 search_products，参数 xxx"）③ **代码执行工具**（LLM 永远不执行，只点菜）④ 结果以 role=tool 回填 → LLM 再生成最终回答
  - 类比：LLM = 点菜的客人（说"宫保鸡丁微辣"），代码 = 厨师（做菜端回来客人评价）
  - vs 现在项目的 extractSearchIntent：现在是"让 LLM 输出 JSON 再解析"（文本约定，易解析失败）；Function Calling = 协议化、结构化、官方支持
- **ReAct 细节（Agent 的"循环"）**：Reasoning + Acting 交替：Thought（想）→ Action（调工具）→ Observation（看工具结果，回填继续）→ 再想……直到 Final Answer。三个终止条件：① LLM 输出最终答案（不再要工具）② 最大轮数 3~5（防死循环烧钱）③ 预算超限兜底。类比：侦探破案——看线索→走访→拿到新线索→再想，直到破案
- **RAG 职责（在 Agent 里的定位）**：RAG = Retrieval-Augmented Generation，先检索再生成，职责 = 给 LLM 喂它不知道的私有数据（开卷考试）。Agent 架构四层：知识层 = RAG（提供事实）/ 决策层 = LLM（决定做什么）/ 行动层 = Function Calling（执行）/ 流程层 = ReAct（循环）。**在 Agent 里 RAG 降级为工具之一**（search_products 工具内部就是 RAG pipeline）。一句话：RAG 管"知识有没有"，FC 管"手能不能做事"，ReAct 管"脑会不会循环决策"
**两项目对照**：

| 特征 | 电商导购 | IoT 助手 |
|------|---------|---------|
| 自主规划 | ❌ 七段流水线写死 | ❌ 三段式写死 |
| 工具调用 | ❌ 无 | ⚠️ 雏形（自然语言调参） |
| 多步循环 | ❌ 单次问答 | ❌ 单次 |
| 记忆 | ⚠️ Redis 会话（聊天记忆） | ⚠️ 会话 + 2min 响应缓存 |

> IoT 雏形说明："调阈值到30" → LLM 识别 UPDATE_POLICY 意图 → 调后端策略接口改真实参数 = 一次 Function Calling（详见 02 文档 Q3）
> 详细对照见 Q12（诚实边界）
- **差什么（升级路径）**：① **规划层**（让 LLM 决定"查知识库/调设备/先看告警再综合"，而不是代码写死）② **多步循环**（执行后结果喂回 LLM 再决策）③ **工具路由**（暴露多个工具让 LLM 选）。实现 = Spring AI Function Calling / LangChain4j + ReAct 循环
- **Spring AI**：Spring 官方 2024 年推出的 AI 应用框架——ChatClient 统一对话（换模型只改配置）/ **Function Calling**（声明 Java 方法为工具，做 Agent 的地基）/ 结构化输出 / RAG 抽象（EmbeddingModel + VectorStore）。类比：**像 Spring Data 统一数据库一样统一大模型调用**
- **Spring AI 长什么样（重要认知：它不是一个独立框架，就是 Spring Boot 的一个 starter）**：
  - 项目结构 = **普通 Spring Boot 项目零变化**（pom + application.yml + @RestController）——引 `spring-ai-starter-model-openai` 依赖 + yml 配 `spring.ai.openai.api-key/base-url/model`，自动装配出 ChatClient Bean，直接注入用（同 spring-boot-starter-data-redis 的套路）
  - 代码形态：`chatClient.prompt().user(q).call().content()`（≈ DeepSeekAiClient.chat）；工具 `@Tool` 注解方法 + `.tools(new XxxService())`，**ToolCallingAdvisor 自动跑完整工具循环**（≈ 手写 ReAct）；流式 `.stream().content()` 返回 Reactor Flux（≈ 手写 SSE）
  - **对照省了什么**：手写 DeepSeekAiClient → ChatClient；extractSearchIntent 输出 JSON 再解析 → `.entity(类)`；方案 P0 手写 Function Calling → `@Tool`；方案 P1 手写 ReAct 循环 → ToolCallingAdvisor 自动
  - **不是"像" Spring Boot，是"就是"**——加依赖换客户端，Controller/业务逻辑不动（印证"未来切换只改 mall-ai 内部"）
  - 参考：[官方 ChatClient 文档](https://docs.spring.io/spring-ai/reference/api/chatclient.html)、[Tools 文档](https://docs.spring.io/spring-ai/reference/api/tools.html)
- **项目为什么手写不用它**（修正版，别用"21 容器"当理由）：
  ① 展示底层原理（SSE 解析/JSON 拼装/token 计算，学习价值）
  ② **收益兑现问题**：Spring AI 价值 = 多模型/多平台抽象——只有 DeepSeek 一个接入点，抽象收益为 0；同时接多个模型时才划算
  ③ OpenAI 兼容协议：换平台只改 base-url + key，手写成本已很低
- **未来切换成本低（用户观点正确）**：改 Spring AI 只动 mall-ai 模块内部（DeepSeekAiClient → ChatClient），AiController/对外接口/其他 10 个服务**零感知**——独立服务 = 内部实现随便换，这就是微服务模块边界价值（呼应 Modulith）
- 话术："两个项目是 RAG 应用不是 Agent——流程写死无自主规划；IoT 有工具调用雏形（调参=Function Calling），差规划层+多步循环，升级用 Spring AI Function Calling。项目手写没上 Spring AI：展示底层+单接入点抽象收益小；但未来切只改 mall-ai 内部，对外接口不变——这个我评估过"

### Q1. AI 智能导购做了什么？核心流程？🔴

【追问1】RAG 是什么？
【追问2】完整流水线有哪些阶段？

【简答】
AI 导购实现了一条 RAG 流水线：用户自然语言 → 意图识别 → 
查询扩展 → ES 多路召回 → 向量检索 → 重排序 → 
SSE 流式输出。

【深挖】
- **RAG**（Retrieval-Augmented 
  Generation）：先检索（Retrieval）再生成（
  Generation）——从商品库检索相关内容，
  喂给大模型生成回答。
  解决大模型"不知道你的商品数据"的问题
- **完整流水线**：
  ```
  用户输入 → 意图识别(DeepSeek解析JSON)
    → 查询扩展(同义词，"衣服"→"男装女装服装鞋类")
    → ES多路召回(IK关键词 + 全文兜底)
    → 向量检索(BGE-M3 语义)
    → 融合排序
    → SSE流式生成(逐字输出)
  ```
- **关键**：每个阶段都有实际作用，面试能讲清"为什么这么做"

**⭐ 完整例子（带数据流动，对着背）**

> 用户输入："给我推荐 5000 块以内、适合学生党的拍照手机，最好是小米的"

| 段 | 处理 | 输出 |
|----|------|------|
| ① 意图识别 | DeepSeek 解析（extractSearchIntent，现有=输出 JSON 再解析） | SearchIntent{keywords:"手机 拍照", budgetMax:5000, brand:"小米", usage:"学生党"}；PreferenceExtractor 把 budget 存 session.preferences（下轮记住） |
| ② 查询扩展 | 同义词扩面（SearchPipeline） | "手机 拍照 影像 摄影 像素" |
| ③ ES 多路召回 | IK 关键词 + 全文兜底 + 预算/品牌结构化过滤（RagServiceImpl.intentSearch） | Redmi K70 Pro 4699 ✓ / RedmiBook 5299 ✗超预算 / iPhone15 ✗非小米 |
| ④ 向量检索 | 预留（embedding-enabled 时走 BGE-M3 + cosineSimilarity；生产关=降级跳过） | 语义相似 Top |
| ⑤ 融合排序 | 关键词分 + 语义分加权 | Top-3 |
| ⑥ LLM 生成 | Top-3 商品拼进提示词 → DeepSeek 基于检索结果组织语言 | 推荐语（基于真实商品，不凭空） |
| ⑦ SSE 流式 | text/event-stream 逐字 | 前端打字效果 |

**核心认知**：⑤ 及之前 = 检索（Retrieval：③ ES 召回 + ④ 向量检索 + ⑤ 融合排序，都是"从 ES 找商品"），⑥ 之后 = 生成（Generation：把 Top-3 拼进提示词让 LLM 组织语言）——检索/生成边界在 ⑤/⑥ 之间；生成永远基于 ES 召回的真实商品，LLM 不知道库存，是 ES 告诉它的 → 不编造（幻觉缓解）+ 商品更新回答自动更新
- 面试话术："RAG 
  的核心是**先检索后生成**——商品数据不预训练进模型，
  而是实时检索喂给模型，这样回答永远基于真实商品，还能解释来源"

### Q3. 向量检索（Embedding）怎么实现的？🔴

> ⚠️ **诚实边界（必须先说）**：生产 `embedding-enabled: false`（application-prod.yml 实证）——**生产跑的是 ES 全文检索（IK）**，向量检索 = **完整代码实现 + test 环境验证 + 预留开关**（ES 索引实测无 semanticVector 字段佐证）。**面试主动交代**："代码完整实现、test 验证过，生产默认关（数据量小收益不兑现），改一行配置按需开"

【追问1】BGE-M3 是什么？
【追问2】语义搜索和关键词搜索区别？

【简答】
用硅基流动的 BGE-M3 模型（1024维）把商品转成向量，ES 
的 `cosineSimilarity` 做语义检索。
能理解"性价比高"这种抽象表达。

【深挖】

**一、基础概念**

- **BGE-M3**：中文 embedding 模型，1024 维（硅基流动托管）。⚠️ **口径更正**：原记"免费"——2026-09-10 实测硅基流动免费额度**已不足**（调用返 402），故"选型理由是免费"这个说法要改成"**bge-m3 是开源模型、可本地自建，托管商按量计费很低**"；被追问别再说"免费" |embedding = 把文本转成"语义坐标"——语义相近的文本坐标近（"华为手机"和"小米手机"近，"牛奶"远）
- **语义搜索 vs 关键词搜索**：关键词 = IK 分词字面匹配（"性价比高"拆不出有效词）；语义 = 向量空间里"性价比高的手机"和"便宜好用的手机"距离近

**二、为什么选硅基流动？（DeepSeek 没有 embedding）**

- 2026-08 全网核实：**DeepSeek 官方无 embedding 接口**（GitHub issue #806 确认），/v1/embeddings 返回 404 → embedding 必须第三方
- 选硅基流动：① bge-m3 **开源**且中文第一梯队（⚠️ 不是"免费用不完"——实测免费额度会耗尽，见上）② 国内直连延迟低 ③ OpenAI 兼容，换平台只改 base-url+key
- ⚠️ 诚实点：DeepSeekAiClient 里 embed() 是预留代码（实际 404），生产 embedding 只走硅基流动
- 向量不只 API 一种生成方式（4 选 1）：① 第三方 API ✅ 本项目 ② 本地开源模型（bge-m3 开源可本地跑）③ 平台自带向量化（MaxKB）④ 自训练（大厂）——embedding 模型开源，API 只是"托管"，选 API 是图省事（⚠️ 托管仍有额度/费用，"免费"说法不成立）

**三、向量检索核心机制**

- **流程**：商品语义文本 → BGE-M3 → 1024 维向量 → 存 ES dense_vector → 查询：用户问题**同模型**转向量 → cosineSimilarity 找最近
- **cosineSimilarity（余弦相似度）**：cos(θ) = (A·B)/(|A||B|)，只看两向量【方向】不看长短，范围 [-1,1]（1=最相似）。ES 用法（代码实证）：script_score `cosineSimilarity(params.queryVector, 'semanticVector') + 1.0`（+1.0 因 ES 分数需非负）。类比：比箭头朝向，不比箭长短
- **为什么用余弦不用欧氏距离**：文本向量模长受文本长短影响（长文本模大）——欧氏距离把"长度"混进相似度；余弦只看方向 → 不受长短干扰，语义检索标配

**四、存 ES 的 4 个配套（缺一不可）**

| 配套 | 要点 | 类比 |
|------|------|------|
| ① mapping 声明 dense_vector | dims 必须=1024（模型输出维度），多/少一维 ES 拒绝写入；similarity: cosine（EsIndexInitializer 实证） | 建表声明 DECIMAL(10,2)，塞别的精度报错 |
| ② 拼"语义文本"再 embedding | name+title+description+brand+tags 拼一句人话（buildSemanticText）；塞原始 JSON 字段名/括号全是噪声 | 食材做成菜再品尝；散装原料品不出味 |
| ③ 查询用【同一个模型】 | 入库/查询/增量全 bge-m3；换模型 = 坐标系不同，向量没法比 | 中英地图标同地点，数字不同没法比 |
| ④ 变更增量同步 | Dubbo ISpuSyncService.syncSpu → 重新 embedding 更新；启动全量 syncAll；不更新 = 检索过期数据 | 货架标签跟着商品变 |

**五、为什么 ES 向量搜索快？（HNSW 分层导航图）**

- **问题**：向量检索 = 找"最近的向量"。暴力全算 = 100 万条 × 100 万次余弦 = O(N)，慢
- **HNSW = 分层导航图**：
  - **分层不是按内容分的，是"抛硬币抽样子集"**：每个向量插入时抛硬币决定晋级到哪些层（正面 → 上一层，反面 → 停）——层 2 ⊂ 层 1 ⊂ 层 0 严格嵌套（出现在高层的点必然也在所有低层，下钻无缝）
  - **"细" = 点数多**：层 3 只有几个"导航牌" → 层 0 全部向量——每个商品实体都在层 0，高层只是导航副本（**不存在"目标被放错层"**）
  - **上粗下细分工**：上层点少 → 邻居连得远（长连接，快速跨越空间 = 赶路）；下层点全 → 邻居连得近（局部精确 = 到门口）
- **搜索 = 逐层精化，不是逐层重试**：从顶层入口贪心走向"离目标更近的邻居"（每层都找得到：该层视野下的最近点）→ 带结果下钻（嵌套保证下层无缝继续）→ 层 0 精确命中。类比：Google 地图连续放大——每层都看到目标，只是越来越清楚
- **它是"近似最近邻"（ANN），会找错吗？会，但工程可接受**：
  - 误判来源：入口随机 / 贪心掉进"局部山谷" / 抽样随机（目标区域恰好没高层副本）
  - 补救：**efSearch 参数**（搜索宽度——每层多探索几个候选，准确率 95%+，代价慢一点）
  - 为什么能容忍：语义检索返回 Top-K 不是唯一答案，第 3 近和第 1 近体验无差——**用极小概率的近似换 O(N) → O(logN) 数量级加速**（同搜索引擎不保证绝对排序）
- IK 倒排索引管字面 + HNSW 管语义，**共存一个索引**（mapping 既有 ik_max_word 文本字段又有 semanticVector 向量字段）
- 诚实点：20 条商品暴力也是毫秒级，HNSW 的优势在数据量大（几千+）才兑现

**六、生产现状与决策**

- 配置开关：`embedding-enabled`（false=全文检索 / true=向量检索）
- ⚠️ 诚实边界：生产 **false** = 跑 IK 全文；向量 = 完整代码 + test 验证 + 预留开关（详见本 Q 开头）
- 为什么默认关：① 20 条商品 IK 够准，语义优势兑现不了 = 收益 0 ② 依赖硅基流动外部 API = 故障点 ③ 稳定优先 ④ 全量重同步限流耗时
- 何时开：商品量级上来 / 语义搜索刚需（"学生党"IK 拆不出）；改一行配置即开（TODO #31 待决策，用户倾向开；⚠️ 但实测额度不足返 402，见 #59）
- ⚠️ 开启前必查（TODO #31）：向量化失败有无自动降级回全文——没有先补，否则硅基流动一挂搜索直接报错

【面试话术】
"embedding 把文本转 1024 维语义坐标，检索用余弦相似度——只看向量方向不比长短，所以语义搜索用它不用欧氏距离。存 ES 要 4 个配套：mapping 声明维度、拼语义文本、查询同模型、增量同步——缺一个就检索不了或检索过期数据。向量化快的根源是 HNSW 图索引，O(N) 暴力算变 O(logN)。生产默认关是工程决策——20 条商品 IK 够用，开了多一个外部 API 故障点；数据量上来改一行配置即开。embedding 用硅基流动因为 DeepSeek 官方没有 embedding 接口"

### Q4. 多轮对话怎么实现的？上下文怎么存？🔴

【追问1】会话存在哪？
【追问2】上下文怎么传给模型？

【简答】
会话存在 Redis（TTL 过期），对话历史拼进 messages 
数组传给 DeepSeek，实现多轮记忆。偏好记忆用 AI 提取存会话，
跨会话画像需升级（见深挖）。

【深挖】
- **会话存储**：Redis key（sessionId），TTL 
  过期自动清理，支持多用户独立会话
- **上下文传递**：把历史 messages（
  user/assistant）拼进 API 的 messages 
  数组，模型能看到上文
- **会话接口**：`/ai/chat/session`（创建）、
  `/ai/chat/send`（发送）、
  `/ai/chat/history`（历史）
- **偏好记忆（现有代码 PreferenceExtractor）**：AI 从最近 3 轮对话提取偏好 JSON（budget/purpose/brandPreference，省 token）→ 存 session.preferences（Redis，TTL 24h）→ 下轮 buildPreferenceContext 拼进 prompt。优点：AI 提取 + 只取 3 轮；局限：**会话级，跨会话丢**

**Agent 记忆完整分类**：

| 类型 | 存什么 | 生命周期 | 项目现状 |
|------|--------|---------|---------|
| 工作记忆 | 当前请求上下文 | 单次请求内 | ✅ messages |
| 短期（会话） | 本次会话历史+偏好 | 会话内（24h） | ✅ session.preferences |
| 长期-画像 | 稳定偏好（预算/品牌/地址） | **跨会话（月/年）** | ❌ 未做 |
| 长期-事件 | 历史交互（买过什么/问过什么） | 持久 | ❌ 未做 |
| 知识记忆 | 领域知识 | 持久 | ✅ RAG（ES/MaxKB） |

- **真实 Agent 的用户画像怎么做**：
  ① **存**：user_profile 表（DB，跨会话持久）：user_id / budget_range / brand_pref / categories / price_sensitivity
  ② **提取合并**：AI 每轮提取 → **"说到的才更新、没说的保留"**（防一次对话清空旧画像）；最新值覆盖旧值
  ③ **使用三时机**：system prompt 注入（回答天然贴合）/ 检索过滤（个性化召回）/ 重排权重（价格敏感→性价比优先）
- **事件记忆 = 记忆的 RAG**（非结构化部分）：历史对话 → 定期摘要 → 摘要向量化存 ES → 新对话用当前问题向量召回相关记忆 → 拼进 prompt（例：用户 3 天前问过"送女生礼物"，今天说"再推荐个"要能想起——画像不够，靠记忆检索；MemGPT/Generative Agents 思路）
- **升级路径**：user_profile 表 + 合并更新逻辑 ≈ 0.5~1 天（复用 PreferenceExtractor）；记忆 RAG = P2（与 Agent 升级一起做）
- **面试话术**：
  "多轮对话的本质是**把历史拼进请求**——模型本身无状态，
  靠传上下文实现记忆。会话存 Redis，天然支持分布式和过期清理。
  真实 Agent 的记忆分四层：工作记忆 / 会话 / 画像 / 事件记忆——
  画像存 DB 持久（说到的才更新、没说的保留），注入 prompt + 检索过滤 + 重排三时机使用；
  事件记忆用记忆 RAG（历史摘要向量化召回）。我的项目做到会话级偏好
  （PreferenceExtractor 提取 budget 存 Redis 24h），跨会话画像和记忆 RAG 是明确升级路径"

### Q5. AI 调用成本怎么控制的？🔴

【追问1】TokenBudgetService？
【追问2】2 元/天预算怎么实现？

【简答】
`TokenBudgetService` 用 Redis 
日计数器统计 token 消耗，全局设置 2 元/天预算上限，
超了就拒绝调用。

【深挖】
- **原理**：Redis 记录每天消耗的 token 数（或预估费用）
  ，每次调用前检查是否超预算
- **为什么需要**：大模型 API 是收费的，不控制会失控（
  尤其演示/测试）
- **实现**：日计数器（key 带日期），累计消耗，超阈值拒绝
- **细节 1 ⚠️ 时区 bug（TODO #8，面试主动讲）**：`LocalDate.now()` 用容器默认时区（UTC）→ **每日预算在北京时间早 8:00 重置，不是零点**——能主动暴露自己项目的 bug = 审计能力；修法：`ZoneId.of("Asia/Shanghai")`
- **细节 2 计价公式**：费用 = 输入 token × 输入价（1 元/百万）+ 输出 token × 输出价（2 元/百万）——**输出比输入贵一倍**；embedding 配置价填 0（⚠️ 那只是配置值；实测硅基流动额度不足、调用返 402，见 TODO #59）；流式末尾 `include_usage` 拿真实 usage 算费，不是估算
- **细节 3 两段式 + 原子性**：`isBudgetExceeded`（调用前查）+ `record`（调用后记）+ Redis `increment` 原子（防并发重复计）+ TTL 设次日凌晨（防 key 永不删）
- **细节 4 流式软肋（诚实点）**：chunk 发完才知道用了多少 token → 只能**前置检查**（超了直接 error），流式中途超支**无法中断**（已发出）——预算控制不是强一致，演示够用
- **面试话术**："AI 是付费 API，
  **成本控制是必须的**——我用 Redis 日计数器实现 2 
  元/天预算，防止测试时调用失控。
  细节上：计价 = 输入×1 + 输出×2 元/百万（输出贵一倍，流式末尾拿真实 usage）；
  检查与记录两段式 + increment 原子；
  诚实点：预算按容器时区（UTC）算，北京早 8 点重置不是零点（TODO #8），
  流式中途超支无法中断只能前置检查"

### Q7. 为什么有两个搜索（ES 和 AI 搜索）？

【追问2】AI 搜索多了什么？

【简答】
普通搜索（mall-search）用 ES IK 关键词检索；AI 
搜索（mall-ai）多了意图识别 + AI 重排序，能理解语义。

【深挖】
- **普通搜索**：ES `multi_match` + IK，
  快但"不懂语义"
- **AI 搜索**：ES 召回 Top-15 → AI 按意图重排序 
  → 返回 Top-5 + 解释
- **区别**："学生党高性价比手机" 普通搜索只能按词匹配，AI 
  搜索理解"学生党=预算有限、性价比"然后重排

  - 业界对照：Google 搜索 vs AI Overview、淘宝搜索 vs 问大家/AI 助手——**AI 是叠加在搜索之上的增强，不是取代**
- **⚠️ 诚实点（项目瑕疵，面试主动讲，TODO #33）**：两个搜索**各维护一个 ES 索引 + 各一套同步链路**——2026-09-02 服务器实测：cool_shark_mall_index（0 条空索引遗留）/ cool_shark_mall_index2（18 条 search）/ cool_shark_mall_ai（20 条 ai）→ **AI 索引比 search 索引多 2 条 = 普通搜索查不到新商品（数据不一致实锤）**。演进方向：统一单一索引 + mall-search 只做召回层 + AI 只做重排层（≈淘宝架构）+ 清理空索引
- **面试话术**："普通搜索是**召回**，AI 
  搜索是**理解+重排**——两者分层，AI 层在 ES 
  召回基础上加语义理解。mall-search 不能删：毫秒级免费是默认路径，
  分页筛选是浏览场景刚需，AI 内部也查同一个 ES——它是地基。
  诚实说项目现在两个搜索各维护一个索引（实测 18 vs 20 条，不一致），
  演进方向是统一索引 + AI 只做重排层，这是我对'AI 与搜索关系'的理解"

### Q8. 前端 AI 交互怎么做的？

【追问1】SSE 流式？
【追问2】思考卡片？

【简答】
后端是 SSE 事件流（`text/event-stream`）；前端用 **fetch + ReadableStream** 流式读取
（不是 EventSource——要 POST 带 sessionId，EventSource 只支持 GET）。逐字渲染 + 思考卡片。

【深挖】
- **SSE 是什么（Server-Sent Events，服务器发送事件）**：HTML5 标准，服务器主动向浏览器推送数据。核心特征：**单向**（只能服务端→客户端）/ 普通 HTTP 长连接（Content-Type: text/event-stream）/ 帧格式 `event: xxx\ndata: xxx\n\n` / 浏览器原生支持（EventSource 自动重连）
- **vs WebSocket（面试常问）**：SSE = 收音机（单向听广播、普通 HTTP、自动重连）；WebSocket = 电话（双向对话、ws:// 协议升级、复杂）——**单向够用选 SSE，双向才 WebSocket**
- **为什么 AI 流式用 SSE**：① 方向天然单向（DeepSeek 生成→前端看）② 复用 HTTP 基础设施（无协议升级，Nginx/负载均衡好适配）③ 原生自动重连 ④ **支持事件类型（event:）→ 能把"思考/商品/文字/结束"分类推送**（→ 第 2 问伏笔）
  ⚠️ 项目细节：前端用 fetch + ReadableStream 而非 EventSource（要 POST 带 sessionId），但传输仍是 SSE 协议——面试要讲清

**事件协议（7 种，前端按 type 渲染）**：

| event | 载荷 | 前端行为 |
|-------|------|---------|
| thinking | "🤖 AI 正在理解需求..."/流水线阶段 | 思考卡片 |
| products | 商品列表 JSON | 商品卡片 |
| categories | 可用分类（无结果引导） | 引导换问法 |
| sessionId | 会话 id | 保存续聊 |
| chunk | 单字/词 | **逐字追加**（打字效果） |
| done | 空 | 结束清理 |
| error | 错误消息 | 提示重试 |

- **为什么设计 7 个事件（一个事件 = 一种前端信息单元）**：
  ① **按类型分**：状态（thinking）/ 结构化数据（products/categories 是 JSON 要渲染卡片，不能拼进文本流）/ 文本（chunk）/ 元数据（sessionId）/ 控制（done/error）——前端 switch 分流，**不靠解析文本猜结构**（若只发 3 个事件，商品数据得从一段话里解析 JSON，又脆又蠢）
  ② **按时机分**：thinking（先）→ products（中）→ chunk（后）→ done（终）——前端才能做出"先冒思考卡 → 再出商品卡 → 文字打字机"的阶段性体验
  ③ **协议自描述**：`event: xxx` 让客户端不用猜这帧是啥。类比：快递单分运单号/收件人/物品/签收字段，不用从一大段话里猜
- **可以新增事件吗？可以！**：SSE 协议支持任意事件名——后端 `writeSSE(out, "myEvent", data)` 一行 + 前端 switch 加一个 case 即可。例子：reason（每条推荐理由）/ related（相关商品）/ cost（实时费用）。**但设计原则：没有新 UI 需求就不加**——事件多一分，生成端/传输端/解析端全链路同步成本多一分

- **帧格式手写**（writeSSE）：`event: chunk\ndata: xxx\n\n`——`data.replace("\n","\\n")` 防回答换行**破帧**（流式最容易踩的坑）
- **破帧问题详解（引起 → 解决）**：
  - **引起**：SSE 帧结构 = 字段一行一个（event:/data:）+ 空行（\n\n）分隔；前端 ai.js 按 `\n\n` 拆帧 → 每帧按行切 → **只认 data: 开头的行**。AI 回答含真实换行（"推荐:\n1. 小米"）时 data 被拆成多行 → 非 data: 开头的行被前端丢弃 = 内容丢失/串帧
  - **解决（两端配合）**：后端 writeSSE 把真实换行 `\n`(1字符) 转义成字符串 `\n`(2字符 \\ + n) → data 永远单行，传输稳定；前端 formatMarkdown 把 `\n`(2字符) 还原成真实换行(1字符) 再渲染 → 页面正常换行（FloatingAI.vue 第 412 行代码实证）
  - 一句话：**后端"藏"防破帧，前端"还"保显示**

**7 种事件在页面的落点（FloatingAI.vue 实证，用户问"推荐5000内拍照手机"）**：

| 事件 | 前端回调 | 页面 UI 效果 |
|------|---------|-------------|
| thinking | onThinking → thinkingSteps.push | 对话区上方**思考步骤胶囊**逐条冒出（🤖理解中 → 🔍意图解析 → 检索中...），自动滚底 |
| products | onProducts → pendingProducts 暂存 | **商品卡片**横排：图+名+价+查看按钮（挂在 AI 气泡下方，done 时渲染） |
| categories | onCategories | 无结果时的**引导按钮**（"试试问 笔记本/运动鞋"） |
| sessionId | onSessionId → 静默保存 | 用户无感（下次续聊用） |
| chunk | onChunk → text += chunk，await 20ms | AI 气泡**打字机效果**（每字 20ms 延迟），自动滚动 |
| done | onDone → 关 loading + 挂 products | 思考卡片消失 + 商品卡片出现；空内容兜底文案 |
| error | onError | AI 气泡直接显示错误文案 |

- **三个关键设计决策**：
  ① **StreamingResponseBody 直接写 OutputStream + flush**（绕过 PrintWriter/Tomcat buffer，穿越缓冲；legacy SseEmitter 120s 保留兼容）
  ② **三层拆缓冲**：应用层 SseNoBufferFilter + 响应头 `X-Accel-Buffering: no`（Nginx 专用）+ Nginx `proxy_buffering off`——**缓冲是流式的头号敌人**，漏一层打字效果就变"攒批输出"
  ③ **前端 fetch + ReadableStream 而非 EventSource**：要 POST 带 body（sessionId+message），EventSource 只支持 GET；fetch 流式给完整控制（拆帧/超时/事件分发）
- **成本与安全**：`stream_options.include_usage=true` → 流式末尾 chunk 带 usage → record 进 TokenBudgetService；预算检查前置（超了直接 error 不调 DeepSeek）；2026-08-14 起 /ai/** 全登录（防匿名刷 token 烧钱）；done 先发 → 关流 → 后台 saveSession（不阻塞连接释放）
- **面试话术**："协议是 SSE 思想（单向、text/event-stream），传输用 fetch 流因为要 POST。事件协议 7 种：thinking/products/chunk/done，帧手写防破帧。关键在**拆三层缓冲**（Tomcat/Nginx/代理），用 StreamingResponseBody 直接写 OutputStream。成本上流式末尾带 usage 顺便记费 + 预算前置 + 全登录"

### Q9. AI 有哪些坑/限制？诚实说

【追问1】大模型幻觉？
【追问2】响应慢？

【简答】
坑：① 大模型可能"幻觉"（编造不存在的商品）→ 用 RAG 
检索真实数据约束；② 响应慢（多次调用）→ 流式输出缓解感知；③ 
成本 → 预算控制。

【深挖】
- **幻觉**：模型可能回答商品库里没有的东西 → RAG 
  只基于检索结果回答，减少幻觉
- **延迟（诚实点：生产 0 调用无实测，链路拆解 + 量级估算）**：
  - 一次问答耗时三段：① 意图识别（1 次 LLM 非流式，约 1~3s）② ES 检索（10~50ms 可忽略）③ 流式生成（TTFB 1~3s + 逐字 20~50 字/s）
  - **首字时间(TTFB)约 3-6 秒**（文档原记录）；完整 100 字回答 ≈ 5~11 秒
  - 慢在 LLM 调用不是架构：事件协议零开销，SSE + thinking 解决的是"感知"——首字前思考卡片填满沉默，首字后打字机占注意力
- **TTFB 是什么（Time To First Byte 首字节时间）**：请求发出到收到第一个 token 的等待 = 流式场景"点击发送到看到第一个字"。类比：打电话拨号后到对方"喂"第一声
- **为什么 DeepSeek 首 token 慢（prefill 机制）**：
  - LLM 生成分两阶段：**prefill（预填充）**= 通读全部输入（历史+商品上下文，几千 token）算完注意力才能吐第一个 token → 1~3s，输入越长越慢；**decode（解码）**= 自回归逐 token 生成（后一个依赖前一个，无法并行）→ 20~60 token/s 天花板
  - 其他：服务端排队（高峰期）/ 共享算力抢 GPU
  - 类比：厨师做菜——prefill = 备料起锅（食材越多越久），decode = 一勺勺舀（快不了）；TTFB = 第一口菜之前
- **优化手段**：减输入长度（压缩历史/精简提示词，项目 QA prompt 已压 60 字符）/ 意图识别只带当前句 / 换更快模型 / thinking 事件填沉默期
- **AI 高并发应对（AI 高并发 ≠ 秒杀高并发）**：
  - **定性**：秒杀 = 大量"快请求"自己可控（限流/预扣/MQ 削峰）；AI = 少量"慢请求"占线程 + 外部 API 配额有限——两个铁约束：① 每个 SSE 请求秒级 + 挂一个 Tomcat 线程（10 个用户就能占满线程池）② LLM API 是外部共享资源（QPS 配额 + token 收费），不能无限调
  - **应对层次（从便宜到贵）**：① **入口限流**：Sentinel QPS 限流 /ai/**（TODO #2 已评估待实施——现在 ai 接口无限流）② **并发闸门**：Semaphore 限制"同时进行的 LLM 调用数"（如 20），超出 429"AI 繁忙"——**核心手段：不设闸门，Tomcat 线程被 AI 占满，其他接口全挂** ③ **缓存热点**：常见问答 Redis 缓存 2min TTL（IoT 已有先例）→ 重复问题不调 LLM，高并发命中率高 ④ **降级链路**：LLM 满/挂 → 降级纯 ES 检索（给商品列表不生成）→ 保证"有响应"而非"卡死"（呼应 TODO #31 降级思想）⑤ **预算 + 频控**：每日预算（有）+ 每用户频控（防单用户刷爆）⑥ **无状态多实例**：会话在 Redis → 天然多实例，SSE 长连接分散（单实例 200 线程 = 200 同时连接上限，×3 实例 = 600）
  - **项目现状**：SSE 异步 ✅ / 每日预算 ✅ / 无状态会话 ✅；Sentinel ai 限流 ❌（TODO #2）/ 并发闸门 ❌ / 问答缓存 ❌ / 降级 ❌——AI 上生产前必修课（TODO #34）
- **成本**：token 计费 → 预算控制
- **面试话术**："AI 的坑我踩过——幻觉用 RAG 约束、
  延迟用流式缓解、成本用预算控制。
  延迟诚实说生产 0 调用没实测，但链路清楚：意图识别 1-3s + 生成 TTFB 1-3s +
  逐字输出，首字 3-6 秒。慢的根源是 LLM 的 prefill——要通读全部输入才能吐第一个
  token，输入越长越慢；优化方向是减输入长度 + 更快模型。
  事件协议本身零开销，SSE 解决的是感知问题。
  **知道局限和知道怎么缓解同等重要**"

### Q11. RAG 到底是什么？（面试被问住过的词，必背）🔴

【追问1】为什么需要 RAG？
【追问2】"检索增强"增强在哪？

【简答】
RAG = Retrieval-Augmented Generation（**检索增强生成**）：
先检索（Retrieval）再生成（Generation）——从知识库
（ES/向量库）检索相关资料，塞进提示词，再让 LLM 基于资料回答。

【深挖】
- **为什么需要**：大模型知识有截止日期，问"新到店的华为Mate70
  多少钱"它不知道（不在训练数据里）→ RAG 让它"开卷考试"：
  每次问答动态检索资料，答案有依据、能实时更新（改资料就改答案）、
  减少幻觉
- **比喻**：大模型像"只读过旧课本的优等生"，RAG 是考试时
  "允许翻一本你准备的参考资料"——先检索相关章节，再照着答
- **"增强"在哪**：不是让模型记更多，而是**动态给"开卷资料"**
- 话术："RAG 的核心是**先检索后生成**——商品数据不预训练进模型，
  而是实时检索喂给模型，回答永远基于真实商品，还能解释来源"

### Q12. 你的 AI 功能算 Agent 开发吗？🔴（诚实边界）

【追问1】Agent 的定义？
【追问2】和 RAG 应用的区别？

【简答】
**严格说不算 Agent，是 RAG 应用 + 工具调用雏形**。
流程写死（正则→意图→RAG），没有自主规划和多步循环。

【深挖】
- **Agent 核心特征**：自主规划（拆任务决定下一步）+
  调用工具（查库/改配置/发消息）+ 多步执行（想→做→看结果→再想）+
  记忆
- **你的项目对照**：
  自主规划 ❌（三段式流程写死）/ 工具调用 ⚠️（IoT 自然语言调参
  会调后端策略接口改真实参数 = 工具调用雏形）/
  多步循环 ❌（单次问答）/ 记忆 ⚠️（SessionManager 24h 会话，
  是聊天记忆不是 Agent 记忆）
- **升级路径**（如果要做 Agent）：
  加规划层——让 LLM 决定"该查知识库 / 调设备接口 / 先查告警再综合"，
  配合 function calling 循环执行
- **如果真 Agent 化，提升什么？（诚实：不是性能！）**：
  - **性能反而更慢更贵**：多步 ReAct = 3~6 次 LLM 调用代替 2 次（每次都有 prefill 延迟）→ 首字从 3-6s 可能涨到 8-15s；token 费用 ×2~3（每轮重发上下文）——**Agent ≠ 更快，Agent = 更能干**
  - **真实提升 = 能力边界**：从"回答问题"升级到"完成任务"——查库存/比价/售后/优惠这类多步操作，单轮 RAG 做不了（数据访问经工具 Dubbo，不限于搜 ES）；错误可纠正（检索无结果 → 自动换词重试）
  - **真正的体验提升 = 用户少问几轮**：一次 15s 做完原本 4 次（共 20s+）的活，还不用自己整合信息——**用"单次更慢"换"总任务更快 + 用户更省事"**
  - **所以必须双路径**：简单问题走快速 RAG（1 次 LLM 保性能），复杂任务才进 Agent（3-6 次换能力）——不能一刀切（呼应方案文档附录 A）
- 话术（诚实版）："严格说我的项目是 RAG 应用，不是 Agent——
  流程是写死的，没有自主规划和多步循环。但我理解 Agent 的核心是
  工具调用：IoT 的自然语言调参已经让 AI 识别意图后调用后端策略
  接口改真实参数，这是工具调用雏形。升级 Agent 我会加规划层 +
  function calling——这是我从 RAG 往 Agent 走的路径。
  诚实说 Agent 化性能不会提升反而更慢更贵（3-6 次 LLM 调用 vs 2 次），
  价值是能力边界——从回答问题到完成任务，省的是用户来回轮次不是单次延迟；
  所以双路径：简单走快速 RAG，复杂才进 Agent"
  → ⚠️ 千万别吹"我做了 Agent"——追问"怎么规划任务"就露馅；
    诚实 + 懂升级路径反而加分

### Q13. 电商 AI 导购 vs IoT AI 诊断（RAG 两种落地对比）🔴

【追问1】有什么不同？
【追问2】真实场景选哪个？

【简答】
电商=**自研 ES 向量检索**（结构化商品数据，要实时+可控）；
IoT=**MaxKB 平台**（故障手册文档，上传即用）。
**知识形态决定方案**。

【深挖】
- **对比表**：

| 维度 | 电商 AI 导购 | IoT AI 诊断（MaxKB） |
|------|-------------|---------------------|
| RAG 实现 | 自研（ES vector + cosineSimilarity） | 平台化（MaxKB 开箱即用） |
| 向量存储 | ES 8.x dense_vector 字段 | MaxKB 内部向量库 |
| Embedding | 自调硅基流动 bge-m3（1024维） | MaxKB 自动向量化 |
| 知识来源 | 商品库（结构化，Dubbo 同步） | 故障手册（文档，后台上传） |
| 知识更新 | 商品变更→Dubbo→重新 embedding | 上传文档→自动切分向量化 |
| 成本模型 | DeepSeek API 按 token → TokenBudget 2元/天 | 私有化部署 → 内存成本（OOM 坑） |

- **性能对比**：
  检索速度：自研 ES 毫秒级 vs MaxKB 秒~十几秒（Gunicorn 30s 超时坑）
  灵活度：自研可叠加价格/品牌过滤、IK+向量混合召回 vs 平台只能文档问答
  部署成本：自研复用已有 ES 零新增组件 vs MaxKB 省开发但吃内存（3.48G ECS OOM）

**优劣势深度分析**：

| 维度 | 电商自研 ES | IoT MaxKB 平台 |
|------|------------|----------------|
| 检索速度 | ⚡ 毫秒级（本地 ES） | 🐢 秒~十几秒（实测坑） |
| 可控性 | ✅ 重排/过滤/召回全可控 | ❌ 黑盒不可调 |
| 结构化过滤 | ✅ 价格/品牌/品类/排序 | ❌ 只能文档问答 |
| 实时更新 | ✅ 变更 Dubbo 同步秒级生效 | ⚠️ 重传文档重新向量化 |
| 业务集成 | ✅ 能连购物车/订单/秒杀（升级 Agent 地基） | ❌ 与业务系统割裂 |
| 开发成本 | ❌ 高（每段流水线自写） | ✅ 零开发上传即用 |
| 文档支持 | ❌ 只能搜结构化商品 | ✅ 天生支持手册/PDF 自动切分 |
| 资源 | ⚠️ 复用已有 ES 零新增 | ❌ 私有化吃内存（3.48G OOM 实坑） |
| 各自坑 | 依赖商品文本质量 / 检索链路自调优 / 开向量依赖第三方 API | 慢 / 吃内存 / 黑盒不准没法调 / 只问答不接业务 |

- 真实场景结论：**看知识形态，可混合**
  结构化数据（商品/订单）→ 自研 ES（实时、可过滤、毫秒级）
  非结构化文档（手册/FAQ）→ 平台（省开发、好维护）
  大厂做法：文档问答走平台，业务检索走自研 ES，中间用编排框架串
- 话术："两个 AI 我都真做过：电商用自研 ES 向量检索，因为知识是
  结构化商品数据——要实时更新、要叠加价格品牌过滤、要毫秒级；
  IoT 用 MaxKB，因为知识是故障手册——上传即用、零开发。
  选型逻辑是**知识形态决定方案**，真实生产两者可混合：
  文档问答走平台，业务检索走自研 ES。两个项目各验证一条路，
  这是我对 RAG 落地最深的体会。"
