### Q1. 描述一次最难的线上故障排查 🔴
【追问1】怎么定位的？
【追问2】根因是什么？怎么修复的？
【简答】最典型的是 **ES 集群 red + 搜索卡死**。排查链路：前端搜索卡死 → 定位 ES red → `allocation/explain` 找到分片分配失败 → 根因是 IK 分词器丢失 → 重装 + 持久化修复。
【深挖】
- **现象**：搜索框输入"手机"页面卡死，ES 集群 red
- **排查**：  
1. `_cluster/health` 看到 red，13 个分片未分配  
2. `_cat/shards` 定位      `cool_shark_mall_index2` 主分片      ALLOCATION_FAILED  
3. `_cluster/allocation/explain`      拿到完整堆栈 → `analyzer [ik_max_word]      has not been configured`  
4. 根因：ES 容器重建后 **IK 分词器丢失**（之前手动装的，     Docker 容器重建即消失）
- **细节补充（来源文档实证）**：  
- **13 个未分配里 12 个是 SkyWalking 索引副本（单节点正常现象），真异常的只有 index2 主分片 1 个**——新手看到 13 个 UNASSIGNED 以为全坏了  
- ES 自动重试 5 次全失败 → **max_retry 封死 → 分片永久 UNASSIGNED**（所以重启没用，必须手动 `reroute?retry_failed=true` 重试）  
- **副本清零原因**：单节点不需要副本（副本要放不同节点），`number_of_replicas=0` 是单节点常态  
- **影响面**：只有前台搜索卡死；商品/秒杀/订单走 MySQL 全正常；AI 导购正常（cool_shark_mall_ai 用 standard 不依赖 IK）
- **修复**：重装 IK + 重试分片分配 + 副本清零 +   **持久化（挂载 plugins 目录）**
- **面试话术**："这次故障让我学到：**Docker   容器内手动装的软件不持久**，必须挂载或写进镜像。排查用   `allocation/explain` 一次拿到完整堆栈，  比瞎猜快得多。还要先做**影响面评估**——13 个未分配里  12 个是单节点正常的副本未分配，真故障只有 1 个主分片"

### Q2. 秒杀为什么突然限流失效？怎么发现和修复的？🔴
【追问1】根因？
【追问2】怎么验证修复？
【简答】压测发现 100 并发全部"已购买拦截"而非限流 → 查 Sentinel 规则被 Nacos 空配置覆盖清空 → 在 Nacos 创建规则解决。
【深挖】
- **现象**：压测 100 并发，应该 10 成功 90 限流，  但全进方法体（已购买拦截），说明限流没触发
- **排查**：  
1. 查秒杀日志：`Sentinel流控规则加载完成: QPS=10`（     代码规则加载了）  
2. 但日志有 `converter can not convert      rules because source is empty`（     Nacos 配置为空）  
3. 根因：`application-prod.yml` 配了      `datasource.flow.nacos`，订阅      `mall-seckill-flow-rules`，**Nacos      里没这个配置 → 空规则覆盖了本地规则**
- **修复**：在 Nacos 创建   `mall-seckill-flow-rules` 配置（  QPS=10），重启生效
- **验证**：压测后 Sentinel 实时监控显示通过   10/拒绝 62
- **机制深挖（为什么空配置覆盖本地）**：Sentinel 规则容器 FlowRuleManager 是**全局唯一 + 整体替换**——本地代码 loadRules（@PostConstruct 先执行）和 Nacos datasource（异步初始化后执行）都只是"往黑板上写"，**谁后写谁生效，不是叠加**。配了 datasource 后规则权威源 = Nacos：Nacos 空 → 擦空黑板（本地 QPS=10 消失）；Nacos 有值 → 加载生效（日志 notify-ok 实证）
- **追问点 1 资源名必须精确匹配**：规则 `resource:"秒杀订单提交"` 必须 = 代码 `@SentinelResource(value="秒杀订单提交")`——名字对不上 = 规则加载了也不命中（静默失效），排查限流不生效先对资源名
- **追问点 2 热更新实时生效（datasource 的价值）**：改 Nacos 配置 → listener 实时推送（日志 notify-listener 实证）→ **规则热更新不用重启**——本地代码规则做不到，这就是规则持久化到 Nacos 的意义
- **追问点 3 QPS 单机维度**：grade=QPS + count=10 = **单实例**每秒 10；集群流控才是总量（双实例各自 10 = 总量 20 失真，呼应 TODO #5 P2 集群流控）
- 面试话术："这是**配置优先级**的坑——我以为代码里的规则够了，但   Nacos datasource 订阅到空配置把本地规则覆盖了。  排查靠日志里的 `source is empty`，一眼定位。  机制上 Sentinel 规则是整体替换不是叠加——配了 datasource 权威源就是 Nacos；  好处是改配置热更新不用重启，坑是资源名必须精确匹配、QPS 是单机维度"

### Q3. Sentinel Dashboard 为什么打不开？怎么修的？🔴
【追问1】端口问题？
【追问2】还有哪些连带问题？
【简答】Sentinel Dashboard 容器实际监听 8858，但 compose 映射 `8090:8080`，端口对不上。改映射 `8090:8858` 解决。连带还有服务和 Dashboard 的 dashboard 地址也要改。
【深挖】
- **现象**：浏览器访问 8090 打不开（HTTP 000）
- **HTTP 000 说明什么**：连接层失败（端口无进程监听/被拒），不是应用层错误（4xx/5xx）——排查先分：连不上（端口） vs 连上了但错（应用）
- **根因**：`bladex/sentinel-dashboard:1.8.6` 镜像 ENTRYPOINT 硬编码 `-Dserver.port=8858`，compose 映射的 8080 是空的
- **为什么 compose 盖不过（配置优先级）**：`-Dserver.port=8858` 在 ENTRYPOINT = **JVM 系统属性档（Spring Boot 高优先级）**——压过 OS 环境变量（compose environment 注入的 SERVER_PORT）和 yml，只能改映射或改镜像（详见速记 20）
- **8858 哪来的**：不是"旧配置"，是 **bladex 镜像 build 时固化的 SCA 生态惯例端口**（Sentinel Dashboard 在 Spring Cloud Alibaba 部署约定就是 8858）；进程实测 `java -Dserver.port=8858` 实证
- **修复**：compose `8090:8080 →   8090:8858`
- **连带**：秒杀服务   `SPRING_CLOUD_SENTINEL_TRANSPORT_DASHBOARD=sentinel:8080` → 也要改 `8858`，否则客户端连不上   Dashboard（看不到曲线）
- **客户端是"上报"不是"访问"**：dashboard 地址 = 客户端启动去 Dashboard **注册**；`transport.port=8870`（秒杀）= 客户端自己的回调端口，Dashboard 通过它拉数据——**多实例同机必须不同**（默认 8719 会撞）
- **要不要把端口改回 8080？（约定大于配置，不改）**：① 8080 是 Spring Boot 通用默认，8858 是 SCA 生态约定——两个都是"约定"，无正统之分 ② compose 端口映射已把对外（8090）和容器内解耦，改容器内端口用户无感 = 零收益 ③ 8858 已是全系统一致（镜像+映射+所有服务地址），改 = 全链路变更 + 回归风险。**约定大于配置 = 系统内默认一致，不是追平框架出厂默认**；真到换官方镜像（默认 8080）/端口冲突/公司规范时才顺势统一
- **登录方式**：Sentinel Dashboard 登录是 `POST /auth/login?username=sentinel&password=sentinel`  （query-string，不是 JSON body）——1.8.6 版本特性，新版本改过（面试提版本避免踩差异）
- 面试话术："这是**镜像默认值和 compose   配置冲突**——ENTRYPOINT 用 -D 硬编码端口（JVM 属性，  比 environment/yml 优先级高），改映射 + 改服务   dashboard 地址，两处都要对。HTTP 000 = 端口没监听不是应用错。  8858 是 SCA 生态惯例、镜像固化的，**端口映射已解耦对外端口，  改回 8080 没有收益**——约定大于配置是系统内一致，不是追平出厂默认"

### Q4. 秒杀压测为什么一直报"已购买"？怎么解决的？🔴
【追问1】root cause？
【追问2】最终方案？
【简答】压测脚本用同一个用户，第一个成功后就"已购买"。解决：注册 100 个真实用户，每个发一次，避免重复购买干扰。
【深挖】
- **现象**：100 并发用 testuser 反复发，只有第 1   个成功，其余"您已经购买过这个商品了"
- **根因**：秒杀有防重复购买（一个用户一件），同一用户只能成功一次
- **排查演进**：  
- v1：单用户 → 全被"已购买"拦  
- v2：10 用户轮流 → 出现重复购买干扰  
- v3：**注册 100 个真实用户**（    benchuser01~100）→ 每个发 1 次 → 干净结果     8成功/89限流
- **脚本**：自动重置库存（1000）+ 清购买标记 + 登录   100 用户
- **深挖 1 压测场景设计（核心认知）**：**限流测试和防重测试是两码事**——想测限流必须绕开防重（多用户各发 1 次）；想测防重就单用户循环。单用户压测测到的是"防重拦截"，不是并发能力（防重三 key 见基础知识速记 10）
- **深挖 2 业务规则也是被测对象**："已购买拦截"不是 bug——它证明**业务规则（一人一件）在高并发下依然正确**，压测不只测性能还验规则
- **深挖 3 贴近真实用户模型**：压测脚本要模拟真实分布（不同 userId/token 独立），否则测的不是目标——100 用户脚本（注册+登录+清标记+重置库存）是正确姿势
- 面试话术："压测暴露了防重复购买机制在工作——它验证的不是 bug，  而是**业务规则在高并发下依然正确**。我用 100   个真实用户绕开干扰，测出干净的限流效果。  方法论上：**限流测试和防重测试要分开设计**——单用户压测测到的是  防重拦截不是并发，贴近真实用户模型（多 userId/token）才是正确姿势"

### Q6. Spring Boot 2 升 3 遇到过什么？🔴
【追问1】javax → jakarta？
【追问2】Security 6 变化？
【简答】升级 Spring Boot 3 主要是：`javax.*` → `jakarta.*` 包名、Spring Security 6 的配置 DSL 变化、Gateway 循环依赖。
【深挖】
- **javax → jakarta（根因，不是 Spring 自己改的）**：Oracle 把 **Java EE 捐给 Eclipse 基金会改名 Jakarta EE**（2017），javax.* 命名空间留给 Java SE 扩展，新版本 API 必须用 jakarta.*——**Spring Boot 3 / Spring Framework 6 基于 Jakarta EE 9+** → servlet/validation/annotation 坐标全迁。答"换包名只是表象，背后是 Java EE → Jakarta EE 生态迁移"。项目 208 处 import 实证（servlet 的 Filter/Request、validation 的 @NotNull/@Pattern、annotation 的 @PostConstruct 等）
- **Security 6**：  `WebSecurityConfigurerAdapter` 移除   → `SecurityFilterChain` + Lambda   DSL；  `@EnableGlobalMethodSecurity`   → `@EnableMethodSecurity`  （项目全服务 SecurityFilterChain Bean + @EnableMethodSecurity(prePostEnabled=true) 实证）
- **Gateway 循环依赖**：Knife4j 注入   RouteLocator 循环 → 用   ObjectProvider 延迟加载（Knife4jSwaggerProvider 代码实证）
- **MyBatis-Plus**：  `mybatis-plus-boot-starter` →   `mybatis-plus-spring-boot3-starter`  （全模块实证——第三方库兼容是升级最大工作量）
- **版本矩阵先定再升（方法论第 1 步）**：升级第一步不是改代码，是**定版本矩阵**——Boot 3.2.5 ↔ Spring Cloud 2023.0.3 ↔ SCA 2023.0.1.2 是"阿里云镜像验证过的兼容组合"（根 pom 注释实证），否则第三方库连环不兼容
- **升级方法论**：① 定版本矩阵（Boot/Cloud/SCA/组件兼容表）② 编译报错驱动修（javax→jakarta 批量替换 + 手动兜底）③ 第三方库查兼容表（换 starter/新坐标，MyBatis-Plus/Knife4j 都是）④ 全链路回归
- **诚实点（JSON 库混用）**：项目 Web 层序列化默认 Jackson（Spring 集成 + @JsonFormat + Long→String 精度配置），业务手写解析用 fastjson **2.0.43**（安全版；fastjson 1.x 有反序列化 RCE 漏洞史）——规范倾向统一 Jackson（TODO #35），但混用功能无碍
- **JDK 21 虚拟线程现状（实证）**：10 个 test yml 开了 `spring.threads.virtual.enabled=true`，**生产 prod 未开**——test 验证能力，生产保守用平台线程（虚拟线程与 Dubbo 线程模型兼容待验证，Boot 3.2 只覆盖 Web 容器层）
- 面试话术："Spring Boot 3 升级的核心是   **Jakarta 命名空间迁移**（背后是 Java EE → Jakarta EE 生态改名，  不是 Spring 自创）+ **Security 配置范式变化**，还有第三方库的兼容  （MyBatis-Plus 要换 starter、Knife4j 循环依赖用 ObjectProvider）。  方法论：先定版本矩阵（Boot 3.2.5 ↔ Cloud 2023.0.3 ↔ SCA 2023.0.1.2），  再编译报错驱动逐个修，最后全链路回归。这个迁移让我对框架演进有了实感"  → 📄 **完整迁移细节（javax 三类迁移/连带坑分类/JDK21 虚拟线程）见 [[SpringBoot3迁移详解]]**（原始记录：问题解决--SpringBoot2升级3 / 问题解决--JDK21与Seata迁移）

### Q7. Seata 遇到过什么坑？🔴
【追问1】版本迁移？
【追问2】Dubbo filter bug？
【简答】Seata 1.x → Apache Seata 2.1.0 迁移，遇到 `dubbo-filter-seata:1.0.2` 的 branchType NPE bug，自定义 filter 解决。
【深挖】
- **版本迁移**：`io.seata` → `org.apache.seata` groupId 变更
- **NPE bug**：`dubbo-filter-seata:1.0.2` 在非事务环境下无条件调 `RootContext.getBranchType()` 返回 null → NPE（  GitHub Issue #6815）
- **现象层（案例视角）**：报错 `Cannot invoke "BranchType.name()" because "branchType" is null`——发生在**所有 Dubbo 调用**(filter 是全局拦截器,商品查询等非事务调用也过),不是只在事务里 → 判断是 filter 层问题而非业务代码
- **解决（双重保护，代码实证）**：自定义   `SeataTransactionConsumerFilter`：  ① **xid 为 null 直接跳过整个块**（无事务调用根本不取 branchType——修正官方"先取 branchType 再判 xid"的顺序颠倒）  ② xid 非空才取 branchType 且**再判一次空**兜底  通过 Dubbo SPI 注册（根 pom 排除官方 filter + META-INF/dubbo/org.apache.dubbo.rpc.Filter 注册，SPI 文件代码实证）
- **修复验证**：排除后官方 filter 不再加载、自定义 filter 经 SPI 生效——回归跨服务下单/普通 Dubbo 调用均正常（普通调用不再 NPE = 修复生效的信号）
- 面试话术："Seata 2.1 的 Dubbo filter 官方有   bug，我**自己实现了 filter   替代**——先判断 xid   存在再取 branchType，用 Dubbo SPI 注册。  这体现了我能深入框架解决问题"  → 📄 **机制完整深挖（传播链/xid 跨服务/版本坑/io.seata 兼容层）见 04-1-中间件选型 Q5 追问5（防抄核弹）**——10 是故障案例视角，04-1 是知识解剖视角

### Q8. 秒杀消息堆积/订单慢怎么排查的？
【追问1】success 表字段不匹配？
【追问2】无限重试？
【简答】秒杀订单创建慢：三层问题叠加——success 表字段不匹配 → 插入失败 → RabbitMQ `basicNack(requeue=true)` 无限重试 → trace 日志刷屏。修复表结构 + 抛 RuntimeException + 降日志级别。
【深挖】
- **现象**：秒杀订单创建慢
- **排查**：  
1. success 表字段和代码不匹配 → INSERT 失败  
2. 失败触发 `basicNack(requeue=true)` →      消息无限重试  
3. `logging.level: trace` → 日志刷屏拖慢
- **修复**：修表结构 + 异常抛 RuntimeException   触发事务回滚（不 requeue）+ 日志级别改 info
- **深挖 1 为什么 requeue=true 会无限重试（毒消息）**：nack + requeue = 消息**立即回队列再投递** → 又失败 → 又 requeue = **死循环（poison message）**——没有退避、没有次数上限，一条坏消息卡死消费
- **深挖 2 失败处理分级（核心面试点）**：  ① 临时错误（DB 抖/网络）→ 可重试，但要**次数上限 + 退避/延迟队列**  ② 永久错误（字段不匹配/格式错/业务规则）→ 重试无意义，三条路：**死信队列 DLX / 记录后手动补偿 / ack 丢弃**（可接受）  ③ 项目秒杀修法（抛 RuntimeException 不 requeue）= 避免死循环，但更企业化是 DLX + 重试次数 + 可观测
- **深挖 3 表结构不匹配 = 运行时错不是编译错**：实体字段 vs success 表列对不上，编译不报、插入才炸（与 Q9 实体映射同族）
- **深挖 4 日志级别是"放大器"**：trace 全局 → 每次 requeue 打全栈刷屏拖慢——不是根因但是放大因素，三层叠加才"慢"
- **深挖 5 项目 MQ 可靠性（当时现状；DLX 已补）**：**当时**是 `acknowledge-mode: manual` + Spring listener retry（max-attempts=3 间隔 1s，prod yml 实证）；**现为 AUTO ack（#70 定稿，见深挖 6）**；秒杀"先落库 seckill_message_retry 表 + MessageRetryTask 每 5s 重发（retryCount<3）"（TODO #11 称低配延迟队列）——**当时全项目无 x-dead-letter 配置 = 没有死信队列** → 第二批补 **DLX**（`order_queue` 声明死信交换机 + `OrderDlxConsumer` 记录原因/告警，#36 ✅ 已完成）→ 第三批 **#65/#70** 把库存扣减链路收口（见下条）
- **深挖 6 企业级 MQ 可靠性（五环，缺哪环看现状）**：  ① 发送端可靠：发送前落库（✅ retry 表）+ publisher confirm  ② 消费重试：listener retry 上限+退避（✅ 3 次 1s）  ③ **死信队列 DLX**（✅ 已有）：重试耗尽 → reject（`defaultRequeueRejected=false`）→ 死信队列 → 死信消费者记录原因 + `【MQ死信告警】`/人工补偿——"重试救不活的坏消息有归宿"  ④ 可观测（⚠️ 部分）：DLX 死信已打 `【MQ死信告警】` 日志；重试次数/DLX 堆积监控未做（呼应 TODO #30）  ⑤ 幂等消费（有 @Idempotent 思路）：重投不重复下单
- **⚠️ 现状盘点（诚实点，2026-09-12 回填）**：**曾无 DLX**（全项目无 x-dead-letter 配置、订单消费者 `OrderQueueConsumer` 用 `requeue=true` 无限重试挂单）→ **第二批补 DLX**（#36 ✅ 已完成：`order_queue` 声明死信 + `OrderDlxConsumer` 记录原因/告警）→ **第三批 #65/#70 收口**：`AcknowledgeMode.AUTO`（监听器完全不碰 channel）+ `defaultRequeueRejected(false)` + 容器重试 3 次后 reject 进死信 + 死信告警；订单与秒杀两条链路均已部署（秒杀侧同款修复 + #72 死信链路实测闭环）
- 面试话术："这个 bug 是**三层问题叠加**——表结构、  消息重试策略、日志级别，单看一个都对，叠起来就慢。排查要一层层剥，  最后发现是'看起来无害的小问题'连锁反应。  机制上 requeue=true 无退避无上限 = 毒消息死循环；失败处理要分级：  临时错误重试（限次数+退避），永久错误走死信/记录/丢弃。  项目可靠性现状：我曾以为'读 x-death 做限次重试'就够，**实测在 classic 队列上无效**（requeue 不写 x-death、计数恒 0 ⇒ 实际还是无限重投）——已修为 **AUTO ack + 容器重试 3 次 + 毒消息 reject 进 DLX + 死信消费者告警**；订单库存扣减链路（#65/#70）与秒杀侧（#72）均已修复并部署，#36 已完成"

### Q12. 部署阶段遇到的最大问题？
【追问1】SkyWalking 部署 Alpine→Debian 是什么？
【追问2】ES 内存设置？
【追问3】Metaspace 是什么？
【简答】部署最大的坑 = 引入 SkyWalking 的**连环坑**：① Alpine(musl)镜像与 Java 安全算法不兼容 → 全服务崩溃 → 换 Debian(glibc)；② Agent 40+ 插件撑爆 Metaspace 128m → 提到 256m；③ 低配服务器 ES 不限内存被 OOM Killer 杀 → `-Xms512m -Xmx512m`。逐一定位解决。
【深挖】
- **坑① SkyWalking Alpine → Debian（容器镜像的"地基"选错）**—— 概念链（面试官可能从 Alpine 追问到 musl/glibc）：  
1. **镜像分层**：你的服务镜像 = JAR → JRE（eclipse-temurin）→ **操作系统发行版**（Dockerfile 第一行 `FROM` 指定，是最底层"地基"）  
2. **Alpine vs Debian = 两个不同的 Linux 发行版**：Alpine 极简（基础镜像 ~5MB，面向体积敏感场景）；Debian 通用完整（~100MB+，社区最大）  
3. **musl vs glibc = C 标准库的两种实现**：JVM 本体是 C++ 写的，native 部分（加密 Provider、内存/线程/网络）依赖 libc 行为 → C 库不同 = Java 运行环境不同  
4. **关键**：Oracle/官方 JDK **只认证 glibc 平台**；Alpine 的 musl 是"非官方组合"，安全算法层易出问题
- **项目真实现象（别背成"agent 不兼容 musl"）**：换 Alpine 后**所有服务崩溃**，Nacos 客户端报 `NoSuchAlgorithmException: MessageDigest get MD5 instance error` —— JDK 安全算法层（MD5 实例化）在 musl 环境失败 → Nacos 配置中心校验（用 MD5）都过不了 → 服务连不上配置中心直接起不来。Agent（纯 Java 字节码探针）只是让问题放大到全部 11 个服务。

| 项 | Alpine（原） | Debian（改后） |
|------|------|------|
| C 库 | musl | glibc |
| Java 官方认证 | ❌ 非认证组合 | ✅ 认证平台 |
| 镜像体积 | 小 | +50MB/服务（实测 596~812MB 含 JRE） |
| 单服务 JVM 启动 | 秒级 | 秒级（换镜像不影响 JVM 启动速度） |
| 本项目结果 | 全部崩溃 | ✅ 正常 |

> **⚠️ 数字纠偏（2026-09-03 复核）**：部署文档曾记"启动 ~30s → ~9min"——**口径错误**。单服务 JVM 启动（含 SW agent）是秒级，9min 实际是"11 个服务全量重建 + 部署到就绪"的总耗时，被误记成单服务启动。面试若被问"换镜像为什么慢"，答"镜像大 50MB，构建/拉取/传输变慢；单服务启动仍是秒级"——不要背 9min。

> **追问澄清(宿主机 vs 容器内,面试高频)**:换的是**容器镜像内的发行版**,与服务器宿主机无关——服务器是 Ubuntu 24.04,但容器内系统由 Dockerfile `FROM` 决定(共享宿主机内核,用户态镜像自带)。Ubuntu 本就是 Debian 家族(同为 glibc),所以"服务器 Ubuntu + 容器 Debian 系"是同族不矛盾。铁证:同一台服务器上 Redis/RabbitMQ 至今跑 Alpine 好好的(非 Java 程序不挑 libc),只有 Java 服务换成 glibc 系。详见 [[Docker容器原理详解]]。

- **坑② OAP Metaspace 溢出**：SkyWalking Agent 挂载 **40+ 插件 jar** → 加载类数量暴涨 → 类元数据撑爆 `-XX:MaxMetaspaceSize=128m` → `OutOfMemoryError: Metaspace`。修复：提到 **256m**（Agent 额外占 ~80MB Metaspace）。
> Metaspace = JVM 存**类元数据**（类结构/方法签名）的非堆区域；Agent 插件越多 → 加载类越多 → Metaspace 越大 → 硬上限要留余量。
- **坑③ ES 被 OOM Killer 杀**：4C16G 低配服务器，ES 默认堆内存过大 → 被系统 OOM Killer 杀掉。修复：显式 `-Xms512m -Xmx512m` 限堆。
- **教训**：① 生产 Java 容器**默认选 glibc 系镜像**（Debian/Ubuntu），不为省体积赌 Alpine ② Agent 场景 `MaxMetaspaceSize` 要留余量（128→256）③ 低配机器中间件必须显式限内存 ④ 连环坑排查法：看日志（`NoSuchAlgorithmException`/`OOM`）→ 查资源（内存/类加载）→ 逐个定位
- **面试话术**："部署是**连环坑**——SkyWalking 镜像、Metaspace、ES 内存，每个都让服务起不来。最典型的是 Alpine：它用 musl 而主流 JDK 只认证 glibc，结果安全算法层 MD5 实例化失败，Nacos 配置校验都过不了，11 个服务全崩。换 Debian 基础镜像解决，代价是镜像大 50MB、构建/拉取/传输变慢（单服务 JVM 启动仍是秒级，别把全量重建耗时记成启动时间）。排查就是看日志、查资源、逐个定位。**教训：生产环境不为省体积选冷门组合**"
