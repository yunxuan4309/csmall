### Q1. 秒杀的核心挑战是什么？你用了哪些手段？🔴
**追问1**：每个手段解决什么问题？
**追问2**：如果只用一个手段，你会保留哪个？
【简答】秒杀挑战是**瞬时高并发 + 库存极有限**（100 并发抢 100 件）。手段：Redis 预扣库存（扛压）、Sentinel 限流（控量）、RabbitMQ 异步削峰（防堵）、Seata 事务（保一致）。
【深挖】

| 手段 | 解决什么问题 | 类比 |
|------|-------------|------|
| Redis 预扣库存 | 数据库扛不住高并发扣减 | 前台验票（快），后台再登记 |
| Sentinel 限流 | 防止瞬间打爆后端 | 只放 X 人进场 |
| RabbitMQ 异步削峰 | 创建订单不阻塞请求 | 排队登记，先发号 |
| Seata 事务 | 扣库存+建订单一致 | 保证不会"扣了库存没订单" |
- **如果只留一个**：Redis 预扣库存（  因为它直接决定了能不能扛住并发，其余是优化）
- 面试话术：  "秒杀设计的原则是**把压力挡在最外层**——Sentinel   挡流量、Redis 挡库存、MQ 挡数据库，层层削峰"

### Q2. Redis 预扣库存是怎么实现的？为什么不会超卖？🔴
**追问1**：用什么命令扣减？原子性哪来的？
**追问2**：库存扣到负数会怎样？
【简答】用 Redis `DECR` 原子自减，扣减后判断 `leftStock < 0` 则拒绝。Redis 单线程保证原子性，不会超卖。
【深挖】
- **代码**：  
```java
Long leftStock = stringRedisTemplate.boundValueOps(stockKey).decrement();
if (leftStock < 0) {
    // 库存不足，拒绝，并回滚
    stringRedisTemplate.boundValueOps(stockKey).increment(); // 加回去
    throw new Exception("库存不足");
}
```
- **为什么不会超卖**：  
- `DECR` 是**原子操作**，Redis 单线程执行，    同一时刻只有一个请求能执行 DECR  
- 即使 100 并发，DECR 也是串行执行，库存从 100 依次减到     0，到 0 后 leftStock<0 被拒绝
- **库存 key**：`mall:seckill:sku:stock:{skuId}`，秒杀开始前预热（  SeckillInitialJob 定时任务）
- **数据库兜底**：最终落库时 SQL 也带 `WHERE   seckill_stock >= quantity` 条件，双保险
- 面试话术："Redis 扣库存是**第一道防线**（快），  数据库条件扣减是**第二道防线**（准），双保险防超卖"

### Q3. Sentinel 限流怎么配置的？为什么 QPS=10？🔴
**追问1**：限流和熔断的区别？
**追问2**：规则存在哪里？重启会丢吗？
【简答】Sentinel 对"秒杀订单提交"接口配置 QPS=10 限流规则，超过的直接快速失败返回"服务器忙"。规则通过 Nacos 配置中心管理，持久化不丢。
【深挖】
- **代码/配置**：`SentinelFlowRuleConfig.java` 用 `FlowRuleManager.loadRules()` 加载 QPS=10；同时   Nacos 里   `mall-seckill-flow-rules` 配置（生产用   Nacos 管理）
- **为什么 QPS=10**：秒杀是天然限流场景，阈值不宜太高。10   QPS 足够展示"部分成功、部分限流"，也保护后端
- **限流 vs 熔断**（追问1 深挖）：  
- **限流** = 管**进来的请求量**，主动预防，    防自己被流量打爆（秒杀 QPS=10 就是限流）  
- **熔断** = 管**下游的健康状态**，被动反应，    下游错误率超标就断开不再调用（防服务雪崩）  
- 一句话区分：限流问"来多少人"，    熔断问"下游还活着吗"  
- 工具：Sentinel 限流/熔断、Hystrix、    Resilience4j；状态机 关闭→打开→半开
- **熔断为什么能防雪崩**：  
- 服务雪崩机制：A 等 B（同步等待）→ A 线程池    被占满 → A 也假死 → 传染给 C → 级联放大  
- 熔断断在源头：下游错误率超标 → 直接断开    快速失败 → 线程不空等 → 故障隔离在 B，    不扩散到 A/C/D  
- 核心 = **快速失败 + 故障隔离**
- **和缓存雪崩的区别**：服务雪崩是**服务间**级联  故障；缓存雪崩是**缓存失效把压力砸给 DB**。  精神相通（局部失效级联放大），但层级和防御不同  （熔断防服务雪崩，随机 TTL/多级缓存防缓存雪崩）
- **规则持久化**：Nacos 管理（  `mall-seckill-flow-rules`），  Dashboard 内存存储重启会丢，Nacos 不会
- **真实踩坑**：Nacos   里配置为空时覆盖了本地规则导致限流失效——这个坑讲出来非常加分
- **压测验证**：100 并发压测，Sentinel   实时监控显示**通过 QPS=10，拒绝 QPS=62**，  证明限流生效

### Q4. RabbitMQ 异步落库怎么实现的？为什么异步？🔴
**追问1**：消息发到哪个队列？消费者做什么？
**追问2**：消息失败/丢失怎么办？
【简答】Redis 扣库存成功后，把创建订单的消息发到 RabbitMQ，请求立即返回。消费者异步从 MQ 取消息创建订单，实现削峰。
【深挖】
- **流程**：扣库存成功 → `convertAndSend`   发消息到队列 → 返回成功 → 消费者（  SeckillQueueConsumer）异步处理 →   创建订单 +   写秒杀成功记录
- **为什么异步**：100 并发里真正成功的只有 ~10 个，  如果同步落库，10 个成功 + 90   个被限流的都会阻塞在数据库操作。  异步后请求不阻塞，数据库压力被削平
- **队列设计**：`seckill_exQueue` /   `seckill_routing_key`（Topic 交换机）
- **消息可靠性**：  
- **JSON 序列化**（不用 Java 序列化，避免版本兼容问题）  
- 成功 `basicAck` 手动确认；    失败抛异常触发事务回滚（Spring 自动重投）  
- 有 `seckill_message_retry`     表做**本地表缓冲 + 定时重试**（    MessageRetryTask 每 5 秒扫描），MQ     恢复后自动补发
- **追问**："消息积压怎么办？" → 秒杀场景积压是正常的（  排队消费），消费者处理速度足够即可；降级方案用本地表兜底
- **追问**："重试表怎么兜底？" → 先 INSERT   `seckill_message_retry`（status=0）→ 发 MQ →   成功置 status=1；失败保持 0，`MessageRetryTask`   每 5 秒扫描重发（上限 3 次），置 1 后不再管（  status：0 待发送 / 1 已发送 / 2 失败达上限）
- **追问**："为什么用 JSON 序列化？" → Java   序列化把类结构快照（全限定类名 + 自动生成的   serialVersionUID）写进消息，两端类版本不一致（  如滚动发布生产者先升级）就 InvalidClassException   整条报废；JSON 自描述，多字段忽略、少字段给默认值，  跨服务版本兼容
- 面试话术："异步是秒杀削峰的关键——**让请求快速返回，  把耗时的落库放到后台排队处理**"

### Q5. 秒杀的完整流程（从请求到落库）？🔴
**追问1**：每一步的具体校验？
**追问2**：哪个环节最可能出错？
【简答】POST `/seckill/{randCode}` → 校验随机码 → 防重复购买 → 防重复提交锁 → Redis 预扣库存 → Dubbo 调 order 建订单 → 发 MQ → 返回。
【深挖】
完整链路（SeckillServiceImpl.commitSeckill）：
1. **校验随机码**：从 Redis 拿 randCode 和参数对比，不匹配拒绝（防刷）
2. **下单锁**：`SETNX`（orderLock key），防并发重复提交，1 分钟 TTL
3. **未支付拦截**：查 ordered key，有未支付订单则拦截
4. **Redis 预扣库存**：DECR 原子扣减，<0 拒绝
5. **Seata 全局事务**：`@GlobalTransactional` 包裹
6. **Dubbo 调 order**：创建订单（mall-order）
7. **发 MQ**：异步写秒杀成功记录
8. **返回**：SeckillCommitVO
- **最可能出错**：库存扣了但订单创建失败（所以需要 Seata）；  MQ 消息丢失（所以有重试表）
- **面试话术**："秒杀流程是**层层校验 +   最终一致**——先挡流量（限流）、再挡重复（防重）、再扣库存（  Redis）、再异步落库（MQ）、最后保证一致（Seata）"

### Q6. 防重复购买是怎么实现的？为什么三个 key？🔴
**追问1**：三个 key 分别管什么？
**追问2**：为什么不只用一个 key？
【简答】三个 Redis key 分离设计：orderLock（下单锁防并发）、ordered（未支付拦截）、reseckill（购买标记防再次购买），各自独立管理。
【深挖】
- **三个 key**：

| key | 前缀 | 作用 | TTL |
|-----|------|------|-----|
| 下单锁 | `mall:seckill:order:lock:` | 防并发重复提交 | 1 分钟 |
| 未支付标记 | `mall:seckill:ordered:` | 拦截未支付订单二次下单 | 有订单时存在 |
| 购买标记 | `mall:seckill:reseckill:` | 支付后防再次购买 | 长期 |
- **为什么分离**（历史踩坑）：以前下单锁和购买标记混用，  导致"支付后还能再下单"。分离后各管各的，逻辑清晰
- **key 格式**：`{前缀}{skuId}:{userId}`，  维度是"用户 × SKU"
- **面试加分**："这是我从真实 bug   里学到的——秒杀的状态要拆细，下单/未支付/已购买是三个不同状态，  混在一个 key 里会出问题"

### Q7. 幂等防重复提交怎么实现？
**追问1**：@Idempotent 注解的原理？
**追问2**：为什么压测请求参数要不同？
【简答】幂等 = 相同操作重复执行多次，效果与执行一次相同。秒杀下单是 POST（天生不幂等），双击/重试会重复建单。用 @Idempotent 注解 + Redis SETNX 防重：同一用户同一参数的请求，3 秒内只放行一次。
【深挖】
- **什么是幂等**：关门键按 1 次和狂按 10 次，  结果一样 → 幂等；银行卡扣款扣 2 次扣 2 份钱  → 不幂等。下单/支付必须做幂等
- **用法**：注解加在 Controller 方法上  
```java
@Idempotent(key = "seckill", expire = 3, message = "秒杀订单正在提交中，请勿重复提交")
```

> key = Redis key 前缀（区分业务场景）；  expire = 锁存活秒数（秒杀 3s、支付 10s）；  message = 被拦截时的提示语
- **原理（AOP 切面自动拦截）**：  ① 算幂等 key = key:userId:MD5(请求参数)  ② Redis SETNX（setIfAbsent）写入  ③ 写入成功 → 放行执行业务，key 存活 expire 秒  ④ 写入失败 → 3 秒内已有相同请求，     直接抛异常拦截，业务代码一行不跑
- **双击场景**：手抖点两下提交按钮 →  第 1 个请求 SETNX 成功，正常下单；  第 2 个请求算出同一个 key，SETNX 失败被拦，  库存不会被二次扣减，也不会建两条订单
- **参数不同不误杀**：key 里带 MD5(参数)，  换收货地址 → 参数变 → MD5 变 → 新 key  → 正常放行。拦的是"同一用户 + 同一参数"
- **业务失败自动删锁**：第一个请求业务抛异常时，  切面 delete(key)，用户可立即重试；  业务成功锁才留到 3 秒自然过期（TTL 防死锁）
- **为什么压测参数要不同**：压测若参数全相同，  同一用户 MD5 相同 → 同一 key →  第 2 个请求起全被幂等拦截，  测的是幂等层，不是真实并发能力。  压测用不同用户（benchuser01~100），  让请求真正打到 Sentinel 限流上
- **和下单锁的区别（双重防重）**：

| 维度 | orderLock | @Idempotent |
|------|-----------|-------------|
| 拦截对象 | 用户 × SKU | 用户 × 参数内容 |
| key 前缀 | order:lock | idempotent |
| 防什么 | 换参数再抢同商品 | 双击/重试同请求 |
| 实现方式 | 业务代码 SETNX | AOP 注解自动拦 |
- 面试话术："幂等注解挡'一模一样的手抖'，  下单锁挡'同一商品换花样再抢'，  两层叠加才是完整防重"

### Q8. 随机码（randCode）机制？🔴
**追问1**：怎么生成的？存哪？
**追问2**：防止什么攻击？
【简答】随机码是 6 位随机数，定时任务生成存 Redis，前端通过详情接口获取。防止秒杀开始前提前下单 + 防接口被刷。
【深挖】
- **生成**：`SeckillInitialJob` 定时任务，`ThreadLocalRandom.nextInt(900000)+100000`，存 Redis `mall:seckill:spu:url:rand:code:{spuId}`
- **获取**：前端调 `GET   /seckill/spu/{spuId}` 详情接口，  返回 `url:  "/seckill/{randCode}"`
- **校验**：下单时从 Redis 拿 randCode   和参数对比，不匹配拒绝
- **TTL**：约 2 小时 5 分钟，过期后定时任务重新生成（  所以每次压测要重新查）
- **防什么**：① 秒杀开始前用户不知道随机码，无法提前构造请求下单；  ② 即使知道 URL，没有正确随机码也下单失败
- **类比**：像演唱会门票防伪码——只有入场时才告诉你，有码才能进

### Q9. 压测怎么做的？结果如何？🔴
**追问1**：用什么压测？为什么不用 JMeter？
**追问2**：压测结果说明了什么？

- 无超卖（数据库验证库存准确扣减）
- **Sentinel 监控**：通过 QPS=10 / 拒绝   QPS=62，正好印证限流阈值
- **SkyWalking**：calls/min=100，  记录请求量和调用链
- 面试话术："压测验证的不是'能不能扛住 100 QPS'，而是'限流、  削峰、事务这些保护机制在真实高并发下确实在工作'"

### Q10. 如果 Redis 挂了怎么办？
**追问1**：秒杀还能进行吗？
**追问2**：重试表能兜底吗？真正解法是什么？
【简答】不能。秒杀链路每一步都依赖 Redis（随机码校验、下单锁、库存 DECR），Redis 挂了功能直接停摆。重试表兜底的是 MQ 消息可靠性，不是 Redis；Redis 高可靠要主从复制 + 哨兵自动切换。
【深挖】
- **Redis 挂了发生什么**：随机码校验 → 下单锁  SETNX → 未支付检查 → 库存 DECR，  每一步都查 Redis，任一异常整个链路失败，  被 fallback 接住，返回"秒杀服务繁忙"
- **为什么不雪崩**：失败快速返回，不堆积线程；  但功能停摆是事实，没有降级能让秒杀继续跑
- **重试表为什么救不了**：它兜的是"库存扣了  但 MQ 消息丢了"——发消息前先落表，  失败定时重发；Redis 是库存载体，  它挂了连扣库存都无法进行
- **真正解法：主从 + 哨兵（企业级标配）**：  主节点写、从节点实时复制数据；  哨兵监视主节点，挂了自动把从提升为主，  秒级切换，客户端自动重连，故障对用户透明
- **和 Nacos/ES 同一个思路**：Nacos 靠 Raft  选主、ES 靠主分片提升、Redis 靠哨兵切换，  本质都是"数据冗余 + 自动故障转移"
- **边界（面试加分）**：主从是异步复制，  主挂瞬间最后几笔 DECR 可能没同步到从；  但不会真超卖——数据库 WHERE  seckill_stock >= quantity 是第二道防线
- **本项目现状**：单机 Redis，无哨兵。  诚实说："单点中间件是短板，生产要 HA"
- 面试话术："Redis 挂了秒杀必然停摆，这是  设计代价——库存必须放 Redis 才能扛并发；  降级表兜 MQ 可靠性，Redis 高可用要主从 + 哨兵"

### Q11. 秒杀集群化后，定时任务为什么要加分布式锁？为什么不用 Redisson/ShedLock？（2026-09-09 新增）
**追问1**：为什么不加锁不行？
**追问2**：为什么自研而不用 Redisson？
【简答】秒杀从 1 实例变 2 实例后，`@Scheduled` 在**每个实例都会触发**：`MessageRetryTask`（每 5s 扫表重发 MQ）两实例同时 `selectPending` 会拿到**同一批** pending 记录 → 重复投递；`SeckillReconcileTask`（库存对账）会重复执行。本地锁（synchronized/ReentrantLock）**跨不了 JVM**，所以用 Redis 分布式锁：`SET key token NX EX ttl` 单命令原子 + TTL 兜底 + **Lua 比较 token 再删**。
【深挖】
- **为什么"定时"必然冲突**：所有实例共享同一 cron/interval，到点**同时触发**（不像 HTTP 请求被网关分散到不同实例）→ 冲突是**系统性的**，不是偶发
- **为什么这两个任务是定时的**：都是**兜底/补偿**——MQ 发送失败、Redis 与 DB 库存漂移，都属于"不知道何时发生"的异常，没有事件可订阅，只能定期巡检（reconciliation / compensating job）
- **要防的是"并发"不是"重复"**：串行天然安全——第一次执行已 `updateStatusSent`（status=1），第二次 `selectPending` 根本取不到这批记录
- **为什么自研不用 Redisson**：① 只需"抢不到就跳过"的**非阻塞互斥**，Redisson 的可重入/看门狗续期/等待队列/Redlock 都是额外能力；② Redisson 自带连接池（默认 64）与 Netty 线程，老机内存本就紧；③ **阶段 3 要把 Redis 迁到哨兵**，而 Redisson 的哨兵配置是另一套 API（`Config.useSentinelServers()`），与 `spring.data.redis.sentinel.*` 不通用；④ 30 行自研能把"SETNX 原子性/TTL 兜底/Lua CAS"逐行讲清，排错直接 `redis-cli` 看 key/value/TTL
- **Redisson 其实已经在 pom 里**（`mall-seckill-webapi` 引了 3.24.3）**但代码零使用**（死依赖）→ 想换随时能换，且**只改 `RedisLockUtils` 一个类**，两个任务类零改动
- **什么时候该换成 Redisson**：任务耗时可能超过 TTL（需要**看门狗自动续期**）/ 需要可重入 / 抢不到要**排队等待** / 需要 **Redlock** 多节点
- **ShedLock 更贴合本场景**：专为 `@Scheduled` 设计（`@SchedulerLock` + `lockAtMostFor`/`lockAtLeastFor`），语义比裸锁精确；但要引依赖 + 配 provider（Redis/JDBC）
- **Redisson 也不是银弹**：看门狗续期依赖客户端存活（GC 停顿/网络分区仍可能失效）；Redlock 本身有争议（Kleppmann 质疑 antirez）→ **真正的正确性仍靠幂等 + DB 约束**（`updateStatusSent` / `seckill_stock>=qty` / `uk_sku_user`）
- **锁放哪**：放在 `mall-seckill` 而不是 `mall-common`——后者被 **17 个 pom** 引用，改它要重建 11 个 jar；等第二个服务也需要时再抽上去
- 面试话术："秒杀双实例后定时任务会在两个 JVM 同时跑，本地锁跨不了 JVM，所以用 Redis 的 SETNX+TTL+Lua CAS；**要防的是并发不是重复**。我没用 Redisson——场景只要非阻塞互斥，而它带来连接池、另一套哨兵配置和一堆用不上的能力；依赖其实已在 pom 里，等任务耗时超过 TTL 或需要可重入时改一个类就能切。"
