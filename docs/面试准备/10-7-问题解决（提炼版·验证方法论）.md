### Q18. #48 生产造数的两条铁律：**可逆**（能精确幂等地清掉）+ **可证**（能证明造对了、也清干净了）

> 来源：[[问题解决--生产造数的数据隔离与复核方法]] §二 / §三 / §四 / §五 / §六

【追问1】往**生产库**造数据，你最怕什么？前后设计改过吗？
【追问2】"清得干净"凭什么保证？靠用户名/手机号前缀不够吗？
【追问3】你说"校验通过了" —— 万一校验本身漏了呢？

【简答】两条铁律：**① 可逆** —— 必须有一份**唯一的清理依据**（影子登记表），**不能靠"猜哪些是假的"**；**② 可证** —— 校验必须覆盖**"没登记的表"**，否则**漏登记 = 漏回填，校验却照样打印通过**。造数的产出不是"数据"，而是**"数据 + 一份能把它清干净的台账 + 一套能证明它对了的校验"**。

【深挖】
- **为什么"用户名前缀"这条防线不够**（三个实测反例）：
  - ① **清理 SQL 顺序错**（先删用户）→ **订单删不掉**，留残留；
  - ② **不可逆污染** —— `pms_spu.sales`、库存这类**累加型字段算不回去**；
  - ③ **Redis 清理想按 pattern 全删** → **误伤真实数据**（把真实用户的秒杀 key 一起删了）。
  - ⇒ 定稿是**三层兜底**：影子登记表 `cs_mall_sim.sim_batch` / `sim_entity`（**唯一清理依据**）+ **快照回滚**（不可逆字段不硬算；实测 MySQL 数据目录**仅 207M**，全量 6 库快照成本极低）+ **Redis 按登记 id 精确删**（✅ **已完成（2026-09-12 晚）**：按坐标精确删 + `sim_baseline` 基线比对闭环 **0 差异**；#67 至此 **5/6 完成**，**仅剩 ① 录像暂缓**）；清理动作 = **逆序 + 分批 + 幂等 + dry-run**。
- **数据标识从"借用字段"改成专用列**（用户拍板："增加专用字段比较好，避免歧义"）：**9 张表各加 `data_source VARCHAR(16) NULL`**（`NULL` = 常规，`SIM` = 模拟造数）—— 语义是**契约而非借用**：可等值查、**可索引**、零副作用、可扩展（`SIM`/`LOADTEST`/`REPLAY` = 数据血缘）。
  - **回填矩阵按"谁写的"分三类**（这是关键设计）：**脚本直接写**的 4 张按 **PK `id`**（登记表里有）；
  - **服务端写**的 5 张（`ums_login_log` / `oms_payment_record` / `success` / `seckill_message_retry` / `res_upload_record`）**脚本拿不到它们的 PK** → 按 **`user_id` 兜底**；
  - **子表**（`oms_order_item`）按**父订单 `order_id`**（`BACKFILL_BY_ORDER`）→ **即便漏登记也能标上**。
- **实测验收（5 次真跑，最后一次全绿）**：浏览 **38** / 加购 **8** / 下单 **4**（已支付 4、支付失败 0）/ 失败 **0**；**60 行**被标记；`✅ 回填校验通过`；**6 项漏标检查全 0**；**清理演练精确删 56 行** —— 其中包含 **3 条"未登记"的订单项**（靠 `order_child` 模式照样删掉），空批次幂等收尾。
- **加列必然撞上 Flyway 的三个坑**（每个都会让应用起不来或静默不生效）：
  - ① **手工 `ALTER` 与迁移并存** → `Duplicate column name 'data_source'` → **Flyway 失败、应用启动失败**（二者只能选一个，**以迁移为准**）；
  - ② 🔴 **`docker restart` 对新迁移是空操作** —— 迁移 SQL **在 jar 里**、jar 是 `COPY` 进镜像的 ⇒ 必须**重新打包 → `docker compose build` → `up -d`**（本项目实测：镜像内 `app.jar` 字节数与新 jar 逐一相符才算真上线）；
  - ③ **"顺手规范化"已应用迁移的行尾** → Flyway **按文件字节算 checksum** → `Migration checksum mismatch` → 服务起不来（实测本仓库 `core.autocrlf=true` 且无 `*.sql` 的 `.gitattributes`，18 个迁移里 **17 个 `w/lf`、1 个 `w/crlf`**）。
- **判"迁移到底跑了没"的三层判据**（比"容器 running"强得多）：① `flyway_schema_history` 出现新版本号且 **`success=1`** → ② 日志 `Migrating schema …` + `Successfully applied 1 migration` → ③ **最后核库**（`information_schema` 里 9 张表 `data_source` 全部 `varchar(16) nullable=YES`、**总数 = 9**）。
  - ⚠️ **一个"假故障"陷阱**：Flyway **依赖 DataSource**、要等 `HikariPool-1 - Starting...` **之后**才跑，而这 4 个服务启动要 **106.5s ~ 176.5s**（ums 151.9 / order 170.3 / seckill 176.5 / resource 106.5）—— **我第一次复核就在启动 2.5 分钟时误判为"迁移没执行/疑似崩溃"** ⇒ 判据只能是日志里的 `Started …Application in`，不是固定等待时间。
- **一次真跑抓出 8 处（G1~G8），最值钱的三条**：
  - **G3** —— 我**手抄服务端正则抄错了**（phone 多抄一组 `[0-9]`，**12 位 vs 真值 11 位**），靠**机器比对法**（从 Java 源抽字面量逐条 diff + 用库里真实数据交叉验证）才抓出来 ⇒ **禁止手抄正则**，服务端改校验后必须重跑比对；
  - **G5** —— 我误判"浏览接口公开"，因为冒烟看到 **HTTP 200** —— 而**本项目鉴权/业务失败也返回 HTTP 200**（`401/429/409` 都在 body 的 `state` 里）⇒ **任何"看 HTTP 200 就以为成功"的冒烟都会骗你**；
  - **G7** —— 订单子表 **3 行漏标**（`verify_backfill()` **只校验登记表里出现过的表** → 漏标却打印 ✅），根因是经典 **REPEATABLE READ 陷阱**（参数里的 `load_address_template(conn)` 是 SELECT，**先于 App 建单求值、把快照定格在"App 还没建订单"那一刻**）；
  - **G8** 更狠：**付了钱不扣库存**（`OrderQueueConfig:80` 配了 JSON 反序列化 → 消息体成 `ArrayList`，而 `OrderQueueConsumer:32` 只接受 `String` → `NoSuchMethodException` → 进死信，`OrderDlxConsumer:38` 只接受 `Message` → **同样失败 → 消息丢失**；运行时铁证：`订单库存扣减完成` **0 次**、`No listener method found` **21 次** = 7 笔 × 3 次重试）⇒ **按"不夹带"纪律只登记 `#65`（P1），不在造数这次变更里顺手改**；✅ **回填（2026-09-12）：`#65` 已修复 + 部署 + 验收**（AUTO ack / 重试 3 次 / reject 进死信 / 死信告警），**`#70` 的 A~E 五处一并部署**（order jar md5 `d39a2488169270f11eb3452b11674d4a`）。
- **复核方法论 F1~F5（"怎么判它生效了"本身就是个坑）**：
  - **F1** 别按固定等待时间猜"生效了没有"（用 `Started` 判据）；
  - **F2** Nacos/Dubbo 报错是**既有环境噪声**，要**做对照实验** —— 本次**没重建**的 `csmall-product` 有 **7 条** Dubbo 报错 + **126 行**栈、`csmall-front` **134 行**栈，**比重建的 4 个服务更多**；
  - **F3** 别用 `grep 'Caused by'` 数异常（会命中提示语文本"caused by configuration server disconnected"），要用**异常类型指纹** `grep -oE '…\.(Exception|Error)' | sort -u` 再**与未动服务逐类比对有没有新面孔**；
  - **F4** 🔴 别一次 recreate 一大片 —— 8 个同时重建启动 **221~319 秒**（vs 只重建 4 个的 **107~176 秒**，慢 2~3 倍，`load average` 峰值 **7.45**）⇒ **分批 2~3 个**；
  - **F5** 🔴 别用"应用名模式"判断服务起没起 —— 网关主类叫 **`MallGatewayWebApi`**（`Started MallGatewayWebApi in 223.421 seconds`），我的 `Started .*Application` 模式匹配不到，**误报过"网关 13 分钟还没起来"** ⇒ 判据要**多模式或外部探活交叉验证**。

**面试话术**
"往生产库造数据这件事，我的两条铁律是**可逆**和**可证**。**可逆**：我一开始以为用户名加个前缀就够了，实测发现不够 —— 清理 SQL 顺序错了会导致订单删不掉，`sales` 和库存这类**累加型字段根本算不回去**，Redis 按 pattern 删还会**误伤真实数据**；所以最后做成**影子登记表**（`sim_batch`/`sim_entity` 是唯一清理依据）+ **快照回滚**兜底 + Redis 按 id 精确删，清理用**逆序 + 分批 + 幂等 + dry-run**；数据标识也从'借用字段'改成**专用列 `data_source`**，并设计了**按'谁写的'分类的回填矩阵** —— 脚本写的按主键、服务端写的（比如支付记录、登录日志）只能按 `user_id` 兜底，子表按父订单兜底。**可证**：校验必须覆盖**没登记的表**，因为我就栽在这儿 —— 有一次订单子表漏标了 3 行，校验却打印了'✅ 通过'，因为它只校验登记表里出现过的表；根因还是个经典陷阱：**参数里的 SELECT 先开启了脚本事务，把 REPEATABLE READ 快照定格在了'App 还没建订单'那一刻**。过程中还有两件收获：一是**把服务端校验抄进脚本 + 机器比对**，因为手抄正则真的会错（我把手机号抄成了 12 位、真值是 11 位）；二是造数顺带做了一次**全链路体检** —— 发现'支付成功但库存一点没减'，追下去是 MQ 消费端类型不匹配导致消息进了死信又二次失败，**按纪律只登记（`#65`）不改** —— ✅ 回填：它后来被正式修复并验收（AUTO ack + 重试 3 次 + reject 进死信 + 死信告警，`#70` 的 A~E 五处一并部署），"先登记、单独一次上"这个顺序正好保证了它可以独立回滚。"

### Q19. #4 阶段 0 本地双实例分布式锁验证：**"不重复执行"必须由失败方证明**

> 来源：[[问题解决--本地双实例分布式锁验证方法]] §一 / §二 / §三 / §四 / §五

【追问1】你怎么验证分布式定时任务的锁**真的生效**？单实例跑一下不行吗？
【追问2】怎么证明"**没有重复执行**"，而不是"另一个实例根本没在跑"？
【追问3】你验证用的测试/断言**本身**可信吗？这套实验能说明生产没问题吗？

【简答】「锁生效了」是一个**观测不到的命题** —— 锁的价值恰恰体现在**失败方**（没抢到的那一次），而失败方的日志**默认是 DEBUG 级、看不见**；**只看成功方的"我修正了"日志，无法区分"互斥生效"和"另一个实例根本没在跑"**。所以本地起了 **Nacos + 两个真实 JVM** 抢同一把 Redis 锁，用**可证伪的计数断言** + **失败方留痕** + **收尾巡检**三项一起证明。

【深挖】
- **三项断言缺一不可**：
  - **① 互斥** —— 造"两实例同一时刻触发同一任务" → 看**失败方**日志「未抢到锁，跳过本次执行」；
  - **② 无重复执行** —— 人为制造 **N 次**待处理状态 → 看**成功方**日志**条数恰好 N 条**；
  - **③ 锁正确释放** —— 跑完 `KEYS mall:seckill:lock:*` **为空**（无漏锁）**且**两实例能**交替**拿到锁。
  - ⇒ 只有 ② 会退化成"单实例也能过"；只有 ① 证明不了"没重复"；只有 ③ 说明不了互斥。**五条方法论**：真实竞争者（两个真实 JVM + 真实 Redis，不用同进程双线程/mock Redis）· 可证伪判据 · 失败方留痕 · 收尾可断言 · **边界诚实**。
- **实验拓扑与两个设计选择**：本地 MySQL 8.4:3306（`cs_mall_seckill`，12 sku / 6 spu）+ Redis 3.2.100:6379 + RabbitMQ 4.3.0:5672 + 临时 Nacos 2.5.2:8848（standalone），外加**两个真实 JVM**（同一份 jar 137.6MB）：`10007/20880/8870/22222` 与 `10017/20881/8871/22223`。
  - ① **为什么必须起本地 Nacos**：`dubbo.registry.address=N/A` 会让 Dubbo 消费者解析不到 provider 地址、**启动直接失败**；顺带收益是两实例注册到**同一个 Nacos**（`mall-seckill` 下 2 个 `healthy=true`）= **真实集群形态**，而不是"两个互不知道对方的进程"。
  - ② **为什么用"对账任务"造场景而不是"重试任务"**：`SeckillReconcileTask.reconcileOnline` **只读 DB + 写 Redis，无 MQ、无外键副作用**；而 `MessageRetryTask` 要触发就得往 `seckill_message_retry` 插 pending 记录 → **会真的发 MQ**、消费失败重投**污染环境** ⇒ 它**只当交叉证据**（观察抢锁日志）—— 这是**主动控制实验污染面**。
- **可证伪判据怎么造**：对账是**幂等**的（修一次之后 Redis 就等于 DB，再修不会产生第二条日志）⇒ 若无锁、两实例并发修，**N 次漂移会出现 >N 条**；反过来 **恰好 N 条 ⇒ 每次处理只发生一次 ⇒ 无重复**。实操：把 `mall:seckill:sku:stock:1` 从 DB 基准值 **45** 改成 **999**（差异 **954** ≥ 对账阈值 **2**），任务每 **5 秒**跑一次（`--seckill.reconcile.online-fixed-delay=5000`，生产默认 5 分钟），并把任务包日志调到 **DEBUG** 才看得到失败方。
- **实测结果（4 项全绿）**：
  - **4 次漂移 → 恰好 4 条修正日志**（实例1 两条、实例2 两条，修正原文 `【秒杀库存对账】skuId=1, Redis=999, DB=45, 差异=954, 已按DB修正为 45`），且两实例**交替**拿到锁（不是固定一台）→ 释放正常、竞争公平；
  - **失败方累计 7 条「未抢到锁，跳过本次执行」**（实例1 4 条 + 实例2 3 条，**跨两个任务** → 把"互斥"从单点巧合变成**交叉证据**）；
  - 收尾：`KEYS mall:seckill:lock:*` → `[]`（无漏锁）+ Redis 库存 **45** = DB **45** + Nacos 两实例均 `healthy=true`。
  - **判据落在哪一行**：失败方留痕 `MessageRetryTask.java:53` / `SeckillReconcileTask.java:77`；抢不到直接 return（不进临界区）`:51-55` / `:75-79`；**异常也释放（均在 `finally`）** `:90-92` / `:85-87`；统一前缀 `RedisLockUtils.java:44`；释放走 **Lua CAS** `:50-52`、`:106`。
- **坑 1（最值钱）：Mockito `mockito-inline` 在受限环境无法初始化** —— 第一版 10 个用例**全 ERROR**（`Could not initialize inline Byte Buddy mock maker` / `Could not self-attach to current VM using external process`）。
  - 排查三段：`dependency:tree` 证明**版本全兼容**（Mockito 5.7.0 + ByteBuddy 1.14.13 + JDK 21）→ 真根因是 inline mock maker 需要 **self-attach**，而受限环境（Windows 走**命名管道**）禁止 → ⭐ **关键反证**：项目里**早就存在、本来就绿**的 `OmsOrderServiceImplTest` 在**同一环境同样报错** ⇒ **环境限制，不是项目缺陷**（曾一度错写成"本项目无法使用 Mockito"，已纠正）。
  - 处置标准 = **被测逻辑"自己算得出来"用 mock；依赖中间件行为的必须打真实中间件**：锁的互斥语义 → **真实 Redis 集成测试**（mock 掉等于"自己造假 Redis 再自证"）；任务编排 → **手写假件**（`FakeLock extends RedisLockUtils` + 反射代理假 Mapper + `ReflectionTestUtils` 注入）→ **`Tests run: 9, Failures: 0, Errors: 0`**。
- **坑 2：TTL 断言不能用秒 —— "是脚本错了，不是代码错了"**：`getExpire(key, SECONDS)` 对 **1 秒** TTL **向下取整成 0** → 断言 `>0` 失败，看上去像"锁没有 TTL"，**而锁本身是正常的** ⇒ 改 `MILLISECONDS`、断言区间 `(0,1000]`。⭐ **认知：断言失败时，第一个要验证的对象是断言本身** —— 若直接相信它，就会把正确的代码改坏（同类教训见 Q18 的 `grep -c` 数单行 JSON）。
- **坑 3~6 与环境观测**：坑 3 `RedisTemplate.execute` **二义性**（`RedisCallback` / `SessionCallback` 两个重载下 lambda 无法推断 → 显式转型）；坑 4 `QosBindException`（实例2 需 `--dubbo.application.qos-port=22223`，仅 WARN 不致命）；坑 5 `Start-Process` 起的 Nacos **被进程树回收** → 改**后台常驻任务**；坑 6 **Sentinel 日志 850KB 噪音**（`DateFileLogHandler` NPE 刷屏）→ 用**类名精确匹配 + 统计行数**（判据本身就是计数，**靠数不靠看**）。被证伪的怀疑：两实例启动耗时**完全相同（45.377s）**一度像"跑的是同一个进程" —— 实际 **PID 不同、端口不同、Nacos 里确实是双实例** ⇒ **别用耗时当同一性证据，用 PID/端口/注册中心**。
- **边界必须自己划（面试加分项）**：本地**只能证明"机制"，不能证明"容量和故障"** —— 跨机注册 IP 可达性 / 哨兵切换 / `lb://` 跨机轮询 / Nacos 心跳剔除 / 重试任务"发 MQ"路径 / 5Mbps 带宽表现**全部推到服务器阶段**；而且这是一次 **exploratory test，不是可回归的自动化测试**（企业做法 = Testcontainers 统一环境 + Chaos Mesh 注入故障 + Prometheus 断言 + CI 每次跑）。
- **最后一层认知：锁不是正确性的唯一保证** —— 主从**异步复制**下主挂瞬间**锁可能双持**（Redlock 争议），所以三层兜底是 `updateStatusSent`（幂等）+ `seckill_stock >= qty`（条件扣减）+ `uk_sku_user`（唯一索引）⇒ **锁只负责降低并发概率，验证的目标也应是"降低并发"而非"绝不重复"**。

**面试话术**
"我被问过'你怎么验证分布式锁真的生效'。我的回答是：**单实例跑不出锁的价值，也证明不了任何事** —— 我本地起了 Nacos + **两个真实 JVM**（10007/20880 与 10017/20881）注册到同一个 Nacos，让它们抢同一把 Redis 锁。关键在我怎么定判据：我没用'日志看起来正常'，而是**造了一个可证伪的计数断言** —— 对账任务每 5 秒跑一次，我把 `mall:seckill:sku:stock:1` 从 DB 基准值 **45** 人为改成 **999**（差异 954 远超阈值 2），一共制造 **4 次**漂移，结果**恰好出现 4 条修正日志**（实例1 两条、实例2 两条），而且两个实例是**交替**拿到锁的 —— **恰好等于才是证据**：若锁失效、两实例并发修正，条数会超过漂移次数。第二个关键是**看失败方**：锁的价值体现在'没抢到的那一次'，所以我特意把任务包日志调到 DEBUG，拿到失败方累计 **7 条**「未抢到锁，跳过本次执行」，而且这 7 条**跨两个任务**（对账 + 消息重试）—— 把'互斥'从单点巧合变成**交叉证据**。收尾再断言：`KEYS mall:seckill:lock:*` **为空**（无漏锁）+ Redis 库存回到 **45** = DB 基准值 + 两个实例在 Nacos 里都 `healthy=true`。过程里最有价值的教训是：**验证脚本本身也会说谎** —— 我有一条 TTL 断言一直失败，追下去发现是 `getExpire(key, SECONDS)` 对 1 秒 TTL **取整成 0**，代码是对的、断言是错的；**如果直接相信断言，我就会把正确的代码改坏**。另外我原本想用 Mockito 写单测，结果 10 个用例全报 `Could not initialize inline Byte Buddy mock maker`；我**没有直接下'项目不能用 Mockito'的结论**，而是拿项目里本来就绿的 `OmsOrderServiceImplTest` 在同一环境复现了同样的错，证明是**环境限制（禁止 self-attach）而非项目缺陷**，随后换成'**真实 Redis 集成测试锁语义 + 手写假件测任务编排**'，9 例全绿。最后我会主动划边界：**本地只能证明机制，不能证明容量和故障**，跨机注册、哨兵切换、网关轮询、带宽压测当时留到了服务器阶段——**这些后来都在 2026-09-09 的跨机集群实验里做完了**（负载分布 60 请求精确 30:30 / Redis 选主 6.1s、客户端 9.1s 自愈 / 停实例剔除通过）；而且**锁不是正确性的唯一保证**，异步复制下锁可能双持，所以我的三层是'锁降低并发 + 幂等 + DB 约束兜底'。"
