## 一、本次评估的 4 个关键发现（原方案未提及 / 与方案假设不同）

### 发现 1（最重要）：#B3 卡在**数据**，不在代码 —— "商品详情页有规格属性"这个假设不成立

原方案称"商品详情页（`/front/spu/detail/{spuId}`、属性模板 `pms/attribute-templates`）**其实是有规格属性的**"。**实测不成立**：

| 表 | 行数 | 说明 |
|---|---|---|
| `pms_attribute`（属性定义：处理器/屏幕/影像…） | **0 行** | **空的**，没有任何属性定义 |
| `pms_sku_specification`（规格参数值：属性名-值对） | **仅 2 行** | 36 个 SKU 里只有 2 个有规格，且都是"存储容量 = 128GB / 1024GB" |
| `pms_attribute_template`（属性模板） | 3 行 | 手机参数 / 笔记本参数 / 服装尺码（**模板在**） |
| `pms_attribute_template_value`（模板可选值） | 18 行 | 6/8/12GB、128/256/512GB、i5/i7/i9、S~XXL…（**可选值在**） |
| `pms_category_attribute_template`（分类↔模板关联） | **0 行** | 空的 |
| `pms_spu_detail.content`（SPU 详情） | 20 行 | **HTML 富文本**，≈ 120~135 字符：`<h2>标题</h2><img .../><p>一句卖点</p>` —— **不是结构化规格** |
| `pms_spu.description` | 20 行 | **一句话卖点**（如"骁龙 8 Gen3，徕卡影像"）—— 有规格**线索**，无规格**参数** |

**结论**：表结构**支持**规格（模板 + 可选值都在），但**规格值从未录入**。因此 `compare_products` 就算加上"规格"维度，也只能返回 `NULL`/空。要真做"性能/影像/续航对比"，必须先**造规格数据**（给 36 个 SKU 按 3 个模板补 `attribute_name`/`attribute_value`）—— 这是**数据工程**，量级远超 0.5 天，且应与 **#63 商品扩容（20→60）** 一起规划，否则造完还要再补一遍。

### 发现 2：#B5 的根因是"模型**编造 spuId**"，不是"模型编造商品"—— 实测审计完整复现

原方案描述现象为"上一轮给的「小米14/RedmiK70Pro」名称和价格**没有真实数据支撑**"。**实测更精确**：

- 生产库**确实有** `小米 14`（id=5，3999 元）与 `Redmi K70 Pro`（id=20，3299 元）→ **名称和价格是有数据支撑的**
- 错的是 **spuId 绑定**：审计（`ai:agent:action:315127bb…`）实测到模型**自己填了错的 spuId**：

```
2026-09-12 12:47:11  round 1  compare_products  args={"spuIds": [1, 2]}   hits=2   ← 实为 iPhone 15 Pro / 华为 Mate 60 Pro ❌
2026-09-12 12:47:13  round 2  search_products    args={"keywords": "手机"} hits=7
2026-09-12 12:47:14  round 3  compare_products  args={"spuIds": [5, 20]}  hits=2   ← 小米 14 / Redmi K70 Pro ✅
```

**根因链**：`agentMessages()`（`ChatServiceImpl.java:210-220`）回放历史时**只回放 `role`/`content` 文本，工具过程不跨轮持久化**（注释原文："工具过程不跨轮持久化"）。所以模型在**新一轮**里知道"上一轮聊的是小米14/Redmi K70 Pro"（在文本里），但**手上没有 spuId ↔ 名称的映射** → 需要 `spuIds` 参数时只能**猜** → 猜成 `[1,2]` → 用户在商品卡片/详情页按 spuId 核对时发现"名称对不上"。

**⇒ 这不是"幻觉出不存在的商品"，而是"工具参数幻觉（编造 ID）"。** 修法与 #B1 同源：**让工具结果（至少 spuId↔名称）随会话持久化**，模型下一轮就有据可依。

### 发现 3：#B1 的"最难的部分"其实**已经做完了** —— 只差"下发"这一步

`CompareProductsTool`（2026-09-11 随 Agent 上线）**已经**产出了完整的结构化对比数据：

```java
// CompareProductsTool.java:32-33、124-130
private static final List<String> DIMENSIONS = List.of("价格","品牌","分类","销量","库存","标签","标题");
Map<String,Object> observation = { "dimensions": DIMENSIONS, "count": n,
    "products": [ {"spuId":..,"name":..,"price":..,"brand":..,"category":..,"sales":..,"stock":..,"tags":..,"title":..} ] }
```

**但它只被塞进 `observation` 回灌给模型**（`executeToolCall` → `toolMessage`），**从未作为 SSE 事件下发给前端**（SSE 事件全集里没有 `compare`）。所以 #B1 的真实工作量 = **把已有结构透传出去**，比"从零设计结构化对比"轻。

**改造点（唯一的技术障碍）**：`AiToolResult` 目前是 `record (String observation, List<Map<String,Object>> hits)`（`AiToolResult.java:19`）—— 只有"给模型的文本"和"给前端的商品卡片"。要下发对比表，需**加一个结构化载荷字段**（如 `Object payload`），由 `ChatServiceImpl` 在工具执行后判断"这是 compare_products 的结果就发 `compare` 事件"。

### 发现 4：#B2 与 #B1 **目标相反** —— 同时做会互相抵消

原方案把 #B2 写成"补输出格式约定（用标准 GFM 表格）"。**但如果做了 #B1**，目标就变成"**别再让模型用 Markdown 表格**"（表格由 `compare` 事件渲染）。两条一起做 = 一边要模型输出表格、一边要前端忽略表格，**自相矛盾**。

⇒ **正确姿势**：`#B1` 做的话，`prompt` 应改成 **"需要横向对比时不要自行排版表格，系统会渲染对比表"**；`#B2` 从"格式规范"降级为"**禁止表格 + 抑制半截表格**"。

## 二、逐条评估

### #B1 商品对比改为 `compare` SSE 结构化下发 —— ✅ 可做，推荐

**现状（实测）**：
- SSE 事件全集：`thinking` / `products` / `sessionId` / `chunk` / `done` / `error` / `categories`（`categories` 仅固定流水线在 0 商品时发）→ **无 `compare`**（`ChatServiceImpl.java:299/330/373/374/520/523/527/538/542/552`）
- 已有**同构范式**：`emitProductsAndSession()`（`ChatServiceImpl.java:371-376`）就是"把结构化商品列表当事件下发"，前端已能渲染商品卡片
- **真实会话实测**（生产 Redis，session `315127bb…`，2026-09-12）：用户问"帮我对比一下 3000 元左右的两款手机，各自优缺点"→ 模型**自发**输出 GFM 表格，且**首列表头为空**：

```
3000 元左右这个价位段目前只检索到 1 款商品，没法做「两款对比」。我再放宽一下价格范围…
| | Redmi K70 Pro | 小米 14 |
|---|---|---|
| 价格 | 3299 元 | 3999 元 |
| 品牌 | 小米 | 小米 |
| 标题 | 「旗舰手机」 | 「轻薄旗舰手机」 |
| 可售库存 | 250 件 | 300 件 |
```

**⇒ 这就是前端 #F1 表格渲染问题的**真实触发源**（已抓到原始流量），也印证方案判断"提示词只能引导、不能保证"。**

**建议契约**（与现有 `products` 事件同构；前端 `el-table` 可直接吃）：

```jsonc
event: compare
data: {
  "dimensions": ["价格","品牌","分类","销量","库存","标签","标题"],
  "products": [
    { "spuId": "5",  "name": "小米 14",        "values": ["3999元","小米","手机","300","300件","轻薄旗舰","轻薄旗舰手机"] },
    { "spuId": "20", "name": "Redmi K70 Pro", "values": ["3299元","小米","手机","250","250件","旗舰","旗舰手机"] }
  ]
}
```

> ⚠️ **注意形状差异**：工具现在的 `products[]` 是**key-value 对象**（`price`/`brand`/…），方案给的是**按 `dimensions` 顺序的 `values[]` 数组**。二者需要在后端组装时**转换**（或前端按 dimensions 取值）—— 必须在定契约时说定，否则又要改一次。

**4 个必须一并想清楚的设计点（方案未覆盖）**：

| # | 问题 | 建议 |
|---|---|---|
| 1 | **何时发**：只有模型调了 `compare_products` 才有 compare 数据；若模型用 `search_products` **口头对比**，前端仍会收到 Markdown 表格文本 | 配合发现 4：prompt 改成"对比必须调 `compare_products`，不要自己写表格" |
| 2 | **事件顺序**：现有纪律是 `products` **早于首个 `chunk`**（`sendStreamWithAgent` 特意缓冲正文保证顺序，`ChatServiceImpl.java:279-282`） | `compare` 应遵守同一顺序（在正文 `chunk` 之前发）；若工具在后续轮才调，则"表格先于/穿插于正文"要前端能接 |
| 3 | **多次调用发哪个**：审计实测**同一会话内先 `[1,2]` 后 `[5,20]`**（模型自我纠正） | 与 `hits` 的现有策略一致 —— **只发"最近一次成功且非空"的**（`ChatServiceImpl.java:327-329/174-176`） |
| 4 | **空值/缺失占位**：`compare_products` 允许部分 spuId 查不到（走 `missingSpuIds`） | 契约里保留 `missingSpuIds`，前端给"暂无"占位 |

**工作量**：`AiToolResult` 加字段 + `CompareProductsTool` 填载荷 + `ChatServiceImpl` 两处（同步/流式）发事件 + 单测 ≈ **0.5~1 天**（与前端估计一致）。**前端**：`el-table` 渲染 ≈ 0.5 天（前端已声明等契约）。

**风险**：低。纯**新增**事件，不动现有事件 → 前端未升级时表现**与现在完全一致**（继续走 Markdown 渲染）。回滚 = 不识别新事件即可。

### #B2 两个 system prompt 补输出格式约定 —— 🟡 建议不单独做

**现状（行号已逐一核实，与原方案引用一致）**：

| 路径 | 位置 | 现有输出格式规则 |
|---|---|---|
| Agent | `ChatServiceImpl.buildAgentSystemPrompt()` **435-452** | **无**（只有"必须调工具/不许编造/挑 2~4 个"） |
| 固定流水线 | `ChatServiceImpl.buildSystemPrompt()` **783-802** | **无**（只有"简洁自然、说明理由"） |

**实测印证"格式随措辞漂移"**：本次真实会话用户**没说"用表格"**，模型**自发**输出了表格 → 漂移确实存在（且漂到了表格）。

**为什么建议不单独做**：
1. 原方案自己也说了"这是体验优化，不是 bug 修复"——前端 #F1 修好后任何形态都能渲染，**收益仅为观感统一**
2. **与 #B1 冲突**（见发现 4）：若打算做 #B1，此条应改写为"禁止表格"
3. ⚠️ **成本被低估**：prompt 是**硬编码在 jar 里**的（`buildAgentSystemPrompt`/`buildSystemPrompt`），**不能靠 `.env` 改** → 必须 `mvn package` 重编译 + `scp jar` + `recreate mall-ai`（~10~20 分钟），不能和"改一行配置"等同

**若要做，建议的措辞方向**（与 #B1 协同版）：

```
输出格式（重要）：
- 需要横向对比多个商品时，必须调用 compare_products 工具，不要自己排版 Markdown 表格
- 只推荐 1~2 件、不需要逐项对比时，用有序列表 + 加粗，不要硬凑表格
- 不要输出半截表格、不要把表格包在代码块里
```

**验收提醒（同意原方案）**：模型有随机性，**不能只看一次** —— 同一问题多次采样看稳定性。

### #B3 工具补"规格参数"字段 —— ⛔ 不建议现在做（卡数据）

**现状（工具字段实测）**：

| 工具 | 返回给模型的字段 | 有 stock？ | 有规格？ |
|---|---|---|---|
| `search_products`（`SearchProductsTool.buildObservation:138-159`） | `spuId`/`name`/`brand`/`category`/`price`/`sales`/`tags` | ❌ **连库存都没有** | ❌ |
| `compare_products`（`CompareProductsTool:102-112`） | 上列 + `stock`/`title`（共 9 项，`DIMENSIONS` 7 个维度） | ✅ | ❌ |
| `get_stock` | 仅库存数字（`hits` 恒为空，实测 `hits=0`） | ✅ | ❌ |

**模型自述与原方案一致**（"商品库只返回价格、品牌、分类、库存、销量这类基础字段，没有处理器、屏幕、影像、电池等规格参数"）—— **它说的是实话**，因为**库里确实没有**（见发现 1）。模型"拒绝编造、如实说数据不足"的表现**是对的**，不应被视为缺陷。

**为什么代码层解决不了**：
- 加维度只需改 `CompareProductsTool.DIMENSIONS` 一行，但**查出来是空的** —— 数据源（`SpuStandardVO`，`SpuStandardVO.java` 全文 187 行**无任何规格字段**）也没有规格
- 真正的数据在 `pms_sku_specification`（SKU 级：`attribute_name`/`attribute_value`）+ `pms_attribute`（属性定义）—— 前者 **2 行**、后者 **0 行**
- 另外：`SpuStandardVO` 是**SPU 级**视图，而规格是 **SKU 级**（同一 SPU 不同 SKU 规格不同）→ 即便造了数据，`compare_products` 的"SPU 粒度对比"语义也要先想清楚（对比 SPU 还是对比具体 SKU？）

**若将来要做，前置清单（按顺序）**：
1. 补 `pms_attribute`（按 3 个模板定义属性：处理器/屏幕/影像/电池…）
2. 按模板给 36 个 SKU 补 `pms_sku_specification`（**推荐与 #63 商品扩容 20→60 合并做**，避免造两遍）
3. `compare_products` 增加"SKU 规格"维度（或新增 `compare_skus` 工具，按 skuId 对比）
4. 明确 `search_products` 是否也带 `stock`（当前不带，但描述里说"返回…销量"，与实现有落差）

**低配替代（可选的"半步行"）**：把 `pms_spu.description`（一句话卖点，含"骁龙 8 Gen3 / 徕卡影像"等线索）与 `title` 纳入对比维度 —— 能支撑"**卖点对比**"，**但不能支撑"参数表"**。若只是想让对比表看起来更丰富，这是 0.5 天内的选项；若目标是"性能/影像对比"，则**必须先造数**。

### #B5 多轮上下文与工具结果口径 —— 🟠 建议修（已定位为确定性缺陷）

**机制（代码实证）**：
- `agentMessages()`（`ChatServiceImpl.java:209-220`）：`system` + **最近 8 条历史（`AGENT_HISTORY_LIMIT = 8`，`ChatServiceImpl.java:42`）** + 本轮用户消息；**历史只回放 `role`/`content`**，工具调用与工具结果**不入历史**
- `forceFirstTool()`（`ChatServiceImpl.java:196-207`）：仅当消息命中 `PRODUCT_INTENT_KEYWORDS`（`ChatServiceImpl.java:48-50`：买/推荐/找/搜/有没有/有货/库存/多少钱/价格/预算/便宜/贵/**对比**/**比较**/哪个/选/适合）时，首轮 `tool_choice=required`
- 设计初衷（注释 191-194）：**防"模型直接引用历史里的商品作答"**（否则前端商品卡片为空）—— 机制本身**有效**，但**只防住了"不查库"，没防住"乱填参数"**

**实测证据链（生产 Redis 审计，`ai:agent:action:315127bb…`）**：

```
12:40:15  round 1  search_products  {"keywords":"手机","budgetMin":2250,"budgetMax":3900,"sortBy":"sales"}  hits=1
12:40:17  round 2  search_products  {"keywords":"手机","budgetMin":2000,"budgetMax":4500,"sortBy":"sales"}  hits=2
12:40:18  round 3  compare_products {"spuIds":[20,5]}   hits=2   ✅
—— 与 AI 回答原文完全对应："3000 元左右这个价位段目前只检索到 1 款商品…我再放宽一下价格范围"
12:47:11  round 1  compare_products {"spuIds":[1,2]}    hits=2   ❌ 猜错（实为 iPhone 15 Pro / 华为 Mate 60 Pro）
12:47:13  round 2  search_products  {"keywords":"手机"}  hits=7
12:47:14  round 3  compare_products {"spuIds":[5,20]}   hits=2   ✅ 自我纠正
```

**结论**：
- ✅ **模型行为链与审计完全吻合** → **不是"工具返回错数据"，也不是"模型编造商品"**，而是**模型在缺少 id↔名称映射时编造了 spuId**（参数幻觉）
- ✅ 原方案把它列为"观察项（优先级中）"**偏轻**：这是**可复现的确定性缺陷**，且**伤害信任度**（用户按 id 核对发现名不对）
- ⚠️ 原方案"上一轮的名称和价格没有真实数据支撑"的**表述需更正**：名称/价格**有**支撑（库里真有），**错的只是 spuId 绑定**

**修复建议（与 #B1 合并做，成本最低）**：
1. 🔴 **工具结果随会话持久化（推荐，治本）**：把"**最近一次工具命中的 spuId ↔ 名称/价格**"作为**结构化摘要**存进 `ChatSession`（Redis 已有会话存储，`SessionManager.java:67-74`），下一轮拼进 `system`/上下文 → 模型不必猜 id
   - 注意：**不要**把整段 observation / tool 消息全量持久化 → 请求体会膨胀（`AGENT_HISTORY_LIMIT` 注释明确说"工具轮请求体最大…历史必须封顶"）
2. 🟠 **`compare_products` 放宽入参（备选/互补）**：允许按 **`keyword`/`name`** 指定对比对象（内部先搜 ID），模型就不必自造 id
3. 🟡 **prompt 强化（便宜但弱）**：①spuId 必须来自**本轮**工具结果，禁止自造；②缺 id 时先调 `search_products` 取 id。**但 prompt 只是引导，不能保证**（与 #B2 同一道理）
4. ⚪ **`compare_products` 加校验（已部分具备）**：当前查不到就记 `missingSpuIds` 并如实返回（`CompareProductsTool:92-129`）—— 可进一步**在 observation 里明确写"该 spuId 不存在，请从 search_products 结果取"**，把纠错信息给足模型

## 四、面试价值（可选讲法）

- **"AI 输出的可控性分层"**：prompt（引导，最弱）→ **契约/结构化事件（保证，最强）** → 前端容错（兜底）。我实测到"模型自发输出表格且首列空"的真实流量，也验证了"prompt 不能保证格式"这个判断 → 所以把"对比"做成**结构化事件**，让模型只负责**挑维度和填值**，不负责排版。
- **"AI 幻觉的两种形态"**：① 编造**商品**（内容幻觉）② 编造**参数/ID**（工具参数幻觉）。本项目实测是**第二种** —— 模型知道商品名（历史文本里有），但把 `spuId` 猜错，根因是"**工具结果不跨轮持久化**"→ 修复 = 给模型**可信的 id 来源**，而不是骂模型。
- **"诚实的能力边界"**：我实测发现"规格对比做不了"**卡在数据不在代码**（`pms_attribute` 0 行）→ 讲清"我评估后**没做**，因为要给 36 个 SKU 造规格数据、还和商品扩容撞车"**比硬做更有说服力**。
