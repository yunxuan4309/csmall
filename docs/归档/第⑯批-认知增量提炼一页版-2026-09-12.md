## 一、变更生效性：六个检查位（★ 本批最值钱）

| 检查位 | 问自己 | 本批反例 |
|---|---|---|
| ① 落到几个实例？ | 服务有几个实例/副本？改**全**了吗？ | 秒杀双实例只升一台 ⇒ MQ 消息被**旧 jar** 那台消费（#69 的 A/B 因此不通过） |
| ② 改的是被订阅的那份吗？ | 消费侧据以生效的标识是什么？ | Nacos **影子 dataId**：PUT 返回 `true`、GET 也读到 200，应用就是不变 |
| ③ 校验覆盖了会被改的全部字段吗？ | 变更集 ⊆ 校验集 吗？有没有**累加量**？ | 造数校验漏了 `sales` ⇒ **假通过**（比没校验更危险，它会让人停止怀疑） |
| ④ 编排真的跑完了吗？ | 有**独立复核** / **看门狗**吗？ | PowerShell 的 `R` 是 `Invoke-History` 别名 ⇒ 5 步编排**静默空跑** |
| ⑤ 命令真的把容器重建了吗？ | `up -d` 有 `✘`/`pull`/`timeout` 吗？容器 **`Up` 时间**变了吗？ | 镜像 tag 回落 `latest` ⇒ 去公网拉超时 ⇒ **容器根本没重建**（但它继续 `Up`、HTTP 200） |
| ⑥ 前置条件在每台机器上都成立吗？ | 要读的文件、要用的组/权限、要用的镜像，**每台**都满足吗？ | 新机 `.env` 是 `640 ecs-user:ecs-user` ⇒ `compose` 直接 `permission denied`，**构建与重建全没跑** |

⇒ **一句话**：别问「我改了吗」，要问「**生效侧现在是什么**」—— 版本看**逐实例指纹**、配置看**消费侧日志**、数据看**前后基线**、流程看**独立复核**、重建看**`Up` 时间**、依赖看**连接日志**（`delegate=amqp://<user>@<host>` + `ACCESS_REFUSED` 计数为 0）。

## 二、消息可靠性（本批主战场）

1. **`x-death` 不是重投计数器**：classic 队列的 `basicNack(requeue=true)` **不写** `x-death` ⇒ 靠它统计"重试次数"必然恒 0 ⇒ **无限重投**（实测 10 分钟 114 次）。
2. **MANUAL ack 的三个坑**（选 ack 模式前**必须扫全模块监听器**，因为配置可能落在影子位置）：① 抛异常**不会** reject ⇒ 消息**永久 unacked**；② 手动 ack 与容器自动 ack **双确认** ⇒ `406 unknown delivery tag`；③ **yml 可能是影子配置**（服务自带 `RabbitListenerContainerFactory` 时 `spring.rabbitmq.listener.simple.*` 完全不生效）。
3. **本批固化的推荐形态**：`acknowledge-mode: auto` + `default-requeue-rejected: false` + `retry.max-attempts=3`（默认 recoverer = `RejectAndDontRequeueRecoverer`）⇒ 监听器**不碰 channel**，成功即返回、失败即重试、耗尽即 reject。
4. **「修好重投」≠「修好可观测性」**：把"无限重试"改成"拒绝"时要追问 —— **拒绝之后这条消息去哪了？** 没有 DLX = **静默丢弃**（只剩日志）；有 DLX 才有人工补偿的入口（本批 #72 就是补这一环）。
5. **Broker 端资源不可变，但 policy 可以后加**：改已存在队列的 `x-dead-letter-*` / TTL 会 `PRECONDITION_FAILED`（**会把消费弄断**）；`set_policy … --apply-to queues` 能在**不删队列、不丢消息**的前提下补上死信。⚠️ policy 属 **broker 侧配置、不在仓库** ⇒ 重建 broker 后**必须重新施加**。
6. **部署顺序**：**先**部署"声明 DLX 组件"的版本，**再**打 policy；反过来会因 `dead-letter-exchange` 不存在而再次静默丢弃。
7. **`__TypeId__` 是载荷类型的承重结构**：实测去掉它后 `fromMessage` 只得 `LinkedHashMap`（"仅靠方法参数提示兜底"并不成立）⇒ 生产端转换器必须写类型头；死信监听因此要**方法级 + 收原始 `Message`**（#65 的教训）。

## 三、双实例 / 两机漂移（同一份配置，行为却不同）

1. **G14：双实例必须同版本**，验收动作 = **逐实例核容器内 jar md5**（`deploy/scripts/deploy-seckill-both.ps1 -CheckOnly`，只读随时可跑），不能只看一个容器。
2. **镜像 tag 必须在 `.env` 或命令行里落地**：`${VAR:-latest}` 没落地时，一台"恰好有 `latest`"就成功、另一台去公网拉就失败 ⇒ **同一条命令两台结果不同**。
3. **两机的权限/资产口径必须对齐**（本批踩了三次）：`ecs-user` 在不在 `docker` 组；`.env` 是 `664` 还是 `640`；`dockerfiles/` 有没有主 Dockerfile —— 不一致必然出现"这台能跑那台不能跑"。
4. **正规部署路径自带 tag**（脚本用 `yyyyMMdd-HHmm` 时间戳）⇒ **手动无 tag 重建是例外路径**，只用于纯配置变更。

## 四、凭据与取证卫生

1. **明文一旦进入聊天 / 文档 / 提交 ⇒ 视为已泄露**：处置只有两条路 —— **轮换**，或**书面记录「接受」并写明范围**（本批各发生一次，且都留了档）。
2. **取证命令自己别造泄漏**：`--format '{{.Config.Image}} | {{range .Config.Env}}{{println .}}{{end}}'` 会把**镜像名与第一个环境变量粘成一行**，`grep` 一打就把同行密钥带出来 ⇒ 正确写法是 `{{.Name}}{{println}}…` + `grep -E '^…='` **行首锚定**。
3. **切换凭据前先证明新凭据可用**：`rabbitmqctl authenticate_user <user> <pw>`（只读、不改状态）⇒ 再去 recreate 服务。
4. **改服务器配置的标准姿势**：备份 → `read -rp`（或 `read -rsp` 静默输入）→ `sed` 写入 → `unset` → **只回显前 4 位**。

## 五、工具链与验收自身（容易被忽略的一类）

1. **`deploy/` 写在 `.gitignore:49` 里**（里面的关键文件是**遗留 tracked**）⇒ 往 `deploy/` **新增文件必须 `git add -f`**，否则"写了但没入库"。
2. **编辑工具可能抹掉 UTF-8 BOM**：含中文的 `.ps1` 在 PS 5.1 下没有 BOM 会按 ANSI 解析（报"字符串缺少终止符"之类怪错）⇒ 改完 `.ps1` **复查头三字节**（`EF BB BF`）。
3. **管道会吞掉退出码**：`cmd | tail -3` 能让失败"看起来成功"（本批的部署脚本就因此**静默跳过构建**）⇒ 关键命令别挂在管道末尾。
4. **验收命令自身要经得起推敲**：`grep -c 406` 会命中 Nacos 连接 id（`…b220ed2d4061_config-0`）这类**假匹配** ⇒ 要按整串 `channel error 406 PRECONDITION_FAILED` 判。

## 六、面试可直接讲的三段

1. **「我最怕的不是 500，是 200 但是错的」**：本批 6 类反例全都不报错 —— 代码提交了、PUT 返回 `true`、脚本打印 ✅、编排"发出去了"、容器还在 `Up`、HTTP 还是 200。解药只有一条：**到生效侧取证**。
2. **MQ 可靠性从"能跑"到"可观测"**：AUTO ack + 限次重试 + reject → DLX → 告警（**含消息体原文**，可人工补偿）；并讲清 `x-death` 的误区、MANUAL 的三个坑、broker 资源不可变与 policy 补救。
3. **双实例部署纪律**：G14（逐实例核 jar 指纹）、镜像 tag 即版本、两机权限/资产口径对齐 —— 全是**实测踩出来的**，不是设计出来的。
