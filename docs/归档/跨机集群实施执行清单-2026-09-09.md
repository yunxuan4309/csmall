## 二、新发现的 3 个硬障碍（**已定夺，2026-09-09**）

> ✅ **决策记录（2026-09-09 用户拍板，含一次修订）**
> 1. **跨机 Dubbo → 走 Path 1（`DUBBO_IP_TO_REGISTRY` + 端口映射）**：符合 Dubbo 官方为"容器 + 端口映射"场景提供的机制，不依赖网络技巧；代价 = 重启老机 product/order 各约 1 分钟（并入窗口 A，分两步安全落地）
>    > 📌 **修订说明**：初版推荐 Path 2（静态路由 + host 网络），复核后认定它是"手工版 overlay"——依赖对端网段稳定、无自愈、单向可达，**不属于行业规范做法**，故改回规范路径。Path 2 保留为回退方案。
> 2. **Redis 客户端 → 全量迁移 11 个服务到哨兵模式**（canary 灰度 1→3→全量）
> 3. **阶段 0 暂不动代码**：方案先行，等窗口时间敲定后再实施

### 🔴 障碍 1：跨机 Dubbo provider 不可达（原纪要只提了"注册 IP"，实际更严重）

事实 #4：**所有 Dubbo provider 注册的都是容器 IP `172.18.0.x:20880`**。新机秒杀副本要消费 product/order 的 Dubbo 服务，而 `172.18.0.0/16` 是老机的 docker bridge 网段，**新机根本路由不到**（且新机若自建同名网段还会 IP 冲突）。

**根因（原理，必须讲清）**：Dubbo 的地址解析链是
```
消费方订阅接口 → Nacos 返回 provider 地址列表 → 消费方【直连】该地址
```
**Nacos 只做注册发现，不做流量代理**——它不是网关，不会替你转发请求。因此**注册进注册中心的地址，必须是"消费者能直连的地址"**。容器默认注册 bridge 网段 IP（`InetAddress.getLocalHost()` 拿到容器 IP），单机内同网段容器互通所以一直没暴露问题，**跨机立刻断**：

```
新机秒杀副本 → 问 Nacos 要 IForSeckillSpuService 的地址
             → 拿到 172.18.0.18:20880（老机 bridge 网段）
             → 新机路由表里没有 172.18.0.0/16
             → 连不上 → No provider available from registry / client-side timeout
```

**运行时行为（排错必须知道）**：Dubbo 默认 `random` 负载均衡 + `Failover` 集群容错（`retries=2`）+ 本项目 `consumer.check: false`（启动不校验 provider）→ **provider 不可达不会导致启动失败，只在调用期报错**。所以跨机排错不能只看"服务起没起来"，要看消费方调用日志关键词：`No provider available from registry` / `Waiting server-side response timeout` / `Failed to invoke the method`。

**两条解法**：

| 路径 | 做法 | 改谁 | 重启 | 影响面 | 风险 |
|---|---|---|---|---|---|
| **✅ Path 1（已选定）** | 老机 product/order 加 `DUBBO_IP_TO_REGISTRY=172.29.193.239` + `DUBBO_PORT_TO_REGISTRY` + 发布 `20880:20880`/`20881:20880` | 老机 2 个服务 | **要重启 product/order** | 全站 Dubbo 消费方改走宿主 IP | 🟡 中（可分两步降风险） |
| Path 2（回退方案） | 新机加静态路由 `172.18.0.0/16 via 172.29.193.239` + 新机容器 host 网络 | 只改新机 | 无 | 仅新机 | 🟡 依赖老机网段、无自愈 |

**为什么选 Path 1（规范优先）**：
- `DUBBO_IP_TO_REGISTRY` / `DUBBO_PORT_TO_REGISTRY` 是 **Dubbo 官方为容器/NAT 端口映射场景提供**的机制（[主机配置](https://cn.dubbo.apache.org/zh-cn/overview/mannual/java-sdk/tasks/framework/more/set-host/) / [部署到 Docker](https://cn.dubbo.apache.org/zh-cn/overview/mannual/java-sdk/advanced-features-and-usage/others/docker/)）→ 声明式、不依赖网络技巧、无"网段变更即失效"隐患
- **改动面比预想小**：实测 `mall-seckill` **无任何 HTTP/Feign 调用**（`@FeignClient`/`RestTemplate` 零命中），跨机依赖**只有 Dubbo**，且只需老机 **product + order** 两个 provider 改注册
- **对老机本地消费方无副作用（已实测）**：容器 → 宿主私网 IP 的映射端口**可达**（`csmall-mysql` 内 `/dev/tcp/172.29.193.239:8848|5672|9200` 全部 OK）→ 本地消费方走宿主 IP 只多一跳 docker-proxy（毫秒级）
- **两步落地降风险**：先发端口并验证 → 再改注册 IP 重启；端口不通就不动注册

**Path 2 的短板（为什么放弃）**：① 不声明式、无自愈，路由丢了就断；② 依赖老机 `csmall_csmall-net` 网段稳定；③ 只打通单向；④ 违反"容器网络由编排层负责"的分层原则——面试被问"为什么不用 overlay/K8s"时只能答"演示级取舍"

### 🔴 障碍 2：Redis 客户端是 standalone，**哨兵切换后"业务无感"不成立**

事实 #11：11 个服务全部配 `spring.data.redis.host=redis`（standalone）。

### 🟡 障碍 3：跨机地址稳定性 → 必须发布 MySQL/Redis 到宿主内网 IP

## 三、阶段 0：定时任务分布式锁（代码，无服务器依赖）

### 3.1 目标
秒杀双实例后，`@Scheduled` 任务**每 tick 只允许一个实例执行**；不引入新依赖（不引 ShedLock），复用项目已有 SETNX 写法。

### 3.2 改造范围（**只改 mall-seckill，不动 mall-common**）
> 为什么不放 mall-common：`mall-common` 被 11 个 jar 依赖，改它=11 个 jar 全量重建重部署；放 mall-seckill 则只重建 seckill 一个 jar，blast radius 最小。

| 文件 | 改动 |
|---|---|
| `mall-seckill-webapi/.../utils/RedisLockUtils.java` | **新增**：`tryLock(key, ttl)` / `unlock(key, token)`（SETNX + Lua CAS 释放） |
| `.../task/MessageRetryTask.java` | 方法体包一层锁，key=`mall:seckill:lock:message-retry`，TTL 30s |
| `.../task/SeckillReconcileTask.java` | `reconcileOnline` key=`...:lock:reconcile-online` TTL 5min；`reconcileDaily` key=`...:lock:reconcile-daily` TTL 30min |

### 3.3 锁语义设计（面试要讲清的点）

```
tryLock：SET key <token> NX EX <ttl>   —— 单命令原子，NX 保证互斥，EX 兜崩溃
unlock ：Lua 比较 token 再 DEL        —— 只删自己加的锁，防"释放别人的锁"
TTL    ：远大于任务耗时（兜进程被杀/网络断），任务正常结束显式释放
```

**为什么不用"只靠 TTL 不释放"**：那样锁窗口内另一个实例的 tick 会被自己人挡掉，任务实际频率腰斩；**显式释放 + TTL 兜底**既保证不并发双跑（互斥），又保持原有节奏。
**为什么并发才是问题**：`MessageRetryTask` 是"扫表 → 发 MQ → 标记已发"，两个实例**同时**扫会拿到同一批 pending 记录 → **重复发消息**；串行执行则后一次扫描时前一次已标记 `status=1`，安全。

### 3.4 代码骨架

```java
// mall-seckill-webapi/.../utils/RedisLockUtils.java
@Component
public class RedisLockUtils {
    /** 释放锁：仅当 value 与 token 一致才删（防误删他人锁） */
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>(
            "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end",
            Long.class);

    private final StringRedisTemplate redisTemplate;

    public RedisLockUtils(StringRedisTemplate redisTemplate) { this.redisTemplate = redisTemplate; }

    /** 尝试加锁，成功返回 token（释放凭证），失败返回 null */
    public String tryLock(String key, Duration ttl) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redisTemplate.opsForValue().setIfAbsent(key, token, ttl);
        return Boolean.TRUE.equals(ok) ? token : null;
    }

    /** 释放锁（Lua 原子比较并删除） */
    public void unlock(String key, String token) {
        if (token == null) return;
        redisTemplate.execute(UNLOCK_SCRIPT, Collections.singletonList(key), token);
    }
}
```

### 5.3 compose 新增（同一份文件，**仅新机启动**）

```yaml
  # ===== 跨机集群：仅新机（csmall-node2）启动 =====
  redis-replica:
    image: redis:7-alpine
    container_name: csmall-redis-replica
    network_mode: host                       # 关键：注册宿主内网 IP，无需 announce 覆盖
    command: ["redis-server", "/usr/local/etc/redis/redis-replica.conf"]
    volumes:
      - ./redis/redis-replica.conf:/usr/local/etc/redis/redis-replica.conf
      - redis_replica_data:/data
    mem_limit: 256m
    restart: on-failure

  redis-sentinel-1:
    image: redis:7-alpine
    container_name: csmall-sentinel-1
    network_mode: host
    command: ["redis-server", "/usr/local/etc/redis/sentinel-1.conf", "--sentinel"]
    volumes:
      - ./redis/sentinel-1.conf:/usr/local/etc/redis/sentinel-1.conf
      - sentinel_1_data:/data
    mem_limit: 128m
    restart: on-failure
  # redis-sentinel-2 / -3 同构（port 26380 / 26381）
```
+ 顶部 `volumes:` 追加 `redis_replica_data:`、`sentinel_1_data:` 等。
> **为什么 Redis/哨兵用 host 网络、而秒杀副本用 bridge**：Redis 没有注册中心，唯一要求是"主/哨兵看到的是可达地址"——host 网络天然满足（`replica-announce-ip` 只是防御性冗余）；秒杀副本必须在 Nacos/Dubbo 注册**宿主 IP + 映射端口**，故用 bridge + 显式覆盖，与老机同构。
> **新机启动命令永远带服务名**：`docker compose up -d redis-replica redis-sentinel-1 redis-sentinel-2 redis-sentinel-3`（不带服务名会把老机的 21 个服务一起拉起来）。

> 🔴 **阶段 3 踩的坑（三层，逐层剥开，详见 [[TODO第三批实现与原理]] §5.4）**：
> 1. `not writable: Permission denied` → conf 属 `ecs-user(1000)`，容器内 redis 是 **uid 999** → `chown 999:1000` 文件；
> 2. `Could not create tmp config file` → 容器内 `/usr/local/etc/redis/` 属 **root** → 改挂到 `/data`；
> 3. `Could not rename tmp config file (Resource busy)` → **单文件 bind-mount 不能被 rename 覆盖**（Docker 固有限制）→ **改为挂目录 `./redis:/conf`** + 宿主目录 `chown 999:1000`。
>
> 结论：**Redis Sentinel 的配置必须放在「目录挂载」里且属 uid 999**，否则它无法持久化故障转移状态（重启后退回监视旧主）。

### 5.6 可选加固：`min-replicas-to-write 1`（TODO #14-P2）```conf
min-replicas-to-write 1
min-replicas-max-lag 10
```
- ✅ 好处：主库在"从库失联"时**拒绝写入**，防切换丢数据（面试点）
- ⚠️ 代价：**新机宕机 → 老机主库拒绝所有写入 → 全站不可用**。必须**从库同步成功后再开**，且要接受这个取舍（回滚 = 改回 0 并 `CONFIG REWRITE`）
- 建议：演练时开启（讲清取舍），日常演示期可留 0

> **不做的后果**：障碍 2——切换后 11 个服务全部 `READONLY`，"业务无感"是假的。

### 6.1 改动（compose env，11 个服务各加 2 行）

```yaml

> Spring Boot 3.2 原生支持 `spring.data.redis.sentinel.*`；配置了 sentinel 后 `host/port` 自动失效。哨兵无密码，故**不设** `SPRING_DATA_REDIS_SENTINEL_PASSWORD`。

### 6.2 灰度顺序（防 11 个服务一起起不来）

```
① 金丝雀 1 个低影响服务（mall-resource 或 mall-search）→ 重启 → 验证 Redis 读写 + 业务接口
② 扩大到 3 个（sso / product / front）
③ 全量（order / seckill / ums / ams / ai / gateway）
④ 每个服务验证：日志无 Redis 连接异常；接口回归（登录/商品详情/下单）
```
| 验证 | 命令 |
|---|---|
| 客户端真的走了哨兵 | `docker logs csmall-xxx --tail 50 \| grep -i sentinel`；或 kill 老机 Redis 后看服务是否自动连新主 |
| 故障转移端到端 | 停老机 Redis → 秒杀下单/登录**成功** → 起老机 Redis |
| 回滚 | 去掉两个 env → `docker compose up -d <服务>`（standalone 立刻恢复；若此时主库已在新机，需先切回或临时把 host 指向新机） |

> 💡 **验证经验（值得记）**：
> 1. **Lettuce 是懒连接**——服务启动后若没业务访问 Redis，`/proc/net/tcp` 里看不到连接。所以"没连接"≠"配置错了"。
> 2. **哨兵连接是瞬态的**：客户端只在**解析主地址时**连哨兵（26379-26381），之后只保留到主库的长连接 → 用"有没有连哨兵端口"来判断哨兵模式是**错误判据**；正确判据是**主库连接的对端地址是宿主 IP 还是容器 IP**。
> 3. **`mall-resource` 是弱金丝雀**：它几乎不访问 Redis，只能验证"配置没把服务搞挂"，验证不了"真的走了哨兵"。真正的行为验证要用**有定时任务读写 Redis 的服务**（如 `mall-seckill` 的 Quartz 预热）。

### 6.5.1 演练设计（为什么这样做）

**演练暴露/验证的 5 条事实（值得记住）**

1. **脑裂窗口 = 10.9s**：老主库重启后按静态配置（`redis-master.conf` 里没有 `replicaof`）**自认为主**，直到哨兵下发 `+convert-to-slave`。期间它虽可写，但客户端只认哨兵返回的地址，不会连它——**这正是 `min-replicas-to-write 1`（TODO #14-P2）存在的意义**：万一有客户端直连老地址，也能被主库拒绝写。
2. **单文件 bind mount 让 `CONFIG REWRITE` 必然失败**：老机 `redis-master.conf` 是单文件挂载，Redis 改写配置需要"写临时文件 + rename"，在单文件挂载上会 `Resource busy`（与哨兵踩过的坑同源）→ 所以**降级只能靠哨兵运行时下发**，不可能持久化到 conf。
3. **哨兵 conf 会被整体重写，与仓库模板必然漂移**：演练后 3 个 `sentinel-*.conf` 都新增了 `sentinel config-epoch mymaster 2`、`myid`、known-sentinel/known-replica 等运行时状态。→ 🔴 **红线：任何时候都不要把仓库模板反向覆盖运行中的 sentinel conf**（会丢 epoch/拓扑认知）。仓库里的只是"初始模板"。
4. **客户端恢复慢于哨兵切换约 3s**：哨兵 6.1s 完成切换，Lettuce 到 9.1s 才重连（连接看门狗的重试间隔 + 向哨兵重新解析主地址）。**业务无感的前提是客户端配了 sentinel**——standalone 客户端会一直重连老地址直到报错。
5. **`./redis:/conf` 目录挂载把 4 个 conf 都暴露给每个容器**（哨兵容器里能读到 `redis-replica.conf`）。这是"目录挂载解决 Resource busy"的副作用；属同机同信任域，**列为 P3 可选加固**（若要收紧，可给每个哨兵单独建目录，但会重新引入多文件维护成本）。

   新机 5 个集群成员用 `network_mode: host`（见 compose §`redis-replica`/`redis-sentinel-*`，原因见该处注释："host 网络 → 主库/哨兵看到的是宿主内网 IP（跨机可达）"），**host 网络绕过 Docker 端口映射**，监听面由 Redis 自己的 `bind` 指令决定。实测宿主监听：

   LISTEN 0.0.0.0:26380  ← 哨兵（无 requirepass）
   LISTEN 0.0.0.0:26381  ← 哨兵（无 requirepass）
   ```
   哨兵配置：`bind 0.0.0.0` + `protected-mode no` + **无 `requirepass`**（11 个客户端也没配 `spring.data.redis.sentinel.password`）。

   **⭐ Redis 官方的安全模型：哨兵靠"网络隔离"而不是"认证"**
   Redis 自带 `sentinel.conf` 开头就写：
   > *"By default protected mode is disabled in sentinel mode. Sentinel is reachable from interfaces different than localhost. **Make sure the sentinel instance is protected from the outside world via firewalling or other means.**"*

   即：**官方主线防护 = 防火墙/网络隔离；`requirepass` 是可选的第二道锁**。官方同时说明其实现细节：
   > *"You can configure Sentinel itself to require a password, however when doing so **Sentinel will try to authenticate with the same password to all the other Sentinels**. So you need to configure all your Sentinels in a given group with the same `requirepass` password."*

   **不认证时"能连上就能做什么"**（威胁模型）：
   | 命令 | 后果 | 是否被 Redis 默认兜底 |
   |---|---|---|
   | `SENTINEL MONITOR fake <攻击者IP> 6379 2` | **最狠**：客户端按哨兵指示连到假主库 → 客户端把 Redis 密码 `AUTH` 过去（明文）→ **凭据泄露 + 数据写进攻击者库** | ❌ 无兜底 |
   | `SENTINEL FAILOVER` | 人为制造切换 | ❌ 无兜底 |
   | `SENTINEL SET ... down-after-milliseconds` | 让它疯狂误判 | ❌ 无兜底 |
   | `SENTINEL SET ... notification-script/client-reconfig-script` | 触发脚本执行（≈RCE） | ✅ **默认已禁止**（`sentinel deny-scripts-reconfig yes`） |

   - 同机：新机上只有这 4 个容器（未来加容器要重新评估）。
   → 这正好落在 Redis 官方"可信网络"模型内。**因此 #50 降级为"观察项"，不进本批必修**；真正有实测证据支撑的待办是 #14-P2（脑裂写丢失）。
   → 若日后边界变化（多租户 VPC / 临时放开 SG / 新机加入其他实例），优先级再提升：**加 `requirepass`（三个哨兵同一密码，自动互认）+ 客户端配 `spring.data.redis.sentinel.password`**。

   > ⚠️ **两个不能作为防护的手段（2026-09-09 修正）**：
   > 1. **`bind 172.29.193.240` 挡不住公网**——阿里云公网 IP 是 **NAT 映射、不在网卡上**（见 §5.6），发往公网 IP 的包会被 DNAT 成私网 IP 再进网卡，因此监听 `0.0.0.0` 与监听私网 IP 的**公网可达性完全等价**。公网闸门**始终只有安全组**。bind 私网 IP 仅作为"监听面收敛 / 与老机口径一致"的整洁性改进。
   > 2. **`protected-mode no` 不是原因**——它本来就是**哨兵模式的官方默认值**（见上方原文），Redis 官方给出的替代是"用防火墙保护"；且在显式 `bind` 下该开关本就不生效。
   >
   > **实证（公网探测，本地非 VPC）**：`47.109.70.197:26379/6380` 与 `8.156.77.197:6379/3306/10087` **全部 blocked**，仅 `8.156.77.197:80` 可达 → 与绑定地址无关，纯粹是 SG 规则。
   > 📌 这与第一批的认知一致（见 [[TODO第一批实现与原理]] §"3306 全映射 0.0.0.0:3306——安全组挡了公网，但宿主机网卡全监听，纵深防御为零"）：**SG 是边界，bind 只是纵深**。
2. 🟡 **`min-replicas-to-write = 0`**（`CONFIG GET` 实测）→ #14-P2 尚未落地；演练已证明它对应真实存在的 10.9s 脑裂窗口。
3. ℹ️ **哨兵 conf 运行时漂移已量化**（印证 §6.5.6 事实 3）：运行时 conf 比仓库模板多出
   `sentinel myid` / `config-epoch 2` / `leader-epoch 2` / `current-epoch 2` / `known-replica` / `known-sentinel ×2` / `latency-tracking-info-percentiles` / `user default`。

**⭐ 分布式锁专项验证（Redis `MONITOR` 取证）**

1. **常态**：18 秒内抓到 **8 次** `SET mall:seckill:lock:message-retry <uuid> EX 30 NX` + **8 次** Lua `EVALSHA` 解锁，来源交替为两个实例（`172.18.0.1`=老机、`172.29.193.240`=新机）→ **锁代码在两台都生效**。
2. **受控争用**（人工 `SET ... MANUAL-CONTENTION-TEST EX 25 NX` 占锁，模拟"另一实例正在执行"）：
   - 20 秒内两实例共发起 **10 次 `SET NX` 尝试**（各 5 次）——**全部失败**（锁 key 值仍是 `MANUAL-CONTENTION-TEST`）→ **`NX` 互斥生效**；
   - 期间 **0 次解锁**（时间线：`206.903` 新机取锁+释放 → `206.962` 老机取锁+释放 → `207.877` 人工占锁 → 之后无 EVALSHA）→ 抢不到锁的实例**正确跳过，不会误删别人的锁**；
   - 演练后**无残留锁 key**。
3. **结论**：`SET NX EX` + Lua CAS 双保险在跨机双实例下成立 → **定时任务不会双跑**（阶段 0 的代码在真实集群里得到验证）。

### 7.7 停实例故障剔除演练（2026-09-09 21:28—21:32，✅ 通过 + ⚠️ 发现 16s 失败窗口）

**方法**：老机起一个每 2 秒的探针（同时记录「网关 HTTP 码」+「Nacos 实例数」）→ 新机 `docker stop csmall-seckill-2` → 观察 → `docker start` 恢复。

**时间线（探针原始记录）**

| 时刻 | 网关 HTTP | 服务应答 | Nacos 实例数 | 说明 |
|---|---|---|---|---|
| 21:28:49—21:29:03 | 200 | ✅ | 2 | 基线 |
| **21:29:05.190** | — | — | — | 【新机】`docker stop csmall-seckill-2` |
| **21:29:06** | 500 | ❌ | **1** | **Nacos 不到 1 秒就摘除** |
| 21:29:06—21:29:22 | 500/200 **交替** | ❌/✅ | 1 | **网关仍把一半请求打到死实例** |
| 21:29:24 之后 | **全部 200** | ✅ | 1 | 单实例稳定服务 |
| 21:30:41.088 | — | — | — | 【新机】`docker start csmall-seckill-2` |
| 21:32:07.517 | — | — | — | `Started ... in 77.669s`，health 200 |
| 21:32+ | **10/10 = 200** | ✅ | **2（healthy）** | **拓扑复原** |

**两个结论**

1. ✅ **故障剔除成立**：实例死亡后，流量由存活实例承接，最终 **100% 成功、无 5xx**（稳定后连续 40+ 次探测全 200）。
2. ⚠️ **但存在约 16 秒的失败窗口**（9 次请求中 5 次 500）——**"高可用"不等于"零中断"**：
   - **Nacos 侧是即时的**：Spring Cloud Alibaba 在**优雅停机时主动注销**（`ContextClosedEvent` → `deregister`），所以不到 1 秒就从实例列表消失，**不用等 15s 心跳超时**；
   - **客户端侧不是即时的**：网关本地缓存的实例列表 **~16 秒后才刷新**，期间 round-robin 会把一半请求送到已死实例；
   - **根因取证**（网关日志）：`io.netty.channel.AbstractChannel$AnnotatedConnectException: finishConnect(..) failed: Connection refused: /172.29.193.240:10017` → `500 Server Error for HTTP GET "/seckill/spu/list"`。

**改进方向（记入 TODO #53）**

| # | 手段 | 效果 |
|---|---|---|
| ① | 网关加重试（LoadBalancer retry / `spring.cloud.gateway.routes[].metadata.retries`） | 打到死实例的请求自动换实例重试 |
| ② | 缩短 LB 缓存 TTL（`spring.cloud.loadbalancer.cache.ttl`，默认 35s） | 缩短窗口 |
| ③ | **优雅下线**：先注销/摘流量 → 等 > LB 缓存 TTL → 再停容器 | 滚动发布的标准做法，**窗口归零** |
| ④ | 断路器（Sentinel / Resilience4j） | 快速失败，避免请求堆积 |

> 📌 **面试话术**："我实测过停实例：Nacos 是**即时摘除**的（优雅停机主动注销），但网关的 LB 缓存有 ~16 秒延迟，这期间 round-robin 会让一半请求打到死实例报 500。所以『高可用』不等于『零中断』——要真正零中断，得做**优雅下线**（先摘流量、等 LB 刷新完再停）或给网关配重试。这个窗口光看配置文件是发现不了的。"

### 7.7.1 ⭐ 优雅下线验证：16s 失败窗口 → **0**（2026-09-09 21:47 实测，**不需要改网关**）

**关键发现**：`PUT enabled=false` 让实例在 Nacos 里"**退出负载均衡但仍继续服务**"——这才是优雅下线的抓手。

**为什么"注销 API"不行、必须用 `enabled=false`**：

| 手段 | 实测结果 |
|---|---|
| `DELETE /nacos/v1/ns/instance`（注销） | 返回 `ok`，但**客户端心跳立刻把它重新注册**（30s 内始终存在）→ ❌ 无效 |
| **`PUT ...&enabled=false`** | ✅ **实例立即从 `instance/list` 消失**，且**进程仍活着继续服务** |

**验证流程与结果**

| 步骤 | 命令 | 观察 |
|---|---|---|
| ① 摘除 | `PUT /nacos/v1/ns/instance?...&ip=172.29.193.240&port=10017&enabled=false` | 返回 `ok`；实例列表只剩 `172.18.0.19` |
| ② 等待 | `sleep 20`（> LB 缓存刷新） | 期间实例**仍在服务**，无任何失败 |
| ③ 停容器 | 【新机】`docker stop csmall-seckill-2` | 21:47:54 |
| ④ 验证 | 老机打 **30 次**网关 | **30/30 = 200，0 次失败** |
| ⑤ 恢复 | 【新机】`docker start csmall-seckill-2` | `Started in 78.98s`；**实例自动恢复 `enabled=true`**；网关 10/10 = 200 |

| 方式 | 请求数 | 失败数 |
|---|---|---|
| 粗暴 `docker stop` | 9 | **5（500）** |
| **优雅下线（本流程）** | 30 | **0** ✅ |

**脚本已入库**：`deploy/scripts/graceful-stop.sh`（`① enabled=false → ② sleep 40 → ③ docker stop`，失败即中止、不停容器）。

### 7.8 负载均衡分布验证（2026-09-09 21:45，✅ 通过：60 次请求精确 30:30）

**难点**：怎么知道"这个请求被哪个实例处理的"？—— 三个常规手段都不可用：

| 手段 | 结果 |
|---|---|
| 服务日志 | 项目不打访问日志 |
| actuator metrics | 被业务 SSOFilter 拦住（返回 401 业务体） |
| 网关日志 | 只有出错时才有日志 |

**最终方案：用 Redis `MONITOR` 归因**

1. **拿登录态**：`cs_mall_ums.ums_user` 里有 110 个测试账号（`testuser1`~`testuser110`，统一弱密码，仅 demo 数据）→ 经网关登录：
   ```bash
   curl -s -X POST http://127.0.0.1:10087/user/sso/login -H 'Content-Type: application/json' \
        -d '{"username":"testuser1","password":"<统一测试密码>"}'
   # 返回 data.tokenValue，请求时带 Authorization: Bearer <tokenValue>
   ```
2. **关键观察**：`GET /seckill/spu/list?page=1&pageSize=10` 内部对每个 SPU 查缓存（`redisTemplate.hasKey`）→ **每个请求在 Redis 留下 12 条 `EXISTS mall:seckill:reseckill:<spuId>:<skuId>`**，而 `MONITOR` 会记录**命令来源 IP**：
   - `172.18.0.1` = 老机实例（容器出网经 docker bridge SNAT）
   - `172.29.193.240` = 新机实例（宿主 IP）
3. 开 `MONITOR` → 经网关打 **60 次**请求（间隔 0.4s）→ 按来源 IP 计数。

**结果**

| 项 | 值 |
|---|---|
| 请求数 | **60**（HTTP 200 全部成功） |
| Redis `EXISTS` 命令总数 | **720**（= 60 × 12，验证了"每请求 12 条"的假设） |
| 老机实例（源 `172.18.0.1`） | **360 条 → 30 个请求** |
| 新机实例（源 `172.29.193.240`） | **360 条 → 30 个请求** |
| **分布** | **50% : 50%（精确 30:30）** |

→ **Spring Cloud LoadBalancer 默认 `RoundRobin` 生效，跨机轮询精确均分**。至此阶段 4 的"双实例 + 负载均衡 + 故障剔除 + 定时任务不双跑"四项全部拿到实测证据。

### 7.9 #14-P2 运行时开启（2026-09-09 21:45，**只开主库**）

**背景**：§6.4 演练实测到 **10.9s 脑裂窗口**（老主库重启后自认为主，直到哨兵降级）；Redis 官方文档对同一场景给出的补丁是 `min-replicas-to-write 1` + `min-replicas-max-lag 10`。

**执行（无需重启、可随时回退）**

```bash
# 【老机】主库 —— 开启
cd /data/csmall; PW=$(grep -E '^REDIS_PASSWORD=' .env | cut -d= -f2-)
docker exec csmall-redis redis-cli -a "$PW" --no-auth-warning CONFIG SET min-replicas-to-write 1
docker exec csmall-redis redis-cli -a "$PW" --no-auth-warning CONFIG SET min-replicas-max-lag 10
# 回退：把 1 改成 0（一条命令，立即生效）

# 【新机】从库 —— ⚠️ 明确【不开】（见下方"为什么不能开在从库上"）
```

**实测结果**

| 检查 | 结果 |
|---|---|
| 老机主库 `min-replicas-to-write` | `0` → **`1`**（`max-lag 10`） |
| 新机从库 | **保持 `0`**（已回退） |
| 写操作（从库在线） | ✅ `SET` 返回 `OK` |
| 复制状态 | ✅ `role:master`、`connected_slaves:1`、`slave0 lag=0` |

**⚠️ 为什么绝对不能开在从库上（2026-09-09 复核发现）**

`min-replicas-to-write` 是**服务器级**参数，**从库被提升为主库后立即生效**。而故障转移后，新主库在"老机重新连上来当从库"之前**手里一个从库都没有**：

| 场景 | 开在从库上的后果 |
|---|---|
| 老机宕机 → 新机被提升 | 新机无从库 → **写操作全部失败，直到老机恢复** |
| 老机长时间不恢复 | 新机**一直不能写** → 比不开更糟 |

换来的保护（新主库崩溃只丢 ≤1s AOF 数据）远小于这个代价 → **决策：只开主库**。

**⚠️ 代价与"演练开关"（主库侧）**

只有一个从库 → **新机不可用时，老机主库会拒写**。所以：

| 场景 | 操作 |
|---|---|
| 要停新机（演练/维护） | 先 `CONFIG SET min-replicas-to-write 0`，完事再设回 `1` |
| 想长期只看可用性 | 直接保持 `0`（放弃分区防丢保护） |

**持久化（用户 sudo，无需重启 Redis）**

```bash
# 【老机】只改 redis-master.conf；redis-replica.conf 不要加（见上）
sudo tee -a /data/csmall/redis/redis-master.conf >/dev/null <<'EOF'

# 2026-09-09 #14-P2：防主从切换丢数据（脑裂窗口内主库拒写）
min-replicas-to-write 1
min-replicas-max-lag 10
EOF
```

> 📌 仓库模板 `deploy/docker/redis/redis-master.conf` 已同步；`redis-replica.conf` 里写明了"不要加"的原因。

## 十一、面试话术（本批可讲点）

1. **跨机容器互通的两种解法**：注册宿主 IP + 端口映射（Dubbo 官方 `DUBBO_IP_TO_REGISTRY`，规范做法）vs 静态路由打通 bridge 网段（手工版 overlay，非规范）——我选了前者，因为它声明式、无"网段变更即失效"隐患
2. **哨兵为什么必须 3 个**：多数派机制，容忍度 =(N-1)/2；2 哨兵挂 1 个即失去仲裁（不是"奇数迷信"）
3. **主从切换的业务无感前提**：客户端必须配 sentinel 模式——standalone 客户端在切换后打到只读从库会 `READONLY`（我实测扫过 11 个服务的 Redis 写点）
4. **双实例定时任务**：SETNX+TTL 互斥 + Lua CAS 释放；并发才是问题（同批 pending 会被重复发 MQ）
5. **注册 IP 陷阱**：容器默认注册 bridge IP，跨机不可达；两条标准解法——`DUBBO_IP_TO_REGISTRY`/`SPRING_CLOUD_NACOS_DISCOVERY_IP`（注册层改写）或 host 网络（网络层）
6. **诚实边界**：2 台小机 = 演示级 HA，不防地域灾难；其余 19 容器仍是老机单实例
7. **边界认知（认知修正）**：**"绑私网 IP 就安全了"在阿里云 NAT 架构下不成立**——公网 IP 不在网卡上，发往它的包被 DNAT 成私网 IP 再进网卡，所以 `bind 0.0.0.0` 与 `bind 私网 IP` 的**公网可达性等价**，唯一公网闸门是安全组。四层边界模型：**SG（边界）→ bind（监听面）→ 认证（身份）→ TLS（传输）**；实测 6379/3306/26379/6380 全被 SG 挡住而绑法各异，`:80` 放开即通。详见 [[TODO第三批实现与原理]] §5.6⑥

## 十二、知识补充：文件完整性校验（哈希指纹）

> 起因：本批每次下发 compose/配置/jar，AI 都要求"本地算 md5 → 你落位后 `md5sum` 比对"。这不是仪式，是**内容寻址（content addressing）**这一通用工程实践的手工版。

### 12.1 我们为什么需要它

跨机下发要经过 **4 跳**：`本地仓库 → scp → 服务器 /tmp → sudo cp → /data/csmall`。每一跳都可能静默出错：

| 风险 | 具体表现 | 本批是否遇到过 |
|---|---|---|
| 换行符转换 | CRLF ↔ LF 差异 | 是（git 换行警告） |
| 编码/BOM | UTF-8 BOM 使首行解析异常 | 是（写 Java 校验工具时） |
| 传输截断 | 大文件中断、磁盘满 | 未遇到（但有风险） |
| 复制不完整 | `cp` 失败/权限不足被忽略 | 未遇到（但有风险） |

> ⚠️ **本仓库自身就有此风险**：每次 `git add` 都提示 `LF will be replaced by CRLF`——说明本机 `core.autocrlf` 会在检出时改写换行符。所以"本地文件与服务器文件是否同字节"**不能靠肉眼，只能靠哈希**。

**哈希 = 文件内容的"身份证"**：内容差 1 个字节（哪怕一个空格、一个换行），32 位十六进制全变。所以 `md5sum` 一致 ⟺ **服务器上的文件与仓库里的文件字节级相同**。

它把"仓库为事实来源"这条纪律从**口号**变成了**可验证的断言**——这是本批最实用的一条运维纪律（已并入 §开头「命令块纪律」第 6 条）。

### 12.2 它是版本号吗？—— 不是

| | 版本号 | 哈希指纹 |
|---|---|---|
| 语义 | 人为命名，单调递增（`v1.2.0`） | 内容的数学函数，无顺序含义 |
| 用途 | 沟通、发布、回滚标记 | **校验"是不是同一份内容"** |
| 改内容会怎样 | 需要人工改 | **自动全变**（这正是我们要的） |

所以本批记录的 `compose md5 b6591fac…` 只回答一个问题："两台机器/仓库里的 compose 是同一份吗？"——不表达"这是第几版"。

### 12.3 行业规范吗？—— 是，而且企业里更自动化

| 场景 | 行业做法 |
|---|---|
| 软件分发 | 发行版 ISO 公布 **SHA-256**；Maven Central 每个制品旁挂 `.sha1`/`.md5` |
| 容器 | 镜像 **digest = `sha256:…`**（内容寻址；`image@sha256:…` 拉取即校验） |
| K8s | ConfigMap/Secret 变更触发滚动更新靠**内容哈希**（Helm `checksum/config` 注解） |
| CI/CD | 制品完整性、SBOM、**SLSA** 供应链 |
| 备份 | `mysqldump \| sha256sum`，恢复后比对 |
| 配置管理 | Ansible/GitOps 下发后做**漂移检测（drift detection）** |

> 我们做的是**手工版**（AI 算 + 人比对）；企业里是**自动版**：CI 产出制品并记录 digest，Ansible/Argo CD 下发后自动比对并报告漂移。**原理完全相同，只是被自动化了。**

### 12.4 局限与更优选择（诚实边界）

1. **MD5 已被证明可构造碰撞**（2004 年起）→ **防"意外损坏"够用，防"恶意篡改"不够**
2. 现代默认应选 **SHA-256**；本批场景是防意外（传输/编码/截断），MD5 可接受，但换 `sha256sum` 更规范
3. 更好的演进路径（择机做，对应 TODO #39）：
   - ① 改用 `sha256sum`（零成本）
   - ② 配置纳入 git，服务器 `git pull` —— git 的对象哈希天然完成校验
   - ③ CI 构建 + 制品 digest 下发（彻底告别手工比对）
