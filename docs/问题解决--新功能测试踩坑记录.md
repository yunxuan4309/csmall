## 一、SkyWalking 全模块接入

### 1.1 mall-resource 启动报错：Public Key Retrieval is not allowed

**现象**：
```
java.sql.SQLNonTransientConnectionException: Public Key Retrieval is not allowed
```

**根因**：`mall-resource` 的 `application-test.yml` 中 JDBC URL 缺少 `allowPublicKeyRetrieval=true` 参数。MySQL 8.0 默认使用 `caching_sha2_password` 认证插件，JDBC 驱动需要显式允许获取公钥。该模块是 11 个模块中唯一漏加此参数的。

**解决**：在 `mall-resource/src/main/resources/application-test.yml` 的 JDBC URL 末尾追加 `&allowPublicKeyRetrieval=true`。

**教训**：所有数据库连接模块的 JDBC URL 应保持一致的参数配置。建议在项目文档中维护一份标准的 JDBC URL 模板。

## 二、JMeter 压测联合演示

### 2.1 JMeter .jmx 文件 XML 结构错误：ClassCastException

**现象**：
```
ClassCastException: class RegexExtractor cannot be cast to class HashTree
```

**根因**：手写 JMeter 测试计划 XML 时，HashTree 内的子元素（HeaderManager、RegexExtractor、JSR223PostProcessor 等）必须各自跟随一个 `<hashTree/>` 标签（即便是空的）。缺少这些空标签时，JMeter 的 XStream 解析器会将下一个元素误解析为 HashTree 导致类型转换失败。

**正确结构**：
```xml
<HTTPSamplerProxy>...</HTTPSamplerProxy>
<hashTree>
  <HeaderManager>...</HeaderManager>
  <hashTree/>                       <!-- 必须！ -->
  <RegexExtractor>...</RegexExtractor>
  <hashTree/>                       <!-- 必须！ -->
</hashTree>
```

**解决**：在 HashTree 内每个非 HashTree 子元素后手动添加 `<hashTree/>`。

### 2.2 TestPlan User Defined Variables 无法被 `__P` 函数读取

**现象**：Login 请求的 body 中 `${__P(USERNAME,testuser1)}` 被当作字面文本发送，未被解析为 `testuser1`。登录请求 body 为 `{"username":"${__P(USERNAME,testuser1)}","password":"${__P(PASSWORD,123456)}"}`。

**根因**：JMeter 有两套独立的变量体系——**Variables**（线程局部，通过 `${VARNAME}` 访问）和 **Properties**（全局，通过 `${__P(propName)}` 访问）。TestPlan 中 `User Defined Variables` 定义的是 Variables，不能用 `__P()` 函数读取。

**解决**：将所有 TestPlan 级别变量从 `${__P(VARNAME,default)}` 改为 `${VARNAME}`，仅保留 JSR223 写入的跨线程属性（TOKEN、RAND_CODE）使用 `${__P()}`。

### 2.3 前置线程组提取的 Token 无法被后续请求使用

**现象**：Setup 线程组的 Login 成功提取了 Token，但 Get SPU 请求返回 401 "您没有登录！"。

**根因**：Token 通过 RegexExtractor 提取后存储为 JMeter **变量**（`${TOKEN}`），但 HeaderManager 中 `Authorization: Bearer ${TOKEN}` 未生效。经排查，JMeter 在加载手写的 HeaderManager XML 后会将其**静默删除**（因为结构不完全符合其内部验证）。

**解决方案演进**：
1. 尝试添加 `HeaderManager` 到 Get SPU 的 hashTree → JMeter 重新序列化时被删除
2. 尝试使用 `JSR223PreProcessor` 动态注入 header → 同样被删除
3. **最终方案**：将 HeaderManager 放在 ThreadGroup 级别（而非 Sampler 级别），`Content-Type` 头对所有请求生效；Sampler 级别的 `Authorization` 头通过规范的 XML 结构保留

**教训**：手写 JMeter XML 时，必须严格遵循 JMeter 保存的 XML 格式（包括所有 `testclass` 属性、`enabled` 属性等），否则 JMeter 会在重新序列化时丢弃不合规元素。

### 2.4 contactName 校验失败：名称必须由2~4字符组成

**现象**：部分线程返回 `"名称必须由2~4字符组成！"`。

**根因**：请求体中 `contactName` 使用了 `"U-${__threadNum}"`，线程 100 时 `"U-100"` 为 5 字符，超出 4 字符限制。

**解决**：改为 `"U${__threadNum}"`（去掉短横线），线程 1→"U1"(2字符)，线程 100→"U100"(4字符)。

### 2.5 单一用户重复购买拦截导致压测效果不佳

**现象**：100 线程共用同一个 token（testuser1），第一条成功后剩余 99 条全部触发 Redis 防重检查 "您已经购买过这个商品了"。

**解决方案**：
1. 在数据库 `ums_user` 表中新增 8 个测试用户（testuser1~testuser10）
2. 创建 CSV 用户凭证文件（`deploy/jmeter/users.csv`）
3. 将测试计划从 Setup+Main 双线程组改为单 ThreadGroup 结构，使用 `CSV Data Set Config` 循环分配不同用户账号
4. 每个线程独立登录 → 获取 SPU → 提交秒杀，10 个用户 × 10 轮循环 = 100 线程

### 2.6 Windows 终端编码导致中文批处理脚本乱码

**现象**：`run-demo.bat` 在 PowerShell 中执行时所有中文字符显示为乱码，`echo` 命令被截断。

**根因**：批处理文件为 UTF-8 编码，但 Windows cmd.exe/PowerShell 默认使用 GBK 编码。

**解决**：将所有 echo 输出改为纯 ASCII 英文文本，避免编码问题。并将 JMeter 启动方式从批处理脚本改为 IDEA JAR Application Run Configuration（直接执行 `ApacheJMeter.jar`）。

## 三、AI 搜索增强

### 3.1 ES Completion Suggester 返回空结果

**现象**：搜索框输入文字后下拉框一闪而过，无补全建议。

**根因**：ES 索引 `cool_shark_mall_ai` 在创建时未包含 `suggestField`（completion 类型）。`EsIndexInitializer` 只在索引不存在时创建，已存在的索引不会更新 mapping。商品同步时也未写入补全数据。

**解决**：
1. 通过 ES PUT Mapping API 为现有索引添加 `suggestField` 字段：
   ```bash
   curl -X PUT "localhost:9200/cool_shark_mall_ai/_mapping" \
     -H "Content-Type: application/json" \
     -d '{"properties":{"suggestField":{"type":"completion"}}}'
   ```
2. 修改 `VectorSyncServiceImpl` 在同步时为 `suggestField` 写入补全词（name + brandName + categoryName + title 的组合）
3. 重新执行 `/ai/sync` 同步 20 条商品到 ES

### 3.2 ES 客户端 `Hit::source` 方法引用类型推断失败

**现象**：编译错误
```
不兼容的类型: 无法推断类型变量 R,A,capture#1,共 ?,T
```

**根因**：`SearchResponse<Map>` 使用原始类型 `Map`，`.map(Hit::source)` 方法引用返回 `Stream<Map>`（raw），无法被 `Collectors.toList()` 推断为 `List<Map<String, Object>>`。

**解决**：将 `.map(Hit::source)` 改为显式转型的 lambda 表达式 `.map(hit -> (Map<String, Object>) hit.source())`。

### 3.3 搜索自动补全不是模糊匹配

**现象**：输入"手机"可匹配"手机 iPhone 15"，输入"平板"可匹配"平板电脑 xxx"，但输入"电脑"无法匹配"平板电脑"。

**根因**：ES Completion Suggester 基于 FST（有限状态机）实现，仅支持**前缀匹配**。"平板电脑"是以"平板"开头而非"电脑"，所以"电脑"无法匹配。这是 ES Completion Suggester 的固有特性，并非 bug。

**结论**：不需要修改。前缀匹配是搜索自动补全的标准行为（类比 Google 搜索框）。

### 3.4 "看了又看"商品卡片点击无法跳转

**现象**：商品详情页底部"看了又看"区域显示正常，但点击卡片无任何反应，浏览器控制台无输出。

**根因**：Element Plus 的 `el-image` 组件默认启用图片预览功能，点击图片会触发预览遮罩层，阻止事件冒泡到父元素的 `@click` 处理器。此外，`el-card` 的 `shadow="hover"` 也会干扰点击事件。

**解决方案演进**：
1. 给 `el-image` 添加 `:preview-src-list="[]"` 禁用预览 → 仍然不生效
2. 将 `@click` 从 `el-card` 移到外层 `<div>` 包装器 → 点击生效但路由不跳转
3. 添加 `console.log` 调试 → 确认函数执行了但 `router.push` 不导航
4. **确认根因**：`router.push` 到同一组件（ProductDetail）时 Vue Router 不会重新挂载组件，而是在已有实例上复用。原代码只在 `onMounted` 中调用 `fetchProductDetail()`，无 `watch` 监听路由参数变化，因此 URL 改变但页面内容不变
5. **最终修复**：
   - 添加 `watch(() => route.params.id, (newId) => { if (newId) fetchProductDetail() })` 监听参数变化
   - 改用 `router.push('/product/' + spuId)` 字符串路径（更可靠）

### 3.5 搜索框 `el-autocomplete` 下拉框一闪而过

**现象**：输入"手机"后下拉框弹出但瞬间消失。

**根因**：ES 索引中没有 completion 数据时，`/ai/search/suggest` 返回空数组，`el-autocomplete` 的 `fetchSuggestions` 回调收到空数组后自动关闭下拉框。同时 API 请求有 200ms 防抖延迟，期间用户继续输入会触发新的请求，旧的请求被取消。

**解决**：问题 3.1 修复后（索引添加 suggestField + 重新同步），补全数据正常返回，下拉框正常显示。

## 四、秒杀 MQ 降级

### 4.1 `retryMapper.insert()` 触发 Seata Druid 解析错误

**现象**：
```
Caused by: com.alibaba.druid.sql.parser.ParserException: ERROR. pos 206, line 4, column 40, token ,
```

**根因**：`SeckillMessageRetryMapper.xml` 的 INSERT 语句中使用了 `NOW()` 函数，Seata 的 Druid SQL 解析器无法正确解析 `NOW()` 与 MyBatis `#{}` 参数占位符混合使用的场景。

**解决**：将 `NOW()` 替换为 `#{gmtCreate}`，在 Java 代码中显式设置 `retry.setGmtCreate(LocalDateTime.now())`。

### 4.2 INSERT 语句中字面值与参数混合导致 Druid 解析失败

**现象**：移除 `NOW()` 后仍报错，且错误信息不明确。

**根因**：SQL 中 `VALUES (#{id}, #{userId}, ..., 0, 0, NOW())` 的 `0, 0` 字面值与 `#{}` 参数混合，Seata Druid 解析器对逗号的处理出现问题。

**解决**：将所有字面值改为参数占位符 `#{status}, #{retryCount}`，Java 端显式 set 值。同时将 SQL 格式统一为与项目其他 Mapper XML 一致的小写单行格式。

### 4.3 MyBatis-Plus 自动填充列名不匹配

**现象**：
```
Unknown column 'gmt_create' in 'field list'
```
实际执行的 SQL 为：
```sql
INSERT INTO seckill_message_retry (..., create_time, gmt_create, gmt_modified) VALUES (...)
```

**根因**：MyBatis-Plus 的 `MetaObjectHandler` 自动填充机制会对所有实体尝试填充 `gmtCreate` 和 `gmtModified` 字段，转换为列名 `gmt_create` 和 `gmt_modified`。但我们的表最初使用 `create_time` 和 `update_time` 命名，与项目其他所有表的 `gmt_create`/`gmt_modified` 命名不一致。

**解决**：
1. Flyway 迁移 V5 SQL：`create_time` → `gmt_create`，`update_time` → `gmt_modified`
2. POJO 字段：`createTime` → `gmtCreate`，`updateTime` → `gmtModified`
3. Mapper XML：所有引用统一更新
4. 数据库表：drop 后重建以匹配新列名
5. Flyway 历史记录：清理迁移失败记录，修复 checksum

### 4.4 Flyway 迁移冲突

**现象**：多次出现 Flyway 启动失败，包括：
- `Table 'seckill_message_retry' already exists`
- `Detected failed migration to version 5`
- `Migration checksum mismatch for migration version 5`

**根因**：在修复 4.3 的过程中，多次手工操作了数据库表（DROP/CREATE）和 Flyway 历史表（DELETE/INSERT/UPDATE），导致 Flyway 的元数据与实际状态不一致。

**解决**：
1. 手动重建数据库表以匹配最新列名
2. 在 `flyway_schema_history` 中正确标记 V5 迁移状态
3. 修复 checksum 值以匹配本地 SQL 文件

**教训**：Flyway 管理的表不应该手工修改，应通过创建新的迁移版本（如 V6）来修改表结构。但在紧急修复阶段，手工操作后必须同步更新 `flyway_schema_history`。

### 4.5 Dubbo 调用失败时 Redis 库存未补偿

**现象**：RabbitMQ 宕机后，order 服务的 `OmsOrderServiceImpl.addOrder()` 内部发送 MQ 失败，异常通过 Dubbo 传回 seckill 服务。此时 Redis 库存已被扣减，但补偿逻辑未覆盖 Dubbo 调用异常。

**根因**：最初的 try-catch 只包裹了 seckill 模块自身的 `rabbitTemplate.convertAndSend()`，未包裹 `dubboOrderService.addOrder()`。order 服务内部也有 MQ 操作，其异常会穿透到 seckill 模块触发 Seata 回滚，但 Redis 库存已扣。

**解决**：将 Dubbo 调用也纳入 try-catch 保护范围，统一补偿逻辑：
```java
try {
    orderAddVO = dubboOrderService.addOrder(orderAddDTO);
} catch (Exception e) {
    // 补偿 Redis 库存
    stringRedisTemplate.boundValueOps(skuStockKey).increment();
    stringRedisTemplate.delete(reSeckillCheckKey);
    throw new CoolSharkServiceException(...);
}
```

### 4.6 补偿后仍显示"已购买"

**现象**：秒杀失败（被补偿）后，秒杀列表仍显示"已购买"标签。

**根因**：补偿时使用 `DECR` 将防重 key 从 1 减为 0，但 Redis 中值为 0 的 key 依然存在，`hasKey()` 返回 true，`isPurchased()` 检查误判为已购买。

**解决**：将所有补偿场景下的 `DECR` 改为 `DELETE`，彻底删除防重 key。

### 4.7 销量数据不联动更新

**现象**：秒杀成功后 `seckill_sku` 和 Redis 库存正常扣减，但前台"已售"数字不变化。

**根因**：`pms_spu.sales` 字段在原代码中只是静态测试数据，无论正常下单还是秒杀下单都不会自动增加。秒杀消费者（`SeckillQueueConsumer`）中没有更新销量的逻辑。

**解决**：
1. 在 `IForSeckillSpuService` Dubbo 接口新增 `incrementSales(spuId)` 方法
2. mall-product 模块实现该方法（`SpuMapper.incrementSales` → `UPDATE pms_spu SET sales = sales + 1`）
3. `SeckillSkuMapper` 新增 `findBySkuId` 方法（从 skuId 获取 spuId）
4. `SeckillQueueConsumer` 在 ACK 后调用 Dubbo 更新销量（try-catch 保护，失败不影响主流程）

## 五、通用/跨功能问题

### 5.1 秒杀 SPU VO Redis 缓存与 Java 序列化兼容性

**现象**：给 `SeckillSpuVO` 添加 `purchased` 字段后，部分秒杀商品显示 NaN 价格或数据异常。

**根因**：Redis 中缓存的 `SeckillSpuVO` 是通过 Java 原生序列化（`RedisTemplate` 默认）存储的。类定义变更后（新增 `purchased` 字段），旧的序列化字节流在反序列化时可能产生不兼容。

**解决**：清空 Redis 中所有 `mall:seckill:spu:vo:*` 和 `mall:seckill:sku:vo:*` 缓存，让它们重新从数据库加载。

**教训**：使用 Java 原生序列化缓存对象时，类结构变更后必须清理缓存。建议通过设置合理的 TTL 或版本号来管理缓存失效。

### 5.2 数据库残留测试数据干扰

**现象**：`success` 表中存在 7 月 19 日和 JMeter 压测遗留的购买记录，导致 testuser1 查看秒杀列表时误显示"已购买"。

**解决**：清理 `success` 表和 Redis `mall:seckill:reseckill:*` 残留 key。

**教训**：测试结束后应及时清理数据库和 Redis 中的测试数据，避免干扰后续测试。

### 5.3 Windows 环境下 RabbitMQ 管理命令不可用

**现象**：`rabbitmqctl` 命令提示"不是内部或外部命令"。

**根因**：Windows 版 RabbitMQ 安装后未将 sbin 目录加入系统 PATH 环境变量。

**解决**：改用 Windows 服务管理命令 `net stop RabbitMQ` / `net start RabbitMQ`（需管理员权限），或通过 Windows 服务管理器（`services.msc`）操作。

## 六、经验总结

1. **手写 JMeter XML 陷阱多**：JMeter 对 XML 结构有严格要求（每个非 hashTree 元素后必须有 `<hashTree/>`，所有属性必须完整），且会静默丢弃不符合规范的元素。建议通过 JMeter GUI 创建基础结构后再手工微调。

2. **JMeter 变量体系要区分清楚**：`${VAR}` = 线程局部变量（User Defined Variables / Regex Extractor），`${__P(PROP)}` = 全局属性（JSR223 `props.put()` 写入）。

3. **Seata + Druid SQL 解析器兼容性**：避免在 INSERT/UPDATE SQL 中使用 `NOW()` 等函数与 `#{}` 参数混合，尽量全部使用参数占位符，由 Java 代码传值。

4. **Flyway 迁移不可手工操作**：一旦手工修改了数据库或迁移文件，必须同步更新 Flyway 的 `schema_history` 表。更好的做法是创建新的迁移版本。

5. **Redis 补偿要用 DELETE 而非 DECR 到 0**：Redis String 值为 0 时 key 依然存在，`hasKey()` 返回 true。涉及"是否操作过"的标记 key，补偿时应直接删除。

6. **Vue Router 同组件复用不触发 remount**：`<router-view>` 渲染同一组件但参数不同时，组件实例被复用，`onMounted` 不会再次触发。必须通过 `watch` 监听 `route.params` 变化来重新获取数据。

7. **MyBatis-Plus 自动填充要求统一列名**：项目所有表使用 `gmt_create`/`gmt_modified` 命名，新表必须保持一致，否则 MyBatis-Plus 的 `MetaObjectHandler` 会尝试插入不存在的列。

8. **ES Completion Suggester 仅支持前缀匹配**：这是 FST 数据结构的固有特性，不是缺陷。需要中缀匹配应使用 Edge NGram 分词器或其他方案。

9. **双 ID 体系必须做好映射**：秒杀模块存在两套 ID——对外使用 `pms_spu.id`（商品主键），对内使用 `seckill_spu.id`（秒杀表自增主键）。所有涉及 `seckill_sku` 查询的方法都需要先做 ID 映射，否则会出现"查A商品返回B商品SKU"或"NaN价格"的问题。

## 四-A、秒杀模块双ID架构问题（补充）

### 4.8 NaN 价格 + 商品跳转错误：ID 映射缺失

**现象**：
- Nike Air Max（PMS id=15，seckill id=5）显示 NaN 价格
- 点击 Nike 跳转到 Xiaomi 14 的详情
- 点击 Xiaomi 14（PMS id=5，seckill id=3）显示"商品不存在"
- Redmi K70 Pro（PMS id=20，seckill id=6）显示 NaN 价格

**根因**：秒杀模块内部存在两套 ID 体系——**对外使用 PMS 商品主键**（`pms_spu.id`），**对内使用秒杀表自增主键**（`seckill_spu.id`）。两者在测试数据中恰好有重叠（id=5 既是 Xiaomi 的 PMS id，又是 Nike 的 seckill 内部 id），导致多处查询串联出错。

**ID 对应关系表**：

| 商品 | pms_spu.id (对外) | seckill_spu.id (对内) |
|------|-------------------|----------------------|
| iPhone 15 Pro | 1 | 1 |
| Huawei Mate 60 | 2 | 2 |
| Xiaomi 14 | 5 | 3 |
| iPad Pro | 6 | 4 |
| Nike Air Max | 15 | 5 |
| Redmi K70 Pro | 20 | 6 |

**三个具体错误**：

**错误 1 — `SeckillSpuVO.id` 被 `BeanUtils.copyProperties` 覆盖**：
`SeckillSpuVO` 的 `id` 字段经过 `BeanUtils.copyProperties(standardVO, seckillSpuVO)` 后变成了 PMS 商品主键（如 Nike=15）。这是**正确的设计**——对外统一使用 PMS id。但早期调试时错误地认为这是 bug，尝试用 `setId(seckillSpu.getId())` 覆盖为内部 id，导致 URL 路由和布隆过滤器全部不匹配。

**错误 2 — `isPurchased(pmsSpuId)` 直接用 PMS id 查 SKU**：
```java
private Boolean isPurchased(Long spuId) {
    List<SeckillSku> skus = seckillSkuMapper.findSeckillSkusBySpuId(spuId);
    // spuId = 15 (PMS id), 但 seckill_sku.spu_id 存的是 seckill_spu.id (5)
    // → 查不到任何 SKU → 永远返回 false
}
```
修复：先通过 `seckillSpuMapper.findSeckillSpuById(pmsSpuId)` 获取 seckill_spu 记录，再用 `seckillSpu.getId()` 查 SKU。

**错误 3 — `listSeckillSkus(pmsSpuId)` 直接用 PMS id 查 SKU**：
```java
List<SeckillSku> seckillSkus = seckillSkuMapper.findSeckillSkusBySpuId(pmsSpuId);
// 同样的问题：pmsSpuId=15，但 SKU 表存的是 seckill 内部 id=5
// → 返回空列表 → 前端 selectedSku=null → NaN
```
修复：同样增加 ID 映射步骤。

**为什么 iPhone 和 Huawei 不受影响**：这两个商品的 `pms_spu.id == seckill_spu.id`（都是 1 和 2），恰好一致，掩盖了 bug。

**架构总结**：

```
外部（URL/VO/DTO）: pms_spu.id  (如 Nike=15)
         │
    ┌────▼────────────┐
    │ findSeckillSpuById │  ← WHERE spu_id = #{pmsSpuId}
    └────┬────────────┘
         │
    seckill_spu.id (如 Nike=5)
         │
    ┌────▼──────────────────┐
    │ findSeckillSkusBySpuId │  ← WHERE spu_id = #{seckillSpuId}
    └───────────────────────┘
```

关键原则：**对外用 PMS id，对内需映射**。所有需要查 `seckill_sku` 表的地方（`isPurchased`、`listSeckillSkus`），必须先通过 `seckillSpuMapper.findSeckillSpuById(pmsSpuId)` 获取内部 id，再用内部 id 查询 SKU。
