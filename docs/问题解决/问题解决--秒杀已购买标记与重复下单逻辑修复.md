# 秒杀已购买标记与重复下单逻辑修复 — 问题排查与解决方案

> 日期：2026-08-01
> 涉及模块：mall-seckill、mall-order、mall-common

---

## 一、取消订单后仍然显示"已购买"

**现象**：秒杀商品后取消订单，秒杀专区仍显示"已购买"，无法重新秒杀。

**根因**：三层 bug 叠加导致 Redis key 无法被删除：

1. `OmsOrderServiceImpl.clearSeckillCheck()` 中删除 key 的拼写为 `seckill:reseckill:`，缺少 `mall:` 前缀，与写入/检查的 key `mall:seckill:reseckill:` 不一致。
2. 方法入口处有 `if (!o.getSn().startsWith("SEK")) return;` 守卫，但所有订单 SN 均为 UUID，此条件永远为 true，方法直接返回。
3. 方法缺失闭合括号，编译无法通过。

**修复**：重构整体逻辑，将"下单"和"已购买"两个概念分离：

- **下单锁** `mall:seckill:order:lock:{skuId}:{userId}` — 1 分钟 TTL，`setIfAbsent` 防双击
- **下单标记** `mall:seckill:ordered:{skuId}:{userId}` — 2 小时 TTL，防重复未支付订单
- **购买标记** `mall:seckill:reseckill:{skuId}:{userId}` — 永久，支付后写入，`isPurchased` 检查

改动文件：
- `mall-common/.../PrefixConfiguration.java` — 新增 `SECKILL_ORDER_LOCK_PREFIX`、`SECKILL_ORDERED_PREFIX` 常量
- `mall-seckill/.../SeckillCacheUtils.java` — 新增 `getOrderLockKey()`、`getOrderedKey()` 方法
- `mall-seckill/.../SeckillServiceImpl.java` — `commitSeckill` 下单锁改为 `setIfAbsent` + 1min TTL；新增 ordered key 检查和写入
- `mall-order/.../OmsOrderServiceImpl.java` — 新增 `markSeckillPurchased()`（支付后写入购买标记 + 清除 ordered）、`clearSeckillOrdered()`（取消/删除时清除 ordered + lock）

生命周期：

```
秒杀成功 → SET order:lock(1min) + SET ordered(2h)
取消订单 → DEL ordered + DEL order:lock  → 可重新秒杀
支付成功 → SET reseckill(永久) + DEL ordered → isPurchased=true
删除订单 → DEL ordered + DEL order:lock  → 可重新秒杀
2h不支付 → ordered 自动过期 → 可重新秒杀
```

## 二、下单后未支付就显示"已购买"

**现象**：秒杀下单后，在秒杀专区立刻看到"已购买"，此时尚未支付。

**根因**：第一版修复中 `commitSeckill` 的 `setIfAbsent` 仍写入 `reseckill` key（与 `isPurchased` 检查的是同一个 key），导致下单后立即可被查到。

**修复**：将下单锁 key 前缀改为 `mall:seckill:order:lock:`，与购买标记 `mall:seckill:reseckill:` 完全分离。`isPurchased` 只检查 `reseckill` key，该 key 仅在支付成功后由 `markSeckillPurchased` 写入。

## 三、取消订单后仍无法重新秒杀

**现象**：取消订单后，ordered key 已清除，但下单锁 `order:lock` 仍在 10 分钟 TTL 内，`setIfAbsent` 返回 false 阻止下单。

**根因**：`clearSeckillOrdered` 只删除了 ordered key，未删除下单锁 key。

**修复**：
- `clearSeckillOrdered` 同时删除 ordered key 和 order:lock key
- 下单锁 TTL 从 10 分钟降至 1 分钟（纯防双击，长期限制由 ordered key 负责）

## 四、秒杀错误提示带"发生异常"前缀

**现象**：重复购买时提示 "发生异常:错误信息为:您已经购买过这个商品了,谢谢您的支持"，用户看到"发生异常"以为系统崩溃。

**根因**：`SeckillController` 的 `@SentinelResource` 配置了 fallback，所有异常（包括业务异常 `CoolSharkServiceException`）都会路由到 `SeckillFallback.seckillFallback()`，该方法硬编码了 `"发生异常:错误信息为:" + e.getMessage()` 前缀。

**修复**：`SeckillFallback.java` — 直接透传 `e.getMessage()`，空消息时兜底为"秒杀服务繁忙，请稍后再试"。

## 五、MQ 消费者重复插入 success 表报错

**现象**：取消订单后重买同一商品，`SeckillQueueConsumer` 报 `Duplicate entry 'X-1' for key 'success.uk_sku_user'`，MQ 消息重试耗尽后丢失。

**根因**：`success` 表有唯一约束 `uk_sku_user(user_id, sku_id)`，取消重买时旧记录未删除，普通 `INSERT` 冲突。

**修复**：`SuccessMapper.xml` — `INSERT INTO` 改为 `REPLACE INTO`。MySQL 的 REPLACE 在命中唯一约束时自动删旧插新，避免 Duplicate entry。

---

## 六、oms_cart 表 saveCart 潜在风险

**现象**：无实际报错（方法未被调用），但 `saveCart` XML 为裸 INSERT，`oms_cart` 表有唯一约束 `uk_user_sku(user_id, sku_id)`，将来若被调用会触发同类问题。

**修复**：`OmsCartMapper.xml` — `INSERT INTO` 改为 `REPLACE INTO`，预防性修复。

## 部署注意事项

1. 部署前清理 Redis 中的残留 key：`mall:seckill:reseckill:*`、`mall:seckill:order:lock:*`、`mall:seckill:ordered:*`
2. 清理数据库 `cs_mall_seckill.success` 和 `cs_mall_seckill.seckill_message_retry` 表中测试残留数据
3. 需重启的服务：**mall-seckill-webapi**、**mall-order-webapi**
4. `mall-common` 新增了常量，所有依赖它的模块需重新编译
