## 一、这一类问题的共性（★ 最值钱）

**压测的目标是"量出被测系统的承载与降级点"，但在这条测量链上有 5 个可能"替被测系统回答"的角色**：

```
         ①干扰项            ②被测系统            ③替身          ④客户端
    ┌──────────────┐   ┌──────────────┐   ┌────────────┐   ┌────────────┐
    │ 入口限流      │   │ 真正的并发闸门│   │ mock LLM   │   │ 压测脚本   │
    │ 每用户频控    │ → │ /线程池/连接池│ ← │(局部替身)  │ → │(本机/另一台)│
    │ 预算墙        │   └──────────────┘   └────────────┘   └────────────┘
    └──────────────┘            ↑                ↑                ↑
        "它先拦住了"        "它才是答案"      "它自己慢了"      "它自己打不动"
```

**三条可直接复用的方法论**：

1. **先证伪干扰项，再测承载**：入口限流 / 每用户频控 / 预算墙**都会先于承载上限生效**，而且它们的失败**长得像成功**（HTTP 200 + 业务错误体）。不先把它们"关掉或绕开"，你量到的是**限流器的能力**，不是系统的能力。
2. **替身（mock）与客户端都要自证**：mock 必须**先单独压**并给出 P50/P99 与吞吐（证明它不是瓶颈）；客户端也必须证明自己没饱和（CPU/负载）。**否则你量到的是工具的性能**。
3. **"失败"必须可分类**：干扰项的失败（被限流 / 被频控 / 被预算拦）**必须与被测系统的降级分开计数**；分不开就等于没测。

**一句话**：**压测的产出不是 RPS，而是"我凭什么相信这个 RPS"。**

## 二、问题 1：**测之前，被测系统就有一个 50% 的缺陷**（串行看不见）

**现象**：20 并发 × 20s，**硬失败 32/64 = 50.0%**、成功率 60.49%；而同样代码**串行 20/20 全 200**。失败请求是 **HTTP 500**，且**根本没到业务逻辑**（mock 侧计数不涨、闸门占用为 0）。

**排查**：
1. 服务端日志：`org.springframework.security.access.AccessDeniedException: Access Denied` + `Unable to handle the Spring Security Exception because the response is already committed`。
2. 关键反直觉点：**成功的请求也会打这条 ERROR** ⇒ 说明它**每次都在抛**，只是"响应是否已提交"的**时序**决定客户端看到 200 还是 500。
3. 读码定位：`/ai/chat/stream` 返回 `StreamingResponseBody`（异步），业务在异步线程写完后会触发一次 **ASYNC 二次派发**；`authorizeHttpRequests(...).anyRequest().authenticated()` 在 Spring Security 6 默认对**所有 dispatcher type** 生效，而那一刻容器线程上**已无认证对象** → 拒绝。

**根因**：**授权规则把"内部再派发"当成"新请求"又鉴权了一次**。文件里原本已有一条针对性的尝试（`MODE_INHERITABLETHREADLOCAL`），但它**无效**——ASYNC 派发用的是**容器线程池里的另一个线程**，不是"当前线程的子线程"。

**修复**：授权规则**最前面**放行内部派发：
```java
.dispatcherTypeMatchers(DispatcherType.ASYNC, DispatcherType.ERROR).permitAll()
```
🔴 **只放行 ERROR 不够**（旧记录只猜到 ERROR 那一半）——两种派发都要放行。安全性：ASYNC/ERROR 是**已通过鉴权请求的内部再派发**，外部客户端**无法伪装**成这两种 dispatcher type 进来；首次 REQUEST 派发仍然要求登录。

**验证（同条件对照）**：硬失败 **50.0% → 0**、成功率 **60.49% → 100%**、100 并发 **0 失败**。
**⚠️ 附带的反直觉**：修完后 **RPS 反而从 12.9 掉到 7.5**、p50 从 1787ms 升到 2210ms —— 因为修复前**一半请求在安全过滤器被秒拒（~130ms）**，把 RPS 抬高、延迟拉低。**"数字变好看了"恰恰要警惕。**

**可复用判据**：**串行正常、并发炸** ⇒ 优先怀疑**竞态/时序**，而不是容量；**失败请求没进业务逻辑** ⇒ 先看**框架层拦截**（安全/限流/序列化），不要先去查数据库或下游。

## 三、问题 2：**替身只读 `Content-Length`，遇到 chunked 请求体就"看不见"**

**现象**：mock 侧出现一条**空请求体**（`rawlen=0`、`json_ok=False`）→ 判定为"普通任务"→ 回纯文本 → 应用 `JSON.parseObject` 抛 `fastjson.JSONException` ⇒ **每次对话都产生一个假 500**（SSE 里是 `event:error`）。**压测会把这类假失败算成系统降级。**

**排查**：给 mock 加"请求摘要"日志（`clen / te / rawlen / json_ok`）后一次跑就现形：
```
[body] clen=None te=chunked rawlen=0 json_ok=False      ← 修复前
[body] clen=None te=chunked rawlen=854 json_ok=True     ← 修复后
```

**根因**：应用的 `chatJson`（JSON 结构化任务）用 **`Transfer-Encoding: chunked`** 发送（**没有 `Content-Length`**），而 mock 只按 `Content-Length` 读 ⇒ 读到 0 字节。

**修复**：mock 实现 **chunked 请求体解析**（读块长 → 读块 → 直到 0 块）。

**可复用判据**：**"存在"与"不存在"不能靠单一字段判断** —— 读请求体要看 `Content-Length` **和** `Transfer-Encoding`；只认其中一个，就会把"有内容"读成"没内容"，而且**错得毫无征兆**（业务侧只看到"下游返回了不合规的响应"）。

## 四、问题 3：**替身自己成为瓶颈（accept 队列默认只有 5）**

**现象**：mock 自压（100 并发 × 10s）出现 **17 次失败**；单独降档到 50 并发只有 2 次。

**排查**：mock 是 `ThreadingHTTPServer`（已线程化），CPU 只占 0.4% ⇒ 不是算力问题。查 `socketserver.TCPServer.request_queue_size` → **默认只有 5** ⇒ 100 条连接同时进来时，**accept 队列溢出丢连接**。

**修复**：自定义 `MockServer(ThreadingHTTPServer)` 并设 `request_queue_size = 512`；复测 20/50/100/150 并发 **0 失败**，**峰值并发 = 150**（证明确实并发）、吞吐 **306 req/s**。

**可复用判据**：**"线程化了"不等于"能扛并发"** —— 线程模型之外还有 **accept 队列**、文件描述符、端口；**先单独压替身**这一步，正是为了把这些"工具自身的容量"提前摘出去。

## 五、问题 4：**流结束的语义搞错 → 客户端挂到读超时**

**现象**：若 mock 发完 `data: [DONE]` 后保持 `keep-alive` 什么都不做，Java 客户端会**一直阻塞**到读超时（表现为请求超长、像"系统很慢"）。

**排查**：读客户端解析循环（`openSseStream`）：`[DONE]` 那一行是 **`continue`，不是 `break`** ⇒ **流结束靠的是连接 EOF**，不是一个结束标记。

**修复**：mock 用 **chunked 编码**显式写结束块 `0\r\n\r\n` **终结响应体**（而不是"发完 [DONE] 就傻等"）。

**可复用判据**：**协议里的"结束标记"不等于"流结束"** —— 做替身/代理/桩时，结束语义要**照抄客户端代码**，不能照抄"文档看起来应该是这样"。

## 六、问题 5：**旁路记账把被测系统的闸门提前关掉（预算墙）**

**现象**：逻辑上"压的是 mock、不花钱"，但**跑到一半之后每个请求都返回"服务繁忙"** —— 看起来像"并发闸门满了"，实际是**日预算被打满**。

**排查**：应用把每次 LLM 调用的 `usage` **都记账**（mock 返回的 usage 也照记）：单价 **1 元/百万（入）+ 2 元/百万（出）**、预算 **2 元/天**、每次调用约 **0.00011 元** ⇒ **约 5000 次调用就打满**；而 100 并发 × 45s 一档就有 ~4500 次调用。

**修复**：让 mock 回 **0 token**（`--prompt-tokens 0 --completion-tokens 0`）⇒ **零记账、零污染、无需放宽预算**（比"临时把预算调大"更干净：不碰安全限额、不用善后）。
> 🔴 而且**"预算超限"与"闸门满"用的是同一句文案**（见问题 6），所以一旦撞上预算，**事后无法分辨**。

**可复用判据**：**替身要"全真"，但记账类副作用要"归零"** —— 流格式、工具调用要尽量像真的；**计费、审计、告警这类副作用必须显式切断**，否则你压的不是性能，是额度。

## 七、问题 6：**两种完全不同的降级，客户端拿到同一句话**

**现象**：脚本按 body 文案分类，结果 `闸门满` 一栏始终是 **0**，而 `其它降级` 高达 **1701 次** —— 但服务端日志明明有上千条 `【AI并发闸门】…当前并发 20/20，已拒绝本次调用`。

**排查**：对流式接口，**闸门满**时服务端 `catch` 写回的是**通用文案** `AI 服务暂时不可用，请稍后重试。`，与"真异常"**完全同一句** ⇒ 客户端**原理上分不开**。
（另一侧：入口限流返回的是 **HTTP 200 + SSE `event:error`**，**不是 429** —— 只看 HTTP 码会把它算成"成功"。）

**修复**：① 判"闸门满"**回看服务端日志**（`grep '【AI并发闸门】'`）；② 脚本在汇总里**醒目提示这一点**，并**明确不把不确定的东西归到 `busy`**（宁可报成 `degraded` + 提示去查，也不"猜一个好看的数字"）。

**可复用判据**：**先确认"失败能不能被分类"，再谈失败率** —— 分不开的失败率是个伪指标；**不要为了让报表好看而猜分类**。

## 八、问题 7：**"总 RPS"被毫秒级的快速失败抬高**

**现象**：agent 链路 100 并发 **总 RPS 53.6**，看起来比 20 并发（20.7）强得多；但**成功只有 ~18/s**（65% 的请求是闸门**毫秒级拒绝**）。

**根因**：被限流/被闸门拒的请求**返回极快** ⇒ 它们把"总请求数/耗时"抬得很高，**总 RPS 变成了"失败得有多快"**。

**修复**：脚本新增 **`成功 RPS` = 成功数 / 耗时**，并排打印；**判承载只看成功 RPS**。

**可复用判据**：**任何"吞吐"都要问一句"分子是什么"** —— 混入快速失败的吞吐会把"系统更早拒绝"误读成"系统更能扛"。

## 九、问题 8：**干扰项的算术没算清 → 用户池建小了**

**现象**：按方案准备"**120** 个用户 token"（"≥ 阶梯峰值"），实际会被**每用户频控**覆盖掉相当一部分请求。

**根因**：**每用户 10 次 / 60s** 的频控决定的是**可持续 RPS 上限**，不是"用户数 ≥ 并发数"：
```
可持续 RPS ≈ N(用户数) × 10 / 60
```
120 用户 ⇒ **仅 20 req/s**；而 100 并发下预期几十 req/s ⇒ 必然撞频控。

**修复**：建 **800** 用户池（≈133 req/s），并把该公式**直接打进脚本启动提示**（低于阈值就提示加大用户数）。

**可复用判据**：**干扰项要"算"，不能"估"** —— 把每个限额换算成**对你要测的那个量的约束**（这里是 RPS），再倒推资源；"看起来够"通常不够。

## 跨问题共性认知与踩坑清单

| # | 认知 | 落地做法 |
|---|---|---|
| 1 | **"数字变好看"是危险信号** | 修 #62 后 RPS 反而下降 —— 因为旧数字里混着**被秒拒的请求**。**变化方向 ≠ 改善方向，要看分子** |
| 2 | **失败请求"没进业务逻辑"是最强的分流线索** | 立刻查框架层（安全/限流/序列化/线程池），别去查数据库与下游 |
| 3 | **替身的日志是证据，不是噪声** | 给 mock 加**请求摘要**（`clen/te/rawlen/json_ok`）与**并发计数**（`active/peak`）—— 问题 2/3 都是靠它们定位的 |
| 4 | **"先单独压工具"是硬性步骤** | 顺序固定：**压 mock → 证明不是瓶颈 → 再压服务端**；客户端同理（CPU/负载取证） |
| 5 | **服务端日志与客户端分类要交叉印证** | 客户端分不开的（问题 6），服务端日志能分开；两者不一致时**以能解释现象的那个为准**，并当场改判据 |
| 6 | **把"不确定"显式暴露，而不是塞进某一类** | 脚本宁可输出"其它降级 + 提示去查服务端"，也不"猜一个 busy" |

## 面试综述话术

> "我做 AI 并发压测时，第一步不是加压，而是**先证明我量到的是被测系统**。
> 这条测量链上有四个角色可能替我回答：**干扰项**（入口限流 5 QPS、每用户频控 10 次/60s、2 元/天预算墙）、**被测系统**、**替身**（内网 mock LLM）、**客户端**。我逐个证伪：入口限流用 Nacos 热改临时放开、预算让 mock 回 **0 token** 彻底不记账、频控按 **N × 10 / 60** 算出需要 **800** 个用户（方案里写的 120 只够 20 req/s）；mock 先**单独压**（0 失败、峰值并发 150、306 req/s），客户端也取 CPU/负载证据（另一台机 load 0.27）。
> 过程中确实抓到两个'测量工具自己说谎'的例子：mock 只按 `Content-Length` 读请求体，而应用用 **chunked** 发送 ⇒ 读到空体、误判任务、**每次对话产生一个假 500**；以及 `ThreadingHTTPServer` 的 **accept 队列默认只有 5**，100 并发实测丢 17 个连接 —— 这两个只有'先单独压 mock'才会暴露。
> 更值钱的是，这轮压测**挖出了一个生产缺陷**：`/ai/chat/stream` **并发下 50% 请求 500**，而**串行 20/20 全 200**。根因是 `StreamingResponseBody` 的 **ASYNC 二次派发**丢了认证、被授权规则拒（老记录只猜到 ERROR 那一半，**只放 ERROR 不够**）；修完同条件对比：硬失败 **50% → 0**。
> 最后我给自己立了两条读数规矩：**判承载只看'成功 RPS'**（总 RPS 会被毫秒级的快速失败抬高 —— 我实测总 53.6 而成功只有 ~18）；**分不开类的失败率不认**（闸门满与真异常共用同一句文案时，我去看服务端日志，而不是猜一个好看的数字）。"
