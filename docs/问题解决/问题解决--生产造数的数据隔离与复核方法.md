## 一、这一类问题的共性（★ 先看这张表，比逐个看个案更重要）

| 维度 | 共性 | 本项目实例 |
|---|---|---|
| **本质** | 造数 = **在生产上做一次"可回滚的写入实验"**，不是"跑个脚本插数据" | 影子登记表 / 快照 / 精确删 |
| **第一铁律：可逆** | 必须有一份**唯一的清理依据**（登记表），**不能靠"猜哪些是假的"** | `cs_mall_sim.sim_batch` / `sim_entity`；只靠用户名前缀**不够** |
| **第二铁律：可证** | 校验必须覆盖 **"没登记的表"** —— 漏登记 = 漏回填 = **校验却打印通过** | G7：`oms_order_item` 3 行漏标，`verify_backfill()` 仍报 ✅ |

> 💡 **一句话记忆**：**造数的产出不是"数据"，而是"数据 + 一份能把它清干净的台账 + 一套能证明它对了的校验"。**

## 二、问题 1：数据隔离 —— 为什么"用户名前缀"这条防线不够

### 初稿只有"用户名前缀"，实测判定不够（三个反例）

| # | 反例 | 后果 |
|---|---|---|
| 1 | **清理 SQL 顺序错误**：先删用户 → **订单删不掉** | 残留脏数据 |
| 2 | **不可逆污染**：`pms_spu.sales`、库存被改写 | 无法还原（累加型字段**算不回去**） |
| 3 | **Redis 清理想按 pattern 全删** → **误伤真实数据** | 把真实用户的秒杀 key 一起删了 |

### 定稿设计（三层兜底）

1. **影子登记表（唯一清理依据）**：`cs_mall_sim.sim_batch`（批次）+ `sim_entity`（实体）→ 清理 = **逆序 + 分批 + 幂等 + dry-run**。
2. **快照回滚兜底**：不可逆字段不硬算，整库快照还原（实测 MySQL 数据目录**仅 207M** → **全量 6 库快照成本极低**）。
3. **Redis 按 id 精确删**（按登记 user id 删 `reseckill` / `ordered` / `orderLock`）—— ✅ **已实现（2026-09-12）**：#67 ⑤ Redis 精确清理已完成并验证（按坐标精确删 + 复核 0 差异）。（原文：~~当前只打印告警，删除代码尚未写入~~）

### 数据标识：从"借用字段"改成**专用列**（2026-09-11 用户拍板）

> 决策原话："**我认为还是增加专用字段比较好，避免歧义**" + "加之后要考虑 flyway 的情况哦，避免报错"。

- **9 张表各加 `data_source VARCHAR(16) NULL`**（`NULL` = 常规；`SIM` = 模拟造数）；语义是**契约而非借用**，等值可查、**可索引**、零副作用、可扩展（`SIM`/`LOADTEST`/`REPLAY` = 数据血缘）。
- **回填矩阵（按"谁写的"分两类，这是关键设计）**：

| 写入方 | 表 | 回填依据 |
|---|---|---|
| **脚本直接写**（4 张） | `ums_user` / `ums_cart` / `oms_order` / `oms_order_item` 等 | 按 **PK `id`**（登记表里有） |
| **服务端写**（5 张） | `ums_login_log` / `oms_payment_record` / `success` / `seckill_message_retry` / `res_upload_record` | 按 **`user_id`** 兜底（**脚本拿不到它们的 PK**，因为它们由 App 插入） |
| **子表** | `oms_order_item` | 按**父订单 `order_id`**（`BACKFILL_BY_ORDER`）→ **即便漏登记也能标上** |

### 实测验收（5 次真跑，最后一次全绿）

- 最后一次：**浏览 38 / 加购 8 / 下单 4（已支付 4，支付失败 0）/ 失败 0**；**60 行**被标记；`✅ 回填校验通过`；**6 项漏标检查全 0**；
- **清理演练精确删 56 行** —— 其中包含 **3 条"未登记"的订单项**，靠 `order_child` 模式照样删掉；空批次幂等收尾。

## 三、问题 2：造数要加列 → 必然撞上 Flyway 的三个坑

> 加 `data_source` 列必须走**迁移**（而不是手工 ALTER），因为"**回写仓库**"是纪律。于是撞上三个坑，**每一个都会让应用起不来或静默不生效**：

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| **1** | **手工 `ALTER` + 迁移并存** | 迁移执行时 `Duplicate column name 'data_source'` → **Flyway 失败 → 应用启动失败** | 二者只能选一个；**以迁移为准**（手工改过的库要先补 `flyway_schema_history` 或干脆只用迁移） |
| **2** | 🔴 **`docker restart` 对新迁移是空操作** | 迁移 SQL **在 jar 里**，而 jar 是 `COPY` 进镜像的（`/data/csmall/dockerfiles/mall-*.Dockerfile`，构建上下文 `/data/csmall/jars/`）→ 重启容器**不会**带来新迁移 | **重新打包 → `docker compose build` → `up -d`**（本项目实测：镜像内 `app.jar` 字节数与新 jar 逐一相符才算真上线） |
| **3** | **"顺手规范化"已应用迁移的行尾** | Flyway **按文件字节算 checksum** → 字节一变 = `Migration checksum mismatch` → **服务起不来** | **绝不改已应用迁移文件的行尾**（实测本仓库 `core.autocrlf=true` 且无 `*.sql` 的 `.gitattributes` → 18 个迁移里 **17 个 `w/lf`、1 个 `w/crlf`**（`V6__add_order_type_to_oms_order.sql`）） |

**判定"迁移到底跑了没"的正确判据**（比"容器 running"强得多）：

1. `flyway_schema_history` 里出现新版本号且 **`success=1`**；
2. 日志里 `Migrating schema … to version "…"` + `Successfully applied 1 migration`；
3. **最后核库**：`information_schema` 里列存在、类型与可空性对（本次 9 张表 `data_source` 全部 `varchar(16) nullable=YES`，**总数 = 9**）。

> ⚠️ **还有一个"假故障"陷阱**：Flyway **依赖 DataSource**，要等日志出现 `HikariPool-1 - Starting...` **之后**才跑；而这 4 个服务启动要 **106.5s ~ 176.5s**（实测 `Started …Application in`：ums 151.9 / order 170.3 / seckill 176.5 / resource 106.5 秒）。**我第一次复核就在启动 2.5 分钟时误判为"迁移没执行 / 疑似崩溃"** —— 判据必须是**日志里的 `Started …Application in`**，不是固定等待时间。

### 因此新增的三道防线（都在脚本里）

1. **`SERVER_REGEX` + `validate_local()`**：把服务端 **7 条真实正则**抄进脚本，`preflight()` 第一步就**一次性验完全部字段**（不碰网络、不碰数据）→ 把"跑一次撞一个"变成"**预检一次全暴露**"。
2. **号段碰撞预检（preflight 第 8 项）**：按计划生成的手机号 / 用户名**逐条 `IN` 查询** `ums_user`，占用即 fail-fast 并提示空闲段 → **不再靠"撞上才知道"**。
3. **禁止手抄正则**（G3 的教训）：脚本注释里写明"**机器比对法**"（从 Java 源抽字面量逐条 diff；**服务端改校验后必须重跑**）。

### 顺带读码确认的 3 件事（都决定"会不会白跑一轮"）

- ✅ **注册接口确实返回用户 id**：`UserController.java:59` → `JsonResult.ok(new RegisterUserVO(...))` → 脚本能拿到 id 做登记；
- ✅ **`@Idempotent` 不会让不同用户互顶**：`IdempotentAspect.java:69` → `idempotent:%s:%s:%s`（`key` / `userId` / `argsDigest`）—— **含 userId**；`contactName` 仍随机以保证 `argsDigest` 变化；
- ✅ **订单项 `data` 不会被服务端解析**：`OmsOrderServiceImpl` 全文无 `data` 字段处理 → 传 `"{}"` 原样落库。

## 五、问题 4：复核方法（F1~**F8**）—— **"怎么判它生效了"本身就是个坑**

> 这一节是 2026-09-11 复核 4 个服务 + 8 个服务时**实战争出来的**，不遵守会误判（我每条都踩过）。

| # | 坑 | 正确做法 |
|---|---|---|
| **F1** | **别按固定等待时间猜"生效了没有"** | 这 4 个服务**启动要 2~3 分钟**（ums 151.9s / order 170.3s / seckill 176.5s / resource 106.5s），且 **Flyway 依赖 DataSource，要等 `HikariPool-1 - Starting...` 之后才跑**。<br>👉 **判据 = 日志出现 `Started …Application in`**；否则会看到"容器 running 但日志为空"的**假故障** |
| **F2** | **Nacos/Dubbo 报错不要当成自己改坏了** | `Server check fail … port 9848`、`Failed register interface application mapping … error code: 5-10` 是**既有环境噪声**。<br>👉 **做对照实验**：拿**本次没重建**的服务比 —— 实测未动的 `csmall-product` 有 **7 条** Dubbo 报错 + 126 行栈、`csmall-front` 134 行栈，**比重建的 4 个服务更多** |
| **F3** | **别用 `grep 'Caused by'` 数异常** | 会命中提示语里的 "This may be **caused by** configuration server disconnected" → 计数虚高（我靠它得出过错误的"异常链 7~9 条"）。<br>👉 用**异常类型指纹** `grep -oE '[a-zA-Z][a-zA-Z0-9._]*\.(Exception\|Error)' \| sort -u`，并与未动服务**逐类比对有没有新面孔** |
| **F4** | 🔴 **别一次 recreate 一大片 —— 会"启动踩踏"** | 8 个服务**同时** `--force-recreate`：启动 **221~319 秒**（resource 221 / gateway 223 / search 297 / ams 297 / front 307 / ums 309 / ai 311 / product 319），而只重建 **4 个**时是 **107~176 秒** → **慢 2~3 倍**；`load average` 峰值 **7.45**（4 核）。<br>👉 **分批（2~3 个一批）**，并且**等 `Started` 出现再判定** |
| **F5** | 🔴 **别用"应用名模式"判断服务起没起 —— 网关的主类名不一样** | 我误报过"`csmall-gateway` 13 分钟还没起来"，实际它 **223 秒就起来了**：日志行是 `c.c.mall.gateway.MallGatewayWebApi - Started MallGatewayWebApi in 223.421 seconds` —— 主类叫 **`MallGatewayWebApi`**，我的 grep 模式 `Started Mall[A-Za-z]*Application` 匹配不到。<br>👉 判据要**多模式**（`Started .*Application in` / `Started .*WebApi in` / `Netty started on port` / `Tomcat started on port`），或**外部探活交叉验证** |

> ✅ **当晚复核实录（4 项全绿）**：镜像重建于 19:05、镜像内 `app.jar` **字节数与新 jar 逐一相符**；`flyway_schema_history` 出现 **V3/V7/V6/V2（success=1）**；Flyway 日志 `Migrating schema … ` + `Successfully applied 1 migration`；**9 张表 `data_source` 全部就位**；4 条网关路由冒烟全 **200**。

## 六、跨问题的共性认知与踩坑清单

1. **造数第一原则是"可逆"**：登记表是**唯一**清理依据；**前缀/命名约定只是辅助**（G4 就是被命名约定坑的：号段被别人占了）。
2. **第二原则是"可证"，而且校验要覆盖"没登记的东西"**：G7 的**校验盲点**比 bug 本身更值得记 —— `verify_backfill()` 只校验登记表里出现过的表，于是"漏标"被打印成了 ✅。
3. **预检 > 重试**：把服务端校验**抄进脚本** + **机器比对**（G3），能把"跑一次撞一个"变成"预检一次全暴露"。
4. ⚠️ **本项目鉴权/业务失败也返回 HTTP 200**（`401/429/409` 都在 body 的 `state` 里）—— G5 的误判就是这个原因；**任何"看 HTTP 200 就以为成功"的冒烟都会骗你**。
5. ⭐ **"可证"里最贵的一课：校验自己也会骗你**（G7 + F6/F7/F8 = 四连，**全是判定方式错、不是数据错**）—— ① 校验范围只覆盖"登记过的表" → 漏标却报 ✅；② **分母取全局** → 多批次必误报；③ **分子取登记条数** → 业务删除被算成漏标；④ **回填有时点** → 之后新增的行天然无标识。⇒ **"造完数"的最后一步永远是用独立口径再核一遍**（本项目落地为 `--verify --batch` + 一份独立复核脚本），而**"报告说通过"不等于"真的通过"**。
5. **"我的验证方法"必须有对照物**：未改动服务的报错量（F2）、客户端成功率（Agent 那条 18/18）、确定性实验（`_analyze`）—— 否则"看起来有问题"和"确实有问题"分不开。
6. **判"服务起来了"用日志判据 + 外部探活**，不用固定 sleep，也不用单一 grep 模式（F1/F5）。
7. **造数不只是造数据，它是一次"全链路体检"**：G8（库存扣减 MQ 链路整体失效，付了钱不扣库存）就是这样被发现的 —— **但按"不夹带"纪律，发现即登记（#65），不在造数这次变更里顺手改**。
8. **我自己犯的错也记进文档**：手抄正则（G3）、`grep -c` 数单行 JSON（#63 验收）、误把 Sentinel 的 URL 覆盖当"无需登录"（G5）—— **方法论层面的错误，写出来比藏起来有价值**。

## 七、面试综述话术（贯穿本类，可直接用）

> "往生产库造数据这件事，我的两条铁律是**可逆**和**可证**。
> **可逆**：我一开始以为用户名加个前缀就够了，实测发现不够 —— 清理 SQL 顺序错了会导致订单删不掉，`sales` 和库存这类**累加型字段根本算不回去**，Redis 按 pattern 删还会**误伤真实数据**。所以最后做成**影子登记表**（`sim_batch`/`sim_entity` 是唯一清理依据）+ **快照回滚**兜底 + Redis 按 id 精确删，清理用**逆序 + 分批 + 幂等 + dry-run**；数据标识也从'借用字段'改成**专用列** `data_source`，并设计了**按'谁写的'分类的回填矩阵** —— 脚本写的按主键、服务端写的（比如支付记录、登录日志）只能按 `user_id` 兜底。
> **可证**：校验必须覆盖**没登记的表**，因为我就栽在这儿 —— 有一次订单子表漏标了 3 行，校验却打印了'✅ 通过'，因为它只校验登记表里出现过的表；根因还是个经典陷阱：**参数里的 SELECT 先开启了脚本事务，把 REPEATABLE READ 快照定格在了'App 还没建订单'的时刻**。**正式造数（1000 行为）又抓出同一族的三个变体**：校验的**分母取全局**（多批次共存必误报 11 条）、**分子取登记条数**（业务删除被算成漏标）、**回填有时点**（之后新增的行天然无标识）—— **四次全是"判定方式"错，不是"数据"错**。
> 过程中还有两件收获：一是**把服务端校验抄进脚本 + 机器比对**，因为手抄正则真的会错（我把手机号抄成了 12 位）；二是造数顺带做了一次**全链路体检** —— 发现'支付成功但库存一点没减'，追下去是 MQ 消费端类型不匹配导致消息进了死信又二次失败，**按纪律只登记不改**。"
