## 一、原始结论（2026-08-01，错误）

`docs/问题解决/问题解决--管理员登录BCrypt兼容性.md` 记录：
> 现象：admin 登录"用户名密码错误"，密码 123456，本地 Windows 正常
> 归因：Windows JDK 生成的 `$2a` 哈希与 Debian JDK 21 BCrypt 实现不兼容（依赖 JDK 安全 Provider）
> 修复：服务器 python 生成 `$2b` 哈希写库 → 能登录

---

## 二、质疑点（2026-09-03，面试准备复核时）

1. **逻辑漏洞**：Spring Security BCrypt 是纯 Java 自实现（自带 Blowfish）→ 同一 jar 跨平台结果**必然一致**，"Provider 不兼容"无技术依据
2. **自相矛盾**：文档用"$2b 修复 null 字节 bug"解释 123456 的失败——但 123456 无 null 字节
3. **现象矛盾**：登录报"用户名密码错误"（认证失败）vs 排查到数据源连接 refused（500）——两个不同错误被混在一次排查
4. **最大疑点**：从没验证"旧哈希是不是真的对 123456 算的"

---

## 三、验证过程（社区查证 + 服务器实验）

### 1. 社区查证
- patrickfav/bcrypt README、Spring Security issue #10150、StackOverflow $2a/$2b 讨论：
  - $2a/$2b 差异只在边界（null 字节/超长密码），对 ASCII 普通密码**无差异**，$2a 可被 $2b 向后兼容验证
  - 纯 Java BCrypt 同 jar 跨平台一致；"跨平台 Provider 不兼容"无社区案例

### 2. 服务器实验（宿主机 python bcrypt 3.2.2 纯算法，零影响只读）
| 实验 | 结果 | 含义 |
|------|------|------|
| 旧 `$2a$10$N.zmdr...` checkpw("123456") | **False** | 旧哈希根本不是 123456 算的 |
| "123456" 新生成 `$2a` 自洽 | True | 实现正常，无跨平台问题 |
| 当前库 admin `$2b` checkpw("123456") | **False** | 修复后密码又变过 |
| liucs/wangkj 同旧哈希 | 三用户同哈希 | 测试数据复制粘贴特征 |

### 3. 追加排除：复制粘贴污染假设（2026-09-03 追问）

**假设**：会不会是"本地生成哈希 → 复制粘贴 → SSH 导入数据库"时多/少复制了一部分，导致哈希损坏？
**判断思路**：若哈希 = "正确哈希 + 污染"，必留下长度/字符/解析痕迹 → 三项检查全部否定即排除。

| 实验 | 结果 | 结论 |
|------|------|------|
| 旧哈希结构检查 | 长度精确 60、全合法 bcrypt 字符、salt(22)+校验(31) 精确 | 污染必留痕 → 无痕 = 非污染 |
| 污染模拟对照（正确哈希 尾部+字符/换行/截断；`$2a$` 被 shell 吃） | 全 False 或抛 Invalid salt | 若真污染，checkpw 行为应不同 |
| 截断反证：旧哈希任意位置截 40~70 字符窗口对 123456 试 | 全不命中 | 若=正确哈希+污染，去污后必有一段命中 → 源头哈希本就不是 123456 |

**结论**：旧哈希直接写死在 `database/init-test-data.sql`（三用户同一串，SQL 文件整体 source 进库）——**非导入链路污染，源头哈希就不是 123456 算的**。"测试数据哈希与声称密码不匹配"的原结论进一步加固。

## 四、真相与证伪结论

```
真实根因:测试数据里的哈希与声称的密码(123456)不匹配
        → 登录失败与 Windows/Debian、$2a/$2b 完全无关
阴差阳错:python 生成 $2b(真正对 123456)写库 → admin 恰好能登
        → 被误记成"跨平台 bug 修好了"
附带发现:liucs/wangkj 仍存旧哈希,若密码声称 123456 同样登不上(TODO #37)
```

## 五、教训（错误归因如何避免）

1. **先验证最基础假设**：排查认证失败第一件事 = `bcrypt.checkpw(声称的密码, 哈希)` 一行——先确认哈希对不对得上密码，再怀疑平台/版本/框架
2. **别给现象编机理**："Provider 不兼容"是编的机理——没有对照实验（同密码不同平台各生成互验）的归因都是猜测
3. **测试数据要验证**：造数据的哈希必须 checkpw 过再入库；手填/复制哈希（三用户同哈希）是雷
4. **错误结论比没结论危险**：错误文档会误导后续所有排查者（本复盘文档之前 10-Q11 也继承了错误归因）
5. **保持自我推翻的能力**：面试/复盘主动质疑自己以前的结论，用实验证伪——这是最硬的工程素养
