# 问题解决 — 消息可靠性与毒消息治理

> **性质**: **一类问题的合集** —— 消息消费者**失败后怎么办**：不丢、不毒、不无限重试
> **覆盖**: 二批 **#36**（订单 requeue 无限重试 → x-death 限次 + DLX 死信）/ 二批 **#14 的 P0 第 3 层**（秒杀消费者落库失败不静默，**同款 x-death 方案**）
> **来源**: 由 [[TODO第二批实现与原理]] §三 与 §4.2 **切割**而来（2026-09-10）
> **关联（仅互链、不合并）**: [[问题解决--RabbitMQ启动]]（安装类问题，与本类不同）、[[问题解决--秒杀]]、[[问题解决--Redis加固与主从数据一致性]]（#14 的库存一致性主体在此）
> **未来可并入本类**: 订单侧**发送确认（publisher confirm）+ 本地消息表**（与秒杀链路对齐）

## 一、这一类问题的共性（★ 先看这张表）

**一句话本质**：**消费者失败时的默认行为是危险的** —— `basicNack(requeue=true)` 会让"毒消息"（永远失败的消息）**无限重试并卡在队头**，阻塞后面所有消息。

### 1.1 本类统一的四步解法（一条可复用的固定套路）

```
① 读 x-death 头判断已重试次数
      ↓
② 未达上限 → basicNack(requeue=true)   （给瞬时故障机会）
      ↓
③ 达上限   → basicNack(requeue=false)  （停止重试）
      ↓
④ 队列声明 DLX → 死信交换机 → 死信队列 → 死信消费者【留痕 + 告警 + 等人工补偿】
```

**为什么不用一刀切的 `requeue=false`**：会**误丢瞬时故障**（Dubbo 抖动 / DB 闪断）的消息，且无感知。
**为什么要读 `x-death`**：RabbitMQ 在每次 requeue 后自动在 header 附加 `x-death`（含 `reason=requeued`、`count`）→ 这是**唯一可靠的"已重试几次"来源**。

### 1.2 ⭐ 核心认知："失败不静默"

比"怎么重试"更重要的是 —— **失败必须留痕，且要区分"能不能自愈"**：

| 失败类型 | 处理 | 实例 |
|---|---|---|
| **可自愈**（瞬时故障）| 限次重试 | Dubbo 抖动、DB 闪断 |
| **不可自愈**（业务性失败）| 立即留痕 + 告警 | 库存永久不足（`rows==0`）、商品下架、消息格式坏 |
| **最危险：已付款却落库失败** | **升级为 ERROR 告警 + 人工介入** | 秒杀：查订单 `state==3`（已支付）→ `【秒杀落库告警】⚠️ 需人工介入` |

> 💡 秒杀那一段的判据很关键：`rows==0` 时先**查订单状态** —— 未支付 → warn（可后续重试）；**已支付 → ERROR 告警**。这把"静默丢弃"变成了"明确人工待办"。

### 1.3 本类暴露出的架构不一致（值得讲）

| 链路 | 发送确认 | 重试机制 | 兜底 |
|---|---|---|---|
| **秒杀** | — | — | ✅ **本地消息表 `seckill_message_retry` + `MessageRetryTask` 每 5s 重发** |
| **订单** | ❌ 无 | ❌ 无 | ❌ 只有 requeue 限次 + DLX 留痕 |

→ **同一项目两条 MQ 链路的可靠性设计不一致（订单弱）**，这是本题最有价值的"发现"而不是"修复"。

### 1.4 共性坑：**Broker 端资源不可变**

MQ 队列/交换机的**参数在创建后不可变** —— 改 DLX/TTL/durable 必须**删队列重建**（详见本文件 §二 问题 1 的 406 报错）。这与"代码可以热更新"是完全不同的心智模型。

## 二、问题 1：#36 MQ requeue 修复 + DLX（含实战 406 问题）

> 原文编号：[[TODO第二批实现与原理]] §三（3.x）


> 详细 MQ 全链路现状分析与阶段规划见本系列配套分析（TODO 第二批讨论记录）。本节记录**已完成的两步**（requeue 修复 + 订单 DLX）与实战踩坑。

### 3.1 问题本质

`OrderQueueConsumer` 失败处理是 `basicNack(deliveryTag, false, true)`——**requeue=true 无限重试**：
- 库存永久不足 / 商品下架 / 消息格式坏 → 每次消费都失败 → **无限 requeue 循环** → 消息永远卡在队列头部，阻塞后续消息 = **毒消息挂单**

### 3.2 修复设计（为什么用 x-death 而不是直接 requeue=false）

**方案对比**：
- ❌ 直接 `requeue=false`：一刀切丢弃——**瞬时故障**（Dubbo 抖动/DB 闪断）也会误丢，订单库存扣减丢失无感知
- ✅ **x-death 限次重试**：RabbitMQ 在每次 requeue 后自动在 header 附加 `x-death`（含 reason=requeued、count=次数）→ 消费前读 count，**前 3 次失败仍 requeue（瞬时故障有机会），第 3 次后 requeue=false（丢弃留痕）**

```java
private static final int MAX_REQUEUE = 3;

public void process(String messageJson, Channel channel,
        @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
        @Header(name = "x-death", required = false) List<Map<String, Object>> xDeath) {
    int requeueCount = countRequeue(xDeath);   // 读 x-death 中 reason=requeued 的 count
    ...
    channel.basicNack(deliveryTag, false, requeueCount < MAX_REQUEUE);
}

private int countRequeue(List<Map<String, Object>> xDeath) {
    // 遍历 x-death：reason=="requeued" 的 count 取最大 = 已重试次数
}
```

### 3.3 疑惑点与原理（面试深挖）

| 疑惑/问题 | 结论 |
|---|---|
| x-death 是什么？ | RabbitMQ 在消息被 requeue/reject/dead-letter 后附加的**投递历史头**，每次 requeue 更新 count；可用于限次重试、死信分析 |
| 为什么不配 Spring retry？ | 订单模块**无 yml listener 配置**且自定义了 `rabbitListenerContainerFactory`（只 setMessageConverter，无 retry advice）——Spring retry 的 `RetryInterceptor` 不在链上，配了也不生效（认知坑：**自定义容器工厂会覆盖 Boot 默认的 retry 装配**）|
| manual ack + retry 能共存吗？ | 秒杀模块配了 manual + retry(max-attempts=3)，但 manual ack 语义下 retry advice 与手动确认交互**存疑（可能双重重试）**——待实测确认（TODO #36 记录）|
| 为什么订单不直接学秒杀配 retry？ | 秒杀有本地消息表（`seckill_message_retry` + `MessageRetryTask` 每 5s 重发）兜底；订单**没有发送确认、没有重试机制**——两条链路可靠性设计不一致（订单弱）|
| requeue 耗尽后消息去哪？ | 当前 requeue=false = **丢弃**（有 ERROR 日志留痕）；企业级应有 **DLX 死信队列**承接 → 记录原因/告警/人工补偿（TODO #36 剩余部分）|

### 3.4 面试话术

"订单库存扣减消费者原本是 `basicNack(requeue=true)`——毒消息会无限重试挂单。我没用一刀切的 requeue=false（会误丢瞬时故障），而是读 RabbitMQ 的 **x-death 头做限次重试**：前 3 次失败保留重试机会，之后 requeue=false 进死信。第二步我补了 **DLX**：order_queue 声明 dead-letter 指向死信交换机，新增 OrderDlxConsumer 记录死信原因 + 告警——形成『限次重试 → 死信留痕 → 人工补偿』的闭环。过程中发现订单模块的可靠性配置是空白的——无发送确认、无 retry（自定义容器工厂绕过了 Boot 默认装配），与秒杀链路（本地消息表 + MessageRetryTask）形成鲜明对比。"

### 3.5 DLX 实现（订单队列死信）

**设计**（Spring AMQP 声明式）：
```java
// OrderQueueConfig —— 业务队列声明死信参数
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable(ORDER_QUEUE)
            .deadLetterExchange(ORDER_DLX_EX)   // order_ex_dlx
            .deadLetterRoutingKey(ORDER_DLX_RK)  // order_dlx_rk
            .build();
}
// + DLX 三件套：order_ex_dlx 交换机、order_queue_dlx 队列(durable)、绑定
```

**死信消费者** `OrderDlxConsumer`（新增）：
- 监听 `order_queue_dlx`，按**原始 String 收消息体**（不反序列化业务类型，兼容不同版本）
- 读 x-death 头提取死信原因 + 输出 `【MQ死信告警】` ERROR 日志（供人工补偿）
- ack 消费防死信堆积；未来可扩展：落库死信表 / 外部告警（TODO #30）

**死信链路闭环**：
```
OrderQueueConsumer 重试 3 次耗尽 → basicNack(requeue=false)
  → RabbitMQ reject → order_queue 声明了 DLX → order_ex_dlx
  → order_queue_dlx → OrderDlxConsumer 记录原因 + 告警
```

### 3.6 实战问题：启动报错 406 PRECONDITION_FAILED（⭐ 本地复现 + 修复）

**现象**：DLX 代码改完后本地启动 mall-order，报：
```
Caused by: ... PRECONDITION_FAILED - inequivalent arg 'x-dead-letter-exchange'
for queue 'order_queue' in vhost '/': received the value 'order_ex_dlx'
of type 'longstr' but current is none
→ Failed to start bean '...RabbitListenerEndpointRegistry' → Application run failed
```

**根因（关键认知）**：**RabbitMQ 队列参数在队列创建后不可变**。
- 本地 RabbitMQ 早已存在旧 `order_queue`（无死信参数，arguments 仅 x-queue-type）
- 新代码声明"同名的、带 x-dead-letter-exchange 的队列" → RabbitMQ 检测参数不匹配 → **406 PRECONDITION_FAILED**
- **Spring AMQP 声明不会更新已存在队列**——它只是发 queue.declare，由 Broker 校验一致性

**修复**：删除旧队列（0 积压零风险）→ 重启应用 → Spring 自动重建带 DLX 的队列。
```bash
# 管理 API 删除（本地 guest/guest）
curl -u guest:guest -X DELETE http://127.0.0.1:15672/api/queues/%2F/order_queue
```

**经验教训（面试可讲）**：
1. **MQ 队列声明是一次性的**——改队列参数（DLX/TTL/durable）必须删队列重建，不像代码可热更新
2. **部署前必查积压**：删队列会丢消息——本项目 order_queue 演示期 0 积压零风险；生产必须先确认积压/先迁移
3. 同理适用于：交换机/绑定参数变更、TTL 调整——**Broker 端资源不可变**是 RabbitMQ 设计约束
4. 本问题在我们自己的代码注释里已预警（"需先删旧队列"），但**本地启动时还是踩了**——预警写进注释 ≠ 执行时记得，最好部署清单化

## 三、问题 2：#14 P0 第 3 层 —— 秒杀消费者落库失败不静默（与 #36 同款 x-death 方案）

> 原文编号：[[TODO第二批实现与原理]] §4.2
> 📎 本题是从 [[问题解决--Redis加固与主从数据一致性]] §三（#14 P0 三层）中**切出的"消费者可靠性"部分**；库存一致性主体仍在那边。


**原问题**：`SeckillQueueConsumer` 库存不足时 `basicAck` **静默丢弃**——用户可能已付款但 success 记录缺失 = 订单悬挂无痕。

**修复**（三兜底，与 #36 同款 x-death 方案）：
1. **失败留痕**：rows==0 时 `log.error【秒杀落库留痕】`（含 skuId/orderSn/quantity/requeue 次数）
2. **已付款告警**：新增 `IOmsOrderService.getOrderStateBySn` Dubbo 查询订单状态，若 `state==3`（已支付）→ `【秒杀落库告警】⚠️ 需人工介入`；否则 warn 可后续重试
3. **限次重试**：读 x-death 头，`basicNack(requeue=false, requeueCount < MAX_REQUEUE=3)`——前 3 次瞬时故障有重试机会，达上限丢弃留痕

```java
if (rows == 0) {
    log.error("【秒杀落库留痕】DB库存扣减失败, skuId={}, 订单号={}, quantity={}, requeue {}/{}", ...);
    Integer state = dubboOrderService.getOrderStateBySn(success.getOrderSn());
    if (state != null && state == 3) { log.error("【秒杀落库告警】⚠️ 已付款订单落库失败，需人工介入！..."); }
    channel.basicNack(deliveryTag, false, requeueCount < MAX_REQUEUE);
    return;
}
```

## 四、问题 3（2026-09-12 新增 · TODO #70）：当"限次重试"本身失效 —— `x-death` 在 classic 队列上不随 requeue 增长

> **一句话**：本类前两个问题靠"**用 `x-death` 计数做限次重试**"治理毒消息；而 2026-09-12 的实测**证伪了这个前提** —— classic 队列下 `basicNack(requeue=true)` **根本不写 `x-death`**，于是"限次"永远到不了上限，**毒消息变成无限重投**。

### 4.1 现象（一天内两次、两种面孔）
- **面孔 A（#65 之前）**：消费者**收不到**消息（类型契约不符 ⇒ `No listener method found ... for class java.util.ArrayList`）⇒ 由 Spring 重试 3 次后**丢进 DLX** ⇒ ⚠️ 当时反而"看起来像限次生效"。
- **面孔 B（#65 修好、业务分支第一次真正跑起来）**：消费者收到了、也执行了，但库存扣减返回 **0 行** ⇒ 走"失败分支" ⇒ **每秒重投一次**：实测 **10 分钟 114 次**、`order_queue` 长期积压 1 条、**`order_queue_dlx` 恒 0（DLX 永远收不到 ⇒ 告警链路形同不存在）**；日志里 `requeue 0/3` **永远是 0/3**。

### 4.2 根因（⚠️ 与 §3.2 的假设相反）

| 写法 | `x-death` 会不会加 | 结果 |
|---|---|---|
| `basicNack(tag, false, **true**)`（requeue） | **不会** —— `x-death` 只在消息**被死信**时写；只有 **quorum 队列**才有 `reason=requeued` | 计数**恒 0** ⇒ `0 < 3` 恒真 ⇒ **永久重投** |
| `basicNack(tag, false, **false**)` / reject / 抛异常 | **会**（消息真正被死信） | 计数才会增长 |

⇒ **§3.2 里"用 `x-death` 做限次"的设计，在 classic 队列 + requeue 这条路径上从一开始就是无效的**。它之所以一直没暴露，是因为**代码根本走不到这条分支**（消息在更上游的环节就挂了）—— ⭐ 这是"**测过 ≠ 覆盖到**"的又一例。

### 4.3 伴随缺陷：`stock > #{quantity}` 的 off-by-one（mall-product）
- `SkuMapper.updateStockById` 的条件是 `where id=#{id} and **stock > #{stock}**`（严格大于）⇒ **买"最后一件"（`stock == quantity`）永远匹配 0 行**。
- **实测**：订单 `41528a60-…`（sku `2084644661212008449`，`stock=1`、quantity=1）⇒ `1 > 1` = false ⇒ 判"扣减失败" ⇒ **一条本该成功的消息就这样变成了永久重投的毒消息**（= 4.1 的面孔 B）。
- **修复**：`>` → **`>=`**（与秒杀侧 `seckill_stock >= #{quantity}` 同口径）。**修复后同一条积压消息立刻成功**：`stock` 1 → 0 · `订单库存扣减完成` +1 · `order_queue` 归零。

### 4.4 修复（可复用）
1. **毒消息一次到位地死信**：`rows == 0`（业务上**永远不可能成功**）⇒ 抛 **`AmqpRejectAndDontRequeueException`** ⇒ 容器 `reject(requeue=false)` ⇒ **进 DLX 并告警**（不要"重试几次再说"）。
2. **瞬时故障交给容器重试**：其它异常**抛出**（不要手动 nack）⇒ `spring.rabbitmq.listener.simple.retry.max-attempts=3` 重试，耗尽后由 `RejectAndDontRequeueRecoverer` reject ⇒ DLX。⚠️ **异常必须抛出去**：吞掉异常 = 容器认为消费成功 ⇒ **静默丢消息**。
3. **ack 模式必须与代码一致**：`acknowledge-mode: manual` + 手动 ack/nack 才配套；否则 **AUTO ack 与手动确认"双确认"**（实测 `channel error 406 PRECONDITION_FAILED unknown delivery tag` —— 与 **§3.6** 那次同源）。
4. **别再依赖 `x-death` 做业务侧限次**（classic 队列）；要精确限次就自己带 `x-retry-count` 头重投，或直接用 quorum / 延迟队列。
5. ⚠️ **配置写在 yml ≠ 生效**：如果模块**自己定义了 `rabbitListenerContainerFactory`**，那么 `spring.rabbitmq.listener.simple.*`（ack 模式 / retry）**完全不生效** —— 必须写在那个 factory 的**代码**里。**实测**：mall-order 写了 `acknowledge-mode: manual`，运行日志仍是 `acknowledgeMode=AUTO`，并因**自动+手动双确认**打出 406；把设置搬进 `OrderQueueConfig#rabbitListenerContainerFactory` 才对。⚠️ **但那里要设的是 `AUTO`，不是 `MANUAL`**：MANUAL 模式下容器**不碰 channel**，监听器抛 `AmqpRejectAndDontRequeueException` **不会**触发 reject ⇒ 消息**永远 unacked**、DLX 收不到（实测：`order_queue` 挂 1 unacked、`order_queue_dlx`=0、告警不响）。**正确组合 = `AUTO`（ack 交容器）+ 监听器完全不碰 channel + `defaultRequeueRejected(false)` + retry advice** —— "抛异常交给容器"这条思路只在 AUTO 下成立，选 MANUAL 就等于把（含"失败也要 reject"的）ack 责任**全部**揽给业务代码，**两半各做一半一定出问题**。**判据**：看运行日志里的 `acknowledgeMode=`，**不要**看消费者的 `ack_required`（AUTO 模式下它同样是 `true` —— 又一个"判据不敏感"）。

### 4.5 面试话术
> "我们早期给 MQ 毒消息做过'限次重试'：失败就 `basicNack(requeue=true)`，从 `x-death` 读重试次数，到 3 次丢死信。**这个设计在 classic 队列上从一开始就是无效的** —— `x-death` 只在消息**真正被死信**时才写，普通 requeue 只是把它放回原队列；它一直没暴露，是因为**代码根本走不到那条分支**。我先修了一个更上游的类型契约缺陷，业务分支第一次真正跑起来，那条消息就开始**每秒重投一次**（10 分钟 114 次），而**死信队列永远是空的**、告警链路形同不存在。更巧的是：触发它的那条消息**本该是成功的** —— 库存扣减 SQL 写的是 `stock > #{quantity}`（严格大于），所以**买最后一件永远失败**，一条正常订单就这么变成了毒消息。现在两件事一起修了：`>` 改 `>=`；失败分支不再自己 nack，而是**毒消息直接 reject 进 DLX**、**瞬时异常交给容器重试 3 次后再进 DLX**，并在**代码里的 listener factory** 上补齐 **AUTO** ack（ack 全交容器、监听器不碰 channel）与限次重试。⚠️ 这里有个我自己踩的坑：我一开始把 `acknowledge-mode: manual` 写进了 `application-prod.yml` —— 但 mall-order **自定义了 listener factory**，**yml 那套是影子配置、压根没生效**（运行日志仍是 AUTO，于是自动+手动双确认打出 406）。所以最后落在代码里：**"配置写在文件里" ≠ "有什么东西在读它"**。"

> **一句话记忆**：**"限次重试生效了" 与 "真在限次" 是两件事** —— 判据要落在**消息是否真的离开了队列**（DLX 有没有东西、队列积压有没有归零），而不是"代码里有那个计数器"。

## 五、跨问题的共性认知与踩坑清单

| 认知 / 坑 | 说明 |
|---|---|
| ⭐ **x-death 是"已重试几次"的唯一可靠来源** | RabbitMQ 自动维护；遍历取 `reason=="requeued"` 的 `count` 最大值 |
| ⭐ **队列参数创建后不可变** | 改 DLX/TTL/durable 必须**删队列重建**。本项目改 DLX 时本地启动报 `406 PRECONDITION_FAILED - inequivalent arg 'x-dead-letter-exchange'` |
| ⚠️ **删队列会丢消息** | 部署前**必查积压**；本项目 order_queue 演示期 0 积压零风险，生产必须先确认/迁移 |
| ⚠️ **自定义容器工厂会绕过 Boot 默认装配** | 订单模块自定义了 `rabbitListenerContainerFactory`（只 setMessageConverter）→ **Spring retry 的 `RetryInterceptor` 不在链上，配了也不生效**（认知坑）|
| ⚠️ **manual ack + retry 交互存疑** | 秒杀配了 manual + `max-attempts=3`，但 manual ack 语义下 retry advice 与手动确认可能**双重重试**（待实测）|
| ⚠️ **预警写进注释 ≠ 执行时记得** | "需先删旧队列"已写在代码注释里，本地启动还是踩了 → **部署清单化**才有效 |
| 🔑 **死信消费者要"按原始 String 收"** | 不反序列化成业务类型，**兼容不同版本的消息体**；ack 消费防死信堆积；未来可扩：落库死信表 / 外部告警（TODO #30）|

## 六、面试综述话术（贯穿本类）

> "MQ 这条线我处理的核心是**消费者失败后的行为**。原来订单消费者是 `basicNack(requeue=true)` —— **无限重试**：库存永久不足、商品下架、消息格式坏这类'毒消息'会永远卡在队头阻塞后面所有消息。我**没有**用一刀切的 `requeue=false`（那会误丢瞬时故障，比如 Dubbo 抖动/DB 闪断，且无感知），而是利用 RabbitMQ 的 **`x-death` 头做限次重试**：它每次 requeue 后自动记录次数，我读它判断 —— **前 3 次失败仍 requeue（给瞬时故障机会），达上限就 `requeue=false` 停止重试**。第二步补了 **DLX 死信**：队列声明死信交换机，新增 `OrderDlxConsumer` 记录死信原因 + 告警 —— 形成『**限次重试 → 死信留痕 → 人工补偿**』的闭环。过程中踩了一个关键坑：**RabbitMQ 队列参数创建后不可变**，改 DLX 必须删队列重建，我本地就报了 `406 PRECONDITION_FAILED`。
>
> 更值得一提的是我在秒杀那条链路上做了**同款但更严的**处理：消费者 `rows==0`（DB 条件扣减失败）时原来直接 `basicAck` **静默丢弃** —— 用户可能已付款但 success 记录缺失，订单悬挂无痕。我改成三兜底：**失败留痕 + 查订单状态（已支付则 ERROR 告警、需人工介入）+ 同款 x-death 限次重试**。这两处合起来让我发现一个**架构不一致**：秒杀有本地消息表 + `MessageRetryTask` 兜底，而**订单侧连发送确认都没有** —— 同一个项目两条 MQ 链路的可靠性设计差了一档，这个'发现'比'修复'更有价值。"
