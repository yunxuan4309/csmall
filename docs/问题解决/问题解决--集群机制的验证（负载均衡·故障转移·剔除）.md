## 二、故障转移演练：切换到底怎么发生的（原 §5.9，逐字迁入） —— ⭐ **本批最有说服力的证据**

**① 一次选主的四个阶段**（实测 6.1s 走完）

| 阶段 | 事件 | 谁在动 | 实测耗时 |
|---|---|---|---|
| 1 | **`+sdown` 主观下线**：单个哨兵发现主库 `PING` 超时 | 任一哨兵 | +0~5s |
| 2 | **`+odown` 客观下线**：达到 `quorum` 的哨兵都认为它挂了 | 多哨兵投票 | **+5.0s**（= `down-after-milliseconds 5000`） |
| 3 | **`+elected-leader`**：基于 Raft 的 leader 选举，选出一个哨兵主持切换 | 哨兵之间 | +5.1s（≈0.06s） |
| 4 | **`+promoted-slave` + `+switch-master`**：leader 提升从库、广播新拓扑 | leader 哨兵 | +6.1s |

**② 时间都花在哪**：**绝大部分是 `down-after-milliseconds 5000`**（必须等够 5s 才能确认主库真死，否则网络抖动就会误切）。真正的选举+提升只用了 **1.1s**。→ 这个值就是"**误判风险 vs 切换速度**"的旋钮：调小切得快但易误切，调大更稳但停机久。

**③ 客户端为什么能自动重连**（这是阶段 3.5 的回报）

Lettuce 的 `ConnectionWatchdog` 在连接断开后：① 按退避策略重连**旧地址**；② 连不上就**重新向哨兵询问主地址**；③ 拿到新地址后直接连新主。实测日志：

```
11:34:01.810 Reconnecting, last destination was 172.29.193.239:6379
11:34:01.841 WARN Cannot reconnect: Connection refused: /172.29.193.239:6379
11:34:10.912 INFO Reconnected to 172.29.193.240:6380      ← 自动切到新主
11:35:59.710 INFO Reconnected to 172.29.193.239:6379      ← 切回老主
```

> **对照**：如果客户端还是 standalone 模式，它会**永远重连那个已死的旧地址**——主从切换对它是"从可用变成不可用"。这就是阶段 3.5 必须做、且必须全部 11 个服务都做的原因。

**④ ⭐ 脑裂窗口 = 10.9s（演练最大的发现）**

老主库 `docker start` 回来后，因为它的 `redis-master.conf` 里**没有 `replicaof`**，它会**按配置自认为主**（实测 `role:master` 持续 10.9s），直到哨兵下发 `+convert-to-slave` 才降级。

- **为什么这么久**：哨兵要等主库恢复被感知（`-sdown`）、再重新纳入拓扑、再下发降级指令。
- **为什么业务没事**：客户端只连**哨兵返回的地址**，不会主动连老地址。
- **为什么仍要防**：万一有客户端/脚本直连老地址，这 10.9s 内它会把数据写进一个**即将被全量覆盖的主库** → 数据丢失。这正是 **`min-replicas-to-write 1`（TODO #14-P2）** 的价值：让"没有从库确认"的主库**拒绝写**。
  > ✅ **Redis 官方文档佐证**（Sentinel 文档 "Example 2: basic setup with three boxes"）：官方用**同一场景**（分区里的旧主库继续被写）说明该配置，并直接给出：
  > ```conf
  > min-replicas-to-write 1
  > min-replicas-max-lag 10
  > ```
  > *"the old Redis master M1 … will become unavailable after 10 seconds. When the partition heals, the Sentinel configuration will converge to the new one"* —— 也就是说，**#14-P2 不是我们自己想出来的加固，而是官方对"哨兵架构固有缺陷"的标准补丁**，我们演练测到的 10.9s 窗口正是它要覆盖的时间。
- **顺带解释了另一个坑**：老机 `redis-master.conf` 是**单文件 bind mount**，Redis 改写配置需要"写临时文件 + rename"→ 必然 `Resource busy`（与哨兵踩的坑同源）→ **降级只能靠哨兵运行时下发，不可能落盘**。

**⑤ 🔴 红线：哨兵 conf 是"运行时状态"，不能反向覆盖**

演练后 3 个 `sentinel-*.conf` 都被哨兵**整体重写**，多了 `sentinel config-epoch mymaster 2`、`myid`、known-sentinel/known-replica 等运行时状态。→ **仓库里的 conf 只是"初始模板"**；任何时候都不要把模板反向覆盖到运行中的哨兵 conf，否则会丢 epoch 与拓扑认知（哨兵可能又按旧地址找主库）。

**⑥ 话术**："我做过真实的故障转移演练：停掉老机主库，**6.1s 哨兵完成选主**（`down-after 5s` + Raft 选举 + 提升），**9.1s Lettuce 客户端自动重连到新主**，11 个服务零硬错误、数据零丢失，之后 `SENTINEL FAILOVER` **1.1s 切回**。过程中我发现**老主库重启后有 10.9s 的脑裂窗口**——它按静态配置自认为主，直到哨兵降级；所以 `min-replicas-to-write 1` 不是可选项，而是防止这段窗口被直连客户端写脏数据的关键配置（已开启）。另外哨兵的 conf 会被运行时重写，仓库模板绝不能反向覆盖。"

> ✅ **#14-P2 已完成（运行时 2026-09-09 21:45 + conf 持久化 2026-09-10 复核确认，仅老机主库）**：`min-replicas-to-write 1` + `min-replicas-max-lag 10`；运行时 `CONFIG SET` 生效后，**两行已落盘到 `/data/csmall/redis/redis-master.conf`（第 15~16 行）**——`CONFIG REWRITE` 在单文件 bind mount 上必然 `Resource busy`，故走"sudo 手工追加"路径（**无需重启 Redis**，重启后自动生效）。✅ 复核证据：`CONFIG GET` = 1/10 与 conf 一致；从库 `state=online, lag=0, min_slaves_good_slaves=1`。
> ⚠️ **新机从库明确不开**（2026-09-09 复核发现）：该参数**对被提升为主库的从库同样生效**，而故障转移后新主库在"老机重新连上来当从库"之前**没有任何从库** → **会拒绝所有写**（老机长时间不恢复就一直不可写），代价远大于收益。**保护职责放在主库那一份即可**。
> ⚠️ **代价与演练开关**：只有一个从库 → **新机不可用时老机拒写**（`NOREPLICAS Not enough good replicas to write.`，读仍可用）；停新机做演练/维护前先 `CONFIG SET min-replicas-to-write 0`，恢复后设回 1。→ 详见 [[跨机集群实施执行清单-2026-09-09]] §7.9。

## 五、疑惑点：为什么"高可用 ≠ 零中断"？怎么做到零中断（原 §6.5，逐字迁入）

**① 服务发现有三层，任何一层有延迟都会出现"打到死实例"的窗口**

```
实例存活  ──①心跳/主动注销──▶  注册中心  ──②推送/轮询──▶  客户端  ──③本地LB缓存TTL──▶  真正发请求
```

| 层 | 本次实测 | 关键机制 |
|---|---|---|
| ① 实例 → 注册中心 | **<1 秒** | Spring Cloud Alibaba **优雅停机主动注销**（`ContextClosedEvent` → `deregister`）；**若是 `docker kill`/进程崩溃，就只能等 15s 心跳超时** |
| ② 注册中心 → 客户端 | 秒级 | Nacos 推送（UDP/gRPC）+ 客户端兜底轮询 |
| ③ 客户端本地缓存 | **~16 秒** | Spring Cloud LoadBalancer 的实例列表缓存（`spring.cloud.loadbalancer.cache.ttl`，**默认 35s**） |

**② 所以"高可用"解决的是"服务还能用"，不是"请求一次都不失败"** —— 要做到后者，必须做**优雅下线（graceful shutdown / connection draining）**：

1. **先摘流量**：把实例在 Nacos 里设为 `enabled=false`（**实例仍在服务**，只是不再被负载均衡选中）
2. **等 > 客户端 LB 缓存 TTL**（默认 35s，所以滚动发布一般等 30–60s）
3. **再停容器**

> 这就是 K8s 里 **readiness probe + preStop sleep** 的等价物：K8s 先让 Pod 从 Service Endpoints 摘掉，再等 `preStop` 睡一会儿，最后才发 SIGTERM。
>
> **本次演练是"直接停容器"的粗暴版**，所以看到了 16s 窗口 —— 这恰好反证了优雅下线的必要性。

**③ ✅ 优雅下线已实现并实测（2026-09-09 21:47）：16s → 0**

| 手段 | 实测 |
|---|---|
| `DELETE /nacos/v1/ns/instance`（注销） | ❌ **无效**——返回 `ok`，但客户端心跳立刻把它重新注册（30s 内始终存在） |
| **`PUT ...&enabled=false`** | ✅ **实例立即从列表消失，进程仍活着继续服务** |
| 流程：`enabled=false` → 等 20s → `docker stop` | ✅ **30 次请求 0 失败**（粗暴停是 9 次 5 失败） |
| 恢复：`docker start` | ✅ 应用启动时自动以 `enabled=true` 重新注册，网关 10/10 成功 |

脚本：`deploy/scripts/graceful-stop.sh`。**这是"操作流程层"的修复——零配置变更、零重启。**

**④ 兜底手段**（应对"别人直接 `docker kill`"这类绕过流程的情况）：网关重试 / 断路器 / 缩短 LB 缓存 TTL（见 TODO #53 ①②④，需重启网关）。

## 七、⭐ 负载均衡分布验证：怎么证明请求真的被均分了（原 §6.7，逐字迁入） —— **60 次 → 30:30**

**① 难点：谁来告诉你"这个请求被哪个实例处理了"？**

| 常规手段 | 结果 |
|---|---|
| 服务访问日志 | 项目没配 |
| `actuator/metrics` | 被业务 `SSOFilter` 拦住（返回业务 401 体） |
| 网关日志 | 只在出错时才有 |

→ **可观测性不够时，就用"副作用"来归因**。

**② 办法：Redis `MONITOR` + 每个请求的 Redis 副作用**

`GET /seckill/spu/list?page=1&pageSize=10` 的实现里，对列表中的每个 SPU 都做 `redisTemplate.hasKey(...)` → **每个请求固定产生 12 条 `EXISTS mall:seckill:reseckill:<spuId>:<skuId>`**。而 `MONITOR` 记录**命令来源 IP**：

| 来源 IP | 对应实例 |
|---|---|
| `172.18.0.1` | 老机实例（容器出网经 docker bridge SNAT） |
| `172.29.193.240` | 新机实例（宿主 IP） |

**③ 实测结果**

| 项 | 值 |
|---|---|
| 请求数 | 60（全部 HTTP 200） |
| Redis `EXISTS` 总数 | **720 = 60 × 12** |
| 老机（`172.18.0.1`） | 360 条 → **30 个请求** |
| 新机（`172.29.193.240`） | 360 条 → **30 个请求** |
| **分布** | **50% : 50%（精确 30:30）** |

→ **Spring Cloud LoadBalancer 默认 `RoundRobin` 生效**，跨机轮询精确均分。

**④ 为什么这个验证值得记**

- **登录态怎么来**：`cs_mall_ums.ums_user` 有 110 个测试账号（`testuser1`~`testuser110`，统一弱密码，demo 数据）→ 经网关 `POST /user/sso/login` 拿 `data.tokenValue`，请求头带 `Authorization: Bearer <token>`。**注意 token 字段名是 `tokenValue` 不是 `token`，且必须带 `Bearer` 前缀**（第一次就踩了这个）。
- **接口需要分页参数**：`/seckill/spu/list` 不带 `page` 会报 `Cannot invoke "Integer.intValue()" because "page" is null`。
- **方法论**：**没有监控指标时，"命令流 + 来源 IP"就是最可靠的归因手段**——和 [[问题解决--本地双实例分布式锁验证方法]] 里用 `MONITOR` 验证锁是同一个思路。

## 八、⭐ 两机固有局限：为什么"从库挂了主库就不让写"（原 §6.9，逐字迁入） —— **2 台机器的固有局限（本项目取舍）**

> 这一节回答一个最反直觉的问题：**老机的 Redis 明明好好的，为什么新机一停，老机就写不进去了？**

#### ① 现象

开启 `min-replicas-to-write 1` 后，新机（从库）一停，老机（主库）**立刻拒绝所有写**：

```
(error) NOREPLICAS Not enough good replicas to write.
```

业务表现：下单失败、库存扣减失败、Redis 锁拿不到 → **读还能用，写全挂**。

#### ⭐ 先建立直觉：两个人的记账小组（"抄账本"，一次就懂）

> **你和搭档每人一本账本。** 规矩是：**你负责记账（主库），搭档负责抄一份（从库）；你记完就完事，不等搭档抄完**（这就是"异步复制"，为了快）。
>
> 你会时不时喊一声"在吗？"（心跳）。**如果没人应答**，你分不清是哪种情况：

| | 情况 A：他请假了 | 情况 B：电话线断了 |
|---|---|---|
| 他的账本 | 还在，只是没更新 | 还在，**而且他老板可能已经让他当正本了** |
| 你继续记账 | ✅ **安全**（你是唯一的账本） | ❌ **危险**（你记的会作废） |
| 你该怎么做 | 继续记 | **立刻停笔** |

**你分不清 A 和 B，就只能选一个动作**——"停笔"只是麻烦，"记了却作废"是灾难 → 所以选**停笔**。

> **这就是 `min-replicas-to-write 1` 的全部含义**：
> **"我（主库）没法确认数据已经安全复制出去时，宁可不写。"**
>
> 它不是"从库挂了所以主库坏了"，而是"**主库主动选择不写，以避免写了也白写**"。

#### ② 根因一：Redis 复制是**异步**的，主库"不知道数据到了没有"

```
客户端 ──写命令──▶ 主库：写进自己的内存/AOF ──▶ 立刻回复"成功"
                                    │
                                    └──异步──▶ 从库（主库不等、不确认）
```

所以**默认情况下主库是"先干了再说"**：它写完就回客户端，数据什么时候到从库、有没有到，它并不知道。

#### ③ 根因二：主库**分不清**两种"失联"

| | 场景 A：从库真的挂了 | 场景 B：只是网络断了 |
|---|---|---|
| 老机看到的 | `connected_slaves = 0` | `connected_slaves = 0`（**一模一样**） |
| 真相 | 老机是唯一副本，**继续写是安全的** | 对面可能已经**选出了新主**，老机写的注定会丢 |
| 该不该写 | 应该写 | **绝对不能写** |
| 主库能分辨吗 | **不能** ← 这就是全部问题的根源 | — |

**一个参数、两种情况、只能选一种行为** → 只能"一刀切"：宁可误拒，也不静默丢数据。

#### ④ 场景 B 的完整时间线（这才是参数真正要防的）

```
t=0      老机 ↔ 新机 网络断开（两台机器都活着）
t=+5s    新机上的 3 个哨兵判定"主库连不上" → 客观下线（+odown）
t=+6s    哨兵提升新机的从库 → 新机成为新主（+switch-master）
t=+6s    老机上的 11 个服务【仍然能连老机的主库】→ 继续写！
         （服务和老机在同一台机器上，网络分区对它们完全无感）
t=愈合    老机被降级为从库 → 全量同步 → 【刚才写的数据全部丢弃】
```

→ `min-replicas-to-write 1` 让老机在 **t=+6s 就停止接受写**，把"**静默丢数据**"变成"**明确报错**"。

> **关键认知**：分区时继续写，不是"写进了安全的地方"，而是"**写进了一个即将被格式化的磁盘**"——分区恢复时哨兵按**配置纪元（config-epoch）**收敛到新主，老机被降级并**全量同步覆盖**，它刚才写的全部作废。

> **为什么宁可报错？** 报错 → 用户看到失败、运维立刻知道、可重试可处理；静默丢数据 → 一切看起来正常，几小时后才发现，**无法挽回**。

#### ⑤ 为什么不能把从库放到老机本地？（另一个坑）

| 原因 | 说明 |
|---|---|
| **保护会失效** | 分区时老机**能看到本机从库** → 参数满足 → 继续写 → 场景 B 重新出现 |
| **不是真冗余** | 同一台机器上的主+从**一起挂**，对"主机宕机"零防护 |

**参数检查的是"有没有从库"，不区分"从库在不在同一台机器上"。**

#### ⑥ 拓扑对照：加副本到底能解决什么

| 拓扑 | 新机宕机 | 老机宕机 | 网络分区 |
|---|---|---|---|
| **1 主(老机) + 1 从(新机)** ← **本项目现状** | 拒写 ❌ | 可写 ✅ | 拒写 ✅ |
| 1 主 + 1 从(新机) + 1 从(新机) | 拒写 ❌ | 可写 ✅ | 拒写 ✅ |
| 1 主 + 1 从(新机) + 1 从(**老机本地**) | 可写 ✅ | 可写 ✅ | **保护失效 ❌** |
| **1 主 + 2 从（新机 + 第三台）** | **可写 ✅** | **可写 ✅** | **拒写 ✅**（完美） |

**结论**：2 台机器下**无解** —— 要么"某个节点挂了就不能写"，要么"允许静默丢数据"。真正的解法是**第三个副本放在第三台机器上**。

> 📌 记住这句话：**同一台机器上的副本，在"这台机器挂掉"的场景里，等于没有副本。** 这就是"新机再加一个从库"没有意义的原因。

#### ⑦ 本项目的取舍（成本 vs 完整性，2026-09-09 决策）

| 项 | 决策 | 理由 |
|---|---|---|
| 是否加第三台服务器 | ❌ **不加** | 学习项目 + 简历项目，**两台已约 ¥140/月**；第三台再 ¥71/月，收益（消除一个罕见场景）不划算 |
| 参数开在哪 | ✅ **只开老机主库** | 覆盖真正的风险场景（分区下旧主库继续被写）；从库侧开了会导致切换后新主库拒写 |
| 计划内停机（停新机做演练/维护） | **演练开关** | 先 `CONFIG SET min-replicas-to-write 0`，恢复后设回 `1` |
| 结果 | 🟡 **接受这个局限** | "**已知、已量化、有开关**"比"不知道"强得多 |

#### ⑧ 如果以后有条件，正确的演进方向

| 方案 | 做法 | 效果 |
|---|---|---|
| **加第三台机器** | 1 主 + 2 从（跨 3 台机） | 任一节点故障都不影响写入 + 分区保护 ✅ |
| **只对关键写要求同步** | 关键写后调用 `WAIT 1 100`（等至少 1 个从库确认，超时 100ms） | 把"全局拒写"改成"只对那一次关键写要求冗余"，可用性影响小得多 |
| **业务层兜底** | 写失败重试 + 告警 | 即使拒写也不至于完全瘫 |

> **共同原则**：副本必须分布在"**会独立故障的机器**"上。这与哨兵官方要求"三个哨兵放在会独立故障的机器上"是同一条原则。

#### ⑨ 面试话术（把"局限"讲成"理解深度"）

> "我给 Redis 开了 `min-replicas-to-write 1`，但很快发现一个反直觉的后果：**从库一挂，主库就拒绝所有写**。想明白之后我理解了它的本质——**Redis 复制是异步的，主库分不清'从库真死了'还是'只是网络断了'**。前者继续写是安全的，后者继续写会导致脑裂丢数据。它只能一刀切选保守。
>
> 但 `min-replicas-to-write` 的**适用前提是至少 2 个从库**——挂一个还剩一个。我只有 1 个从库，所以任何一台机器故障都会让写入停摆。我评估了三种方案：① 加第三台机器（能完美解决，但要再加 ¥71/月，学习项目不划算）；② 把从库放到主库同机（**会破坏分区保护**，因为主库能看到本机从库就继续写）；③ 接受局限 + 演练开关。
>
> 最后我选了 ③，并且把参数**只开在主库侧**——因为故障转移后新主库手里没有从库，开了它反而会长时间不可写。**结论是：这不是配置错了，而是副本数量不足时这个参数的固有局限，我把它记录在文档里而不是假装没这回事。**"

## 九、跨问题的共性认知与踩坑清单

| 认知 / 坑 | 说明 |
|---|---|
| ⭐ **"停实例"≠"立刻不被打"** | Nacos 侧 <1 秒摘除，但客户端持有实例列表缓存（Spring Cloud LoadBalancer 默认 TTL 35s，实测窗口 **16s**）→ 窗口内的 500 只有"摘流量 + 等"才能消掉（原 §6.4 / §6.5） |
| ⭐ **"高可用"治的是"服务还能用"，"零中断"要的是"请求一次都不失败"** | 优雅下线是**操作流程层的修复**——零配置变更、零重启：`deploy/scripts/graceful-stop.sh`（原 §6.5） |
| ⭐ **`DELETE /nacos/v1/ns/instance` 注销是无效的** | 返回 `ok`，但客户端心跳立刻把它重新注册；必须用 `PUT ...&enabled=false`（**实例仍在服务，只是不再被负载均衡选中**）（原 §6.5） |
| ⭐ **没有监控指标时，用"副作用 + 来源 IP"归因** | 列表接口里每个 SPU 一次 `hasKey` → 每请求固定 12 条 `EXISTS`；`MONITOR` 记来源 IP → 精确 30:30。与验证分布式锁是同一思路（原 §6.7） |
| ⚠️ **哨兵 conf 是"运行时状态"，不能反向覆盖** | 演练后 3 个 `sentinel-*.conf` 被整体重写（多出 `config-epoch` / `myid`）；仓库模板只是初始模板。且单文件 bind mount 无法 rename → 老主库降级只能靠哨兵运行时下发（原 §5.9） |
| ⚠️ **`min-replicas-to-write` 有两个前提** | ① **≥2 个从库**（只有 1 个时任何一台机器故障都会让写入停摆）；② **不要开在"可能被提升为主库"的从库上**（切换后新主库手里没有从库 → 拒写）（原 §5.9 / §6.9） |

## 十、面试综述话术（贯穿本类）

> "跨机集群这条线我做完最大的体会是：**'集群'不是'多起一个实例'，而是四个必须被分别证明的机制**。**第一，负载均衡真的均分**——我没有只相信配置里的 `lb://`，而是用 Redis `MONITOR` 把每个请求的副作用（每请求固定 12 条 `EXISTS`）按来源 IP 归因到实例，60 个请求拿到**精确的 30:30**，证明 `RoundRobin` 真的在跨机轮询。**第二，故障转移真的自动**——我停掉老机主库做了真实演练：**6.1s 哨兵完成选主**（其中 5s 是 `down-after` 必须等够，真正的 Raft 选举 + 提升只有 1.1s），**9.1s Lettuce 客户端自动重连到新主**，11 个服务零硬错误、数据零丢失，之后 `SENTINEL FAILOVER` 1.1s 切回；而且我发现老主库重启后有 **10.9s 的脑裂窗口**（它按静态配置自认为主），所以 `min-replicas-to-write 1` 不是可选项。**第三，注册剔除真的有窗口**——停实例后 Nacos **不到 1 秒**就摘除了，但网关侧仍有一半请求打到死实例报 500，持续 **~16 秒**（客户端实例列表缓存 + 兜底轮询），所以**'高可用'不等于'零中断'**。**第四，优雅下线真的零中断**——`PUT ...&enabled=false` 先摘流量、等 20s 超过缓存 TTL、再 `docker stop`，**30 次请求 0 失败**；注意 `DELETE` 注销是无效的，心跳会立刻重新注册。最后我保留了一条**诚实的边界**：副本必须分布在'会独立故障的机器'上——我只有 1 主 1 从两台机器，`min-replicas-to-write 1` 于是变成'新机一停老机就拒写'，这是**副本数量不足时该参数的固有局限**，我量化后选择接受并保留'演练开关'，而不是假装没这回事。"
