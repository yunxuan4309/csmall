## 一、这一类问题的共性（★ 先看这张表，比逐个看个案更重要）

| 维度 | 共性 | 本项目实例 |
|---|---|---|
| **触发条件** | 线上对象（**索引 / 表 / 数据**）**早于**当前代码存在，或**由另一条路径**写进去 | 索引 `creation_date` ≈ 2026-07-31，**早于** `EsIndexInitializer` 上线 |
| **为什么"静默"** | 三条都不报错：① **查询打错字段形态** → 0 命中（看着像"没有数据"）；② **异常被 try-catch 吞掉** → 接口返回空；③ **类型不匹配** → 只在**开关打开后**才炸 | `term brandName` = 0 命中 · `/ai/search/suggest` 恒空 · 向量检索"一开必失败" |
| **为什么"不自愈"** | 初始化逻辑是 `if (exists) return` —— **只创建、不校验** | 启动日志 `ES索引 [cool_shark_mall_ai] 已存在` |
| **何时才暴露** | 只在**特定路径**：品牌过滤 / 补全接口 / 开了向量开关 / 用**后台接口**新增秒杀 | 4/12 个秒杀 SKU 从不预热，靠**永久 key 偶然兜住** |
| **为什么"改了也不一定生效"** | 变更的**入口不止一个**（多实例 / 影子配置 / 只改了代码没重建镜像 / 校验漏了会被写的字段）⇒ 「**我提交了变更**」≠「**生效的是变更后的版本**」 | 双实例**只重建一台** → 那条 MQ 消息被**旧 jar 的副本**消费；Nacos 改的是**同名影子 dataId** → PUT 返回 `true` 而应用行为不变 |
| **共性解法** | ① **靠实测而不是读代码**下结论；② 实验要选**决定性**的；③ 找出"**是谁创建的**"；④ 修完**必须回归**（改动会牵动别的路径）；⑤ 把"**下次怎么核**"写成命令；⑥ **变更后验证"生效侧"而不是"提交侧"**（逐实例核版本 / 看消费侧日志与行为 / 校验覆盖全部会被写的字段） | 见第二、三、四节 |

> 💡 **一句话记忆**：这一类问题的可怕之处是"**能跑**"—— 功能看着正常，只是**结果一直是错的**。
> 💡 **第二句记忆（2026-09-12 补）**：**"改了"和"生效了"是两件事** —— 变更有四个说谎的入口：**多实例（只改了一台）、影子配置（改的不是被订阅的那份）、校验（只查了不会被写的字段）、编排（命令发出去了但没执行）**。

## 二、问题 1：#63 ES 索引 mapping 与代码期望不符

### 现象（三个后果，都是"静默"的）

| # | 现象 | 症状形态 |
|---|---|---|
| 1 | **品牌过滤恒不生效** | `RagServiceImpl.intentSearch` 用 `term brandName` 打 `text` 字段 → **恒 0 命中**（品牌维度只能靠 `fullTextSearchNoPrice` 兜底） |
| 2 | **`/ai/search/suggest` 补全恒返回空** | completion suggester 打 `text` 字段**抛异常被吞掉** |
| 3 | **向量检索一旦开启必失败** | 当时 `embedding-enabled: false` 所以**还没暴露**；开后 `semanticVector` 会被动态映射成 `float` 数组，而检索用 `scriptScore + cosineSimilarity(params.queryVector, 'semanticVector')` → 类型不匹配 → **#31 白做** |

### 排查（★ 本节最值钱：怎么把"期望 vs 实际"两边都钉死）

**先备份现场（留证 + 事后可比对）**：

```bash
curl -s localhost:9200/cool_shark_mall_ai/_mapping   > /tmp/mapping-before-$(date +%F).json
curl -s localhost:9200/cool_shark_mall_ai/_settings >> /tmp/mapping-before-$(date +%F).json
curl -s localhost:9200/cool_shark_mall_ai/_count     | tee /tmp/es-count-before.txt
```

**期望侧 ⟷ 实际侧对照**（期望 = `EsIndexInitializer.createIndex()` 的 mapping 常量；实际 = `curl localhost:9200`）：

| 期望（代码） | **线上实际** | 影响 |
|---|---|---|
| `dynamic: false` | **未设置 → ES 默认 `true`** | 字段类型由首个写入值决定，随时可能变 |
| 4 个字段用 `ik_max_word` | 全是 `text`+`keyword` 子字段，**无 analyzer** | IK 未生效 |
| `categoryName/brandName/pictures/tags` 为 `keyword` | 全是 `text` | → 品牌过滤失效 |
| `listPrice: double` | `listPrice: float` | 类型不一致（影响小） |
| `semanticVector: dense_vector(dims=1024, cosine)` | **完全没有该字段**（`grep -c semanticVector` = 0） | → 向量检索必失败 |
| `suggestField: completion` | **`text`** | → 补全恒空 |

**三个决定性实验（缺一不可）**：

1. **`_analyze` 判分词**：`{"field":"name","text":"小米手机"}` → **4 个 `<IDEOGRAPHIC>` 单字** = standard 分词 ⇒ **IK 未生效**（这是**确定性**实验：重建成不成功它骗不了人）。
2. **`term` vs `match` 判"是数据问题还是查询问题"**：`term brandName="小米"` = **0** ／ `term brandName.keyword="小米"` = **4** ／ `match` = **4** ⇒ **数据没问题，是查询打错了字段形态**（最强的证据形态）。
3. **`_cat/plugins` 排除"最坏情况"**：**`analysis-ik 8.6.0` 已加载**，显式 `{"analyzer":"ik_max_word"}` 能正确切出 `小米`/`手机`（type=`CN_WORD`）⇒ 原方案里"重建后 IK 仍不生效"这个**失败预案被排除**（否则不敢动）。

> 另外核对了：`cool_shark*` **只有这一个索引、无别名**（排除"查错索引"）；`suggestField` 写入形状确实是**字符串数组**（正是 `completion` 期望的形状 → 重建后立刻可用）；`semanticVector` mapping 与文档里都没有（因 `embedding-enabled=false`）。

### 根因：**谁创建的？为什么不自愈？**

- **不自愈**：`EsIndexInitializer` **只在索引不存在时才创建**（`if (exists) return`）→ 这份漂移**永不修复**；启动日志 `ES索引 [cool_shark_mall_ai] 已存在` 是铁证。
- **谁创建的（反推，非实测）**：线上 settings 是 `number_of_shards=1 / number_of_replicas=0`，**与代码期望一致**，但 **mapping 全空** ⇒ 说明当年那次创建**带了 settings、没带 mappings**（某个历史版本），**而不是 ES 自动创建**（自动创建 replicas 会是 1）。**具体版本未能查明**。

### 修复与验收（含一次**我自己的错误**）

```bash
# ① 先停 mall-ai（避免"索引已删、服务还在查询"的报错窗口）
cd /data/csmall && docker compose stop mall-ai
# ② 删索引（dense_vector 的 dims 建成后不可改 → 只能删了重建）
curl -X DELETE localhost:9200/cool_shark_mall_ai
# ③ 重建 + 全量同步
docker compose up -d mall-ai
#    ★ 必须等启动完成：docker logs -f csmall-ai | grep "Started MallAiWebApiApplication"
#    ★ 再看一行 "启动自动同步完成，共 N 条商品"
```

| 验收项 | 修前 | 修后（实测） |
|---|---|---|
| `dynamic` | 未设置（= `true`） | **`false`** ✅ |
| 4 个 text 字段分词 | 4 个单字 | **`小米`/`手机`（`CN_WORD`）** ✅ |
| `brandName/categoryName/pictures/tags` | `text` | **`keyword`** ✅ |
| `semanticVector` | 不存在 | **`dense_vector` `dims=1024` `similarity=cosine`** ✅ |
| `suggestField` | `text` | **`completion` + `ik_max_word`** ✅ |
| `term brandName="小米"` | **0** | **4** ✅ |
| 补全 | 恒空 | **`prefix=小米` → 返回「小米 14」** ✅ |

> 🔴 **本次执行纠正了我自己的一处错误（方法论的教训）**：验收命令里我写的 `grep -c ik_max_word` **期望 4** 是错的 —— ① `grep -c` 数的是**行数**，而 mapping 是**单行 JSON** ⇒ 永远只返回 0/1；② 实际出现次数是 **5**（4 个 text 字段 + `suggestField` 也用 `ik_max_word`）。正确写法 `grep -o … | wc -l`。
> **教训：验收命令本身也要被验收** —— 所幸关键那条 `_analyze` 是**确定性**的，所以用户看到 "1 ≠ 4" 时没有误判。

### 修复附带风险（**修 A 会牵动 B**）

重建后 `brandName / categoryName / pictures / tags` 从 `text` 变 **`keyword`**，而 `RagServiceImpl` 的 `multiMatch` **正包含这三个字段** → 从"部分匹配"变"**整值精确匹配**"：

- **好处**：`term brandName` 过滤（原本恒 0）**开始生效**；
- **风险**：查询串若是"小米手机"，keyword 字段 `"小米"`**不再命中** → **召回可能变少**；
- ⇒ **重建后必须跟一次召回回归**。实测**未发生**：`小米手机` 8 · `小米` 4 · `手机` 7 · `华为` 3 · `笔记本` 5 · `旗舰` 3 —— **原因**：`semanticText` 里本身就写着「品牌：小米 | 分类：手机 | 标签：…」→ 品牌/分类召回由 `semanticText`（权重 3）兜住。

## 三、问题 2：#64 秒杀预热 —— **同一字段两种含义**

### 现象

12 个秒杀 SKU **只有 8 个被预热**，另外 4 个靠**凌晨 03:30 对账写的 `TTL=-1` 永久 key** 偶然兜住。

### 根因

`seckill_sku.spu_id` **存的是 `seckill_spu.id`**（前端详情 / 限购按它查），而**预热 Job 用的是 pms `spu_id`** → **二者只在"碰巧相等"时一致**。现有 6 行里 **4 行错位**。

### 为什么难发现（三条，缺一不可）

1. **"能下单"** —— 永久 key 兜住了，没人报障；
2. **只在新增 / 换批时暴露** —— 存量靠对账"擦屁股"；
3. 🔴 **用后台接口新增必然踩** —— MyBatis-Plus 会给**雪花 id** → `id ≠ spu_id` → **预热永不命中**（新数据反而比老数据更容易坏）。

### 硬约束（绕过去的做法，不是修复）

> **新增秒杀必须满足：`seckill_spu.id == seckill_sku.spu_id == pms_spu.id` 三者相等。**
> ⚠️ **不要用后台接口新增**（会给雪花 id）。

### 附带结论：Redis 预热键"哪些能手工写、哪些绝对不能"

| key | 能否手工写 | 原因 |
|---|---|---|
| `mall:seckill:sku:stock:<pmsSkuId>` | ✅ **能**（建议写） | `StringRedisTemplate`，值是**纯数字字符串** → `redis-cli SET` 兼容 |
| `mall:seckill:spu:url:rand:code:<pmsSpuId>` | ❌ **不能** | 值是 **JDK 序列化的 Integer** → 手工写格式对不上，反序列化异常 |
| `spu:bloom:filter:<today>` | ❌ **不能** | 是 Redis **SET**（不是真布隆），成员是 **JDK 序列化的 String** |

⇒ **共性认知**：**"能手工补数据"的前提是"序列化格式匹配"** —— 用 `redis-cli` 补线上 key 之前，必须先确认这个 key 是**模板写的**还是**序列化写的**。

> **状态**：✅ **已修（2026-09-12）** —— `SeckillInitialJob` 改用 `seckillSpuMapper.findSeckillSkusBySpuId(spu.getId())`（不再拿 pms id 去查），实测**预热覆盖 12/12**（原 8/12），SKU `11/12/13/14` 于 `05:59:00` 打日志「库存数成功预热到缓存」。
> ⚠️ **有一处"故意不改"**：随机码 key 仍用 `getRandCodeKey(spu.getSpuId())` —— 前端拿的是 `seckill_spu.spu_id`（pms id），改它会把**本来是对的**那条路径改坏（"修 A 会牵动 B"的现场判断）。
> 🔴 **同一根因的另一半在消费侧（= 生产缺陷 #69）**：`SeckillQueueConsumer:98` 同样把 `seckill_sku.spu_id`（= `seckill_spu.id`）当 pms id 用 → `incrementSales` **累加到了错误的商品**上（实测 `pms_spu.sales`：`sales[4] 1→2→3`、`sales[6] 1→2`）。详见下方 **问题 3**。
> 📌 **本文档原先写"未修"是 2026-09-11 的时点** —— 修完**必须回头改这一行**（本次即如此），这正是 CLAUDE.md §五·8「分册状态纠偏」的第 ⑤ 类漂移。
> **原改动计划（历史留档）**：1 个 Job（`SeckillInitialJob` 改用 `getId()`）+ 历史数据订正，涉及秒杀可用性 → **需单独窗口，按纪律不夹带**（2026-09-12 按此单独执行）。

## 四、问题 3：变更"做了"≠"生效了"（★ 2026-09-12 新增：四个"我以为改好了"的实测个案）

> **共同点**：四个个案**全都不报错**，而且在我自己的视角里都**已经"完成"了** —— 代码提交了 / 配置 PUT 返回 `true` / 脚本打印 ✅ / 编排命令发出去了。
> **只有站到"生效侧"去看，才发现压根没生效。** 这一节的价值不在四个坑本身，而在逼自己回答一个问题：**我凭什么相信这次变更生效了？**

### 4.1 个案 A：多实例版本不一致 —— 只重建了一台，**旧 jar 的那台消费了那条消息**

- **背景**：秒杀服务是**跨机双实例**（老机 `csmall-seckill` + 新机副本 `csmall-seckill-2`），两者注册**同一个 Dubbo 服务**、消费**同一个 MQ 队列**（竞争消费）。
- **现象**：修好 `incrementSales` 的错商品问题后，按常规流程重建镜像、部署、重启 → **重做 A/B 验证，错误照旧复现**（"非目标 spu"告警仍在）。
- **根因**：那次部署**只升级了老机那台**；新机上的副本容器还跑着**旧 jar**（`csmall/mall-seckill-replica:20260909`），而这条消息**恰好被它消费**了 → 旧代码照旧写错商品（副本日志时间戳 `05:48:38` 对得上）。
- **修复**：**两台**换成同一份 jar / 同一镜像 tag（`csmall-mall-seckill:20260912`），并把副本的差异**收敛成两个环境变量**（`SERVER_PORT` + `SW_AGENT_NAME`），不再维护两套镜像、不再有"两个版本并存"的土壤。
- **★ 可复用判据**：**"部署完成"不能只看一个容器**，必须**逐实例**核 jar 指纹（容器内 vs 宿主 jars 文件 + 状态 + HTTP）：
  ```bash
  # 逐实例核对（老机 + 新机各跑一次）；容器内路径 /app/app.jar，宿主 /data/csmall/jars/mall-seckill.jar
  docker exec csmall-seckill   md5sum /app/app.jar && md5sum /data/csmall/jars/mall-seckill.jar
  docker exec csmall-seckill-2 md5sum /app/app.jar   # 两台 md5 必须相同
  ```
  > ⚠️ **两个连带教训**：① 副本镜像 tag **别写死日期**（`docker compose build` 会覆盖同名 tag，导致"我明明构建了"却拿到旧层）；② 有副本的微服务，**部署清单必须写"逐实例"** —— 已固化为 `deploy/scripts/deploy-seckill-both.ps1 -CheckOnly`（只读，随时可跑；md5 不一致直接红字报警）。

### 4.2 个案 B：Nacos 影子 dataId —— **PUT 返回 true、GET 也读到 200，应用就是不变**

- **背景**：压测要把 AI 链路并发阈值 5 调到 200，走 Nacos 配置热更新（**不改代码、不重启**）。
- **现象**：`POST /nacos/v1/cs/configs` **返回 `true`**，再 `GET` 也**确实读到 200**；但压测里"成功 RPS"**恒定 5.0**、入口限流 95~98% —— 配置"改成功了"，**行为一点没变**。
- **根因**：**改的不是应用订阅的那个 dataId**。应用订阅 `mall-ai-flow-rules`（**没有扩展名**），我 PUT 的是仓库文件形态的 `mall-ai-flow-rules.json` ⇒ 在 Nacos 上**新建了一个同名影子配置**，应用侧**从未收到通知**（`notify-ok` 的 md5 从头到尾都是旧规则的）。
- **修复与取证**：改为 PUT **正确的 dataId** → **在消费侧取证**：应用日志出现 `notify-ok`（`md5=ef13f50d…`），阈值真的生效后成功 RPS 才上去；顺手**删掉影子配置**（否则下次一定还会有人改错那一份）。
- **★ 可复用判据**：
  1. **"服务端返回成功"不是证据** —— 配置类变更必须在**消费侧**验证（应用日志的 `notify-*` / 实际行为指标）。
  2. **改之前先确认"应用订阅的到底是哪个 dataId"**（照应用的 `spring.cloud.sentinel.datasource.*.data-id` 抄，**别照仓库文件名抄**）。
  3. 改完**先跑一个最小档探针**再压全量 —— 阈值真生效的话，**最小的那一档就该变**。

### 4.3 个案 C："假通过" —— 脚本打印了 ✅，但**校验漏了会被写的字段**

- **现象**：造数脚本跑完打印「✅ 全部回位 / 校验通过」，但我**每次都发现 `SUM(sales)` 比基线多 1**（多出来的正是被错写的那个商品）。
- **根因**：脚本的校验**只覆盖 `seckill_stock` / `stock`**，而实际被写坏的是 **`sales`（累加字段）** ⇒ **校验集不是变更集的超集**，于是"通过"是**假的**（更糟：它让我**停止了怀疑**）。
- **修复**：① 校验口径**升级为批次维度**（原先全局口径，跨批次必然误报）；② 增加**基线比对** —— 造数前 `--baseline` 存一份（11 张表行数 + `sum_stock`/`sum_sales`），清理后 `--compare-baseline` 比对，**任何一项不符即报错**。
- **★ 可复用判据**：
  > **"校验通过"必须能回答"校验覆盖了哪些字段"** —— 覆盖不全的 ✅ **比没有校验更危险**。
  > 兜底做法：对"会被写到的**聚合量**"做**前后基线比对**，而不是只做"写得对不对"的点检（这个坑是**基线比对抓出来的**）。

### 4.4 个案 D：编排脚本空跑 —— **5 步远程编排一步没执行，而且它不报错**

- **现象**：一段"备份配置 → 改 AI 指向 mock → 压测 → **还原** → 复核"的 5 步编排，执行后**看似正常**；复核时发现**生产仍停在"AI 指向 mock"**（**还原那一步没跑**）。
- **根因**：PowerShell 里 **`r` / `R` 是 `Invoke-History` 的内置别名** ⇒ 自定义的 `R` 函数**被别名优先解析**，`R $host @'…'@` 变成"调用历史命令"，**整段静默空跑**。
- **处置**：**先手工还原并逐项复核**（AI 指向 / 开关 / Nacos 阈值 / mock 进程 / 容器数），再把函数名改成不易撞的名字（`Ssh-Run`），并在脚本文件头写明这个陷阱。
- **★ 可复用判据**：
  1. **别用单字母/易撞别名的函数名**（先 `Get-Alias` 确认）；脚本要能**自证执行过**（每步打印 + 关键返回值）。
  2. **"有副作用的编排"必须配看门狗**：**先武装"定时自动还原"**，再开始有副作用的步骤 —— 即使编排中断 / 空跑，**最终状态也会自己回到基线**（本次是事后补的，**事前就该有**）。
  3. **长脚本的"完成"以复核为准**：对**生产最终状态**做一次独立取证，而不是相信脚本自己的打印。

### 4.5 本节小结：变更生效性的"四个检查位"

| 检查位 | 问自己 | 今日反例 |
|---|---|---|
| **① 落到几个实例？** | 这个服务有几个实例/副本？我改了**全部**吗？ | A：双实例只改一台 → 旧 jar 消费了消息 |
| **② 改的是被订阅的那份吗？** | 消费侧**据以生效**的标识是什么（dataId / key / 文件名）？ | B：影子 dataId，PUT 成功而应用无感 |
| **③ 校验覆盖了会被改的全部字段吗？** | 变更集 ⊆ 校验集 吗？有没有**累加量**？ | C：漏了 `sales` → 假通过 |
| **④ 编排真的跑完了吗？** | 有**独立复核**吗？有**看门狗**吗？ | D：别名空跑 + 无看门狗 |

⇒ **一句话**：**别问"我改了吗"，要问"生效侧现在是什么"** —— 版本看**逐实例指纹**、配置看**消费侧日志**、数据看**前后基线**、流程看**独立复核**。

## 六、跨问题的共性认知与踩坑清单

1. **"能跑"≠"对"**：本例三个问题全部表现为"功能正常"（品牌过滤有兜底、补全没人用、预热靠永久 key）。
2. **判断"线上是什么"只能靠实测，而且实验要选决定性的** —— `_analyze` 是确定性的；`term` vs `match` 能区分"**数据问题**"还是"**查询问题**"（本次是后者）。
3. **先排除"最坏情况"再动手**：原方案把"IK 插件不可用"列为失败预案 → 用 `_cat/plugins` 实测排除，**否则不敢删索引重建**。
4. **反推"是谁创建的"**：用 `creation_date` + `settings 与 mapping 是否一致` 判断"历史版本写的"还是"ES 自动创建"（自动创建 replicas 会是 1）。
5. **修 A 会牵动 B**：mapping 一改，**召回语义就变了** ⇒ 修复清单里必须**自带回归项**（本次做了召回回归）。
6. **"同一字段两种含义"是设计债**：三值相等是**绕过去**，不是修复；要不要修、什么时候修，要按"**不夹带**"纪律单独决策。
7. **初始化类只创建不校验 = 漂移的水库**（`if (exists) return`）⇒ 这一类系统需要**定期核对机制**，而不是等报错。
8. **验收命令自身要经得起推敲**（`grep -c` 数单行 JSON 恒 0/1；`grep 'Caused by'` 会命中提示语文本）。
9. ⭐ **"我做了变更"与"变更生效了"是两件事**（2026-09-12 新增）—— 变更有四个说谎的入口：**多实例 / 影子配置 / 校验漏项 / 编排空跑**；**唯一的通用解药是"到生效侧取证"**（逐实例指纹 / 消费侧日志 / 前后基线 / 独立复核）。
10. **"服务端返回成功"不是证据**：Nacos PUT 返回 `true`、脚本打印 ✅、`docker compose up` 退出码 0 —— 都只是**提交侧**的证据。
11. **"校验通过"的边界必须在文档里写出来**："校验覆盖了哪些字段"答不上来的 ✅ = **假通过**（比没有校验更危险，因为它会让人停止怀疑）。
12. **有副本 / 有热配置 / 有编排脚本的变更，事前就要有"看门狗 + 逐实例核对"**，而不是出事后再补（本次两条部署纪律即由此而来，见 `deploy/scripts/deploy-seckill-both.ps1` 文件头）。

## 七、面试综述话术（贯穿本类，可直接用）

> "我最怕的不是 500，是 **200 但是错的**。这个项目里有四类同类问题，本质都是'**代码期望**'和'**线上实际**'两个事实来源谁都不自动对齐：
> 一次是 ES 索引 —— 代码里写好了 `ik_max_word`、`keyword`、`dense_vector`，但线上这份索引是**更早的某个版本**建的，`mapping` 全空；初始化类又是 `if (exists) return`，所以**永不自愈**。表现是品牌过滤恒 0 命中、补全恒空、向量检索一开就废。我是靠三个**决定性实验**定的性：`_analyze` 出来 4 个单字说明 IK 没生效；`term` 打 0 而 `term .keyword` 打 4，说明**是查询打错了字段形态、数据没问题**；`_cat/plugins` 说明 IK 插件其实好好的，排除了最坏情况。修完还专门做了**召回回归**，因为 `keyword` 化会让部分匹配变成整值匹配。
> 第二次是秒杀预热 —— 同一个 `spu_id` 字段有**两套语义**（存的是 `seckill_spu.id`，预热却用 pms 的 `spu_id`），只在碰巧相等时才一致，12 个 SKU 有 4 个从来没预热过、靠对账写的永久 key 偶然兜住。这类问题的可怕之处就是'**能下单**'。
> 第三次是 MySQL 侧的实体/库/DDL 三方漂移，我单独写了一篇。
> 第四次更隐蔽 —— **不是"线上和代码不一致"，而是"我以为我改了，其实没生效"**。同一天我踩了四个：改了一个微服务的 bug，但它是**双实例**、我只重建了一台，那条消息被另一台**旧 jar** 的副本消费了，所以我"验过了"的错误照旧复现；调并发阈值时我 PUT 到 Nacos 返回 `true`、`GET` 也读到了新值，可应用订阅的是**另一个同名、没有扩展名的 dataId**，我改的是个**影子配置**（成功 RPS 从头到尾恒定在旧阈值）—— 这两次都是**只看提交侧、没看生效侧**。第三次是我写的清理脚本打印「✅ 校验通过」，但它的校验**只覆盖库存、没覆盖销量**，那个"通过"是**假的**，最后靠**造数前后的基线比对**才抓出来。第四次更离谱：一段 5 步的远程编排**一步都没执行**，因为 PowerShell 里 `r` 是 `Invoke-History` 的别名，把我自定义的函数名覆盖了，**静默空跑**。
> 所以现在我判断一次变更是否真的生效，有四个固定检查位：**① 落到几个实例（逐实例核 jar 指纹）② 改的是不是被订阅的那份（看消费侧日志，不看服务端返回码）③ 校验是否覆盖了所有会被写的字段（含累加量，用基线比对兜底）④ 编排有没有真的跑完（独立复核 + 事前武装看门狗还原）**。"
> 所以我的结论是：**这类"不报错、不自愈、只在特定路径暴露"的问题，必须靠定期核对机制去发现，不能等报错**。"
