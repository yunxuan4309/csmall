## 一、这一类问题的共性（★ 先看这张表，比逐个看个案更重要）

| 维度 | 共性 | 本项目实例 |
|---|---|---|
| **触发条件** | 线上对象（**索引 / 表 / 数据**）**早于**当前代码存在，或**由另一条路径**写进去 | 索引 `creation_date` ≈ 2026-07-31，**早于** `EsIndexInitializer` 上线 |
| **为什么"静默"** | 三条都不报错：① **查询打错字段形态** → 0 命中（看着像"没有数据"）；② **异常被 try-catch 吞掉** → 接口返回空；③ **类型不匹配** → 只在**开关打开后**才炸 | `term brandName` = 0 命中 · `/ai/search/suggest` 恒空 · 向量检索"一开必失败" |
| **为什么"不自愈"** | 初始化逻辑是 `if (exists) return` —— **只创建、不校验** | 启动日志 `ES索引 [cool_shark_mall_ai] 已存在` |
| **何时才暴露** | 只在**特定路径**：品牌过滤 / 补全接口 / 开了向量开关 / 用**后台接口**新增秒杀 | 4/12 个秒杀 SKU 从不预热，靠**永久 key 偶然兜住** |
| **共性解法** | ① **靠实测而不是读代码**下结论；② 实验要选**决定性**的；③ 找出"**是谁创建的**"；④ 修完**必须回归**（改动会牵动别的路径）；⑤ 把"**下次怎么核**"写成命令 | 见第二、三节 |

> 💡 **一句话记忆**：这一类问题的可怕之处是"**能跑**"—— 功能看着正常，只是**结果一直是错的**。

## 二、问题 1：#63 ES 索引 mapping 与代码期望不符

### 现象（三个后果，都是"静默"的）

| # | 现象 | 症状形态 |
|---|---|---|
| 1 | **品牌过滤恒不生效** | `RagServiceImpl.intentSearch` 用 `term brandName` 打 `text` 字段 → **恒 0 命中**（品牌维度只能靠 `fullTextSearchNoPrice` 兜底） |
| 2 | **`/ai/search/suggest` 补全恒返回空** | completion suggester 打 `text` 字段**抛异常被吞掉** |
| 3 | **向量检索一旦开启必失败** | 当时 `embedding-enabled: false` 所以**还没暴露**；开后 `semanticVector` 会被动态映射成 `float` 数组，而检索用 `scriptScore + cosineSimilarity(params.queryVector, 'semanticVector')` → 类型不匹配 → **#31 白做** |

### 排查（★ 本节最值钱：怎么把"期望 vs 实际"两边都钉死）

**先备份现场（留证 + 事后可比对）**：

```bash
curl -s localhost:9200/cool_shark_mall_ai/_mapping   > /tmp/mapping-before-$(date +%F).json
curl -s localhost:9200/cool_shark_mall_ai/_settings >> /tmp/mapping-before-$(date +%F).json
curl -s localhost:9200/cool_shark_mall_ai/_count     | tee /tmp/es-count-before.txt
```

**期望侧 ⟷ 实际侧对照**（期望 = `EsIndexInitializer.createIndex()` 的 mapping 常量；实际 = `curl localhost:9200`）：

| 期望（代码） | **线上实际** | 影响 |
|---|---|---|
| `dynamic: false` | **未设置 → ES 默认 `true`** | 字段类型由首个写入值决定，随时可能变 |
| 4 个字段用 `ik_max_word` | 全是 `text`+`keyword` 子字段，**无 analyzer** | IK 未生效 |
| `categoryName/brandName/pictures/tags` 为 `keyword` | 全是 `text` | → 品牌过滤失效 |
| `listPrice: double` | `listPrice: float` | 类型不一致（影响小） |
| `semanticVector: dense_vector(dims=1024, cosine)` | **完全没有该字段**（`grep -c semanticVector` = 0） | → 向量检索必失败 |
| `suggestField: completion` | **`text`** | → 补全恒空 |

**三个决定性实验（缺一不可）**：

1. **`_analyze` 判分词**：`{"field":"name","text":"小米手机"}` → **4 个 `<IDEOGRAPHIC>` 单字** = standard 分词 ⇒ **IK 未生效**（这是**确定性**实验：重建成不成功它骗不了人）。
2. **`term` vs `match` 判"是数据问题还是查询问题"**：`term brandName="小米"` = **0** ／ `term brandName.keyword="小米"` = **4** ／ `match` = **4** ⇒ **数据没问题，是查询打错了字段形态**（最强的证据形态）。
3. **`_cat/plugins` 排除"最坏情况"**：**`analysis-ik 8.6.0` 已加载**，显式 `{"analyzer":"ik_max_word"}` 能正确切出 `小米`/`手机`（type=`CN_WORD`）⇒ 原方案里"重建后 IK 仍不生效"这个**失败预案被排除**（否则不敢动）。

> 另外核对了：`cool_shark*` **只有这一个索引、无别名**（排除"查错索引"）；`suggestField` 写入形状确实是**字符串数组**（正是 `completion` 期望的形状 → 重建后立刻可用）；`semanticVector` mapping 与文档里都没有（因 `embedding-enabled=false`）。

### 根因：**谁创建的？为什么不自愈？**

- **不自愈**：`EsIndexInitializer` **只在索引不存在时才创建**（`if (exists) return`）→ 这份漂移**永不修复**；启动日志 `ES索引 [cool_shark_mall_ai] 已存在` 是铁证。
- **谁创建的（反推，非实测）**：线上 settings 是 `number_of_shards=1 / number_of_replicas=0`，**与代码期望一致**，但 **mapping 全空** ⇒ 说明当年那次创建**带了 settings、没带 mappings**（某个历史版本），**而不是 ES 自动创建**（自动创建 replicas 会是 1）。**具体版本未能查明**。

### 修复与验收（含一次**我自己的错误**）

```bash
# ① 先停 mall-ai（避免"索引已删、服务还在查询"的报错窗口）
cd /data/csmall && docker compose stop mall-ai
# ② 删索引（dense_vector 的 dims 建成后不可改 → 只能删了重建）
curl -X DELETE localhost:9200/cool_shark_mall_ai
# ③ 重建 + 全量同步
docker compose up -d mall-ai
#    ★ 必须等启动完成：docker logs -f csmall-ai | grep "Started MallAiWebApiApplication"
#    ★ 再看一行 "启动自动同步完成，共 N 条商品"
```

| 验收项 | 修前 | 修后（实测） |
|---|---|---|
| `dynamic` | 未设置（= `true`） | **`false`** ✅ |
| 4 个 text 字段分词 | 4 个单字 | **`小米`/`手机`（`CN_WORD`）** ✅ |
| `brandName/categoryName/pictures/tags` | `text` | **`keyword`** ✅ |
| `semanticVector` | 不存在 | **`dense_vector` `dims=1024` `similarity=cosine`** ✅ |
| `suggestField` | `text` | **`completion` + `ik_max_word`** ✅ |
| `term brandName="小米"` | **0** | **4** ✅ |
| 补全 | 恒空 | **`prefix=小米` → 返回「小米 14」** ✅ |

> 🔴 **本次执行纠正了我自己的一处错误（方法论的教训）**：验收命令里我写的 `grep -c ik_max_word` **期望 4** 是错的 —— ① `grep -c` 数的是**行数**，而 mapping 是**单行 JSON** ⇒ 永远只返回 0/1；② 实际出现次数是 **5**（4 个 text 字段 + `suggestField` 也用 `ik_max_word`）。正确写法 `grep -o … | wc -l`。
> **教训：验收命令本身也要被验收** —— 所幸关键那条 `_analyze` 是**确定性**的，所以用户看到 "1 ≠ 4" 时没有误判。

### 修复附带风险（**修 A 会牵动 B**）

重建后 `brandName / categoryName / pictures / tags` 从 `text` 变 **`keyword`**，而 `RagServiceImpl` 的 `multiMatch` **正包含这三个字段** → 从"部分匹配"变"**整值精确匹配**"：

- **好处**：`term brandName` 过滤（原本恒 0）**开始生效**；
- **风险**：查询串若是"小米手机"，keyword 字段 `"小米"`**不再命中** → **召回可能变少**；
- ⇒ **重建后必须跟一次召回回归**。实测**未发生**：`小米手机` 8 · `小米` 4 · `手机` 7 · `华为` 3 · `笔记本` 5 · `旗舰` 3 —— **原因**：`semanticText` 里本身就写着「品牌：小米 | 分类：手机 | 标签：…」→ 品牌/分类召回由 `semanticText`（权重 3）兜住。

## 三、问题 2：#64 秒杀预热 —— **同一字段两种含义**

### 现象

12 个秒杀 SKU **只有 8 个被预热**，另外 4 个靠**凌晨 03:30 对账写的 `TTL=-1` 永久 key** 偶然兜住。

### 根因

`seckill_sku.spu_id` **存的是 `seckill_spu.id`**（前端详情 / 限购按它查），而**预热 Job 用的是 pms `spu_id`** → **二者只在"碰巧相等"时一致**。现有 6 行里 **4 行错位**。

### 为什么难发现（三条，缺一不可）

1. **"能下单"** —— 永久 key 兜住了，没人报障；
2. **只在新增 / 换批时暴露** —— 存量靠对账"擦屁股"；
3. 🔴 **用后台接口新增必然踩** —— MyBatis-Plus 会给**雪花 id** → `id ≠ spu_id` → **预热永不命中**（新数据反而比老数据更容易坏）。

### 硬约束（绕过去的做法，不是修复）

> **新增秒杀必须满足：`seckill_spu.id == seckill_sku.spu_id == pms_spu.id` 三者相等。**
> ⚠️ **不要用后台接口新增**（会给雪花 id）。

### 附带结论：Redis 预热键"哪些能手工写、哪些绝对不能"

| key | 能否手工写 | 原因 |
|---|---|---|
| `mall:seckill:sku:stock:<pmsSkuId>` | ✅ **能**（建议写） | `StringRedisTemplate`，值是**纯数字字符串** → `redis-cli SET` 兼容 |
| `mall:seckill:spu:url:rand:code:<pmsSpuId>` | ❌ **不能** | 值是 **JDK 序列化的 Integer** → 手工写格式对不上，反序列化异常 |
| `spu:bloom:filter:<today>` | ❌ **不能** | 是 Redis **SET**（不是真布隆），成员是 **JDK 序列化的 String** |

⇒ **共性认知**：**"能手工补数据"的前提是"序列化格式匹配"** —— 用 `redis-cli` 补线上 key 之前，必须先确认这个 key 是**模板写的**还是**序列化写的**。

> **状态**：**未修**（登记 TODO **#64**）。改动 = 1 个 Job（`SeckillInitialJob` 改用 `getId()`）+ 历史数据订正，涉及秒杀可用性 → **需单独窗口，按纪律不夹带**。

## 五、跨问题的共性认知与踩坑清单

1. **"能跑"≠"对"**：本例三个问题全部表现为"功能正常"（品牌过滤有兜底、补全没人用、预热靠永久 key）。
2. **判断"线上是什么"只能靠实测，而且实验要选决定性的** —— `_analyze` 是确定性的；`term` vs `match` 能区分"**数据问题**"还是"**查询问题**"（本次是后者）。
3. **先排除"最坏情况"再动手**：原方案把"IK 插件不可用"列为失败预案 → 用 `_cat/plugins` 实测排除，**否则不敢删索引重建**。
4. **反推"是谁创建的"**：用 `creation_date` + `settings 与 mapping 是否一致` 判断"历史版本写的"还是"ES 自动创建"（自动创建 replicas 会是 1）。
5. **修 A 会牵动 B**：mapping 一改，**召回语义就变了** ⇒ 修复清单里必须**自带回归项**（本次做了召回回归）。
6. **"同一字段两种含义"是设计债**：三值相等是**绕过去**，不是修复；要不要修、什么时候修，要按"**不夹带**"纪律单独决策。
7. **初始化类只创建不校验 = 漂移的水库**（`if (exists) return`）⇒ 这一类系统需要**定期核对机制**，而不是等报错。
8. **验收命令自身要经得起推敲**（`grep -c` 数单行 JSON 恒 0/1；`grep 'Caused by'` 会命中提示语文本）。

## 六、面试综述话术（贯穿本类，可直接用）

> "我最怕的不是 500，是 **200 但是错的**。这个项目里有三次同类问题，本质都是'**代码期望**和'**线上实际**'两个事实来源谁都不自动对齐：
> 一次是 ES 索引 —— 代码里写好了 `ik_max_word`、`keyword`、`dense_vector`，但线上这份索引是**更早的某个版本**建的，`mapping` 全空；初始化类又是 `if (exists) return`，所以**永不自愈**。表现是品牌过滤恒 0 命中、补全恒空、向量检索一开就废。我是靠三个**决定性实验**定的性：`_analyze` 出来 4 个单字说明 IK 没生效；`term` 打 0 而 `term .keyword` 打 4，说明**是查询打错了字段形态、数据没问题**；`_cat/plugins` 说明 IK 插件其实好好的，排除了最坏情况。修完还专门做了**召回回归**，因为 `keyword` 化会让部分匹配变成整值匹配。
> 第二次是秒杀预热 —— 同一个 `spu_id` 字段有**两套语义**（存的是 `seckill_spu.id`，预热却用 pms 的 `spu_id`），只在碰巧相等时才一致，12 个 SKU 有 4 个从来没预热过、靠对账写的永久 key 偶然兜住。这类问题的可怕之处就是'**能下单**'。
> 第三次是 MySQL 侧的实体/库/DDL 三方漂移，我单独写了一篇。
> 所以我的结论是：**这类"不报错、不自愈、只在特定路径暴露"的问题，必须靠定期核对机制去发现，不能等报错**。"
