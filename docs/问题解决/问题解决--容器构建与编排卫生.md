## 一、这一类问题的共性（★ 先看这张表）

**一句话本质**：**容器编排有很多"看不见的隐含约束"** —— 违反它们不会报错，只会**悄悄不生效**或**在特定时刻才炸**。

### 1.1 五个反复踩到的隐含约束

| # | 约束 | 后果 | 本项目实例 |
|---|---|---|---|
| ① | **单一事实源**：同一产物只能有一份 | 双份不一致 → 手动 build 时踩到旧版 | **#38**：模块目录残留 11 份 Alpine 旧 Dockerfile，与 `deploy/docker/dockerfiles/` 的正式版不一致 → 重踩 **Alpine musl 与 MD5 不兼容**的历史事故 |
| ② | **env 是容器创建时的快照** | `docker restart` **不重读 env** → "改了不生效" | 所有"改密码/改密钥/改配置"类操作都必须 `docker compose up -d` **recreate** |
| ③ | **单文件 bind mount 不能被 rename** | 需要"写临时文件 + rename"的程序（Redis/Sentinel 改写配置）**必然失败** | `CONFIG REWRITE` → `Resource busy`；哨兵必须挂**目录** |
| ④ | **挂载文件的属主必须是容器内运行用户** | 容器读不了配置 → 启动即失败 | Redis 容器内是 **uid 999**，宿主机 `ecs-user` 属主 + `chmod 600` → `Permission denied` |
| ⑤ | **`restart` 策略语义反直觉** | 宿主机重启后容器**不自动恢复** | `on-failure` **不扛** daemon 重启（只有 `unless-stopped` 扛）→ **#51** |

### 1.2 ⭐ 认知一：**"改了不生效"的四个真凶**（本类最实用的排查清单）

| 真凶 | 现象 | 判据 |
|---|---|---|
| **env 快照** | 改了 `.env`/compose 但行为没变 | 用 **`restart`** 而不是 `up -d`（recreate） |
| **中间件初始化变量** | MySQL `MYSQL_ROOT_PASSWORD`、RabbitMQ `RABBITMQ_DEFAULT_*` 改了无效 | 数据卷**已存在** → 必须运行时命令改 + 落盘 |
| **配置权威源覆盖** | 本地默认被远端空配置擦除 | Sentinel/Nacos 类（见 [[问题解决--资源治理与流量防护]]）|
| **加载时机/懒加载** | Dashboard 看不到但实际生效 | `eager` 类开关 |

### 1.3 ⭐ 认知二：**重启策略的权威语义**（2026-09-10 经官方文档核实）

[Docker 官方文档](https://docs.docker.com/engine/containers/start-containers-automatically/) 原文：
> `on-failure` **only prompts a restart if the container exits with a failure. It doesn't restart the container if the daemon restarts.**

| 策略 | 容器进程自己崩 | **宿主机 / Docker daemon 重启** | 手动 stop 后 |
|---|---|---|---|
| `no` | ❌ | ❌ **不恢复** | ❌ |
| `on-failure` | ✅（仅非零退出）| ❌ **不恢复** ← **反直觉** | ❌ |
| `unless-stopped` | ✅ | ✅ **恢复** | ❌（保持停止）|

**2.5 节有本项目的两机实测结果。**

### 1.4 认知三：**"running ≠ 可用"**

容器 `Up` 不等于服务可用 —— 验证必须看**三件事**：端口监听 + 注册中心注册 + **实际请求**。
（本项目实例：gateway 启动竞态后容器显示 running、未监听端口、未注册 Nacos）

## 三、问题 2：gateway 与 Nacos 的启动竞态（重启即愈但暴露配置缺陷）

> 原文编号：[[TODO第一批实现与原理]] §9.3


**现象**：全量重建后 gateway `Application run failed`（Nacos 注册 `Client not connected`），未监听 10087、未注册 Nacos；但因 compose 中 gateway **无 restart 策略**且 JVM 未退出，容器显示 running 实际不可用。

**根因**：gateway 重建时 Nacos 尚未完全就绪（grpc 9848 竞态），首次注册失败即整个 Spring 上下文启动失败。

**修复（两层）**：
1. 即时：`docker restart csmall-gateway`（Nacos 已稳 → 启动成功）
2. 根治：compose gateway 补 `restart: on-failure`（与 product/order/seckill 等 6 个服务对齐），`docker update --restart on-failure csmall-gateway` 即时生效 + compose 持久化

**经验**：① 依赖 Nacos 的服务重建时有启动竞态，`restart: on-failure` 是底线（gateway 之前漏了）；② 容器 "running" ≠ 服务可用，验证要看端口监听 + Nacos 注册 + 实际请求。

> ⚠️ **2026-09-10 复核（#51 现状，两机实测）**：
> - `restart` 策略在 compose 里**只给 12 个服务配了**：**11 个 `on-failure`**（老机 6：front/gateway/order/product/search/seckill；新机 5：redis-replica / 3 哨兵 / mall-seckill-2）+ **`mall-resource` 的 `unless-stopped`**。**其余 14 个服务根本没配**（mysql/redis/nacos/rabbitmq/es/seata/sentinel/skywalking-oap/skywalking-ui/mall-sso/mall-ums/mall-ams/mall-ai/frontend）。
> - 老机实测运行中 21 容器 = **6 个 `on-failure`** + **1 个 `unless-stopped`** + **14 个 `no`** → **与 compose 文件完全一致**（那 5 个多出来的 `on-failure` 属于**新机**，不在老机运行）。
> - ✅ **"#51"的含义（2026-09-10 经官方文档核实）**：`restart` 策略确实配在 compose 里（12 个服务），**但对"宿主机/Docker 重启"只有 `unless-stopped` 才有效**。[Docker 官方文档](https://docs.docker.com/engine/containers/start-containers-automatically/) 原文：**"`on-failure` only prompts a restart if the container exits with a failure. It doesn't restart the container if the daemon restarts."** → 老机重启后**只有 `csmall-resource`（`unless-stopped`）会自己回来，其余 20/21 不会**。⚠️ **我第一轮把这里写成"14/21"是错的**（只数了 `no`，漏了 `on-failure` 同样不恢复）—— 项目原记载的 **20/21 才是对的**。
> - 🔴 **新机同样中招（当时文档未记）**：新机 5 个容器**全部是 `on-failure`**（redis-replica / 3 哨兵 / mall-seckill-2）→ **新机重启后 5/5 全不恢复**。**连锁风险更严重**：从库与哨兵都不在 → 老机 Redis 主库因 `min-replicas-to-write 1` **拒绝所有写**（`NOREPLICAS`）→ 秒杀/登录 token 等全挂；且哨兵全没，无法故障转移。
> - ℹ️ 两台 `LiveRestoreEnabled=false`（老机 `daemon.json` 无该配置）→ `systemctl restart docker` 会**停掉全部容器**再按策略恢复；两台 docker 均为 `enabled`（开机自启 daemon），**没有任何 systemd 单元 / cron 兜底**（实测查过）→ 重启后必须人工 `docker compose up -d`。
> - 修法：14 个 `no` + 6 个 `on-failure` 统一改 `restart: unless-stopped`（新机 5 个同样要改），逐个 `up -d --force-recreate`（改变更窗口事项）。
> - 🔎 **顺带纠正一个容易犯的比较错误**：`deploy/docker/docker-compose.yml` 是**两机合并的单一文件**（26 服务 = 老机 21 + 新机 5），两台机器的 `/data/csmall/docker-compose.yml` 就是这同一份（实测两机容器 label 的 `config_files` 都指向它）。**拿"文件里的总数"和"某一台在跑的服务数"比会得出错误结论**——我第一轮就因此误判成"仓库 11 个 vs 服务器 6 个 = 未部署"。


### 2.5 ⚠️ 连带问题：restart 策略缺失（TODO #51，2026-09-10 两机实测复核）

上面"根治"只给 gateway 补了 `restart: on-failure` —— 但**实测发现这个策略对"宿主机重启"根本不管用**（见 §1.3 官方语义）。完整复核结果：

| 机器 | `no` | `on-failure` | `unless-stopped` | **重启后会自己回来** |
|---|---|---|---|---|
| **老机**（21 容器）| 14 | 6 | 1（`csmall-resource`）| **1/21** → 20 个不恢复 |
| **新机**（5 容器）| 0 | **5（全部）** | 0 | **0/5** → 全不恢复 |

**配置在 compose 里的分布**：只有 **12 个服务**配了 `restart`（11 个 `on-failure` + `mall-resource` 的 `unless-stopped`）；其余 **14 个服务压根没配**（`mysql`/`redis`/`nacos`/`rabbitmq`/`elasticsearch`/`seata`/`sentinel`/`skywalking-oap`/`skywalking-ui`/`mall-sso`/`mall-ums`/`mall-ams`/`mall-ai`/`frontend`）。

**🔴 新机不恢复的连锁后果（比老机更危险）**：新机跑的是 Redis 从库 + 3 哨兵 + 秒杀副本，全部 `on-failure` → 新机一重启，**从库与哨兵同时消失** → 老机 Redis 主库因 `min-replicas-to-write 1` **拒绝所有写**（`NOREPLICAS`，读仍可用）→ 秒杀/登录 token 黑名单等写入路径全挂，且哨兵全灭无法故障转移。

**其他实测事实**：两台 `LiveRestoreEnabled=false`（`systemctl restart docker` 会停掉全部容器）；两台 docker 均 `enabled`（开机会起 daemon）；**无任何 systemd 单元 / cron 兜底**（已查 `/etc/systemd/system`、`/etc/cron.d`、`/etc/crontab`）；老机已连续运行 **42 天**（2026-07-29 起）→ **从未暴露过**。

> ⚠️ **方法学说明**：两机的容器都创建于各自**本次开机之后** → **没有任何一次真实重启可供观察**，结论来自**官方语义 + 配置实测**，不是实测复现。要复现只能真重启（**绝不能裸试** —— 老机会停全站）。

**修复方案（TODO #51）**：compose 把这 **20 个**（老机 14 `no` + 6 `on-failure`）与**新机 5 个**统一改 `restart: unless-stopped` → 逐个 `up -d --force-recreate`（改策略必须 recreate；注意 ES 分片，**永远别裸跑 `up -d`**）→ 可选加 systemd unit 兜底。

> 📎 **同一问题的更早一次记录**：[[问题解决--resource容器Nacos竞态与restart缺失]]（当时 `csmall-resource` 崩溃后永久下线，实测 22 个服务只有 5 个配了 restart）。

## 五、跨问题的共性认知与踩坑清单

| 认知 / 坑 | 说明 |
|---|---|
| ⭐ **基础镜像的"隐性契约"** | `eclipse-temurin:21-jre-alpine`（musl）与 MD5/BCrypt 等算法不兼容 → **Dockerfile 必须统一到 Debian 版并作为单一事实源**；同一产物的多份副本必须清理 |
| ⭐ **删 Dockerfile 前先确认引用** | 残留版虽"零引用"（compose 全部指向正式版），但**任何人手动 `docker build` 都会重踩坑** → 清理的理由是"防未来踩坑"，不是"现在有问题" |
| ⚠️ **依赖 Nacos 的服务重建有启动竞态** | Nacos 尚未就绪（grpc 9848 竞态）→ 首次注册失败即整个 Spring 上下文启动失败。`restart: on-failure` 是底线（但对宿主机重启无效！）|
| ⚠️ **容器 "running" ≠ 服务可用** | 验证必须看：**端口监听 + Nacos 注册 + 实际请求** 三件套 |
| ⚠️ **`docker compose down` 慎用** | 本项目历史踩坑：可能损坏 ES 分片 → 优先 `up -d --remove-orphans` 或单服务 recreate |
| ⚠️ **compose 文件是"两机合并的单一文件"** | 本项目 `deploy/docker/docker-compose.yml` 含 **26 服务**（老机 21 + 新机 5，新机 5 个用 `network_mode: host`），**两台服务器的 `/data/csmall/docker-compose.yml` 就是这同一份** → **比较"某机现状"时只能看该机在跑的服务**，拿"文件里的总数"比会得出错误结论 |
| 🔑 **基础镜像要有"来源记录"** | 两台都直连不了 Docker Hub；老机配的第三方镜像站有一个**已失效**（普通 `docker pull` 会先试死站而卡死）→ 可用办法是镜像名前加可用镜像站前缀（TODO #52 记录了实测结论）|

## 六、面试综述话术（贯穿本类）

> "**容器/编排这条线我讲的是"看不见的隐含约束"**。先是**构建卫生**：我发现项目里 Dockerfile 有**两份** —— 模块目录下残留 11 份旧版（`eclipse-temurin:21-jre-alpine`），`deploy/docker/dockerfiles/` 下是 11 份正式版（Debian + 完整 JVM 参数 + SW agent）。compose 全部指向正式版，残留版**零引用**，但**任何人手动 `docker build` 都会重踩 Alpine musl 与 MD5 不兼容的坑**（历史事故）→ 我 `git rm` 掉残留版，**单一事实源 = `deploy/docker/dockerfiles/`**。
>
> 然后是**启动竞态**：全量重建后 gateway 启动失败（Nacos grpc 9848 竞态，首次注册失败即整个 Spring 上下文崩），但因为它**没有 restart 策略**、JVM 又没退出，容器显示 `running` 实际不可用 —— 这让我总结出两条经验：**① 依赖 Nacos 的服务重建时有启动竞态，`restart` 是底线；② 容器 `running` ≠ 服务可用，验证必须看"端口监听 + Nacos 注册 + 实际请求"三件套**。
>
> 而这条线最后引出一个**比集群更严重的可用性隐患**：我复核两台机器的 restart 策略，发现**只有 12 个服务配了 restart**，其余 14 个（**MySQL / Redis / Nacos / RabbitMQ / ES / Seata / Sentinel 等全部中间件**）压根没配。更关键的是我去查了 **Docker 官方文档**，确认了一个**反直觉的事实**：`on-failure` **只在容器非零退出时重启，Docker daemon 重启时不会拉起** —— 所以只有 `unless-stopped` 能扛宿主机重启。实测结果：**老机重启后只有 1/21 个容器会自己回来**（`csmall-resource`），而**新机 5 个全是 `on-failure` → 5/5 全不恢复**。新机这个连锁后果更危险：它跑的是 Redis 从库 + 3 哨兵，一重启全没 → 老机 Redis 因 `min-replicas-to-write 1` **直接拒绝所有写**。老机已经连续跑了 42 天所以从未暴露。我在文档里也诚实标注了方法学边界：**两机容器都创建于本次开机之后，没有真实重启可供观察**，所以结论来自官方语义 + 配置实测，不是实测复现 —— 要复现只能真重启，而那是绝对不能在无窗口时裸试的。"
