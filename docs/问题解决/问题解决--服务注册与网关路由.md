## 一、这一类问题的共性（★ 先看这张表）

**一句话本质**：**调用方手里那个"服务地址"是错的**。同一本质有两种形态，解法互相印证：

| 形态 | 错在哪 | 典型触发 | 本类记录 |
|---|---|---|---|
| ① **身份错** | 一个服务在注册中心**有两个身份**：HTTP 实例与 Dubbo 实例注册在**同一个服务名**下 → 网关 `lb://` 轮询会把请求打到 Dubbo 端口（非 HTTP 协议）→ 握手失败 | 部署后 Dubbo 应用名与 Spring 应用名撞名 | **问题 1**（二批 #6）|
| ② **地址过期** | 一个服务**换了 IP**（容器重建/漂移），而反向代理**只在加载配置时解析一次并永久缓存**主机名 → 一直打旧 IP | `docker compose up -d` 重建任意上游容器 | **问题 2**（2026-09-10 抢修）|

**两者共同的排查入口：先问"请求最终打到了谁"** —— 把**代理/网关日志里的 upstream 地址**与 **Nacos 实例列表 / `docker inspect` 的真实地址**对照。地址对不上，就一定是这两类之一；**别急着怀疑业务代码**。

### 1.1 症状指纹（子形态①：身份错，一眼识别）

```
网关日志: 500 Server Error for HTTP GET /seckill/spu/list
          java.lang.IllegalArgumentException: invalid version format: UNSUPPORTED
          R:172.18.0.20:20880      ← ★ 目标是 20880（Dubbo 端口），不是 HTTP 端口
```

**"时好时坏/第二次才失败"的机理**：`lb://` 是**轮询** —— 第 1 次命中 HTTP 实例（成功）、第 2 次轮到 Dubbo 端口（失败）。**不是"第二次才出问题"，是交替命中时恰好被观察到。**

### 1.2 ⭐ 关键认知：Dubbo 3.x 的**应用级注册** + 消费者按**接口**引用

| 角色 | 注册/发现方式 | 影响 |
|---|---|---|
| **Dubbo provider** | Dubbo 3.x **应用级注册** → `dubbo.application.name` 会被当作 Nacos 服务名注册 | 若它 = `spring.application.name` → **与 HTTP 实例撞名** |
| **Dubbo consumer** | 按**接口**引用（接口级注册、`providers:com.cooxiao...` group）→ **不依赖应用名** | ✅ **所以改 Dubbo 应用名不影响任何调用方**（order/ai 早就是 `*-dubbo` 独立名且全链路正常 = 现成验证）|
| **Gateway `lb://`** | 按**服务名**取全部实例轮询 | ❌ 撞名时会把 20880 也当 HTTP 端点 |

**正解 = 把两种身份拆到两个服务名下**：HTTP 实例留在 `spring.application.name`（供 gateway `lb://`），Dubbo 20880 移到 `*-dubbo`（供接口级消费发现）。

### 1.3 ⭐ 共性排查手法：**三向对照 + 按故障模式全量清查**

```
gateway 的 lb:// 路由清单  ×  Nacos 实例列表（服务名 → 实例端口）  ×  各模块 @DubboService 扫描
```

**别只修当前故障的那个模块** —— 本题就是这么做的，一次揪出 4 个模块：

| 模块 | 撞名? | 暴露 @DubboService? | 处理 |
|---|---|---|---|
| mall-seckill | ⚠️ | ✅ | ✅ 改 `mall-seckill-dubbo`（本次故障）|
| mall-ums | ⚠️ | ✅ | ✅ 改 `mall-ums-dubbo`（**潜伏隐患，一并修**）|
| mall-product | ⚠️ | ✅ | ✅ 改 `mall-product-dubbo`（**历史遗留，曾用直连 9010 规避**）|
| mall-ai / mall-order | 已分开 | ✅ | 不用动（本就是 `*-dubbo`）|
| mall-front / search / ams | ⚠️ | ❌ **无 provider** | **不用改**（不注册 20880，`lb://` 实测安全）→ 记为规范项 TODO #45 |

> 💡 **"按故障模式全量清查"比"单点修复"更有价值** —— 这是本题最值得讲的工程习惯：不是"修好了"，而是"**这个故障模式还在别处吗**"。

### 1.4 验证方式（子形态①：身份错）

- Nacos 实例列表：确认 `mall-seckill` 下**只剩 HTTP 实例**、`mall-seckill-dubbo` 下是 Dubbo 实例
- 反复访问故障接口（**要打多次**，因为轮询是交替命中）→ 0 次 500
- 全链路回归：秒杀页「商品列表 → 秒杀 → 返回 → 再进秒杀」

### 1.5 症状指纹（子形态②：地址过期）

```
nginx error log: connect() failed (111: Connection refused) while connecting to upstream,
                 upstream: "http://172.18.0.9:10087/user/sso/login"
                    ↓ 关键自问：172.18.0.9 真的是网关吗？
docker inspect csmall-gateway  → 172.18.0.7      ← 网关真实 IP
docker inspect <别的容器>       → 172.18.0.9      ← 那个 IP 早被另一个容器拿走了
容器内 getent hosts mall-gateway → 172.18.0.7     ← ★ DNS 是对的！是 nginx 缓存了旧值
```

**三个必查判据**：① 报错方是 **nginx 还是网关**（502 的来源不同，含义完全不同）；② upstream 的 IP **属于哪个容器**；③ **DNS 解析对不对**（对 → 是缓存问题，不对 → 是 DNS/网络问题）。

**确认缓存根因的杀手锏**：比对 `docker inspect <代理容器> --format '{{.State.StartedAt}}'` 与**上游容器重建的时间**——代理启动早于上游重建、且 `Restarts=0`，就必然在用旧 IP。

## 二、问题 1：秒杀页二次进入 500（Dubbo 应用名撞名，全项目修复）

> 原文编号：[[TODO第二批实现与原理]] §七·五


> **2026-09-08 晚，部署 #5 后用户实测发现**：商品列表 → 秒杀 → 商品列表 → 秒杀，**第二次进秒杀报 500**（浏览器先 404 后 500，`seckill/spu/list` 持续失败）。属于第二批部署后的**回归/隐藏 bug 排查**，快速定位并修复。

### 现象与排查链

| 步骤 | 证据 | 结论 |
|---|---|---|
| ① 看 seckill 日志 | 无 ERROR、无业务异常 | 不是应用层代码问题 |
| ② 看 gateway 日志 | **`500 Server Error for HTTP GET /seckill/spu/list` + `java.lang.IllegalArgumentException: invalid version format: UNSUPPORTED` + `R:172.18.0.20:20880`** | gateway 把请求转发到了 **Dubbo 端口 20880**(非 HTTP 协议) |
| ③ 查 Nacos 实例 | `mall-seckill` 服务下有 **2 实例: 10007(HTTP) + 20880(Dubbo)** | gateway `lb://mall-seckill` 轮询,一半请求打到 Dubbo 端口 |
| ④ 对照代码 | seckill `dubbo.application.name` = `mall-seckill` = spring 名(**撞名**);order 用 `mall-order-dubbo`(分开,安全) | **根因 = TODO #6 同类问题,发生在 mall-seckill** |

**"第一次成功、第二次 500"的机理**：gateway 的 `lb://` 是**轮询负载均衡**——第 1 次请求路由到 10007(HTTP 成功),第 2 次轮到 20880(Dubbo,非 HTTP 协议握手失败 → 500)。不是"第二次才出问题",是**交替命中**时用户恰好观察到失败。

### 全项目排查(不止修一个)

gateway `lb://` 路由 × Nacos 实例列表 × `@DubboService` 扫描三向对照,揪出全部"暴露 Dubbo + 撞名"模块:

| 模块 | 撞名? | 暴露 @DubboService? | 处理 |
|---|---|---|---|
| mall-seckill | ⚠️ | ✅ (ForOrderSeckillRecord) | ✅ 改 `mall-seckill-dubbo` |
| mall-ums | ⚠️ | ✅ (UserServiceImpl) | ✅ 改 `mall-ums-dubbo`(潜伏隐患,一并修) |
| mall-product | ⚠️ | ✅ (7 个 service) | ✅ 改 `mall-product-dubbo`(原 #6 主角,曾用直连 9010 规避) |
| mall-ai / mall-order | 已分开 | ✅ | 不用动(本就是 `*-dubbo`) |
| mall-front/search/ams | ⚠️ | ❌ **无 provider** | **不用改**(不注册 20880,Nacos 实测仅 HTTP 实例,lb:// 安全)→ 统一规范入 TODO #45(第三批) |

### 为什么改注册名不影响调用方(关键认知)

Dubbo 消费者按**接口**引用(`providers:com.cooxiao.mall.product.*` 接口级注册),**不依赖应用名**——order/ai 早就是 `*-dubbo` 独立名且全链路正常,是现成验证。改名只影响 Nacos 里"服务名 → 实例"的组织:HTTP 实例留在 spring 名下(供 gateway lb://),Dubbo 20880 移到 `*-dubbo` 名下(供接口级消费发现)。

### 面试话术

"部署后用户反馈秒杀页第二次进入 500——排查 gateway 日志发现 `invalid version format: UNSUPPORTED` 且目标是 **20880 端口**,立刻明白是 `lb://` 轮询把请求打到了 Dubbo 端口。根因是 **Dubbo 应用名与 Spring 应用名撞名**,Dubbo 3.x 应用级注册把 20880 混进服务名。我做的不只是修 seckill,而是**全项目排查**:gateway lb:// 路由 × Nacos 实例 × @DubboService 三向对照,发现 ums 也撞名且有 provider(潜伏隐患)一并修,product 是历史遗留(曾用直连规避)也根治;front/search/ams 虽撞名但无 provider 不构成风险,记为规范项防未来踩坑。这个排查思路——'不只是修当前故障,而是按故障模式全量清查'——比单点修复更有价值。"

## 三、问题 2：nginx 静态解析上游 IP —— 网关重建后全站 API 502（2026-09-10 抢修）

> 与问题 1 **同一族**：调用方持有了服务的错误地址。问题 1 是"**身份错**"（把 Dubbo 端口当成 HTTP 端点），本题是"**地址过期**"（容器重建换了 IP，代理仍打旧 IP）。**用户侧现象都是"页面/接口挂了"，但根因层完全不同。**

### 现象

用户反馈整站登录失败，浏览器控制台一片 502：

```
POST http://8.156.77.197/user/sso/login   → 502 Bad Gateway
GET  /front/category/all                  → 502
GET  /front/category/all: 服务器错误 502
```

### 排查链（每一步都排除掉一种可能，**不猜**）

| 步骤 | 命令 / 证据 | 结论 |
|---|---|---|
| ① 服务是不是挂了？ | `docker ps` → **21 容器全 Up**；`docker ps -a` 无 Exited/Restarting | ❌ 不是容器挂了 |
| ② 资源是不是打满？ | `free -m` 15G 用 11.4G / `df -h` 53% / load 1.5 | ❌ 不是资源问题 |
| ③ 网关自身健康吗？ | `curl 127.0.0.1:10087/actuator/health` → **200** | ✅ 网关活着且健康 |
| ④ **502 是谁报的？** | `docker logs csmall-frontend` → `connect() failed (111: Connection refused) while connecting to upstream`，upstream = **`http://172.18.0.9:10087`** | ⭐ 是 **nginx** 报的，不是网关 |
| ⑤ `172.18.0.9` 是谁？ | `docker inspect` → gateway = **172.18.0.7**；**172.18.0.9 = mall-ai**（当天刚重建拿到这个 IP） | ⭐ nginx 把请求打到了**错的容器**（10087 上没人监听 → 连接被拒）|
| ⑥ nginx 里写的是什么？ | conf 里是**主机名** `proxy_pass http://mall-gateway:10087`；容器内 `getent hosts mall-gateway` → **172.18.0.7（正确）** | ⭐ **DNS 是对的** → 问题在 nginx 自己 |
| ⑦ 为什么还在打旧 IP？ | frontend StartedAt = **09-08 04:14 UTC**、`Restarts=0`；gateway StartedAt = **09-09 11:22 UTC** | ⭐ nginx **只在加载配置时**解析主机名一次并**永久缓存** |

**故障窗口**：网关在 **09-09 19:22(CST)** 被重建（IP 由 `.9` → `.7`），nginx 从那一刻起一直打 `.9`，直到 **09-10 19:58** 修复 —— **静默坏了约 24.5 小时**。
（⚠️ 这本身就是**第二个问题**：内部 healthcheck 拦不住这类故障 —— 21 容器全 Up、网关自身健康检查 200，业务却全挂 → 衍生 TODO **#61 外部探活监控**。）

### 根因

`proxy_pass http://<主机名>:<端口>` 里的主机名，nginx **只在配置加载那一刻**解析一次，之后**永不重解析** —— 效果**等价于写死 IP**。
容器化环境里"容器重建 → 换 IP"是常态，于是"写主机名"给人的安全感是**假的**：它只在"代理比上游先起、且此后上游永不重建"时才成立。

### 修复（先恢复、再根治，抢修不夹带）

1. **立即恢复**：`docker restart csmall-frontend` → nginx 重新解析 → **秒级恢复**（不改配置、不动数据、随时可重复）
2. **隔离验证**（新建临时网络 + 一次性容器，**全程不碰生产**）做 A/B：

   | 场景 | 动态解析 | 静态解析（= 生产原状） |
   |---|---|---|
   | 基线（目标容器在位） | 200 | 200 |
   | **模拟容器重建后**（旧 IP 被占位容器接管，新目标在新 IP） | **200 OK（自动跟随）** | **502（仍打旧 IP）** ← 精确复现本次故障 |

   过程中还白捡两次实证：① 静态写法在**启动时**解析不到主机名 → `host not found in upstream` **直接起不来**；② 我最初拿生产镜像当测试目标，而它镜像里烧的 conf 依赖 `mall-gateway`，在隔离网络里解析不到 → **nginx 根本没起来**（同一类脆弱性的又一次现形）。
3. **生产改造**（**URI 语义零变化**）：

   ```nginx
   resolver 127.0.0.11 valid=10s ipv6=off;     # Docker 内嵌 DNS
   upstream mall_gateway {
       zone mall_gateway 64k;                   # resolve 需配合 zone
       server mall-gateway:10087 resolve;       # 每 10s 重新解析，不再依赖重启 nginx
   }
   # 6 处 proxy_pass：http://mall-gateway:10087 → http://mall_gateway
   ```

   ⚠️ **刻意不用 `set $gw mall-gateway:10087; proxy_pass http://$gw;` 变量法**：用了变量后 nginx 的 URI 处理语义会变（不再做 URI 规范化、与 `rewrite ... break` 的交互不同），而本项目有 `/api/xxx/ → 剥前缀转发` 的 rewrite location —— **只有 `upstream` 块能保证语义与改造前完全一致**。
   ⚠️ **`resolve` 是 nginx ≥ 1.27.3 才在 OSS 版开放**（当前容器 1.31.5 ✓）；若把基础镜像退回旧版本会**语法错误起不来** → 部署前必跑 `nginx -t`。
4. **应用方式**：`docker cp` → `nginx -t` → **`nginx -s reload`**（热加载、**零停机**、不重启容器）
5. **烘进镜像**：先把旧镜像打 `csmall-frontend:pre-dynamic-20260910` 标签（回滚点），再 `docker commit` 把新 conf 烘进镜像 —— 因为服务器上**没有 `nginx:alpine` 基础镜像**（`docker compose build` 短期不可用），不 commit 的话"下次容器重建就回退"。

### 验证（**逐条路由**，不是"能打开就行"）

| 验证项 | 结果 |
|---|---|
| `POST /user/sso/login` | 返回真实 `tokenValue` ✓ |
| `GET /api/front/category/all`（**rewrite 剥前缀路径**） | `{"state":401,...}` ✓ **URI 语义未变**（这正是变量法会踩坏的地方）|
| `GET /admin/dashboard`（Accept: json → `@gateway` 命名 location） | 正确走网关 ✓ |
| `/ai/chat/history`、`/seckill/spu/list`、SPA `/` | 200 ✓ |
| **nginx 错误日志** | 无 `[error]/[emerg]/[crit]` ✓ |
| **镜像内 conf md5** | = 修复版 `9ce6f00d…`（不是旧版 `8bdd4cd2…`）✓ |
| 终态 | **21 容器全 Up、0 异常** ✓ |

### 附带发现（同一族的下一个雷，已单独立项）

排查中发现**前端 nginx conf 与仓库副本双向漂移**：本地那份（被 `.gitignore` 的 `deploy/` 忽略、**未入库**、8/1 16:55）比**服务器现行版**（8/1 23:15，多 `@gateway` + `/admin/dashboard` 路由）**旧**，却多了两块生产没有的内容：

- **SSE `proxy_read_timeout/proxy_send_timeout 180s`**（预防性：思考模式下 reasoning 分片被刻意忽略 → 模型"闷头思考"期间 nginx 收不到字节 → 默认 60s 无数据即被掐断。当前 0 次实际发生）
- **`location ~ ^/seckill/?\d*$`**（`/seckill/:id` 页面刷新的 SPA 保护 —— **生产现在确实坏**：`GET /seckill/123` 返回 `{"state":401,"message":"您没有登录！"}` JSON，而不是秒杀详情页）

根因是 **conf 不在版本控制里**（`deploy/` 被 ignore）→ 已 `git add -f deploy/docker/frontend/nginx.conf` 纳入跟踪。

**✅ 两块差异的处理（用户 2026-09-10 决策：合并并上生产）**：

| 块 | 处置 | 验证证据 |
|---|---|---|
| **② `/seckill/:id` SPA 保护** | ✅ **已合并上线** | 合并前 `GET /seckill/123` → `{"state":401,...}` JSON（页面刷新看到 JSON）；合并后 → **`text/html`** ✓ 且 `/seckill/spu/list`、`/seckill/sku/list/1`、`POST /seckill/{code}` **全部仍走网关 JSON**（真 API 未被吃掉）✓ |
| **① SSE 180s** | ✅ **已合并上线**（预防性）| `nginx -T` 显示 SSE location 内 `proxy_read_timeout 180s` ✓；当前生产 **0 次**实际超时记录 |

合并方式仍是"**先隔离校验 → `docker cp` + `nginx -t` + `nginx -s reload` 零停机 → 逐条路由回归**"，并二次 `docker commit` 烘进镜像（回滚点 `dynamic-only-20260910`）。**关键教训：抢修与"顺手发现的改进"分两次上，每次都能独立回滚。**

### 面试话术（问题 2）

> "用户报整站登录 502。我没急着改配置，先**逐层排除**：容器全 Up → 不是挂了；内存/磁盘/负载正常 → 不是资源；`curl` 网关健康检查 **200** → 网关是好的。第四步看 nginx 日志，`connect() failed (111) while connecting to upstream http://172.18.0.9:10087` —— 关键一问：**172.18.0.9 是网关吗**？`docker inspect` 一查，网关是 `172.18.0.7`，而 `172.18.0.9` 是当天刚重建的 **mall-ai**。可 conf 里明明写的是主机名 `mall-gateway`，容器内 `getent hosts` 也解析正确 —— 所以根因是 **nginx 只在加载配置时解析一次主机名并永久缓存，等价于写死 IP**；网关容器一天前重建换了 IP，nginx 却一直打旧 IP，**静默坏了 24 小时没人发现**。
>
> 修复我分了三步：先 `docker restart frontend` **秒级恢复**；再在**隔离网络**里用一次性容器做 A/B —— 容器重建后动态解析 200、静态解析 502，**先证明方案再动生产**；然后改成 `resolver + upstream ... resolve` 动态解析。这里有个细节我很在意：我**没有用** `set $var` 的变量写法，因为那会改变 nginx 的 URI 处理语义，而我们有一个 `/api/ 剥前缀` 的 rewrite location —— 用 `upstream` 块才能保证语义零变化，改完我逐条路由验证过。最后 `nginx -t` + `nginx -s reload` **零停机**生效，并把 conf `docker commit` 进镜像防止下次重建回退。
>
> 事后我把'**21 个容器全 Up、网关健康检查还是 200，业务却全挂了 24 小时**'单独记成一条待办：**内部 healthcheck 抓不到这类故障，必须有外部端到端探活**。"

## 四、跨问题的共性认知与踩坑清单

| 认知 / 坑 | 说明 |
|---|---|
| ⭐ **Dubbo 应用名 ≠ Spring 应用名** | 两者相同 = 把 RPC 端口暴露进网关的服务发现列表。**规范：`dubbo.application.name` 一律加 `-dubbo` 后缀** |
| ⭐ **改注册名不影响调用方** | Dubbo 消费者按**接口**引用（接口级注册），不依赖应用名 → 改名是**安全操作**（order/ai 早就这么干且全链路正常）|
| ⭐ **"无 provider 就不用改"** | front/search/ams 虽撞名但不暴露 `@DubboService`、不注册 20880 → `lb://` 实测安全。**判据是"是否注册了 RPC 实例"，不是"名字是否相同"** |
| ⚠️ **间歇性故障先怀疑轮询** | "时好时坏""第二次才失败" = 多实例轮询命中了坏实例，**不是**偶发/随机 bug |
| ⚠️ **端口是故障指纹** | 网关日志里出现 `20880`（或任何 RPC 端口）= 协议不匹配，而不是业务异常 |
| 🔑 **同类风险面** | 任何"同一进程同时提供 HTTP + RPC"的服务都要检查：Nacos 服务名下是否混入了 RPC 实例 |
| ⭐ **写主机名 ≠ 地址不会变（问题 2）** | nginx `proxy_pass http://<主机名>` 只在**配置加载时**解析一次并永久缓存 = 等价写死 IP。容器化环境必须显式 `resolver` + `upstream ... resolve`（或改配置后 reload/重启代理）|
| ⭐ **502/504 先定位"谁报的"（问题 2）** | nginx 报 502 = "连不上上游"；网关报 502 = "上游返回了错"。**先看谁的日志、upstream 指向哪个 IP/容器**，再谈根因 |
| ⭐ **"进程活着" ≠ "链路活着"（问题 2）** | 21 容器全 Up、网关自身 `/actuator/health` = 200，业务仍可能全挂 24 小时 → 必须有**外部端到端探活**（TODO #61 ⇒ ✅ 已于 2026-09-12 上线：新机 cron 每 5 分钟、9/9 PASS）|
| ⚠️ **改 nginx 上游别用变量法（问题 2）** | `proxy_pass http://$var` 会改变 URI 处理语义（与 `rewrite ... break` 交互不同）→ 用 `upstream + resolve` 才能语义零变化 |
| ⭐ **抢修纪律：不夹带（问题 2）** | 抢修只做"恢复到原行为 + 一类根因修复"；顺手发现的其他差异（两块漂移配置）**单独决策、单独验证**，否则抢修本身变成新的风险源 |

## 五、面试综述话术（贯穿本类）

> **本类两个形态一句话对比（面试可直接用）**：问题 1 是"**服务的身份错了**"（Dubbo 端口混进 HTTP 服务名 → 网关轮询打到 RPC 端口）；问题 2 是"**服务的地址过期了**"（容器重建换 IP，nginx 缓存旧 IP 永不重解析）。两者的排查入口完全一致 —— **先问"请求最终打到了谁"，再把代理日志里的地址与注册中心/容器的真实地址对照**；也都不该先怀疑业务代码。

> "部署后用户反馈**秒杀页第二次进入报 500**。我第一步看 seckill 日志 —— 没有 ERROR、没有业务异常，说明不是应用层代码问题；第二步看网关日志，看到 `500 Server Error for HTTP GET /seckill/spu/list` + `IllegalArgumentException: invalid version format: UNSUPPORTED`，而且目标端口是 **20880** —— 我立刻明白网关把 HTTP 请求打到了 **Dubbo 端口**。查 Nacos 发现 `mall-seckill` 服务下有**两个实例：10007（HTTP）+ 20880（Dubbo）**，网关 `lb://` 轮询时一半请求会打到 Dubbo 端口；根因是 **Dubbo 应用名与 Spring 应用名撞名**（Dubbo 3.x 是应用级注册，把 20880 混进了服务名）—— 这也解释了为什么是"第一次成功、第二次 500"：**不是第二次才出问题，是交替命中**。
>
> 我做的不只是修 seckill，而是**按故障模式做了全项目清查**：用「gateway 的 `lb://` 路由 × Nacos 实例列表 × `@DubboService` 扫描」三向对照，发现 **mall-ums 也撞名且有 provider（潜伏隐患）**一并修了、**mall-product 是历史遗留**（曾用直连端口规避）也根治；front/search/ams 虽撞名但**无 provider 不构成风险**，记为规范项防未来踩坑。关键认知是 **Dubbo 消费者按接口引用、不依赖应用名**，所以改注册名完全安全 —— order/ai 早就是 `*-dubbo` 独立名且全链路正常，就是现成的验证。"
