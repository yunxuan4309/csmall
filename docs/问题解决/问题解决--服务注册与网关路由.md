## 一、这一类问题的共性（★ 先看这张表）

**一句话本质**：**一个服务在注册中心"有两个身份"** —— HTTP 实例和 Dubbo 实例注册在**同一个服务名**下，网关 `lb://` 轮询时会把请求打到 Dubbo 端口（非 HTTP 协议）→ 握手失败。

### 1.1 症状指纹（一眼识别这类问题）

```
网关日志: 500 Server Error for HTTP GET /seckill/spu/list
          java.lang.IllegalArgumentException: invalid version format: UNSUPPORTED
          R:172.18.0.20:20880      ← ★ 目标是 20880（Dubbo 端口），不是 HTTP 端口
```

**"时好时坏/第二次才失败"的机理**：`lb://` 是**轮询** —— 第 1 次命中 HTTP 实例（成功）、第 2 次轮到 Dubbo 端口（失败）。**不是"第二次才出问题"，是交替命中时恰好被观察到。**

### 1.2 ⭐ 关键认知：Dubbo 3.x 的**应用级注册** + 消费者按**接口**引用

| 角色 | 注册/发现方式 | 影响 |
|---|---|---|
| **Dubbo provider** | Dubbo 3.x **应用级注册** → `dubbo.application.name` 会被当作 Nacos 服务名注册 | 若它 = `spring.application.name` → **与 HTTP 实例撞名** |
| **Dubbo consumer** | 按**接口**引用（接口级注册、`providers:com.cooxiao...` group）→ **不依赖应用名** | ✅ **所以改 Dubbo 应用名不影响任何调用方**（order/ai 早就是 `*-dubbo` 独立名且全链路正常 = 现成验证）|
| **Gateway `lb://`** | 按**服务名**取全部实例轮询 | ❌ 撞名时会把 20880 也当 HTTP 端点 |

**正解 = 把两种身份拆到两个服务名下**：HTTP 实例留在 `spring.application.name`（供 gateway `lb://`），Dubbo 20880 移到 `*-dubbo`（供接口级消费发现）。

### 1.3 ⭐ 共性排查手法：**三向对照 + 按故障模式全量清查**

```
gateway 的 lb:// 路由清单  ×  Nacos 实例列表（服务名 → 实例端口）  ×  各模块 @DubboService 扫描
```

**别只修当前故障的那个模块** —— 本题就是这么做的，一次揪出 4 个模块：

| 模块 | 撞名? | 暴露 @DubboService? | 处理 |
|---|---|---|---|
| mall-seckill | ⚠️ | ✅ | ✅ 改 `mall-seckill-dubbo`（本次故障）|
| mall-ums | ⚠️ | ✅ | ✅ 改 `mall-ums-dubbo`（**潜伏隐患，一并修**）|
| mall-product | ⚠️ | ✅ | ✅ 改 `mall-product-dubbo`（**历史遗留，曾用直连 9010 规避**）|
| mall-ai / mall-order | 已分开 | ✅ | 不用动（本就是 `*-dubbo`）|
| mall-front / search / ams | ⚠️ | ❌ **无 provider** | **不用改**（不注册 20880，`lb://` 实测安全）→ 记为规范项 TODO #45 |

> 💡 **"按故障模式全量清查"比"单点修复"更有价值** —— 这是本题最值得讲的工程习惯：不是"修好了"，而是"**这个故障模式还在别处吗**"。

### 1.4 验证方式

- Nacos 实例列表：确认 `mall-seckill` 下**只剩 HTTP 实例**、`mall-seckill-dubbo` 下是 Dubbo 实例
- 反复访问故障接口（**要打多次**，因为轮询是交替命中）→ 0 次 500
- 全链路回归：秒杀页「商品列表 → 秒杀 → 返回 → 再进秒杀」

## 二、问题 1：秒杀页二次进入 500（Dubbo 应用名撞名，全项目修复）

> 原文编号：[[TODO第二批实现与原理]] §七·五


> **2026-09-08 晚，部署 #5 后用户实测发现**：商品列表 → 秒杀 → 商品列表 → 秒杀，**第二次进秒杀报 500**（浏览器先 404 后 500，`seckill/spu/list` 持续失败）。属于第二批部署后的**回归/隐藏 bug 排查**，快速定位并修复。

### 现象与排查链

| 步骤 | 证据 | 结论 |
|---|---|---|
| ① 看 seckill 日志 | 无 ERROR、无业务异常 | 不是应用层代码问题 |
| ② 看 gateway 日志 | **`500 Server Error for HTTP GET /seckill/spu/list` + `java.lang.IllegalArgumentException: invalid version format: UNSUPPORTED` + `R:172.18.0.20:20880`** | gateway 把请求转发到了 **Dubbo 端口 20880**(非 HTTP 协议) |
| ③ 查 Nacos 实例 | `mall-seckill` 服务下有 **2 实例: 10007(HTTP) + 20880(Dubbo)** | gateway `lb://mall-seckill` 轮询,一半请求打到 Dubbo 端口 |
| ④ 对照代码 | seckill `dubbo.application.name` = `mall-seckill` = spring 名(**撞名**);order 用 `mall-order-dubbo`(分开,安全) | **根因 = TODO #6 同类问题,发生在 mall-seckill** |

**"第一次成功、第二次 500"的机理**：gateway 的 `lb://` 是**轮询负载均衡**——第 1 次请求路由到 10007(HTTP 成功),第 2 次轮到 20880(Dubbo,非 HTTP 协议握手失败 → 500)。不是"第二次才出问题",是**交替命中**时用户恰好观察到失败。

### 全项目排查(不止修一个)

gateway `lb://` 路由 × Nacos 实例列表 × `@DubboService` 扫描三向对照,揪出全部"暴露 Dubbo + 撞名"模块:

| 模块 | 撞名? | 暴露 @DubboService? | 处理 |
|---|---|---|---|
| mall-seckill | ⚠️ | ✅ (ForOrderSeckillRecord) | ✅ 改 `mall-seckill-dubbo` |
| mall-ums | ⚠️ | ✅ (UserServiceImpl) | ✅ 改 `mall-ums-dubbo`(潜伏隐患,一并修) |
| mall-product | ⚠️ | ✅ (7 个 service) | ✅ 改 `mall-product-dubbo`(原 #6 主角,曾用直连 9010 规避) |
| mall-ai / mall-order | 已分开 | ✅ | 不用动(本就是 `*-dubbo`) |
| mall-front/search/ams | ⚠️ | ❌ **无 provider** | **不用改**(不注册 20880,Nacos 实测仅 HTTP 实例,lb:// 安全)→ 统一规范入 TODO #45(第三批) |

### 为什么改注册名不影响调用方(关键认知)

Dubbo 消费者按**接口**引用(`providers:com.cooxiao.mall.product.*` 接口级注册),**不依赖应用名**——order/ai 早就是 `*-dubbo` 独立名且全链路正常,是现成验证。改名只影响 Nacos 里"服务名 → 实例"的组织:HTTP 实例留在 spring 名下(供 gateway lb://),Dubbo 20880 移到 `*-dubbo` 名下(供接口级消费发现)。

### 面试话术

"部署后用户反馈秒杀页第二次进入 500——排查 gateway 日志发现 `invalid version format: UNSUPPORTED` 且目标是 **20880 端口**,立刻明白是 `lb://` 轮询把请求打到了 Dubbo 端口。根因是 **Dubbo 应用名与 Spring 应用名撞名**,Dubbo 3.x 应用级注册把 20880 混进服务名。我做的不只是修 seckill,而是**全项目排查**:gateway lb:// 路由 × Nacos 实例 × @DubboService 三向对照,发现 ums 也撞名且有 provider(潜伏隐患)一并修,product 是历史遗留(曾用直连规避)也根治;front/search/ams 虽撞名但无 provider 不构成风险,记为规范项防未来踩坑。这个排查思路——'不只是修当前故障,而是按故障模式全量清查'——比单点修复更有价值。"

## 三、跨问题的共性认知与踩坑清单

| 认知 / 坑 | 说明 |
|---|---|
| ⭐ **Dubbo 应用名 ≠ Spring 应用名** | 两者相同 = 把 RPC 端口暴露进网关的服务发现列表。**规范：`dubbo.application.name` 一律加 `-dubbo` 后缀** |
| ⭐ **改注册名不影响调用方** | Dubbo 消费者按**接口**引用（接口级注册），不依赖应用名 → 改名是**安全操作**（order/ai 早就这么干且全链路正常）|
| ⭐ **"无 provider 就不用改"** | front/search/ams 虽撞名但不暴露 `@DubboService`、不注册 20880 → `lb://` 实测安全。**判据是"是否注册了 RPC 实例"，不是"名字是否相同"** |
| ⚠️ **间歇性故障先怀疑轮询** | "时好时坏""第二次才失败" = 多实例轮询命中了坏实例，**不是**偶发/随机 bug |
| ⚠️ **端口是故障指纹** | 网关日志里出现 `20880`（或任何 RPC 端口）= 协议不匹配，而不是业务异常 |
| 🔑 **同类风险面** | 任何"同一进程同时提供 HTTP + RPC"的服务都要检查：Nacos 服务名下是否混入了 RPC 实例 |
