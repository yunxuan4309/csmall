> 日期：2026-08-01
> 影响功能：秒杀专区、订单取消、管理员后台（仪表盘/系统管理/商品管理/分类管理）
> 涉及模块：mall-seckill、mall-order、mall-sso、mall-gateway-server、mall-common、nginx、mall-product

---

## 一、秒杀"已购买"标记取消后无法清除

### 现象

秒杀商品后取消订单，秒杀专区仍显示"已购买"，无法重新秒杀。

### 根因

原始代码在 `OmsOrderServiceImpl.clearSeckillCheck()` 中存在三个叠加 bug：

1. **Redis key 前缀不一致**：删除时手工拼接 `seckill:reseckill:`，缺少 `mall:` 前缀。写入/检查均通过 `PrefixConfiguration.SECKILL_RE_SECKILL_PREFIX`（值为 `mall:seckill:reseckill:`）
2. **SEK 守卫永远不成立**：方法入口 `if (!o.getSn().startsWith("SEK")) return;`，所有订单 SN 均为 UUID，条件恒为 true，方法直接返回
3. **方法缺失闭合括号**：语法错误导致编译失败

### 解决方案

重构整体设计，引入三把独立的 Redis key：

| Key | 前缀 | TTL | 用途 |
|-----|------|-----|------|
| 下单锁 | `mall:seckill:order:lock:{skuId}:{userId}` | 1 分钟 | `setIfAbsent` 防双击 |
| 下单标记 | `mall:seckill:ordered:{skuId}:{userId}` | 2 小时 | 防重复未支付订单 |
| 购买标记 | `mall:seckill:reseckill:{skuId}:{userId}` | 永久 | `isPurchased` 检查 |

生命周期：

```
秒杀成功 → SET order:lock(1min) + SET ordered(2h)
取消订单 → DEL ordered + DEL order:lock → 可重新秒杀
支付成功 → SET reseckill(永久) + DEL ordered → isPurchased=true
删除订单 → DEL ordered + DEL order:lock → 可重新秒杀
2h不支付 → ordered 自动过期 → 可重新秒杀
```

### 改动文件

- `mall-common/.../PrefixConfiguration.java` — 新增 `SECKILL_ORDER_LOCK_PREFIX`、`SECKILL_ORDERED_PREFIX`
- `mall-seckill/.../SeckillCacheUtils.java` — 新增 `getOrderLockKey()`、`getOrderedKey()`
- `mall-seckill/.../SeckillServiceImpl.java` — `commitSeckill` 重构为三把 key 分离
- `mall-order/.../OmsOrderServiceImpl.java` — 新增 `markSeckillPurchased()`、`clearSeckillOrdered()`

## 二、秒杀错误提示带"发生异常"前缀

### 现象

重复购买时提示 "发生异常:错误信息为:您已经购买过这个商品了,谢谢您的支持"

### 根因

`SeckillController` 的 `@SentinelResource(fallbackClass = SeckillFallback.class)` 将所有异常（包括业务异常 `CoolSharkServiceException`）路由到 `SeckillFallback.seckillFallback()`，该方法硬编码了 `"发生异常:错误信息为:" + e.getMessage()` 前缀。

### 解决方案

`SeckillFallback.java` — 直接透传 `e.getMessage()`，空消息时兜底为"秒杀服务繁忙，请稍后再试"。

## 三、MQ 消费者重复插入 success 表报错

### 现象

取消订单后重买同一商品，`SeckillQueueConsumer` 报 `Duplicate entry for key 'success.uk_sku_user'`，MQ 消息重试耗尽后丢失。

### 根因

`success` 表有唯一约束 `uk_sku_user(user_id, sku_id)`，取消重买时旧记录未删除，普通 `INSERT` 冲突。

### 解决方案

`SuccessMapper.xml` — `INSERT INTO` 改为 `REPLACE INTO`。MySQL 的 REPLACE 在命中唯一约束时自动删旧插新。

### 副作用

`REPLACE INTO` 在命中唯一约束时会删除旧行再插入，`gmt_create` 会刷新为当前时间。MyBatis-Plus 自动填充 `gmt_create`/`gmt_modified` 与 REPLACE INTO 兼容（不影响语法），但不可与 `ON DUPLICATE KEY UPDATE` 的 `values()` 函数同时使用（自动填充会注入额外参数导致 SQL 语法错误）。

## 四、管理员后台 SPA 刷新白屏

### 现象

在管理员端任意子页面刷新（F5）后显示 `Whitelabel Error Page (type=Not Found, status=404)`。

### 根因

nginx 配置中 `^/(admin|sso|...)/` 正则将所有 `/admin/` 开头的 GET 请求均转发至 Gateway。浏览器刷新 `/admin/dashboard` 这类 SPA 页面时，Gateway 收到后找不到对应接口返回 404。

### 解决方案

`nginx.conf` 新增 3 条规则：

1. **Admin SPA 保护** — `^/admin/(?!dashboard)` 匹配的 GET 请求直接返回 `index.html`
2. **Dashboard API 兼容** — 精确匹配 `= /admin/dashboard`，使用 `error_page 418 = @gateway` 技巧绕过 nginx `if` 中 `proxy_set_header` 的限制，根据 `Accept` 头区分 API 调用（`application/json`）与页面刷新（`text/html`）
3. **`/api/ams/` 前缀支持** — 前端部分接口（如 `/api/ams/admin/list`）带 `/api/` 前缀，nginx 剥离后转发 Gateway

## 五、管理员后台权限缺失

### 现象

登录管理员后，"系统管理"下所有子菜单报 `Access Denied`，"商品管理"下品牌管理正常但分类/商品列表报 500。

### 根因

1. **权限数据缺失** — 服务器 `ams_permission` 表缺少 `/ams/admin/read` 等权限条目，且 `ams_role_permission` 未关联
2. **表字段缺失** — `ams_permission` 缺少 `value` 列，`pms_brand` 缺少 `pinyin`、`sales`、`enable` 等 8 列

### 解决方案

- 插入缺失权限 + 关联 SUPER_ADMIN 角色
- ALTER TABLE 补全缺失列
- SSO 重启后重新登录获取新 Token（Token 内包含完整权限）

## 六、分类管理/商品列表 500 错误（Nacos 双注册）

### 现象

分类管理始终 500，商品列表随机 500（第一次可能成功，切换页面后失败）。

### 根因

`mall-product` 在 Nacos 中同时注册了 **HTTP 9010**（Spring Cloud）和 **Dubbo 20880**（RPC）两个实例。Gateway 的 `lb://mall-product` 负载均衡可能选中 Dubbo 端口，收到非 HTTP 二进制数据后报 `HttpResponseDecoder` 解析错误。

### 解决方案

`mall-gateway-server/application-prod.yml` — `/pms/**` 路由从 `lb://mall-product` 改为 `http://mall-product:9010` 直连。

> 其余服务（mall-front/order/search/seckill/sso/ams/ums/resource/ai）不受影响，因为它们要么不注册 Dubbo 端口，要么只作为 Dubbo Consumer。

## 七、仪表盘今日销售额为 0

### 现象

已支付订单但仪表盘"今日销售额"、"今日订单数"始终为 0。

### 根因（两层）

1. **SQL 字段错误** — `DashboardController` 中使用 `DATE(gmt_create) = CURDATE()` 过滤今日订单，但 `gmt_create` 是下单时间而非支付时间。正确应使用 `gmt_pay`
2. **生产环境缺少 order 数据源** — `application-prod.yml` 只配置了 `admin` 和 `user` 两个数据源，缺少 `order` 数据源。`orderJdbcTemplate` 初始化失败导致 `queryForMap` 抛异常被静默吞掉

### 解决方案

- `DashboardController.java` — `gmt_create` → `gmt_pay`（今日订单 + 近 7 天趋势共 2 处）
- `application-prod.yml` — 新增 `order` 数据源
- `docker-compose.yml` — SSO 服务新增 `SPRING_DATASOURCE_ORDER_JDBC_URL` 环境变量
