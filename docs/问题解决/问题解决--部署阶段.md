# CoolShark Docker 容器化部署 — 踩坑记录与问题解决方案

> 部署日期：2026-07-29 ~ 2026-07-30
> 服务器：阿里云 ECS 4C16G (Ubuntu 24.04)，公网 IP: 8.156.77.197
> 部署方式：Docker Compose 编排 20 个容器（8 中间件 + 11 微服务 + 1 前端 Nginx）

---

## 一、核心架构矛盾：`my.server.addr` 变量复用

### 1.1 问题背景

项目原始设计为 systemd 单机部署，所有服务共用 `application-prod.yml` 中的一个变量：

```yaml
my:
  server:
    addr: ${ALIYUN_SERVER_IP:127.0.0.1}
```

这个变量在单机部署下指向 `127.0.0.1`，所有中间件也都在同一台机器上，相安无事。

迁移到 Docker 后，每个中间件和服务都有独立的容器 hostname（`mysql`、`redis`、`nacos`、`rabbitmq`、`elasticsearch`、`seata`、`sentinel`），一个 IP 地址无法同时指向 7 个不同的容器。

### 1.2 影响范围

`my.server.addr` 被以下 7 类配置引用：

| 配置项 | 原始值 | Docker 正确值 |
|--------|--------|-------------|
| Nacos 注册/配置中心 | `${my.server.addr}:8848` | `nacos:8848` |
| MySQL JDBC URL | `${my.server.addr}:3306` | `mysql:3306` |
| Redis Host | `${my.server.addr}` | `redis` |
| RabbitMQ Host | `${my.server.addr}` | `rabbitmq` |
| Elasticsearch URIs | `${my.server.addr}:9200` | `elasticsearch:9200` |
| Seata grouplist | `${my.server.addr}:8091` | `seata:8091` |
| Sentinel Dashboard | `${my.server.addr}:8080` | `sentinel:8080` |

### 1.3 解决方案

在 `docker-compose.yml` 中为每个服务注入精确的环境变量，覆盖应用内的 `my.server.addr` 推导：

```yaml
environment:
  # Nacos（保持 ALIYUN_SERVER_IP: nacos）
  ALIYUN_SERVER_IP: nacos

  # MySQL — 用 SPRING_DATASOURCE_URL 覆盖（每个模块数据库名不同）
  SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/cs_mall_pms?...

  # SSO 双数据源（admin + user）
  SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/cs_mall_ams?...
  SPRING_DATASOURCE_USER_JDBC_URL: jdbc:mysql://mysql:3306/cs_mall_ums?...

  # Redis
  SPRING_DATA_REDIS_HOST: redis

  # RabbitMQ
  SPRING_RABBITMQ_HOST: rabbitmq

  # Elasticsearch
  SPRING_ELASTICSEARCH_URIS: http://elasticsearch:9200

  # Seata
  SEATA_SERVICE_GROUPLIST_DEFAULT: seata:8091

  # Sentinel
  SPRING_CLOUD_SENTINEL_TRANSPORT_DASHBOARD: sentinel:8080
```

### 1.4 教训

**不要在配置文件中用一个变量指向多个不同服务。** 每个中间件的地址应当独立配置。更好的做法是在 `application-prod.yml` 中拆分：

```yaml
# 不推荐
my.server.addr: 127.0.0.1  # 万能变量

# 推荐
nacos.server-addr: 127.0.0.1
mysql.host: 127.0.0.1
redis.host: 127.0.0.1
# ... 各自独立
```

## 二、Seata 启动时序问题

### 2.1 现象

mall-product、mall-order、mall-search、mall-seckill、mall-front 五个服务反复崩溃重启，日志显示：

```
org.apache.seata.common.exception.FrameworkException: can not connect to [172.18.0.x:8091]
```

### 2.2 根因

Seata Server 启动需要约 90 秒，而依赖它的 5 个服务启动只需约 30 秒。服务在 Seata 就绪之前就尝试连接 → 连接失败 → Spring Boot 启动中断 → 容器退出。

每次 `docker compose down && up` 重建网络后，容器 IP 会变化，Seata 连接地址也变。

### 2.3 解决方案

1. **给 Seata 添加健康检查 + 启动等待**：

```yaml
healthcheck:
  test: ["CMD-SHELL", "wget -qO- http://localhost:7091 || exit 1"]
  interval: 15s
  timeout: 5s
  retries: 20
  start_period: 90s  # 等待 Seata 完全启动
```

2. **依赖服务等 Seata 就绪**：

```yaml
depends_on:
  seata: { condition: service_healthy }
```

3. **所有服务添加自动重启**：

```yaml
restart: on-failure
```

## 三、Seata AT 模式要求 undo_log 表

### 3.1 现象

```
Caused by: java.lang.IllegalStateException: in AT mode, undo_log table not exist
```

### 3.2 根因

Seata AT 模式在每个参与分布式事务的数据库中需要一个 `undo_log` 表来记录回滚信息。项目中只有 `cs_mall_seckill` 有 Flyway 自动创建 `undo_log`，但 `cs_mall_pms`、`cs_mall_oms` 没有。

### 3.3 解决方案

在 MySQL 初始化脚本中为所有使用 Seata 的数据库添加 `undo_log` 表：

```sql
CREATE TABLE IF NOT EXISTS cs_mall_pms.undo_log (...);
CREATE TABLE IF NOT EXISTS cs_mall_oms.undo_log (...);
CREATE TABLE IF NOT EXISTS cs_mall_seckill.undo_log (...);
```

应直接写入 `mysql-init.sql` 中，确保首次部署就有。

## 四、Elasticsearch 缺少 IK 分词器

### 4.1 现象

```
[mapper_parsing_exception] Failed to parse mapping: analyzer [ik_max_word] has not been configured in mappings
```

### 4.2 根因

商品搜索和 AI 模块使用 IK 中文分词器，但 Docker 镜像 `elasticsearch:8.6.0` 默认不带 IK 插件。

### 4.3 解决方案

```bash
docker exec csmall-es elasticsearch-plugin install -b \
  https://get.infini.cloud/elasticsearch/analysis-ik/8.6.0
docker restart csmall-es
```

## 五、数据库初始化时序：Flyway vs 测试数据

### 5.1 现象

```
ERROR 1146 (42S02): Table 'cs_mall_pms.pms_category' doesn't exist
```

### 5.2 根因

`init-test-data.sql` 中使用了 `TRUNCATE TABLE` 和 `INSERT INTO`，但这些表由 Flyway 在**微服务首次启动时**自动创建。如果在所有服务完全启动之前就导入测试数据，Flyway 还没建表，SQL 执行失败。

### 5.3 解决方案

**正确顺序**：
1. MySQL 容器启动 → `mysql-init.sql` 创建空数据库
2. 微服务全部启动 → 各模块 Flyway 自动建表
3. 确认所有服务注册到 Nacos
4. **最后**导入测试数据

## 六、Docker 网络与镜像拉取

### 6.1 Docker Hub 拉取超时

国内网络访问 `docker.io` 不稳定。配置阿里云镜像加速：

```bash
sudo tee /etc/docker/daemon.json << 'EOF'
{
  "registry-mirrors": [
    "https://dockerpull.org",
    "https://docker.1ms.run"
  ]
}
EOF
sudo systemctl restart docker
```

### 6.2 镜像源限流

免费镜像源有请求频率限制，会出现 `429 Too Many Requests`。首次拉取需要耐心等待，或更换镜像源重试。

### 6.3 Seata 官方镜像不可用

`seataio/seata-server:2.1.0` 在某些镜像源中不存在。替换为：

```
apache/seata-server:2.1.0
```

## 七、nginx 配置问题

### 7.1 服务名不匹配

原始 nginx.conf 使用 `gateway:10087`，但 Docker Compose 的服务名是 `mall-gateway`。

```nginx
# 错误
proxy_pass http://gateway:10087;

# 正确
proxy_pass http://mall-gateway:10087;
```

### 7.2 SSE 流式路径缓冲

AI 导购 SSE 流式接口需要 nginx 关闭缓冲：

```nginx
location = /ai/chat/stream {
    proxy_pass http://mall-gateway:10087;
    proxy_buffering off;      # 关键！
    proxy_cache off;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
}
```

### 7.3 API 路径覆盖不完整

旧 nginx.conf 只有 `/api/` 和 `/upload/` 两个代理，但前端实际使用 12 个不同路径前缀：

```
/admin/ /sso/ /oms/ /front/ /seckill/ /ai/ /search/ /user/ /ums/ /pms/ /resource/ /upload/
```

修复：使用正则一次性覆盖全部：

```nginx
location ~ ^/(admin|sso|oms|front|seckill|ai|search|user|ums|pms|resource)/ {
    proxy_pass http://mall-gateway:10087;
}
```

## 八、CORS 跨域 IP 过期

### 8.1 现象

浏览器登录成功但页面数据加载失败，浏览器控制台报 CORS 错误。

### 8.2 根因

`mall-gateway-server` 的 `CorsConfig.java` 中硬编码了旧服务器 IP `8.156.85.160`，新服务器 IP 是 `8.156.77.197`，CORS 校验不通过。

### 8.3 解决方案

更新为当前服务器 IP，并删除已废弃的域名（`coolshark-shop.cn`）：

```java
config.addAllowedOrigin("http://8.156.77.197");
```

## 九、环境变量命名错误

### 9.1 `RESOURCE_HOST` vs `CUSTOM_FILE_UPLOAD_RESOURCE_HOST`

docker-compose 中使用了 `RESOURCE_HOST` 试图覆盖应用内的 `custom.file-upload.resource-host`。

Spring Boot 对**自定义属性**不会做 relaxed binding。环境变量必须用全大写、下划线分隔的完整路径才能覆盖自定义属性：

```bash
# 无效
RESOURCE_HOST=http://8.156.77.197/

# 有效
CUSTOM_FILE_UPLOAD_RESOURCE_HOST=http://8.156.77.197/
```

### 9.2 教训

Spring Boot 的 relaxed binding 只对标准属性生效（`spring.datasource.url` → `SPRING_DATASOURCE_URL`）。自定义属性必须用完整的点号路径转大写加下划线。

## 十、SSO 双数据源

### 10.1 现象

SSO 登录返回 `state:500, message:null`。

### 10.2 根因

SSO 模块有两个数据源：`spring.datasource.admin`（cs_mall_ams，管理员认证）和 `spring.datasource.user`（cs_mall_ums，用户认证）。我们只覆盖了主数据源 `SPRING_DATASOURCE_URL`，第二个数据源仍然使用 `${my.server.addr}`。

### 10.3 解决方案

添加第二个数据源的环境变量覆盖：

```yaml
SPRING_DATASOURCE_USER_JDBC_URL: jdbc:mysql://mysql:3306/cs_mall_ums?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai
```

## 十一、MySQL 字符编码导致中文乱码

### 11.1 现象

浏览器显示商品名称为乱码：`HUAWEI Mate 60 Pro æ‰‹æœº`

### 11.2 根因

通过 cat 管道导入 SQL 时，MySQL 客户端未指定 UTF-8 字符集，中文数据以错误编码存储。

### 11.3 解决方案

```bash
docker exec -i csmall-mysql mysql -uroot -p${MYSQL_ROOT_PASSWORD:-root} \
  --default-character-set=utf8mb4 < /tmp/init-test-data.sql
```

同时确保数据库创建时使用 `DEFAULT CHARSET utf8mb4`。

## 十二、RabbitMQ 4.x 健康检查命令变更

### 12.1 现象

RabbitMQ 容器始终显示 `(unhealthy)`。

### 12.2 根因

RabbitMQ 4.x 将 `rabbitmq-diagnostics` 命令替换为 `rabbitmqctl`，旧健康检查命令失败。

### 12.3 解决方案

```yaml
healthcheck:
  test: ["CMD", "rabbitmqctl", "status"]  # 4.x 兼容
```

## 十三、POM XML 批量编辑导致格式损坏

### 13.1 现象

给 11 个模块添加 actuator 依赖时，使用 `sed` 和 `awk` 批量修改 POM，导致 XML 嵌套错误（`Malformed POM: Unrecognised tag: 'dependency'`）。

### 13.2 根因

Windows 下的 `sed` 和 `awk` 对 XML 的正则匹配不精确，将 `<dependency>` 标签错误插入到已有 `<dependency>` 块内部。

### 13.3 解决方案

用 Python 精确解析和替换，避免正则操作 XML 的风险。

## 部署经验总结

1. **一个变量不要指向多个服务**：`my.server.addr` 是整个部署过程中最大的坑
2. **Docker 健康检查是必需的**：Seata 启动慢导致连锁故障，健康检查 + `depends_on` 是正确解法
3. **首次部署要分阶段**：先中间件 → 等就绪 → 再微服务 → 等 Flyway → 再灌数据
4. **环境变量命名要精确**：自定义属性不能用简写，必须全路径大写
5. **本地改好再上传**：在服务器上用 sed 改文件极易出错，优先本地 Python 编辑 → scp 上传
6. **首次部署需要手动步骤**：IK 分词器安装、undo_log 建表、测试数据导入都是当前需要手动操作的，后续应自动化
