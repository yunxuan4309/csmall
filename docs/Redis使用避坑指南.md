# Redis 使用避坑指南

> **创建日期**: 2026-08-21
> **适用对象**: 实习生 / 经验不足的后端开发者;面试复习
> **关联**: `docs/评估报告/TODO文件.md`（R1~R4、R8 条目）、`docs/项目上下文文档.md` §6.6、`docs/归档/Redis配置加固与哨兵模式方案.md`
> **核心思想**: Redis 性能强，但**不能随便造**——设计前不仅要考虑 MySQL，也要考虑 Redis 的数据结构、容量、持久化与运维边界。

---

## 一、先建立三个核心认知（为什么 Redis 容易踩坑）

1. **单线程执行模型**：Redis 命令执行是单线程的（6.0+ 的 I/O 线程只负责网络读写，不改变执行模型）。**任何 O(N) 操作都会阻塞所有其他命令** → 大 key、KEYS、慢脚本是"定时炸弹"。
2. **Redis 是缓存/加速器，不是万能存储**：数据可丢（需持久化）、内存有限（需上限）、非关系型（无事务回滚语义）。设计时默认"Redis 里的数据随时可能没有"。
3. **运维三件套不能省**：持久化（AOF/RDB）+ 认证（密码）+ 内存上限（maxmemory）。少了任何一件，上线后都会以事故形式补课。

## 二、错误清单（按类别）

### 2.1 数据结构与内存

| # | 错误 | 后果 | 正确做法 | 本项目状态 |
|---|------|------|---------|-----------|
| 1 | 什么都存 String，不用 Hash/Set/ZSet | 内存浪费、读写 O(N)、丢原子能力 | 对象→Hash、标签→Set、排行榜→ZSet、队列→List | ✅ 结构选型合理 |
| 2 | 不设 TTL | 键无限堆积，内存打满 | 所有缓存键必须有 TTL；仅业务语义上需要永久的键（如购买标记 reseckill）才豁免 | ✅ 基本都有 TTL |
| 3 | Java 默认序列化（`RedisTemplate` 默认 valueSerializer=java） | 体积膨胀 3~5 倍、跨语言不可读、出现 `\xAC\xED` 乱码 | 统一 JSON 序列化（`GenericJackson2JsonRedisSerializer`） | ⚠️ 项目 value 用 java 序列化，数据量上来后可优化（见 R8） |
| 4 | 把大文件/日志塞 Redis | 单键超大、网络阻塞 | 文件/日志走文件系统/对象存储，Redis 只放结构化数据 | ✅ 未发生 |
| 5 | 数值当字符串存 | 丢 `incr/decr` 原子能力 | 计数场景必须数值型 + 原子命令 | ✅ 库存用数值型 |

### 2.2 并发与一致性（最容易翻车）

| # | 错误 | 后果 | 正确做法 | 本项目状态 |
|---|------|------|---------|-----------|
| 6 | `get` + `set` 当成原子操作（读改写竞态） | 并发下丢失更新 | `incr` / `setnx` / Lua / `WATCH` | ✅ 未使用 |
| 7 | 分布式锁只加锁不设过期（或 `setnx` 和 `expire` 分两步） | **死锁**，锁永不过期 | 一条命令：`SET key val NX EX 30` | ✅ `setIfAbsent("1",1,MINUTES)` 标准姿势 |
| 8 | 释放锁删了别人的锁 | 误删他人锁 → 并发失控 | value 存唯一标识，删除前比对（Lua 原子完成） | ✅ 秒杀锁语义独立 |
| 9 | 缓存穿透/击穿/雪崩不防 | 高并发打穿 DB | 穿透→空值缓存/布隆；击穿→互斥锁；雪崩→TTL 随机抖动 | ✅ 秒杀有布隆（Set 替代）+ 空值处理 |
| 10 | 双写一致想当然："更新库就更新缓存" | 并发下数据不一致 | 删缓存而非更新缓存 + 处理删除失败/延迟双删 | ✅ 缓存只读不双写 |

### 2.3 连接与运维

| # | 错误 | 后果 | 正确做法 | 本项目状态 |
|---|------|------|---------|-----------|
| 11 | 每次 `new` 连接不池化 | 连接耗尽，服务挂 | 连接池（Lettuce/Redisson 自带） | ✅ Spring Data Redis 自带 |
| 12 | 生产用 `KEYS *` / `FLUSHALL` | 阻塞数秒~数分钟 | 一律 `SCAN` 渐进式；`FLUSHALL` 加 `async` 且先备份 | ✅ 未使用 KEYS |
| 13 | 无持久化/无备份 | 重启丢 60s~15min 数据 | AOF + RDB + 定期备份 | ✅ R2 已修复（2026-09-07：AOF 开启） |
| 14 | 单机裸奔当高可用 | 进程一挂全停 | 哨兵/集群 | 🔴 已规划哨兵方案（1主1从2哨兵） |
| 15 | 不设密码 / 不设内存上限 | 内网裸奔、OOM 失控 | requirepass + maxmemory + mem_limit | ✅ R1/R3 已修复（2026-09-07） |
| 16 | 容量规划缺失 | noeviction 打满后**拒绝写入**，业务停摆 | 预估单 key 增长 + 大键巡检 | ✅ R3 已修复；R8 巡检常态化 |

### 2.4 使用姿势

| # | 错误 | 后果 | 正确做法 | 本项目状态 |
|---|------|------|---------|-----------|
| 17 | 循环里逐个 `get` | N 次网络往返，性能差 10 倍 | `mget` / pipeline | ✅ 未使用 |
| 18 | `RedisTemplate` 和 `StringRedisTemplate` 混用 | key 序列化前缀不同 → **读不到数据** | 全项目统一序列化规范，混用时明确各自 key 序列化方式 | ⚠️ 两套 template 并存，注意别混（见 §三） |
| 19 | key 命名无规范 | 冲突、难排查 | 统一前缀 + 业务分层 | ✅ `PrefixConfiguration` 统一管理 |
| 20 | 误以为 `MULTI/EXEC` 有回滚 | 事务里一条失败其余照常执行 | 强原子用 Lua（见 TODO #10） | ✅ 未使用事务 |

## 三、本项目 Redis 现状对照

### 3.1 做对的地方（面试可讲 ✅）

- **分布式锁姿势正确**：`setIfAbsent(key, "1", 1, MINUTES)`——加锁 + 过期一条命令，防死锁
- **key 统一命名**：`PrefixConfiguration` 管理 `mall:seckill:xxx` 前缀，避免冲突、方便排查
- **防超卖**：库存用数值型 + `DECR` 原子扣减，`leftStock < 0` 判断 + 失败补偿（`increment` 回补）
- **秒杀链路"Redis 闸门 + MQ 管道"**：Redis 预扣库存 + 标记，RabbitMQ 异步落库削峰
- **当前无大键**：21 键、最大 9.7KB、慢日志为空（2026-08-21 实测）

### 3.2 加固项（✅ 2026-09-07 已全部修复，原 🔴 记录转已完成）

| 项 | 问题 | 修复状态（2026-09-07） |
|----|------|------|
| R1 | 无密码 + 密码链路脱节 | ✅ requirepass 开启 + 11 微服务注入 `SPRING_DATA_REDIS_PASSWORD`，6379 收窄 127.0.0.1 |
| R2 | AOF 关闭，重启丢数据 | ✅ `appendonly yes` + `appendfsync everysec`（执行踩坑见评估报告《TODO第一批实现与原理》§9.2）|
| R3 | 无 maxmemory + noeviction | ✅ `maxmemory 256mb` + `volatile-lru` |
| R4 | 无自定义 redis.conf | ✅ conf 挂载容器（不加 :ro），配置持久化 |
| R8 | 大键巡检（当前无，增长后执行） | 🟡 常态化巡检项（月检 + 大版本前），未到期 |

### 3.3 序列化注意点（⚠️ 潜在坑）

项目同时存在 `RedisTemplate`（value=Java 序列化，用于 SPU 缓存）和 `StringRedisTemplate`（库存/随机码/标记）。**两者 key 都用 String 序列化但 value 不同**——新增代码时务必：
- 读写同一业务 key 时保持同一 template 类型
- 想跨服务/跨语言读取 Java 序列化的值会乱码，未来可整体迁移 JSON 序列化（R8 已记）

## 四、面试讲解要点（把"避坑"讲成"深度"）

1. **分布式锁**："SETNX + 过期 + 唯一 value 释放"，一条命令原子完成，防死锁防误删
2. **缓存三兄弟**：穿透（查无数据打 DB）→ 空值/布隆；击穿（热点 key 过期）→ 互斥锁；雪崩（大量同时过期）→ TTL 抖动
3. **一致性**：缓存只读，写库后删缓存；Redis 事务是弱事务（无回滚），强原子用 Lua
4. **演进路线**：单机（当前）→ 哨兵（已定稿方案）→ 集群（注意同 slot 限制）；大键/慢日志/持久化巡检常态化
5. **为什么 Redis 不能随便造**：单线程模型下，O(N) 操作、大 key、KEYS、长脚本都会阻塞全站——设计前先想数据结构、容量、TTL

## 五、开发前 / 上线前自检清单

- [ ] 每个 key 是否有明确的 TTL？(永久键是否业务上有意为之？)
- [ ] 单 key 容量是否有上限？(会不会长成"大 key"？)
- [ ] 是否用了正确的数据结构？(String/Hash/Set/ZSet/List)
- [ ] 多命令是否需要原子？(用 incr/setnx/Lua,不要 get+set)
- [ ] 锁是否一条命令加锁+过期？释放是否校验唯一 value？
- [ ] 是否只用一个 RedisTemplate 规范？序列化方式是否统一？
- [ ] 是否有循环内逐条访问 Redis？(改 mget/pipeline)
- [ ] 生产环境是否禁用了 KEYS/FLUSHALL？
- [ ] 持久化、密码、内存上限是否配置？(AOF/requirepass/maxmemory)
- [ ] 是否有巡检节奏？(--bigkeys / SLOWLOG / INFO memory)
