## 一、项目概述

### 1.1 项目背景

CoolShark（酷鲨）是一个基于 Spring Cloud Alibaba 的微服务电商平台，面向 C 端用户提供商品浏览、搜索、购物车、下单、支付、秒杀等完整购物流程，同时提供后台管理系统进行商品、订单、用户管理。此外集成了 AI 智能导购模块，支持自然语言商品问答、多商品对比和多轮对话导购。

**当前状态**: Docker 容器化部署完成，21 个容器（新增 SkyWalking OAP + UI）稳定运行于阿里云 ECS（**老机** 4C16G，Ubuntu 24.04，公网 IP: 8.156.77.197）。

**2026-09-09 新增：第二台服务器（新机 `csmall-node2`，2C8G，公网 47.109.70.197 / 私网 172.29.193.240）** —— 与老机**同 VPC 同安全组**（内网互通实测 0.43ms），用于**跨机集群实验**：Redis 从 + 3 哨兵、秒杀副本(10017)、造数/压测执行位。属 TODO 第三批 #4/#9/#14-P2/#42 范畴，方案见 [[跨机集群方案-讨论纪要-2026-09-09]]。⚠️ 前置：老机 MySQL(3306)/Redis(6379) 绑 `127.0.0.1`（第一批安全加固）→ 跨机不可达，需端口放行改造。

> ✅ **2026-09-09 晚：跨机集群已建成（阶段 0~5 完成）**——老机 = **Redis 主(6379)** + **秒杀实例1(10007)**；新机 = **Redis 从(6380) + 3 哨兵(26379-26381, quorum=2)** + **秒杀实例2(10017)**；端口放行已完成（3306/6379/20880/20881 绑私网 IP，无需改安全组）。实测：**故障转移选主 6.1s / 客户端 9.1s 自愈 / 数据零丢失**；**负载分布 60 请求精确 30:30**；**定时任务锁互斥验证通过**；停实例剔除通过（⚠️ 16s 失败窗口见 TODO #53）。**#14-P2 亦已完成**（`min-replicas-to-write 1`，运行时 09-09 + conf 落盘 09-10）→ **跨机集群主线 100% 收口**。详见 [[TODO已完成-明细-2026-09-12]] §十三、[[TODO第三批实现与原理]] §五/§六。

## 六、关键设计决策

### 6.1 架构决策

1. **RPC 选型**: 使用 Apache Dubbo 3.3.2 替代 OpenFeign，性能更优，支持多种序列化协议
2. **分布式事务**: Seata AT 模式，`@GlobalTransactional` 注解标注核心业务流程
3. **ID 生成**: MyBatis-Plus `IdWorker`（雪花算法），自定义 XML INSERT 需手动调用 `IdWorker.getId()`（已弃用 mall-leaf）
4. **认证方式**: SSO 统一登录 + JWT Token + Spring Security 6.x，无状态设计
5. **API 文档**: Knife4j (OpenAPI 3)，生产环境 `knife4j.production: true` 屏蔽
6. **Long 精度**: 全局 Jackson 配置 `Long → String` 序列化，避免 JS 精度丢失（雪花 ID 为 19 位）
7. **Seata Dubbo Filter**: 自定义实现替代官方 bug 版本（`dubbo-filter-seata:1.0.2` 存在 branchType NPE）
8. **连接池**: 混合使用——**mall-resource 用 HikariCP**（曾因 Druid `max-wait=0` 无限等待导致上传线程挂死，2026-06 切换）；**其余 6 个服务（product/order/seckill/ums/ams/sso）仍为 Druid 1.2.24**（prod yml 显式 `type: DruidDataSource`，稳定运行）。统一到 HikariCP 为长期规划（需全量回归，暂缓）。详见 `docs/评估报告/TODO文件.md` R5

### 6.2 秒杀架构

- **库存预热**: Redis 预扣库存，减少数据库压力
- **异步落库**: RabbitMQ 消息队列异步创建订单，实现削峰
- **防缓存穿透**: 当前本地开发用 Redis Set 替代布隆过滤器（Windows Redis 不支持 RedisBloom），生产环境需切换
- **防超卖**: SQL 扣减库存加 `AND seckill_stock >= #{quantity}` 条件
- **消息积压保护**: RabbitMQ JSON 序列化替代 Java 序列化，`basicNack` 失败后抛出 RuntimeException 触发事务回滚

### 6.3 图片 URL 策略

- **存储**: 数据库只存纯相对路径（如 `spu_1_1.jpg`），不存完整 URL
- **拼接**: 服务层 `ImageUrlPrefixHelper`（`mall-product-webapi/.../utils/`）根据环境 `resource-host` 配置动态拼完整 URL
- **静态服务**: 生产环境 Nginx 直接从 `/data/csmall-upload/` 提供图片（`~* \.(jpg|png|gif|webp)$`），不经过 Java 服务栈
- **已上传图片兼容**: 工具类自动跳过已含 `http://` 前缀的路径

### 6.4 AI 智能导购架构

> **双路径（2026-09-11 起）**：生产走 **Agent 链路**（`AI_AGENT_ENABLED=true`，Function Calling）；**固定流水线**退化为**降级兜底**。两者共用同一套 ES 检索与 SSE 契约。

| 路径 | 触发 | 实现要点 | 定位 |
|------|------|---------|------|
| **Agent**（生产主用） | `AI_AGENT_ENABLED=true` | 模型**自己决定**查什么/查几次/何时收口（最多 `AI_AGENT_MAX_ROUNDS=3` 轮）；首轮命中商品意图关键词时 `tool_choice=required` | 主力链路 |
| **固定流水线** | 开关关闭 **或** Agent"一字未写"即失败 | 意图提取 → 查询扩展 → 多路召回 → 流式生成 | **降级兜底**（`sendStreamWithPipeline`） |

- **两级保护**：① 预算超限 → 直接 `error` 收尾；② Agent"一字未写"即失败（网络/工具异常）→ **静默降级到流水线**；**已写出内容则如实报错**，不拼接两段回答（`ChatServiceImpl.java:358-368`、`489-495`）

**工具集（3 个）**

| 工具 | 入参 | 返回给模型 | 说明 |

### 6.6 Redis 一致性策略：不使用 Redis 事务（2026-08-21 确认）

**结论**：全项目**未使用 Redis 事务（MULTI/EXEC）**。排查证据（全仓库代码检索）：无 `multi()/exec()/watch()/unwatch()/discard()`、无 `SessionCallback`、无 `executePipelined`；各模块 `RedisTemplate` 配置类（`RedisCustomConfiguration` / `RedisConfiguration`）仅配置序列化器，**未开启 `setEnableTransactionSupport(true)`**，因此 `@Transactional` 也不会驱动 Redis 事务。

**当前原子性方案**（全部为单命令原子操作）：

| 场景 | 方案 | 说明 |
|------|------|------|
| 秒杀下单锁 | `setIfAbsent`（SETNX） | 防并发重复下单，1 分钟过期 |
| 秒杀库存扣减/回补 | `increment` / `decrement` | 单命令原子，`leftStock < 0` 判断防超卖 |
| 幂等控制 | `setIfAbsent` | `IdempotentAspect` |
| token 黑名单 | Set `add` / `isMember` | 各模块 `SSOFilter` |
| AI 预算日计数 | `increment` | `TokenBudgetService` |
| 秒杀随机码/购买标记/未支付标记 | `set` / `delete` | 单 key 写入 |
| **定时任务分布式锁（集群化）** | `setIfAbsent` 加锁 + **Lua CAS 释放** | `RedisLockUtils`（mall-seckill）：双实例下防 `MessageRetryTask` / `SeckillReconcileTask` 并发双跑 |

秒杀多 key 联动（orderLock / ordered / stock / reseckill）采用**"分布式锁 + 失败补偿"**保证最终一致（下单失败/库存不足时 `increment()` 回补库存 + `delete` 释放锁），而非 Redis 事务。

**定时任务分布式锁（2026-09-09 新增，#4 秒杀集群化前置）**：秒杀双实例后 `@Scheduled` 会在**两个实例同时触发**——`MessageRetryTask`（扫表重发 MQ）两实例同时 `selectPending` 会拿到同一批记录 → **重复投递**；`SeckillReconcileTask` 会重复对账（"连续同向差计数"被加倍累计）。本地锁（`synchronized`）跨不了 JVM → 用 `mall-seckill/utils/RedisLockUtils`：`SET key token NX EX ttl` 原子加锁 + TTL 兜底 + **Lua 比较 token 再删**（防误删他人锁）；锁只保证"不并发"，**正确性仍靠幂等**（`updateStatusSent`）+ DB 条件扣减 + 唯一索引兜底。
> **选型**：未用 Redisson（`mall-seckill-webapi/pom.xml` 已引 3.24.3 但**代码零使用**，属死依赖）——场景只需非阻塞互斥，而 Redisson 带来可重入/看门狗/Redlock/连接池（默认 64）与另一套哨兵配置 API；也未用 ShedLock（更贴合 `@Scheduled` 但需引依赖 + 配 provider）。演进条件见 [[TODO第三批实现与原理]] §4.7。

**⚠️ Redis 高可用局限（2026-09-09，务必知悉）**：生产 Redis 是**跨机 1 主 1 从 + 3 哨兵**（老机主 / 新机从），并已开启 `min-replicas-to-write 1`（**只开主库**）。**由此带来一个已知局限**：**新机（从库）不可用时，老机主库会拒绝所有写**（`NOREPLICAS Not enough good replicas to write.`）——读仍可用。原因：Redis 复制是异步的，主库分不清"从库真死了"（继续写安全）与"只是网络断了"（继续写会脑裂丢数据），只能一刀切选保守。**停新机做演练/维护前，先执行 `CONFIG SET min-replicas-to-write 0`，恢复后设回 1**（"演练开关"）。**这是 2 台机器下 `min-replicas-to-write` 的固有局限**（该参数的设计前提是 ≥2 个从库），真正的解法是第三个副本放第三台机器——已评估，成本不划算，故接受。完整推导/拓扑对照/面试话术见 [[TODO第三批实现与原理]] §6.9。

**未来演进预判**：
- **短期（演示阶段）**：不会引入 Redis 事务，现有"单命令原子 + 锁 + 补偿"足够
- **中期**：若秒杀需"扣库存 + 标记 + 随机码"多 key 强原子，优先使用 **Lua 脚本**（原子性、可回滚语义、单次网络往返均优于 MULTI/EXEC），而非传统事务；抢券/抽奖/资格预占等"读-改-写"场景可用 `WATCH` 乐观锁
- **注意**：若未来引入 Redis Cluster，MULTI/EXEC 与 Lua 仅支持**同 slot 的 key**，跨 key 事务/脚本受限
- **与哨兵模式的关系**：切换瞬间连接中断，任何进行中的操作（含事务/多命令/脚本）都会报错，客户端重连重试即可（非 Lua 特有）；Lua **短脚本（毫秒级）与哨兵可安全共存**，大厂（阿里云 Tair / AWS ElastiCache）普遍同时使用；仅需防范"长脚本阻塞主节点导致哨兵误判"，方案见 `docs/评估报告/TODO文件.md` #10 与 `docs/归档/Redis配置加固与哨兵模式方案.md`

### A.5 安全组配置

> **两台共用同一安全组** `sg-2vc9i0zxt8gbq18mo8ea`（2026-09-09 起）→ **同组内网互信**：VPC 内网（172.29.193.0/20）互通不限速（实测 ping 0.43ms），公网侧按下表放行。

| 端口 | 协议 | 来源 | 用途 |
|------|------|------|------|
| 22 | TCP | 0.0.0.0/0 | SSH 远程登录 |
| 80 | TCP | 0.0.0.0/0 | HTTP 前端访问 |
| 443 | TCP | 0.0.0.0/0 | HTTPS（暂未使用） |

**⭐ 边界认知（2026-09-09 修正，重要）**：**安全组是唯一的公网边界**。阿里云公网 IP 是 **NAT 映射、不在网卡上** → 发往公网 IP 的包会被 DNAT 成私网 IP 再进网卡，因此服务绑 `0.0.0.0` 还是绑私网 IP，**公网可达性完全等价**（实测 `6379/3306/10087/26379/6380` 全 blocked、仅 `:80` 通，与绑法无关）。绑定地址只决定"本地哪些地址接受连接"，属**纵深防御**而非边界。分层模型：**SG（边界）→ bind/ports（监听面）→ 认证（身份）→ TLS（传输）**，详见 [[TODO第三批实现与原理]] §5.6⑥。

**跨机内网实测（2026-09-09，新机 → 老机）**：22/80/8848/5672/8091/9200/10007 ✅ 通；3306（MySQL）/ 6379（Redis）初测 ❌ 不通——第一批安全加固把这两个端口绑到 `127.0.0.1`（见 A.3 加固记录），**这是跨机集群的硬前置**；**阶段 2 已改绑宿主私网 IP `172.29.193.239`**（不是 `0.0.0.0`，作纵深防御）且**实测无需改安全组**（同组内网互通不受公网规则限制），详见 TODO「🚀 第三批执行清单」阶段 2。

### A.6 部署方式

- **Docker Compose**：`/data/csmall/docker-compose.yml` 编排 **21 个容器**（7 中间件 + 2 链路服务 + 11 微服务 + 1 前端）；`.env` 注入敏感配置；日志全部 stdout（`docker logs`）；ES 限 `-Xms512m -Xmx512m`
- **2026-09-09 起同一份 compose 还含 5 个"跨机集群成员"**（`redis-replica` / `redis-sentinel-1~3` / `mall-seckill-2`）—— **只在第二台机器 csmall-node2 上启动**；老机仍只启动原有 21 个

> 🔴 **新机（csmall-node2）上永远不要裸跑 `docker compose up -d`**
> 两机共用同一份 compose（文件里既有老机 21 个、也有新机 5 个）→ **裸跑（不带服务名）会把老机 21 个服务在新机一起拉起**：无数据无配置、必然失败或半残，且可能抢端口 / 注册到同一 Nacos 造成实例混乱。
> **正确用法（必须带服务名）**：新机 `docker compose up -d redis-replica redis-sentinel-1 redis-sentinel-2 redis-sentinel-3`、`docker compose up -d --no-build mall-seckill-2`；老机 `docker compose up -d mysql redis nacos mall-seckill ...`。**排查/重启单个服务同理**。详见 [[跨机集群实施执行清单-2026-09-09]] §四·五。

> 🧾 **下发文件必须校验哈希**：跨机下发（compose / 配置 / jar）经 `仓库 → scp → /tmp → sudo cp → /data/csmall` **4 跳**，任一跳可能**静默改字节**（CRLF↔LF、BOM、截断）→ 纪律：**本地算 md5 → 落位后 `md5sum` 比对，一致才继续**（哈希是内容指纹，把"仓库为事实来源"变成**可验证断言**）。原理与 MD5 局限（只防意外、不防篡改）见 [[跨机集群实施执行清单-2026-09-09]] §十二；凭据文件（`.env`）只查行数与权限、**连哈希也不对外报**。

> 🔴 **容器 restart 策略：重启后老机 20/21、新机 5/5 都不会自动恢复**（TODO #51）
> 实测：老机 **14 `no` + 6 `on-failure` + 1 `unless-stopped`**；新机 5 个全 `on-failure`。**Docker 官方文档核实**：`on-failure` **不扛 daemon 重启**，只有 `unless-stopped` 能 → 老机仅 `csmall-resource` 会自己回来，新机 5/5 全不回。⚠️ **新机不恢复的连锁**：Redis 从 + 3 哨兵消失 → 老机主库因 `min-replicas-to-write 1` **拒绝所有写**（秒杀/登录全挂），且哨兵全灭无法故障转移。
> **因此**：① 无窗口**不要重启任一机器的 Docker**；② 恢复 = 逐个 `docker compose up -d <服务名>`（**永远不要裸跑**，见上方红线）；③ 根治 = compose 全量改 `restart: unless-stopped`（两台共 25 个）并逐个 recreate。
